The contract is the task lifecycle

The schema matters, but the state machine is what a client has to code against. Eight states, four of them terminal.

In flight the task id persists across every interaction
SUBMITTED
accepted, not started
→
WORKING
peer is executing
Interrupted, not failed the client action is the whole integration
TASK_STATE_INPUT_REQUIRED
needs more information, is pausing
Client: attach the missing field, send another message on the same taskId.
TASK_STATE_AUTH_REQUIRED
needs credentials before it can continue
Client: refresh the credential out of band, then continue. Do not resend as new work.
either state resumes the same task, it does not start a second one
Terminal (4) a task ends in exactly one of these
COMPLETED
read artifacts, validate against the output schema
FAILED
surface the reason code, do not blind retry
REJECTED
surface the reason code, do not blind retry
CANCELED
record the cancellation in your own audit trail

A client that only handles completed and failed abandons work that was sitting there waiting for one clarification. The task looks like a hang in its own logs while the peer's logs show it politely waiting. Messages carry a required messageId, an optional contextId that groups related tasks into one conversation, and an optional taskId.
