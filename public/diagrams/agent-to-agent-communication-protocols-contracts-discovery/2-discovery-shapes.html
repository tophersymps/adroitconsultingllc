Discovery: three shapes, three security postures

The client has to find the agent and learn what it does before it sends anything. How it finds the Agent Card is an architecture decision, not a detail.

Well-known path https://{agent-server-domain}/.well-known/agent-card.json RFC 8615 convention
Well-known URI
Default for public agents
How it works
Client knows the domain, fetches the card at the fixed path. No out-of-band coordination.
What it buys
Simple, standards-based, domain-controlled.
What it costs
The endpoint needs authentication if the card describes anything sensitive.
Curated registry
Governance and search
How it works
A central service holds cards, clients query by skill or tag.
What it buys
Capability search, governance, and selective disclosure: the registry returns different cards depending on who asks.
What it costs
The specification prescribes no registry API, so every registry you meet is proprietary.
Direct configuration
Tightly coupled systems
How it works
The client is handed the card URL or its contents by config.
What it buys
Fine for tightly coupled systems and development.
What it costs
Useless for dynamic discovery, and every capability change needs a client redeploy.
Cards change rarely, so the spec leans on ordinary HTTP caching
Servers send Cache-Control and an ETag. Clients revalidate with If-None-Match instead of refetching. That is a contract problem the first time a stale cached card tells your client that a retired skill still exists.
