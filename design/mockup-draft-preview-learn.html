Data Cloud Identity Resolution in OmniStudio

~18 min readDraft

Identity resolution is where Data Cloud earns its keep — and where most OmniStudio implementations quietly under-deliver. This lesson walks the unified profile pattern: how to map source individuals, dedupe on golden keys, and expose the resolved profile inside an OmniScript without breaking the page.

Golden keys vs. matching rules

A golden key is a survivorship decision: when two records look like the same person, which attributes win? Data Cloud gives you both deterministic keys and fuzzy matching. The mistake is treating them as alternatives — you want deterministic first, fuzzy as the fallback, never the other way around.

"Identity resolution is a series of small, defensible decisions — not a machine-learning miracle." — Adroit delivery notes, 2026

The three-source merge

Your typical OmniStudio project has three sources of truth: the CRM person record, the marketing engagement profile, and the commerce customer. Each resolves differently:

  • CRM person — deterministic on email, survivorship to the most recent update
  • Marketing profile — fuzzy on name + postal, confidence threshold ≥ 0.85
  • Commerce customer — keyed on external ID, never merged across tenants
// example: resolution strategy block
resolution:
  sources: [crm_person, marketing_profile, commerce_customer]
  order: deterministic, fuzzy
  golden_key: person_id
  survivorship: most_recent_update

Exposing the resolved profile

Once the profile resolves, the OmniScript fetches it via a Data Cloud data action — and here's the trap: the resolved profile is read-only by default. If your script mutates it, you've broken the survivorship contract. Read it, display it, and write updates back to the source, not the resolution.
