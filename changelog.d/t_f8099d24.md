### Raise the auth mint budget so the cold build/ISR mint completes (t_f8099d24)

**What** - One value plus one test file. `MINT_BUDGET_MS` in `src/lib/db/server.ts` goes from
`800` to `3000` and is now `export`ed so a test can pin it; the doc comment above it records the
measured cold-mint evidence and why the old value was wrong. `src/lib/db/server.budget.test.ts`
gains a `describe("mint budget floor (t_f8099d24)")` block (floor `>= 2500`, ceiling `<= 5000` so
the budget stays a bound) and derives its existing wall-clock bounds from `MINT_BUDGET_MS` instead
of hard-coding 800 ms, so the assertions stay about ONE shared per-request budget rather than about
a particular number. Nothing else changed: the cooldown (`MINT_COOLDOWN_MS`), the negative cache,
the single-flight in `anonymous-token.ts` and the stale-while-error behaviour are untouched.

**Why** - The mint budget is a `AbortSignal.timeout` on the FIRST mint of a process. `800` ms was
chosen from a WARM local measurement (108 ms, 20/20 under budget) and read as "any healthy mint",
but a process's first mint is a COLD connection and in Vercel's build environment it does not answer
inside 800 ms. Production build `dpl_ChFZJ95` logged the first `[db] token unavailable` about 800 ms
after the static-render phase started (the budget firing, not an endpoint error), plus
`/atlas build warning: ... Publishing the graceful empty hub`, and served `/atlas` with 0 courses.
`/atlas` is `force-static` + `revalidate = 3600`, so the empty render was baked into the CDN-cached
hub, and because every revalidation runs in a fresh lambda whose first mint is cold again, the hub
re-baked itself empty every hour and never healed. The endpoint was never unhealthy, the budget was.
The budget only bounds a cache-MISS mint (`anonymous-token.ts` caches the anonymous JWT
process-wide, the session and `/get-session` results are per-request `cache()`d), so a warm mint
still returns in about 110 ms and pays none of this.

**Known Issues** - Two acceptance checks need the deploy and cannot be observed from this worktree.
"The deployed `/atlas` renders series cards" needs the merge and the Vercel production deploy. "The
ISR re-render does not re-bake an empty page after the first revalidate window" needs an hour of
production traffic after that deploy. This worktree also cannot reproduce the cold mint itself: the
same mint answers in 75-150 ms here even on a brand-new connection, which is exactly why the
regression survived local verification twice. The Vercel preview build for this branch is the
environment that can, and its build log is checked before merge. `3000` ms is the top of the range
proposed in the card because the cold-mint cost is only bounded as "more than 800 ms", never measured
exactly; if a production build still degrades, the same log line will say so and the value needs to
go up again, not the classification.
