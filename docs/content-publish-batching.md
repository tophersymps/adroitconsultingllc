# Content publish batching (content-queue)

Content publishes used to push straight to `main`, so every published article or lesson was its own
production deployment. That is why a busy day could rack up dozens of builds.

## How it works now

`content-worktree-publish.sh` has two publish modes:

- `publish ...` pushes straight to `main`. One publish, one deployment. Used by anything that must go
  live immediately.
- `queue ...` commits to the `content-queue` holding branch instead.

A flusher cron merges `content-queue` into `main` three times a day, so any number of publishes in a
window costs a single deployment.

## The generated registry

`src/data/learn.ts` is regenerated by every lesson publisher. If each queued commit carried it, the
queue would conflict on it on every flush, which is the same failure mode that made `CHANGELOG.md`
produce 50 resolution merges on 2026-10-23.

So `queue` excludes it, and `flush` rebuilds it once from the merged content files with
`node scripts/build-learn.js`. The registry still ends up correct on `main`; it just gets written once
per flush instead of once per publish.

## Operating it

```
content-worktree-publish.sh depth    # commits waiting on the queue (0 = healthy)
content-worktree-publish.sh flush    # merge now; prints nothing when empty
```

`flush` fails loudly and leaves the queue intact if the merge conflicts, if `build-learn.js` errors,
or if the push is rejected. It never force-pushes and never discards queued work.
