Every interactive component you have built sits on top of a layer you probably never tested: the keyboard interface. Tab moves focus to a control, arrow keys move it between siblings inside a widget, Enter and Space activate, Escape closes. That is not a nice-to-have detail in a menu or a date picker. It is the contract underneath every drop-down, every combobox, every dialog your design system ships.

The problem is that this contract is invisible to most of the people who build it. A mouse user never sees focus move, so a design team can ship a gorgeous menu that is completely unusable with a keyboard and never notice. The numbers say this is the norm, not the exception. The 2026 WebAIM Million, an automated audit of the top one million home pages, found that 95.9% of them had detectable WCAG 2 A/AA failures, up from 94.8% in 2025[^1]. That was the first year in a decade the web got measurably less accessible, reversing six years of small improvements, and the report names complexity as a likely driver: the average page now carries 1,437 elements and over 133 ARIA attributes, up 27% in a single year[^1]. More widgets, more custom components, more code that needs manual keyboard support, and a testing habit that does not cover it.

This article is the practical side of that. Not a compliance lecture, but the actual rules, the algorithms, and the test loop. What does WCAG 2.2 demand of your focus handling? How does roving tabindex really work, and when should you use it instead of a simple focus move? Why does focus disappear when a dialog closes, and what do you do about it? By the end you can audit a component, fix the common failures, and put a keyboard test into your workflow that catches regressions before a client does.

## Why this is a design-engineering problem, not a screen-reader problem

The most common misconception is that keyboard support only matters to blind users. Not true. Keyboard navigation serves people with motor disabilities who cannot use a mouse, people with low vision who cannot easily track a pointer, power users who prefer keystrokes, and anyone using a switch, voice input, or external Bluetooth keyboard on mobile[^2]. The Level Access guide puts physical, motor, and visual disabilities, screen reader users, and mobile Bluetooth keyboard access in the same camp[^2].

Here is the design-engineering angle. Native HTML elements get keyboard support for free, out of the box. The plain button element and the native select handle Tab, Enter, Space, and Escape correctly because the browser provides the interaction. The moment you replace them with a custom component, that free support disappears and you have to write it back[^9]. ARIA does not add keyboard behavior; it only announces semantics. The APG guidance states this bluntly: a div given role equal to button is a promise to the user that you also wrote the JavaScript for the keyboard interactions a button provides[^9]. A role without the behavior is a broken promise that is invisible to everyone except the person stuck inside it.

That is why this lands in design engineering. Every custom menu, listbox, tree, slider, and dialog you have in a component library is a place where keyboard support was either written deliberately or silently dropped. And because the existing published content on accessibility testing (see the separate article on automated testing) shows that rule engines catch only a subset of these failures, the manual keyboard pass has to be part of the stack[^1].

## The WCAG 2.2 rulebook for focus handling

WCAG 2.2 gives you a small set of criteria that together pin down almost everything that matters. You do not need to memorize the whole spec. The keyboard-relevant ones form a complete contract[^2]:

- **2.1.1 Keyboard (Level A).** Everything operable by mouse must be operable by keyboard, with no timing requirement that traps a user.
- **2.1.2 No Keyboard Trap (Level A).** If you can Tab into something, you have to be able to Tab or Escape out of it. Dialogs and embedded content are the usual culprits.
- **2.4.3 Focus Order (Level A).** Focusable components receive focus in an order that preserves meaning and operability[^3]. Where the automated testing layers fit alongside a manual keyboard pass is covered in our [accessibility testing guide](/field-notes/accessibility-testing-layers-ci-2026).
- **2.4.7 Focus Visible (Level AA).** At least one mode of operation keeps the focus indicator visible, for as long as it has focus[^4].
- **2.4.11 Focus Not Obscured (Minimum, Level AA, new in 2.2).** When something receives keyboard focus, it must not be entirely hidden by author-created content, meaning sticky footers, sticky headers, or non-modal dialogs that cover the focused item fail this[^5].
- **2.4.13 Focus Appearance (Level AAA, new in 2.2).** The indicator must be at least as large as a 2 CSS pixel thick perimeter of the component and change the pixels it covers by at least 3:1 contrast[^6].

You can build a defensible keyboard experience against just the A and AA set, plus treating Focus Appearance as an internal standard even if you do not claim AAA conformance. The two new 2.2 criteria matter because they close real gaps. 2.4.11 catches the sticky header that slides over the input you just tabbed to. 2.4.13 catches the 1 pixel dashed indicator nobody can see.

## What roving tabindex actually is

The trickiest part of keyboard support is the pattern called roving tabindex, and it is worth understanding precisely because it is the difference between a usable widget and a punishing one.

Consider a radio group, a tab list, a menu, or a listbox. Each widget contains several focusable items. If every item were in the tab sequence, the user would press Tab a dozen times to cross one widget, and every stop would interrupt the flow of the page. The roving tabindex pattern avoids this: only one element inside the widget is in the tab sequence at a time[^9]. Tab moves into the widget (to that one element). Arrow keys move focus between the sibling items without leaving the widget. Tab moves out again[^9].

Concretely, the algorithm is:

1. All items except the current one carry `tabindex="-1"`. The current item carries `tabindex="0"`.
2. On ArrowDown or ArrowRight, prevent the default, move to the next item, set `tabindex="0"` on it and `tabindex="-1"` on the old one, then call `.focus()` on the new item.
3. On ArrowUp or ArrowLeft, do the same in reverse.
4. Tab and Shift+Tab are not intercepted; they let focus leave the widget to the next element in the document.

That single pattern applies to menus, tab panels, listboxes, tree views, and grids[^9].

![Roving tabindex: one item carries tabindex 0 and sits in the tab sequence, arrow keys move between siblings inside the widget, and Tab or Shift+Tab moves focus out](</diagrams/keyboard-navigation-focus-management-2026/1-roving-tabindex.png>)

It is the APG-recommended approach for composite widgets, and it is much easier to maintain than positive `tabindex` values, which the APG warns against because they disrupt the natural tab sequence and are hard to reason about[^9][^3].

A common failure is treating a widget like a flat list of focusable elements. If a menu exposes every item to the Tab key, a keyboard user tabs through the whole menu to get anywhere, and a screen reader announces every stop. The roving tabindex fixes both by keeping the widget to a single tab stop and moving internally with arrows.

## Focus management around dialogs and dynamic content

The second big focus problem appears when content appears and disappears. When a modal dialog opens, focus must move into it, stay constrained to it while it is open, and return to the trigger when it closes[^10]. The 2.4.3 understanding document walks through exactly this: open a modal, set focus inside, make the rest of the page inert while it is open, and on dismiss return focus to the button or the element after it[^3].

The failure mode that trips most teams is the return. If you close a dialog and do not move focus back to the button that opened it, the browser drops focus to the body or the top of the page. The APG calls out this exact scenario: when the active element is hidden or removed, and the author does not set focus to a nearby element, browsers move focus to `body`, which is a loss of focus within the interface[^10]. The user then has to find their place again, which breaks the task. Store a reference to the trigger before opening, and `.focus()` it on close.

The same rule applies to deleting an item from a list, collapsing a section, or any interaction that removes the currently focused element: you must move focus somewhere sensible, usually to the element that follows the removed one[^10]. Leaving it to the browser is a bug, not an edge case.

For a dialog, decide on a keyboard strategy up front. The robust approaches are a true modal that traps focus with a Tab cycle and honors Escape, or for a non-modal disclosure, let Tab leave but return focus to the trigger on collapse. What never passes is a dialog that lets focus escape into the page while open (breaking 2.4.3's meaning and operability) or that traps without Escape.

![Dialog focus lifecycle: focus sits on the trigger, enters the dialog on open, stays constrained while open, and returns to the trigger on close; a dialog that closes without returning focus drops it to the body](</diagrams/keyboard-navigation-focus-management-2026/2-dialog-focus-lifecycle.png>)

## The visible indicator: size, contrast, and the modern CSS

Focus Visible (2.4.7) is Level AA: you must provide a visible indicator in at least one mode of operation[^4]. But visibility is not binary, and that is where 2.4.13 Focus Appearance sharpens the requirement. The indicator must be at least as large as a 2 CSS pixel thick perimeter of the component, and the pixels it changes must differ by at least 3:1 in contrast from the unfocused state[^6].

The 2 pixel minimum is easier to hit than it sounds. The WCAG understanding document works the example of a 90px by 30px button, whose 2 CSS pixel thick perimeter has an area of 480 square pixels.

![Focus Appearance spec: the indicator must be at least as large as a 2 pixel thick perimeter of the unfocused component, so a solid 2px outline around a 90 by 30 button meets the 480 square pixel floor while a thin inset indicator needs 3px](</diagrams/keyboard-navigation-focus-management-2026/3-focus-appearance-spec.png>)

A solid 2px outline around the component meets the requirement directly. An inset indicator needs to be thicker, about 3px, because the area check counts against the perimeter. The practical takeaway: a plain 2px outline, offset slightly with `outline-offset`, is the path of least resistance. The bigger the visual change on focus, the easier it is for someone with low vision to track[^6].

Contrast against unknown backgrounds is the subtle part. A single indicator color can pass against one background and fail against another on the same page. The WCAG technique C40 solves this with a two-color indicator: a light band and a dark band, where the two colors have a 9:1 contrast with each other. That guarantees one of the two bands always achieves the 3:1 requirement against any solid background[^7]. In CSS you can build it by combining `outline` and `box-shadow`:

```css
*:focus {
  outline: 2px #F9F9F9 solid;
  outline-offset: 0;
  box-shadow: 0 0 0 4px #193146;
}
```

That is the C40 pattern from the WCAG techniques: an inner light band and an outer dark band, each 2px, together large enough to pass and one of them always contrasting[^7].

![Two-color focus indicator: a light band and a dark band at 9:1 contrast with each other guarantee one band always carries 3:1 contrast against any solid background](</diagrams/keyboard-navigation-focus-management-2026/4-two-color-indicator.png>)

## The modern switch: `:focus-visible`

There is one CSS tool that makes all of this dramatically easier, and it deserves its own paragraph because it eliminates the most common tension in focus styling. The tension is this: designers do not want a focus ring on every mouse click, because it reads as noise. But keyboard users need it every time. `:focus-visible` resolves the tension by applying focus styles only when the focus was given in a way that needs an indicator, which for the major browsers means keyboard navigation, while generally skipping the ring for mouse clicks[^8].

The WCAG technique C45 uses `:focus-visible` to provide keyboard focus indication, and it is rated sufficient for meeting 2.4.7 when the styles are actually visible[^8]. The pattern looks like this:

```css
:focus-visible {
  outline: 3px solid #7c3aed;
  outline-offset: 2px;
}
```

Two cautions. First, you still need a visible fallback for cases where a pointer interaction also benefits from focus indication, which the C45 technique notes explicitly[^8]. Second, set `outline` styles and do not rely on `box-shadow` alone, because user agents suppress `box-shadow` in forced-colors and high-contrast modes. The C40 technique warns authors to avoid `box-shadow` on its own for focus, and to keep an `outline` for compatibility[^7].

## The test loop that catches regressions

None of this survives contact with a fast-moving design system unless you test it, and you have to test it at the right moments. The WCAG understanding pages give the manual procedure for 2.4.7: set focus with the keyboard for every interactive component and verify an indicator is visible[^4]. That is the baseline. But a component library regenerating every sprint needs more than an occasional manual audit, so you want three layers.

First, a scripted keyboard walk as part of your component test suite. For every interactive component, drive the focus through its full cycle: Tab into it, arrow through its items, Escape out of temporary states, and assert that focus lands where the pattern says it should (the current roving item, the right dialog control, the restored trigger). This catches the focus-drop-to-body bug and the missing roving update, which are the two failures users hit first[^10].

Second, a forced-focus visual check. Because focus appearance and contrast are hard to assert reliably in automated DOM tests, capture focused and unfocused states of key components and diff them, or at least spot-check with OCR on a focused screenshot that an actual indicator rendered and the focused element changed meaningfully. This is the layer that catches a `2px` indicator that was quietly overridden by a more specific rule.

Third, the unplug-the-mouse smoke test, which the Level Access guide recommends directly: disconnect your mouse and complete the three or four core tasks of the product with only Tab, Shift+Tab, Enter, Space, arrows, and Escape[^2]. That five-minute pass, repeated before every release, finds focus traps and dead ends faster than any static analysis. Keep a short checklist, one per component, so the smoke test is repeatable and does not drift.

## What a keyboard accessible component library looks like

Pull it together and you get a clear picture of the shape a design system takes when it treats keyboard support as a first-class interface pattern. Every composite widget uses roving tabindex with a single tab stop. Every dialog moves focus in on open, constrains it while open, and returns it to the trigger on close. Every interactive component carries a visible indicator via `:focus-visible` that meets the 2 pixel and 3:1 bar. Sticky elements use `scroll-padding` so they never cover the item with focus, which the 2.4.11 criteria and the C43 technique make possible[^5]. And every component ships with keyboard tests in the same suite as its interaction tests.

Visually, a subtle focus ring on mouse is fine, so long as the keyboard ring stays strong and predictable. The two are no longer a trade-off, because `:focus-visible` lets you give each input method the styling it needs without leaking one into the other[^8].

Here is the thing worth remembering when the accessibility audit comes back and someone asks which layer caused the failures. Keyboard nav is not a screen-reader concern and not a checkbox. It is the interface layer every component sits on, it is cheap to get right with roving tabindex and `:focus-visible` and a proper focus-return handler, and it is the one layer a mouse user will never see fail until a real user hits it. Test it like the contract it is.
