A request arrives. The orchestrator calls a sub-agent, the sub-agent calls a tool, the tool calls a vendor API. Every layer has a timeout, and each one was chosen by someone who could not see the others. The person who asked gave up at around ten seconds and reloaded the page. Your chain keeps working on that abandoned question for another two minutes, streaming tokens into a socket nobody is reading.[^3]

The number is rarely wrong. What is missing is a clock anyone owns. A timeout is a local guess about how long one call should take; a deadline is a shared fact about when the work stops mattering, declared once at the edge and carried through every handoff. Agents need the second one more than plain services do, because an agent loop decides for itself when it is done.

## A timeout is a local guess, a deadline is a shared fact

A per-call timeout gets chosen from the downstream service's own latency. Amazon's guidance is to accept a small false-timeout rate, read the matching latency percentile, and add padding for the network, and it flags a trap that catches agent stacks: a timer started before a new secure connection is established includes that handshake, while a reused connection never pays it.[^4] That is a sound way to choose one number, and it says nothing about a chain of five.

Chained timeouts add up. Four hops that each wait thirty seconds can spend two minutes before the first one gives up, and nobody chose that total. The alternative puts one deadline at the edge and lets each stage inherit the remainder: a thirty second budget that spends seven seconds at the first hop hands twenty three seconds to the next call, which hands nineteen to the one after that if it spends four.[^3] The numbers shrink as the chain deepens, which is the point. Concretely: hold back a few hundred milliseconds for the trip home, hand 9.6 seconds to the orchestrator, 6.4 to the sub-agent once it has spent 3.2 seconds of real work, and 2.8 to the tool call. gRPC sets no deadline by default, so a client that never sets one waits while holding every resource that request needs.[^1][^2]

Without that discipline the failure is quiet. A hop that invents its own longer clock for the call downstream is not being generous, it is spending time the caller already stopped counting on, and no log line says so.[^3]

gRPC has encoded the pattern for years, and its vocabulary is worth borrowing even if you never run it. A deadline is a point in time, a timeout is a duration, and the difference matters across machines, because one host cannot trust another's clock, so the deadline travels as the remaining duration with elapsed time already deducted.[^1] Whether you call gRPC or fetch with an abort signal, the shape holds: the caller sets an instant, and the instant travels.

## Slow and stuck are different failures, so you need two clocks

Ten minutes is a reasonable deadline for a research agent and a catastrophic one for a chat reply, and the defaults around your code are larger than the patience they serve. The OpenAI SDK waits ten minutes per request before raising a connection timeout, and retries twice on the way there.[^5] A Vercel function gets three hundred seconds by default, and Pro and Enterprise can raise one to eight hundred.[^6] Cloudflare answers the client with a 524 after a hundred and twenty five seconds of silence from the origin, then leaves the origin working.[^7] A person waiting on a chat reply is gone long before any of those numbers.

One timer cannot tell thinking from dead, so add a second clock that measures silence. An agent emitting a token every couple hundred milliseconds for four minutes is healthy and should finish. An agent that emitted two events and then nothing for thirty seconds is stuck, and every second after that is a held worker slot and a live token meter.

Vercel's documentation is explicit that HTTP/2 handlers receive connection level ping frames while the response is idle, that HTTP/1.1 has no equivalent, and that handlers running long should stream progress or heartbeat data while the work happens.[^6] Same instruction for an agent loop: emit a step event when a tool call starts and another when it returns. Those events are the signal that separates a slow answer from a dead one. Keep a timeout distinct from a user cancellation when you abort, since one of them means the person already left.[^8]

![Two clocks inside one ten minute deadline: work that keeps emitting events resets the idle clock and finishes, while a stream silent for thirty seconds is killed as stuck, beside the defaults each layer imposes: ten minutes per request, three hundred per function, and 524 at a hundred and twenty five](</diagrams/timeout-deadline-budget-agent-pipeline-2026/2-two-clocks.png>)

## When the clock expires, stop the work

Returning an error stops nothing. If the deadline ends the request handler while the model call is still streaming and the tool call is still in flight, you kept the worse half of the problem: the status code says 504, the tokens keep flowing, the vendor keeps billing, and a write may still land after the person who asked has moved on.

Cancellation has to travel the path the deadline did. The gRPC rule is blunt: once a call is cancelled or its deadline passes, the server application is responsible for stopping any activity it has spawned.[^1] An agent is a machine for spawning activity. The sub-agent needs a checkpoint where it reads its own clock, the tool client needs to accept the same abort signal as its caller, and the loop has to stop between steps rather than in the middle of a write.

SRE adds the staging rule: a handler that parses, then fetches, then processes should check the deadline before each stage instead of discovering the budget was spent after spending it.[^3] The arithmetic is unkind. With a hundred second deadline and five percent of requests never completing, the requests nobody wants consume five thousand threads on a frontend that has a thousand, and the service ends up serving under a fifth of its traffic.[^3]

Long work belongs behind a status endpoint the client polls, which is Cloudflare's own recommendation for anything that outruns its proxy read timeout,[^7] and every mutating step has to be safe to repeat, since a cancel can arrive after the write committed. That second requirement is why [durable execution](/field-notes/agent-durable-execution-state-machines-2026) exists. The deadline tells you when to quit. Idempotency keys make quitting safe.

![What keeps running after a deadline: the error only path returning a 504 while the generation, the in flight tool call and the worker slot stay live and billed, against a cancel path where one abort signal stops the call and frees the slot](</diagrams/timeout-deadline-budget-agent-pipeline-2026/3-cancel-path.png>)

## Budget the clock the way you budget steps

An agent already has a budget for steps and a budget for dollars, both of which [deserve hard ceilings](/field-notes/agent-loop-spend-guardrails-2026). The clock is the third, and it is the one the user measures.

Start from what the caller will really wait, not from the slowest dependency. If the answer has to arrive inside ten seconds, that is the budget, and every hop's number gets derived from it. Hold back a few hundred milliseconds per hop for network transit and post-processing before the answer is handed back, because the deadline that matters belongs to the caller, not to the middle of the chain.[^3] Then check the clock before any stage that costs real time or money: the retrieval, the model call, the write. Retries live inside the same budget with backoff and jitter, because a retry storm against a dependency that is already failing makes it worse.[^4] SRE's version is a retry ceiling per process, something like sixty retries a minute.[^3] A remaining-budget field on every span turns this into an observable number, and gRPC's advice is to tune the value with a flag rather than a release.[^2]

One rule from the unattended side of our own pipeline generalizes: the layer that owns the budget should be the layer with the authority to stop the work. Scheduled agents and overnight jobs run under a wall clock limit, and when one hangs it is the supervisor's timer that ends it, not the worker's own error handling.

Open the slowest agent request you still have traces for and write down how long the person waiting would have tolerated. If that number is smaller than every timeout in the path, you do not need a smaller timeout. You need a deadline.
