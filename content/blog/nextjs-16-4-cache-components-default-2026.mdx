On October 6, 2026, the Next.js team stopped treating Cache Components like an experiment. In the [16.4 release](https://nextjs.org/blog/next-16-4), they recommended the model for every Next.js app, enabled it by default in all new `create-next-app` projects, and announced that it will become the default programming model in Next.js 17.[^1] If your app is on 16.x today, you have a migration coming. You do not need to take it all at once, and the release also shipped the tools that make a staged adoption safe: `ensureStatic`, the `navigation()` and `prefetch()` functions, and agent-driven upgrade tooling that does most of the mechanical work.

This article is the adoption playbook. It assumes you have read how the model thinks about timing, which we covered in [Next.js 16 caching: stale, revalidate, expire](/field-notes/nextjs-16-cache-lifecycle-2026), and how instant navigations work, in [Next.js 16.3 instant navigations](/field-notes/nextjs-16-3-instant-navigations). Here we focus on the part 16.4 adds: given a working App Router app, how do you move it onto Cache Components without a big-bang rewrite, and what are the new controls that keep it honest once you do?

## What actually changed in 16.4

The core idea of Cache Components is not new. The `'use cache'` directive and `cacheLife` profiles have been part of the framework for several releases. What changed on October 6 is the recommendation and the default. Before 16.4 the Next.js team held back from recommending the model universally because a few cases could not meet the same cost and performance guarantees as the previous model. This release closes those gaps, and the recommendation flips: Cache Components is now the best choice for every app.[^1]

Practically, that shows up in three ways. New projects get the model on by default, so greenfield work gets the benefits with no configuration. The framework ships a new `ensureStatic` config that lets you guarantee part of a route stays static, closing the main objection teams had about Cache Components, which was that a single dynamic component could quietly make an otherwise static page render per request. And a new agent workflow, built around `next upgrade --agent`, gives you a way to migrate an existing codebase route by route without writing all the migration glue by hand.[^1]

The rest of the release is speed that everyone gets regardless of caching. Turbopack's disk cache uses 20 to 25 percent less space through Zstandard compression, dev servers compile only the server updates a request actually needs, and production bundles are smaller through shorter CSS class names and export mangling.[^1] Those are welcome, but they are not the story. The story is that caching, which was once spread across `fetch` options, route-segment exports, and implicit behavior, is now one model with explicit controls, and 16.4 gives you the levers to manage it.

## The three navigation stages are the mental model

Before you can use `ensureStatic`, `navigation()`, or `prefetch()`, you need the model of navigation they all operate on. With Partial Prefetching on, a Next.js route loads in three stages, and each stage fetches a different amount of the route from the server.[^2]

The first stage is the App Shell, what a default Link loads. It is the route's static output: layout chrome, shared navigation, and Suspense fallbacks. Links to the same route share it, and it is fetched once and cached for the session. The second stage is a per-link prefetch, which only happens for links you opt into with `prefetch={true}`. It adds the content that depends on that link's URL data, which the shared shell cannot include, such as `params` and `searchParams`. The third stage is the navigation itself, which happens on the click and renders everything that remains.[^2]

![The three navigation stages in Next.js 16.4: a default Link loads the App Shell with static output and Suspense fallbacks; a Link with prefetch set to true adds URL-data content from params and searchParams; and the navigation on click renders everything that remains. The deferral functions mark the boundaries: await navigation() keeps work out of both the shell and the per-link prefetch so it renders only on navigation, while await prefetch() keeps work out of the shell but includes it in a per-link prefetch.](</diagrams/nextjs-16-4-cache-components-default-2026/1-navigation-stages.png>)

The reason these stages matter is that they give you a cost model. A route can be served entirely from static output, which a CDN can cache, so a link into it costs no server CPU at all. It can mix static and cached content with request-specific content rendered at request time, which is flexible but means every request to that piece hits the server. Understanding which stage each piece of work belongs to tells you which control to reach for. Static output you want to guarantee belongs to `ensureStatic`. Work you want to defer to a later stage belongs to `navigation()` or `prefetch()`.

## `ensureStatic`: guarantee a stage stays static

The feature that closes the biggest objection to Cache Components is `ensureStatic`. Its job is to keep a selected route output static instead of letting it render per request, and to make that guarantee stick as the code changes.[^3]

You export it from a page or layout. The value selects how far the static requirement extends through the navigation stages. `'shell'` requires the App Shell to be static. `'prefetch'` requires both the App Shell and per-link prefetches to be static. `'navigation'` requires the complete server-rendered route to be produced during prerendering, so initial loads and client navigations all use static output. Each stricter level includes the earlier ones. `'auto'` is the default and adds no requirement; `false` preserves normal rendering and prevents a parent segment from applying a stricter level.[^3]

The value that most teams will want for their marketing pages, blog posts, and ecommerce catalog pages is `'navigation'`. Set it on a route and Next.js validates the complete static-output requirement during both `next dev` and `next build`, failing the build if anything adds request-time rendering.[^3]

```ts
// app/store/products/[slug]/page.tsx
export const ensureStatic = 'navigation'

export default function ProductPage() {
  // ...
}
```

What makes `ensureStatic` more than a declaration is that it is enforced. If you later add a component that reads `cookies()`, `headers()`, server-side `searchParams`, or an uncached `fetch`, or passes request-dependent data to a Client Component, the build fails instead of silently making the page dynamic.[^3] A developer who adds a personalization widget to what should be a static product page gets a compile error that names the offending access, in the spirit of how Next.js already surfaces instant-navigation violations. That is the difference between configuration and a guardrail: `ensureStatic` does not just tell the framework your intent, it refuses to let the code drift from it.

There is a real cost and it is worth naming. `'navigation'` is strict. It requires the route to read nothing request-dependent, and a dynamic route must export `generateStaticParams()` returning at least one complete parameter set, or the build fails.[^3] It also restricts the cache timing: a `use cache` scope whose `stale` is under 30 seconds, whose `revalidate` is 0, or whose `expire` is under five minutes is rejected, because those values imply near-request-time freshness that a fully static route cannot honor.[^3] For genuinely static content, that is fine. For a personalized dashboard, it is the wrong tool, and the point is to use it only where static output belongs.

![ensureStatic: how far each value pins the route to static output. With 'auto' no stage is required static. With 'shell' only the App Shell is static. With 'prefetch' the App Shell and per-link prefetch are static. With 'navigation' the complete route is static, including the response returned after navigation, and Next.js fails the build if request-time rendering is added later.](</diagrams/nextjs-16-4-cache-components-default-2026/2-ensurestatic-levels.png>)

Because `ensureStatic` is a route-segment config, it composes up and down the tree. Set `'navigation'` on the root layout and every page in the site inherits the static guarantee; push it down to nested layouts or pages when a section starts to need dynamic content. A descendant can set a stricter level than its parent, but not a weaker one, and Next.js errors on a build where a child tries to relax a parent's constraint.[^3] Start strict at the root and carve out dynamism deliberately, rather than the reverse, which is how a fully static site stays that way as it grows.

The one thing `ensureStatic` does not replace is per-subtree deferral. When you need to keep one component out of a stage but leave the rest of the route alone, the finer-grained tool is a deferral function.

## `navigation()` and `prefetch()`: defer work to a later stage

Where `ensureStatic` controls a route as a whole, `navigation()` and `prefetch()` control a single component subtree. Both are async functions you `await` inside a server component, and both need Cache Components enabled and throw if it is not.[^4]

`await navigation()` keeps the runtime work below the call out of the App Shell and out of per-link prefetches. It runs when the user actually navigates. During a prefetch, the nearest Suspense fallback renders in place of that content. This is the tool for expensive, reusable content that no prefetch should pay to generate, like a comment thread that depends on the post and a sort preference.[^4]

```ts
import { Suspense } from 'react'
import { cookies } from 'next/headers'
import { cacheLife, navigation } from 'next/cache'

async function Comments({ params }) {
  await navigation() // runtime work below renders on navigation
  const { slug } = await params
  const sort = (await cookies()).get('comment-sort')?.value ?? 'newest'
  const items = await getComments(slug, sort)
  return items // render the list below the navigation boundary
}

async function getComments(slug, sort) {
  'use cache'
  cacheLife('hours')
  return db.comments.list({ slug, sort })
}
```

The key detail is where the deferral boundary sits relative to caching. The code below `navigation()` can still be a `use cache` scope with a cache lifetime; the function defers it out of the prefetch without giving up its cacheability. When every read of `cookies()`, `headers()`, `params`, and `searchParams` sits below a `navigation()` call, the prefetch produces nothing beyond the static output the build already generated, so the prefetch can be served from that output and cached in a CDN, costing no server CPU at all.[^4]

`await prefetch()` is the sibling with a different boundary. It keeps work below it out of the App Shell, but includes it in an explicit per-link prefetch with `prefetch={true}`.[^5] Reach for it when content depends on the link's URL data, so it belongs in the per-link prefetch and not the shared shell. The distinction between the two functions is a single question: should this content appear in a per-link prefetch, or wait for the actual navigation? If the answer is "wait for navigation", use `navigation()`. If "include it in the prefetch but not the shell", use `prefetch()`.

There is a subtlety worth respecting. Leaving content uncached also keeps it out of prefetches, but it gives up the cache lifetime. `navigation()` lets you have both: the content is deferred to the click, and once shown, a `cacheLife` with a `stale` of five minutes or more lets the client-side router reuse it on later visits to the route. That is the difference between "render on click every time" and "defer the first generation, then reuse".

## The agent tooling that makes migration tractable

The adoption story rests on one more piece of 16.4: the framework now assumes your coding agent will help you migrate. `next upgrade --agent` is a CLI command that determines your installed version, selects a target release based on a policy, prepares the relevant migration guides and Skills, and hands the task to a coding agent, which applies the update, resolves migration issues, and verifies the app still works.[^6]

You run it from the app directory:

```bash
npx next@canary upgrade --agent=latest
```

Using `next@canary` runs the latest upgrade tooling even if your app is on an older version. The policy selects the target: `security` picks the latest safe release for security advisories, `latest` moves you to the newest stable, and `experimental-future` applies `latest` and then adopts the features Next.js plans to enable by default, which today includes Cache Components and Partial Prefetching.[^6]

This matters for adoption because the model change is broad. For an App Router project on 16.3 or later, the `experimental-future` policy prepares the Cache Components guide and its adoption Skill, so moving to the new caching default becomes part of an upgrade instead of a separate migration project.[^6] The agent workflow also scales the mechanical parts, running checks, verifying the result, and using a separate git worktree when one is available, so a failed migration does not dirty your main branch.

The upgrade path is the one time a coding agent earns its keep in this workflow. Cache Components adoption touches many small decisions, which routes to tag, which `cacheLife` profiles fit which data, which stages deserve deferral, and the agent, pointed at the migration guide and Skills, handles the volume while you review the diff. The framework reinforces the pattern with `experimental.agentUpgrade`, which nags your editor or build when a relevant upgrade is available, defaulting to a security-focused policy that only pings you when a known vulnerability affects your installed version.[^7]

## A four-step adoption the whole team can commit to

Put together, the three new surfaces compose into a staging plan that keeps an existing app shippable through every step.

**Step one: turn the model on.** Add `cacheComponents: true` and `partialPrefetching: true` to `next.config.ts`.[^2] This is the whole team's entry point. Nothing else is required to start, and the two flags are the shared vocabulary for every conversation after this one.

**Step two: tag data with `use cache` and a `cacheLife` profile.** Start with the routes whose data is expensive but changes slowly, product catalogs, public guides, blog content. Mark the async data scope, pair it with the right `cacheLife` profile, and let the route stream static and dynamic content together. Leave the routes you are not ready to touch, which is the point of a staged model: every route is cacheable or not on its own terms.

**Step three: set the boundary per route.** For pages that must stay static, add `ensureStatic = 'navigation'` and let the build enforce it. For content that should not be prefetched, drop a `navigation()` call. For content that belongs to a per-link prefetch, use `prefetch()`. This is where 16.4's model shows its value: you are not choosing a rendering mode per route anymore, you are placing one of four controls at the exact depth where it belongs.

**Step four: hold the line.** `ensureStatic` turns regressions into build errors, which is the only way a static promise survives a team that changes. Convert routes one at a time, run the build between each, and let the agent tooling handle the version bumps. A route you have not converted simply stays on its current behavior, which is what makes the migration reversible.

Adopting Cache Components is not an all-or-nothing rewrite. It is a sequence of small, individually safe changes enabled by one config and made durable by three new controls. For new apps, 16.4 handles it for you. For the app you already have in production, the playbook above is the path that gets you to the same place without a feature freeze.
