React 19.3 shipped on September 9, 2026, and the four APIs it stabilized read less like a new-feature dump and more like a confession.[^1][^2] The React team has spent two years watching teams trip over the same problem: a component renders twice, once on the server to produce the initial HTML and once on the browser to attach event handlers, and the seam between those two renders is where the bugs live. Time zones that disagree with themselves. Saved drafts that flash blank for a frame. List animations hand-rolled with fifty lines of CSS and an effect. React 19.3 turns each of those fixes into a first-class API, and moving to it is a package bump, not a rewrite. This release also continues the arc that [React 19.2's stabilization](/field-notes/react-19-2-activity-useeffectevent) started, where React keeps promoting useful experimental behavior into supported form.

This is the release note for the gap that server rendering has never quite closed. It is worth reading even if you do not touch animation or refs, because the headline API, `browser()`, changes how you write every component that reads a browser-only value.

## The component lives in two environments at once

Every server-rendered React tree runs in two places. On the server, components render to a string of HTML that the browser paints before any JavaScript runs. On the client, React renders again to hydrate that HTML, matching the server's output and attaching interactivity. Most components produce the same output in both runs, which is what makes hydration work.

A few components cannot. A component that reads `localStorage` has no storage on the server. A component that shows the visitor's local time zone has no reliable time zone there either. `Intl.DateTimeFormat().resolvedOptions().timeZone` is correct only in the browser, because the server does not know which visitor it is rendering for.

When such a component renders a different value on the client than it did on the server, React detects the mismatch, logs a recovery error, and replaces the mismatched subtree. Users see the corrected version, but the page has already broken hydration once and applied a silent repair. Before 19.3 the only clean-looking fixes were workarounds that carried their own cost: a `useEffect` that flips a `mounted` boolean and delays the real value by a frame, or a `typeof window` check that guesses which environment you are running in.[^3]

Let me be specific about what that workaround really costs. The mounted-state pattern renders nothing, or a placeholder, waits for an effect to run after paint, then re-renders with the real value. On a page with several such components, that is several flashes of placeholder that resolve at different frames. It is also a footgun, because the pattern is easy to get subtly wrong: if the effect never runs, or the value is read on the server and cached, the placeholder becomes the permanent state. The window check is worse, because modern bundlers can replace `typeof window` at build time and turn a browser check into dead code you never notice.

## `browser()` makes opting out first class

React 19.3 adds a real answer. `browser` is exported from `react-dom`, and you pass what it returns to `use`:

```js
// SavedDraft.js
'use client';

import { use, useState } from 'react';
import { browser } from 'react-dom';

function SavedDraft() {
  use(browser('The draft is stored in localStorage.'));
  const [draft, setDraft] = useState(
    () => localStorage.getItem('draft') ?? ''
  );
  return draft;
}
```

On the server, `use(browser())` stops the component from rendering and leaves the nearest Suspense boundary's fallback in its place. In the browser, `use(browser())` returns `undefined` and the component renders normally.[^3] The change from the old workaround is structural: instead of rendering nothing and hoping an effect fixes it, you declare that this component has no meaningful server output, and you let Suspense show a proper loading state.

That means the component must sit inside a Suspense boundary on the server, or the render fails, and it must run in a Client Component, so a Server Component cannot call it directly. Both are enforced by React, not left to convention.[^3] For the saved-draft case, a small wrapper that renders the Suspense fallback ("Loading draft...") in its place around the component is all you need. The initial HTML carries that fallback. Once hydration runs in the browser, `SavedDraft` renders the actual draft loaded from `localStorage`. No server ever emits a wrong draft value, and the browser never has to repair a mismatch. The result is the same visual as the mounts-then-repairs workaround, but without the flash and without the window check.

Because `use(browser())` behaves like any other `use` call, it works inside conditionals and after early returns. That unlocks the pattern that most teams actually need, which is conditional: render on the server when you can, opt out to the browser only when you cannot.[^3]

```js
export function useTimeZone(defaultTimeZone) {
  if (defaultTimeZone !== undefined) {
    return defaultTimeZone;
  }
  use(browser('No default time zone was provided.'));
  return Intl.DateTimeFormat().resolvedOptions().timeZone;
}
```

Pass a default and the component renders it into the initial HTML and keeps it in the browser. Omit it and the component suspends on the server, then shows the visitor's real time zone after hydration. The same component does either job, chosen by a prop.

The pattern generalizes to data fetching. A Suspense-enabled query library can opt out of server rendering unless the loader already supplied its data:

```js
function useBrowserQuery(query, options) {
  if (options.initialData === undefined) {
    use(browser('useBrowserQuery: no initial data provided.'));
  }
  return useQuery(query, options);
}
```

With `initialData`, the product details component renders its real content into the HTML on the server. Without it, the server leaves the Suspense fallback and the browser fetches the data or reads it from its client cache.[^3]

There is also a hook for your observability. `renderToPipeableStream` accepts a `onBrowserBailout` callback that reports each time a component opts out of server rendering, and if you pass a reason string or function to `browser`, it arrives as the error's cause.[^3] You can also pass the value returned by `browser` as the reason when aborting a server render, which tells React: stop waiting on the server, leave the pending boundaries in their fallback state, and let the browser finish them.[^3] For a slow first request this is how you ship the shell within a time budget and defer the rest to the client.

If you have written the mounted-state dance more than a couple of times, `browser()` is the upgrade that removes the ceremony. It reads better, it enforces the Suspense boundary, and it gives you a hook to count the components that need it.

## The conditional pattern, spelled out

The data-fetching variant above is the one teams reach for most, so it is worth drawing the decision it encodes. A component that reads from a query cache does not have to opt out of server rendering wholesale. If the loader passed it initial data, it can render fully on the server, keep that content in the HTML, and stay crawlable. Only when it has no data at all does it hand the work to the browser.

![The conditional use(browser()) pattern for data fetching: if the loader passed initialData, the component renders on the server into the initial HTML. If not, the hook calls use(browser()) before useQuery, the server leaves the Suspense fallback in place, and the browser fetches or reads from its client cache. The same component does either job, chosen by a prop.](</diagrams/react-19-3-two-environment-apis-2026/4-browser-conditional.png>)

That single decision, initial data present or not, is the boundary. Keep it in one custom hook so every data-reading component inherits it, and you never sprinkle `browser()` calls through your pages.

## `ViewTransition` makes UI change declarative

The second stabilized API is `ViewTransition`, which finally gives React a first-class way to animate enter, exit, and content changes. Under the hood it drives the browser's View Transition API, and React runs `startViewTransition` for you, so you do not hand-write the plumbing.[^4][^5]

The key constraint is that only updates marked as a Transition animate. A plain `setState` shows immediately with no animation. Updates inside `startTransition`, a Suspense reveal, or a `useDeferredValue` change activate the `ViewTransition`.[^5] You wrap the UI you want to animate in a `ViewTransition` component and drive the change through `startTransition`:

```js
import { startTransition } from 'react';

function toggle(setter) {
  startTransition(() => setter((v) => !v));
}
```

React picks the animation from how the tree changed. When the wrapped tree mounts, it runs an enter animation. When it unmounts, exit. When its content or style changes, update. When a named `ViewTransition` is removed in one place and added in another, it runs a share animation that moves the element between the two spots.[^5] You can set the animation for each trigger with props, so a carousel can slide forward on next and backward on previous by tagging the transition with `addTransitionType('next')` or `addTransitionType('previous')` inside the state update.[^6]

A practical note for ships: `ViewTransition` is DOM-only for now, and two boundaries with the same name mounted at once throw. When you map a list and each row is a `ViewTransition` with the name "item", every row passes the same name and React errors, so either leave the name off (the default is a unique per-instance name) or make it unique with the item id.[^5] For the navigation side of this pattern, the instant-navigation work in [Next.js 16.3](/field-notes/nextjs-16-3-instant-navigations) pairs naturally with `ViewTransition` to keep the seam between routes from flashing.

The animations integrate with Suspense in a way that matters for loading sequences. Wrap a Suspense boundary and the fallback first appears with no animation, then animates into the final content when it resolves. The same mechanism lets images and fonts opt into Suspense while they load, so a card waits for its data, image, and font together instead of each popping in whenever it finishes. React's own guidance is to use these sparingly: fallbacks appear immediately without animation, a fallback updates to its final content with animation, and cached content appears instantly without animation. Pair that with a `prefers-reduced-motion` media query, because React does not disable animations for you.[^5]

## Fragment Refs reach your own DOM without a wrapper

The third API solves a quieter but stubborn problem. Components that render several siblings with no single parent had no clean way to attach a ref, and components that do not pass along their `ref` prop were unreachable entirely. The usual answer, wrapping the children in a div so you have something to ref, interferes with styling and layout, and it is impossible when the component comes from a library you do not control.

In 19.3 a Fragment accepts a ref and gives you a `FragmentInstance` that operates on the children as a group, without changing the tree structure. It offers a focused set of operations: `addEventListener`, `removeEventListener`, and `dispatchEvent` for events on first-level children; `focus`, `focusLast`, and `blur` for moving focus across nested children; `observeUsing` and `unobserveUsing` to connect an `IntersectionObserver` or `ResizeObserver`; and `getClientRects`, `getRootNode`, `compareDocumentPosition`, and `scrollIntoView` for measurement and scrolling.[^7]

The payoff is a component like `InView` that fires an `onChange` when its children enter or leave the viewport, even though the children expose no `ref` and share no parent. That is the kind of behavior you previously had to build into every consumer. With a fragment ref it lives once, in one wrapperless component.[^7]

## Server Components can render Context directly

The fourth change is smaller but removes real boilerplate. Server Components cannot create Context, but since 19.3 they can render one imported from a `'use client'` module, without a wrapper Provider component. Where you previously wrote a `UserProvider` purely to pass a prop through to `UserContext`, you now import `UserContext` itself and render it with the current user as its value from the Server Component.[^1] It matters most for Contexts that exist only to let the server share data with the rest of the client tree.

The same release adds Trusted Types support. Under a Content-Security-Policy that enforces a Trusted Types requirement, React previously coerced `TrustedHTML` and related values back to plain strings with `'' + value`, which the browser rejects. React now passes those values through uncoerced, so Trusted Types policies work as intended and the CSP-based XSS defense holds.[^1][^8]

## Which one should you reach for

The four APIs answer different questions, and a team adopting 19.3 should map them to the code they already maintain.

Reach for `browser()` the moment a component cannot produce meaningful UI on the server: saved drafts, the visitor's time zone, a viewport-dependent layout, anything that reads `localStorage` or `window`. It replaces the mounted-state dance and the window check, and it is the rare React change that removes code rather than adding it.

Reach for `ViewTransition` when a user action changes the tree and you want it to animate: expanding a panel, swapping a route, reordering a list, moving a shared element. Remember it only fires for Transition-marked updates, so pair it with `startTransition`, gate it behind `prefers-reduced-motion`, and leave the name off unless you are doing a shared-element move.

Reach for Fragment Refs when you need to observe, focus, or measure a group of siblings without adding a wrapper, especially around third-party components that hide their internals.

Reach for Context-in-Server-Components when you find yourself writing a Provider that only forwards a prop. It disappears.

The pattern across all four is the same: React is giving you a named, supported way to do what teams were already doing with hand-rolled code, and deleting the sharp edges. `browser()` is the one most teams will adopt first, because hydration mismatch and placeholder flash are problems every server-rendered app eventually meets. Upgrade React to 19.3.0, mark your browser-only components with `use(browser())`, and watch the hydration warnings that used to scroll past your console stop appearing. The other three you will reach for when the specific pain shows up, and when it does, the hand-rolled version you delete is the reason the change pays for itself.
