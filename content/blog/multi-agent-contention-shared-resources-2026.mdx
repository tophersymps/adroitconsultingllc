A multi-agent demo runs beautifully in a notebook. Five specialists fan out, each holds up its corner, and the whole thing converges on a tidy answer. Then the same pipeline hits a real load test, and the dashboard fills with 429s, stalls, and one agent quietly doing nothing while the queue backs up. The models did not get worse. What changed is that five isolated agents became five agents sharing the same resources, and nobody built the machinery for that.

There is a body of research that explains exactly why this happens, and it is not the story most teams tell themselves. A 2026 position paper on concurrency in multi-agent systems argues that a large share of failures that get blamed on coordination or communication are really concurrency problems: agents concurrently reading and writing shared state, with long LLM inference windows widening the window in which those operations collide. The authors call this a fundamental temporal asymmetry. A model spends seconds or minutes thinking, and while it thinks, other agents modify the environment the first agent is reasoning about, repeatedly. The failure is not that either agent was wrong. It is that both were right on their own and wrong in sequence.[^1] Much of what teams write off as a coordination breakdown is really this: the structural failure modes we mapped in an earlier piece on [multi-agent failure](/field-notes/multi-agent-failure-structural-2026) are often contention surfacing as a tangle of retries and stale writes.

That is the shift this article asks for. When a multi-agent pipeline breaks under load, the place to look first is not model quality, prompt quality, or even orchestration topology. It is the narrow shared resources every agent reaches through at once: the rate-limited model endpoint, the shared tool API, the one state or queue store, the single write lock. Capable agents find the boundary and pile onto it. Here is the failure taxonomy, the signals that say which one you are inside, and the fixes that survive real concurrency.

## The boundary is the agent's weakest link, not the model

Rate limits are the most common shared boundary, and they expose the shape of the problem better than anything else. API providers issue limits per account, not per agent.[^3] The quota is shared while consumption is distributed, so no individual agent is misbehaving. Each one makes exactly the calls it was designed to make, and the aggregate behavior alone trips the limit.[^3]

![A fleet of parallel agents, each below its own assumed limit, routing into one shared model account whose collective request rate exceeds the provider quota, triggering a 429 rejection](</diagrams/multi-agent-contention-shared-resources-2026/1-quota-pileup.png>)

The numbers make the trap concrete. Ten parallel agents each making one call per second exhaust an OpenAI Tier 1 account's 500 requests-per-minute ceiling in 50 seconds, before any of them finishes its first task.[^3] Anthropic's Tier 1 ceiling is tighter still, roughly 50 requests per minute and 1,000 per day for some models, low enough that a handful of agents spending a normal afternoon exceed it.[^3] And agent work is not smooth. Execution is bursty by nature: agents sit mostly idle while they evaluate context, then fire intense microbursts when several workers reach a tool call at once. A pipeline with five parallel agents analyzing repository components can trigger 50 tool invocations in under three seconds without any coordination.[^8]

The lesson is not that rate limits are unfair. It is that per-agent self-policing cannot work, because no individual agent can see the load the others are creating.[^3] The boundary is account-level and the awareness is agent-level, so the two never line up. When a fleet 429s, each agent is petitioning a wall it never saw coming.

## A retry is a second attempt at the same collision

The default response to a 429 makes the problem substantially worse. Every agent framework retries, so when several agents hit the limit at once, they all receive the 429 at once, wait the same fixed interval, and retry at the same instant. The retry wave becomes a new burst that trips the limit again, and the cycle compounds until it is a self-sustaining failure loop.[^3][^2]

One engineer running a nine-agent system against GitHub's API logged the failure in detail. Nine agents launched together and opened ten pull requests in 22 minutes, until minute eight, when GitHub began returning 429s. Every agent retried at the same time. The retry wave triggered a second 429 wave, which triggered a third. Within roughly 90 seconds the account had burned through GitHub's 5,000 requests-per-hour limit and was locked out entirely.[^2] A single rate-limit hit, amplified by synchronized retries, became a system-wide outage.

The amplification is multiplicative in a fleet. Ten agents hitting a limit produce ten simultaneous retries, each wave indistinguishable from the original burst.[^3] There is also a quiet cost. A 429 is a deterministic rejection, but an agent that makes partial progress before hitting the ceiling is still billed for the partial completion. A run that fires 100 calls during a retry storm, 70 of them 429s and 30 partial completions, pays full token price for the 30 partial completions that produced no useful work.[^3]

![Two timelines of retry after a 429: synchronized agents retrying on a fixed interval collide again and enlarge the burst, while full-jitter backoff spreads the same ten agents across the wait window](</diagrams/multi-agent-contention-shared-resources-2026/2-thundering-herd.png>)

The fix for this specific failure is well established and cheap. Exponential backoff without jitter still leaves agents synchronized, so the standard is exponential backoff with full jitter: each retry draws a random delay from zero up to the backoff cap, spreading ten agents that saw the same 429 across the wait window instead of firing them together. Roughly, full jitter cuts the probability of a thundering herd by a factor linear in the number of retrying agents.[^3] It does not fix the underlying quota sharing, but it stops the pileup from manufacturing its own second, larger wave.

## Shared state magnifies every error you can already name

Rate limits are the visible boundary. The invisible one is shared state, and it is the one the research keeps pointing at. Two agents can each act within their own rules and still corrupt the system, because between the moment one agent reads a value and the moment it writes back, another agent changes that value. The classic example is two coding agents on a shared repository. One reads a utility module and starts implementing a feature that imports a function from it. The other refactors that same module, renaming the function, while the first agent is still somewhere in its long inference window. Both finish their own task correctly. The system ends up with a broken import, and nothing threw an error.[^1]

This is a stale-read hazard, and it is not an edge case in multi-agent systems. It is structural, because of the temporal asymmetry: reasoning time dominates, so the window in which interleaved operations can conflict is huge, orders of magnitude longer than the execution time of any single tool action.[^1] The concurrency paper maps a whole table of apparently distinct "coordination" failures onto classical concurrency anomalies. In one benchmark suite, premature submission accounted for roughly 37% of failures and tracing to missing synchronization barriers, and inter-agent misalignment in another benchmark hit nearly 37%, rooted in stale reads and inconsistent state. Isolating agents onto separate worktrees in one coding benchmark moved the success rate from about 55% unisolated to roughly 63% isolated.[^1]

The pathological end of shared-state contention is deadlock, and multi-agent systems reach it faster than ordinary distributed systems because the resource-acquisition order is often decided by the LLM at runtime rather than fixed and reviewed in code. Two agents each acquire one shared resource and wait on the other, forming a closed cycle that no one can break. One agent's failure-mode catalog documents exactly this: two document agents both need to lock two sections to make cross-referencing edits, each takes one, and both block forever holding a lock the other needs. The catalog estimates that systems without consistent lock ordering hit deadlock in roughly one in several thousand to tens of thousands of concurrent multi-resource operations, a rate that climbs sharply as agents hold more resources at once.[^5]

![Two agents each hold one of two shared locks and wait on the other, forming a deadlock cycle, while a separate stale-read panel shows an agent rebuilding an import from a module another agent refactors mid-inference](</diagrams/multi-agent-contention-shared-resources-2026/3-shared-state.png>)

Even the persistence layer under a framework becomes a shared boundary under load. LangGraph ships with an in-memory or SQLite checkpointer by default, which is fine for a notebook and fatal for a swarm, because SQLite supports a single writer at a time. In one production write-up, a load test with 50 concurrent users deadlocked the default SQLite checkpointer within 90 seconds and caused every background agent task to time out. The team's fix was to move to a Postgres-backed checkpointer with a connection pool and row-level advisory locks, which let thousands of isolated agent threads persist checkpoints concurrently with sub-5-millisecond write overhead.[^7] Fixing it correctly is a durability problem as much as a throughput one, and the discipline that lets a long run survive a crash, which we covered in [durable execution](/field-notes/agent-durable-execution-state-machines-2026), only pays off when the shared state it preserves is also correct under concurrency.

## Starvation looks like one misbehaving agent, but it is a scheduling problem

Contention does not always stall everything. Sometimes it quietly decides which work gets to proceed, and that decision is usually wrong. When all agents draw on the same shared quota, a low-priority consumer can starve the work that matters. In the nine-agent GitHub incident, the lead agent making critical architecture decisions sat stuck behind a background agent that had consumed the remaining completions doing low-priority issue triage. Both had equal retry priority, so there was no way to say one goes first.[^2]

The same failure shows up at fleet scale. When many agents share one API key, a single agent stuck in a re-planning loop can starve every other agent on the cluster. One operations account describes rescuing a team where a single runaway agent burned through thousands of dollars of API credits overnight while the dashboard sat at roughly 99% 429 errors.[^4] The interesting thing is that the runaway was not special. It was just the agent that happened to be in the retry loop, and the shared boundary let it monopolize the resource for everyone.

Priority inversion is different from deadlock. Deadlock is a circular, unresolvable wait; inversion is an ordering problem where critical work waits behind noise because nothing assigns priority.[^5] The fix is a scheduling policy on the shared resource, not better prompt engineering. A server should know that the architecture-deciding agent comes before the triage agent, that background polling yields when the pool tightens, and that a denied low-priority agent gets promoted after it has waited too long, so it does not starve forever.[^2]

![A priority ladder over the shared pool: a background poller and planner consume quota ahead of a critical lead agent, while tiered priorities, a donation pool, and a starvation promotion keep critical work from waiting forever](</diagrams/multi-agent-contention-shared-resources-2026/4-starvation.png>)

## Enforce at the infrastructure layer, never inside the agent

Every fix above shares one principle, and it is the reason single-agent tricks fail. The individual agent is the wrong place to enforce anything about shared resources, because the agent cannot see the aggregate and because anything in its context window can be influenced by its own output. A self-imposed limit is bypassable by a stuck loop, a misconfigured task, or a prompt injection that instructs the agent to keep calling.[^3] Enforcement has to sit outside the agent's reasoning loop, between the fleet and the resources it shares.

![A layered containment stack between the agent fleet and the shared resources: a rate governor with token budgets, a circuit breaker, distributed locking with timeouts, idempotent writes, and task decomposition onto disjoint resources](</diagrams/multi-agent-contention-shared-resources-2026/5-remedy-stack.png>)

The concrete pattern is a coordination layer that every agent consults before it calls out. This is the rate-governor pattern: a service that tracks usage across all agents, pools the shared quota, and decides whether to forward, queue, or reject each call.[^4][^2] It reads the provider's remaining-quota headers after every call rather than waiting for a 429, so it can slow background agents down before the wall arrives. It holds a shared ledger instead of separate wallets, so an idle agent donates its unused reservation and a critical agent can draw on the pool. It assigns priority, so background work parks first when the pool gets tight, and it promotes a starved agent before it dies waiting.[^2]

Against the retry storm, the layer adds a circuit breaker keyed to the error rate, opening when the 429 share crosses a threshold over a short window and failing fast instead of letting agents retry into the wall. The circuit should be scoped per model and per tenant, because one model throttling does not mean another is, and cutting off all traffic punishes the healthy path.[^4] Token budgets with pre-flight checks close the cost hole, estimating whether an imminent call will push the account over its budget before sending it. A single 100k-token reasoning call can consume as much budget as dozens of short ones, so request counts alone are the wrong unit.[^4]

On shared state, the same outside-the-agent rule applies. Distribute locking where agents genuinely share mutable state, with timeouts on every acquisition so a held lock cannot block forever, and prefer atomic operations over read-modify-write sequences wherever the store supports them.[^6] Where a lock must be held, a timeout-based detection that releases the agent's other locks and retries after randomization can cut mean time to recovery from a deadlock by over 90% compared to a human noticing and killing processes.[^5] Make every write idempotent with a unique operation ID, so a retry after a timeout produces the same result as the original and never double-processes.[^6] And where possible, do not share at all: the research consistently shows that task decomposition that gives agents largely disjoint resources removes the contention before it needs to be managed.[^1][^8]

This is not speculative architecture. We hit the same shape inside our own content pipeline, where several automated writers and reviewers share the same model accounts and the same repo at once. The structural answer was the same one the research lands on: put a coordination and verification layer outside any individual writer, with shared budgets, explicit gates, and health checks that run before anything proceeds. Each agent stays focused on its job; the shared-boundary enforcement lives in the layer none of them can edit. The lesson carried straight over to client agent builds: the agent is the reasoning, and the coordination layer is the contract that keeps a crowd of agents from colliding on what they share.

## Contention is a design input, not a cleanup task

The hardest part of concurrency bugs is that they are timing-dependent. They pass unit tests, behave in staging, and detonate in the highest-traffic window of production, because they only appear when two specific operations interleave.[^6] That means waiting to find them is not a plan. The systems that survive are the ones that treat contention as a first-class design input.

Build it in from the start. Assign every agent to disjoint resources where the problem allows it, and where sharing is unavoidable, protect it with locks that time out and writes that are idempotent. Run intentional-concurrency tests, launching several agents against a shared resource simultaneously to see what breaks, rather than hoping nothing does.[^6] Design per-tenant quotas before a multi-tenant platform ships, so one tenant's runaway cannot take down the others.[^4] And put the enforcement outside the agent, in a layer the agent cannot see or influence.

When a multi-agent pipeline starts failing under load, the instinct is to blame the models. Redraw the mental model instead. The models were always the reliable part. The collisions live in the shared boundary, and that is where the fix belongs.
