A client once described their Salesforce org the way people describe a bad roommate: it mostly works, but it does strange things at night and never tells anyone. A sync job that silently drops 3% of orders for two days. A flow that rolls back a customer's save with "an unhandled fault has occurred in this flow" and gives nobody a way to trace it. An integration that looks green on the dashboard while the ERP never received a shipment. These are not bugs in the happy path. They are missing answers to the question every production build must answer: what happens when it fails, and who notices?[^1]

The reason this layer goes unbuilt is structural. Demos and user acceptance tests exercise the path where everything works. Volume, timing, and row locks only appear in production, and when they do, the platform's defaults are quiet. A flow failure rolls back and emails the person who last edited it, who has since left the company. An Apex caught exception silently commits half a transaction. An at-least-once message bus redelivers an event and a subscriber inserts a duplicate record. Each default is defensible on its own. Together they mean your automation can fail every night and the first human to know is a customer.

This article is the recovery layer: fault handling for Flow, transaction control for Apex, and the idempotency-retry-dead-letter-reconciliation chain for integrations. It is the companion to our [Flow failure patterns](/field-notes/salesforce-failure-patterns-2026), which names the six places builds break; this is what to build so the breakage is visible and recoverable. We apply the same instinct internally: every Adroit blog draft runs through a mechanical verifier that checks citations before editorial review, because a detection gate belongs on content too.

## Flow: decide what happens when an element fails, or it decides for you

Flow fails differently depending on the flow type, and most teams build as though they are all the same. A record-triggered flow runs inside the record's database transaction: an unhandled element failure rolls back the entire save, including the record change that triggered the flow and every other automation in it.[^2] A screen flow has internal transaction boundaries at every Screen and Pause element, so a failure rolls back only the work since the last boundary, and anything committed before a screen the user already passed stays in the database. A scheduled or platform-event flow fails per interview, with no user to see it, so the only default signal is an email.[^2] Same mechanism, three very different blast radii.

The core tool is the fault path, a second connector from any element that can fail, Get, Create, Update, Delete Records, or an Action. It is a try/catch built into a single node, and it exposes `$Flow.FaultMessage`, the actual error text from the failed element.[^3] The minimum viable fault path does three things: persists the failure to a custom error log object, alerts a human, and decides what the user sees.[^2] The log object is the foundation: a custom `Error_Log__c` with the flow API name, the element that failed, the triggering record ID, `$Flow.FaultMessage`, the running user, and a timestamp, plus a resolved flag so triage has a lifecycle. Route every fault-capable element to it and you have a queryable error history instead of relying on the platform's built-in flow error emails, which go to whoever last modified the flow and drown easily.[^3]

Real orgs collapse fault handling into three patterns, and the choice is about who is watching and whether the operation can be retried.[^3] The first, notify and stop, routes the fault path to a human-visible message or an email and ends. It does not try to recover; it makes sure a human finds out before the customer does, and it is the right default for most flows. The second, log and continue, writes the error log record and reconnects to the main path so one failed record does not kill the other ninety-nine in a batch. The third, retry then escalate, loops back to attempt the operation again, usually after a Decision checks a retry counter, and escalates to a log after N attempts. Reserve the third for transient failures like callout timeouts; retrying a validation rule error wastes iterations because it will fail identically every time.[^3]

![The three Flow fault-handling patterns: notify and stop for most flows, log and continue so one bad record does not kill a batch, and retry then escalate for transient failures, each routing through a shared error log object with a resolved flag](</diagrams/salesforce-error-recovery-2026/1-flow-fault-patterns.png>)

Two traps deserve their own warnings. A fault path that swallows the error, routing to an End element with no logging and no notification, is worse than no fault path at all: it converts a loud failure into a silent one, and you believe the flow works while it drops records for weeks.[^3] The other is the partial-commit trap. When an element fails and you have a fault path, the error is considered handled and the transaction does not auto-rollback; it continues down the fault path, and whatever you committed before the failure stays committed unless you explicitly roll it back. Say a flow creates an Order, then three Order Line Items, and the third fails. A fault path that just emails and ends leaves an Order with two line items and no third one. The fix is the Roll Back Records element, which explicitly reverts all uncommitted DML from inside a fault path. The rule of thumb: if a flow performs multiple related DML operations that must succeed or fail together, its fault path needs a Roll Back Records element.[^4] Note it applies to the current transaction only; it cannot undo anything committed at a previous Screen or Pause in a multi-step wizard, so design the commit points before the rollback story.[^2]

## Apex: the transaction is the contract, and caught exceptions are the leak

Apex runs inside the same transaction model, and its failure semantics are precise and commonly misunderstood. A DML statement on a list is all-or-nothing: if one record fails, the platform throws a `DmlException` and rolls back the entire statement, including records that would have succeeded. To allow partial success, you call the `Database` method with `allOrNone` set to false, in which case it returns a `SaveResult[]` whose elements correspond one-to-one to the records you passed, each carrying an `isSuccess()` flag and the errors on the failures. That array is the contract: you must capture and inspect it, because a `Database` call that discards its return value gives you no idea whether any of the records actually saved.[^5]

The subtle leak is not in the all-or-nothing path. It is what happens when you catch an exception. The platform's automatic rollback runs on unhandled exceptions only. If an exception is caught anywhere in the stack and the `catch` block does not explicitly undo earlier DML, those earlier changes are committed. This is easy to trigger unintentionally: code that updates an Account, then runs a query whose result is unexpectedly empty, throws a `System.QueryException`, which a broad `catch (Exception e)` swallows, and the Account update commits anyway, even though the transaction as a whole never finished. The same class of bug can have security consequences, for example a registration flow that catches a business-logic check failure after creating a User, leaving an account that can log in against the business rule.[^5]

The tool for making a caught-failure path correct is the savepoint. `Savepoint sp = Database.setSavepoint();` marks a position in the transaction, and `Database.rollback(sp);` undoes every uncommitted DML after it. Put a savepoint at the start of a unit of work, and in the catch block roll back to it before you log and return control. This is the discipline that turns "catch this exception" from a rollback-into-oblivion into a deliberate decision about what partial state, if any, survives.[^5] One limit note: a `System.LimitException`, the governor-limit overrun, cannot be caught and will roll back the transaction even inside a try block, which is why limit-safe design is prevention, not error handling.[^5]

## Integrations: the four-layer chain that catches silent failures

Integration failures are the largest category of silent breakage, and the reason is that they rarely fail loudly. The error handling that protects a message-based integration is a chain of four layers, each depending on the one before it, and most teams implement one or two.[^1]

The first layer is idempotency, because the platform's event delivery is at-least-once and the same message can arrive more than once. Without idempotency, a retry creates duplicate records. The fix is an external ID that uniquely identifies the event, not just the record, and an upsert keyed on it with a unique constraint, plus a log of which event IDs have already been processed. The caution from production: every sub-operation with an external side effect has to be idempotent itself, not just the final record, so an upsert on the order does not prevent a duplicate call that updates external inventory.[^1]

The second layer is retry with backoff, and it only works if you classify errors first. Temporary errors, a timeout, a 503, a rate limit, are candidates for exponential backoff. Structural errors, a missing required field or a validation violation, should never be retried because they will fail identically; send them straight to the dead-letter queue. Authorization or configuration errors, an expired token or an API version change, warrant an immediate alert because they block the whole queue, not a single message. The default retry budget is three to five attempts with backoff, never infinite, and in Salesforce retries usually live in a Queueable or Batch job with a retry counter stored on the record.[^1]

The third layer is a dead-letter queue with an owner. It is a contract, not storage: each message in it carries the original event ID, the full payload, a classified failure reason, the attempt count, and when it entered the queue. Implement it either as a dedicated custom object with list views by error type, when business owners need to see it inside Salesforce, or as an external queue at the middleware layer, when a technical team monitors outside. Assign an owner and a resolution SLA by event type, not system, or the queue becomes a pile nobody touches.[^1]

The fourth layer is reconciliation, the check that catches what the first three missed. Even with perfect idempotency and retry, a message can succeed technically but carry a wrong value from outdated source data. Reconciliation compares counts or aggregate sums between the two systems, such as orders created in the ERP against orders created in Salesforce for the same day, on a daily or hourly cadence depending on volume, and alerts when the discrepancy exceeds zero. It does not need field-by-field checking; an aggregate count is enough to signal that something is worth investigating.[^1]

![The four-layer integration recovery chain in order: idempotency stops duplicates and the layer beneath every retry, retry with backoff self-heals transient failures, a dead-letter queue with an owner flags permanent ones, and reconciliation catches what succeeded technically but is business-wrong](</diagrams/salesforce-error-recovery-2026/3-integration-recovery-chain.png>)

A concrete case shows why all four matter. A 40-branch retailer synced orders to an ERP with a simple synchronous REST call, no retry, no dead letter. In peak season the ERP returned timeouts on about 3% of calls, and those orders silently vanished, still marked sent in Salesforce while the ERP never saw them. In two days roughly 140 orders accumulated that never reached packing, discovered only when customers called. The fix was a Queueable layer that retried up to five times with a 1, 5, 15, 30, 60 minute backoff, a sync-status field with Pending, Synced, and Failed values, a custom object for final failures with a manual retry button, and a daily reconciliation report comparing order counts that alerted when the gap was non-zero. Detection time went from two days to under an hour.[^1]

## Platform events: the bus is at-least-once, so design the subscriber for that

Platform events are the transport underneath much of this, and their semantics are the reason the idempotency layer is not optional. A platform event is a special sObject that flows through a message bus and is delivered asynchronously to subscribers; it is not a durable database record, so the bus's delivery rules are the contract.[^6] Two facts dominate. Delivery to subscribers is at-least-once, so the same event can be delivered more than once and a subscriber that blindly inserts per event will eventually create duplicates; the fix is the idempotent, upsert-keyed handler described above.[^6] And events are retained on the bus for only 72 hours, so an external subscriber that is down across a long weekend can miss events permanently; external consumers must persist their ReplayId durably and alert as the gap approaches the retention edge, and anything that needs full history must persist it on consumption because the bus will not hold it.[^6]

Retry on the bus is bounded, and you own the final attempt. An Apex subscriber that hits a transient failure throws `EventBus.RetryableException` to ask the platform to redeliver the batch, but retries are capped by a retry count and an elapsed ceiling of roughly ten minutes, after which the platform gives up. The subscriber must check the retry context and, on the last attempt, fall back to an error log rather than throwing into the void. Without that terminal branch, a retry strategy is just delayed data loss.[^6]

![The platform event bus: publish after commit versus immediately, at-least-once delivery that requires idempotent subscribers, bounded retry via EventBus.RetryableException with a terminal log branch, and a 72-hour retention window that forces durable ReplayId persistence](</diagrams/salesforce-error-recovery-2026/4-platform-event-bus.png>)

There is also a publish-side decision that shapes failure recovery. On the event definition you choose whether the event publishes after the transaction commits or immediately. Publish After Commit fires only if the surrounding transaction succeeds, the safe default for an event that asserts something about persisted data, so a "record created" event does not leak for a record that never saved. Publish Immediately fires the moment `publish` runs regardless of the transaction outcome, which is correct for audit and telemetry where you want the "attempt happened" signal even on failure. Choosing the wrong default is a bug that only shows up under rollback conditions, which is to say in production. And always inspect the `SaveResult` from `EventBus.publish`, because an unchecked publish failure is a silently dropped message.[^6]

## Observability is the layer that ties the recovery together

Every mechanism above produces the same requirement: the failures have to be visible and triageable. That is a design decision, not an accident of the platform. Three settings make flow failures operational. Redirect flow error emails to the Apex exception email recipient list rather than the flow's last modifier, because the default is how errors disappear when people change roles. Review Failed Flow Interviews weekly, because failed resumable interviews sitting there are silent data loss in progress. And report on the error log object, because once fault paths log consistently, error volume per flow becomes a dashboard metric and a spike becomes a page instead of a surprise.[^2]

The through-line is simple. Apex has a precise transaction contract, and the platforms' defaults are either all-or-nothing rollback or a quiet caught commit; either way it is your job to decide which. Flow gives you fault paths but not retry, so retry is a pattern you assemble from a fault path, a log, and a Queueable. Integrations deliver at-least-once on a bus that purges in 72 hours, so idempotency is load-bearing, not optional. None of this is glamorous, and none of it shows up in the demo. It is the difference between an org that breaks and is discovered after a customer complains, and one that flags its own 3% failure within the hour.[^1]

The practical first move is cheap and specific. Pick the flow that matters most, open it, and count how many Create, Update, Delete, and Action elements have a fault connector. For the ones that do not, choose one of the three patterns, notify and stop or log and continue, and wire it. Then build one reusable error log object and a subflow that writes to it. That single change turns your worst silent failure into a visible one, and it is the entire point of the recovery layer.[^4]
