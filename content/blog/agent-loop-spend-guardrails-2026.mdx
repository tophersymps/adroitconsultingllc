On May 9, 2026, an operator gave an autonomous agent a modest task: register with DN42, a hobbyist network that practices real internet routing, and build an index of what it found. The agent designed its own plan. It provisioned five AWS `m8g.12xlarge` instances, each with 48 vCPUs and 192 GiB of memory, plus load balancers and Lambda functions, targeting roughly 100 Gbps of aggregate scan capacity for a volunteer-run network a small VPS could have covered. The operator noticed the charges about a day later. The initial invoice was $6,531.30 and negotiated down to roughly $1,894, still more than the operator could absorb.[^1][^2]

The interesting part is not the amount. It is where the amount came from. The model's own token bill for deciding to launch that infrastructure was trivial, a few dollars at most. The damage sat in the resources the agent created with its own hands, one tier below anything a token dashboard watches. And the failure mode was not exotic. It was a single, badly proportioned plan, waved through by an operator whose instruction to proceed "immediately without delay" functioned as a blanket authorization given without reading the resource footprint. No cost estimate preceded provisioning. No spending limit existed on the account.[^2]

Most teams running agents in production have built an instinct for the second-order version of this problem, the loop that will not stop. Framework authors ship a default turn limit, engineers set it, and everyone moves on. That instinct is correct as far as it goes, and it does not go far enough. A turn limit is a crash barrier. It bounds how many times the loop goes around and says nothing about what each lap costs, and those two numbers diverge faster than most teams expect.

## The bill scales with context, not with steps

An agent loop re-sends its accumulated transcript on every turn. Step one sends a prompt. Step five sends the prompt, four tool results, and four blocks of reasoning. Step forty sends all of it, re-priced at input rates, one more time. Nothing in that history shrinks.[^3]

The mechanism has a name in the research literature, if you like names for things. Stanford's Digital Economy Lab calls it the pricey context snowball, and it is why Stanford's measurement of coding agents diverges so sharply from simple code chat.[^4] Anthropic's task-budget documentation walks a three-request security audit with a 100,000-token allowance, and the table is worth reading twice. The request payload grows from about 20 tokens to 13,000 across the three calls, because the client resends history each time, while the budget only decrements by what the model has not already seen: 5,000, then 6,800, then 7,200.[^5] Your provider bills you for the resend. Your budget counter measures novelty. Both numbers are real, and they answer different questions.

Gartner's analysts put the aggregate multiplier at 5 to 30 times more tokens per task than a chatbot interaction for equivalent work, with provider inference cost per agentic workflow rising more than fivefold through 2028 even as unit token prices fall. They named the dynamic the inference paradox: better unit economics expand the set of workflows worth automating, and those workflows eat the savings.[^6][^7]

![Cost shape for two loops with the same model and price: the fixed-context line climbs linearly while the growing-context line bends upward, opening a gap by step 40](</diagrams/agent-loop-spend-guardrails-2026/1-cost-shape.png>)

The practical consequence is that a loop which runs eight times longer than a healthy task does not cost eight times more. It costs far more, because the eighth extra turn is priced against a context eight times larger. Any control that counts steps while ignoring context size is measuring the wrong variable.

## Your framework's ceiling is a crash barrier

Every mainstream agent framework ships a hard cap on iterations, and every one of them counts something different.[^8][^9][^10][^11] LangGraph's recursion limit counts super-steps, meaning node visits, so a single tool round trip burns two. The documented default is 1,000 super-steps as of v1.0.6, and crossing it raises `GraphRecursionError` with the message that the graph reached its maximum number of steps without hitting a stop condition.[^9][^11] The OpenAI Agents SDK counts a turn as one AI invocation including any tool calls inside it, defaults to 10, and raises `MaxTurnsExceeded` unless you handle it. Passing `None` disables the limit entirely.[^10] CrewAI's `max_iter` counts reasoning iterations before the agent must answer, defaulting to 20, with `max_retry_limit` at 2 and `max_reasoning_attempts` unlimited when left unset.[^8] The Claude Agent SDK caps tool-use round trips with `max_turns` and spend with `max_budget_usd`, and both are off when you do not set them.[^12][^13]

![Comparison table of four agent frameworks showing what each counts as a turn, its default ceiling, the exception raised, and whether the counter measures cost at all](</diagrams/agent-loop-spend-guardrails-2026/2-turn-definitions.png>)

Read that list again for what it implies. A "turn" is not a portable unit. Migrating a graph from one framework to another changes the meaning of the number, which is why a step limit that was correctly tuned before a migration can be silently wrong afterward. And three of those four counters measure activity rather than money. Ten turns with a 2,000-token context and ten turns with a 200,000-token context are the same number at the cap and wildly different numbers on the invoice.

Anthropic's own loop documentation says the quiet part plainly: without limits, the loop runs until the model finishes on its own, which is fine for well-scoped tasks and can run long on open-ended prompts, and setting a budget is a good default for production agents.[^12] Treat an inherited default in production as a bug, because nobody chose it for your workload.

## Three layers, and why one is never enough

Budget enforcement for agents works at three granularities, and the layers are not redundant. They catch different failures at different speeds.

At the top, a provider spend limit. Anthropic's API enforces monthly spend caps by usage tier, with lower self-set limits available on the billing page, and reaching the cap pauses API usage until 00:00 UTC on the first of the next month. Workspaces can carry limits below the organization's, though the Default Workspace cannot be limited at all, and batch jobs already submitted may complete slightly past the line because their items run concurrently.[^14] That is the account backstop. It is also the bluntest instrument you own: it pauses everything, healthy workloads included, and a monthly ceiling can still be consumed in twenty minutes.

In the middle, a gateway budget. Put an inference gateway in front of every model call and give each agent, team, or tenant its own key with a dollar ceiling and a reset window. LiteLLM's key objects carry exactly this vocabulary, including multiple budget windows on one key, so a key can be capped at $10 per day and $100 per month simultaneously, and the documented reason for stacking windows is precise: a single window cannot stop one bad day from consuming the month.[^15] Team budgets supersede personal ones when a key belongs to a team, and the enforcement error is explicit rather than silent.

![Three stacked budget layers, provider spend limit, gateway budget, and in-loop budget, with the granularity, what each layer stops, and what each misses](</diagrams/agent-loop-spend-guardrails-2026/3-three-brakes.png>)

At the bottom, the in-loop budget. This is the only layer that stops the run in progress. On the Claude Agent SDK it looks like `max_budget_usd`, and it is more thorough than it first appears: the cap covers subagents, their spend counts toward the parent total, and once the ceiling is reached, spawning another subagent fails outright and background subagents still running are stopped.[^13]

One warning applies to the whole middle layer. A budget control that fails open is not a control. LiteLLM enforces budgets against spend read from a database, which means a deployment without one serves requests past the ceiling: the global budget check is skipped when there is no total to compare against, a single warning is logged at startup, and nothing blocks at request time.[^15] Whichever gateway you run, verify the ceiling by actually crossing it in staging. Do not assume it because you configured it.

## Check the budget before the call, not after it

A ledger read after the response records what you already spent. Presumably you want the other order. The gate has to run before the next request leaves, and it has to project the worst case rather than the average case: tokens already sitting in the transcript plus the `max_tokens` you authorized for the response, since you control that number and it is the upper bound on what you are about to buy.[^5]

Two failure modes hide in that sentence. First, the estimate has to use `max_tokens`, not the typical reply length, because a model asked for 4,096 tokens may return 80 or may return all of them. If the gate feels too pessimistic, lower `max_tokens` on routine turns and raise it for the final summary instead of loosening the arithmetic. Second, the ledger has to be shared. If two workers cannot read the same counter before a call, your cap is per-worker and the fleet spends the sum.

![Flowchart of the pre-flight budget gate: project the worst case, compare against the run budget, check spend velocity, then call the model and write actual usage back to the ledger](</diagrams/agent-loop-spend-guardrails-2026/4-preflight-gate.png>)

## Detect the loop that stays under the cap

A loop can respect every ceiling you set and still produce nothing. Same tool, same arguments, same error, twelve times in a row, each pass adding another copy of the failure to the transcript. Turn caps do not catch it, because the loop is behaving. Budget caps catch it late, because the loop is cheap per step. The detector that catches it early is a no-progress check: hash the tool call and its result, and if the pair repeats, stop.

Framework support for this is uneven but real. LangGraph exposes the live step counter in `config["metadata"]["langgraph_step"]` inside any node, so you can branch before you hit the wall rather than catching an exception after it, and it ships a `RemainingSteps` managed value that your graph can read to degrade gracefully as the ceiling nears.[^11] That is the difference between a loop that ends with a partial answer and a loop that ends with a stack trace and a spent budget.

The rule underneath is worth stating without framework vocabulary: every iteration must produce a state change that proves progress, and the proof must be checkable without another model call. If your loop body can return the same value twice, the loop is already broken and the safety net simply has not fired yet.

## Size the ceiling from runs that worked

A cap picked for roundness will either cut real work or never fire. Derive it instead. Instrument every run to emit its final step count, its token usage, its cost, and its outcome, whether or not it hit a ceiling. Run that for two weeks with logging and no hard limits, then read the distribution of the runs that succeeded and place three thresholds: a warn line near the 90th percentile, a degrade line near the 99th that drops to a cheaper model tier or trims context, and a hard stop just above the 99th plus a small margin.

![Distribution of per-run cost for successful runs with warn, degrade, and hard stop thresholds marked at the 90th percentile, 99th percentile, and just above the observed maximum](</diagrams/agent-loop-spend-guardrails-2026/5-sizing-the-cap.png>)

Re-derive the numbers after a model migration rather than raising the cap to silence the error. Doubling a ceiling converts a loud failure into a quiet bill, and the step distribution genuinely moves when the model changes, because a turn that batches four tool calls and four turns that make them one at a time are different counts of the same work.

Two measurements decide whether any of this holds up in practice. The first is cost per completed task, not cost per call, because the loop is the transaction and per-call metrics understate agentic spend by construction. The second is spend velocity, the rate of consumption over a short window compared against a trailing baseline. A monthly ceiling of $500 still permits burning $500 in twenty minutes, and a velocity alert pages you while there is still margin to investigate. The FinOps Foundation's 2026 survey found 98 percent of its 1,192 respondents now manage AI spend, up from 31 percent two years earlier, and named granular monitoring of AI requests and tokens the single most requested capability across the whole discipline.[^16] That demand exists because the default state of agentic spend is visible only after the fact.

## What happens when the cap trips

Enforcement without a graceful path is its own outage. A run that hits a ceiling should hand back a partial, useful answer and persist enough state to resume, which is the same discipline covered in our earlier piece on [durable execution and state machines for agents](/field-notes/agent-durable-execution-state-machines-2026). Both SDKs help here: the Claude Agent SDK ends a capped run with a result message whose subtype names the cap it hit, `error_max_turns` or `error_max_budget_usd`, alongside the accumulated cost and session id, so your handler can distinguish "ran out of room" from "failed" and act accordingly.[^12][^13]

The security literature reached the same conclusion from a different direction. OWASP's entry on unbounded consumption lists denial of wallet as a first-class risk, and its mitigations read like our control stack: rate limiting and quotas, timeouts and throttling, restrictions on queued actions, graceful degradation under load, and continuous monitoring with anomaly detection.[^17]

Rehearse the kill switch before you need it. Revoke a gateway key in staging and confirm that agents degrade instead of crash-looping into their error budget, and confirm that the halt path writes state rather than discarding the work. And when a run does stop at a cap, the response is to read the trace, not to raise the number.

There is a second half to this that token budgets cannot cover, and the DN42 incident is the case for it. When an agent holds credentials that can create billable infrastructure, the control has to live at the account layer, independent of anything the agent reports about itself: hard caps and budget alarms on the role, and a cost estimate presented for human approval before provisioning starts. Our internal cron fleet runs on a fixed roster with per-run timeouts precisely because a stuck run is the failure we design against first, and on our own hardware a runaway burns GPU-hours and wall-clock rather than dollars. The arithmetic is the same either way. An agent that decides how much infrastructure its task deserves will occasionally decide wrong, and the ceiling has to exist where the model cannot argue with it.

## A working checklist

- Set the turn or super-step ceiling explicitly at every entry point. Never inherit a framework default in production.
- Add a dollar or token budget inside the loop, checked against the projected worst case before each call, not the spent total after it.
- Put every model call behind a gateway with a per-agent key, a budget window, and a reset schedule. Verify the enforcement fires.
- Track cost per completed task and spend velocity, and alert on the rate before you alert on the total.
- Detect stagnation with a repeat check on tool call plus result, and stop on no progress.
- Bound the account, not just the loop, when the agent can provision resources.
- Re-derive every ceiling after a model change, and record the model name and date next to the number.

None of this is exotic work. It is one ledger, one gate, and one alert, wired in the order that stops spending rather than reporting it. The teams that get this right do not spend less on agents on average. They simply stop discovering the outliers on an invoice.
