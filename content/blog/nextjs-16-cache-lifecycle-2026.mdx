Most teams I meet have the same vague theory of how Next.js caching works: "something gets cached, and revalidate eventually fixes it." That theory was survivable in the App Router's early days because the defaults did a lot of the work and the failures were subtle. In Next.js 16 that vagueness stops being survivable, because the framework rewrote the model and made caching explicit. The old knobs, the `fetch` `cache` option, `unstable_cache`, route-segment `revalidate`, and the ISR `revalidate` value, still work for a while, but the new model replaces them with a single idea: every piece of cacheable work carries three numbers.

The three numbers are `stale`, `revalidate`, and `expire`. Once you read those correctly, the rest of Cache Components, the `use cache` directive, `cacheLife` profiles, and the two invalidation functions, all fall into place. Get one number wrong and you ship either a page that blocks every request or a page that shows yesterday's data forever, and you will not get a compiler error for it. The syntax compiles either way. Only the behavior differs.

This is the caching-side companion to our [Next.js 16.3 instant navigations](/field-notes/nextjs-16-3-instant-navigations) piece. That article is about the request path: what a user sees while a navigation resolves. This one is about the data path: how long a cached result lives, when the server refetches in the background, and when a request is allowed to block. They sit right next to each other. The navigations article tells you to mark data with `use cache` so a route can render from cache instantly; this article tells you what that marker actually means and how long it lasts.

## What Cache Components changed

Cache Components is a feature you turn on with one flag in `next.config.ts`: `cacheComponents: true`.[^cachecomponents] Once it is on, the `use cache` directive becomes available. Put `use cache` at the top of an async function, a component, a page, or a whole file, and Next.js treats that unit's output as cacheable. Functions and components marked with `use cache` must be async.[^usecache]

The change from the old model is not the flag. It is the mental model underneath. In the previous model, caching behavior was spread out across several mechanisms that each claimed part of the job: `fetch` had a `cache` option and a `next.revalidate` option, `unstable_cache` wrapped database calls, and route segments exported a `revalidate` constant. Each of those interacted with the rendering model in ways you had to remember, and a subtle interaction, for example a `fetch` before a `cookies()` call becoming static, was a footgun.

Cache Components compresses all of that into the directive plus `cacheLife`. You decide what to cache by placing `use cache`, and you say how long it lives by giving that scope a `cacheLife` profile. Next.js recommends pairing every cache directive with a `cacheLife`; without one, an implicit `default` profile applies, which most people should not rely on because its exact values are easy to forget.[^recom]

## The three numbers a cache owns

Every cached result, no matter the profile, is governed by the same three timing properties.

`stale` is a client-side number. It is how long the client's router can display the cached content without checking the server. During the `stale` window, a navigation shows the cached UI with zero network request, so it is instant. After it expires, the router must check with the server on the next navigation or request. The default profile sets `stale` to five minutes, taken from `staleTimes`.[^staletime]

`revalidate` is a server-side number. It is how often the server regenerates the cached content in the background. When a request arrives after this period, the server serves the cached version immediately, then regenerates fresh content in the background and replaces the cache. This is the same idea as Incremental Static Regeneration, expressed as a cache lifetime. The default profile sets `revalidate` to fifteen minutes.[^revalidate]

`expire` is the hard ceiling. It is the maximum time before the server must regenerate the cached content, and it behaves differently from `revalidate`: after `expire`, if there has been no traffic, the next request regenerates synchronously and waits. So `revalidate` trades a background refresh for staleness, while `expire` trades a blocking request for correctness. When you set both, `expire` must be longer than `revalidate`; Next.js validates this and errors on an invalid configuration.[^expire]

![The three cache timing values a client and server side: stale is how long the client shows cached content without checking the server, revalidate is how often the server regenerates content in the background, and expire is the hard ceiling after which a cold request regenerates synchronously and waits.](</diagrams/nextjs-16-cache-lifecycle-2026/1-three-timing-values.png>)

The reason the ordering matters is that the three values answer three different questions about the same result. `stale` answers "how long can I avoid a round trip?" `revalidate` answers "how fresh does the data have to be on the server?" `expire` answers "how stale am I willing to let it get before I block?" Most caching confusion traces back to treating all three as one. They are not one. A five-minute `stale`, a fifteen-minute `revalidate`, and a never-`expire` mean a page can show data that is up to the age of the slowest regenerated entry, while feeling instant on every fast navigation. That is the default profile, and it is a tradeoff, not a bug.[^defaulttable]

## Reading a cache profile

Next.js ships six preset cache profiles, plus `default`. Each balances the same three factors: how long users see cached content without checking, how often the server regenerates, and when old content expires completely. The profiles are named for how often content changes.

- `seconds` for real-time data like stock prices or live scores
- `minutes` for frequently updated content like social feeds and news
- `hours` for content updated multiple times a day, like product inventory or weather
- `days` for daily updates like blog posts
- `weeks` for weekly updates like podcasts and newsletters
- `max` for content that rarely changes, like legal pages and archived pages[^proflabels]

| Profile | Use case | `stale` | `revalidate` | `expire` |
| --- | --- | --- | --- | --- |
| `default` | Standard content | 5 min | 15 min | never |
| `seconds` | Real-time data | 30 sec | 1 sec | 1 min |
| `minutes` | Frequently updated | 5 min | 1 min | 1 hour |
| `hours` | Multiple updates/day | 5 min | 1 hour | 1 day |
| `days` | Daily updates | 5 min | 1 day | 1 week |
| `weeks` | Weekly updates | 5 min | 1 week | 30 days |
| `max` | Rarely changes | 5 min | 30 days | 1 year |

Notice what the presets actually differ on. `stale` stays at five minutes across every profile, because the client experience of using cached UI for five minutes is the same regardless of how often the underlying data changes. What changes is the server side: how eagerly ahead of the reader's patience the server regenerates. `revalidate` climbs from one second to thirty days, and `expire` follows it from one minute to a year. So picking a profile is really picking how stale you let the server's copy get before it blocks, not how long the client waits.

![Seven Next.js cache profiles compared: default, seconds, minutes, hours, days, weeks, and max, each showing how the stale, revalidate, and expire values change while stale stays at five minutes and revalidate and expire climb.](</diagrams/nextjs-16-cache-lifecycle-2026/2-cache-profiles.png>)

Three of these presets are safe defaults for whole classes of content, and starting there is fine. Real-time dashboards reach for `seconds`. A blog or catalog reaches for `hours` or `days`. Static legal or archived pages reach for `max`. The trap is reaching for a preset because it sounds fast without checking what `expire` does to your cold-start behavior. A heavily cached route with `days` can serve a stale snapshot to a real person for up to a week if `expire` passes with no traffic and the data truly is cold. That is often fine for blog content and wrong for a shopping cart.

## Where `use cache` belongs

The directive works at two levels, and they cache different things.

Data-level caching puts `use cache` inside a function that fetches or computes data. `getUsers()`, `getOrderSummary()`, a database query, all qualify. This is useful when the same data feeds multiple components, or when you want to cache the data independently of the UI that renders it. The function's output becomes the cache entry, keyed by its inputs.[^datalvl]

UI-level caching puts `use cache` at the top of a whole component or page. The rendered output, the JSX, is what gets cached. Use it when several components render the same view, or when you want the entire section cached as a unit. The blog example below, where a page renders a list of posts fetched once and revalidated hourly, is the canonical case.[^uilvl]

```tsx
export default async function BlogPage() {
  'use cache'
  cacheLife('days')
  const posts = await getBlogPosts()
  return renderPosts(posts)
}
```

Whatever level you choose, there is a hard constraint: cached functions cannot read request-time APIs like `cookies()`, `headers()`, or `searchParams`, and the restriction follows the call stack. A helper a cached function calls that reads one of these fails the same way, with the `next-request-in-use-cache` error. On a dynamically rendered route the failure surfaces when the route runs, which means it can pass `next build` and fail under `next start`.[^constraint] That is one of the most important gotchas in the model. The fix the docs recommend is to read those values outside the cached scope and pass them in as arguments; the values then become part of the cache key, so different users naturally get different entries.[^passargs]

## How a cache key is built

A cache entry is identified by more than the function name. Next.js builds the key from four parts: the build ID, which is unique per build and changing it invalidates every cache entry; the function ID, a secure hash of the function's location and signature; the serializable arguments, which are the props for a component or the arguments for a function; and, in development only, an HMR refresh hash that invalidates the cache on hot module replacement. When a cached function references a variable from an outer scope, that variable is automatically captured and bound as an argument, so it joins the key too.[^key]

The practical consequence is that caching is precise without you doing extra work. Two different `userId` values produce two separate cache entries, because the captured `userId` is part of the key.[^closure] And because the build ID is part of the key, a new deploy invalidates all cache entries, including durable remote ones. Fresh deploy, fresh cache, no manual purge.[^buildid]

Arguments and return values must be serializable. Primitives, plain objects, arrays, Dates, Maps, Sets, TypedArrays, and ArrayBuffers work as arguments; return values accept those plus JSX elements. Class instances, functions (except as pass-through), Symbols, WeakMaps, WeakSets, and URL instances do not.[^serial]

## Invalidation: the two functions that change data

Caching is only half the job. The interesting part is knowing which of the two invalidation functions to call, because they have opposite freshness semantics.

`updateTag` is for read-your-own-writes. It can only be called from inside a Server Action, and it immediately expires the cached data for a tag. The next request waits for fresh data rather than serving stale content, so the user who just made a change sees it immediately. If a user creates a post, you call `updateTag('posts')` inside the action, then `redirect` to the new post, and the next read reflects the change.[^updatetag]

`revalidateTag` is for stale-while-revalidate, and it can be called from Server Actions and Route Handlers. It marks the tagged data as stale. The next request for that data is served stale content while a fresh copy regenerates in the background. The second argument controls how long stale content may be served; the recommended value is `max`, a one-year window that practically always serves stale content while revalidation runs. Without that window, or with `{ expire: 0 }`, the next request blocks until the revalidation completes.[^revalidatetag]

![The two cache invalidation paths: a user-triggered server action calls updateTag so the next read is fresh immediately, while an external webhook or route handler calls revalidateTag to serve stale content during a background refresh.](</diagrams/nextjs-16-cache-lifecycle-2026/3-invalidation-paths.png>)

The choice between them is a statement about who can wait. If the person who caused the change is also the next reader, you want `updateTag`, because they expect their own write to be visible. If the invalidation comes from outside, say a CMS webhook or another service hitting a Route Handler, `updateTag` is not available and you use `revalidateTag` with `max` or an explicit expire window.[^routehandler]

There is also `revalidatePath`, which invalidates every cached entry for a specific route path rather than a tag. It is useful when you want to refresh a route without knowing which tags it uses. For a migration, the docs give the rule of thumb: `updateTag` for read-your-own-writes, `revalidateTag` with `max` for background revalidation, and `revalidatePath` for whole-route refresh when tags are unknown.[^path]

![A decision flow for choosing how to refresh cached data: a user finishes a mutation in a server action, use updateTag for immediate visibility; a webhook or external service triggers refresh, use revalidateTag with max for stale-while-revalidate; a route needs a full refresh and you do not know its tags, use revalidatePath.](</diagrams/nextjs-16-cache-lifecycle-2026/4-revalidation-decision.png>)

## What ISR means now

Incremental Static Regeneration is not gone, it is reborn as an interaction between `use cache`, `generateStaticParams`, and the App Shell. When you prune dynamic params with `generateStaticParams`, Next.js prerenders the listed URLs at build time. A visit to any other URL gets the App Shell instantly, then the page is upgraded in the background with its now-known params and cached for the next visitor. A prefetch counts as that first visit, so navigating to an unlisted URL lands on the upgraded result.[^isr]

The practical translation from the old model is clean. If you came from the Pages Router, `fallback: true` in `getStaticPaths` is now the default behavior; `router.isFallback` is no longer needed; `getStaticProps` with `revalidate` maps to `use cache` with `cacheLife`; and `getStaticPaths` maps to `generateStaticParams`.[^isrmap]

## The migration instinct that matters

Teams migrating to Cache Components usually skip straight to the syntax. That is the easy part, and it is not where migrations fail. They fail on the three numbers, specifically on the instinct to set everything to `seconds` because real-time feels safer. It is not safer. `seconds` sets `expire` to one minute, which turns any route quieter than one request a minute into a synchronous, blocking regeneration on every visit, which is the exact opposite of the instant navigation the framework promises.

The better instinct is to start with the stable preset that matches the content's real update cadence, get the page rendering from cache, then tighten toward `seconds` only on the specific sub-components that genuinely need real-time data, and leave the durable UI on the slower profile. We use this same reasoning inside our own delivery pipeline, where a shared server-rendered dashboard caches its catalog on `hours` while a live status bar on the same page runs on `seconds`. Both are correct, because each answers a different freshness question.

Set the profile, tag the cache, and choose the invalidation function on the semantics of who is waiting. Read those three numbers and the directive rewards you with routes that render instantly and refresh without blocking. Misread them and the same syntax quietly serves stale data or stalls cold requests, with no error from the compiler. That is the whole leap from the old model: caching is no longer a mystery to debug, it is a contract you write down in three numbers.
