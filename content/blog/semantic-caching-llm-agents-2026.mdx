Every LLM call in your stack is a chance to skip the model entirely. The provider-side prompt caching most teams already run only fires when the input is byte-for-byte identical, which is why it does so little for natural language. Users rarely phrase the same question the same way twice, so an exact-match cache sits populated and almost never fires.[^1] Semantic caching closes that gap by matching on meaning instead of text: embed the incoming request, search a vector store for a similar prior request, and if the similarity clears a threshold, return the stored answer without calling the model at all.[^2]

The savings are real and large. A cache hit replaces a several-hundred-millisecond model call with a tens-of-milliseconds vector lookup, and it removes the per-token charge entirely.[^2] Oracle's engineering team reports response-time improvements around 97 percent on cached queries, from roughly 1.67 seconds down to about 0.05 seconds, and token reduction that tracks the hit rate almost one for one.[^3] LogicMonitor's controlled tests measured cache hits cutting response times by 50 percent, a 2.5x speedup, on the second run of a semantically similar prompt.[^1]

But semantic caching is the one caching layer where "it works in the demo" and "it is safe in production" are very different claims.[^2] The whole safety of the trade lives in two places: the similarity threshold you match on, and what you allow into the cache in the first place. Get the first wrong and you serve confident answers to questions that were never quite asked. Get the second wrong and you can serve one user's data to another, a privacy failure, not just a wrong answer.[^2] This article is both halves: how the mechanism works, the single knob that governs it, the cases where it quietly serves the wrong answer, and where the cache should live.

## The three layers of LLM caching, and which one this is

"Caching" in an LLM stack covers three distinct mechanisms with very different reach and risk, and it is worth being precise about which one you are deploying, because they compose rather than replace each other.[^2]

Provider prefix caching reuses an exact, identical prompt prefix, the system prompt and tool definitions that repeat unchanged across calls. The provider matches on an exact prefix and bills the repeated portion at a steep discount. It is automatic, safe, and it never serves a wrong answer because it only matches identical text.[^2] This is the layer our earlier piece on prompt caching covers in depth, and it is the cheapest token you are not claiming when your workload has a stable head and a growing tail.[^4]

Exact-match response caching hashes the entire normalized request and returns the stored response on an identical hash. Also safe, identical input produces identical output, but the hit rate is low, because users rarely phrase things identically.[^2]

Semantic caching is the third layer and the subject here. It embeds the request and serves a cached response when a similar prior request exists. This is where the hit rate jumps, because "where is my package?" and "has my order shipped yet?" can share a cached answer, and it is also where the risk appears, because "similar" is a judgment call made by a similarity threshold rather than an exact match.[^2]

![The three layers of LLM caching: provider prefix caching reuses an exact prompt prefix at a billing discount, exact-match response caching hashes the whole request, and semantic caching embeds the request and serves a similar prior response, the layer with the highest hit rate and the only one that can serve a wrong answer.](</diagrams/semantic-caching-llm-agents-2026/1-three-layers.png>)

The distinction matters for a practical reason. Prompt caching is a provider feature: the provider still generates a fresh completion, it just bills the repeated prefix at a lower rate. Semantic caching is a gateway feature: on a hit, the provider is never called, and a stored response is returned instead.[^5] That is why the two are independent and can run together. You cache the static prefix on every call, and you semantically cache whole responses only on the routes where it is safe.[^2]

## How semantic caching works: embed, match, serve

The mechanism is three steps. Embed the incoming request into a vector. Search a vector store for the nearest prior request within the right scope. If the nearest neighbor's similarity exceeds a threshold, return its stored response; otherwise call the model and store the new request and response pair for next time.[^2]

On a hit, you have replaced a model call, typically several hundred milliseconds and a per-token charge, with an embedding call and a vector lookup, on the order of tens of milliseconds and a fraction of the cost. On a miss, you have added the embedding and lookup latency to the normal model call, which is the small tax you pay for the chance at a hit. The economics of that trade depend entirely on the hit rate, and the safety depends entirely on the threshold.[^2]

The storage is a vector database that doubles as a cache. Oracle's team describes running it on Valkey Search, which combines cache storage and vector search in one system: create an HNSW index, make sure the vector dimensions match the embedding model output, insert data as hashes or JSON documents, and query with FT.SEARCH.[^3] The vector lets you find semantically similar requests; the cached value lets you reuse a previous response. The tradeoffs are the usual vector-store ones, HNSW memory can be high, and the operational complexity depends on your infrastructure.[^3]

![The semantic cache lookup path: an incoming request is embedded into a vector, searched against a scoped vector store, and if the nearest neighbor clears the similarity threshold the stored response is returned without calling the model; on a miss the model is called and the new request and response pair is stored for next time.](</diagrams/semantic-caching-llm-agents-2026/2-embed-match-serve.png>)

## The similarity threshold is the whole game

The threshold decides how close a new request must be to a cached one to count as a hit, and it is a direct precision and recall tradeoff. Set it too low, accept loose matches, and the hit rate is high but you serve answers to questions that were not quite asked. Set it too high, demand near-identical phrasing, and the cache is safe but rarely fires, collapsing toward exact-match caching with extra steps.[^2]

There is no universal correct value, because it depends on the embedding model, the domain, and how much a wrong answer costs you. The way to set it is empirical: assemble labeled pairs of requests that should and should not share an answer, sweep the threshold, and pick the point where false hits drop to an acceptable rate for that route. High-stakes routes, anything touching money, health, or identity, warrant a conservative threshold or no semantic caching at all. Low-stakes informational routes, documentation Q&A and general explanations, can run looser. Per-route thresholds, not one global number, are the production pattern.[^2]

Oracle's worked example shows the tradeoff concretely. A query about machine learning has three possible cached matches: a strong match at a similarity score of 0.94, a weaker one at 0.76, and a loose one at 0.52. At a threshold of 0.90, only the strong match returns. Lower the threshold to 0.75 and the cache returns the 0.76 match, which is a different concept. Lower it to 0.50 and it returns the 0.52 match, which is barely related. A high threshold gives more accurate matches but fewer hits; a lower threshold increases hits but may return answers that are less relevant to the original query.[^3]

## Embedding-close is not meaning-equal

The core hazard is simple to state and easy to underestimate: embeddings capture topical similarity, not logical equivalence. "What is the capital of France?" and "What is the capital of Germany?" sit extremely close in embedding space, same structure, same domain, one word different, yet they require different answers. A threshold tuned for recall will treat them as the same question.[^2]

The mitigations stack, and none is complete on its own. A conservative threshold reduces loose matches. Entity and keyword guards add a check that the salient entities, the country, the order number, the product, match before serving a hit, catching the France and Germany case that pure cosine similarity misses. Per-namespace caches keep distinct contexts from colliding. And the most reliable mitigation is upstream: do not cache the classes of request where a near-miss is dangerous at all.[^2]

![The embedding-close-is-not-meaning-equal failure: two queries sit inside the same similarity ring in embedding space, so a recall-tuned threshold treats them as the same question, but they require different answers, and a personalized query cached without user scope can serve one user's data to another.](</diagrams/semantic-caching-llm-agents-2026/3-embedding-close.png>)

The canonical failure is the cold open. TrueFoundry's engineers describe a backend engineer who put a semantic cache in front of a support assistant and had a good week, model-call volume dropped 35 percent and latency on hits fell from roughly 900 milliseconds to under 40, and then a bad one. A customer asked "where is my delivery?" and got a confident, detailed answer about someone else's order. Two customers had asked semantically identical questions minutes apart; the cache embedded both to nearly the same vector, scored a hit, and served the first customer's answer to the second.[^2]

The cache was working exactly as designed. It just had no idea that "where is my delivery?" means something different depending on who is asking. The embedding does not encode the user, so a personalized answer cached without user scope is a data-leak vector, not just a wrong answer.[^2]

## What you must never cache

Some responses are unsafe to serve from a similarity match regardless of how good the threshold is, because the thing that makes two requests different is not in the text the embedding sees. The safe default for all of these is "do not semantically cache," and the exception should require an explicit per-user scope.[^2]

Personalized responses are the first class. "Where is my order?" depends on who is asking, and a mis-scoped cache serves one user's data to another. Time-sensitive answers are the second: "what is today's balance?", statuses, prices, correct at write time and wrong minutes later. Oracle's example is the weather in Seattle today versus tomorrow, semantically similar, but they must not return the same cached answer.[^3] Stateful conversational turns are the third, because the right answer depends on prior turns in the session, which a single-request embedding does not capture. High-stakes outputs are the fourth: money, health, legal, identity, where the cost of one false hit outweighs the cost saving.[^2]

The same logic applies to cross-user data. "What is my account balance?" and "What is John's account balance?" may look structurally similar, but they must never share cached responses across users.[^3] This is where the cache key design does the real work.

## Cache key design, scoping, and invalidation

A semantic cache entry is not keyed by text alone; it is keyed by an embedding inside a namespace, and the namespace is where correctness is enforced. The namespace should encode everything that makes two textually similar requests genuinely different: the tenant or user for anything user-specific, the model, the system-prompt version, and the active tool set. Two identical questions under different system-prompt versions are different questions, because the instructions that shape the answer changed.[^2]

The correctness story is built in via two-level namespacing. Level one is automatic: every cache entry is scoped to the calling user or virtual account, so User A's request can never hit User B's entry. Level two is optional: a namespace field partitions further, per tenant, per environment, per system-prompt version. Together they make a gateway-level semantic cache safe to share across services without each one re-implementing isolation.[^2]

Invalidation has two triggers. Time, via a TTL chosen for how fast the underlying truth changes, short for anything that drifts, longer for stable reference answers. And version, via the namespace: bumping the system-prompt version or changing the tool set rolls the cache forward, so stale answers from the old configuration are never served. The failure to invalidate on a prompt change is a common and subtle bug: the prompt improves, but cached answers keep reflecting the old one until the TTL expires.[^2]

## The economics: hit rate governs everything

The value of semantic caching is governed by one number: the hit rate. As an illustrative model, suppose a route runs at some per-call model cost and the cache achieves a 30 percent hit rate at a safe threshold. Roughly 30 percent of requests now skip the model call, so cost on that route falls by close to 30 percent, minus the embedding and lookup cost, which is small relative to a generation. Latency improves on exactly those 30 percent of requests, dropping from a several-hundred-millisecond generation to a tens-of-milliseconds lookup, which pulls down both the average and the tail.[^2]

Oracle's rule of thumb is that token reduction tracks the hit rate almost one for one: a 20 percent hit rate means about 20 percent fewer LLM tokens, 50 percent means about 50 percent fewer, 70 percent means about 70 percent fewer, when a hit lets you skip the LLM call entirely.[^3] A realistic useful range is often 20 to 60 percent if your traffic has repeated intent, and it can reach 80 percent or more on narrow, repetitive workloads like support bots, docs Q&A, and internal assistants.[^3]

Two honest caveats on the math. The hit rate is workload-specific, a narrow FAQ-style assistant might see far more than 30 percent while a long-tail creative workload might see almost none, so the only credible number is the one you measure on your own traffic. And the savings are net of the embedding tax on every miss; if your hit rate is very low, you can spend more on embeddings than you save. Measure the cacheable fraction before committing, rather than assuming a headline rate.[^2]

The multi-agent case is where the numbers get interesting. A single agent resolving one support ticket might make five to ten LLM calls, and a multi-agent application can trigger many more across planners, tools, reviewers, and summarizers.[^1][^3] Without caching, costs grow quickly. A production study of a multi-agent natural-language-to-code system for enterprise analytics reported a 67 percent cache hit rate on production queries, a dual-threshold decision mechanism that separated exact-match retrieval from reference-guided generation, and a 40 to 60 percent reduction in token consumption through intent-driven prompt assembly, while maintaining 94.3 percent semantic accuracy across more than 10,000 queries.[^6]

## Where the cache lives: gateway versus application

A semantic cache can live in the application, but the gateway is the stronger default for the same reasons that apply to routing and reliability: it already sits on every request, so the cache is shared across services rather than reimplemented in each, and it already holds the per-call cost and latency telemetry needed to measure whether the cache is actually paying off.[^2]

The division of labor is the one that recurs across the LLM gateway stack. The gateway provides the shared, scoped, observable cache: one place to enforce per-tenant scoping, one place to see the hit rate, cost saved, and latency saved. The application owns the policy decision of which routes are safe to cache and at what threshold, because only the application knows that "where is my delivery?" is personalized and "what is your return window?" is not.[^2] This mirrors the control-plane argument for model routing and gateway governance we have covered elsewhere: the gateway is the natural place for cross-cutting concerns, and the application keeps the domain judgment.[^7]

## The discipline that makes it safe

Semantic caching earns real cost and latency wins on the routes where similar questions genuinely share an answer, and the discipline that makes it safe is knowing, route by route, which questions those are.[^2] The threshold is a precision and recall tradeoff you tune per route, not a global constant. The namespace is where correctness is enforced, carrying tenant, model, and prompt version so a lookup can never return another user's data or an answer shaped by an old prompt. And the never-cache list is upstream of all of it: personalized, time-sensitive, stateful, and high-stakes responses do not belong in a similarity match at all.

The teams that treat semantic caching as a tool with a known failure mode they design around will carry a structurally lower unit cost into every task they automate. The ones that treat it as a transparent speedup they can apply everywhere will keep paying for it in a different currency: a confident wrong answer, or worse, a data leak that the cache was working exactly as designed to produce.[^2]
