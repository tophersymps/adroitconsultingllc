A Salesforce org defends itself against a lot of things well. A login from an unfamiliar country gets challenged. A profile without the API Enabled permission cannot call the API. A departing employee loses their session the moment their user is deactivated. Every one of those defenses assumes the attacker starts by logging in as somebody. The three largest Salesforce data theft campaigns of the past year never did.

In August 2025, a threat actor tracked as UNC6395 used compromised OAuth tokens tied to the Salesloft Drift application to pull data out of customer Salesforce instances. The actor ran count queries against Account, Opportunity, User, and Case to size each org before pulling detail records, then deleted its query jobs to cover the trail. Google's threat intelligence team assessed the goal was credential harvesting: the stolen data was searched for AWS access keys, passwords, and Snowflake tokens.[^1] On August 20, 2025, Salesloft and Salesforce revoked every active access and refresh token for the Drift application, and Salesforce pulled it from the AppExchange.[^1][^2] There was no vulnerability in the Salesforce platform, and no customer misconfiguration was required. The tokens were valid, so the API accepted them.[^1]

The pattern repeated. In November 2025, attackers used tokens taken from the Gainsight application to read data across customer Salesforce orgs, with an exposure window running from October 23 to November 19 before Salesforce disabled the connections.[^5] In June 2026, an extortion crew got into Klue's integration infrastructure through a legacy credential created for a pilot that never shipped, used that access to push code that harvested the OAuth tokens Klue's customers had granted, and then queried Salesforce REST APIs at connected customer environments with automated Python scripts, running for roughly 24 hours per target.[^3][^4] Klue's own account is the plainest version of the story: an attacker gained access through a compromised legacy credential associated with an integration service, used it to obtain OAuth tokens connecting Klue to third party platforms including Salesforce, and accessed data within connected customer environments.[^3]

Read those three incidents as one campaign and the conclusion is uncomfortable. The most valuable credential in your org is not a password. It is the refresh token you issued to a vendor two years ago and have not looked at since, held by an application your users authorized in a demo, running under the permissions of an integration user whose job title no longer exists on the org chart.

## Why this attack class does not trip your alarms

Every control in the login path is designed for a human arriving at an authentication endpoint. The token path skips that endpoint entirely. Whoever holds a valid refresh token exchanges it for an access token on demand and then calls the API, and as far as Salesforce is concerned the application is doing exactly what the customer authorized it to do.

That is why the incident response guidance from Google's investigation reads like a forensics checklist rather than a firewall list. It recommends reviewing event monitoring logs for unusual activity associated with the connection user, reviewing authentication activity from the connected app, and reviewing query events that log executed SOQL queries.[^1] The tells were the ones that live beside a valid session, not in front of it: malicious user agent strings such as `Salesforce-Multi-Org-Fetcher/1.0` and `Salesforce-CLI/1.0`, and traffic from virtual private servers and Tor exit nodes.[^1] The extortion stage that follows is not incidental either: the FBI's advisory on this campaign class describes the stolen data being turned into leverage against the affected organizations, which is what makes the window between theft and response so expensive.[^14]

The uncomfortable part for a platform team is the tempo. ReliaQuest's telemetry from the Klue incident showed automated Python scripts against the Salesforce REST API, exfiltrating data over roughly a 24-hour window per environment.[^4] Twenty-four hours is not enough time for a monthly security review to notice, and the queries look authorized, so a first responder looking for failed logins or a suspicious device will find nothing at all.

![The three incidents drawn as one timeline: August 2025 Salesloft Drift with tokens revoked on August 20, November 2025 Gainsight with connections disabled on November 20 after an exposure window opening October 23, and June 2026 Klue where a credential created for a 2022 pilot was used to harvest customer tokens, showing the same three stage mechanism of vendor compromise to token theft to authenticated exfiltration in each case](</diagrams/salesforce-oauth-token-governance-2026/2-incident-timeline.png>)

## The four controls that landed in May, and what each one does

Salesforce's answer was not a customer-side setting. It was a requirement placed on the applications themselves. Any Connected App or External Client App shipped in connection with a partner application and in use by more than two customer production orgs had to implement four OAuth controls by May 11, 2026, the same date for all four, with non-compliance carrying a risk of AgentExchange de-listing or suspension of the application's ability to interoperate with Salesforce services.[^6]

Understanding each control matters because they fail in different places and require different client changes.

**Proof Key for Code Exchange (PKCE)** protects the authorization code flow against intercepted authorization codes. The client generates a high-entropy `code_verifier`, sends a hashed `code_challenge` with the authorization request, and presents the original verifier at the token endpoint. Confidential clients send both the verifier and the client secret; public clients must omit the client secret entirely, because the verifier is the only identity proof the flow relies on.[^6]

**Refresh Token Rotation (RTR)** makes each refresh one time use. The old refresh token is invalidated when a new one is issued, so a stolen token stops working as soon as the legitimate client performs its next refresh. Salesforce calls it a critical defense against long term session hijacking, and the client changes are the hard part: the application has to capture and persist the new refresh token on every refresh, detect a rejected refresh as a possible compromise signal, and handle the race condition where parallel refresh requests compete for the same token.[^6]

**The 30-day idle Time-to-Live (TTL)** invalidates a refresh token that has not been used for 30 days. Each use resets the clock, so an active nightly integration never notices it, and a job that runs once a quarter notices it every time.[^6]

**The Refresh Token IP Allowlist** rejects refresh requests from any address outside a registered set of ranges, which is the control that most directly answers the Drift pattern: a stolen token is useless from an attacker's network when the refresh must originate from the vendor's own egress.[^6]

Two details turn this from a vendor's problem into your project. First, PKCE and RTR cannot be disabled once enabled, so the switch is permanent.[^6] Second, all four controls change behavior at the token endpoint, which means every integration built on the old assumption of a stable, indefinitely reusable refresh token is a candidate for a break when its vendor ships the update.

![The four OAuth controls mapped across the three layers that have to change: at the partner application layer the vendor enables PKCE, refresh token rotation, the 30 day idle timeout, and the refresh token IP allowlist; in your org the administrator deals with re-authorization prompts and the new credential that comes with a migrated app; and in your client code the integration must store rotated tokens, serialize parallel refreshes, refresh before the idle limit, and originate from an allowlisted address](</diagrams/salesforce-oauth-token-governance-2026/3-four-controls-layers.png>)

## What breaks when the controls turn on

The failure mode is not the control, it is the client that assumed the old behavior. Four breakages show up repeatedly in orgs that turn these settings on.

**Parallel refresh race.** An integration that refreshes from multiple workers, containers, or cron hosts at the same time will eventually have two workers present the same refresh token. The first exchange succeeds and rotates the token; the second is rejected. Salesforce names this race condition explicitly and requires clients to handle it.[^6] The fix is a single-flight refresh, a lock or queue so only one refresh runs per credential at a time and every other worker reads the new token from shared storage rather than refreshing independently. The related mistake is treating every rejected refresh as a compromise. A rejected refresh may mean the token was rotated by a sibling process; the client should re-read the stored token once before escalating.

**Idle expiry on low-frequency jobs.** The 30-day idle TTL resets on use, which is what makes it safe for integrations that talk to Salesforce daily and dangerous for the ones that run on a calendar. A quarterly reconciliation, an annual audit extract, or a seasonal import will find an invalid token every single run and will need either a scheduled refresh before the 30-day mark or an acceptance that a human re-authorizes it.[^6] That decision belongs in design, not in the runbook after the first 2 a.m. failure.

**Allowlisting when your egress moves.** The IP allowlist only works if both ends have stable addresses. Cloud hosted middleware that autoscales behind changing outbound addresses cannot be allowlisted until the network work is done, and the vendor side has published ranges you must add on your side so their refresh traffic is not rejected. Coordination is the work here, and the coordination is per integration.

**The absent authorizer.** A refresh token is bound to the user who granted it. Deactivate or freeze that user, and the grant dies with them, which is a genuinely useful security property and a surprisingly common cause of a broken nightly job. It also cuts the other way: the most common way to break a token path an attacker is using is to deactivate the integration user, which is the fastest mitigation available during an incident.

The org-side hardening list from the Drift investigation is worth keeping as a configuration review, because it targets the same credential surface from the other direction: review and restrict connected app scopes so nothing holds full access it does not need, set the app's IP relaxation policy to enforce IP restrictions, define login IP ranges on the integration user's profile, remove the API Enabled permission from profiles and grant it only through a permission set where it is actually required, and tighten session timeout values to limit the life of any session that is compromised.[^1]

## The inventory nobody keeps

The Klue incident has a detail that should make every Salesforce administrator uncomfortable. The credential that opened the door was created in 2022 for a limited pilot and left active long after the pilot ended.[^3] It was not a sophisticated intrusion technique. It was a piece of configuration that nobody had a reason to revisit, because no system reported on it and no person owned it.

Salesforce made the creation side harder to get wrong. In the Spring '26 release, creating new Connected Apps is restricted by default across both the Setup user interface and the Metadata API, with package installation as the exception, and re-enabling creation now requires a request to Salesforce Support.[^7][^8] External Client Apps are the intended replacement, and their security posture is structurally different in ways that matter to an inventory: an External Client App is local and secure by default, does not exist in a target org until it is installed, requires explicit authorization through profiles or permission sets, and does not support the retired username and password OAuth flow at all.[^7][^8] The older model let any user with API access self-authorize a globally defined application, which is the surface that social engineering attacks and shadow integrations exploited.

That shift also creates the migration problem. An External Client App gets a different consumer key and secret, so migrating is a cutover per integration, not a rename, and every system holding the old credentials has to be updated in the same window. The flow choice that replaces each retired pattern is a design decision rather than a swap, and we covered that decision, including when the web server flow is the right answer over client credentials, in [the identity seam piece](/field-notes/salesforce-integration-seams-2026). The enforcement calendar those retirements sit on, with the dates that force each migration, is laid out in [the release discipline guide](/field-notes/salesforce-release-discipline-2026). What matters here is that the org-side default is now deny by default, which means your inventory stops growing on its own but does not shrink on its own either.

Finding what is already there is a matter of four screens and one report. The Connected Apps OAuth Usage page lists every application that has been used to authenticate, with a user count you can open to see who authorized the app and when they last used it, and it is also where you block an application outright or revoke a single user's grant. A report on the OAuth token object surfaces authorizations that have not been used in 90 days, which is the prioritized list for a deeper review. Login History shows which applications have actually been authenticating, which is a more honest signal than which applications exist. The Setup Audit Trail shows who created or changed an authentication configuration and when. Run those four against a real org and the usual find is a handful of applications nobody can name an owner for, at least one authorized by a user who left, and a pair of entries that turn out to be the same integration configured twice during a migration that stopped halfway.

## What you can actually see

Detection data in Salesforce splits along a license line that most stakeholders do not know exists until they ask for a log that is not there. A base license includes daily event log files for a core set of event types, including Login, Logout, and Apex Unexpected Exception, and file retention on that tier is 24 hours. Event Monitoring unlocks more than 70 event types, hourly file generation, and longer retention on platform.[^9][^10] The gap between those tiers is the difference between knowing that somebody logged in and knowing what they queried after they did.

With Event Monitoring in place, the event types that matter for a token incident are not the login events. They are API volume, bulk API results, report exports, list view queries, and session events, plus the Threat Detection anomaly events that Salesforce ships prebuilt. And here the platform's own guidance contains the sentence every architect should read twice: the anomaly events, including API anomaly, guest user anomaly, and report anomaly, can take hours to complete, are statistical in nature, and are explicitly not a real-time blocking control.[^11] For deterministic real-time enforcement, Salesforce points to Transaction Security Policies, which evaluate the same event stream against known-pattern rules and can block or challenge an action as it happens, with blocking an oversized list view access given as the worked example.[^11] In other words, the statistical layer tells you what happened hours ago, and the policy layer is what stops the next export.

Salesforce's forensic guidance also draws the line that matters for an integration rather than a person. Anomaly detection works best when behavior is consistent and predictable, and a non-human identity is exactly that, which is why per application baselines outperform per user baselines for this threat class. Salesforce's published method runs SOQL against event logs for the past 180 days, builds per identity baseline statistics, and scores deviations, with a thin baseline path for identities that do not have enough history to score.[^11] Their Log Analysis Guide goes deeper into the specific log files and event types.[^12] Historical event data beyond the standard window is available separately.[^13]

## The order to do it in

The remediation sequence that holds up starts with naming owners, because every later step depends on a person being accountable for an integration.

1. **Inventory and assign an owner per application.** Use the OAuth Usage page, the OAuth token report, Login History, and the Setup Audit Trail together. Every application gets a named owner and a stated purpose, and anything without either is a revocation candidate rather than a maybe.
2. **Revoke what has no owner or no use.** Block the application or revoke the individual grants, then confirm the revocation took effect by watching for authentication errors from the expected client. Removing an integration is only finished when the system on the other end has actually stopped.
3. **Move surviving integrations off shared human identities.** A dedicated integration user with an API-only profile, scoped object and field permissions, login IP ranges, and API access granted through a permission set rather than a profile. The identity you assign is the access you grant, and this is the step that shrinks the blast radius of the next vendor incident rather than the last one.
4. **Turn on the four controls in a sandbox first, and test the refresh path deliberately.** Force the parallel refresh case, let a token go idle in a test environment if the integration is low frequency, and confirm the client recovers from a rejected refresh by re-reading the stored token. The point of the sandbox pass is to find the race condition on a Tuesday afternoon instead of in production at 2 a.m.
5. **Migrate classic Connected Apps to External Client Apps.** Expect new credentials per integration, a cutover window, and a list of every system holding the old key before you start.
6. **Instrument a baseline per application.** Volume per hour, user agent, source address. The Drift indicators were user agent strings and network ranges, and those only mean something against a baseline you built before the incident rather than during it.
7. **Rehearse the revoke.** Time how long it takes to cut one application's access completely, including the downstream system. If the answer is measured in days, the controls you have are theoretical.

The internal version of step one is the habit worth copying: our own delivery pipeline issues each job a scoped credential and rotates it on a schedule, and the operating rule is that a credential without an owner counts as already revoked. That rule is not unique to us, and it is the whole lesson of the past twelve months compressed into a sentence. An integration with a named owner and a rotation date is an asset. The same integration without them is a standing grant, and the only question left is which day somebody else decides to use it.

Salesforce has now made the platform side of this hard to ignore, with the four controls required of the applications and creation restricted by default in the org.[^6][^7] What it cannot do is tell you which of your integrations matter, who authorized them, or what breaks on the day a vendor rotates a token at 3 a.m. That part is the inventory, the owner, and the rehearsal, and it is a day of work per integration the first time and an hour a year after that.
