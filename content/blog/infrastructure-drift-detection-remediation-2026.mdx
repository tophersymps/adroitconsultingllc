A security group rule gets opened to a wide CIDR during an incident and never reverts. An instance type is bumped in the cloud console to ride out a traffic spike, and the Terraform that declared `t2.micro` is left behind. An S3 bucket drifts from private to public for a "temporary" share. Each change solved a real problem at the moment it was made. Each one also broke the one guarantee infrastructure as code is supposed to give you: that the things running in your cloud are the things your code describes.

Drift is the gap between your declared configuration and your live environment. It is not an edge case. It is the normal state of every system that has a human and a browser console in its future. The 2024 State of Kubernetes Security report found that 75 percent of organizations had at least one security incident caused by configuration inconsistency in the previous 12 months, and that 89 percent of production environments carried at least 17 distinct node configurations even when deployed from identical manifests.[^1] This article covers what drift is, why it is dangerous, how to detect it continuously, and the decision framework for fixing it without making things worse. The goal is not zero drift. The goal is drift that is visible, classified, and acted on within hours instead of found during an outage.

## The two gaps drift hides in

Most teams picture infrastructure as a neat triangle: you write code, a plan is generated, an apply makes the cloud match. Reality has two junctions in that chain, and both of them leak.

The first gap is between your configuration and the state file. The state file is not a copy of your code; it is a record of the last known attributes of each managed resource, updated on each apply. If Terraform has not run since the config changed, state and config diverge. The second gap is between state and the real world. Any change made outside Terraform, a console edit, an autoscaling event, a script that mutates a tag, lives in the cloud but not in state. A `terraform plan` compares configuration to state, but state itself ages against reality, so a plan run without a refresh can miss changes the cloud holds that state does not.[^2]

This is why drift sneaks up on teams. A plan run that should detect a problem cannot see what the state file never recorded. The fresh history in your state file says the world matches, so no one looks closer. The gap accumulates quietly until a deploy runs against it, and then the plan that promised "no changes" suddenly proposes to delete half the environment.[^2]

![Drift hides in two gaps: a plan compares declared configuration to the state file, and the state file ages against the live cloud, so both junctions leak and a plan without refresh cannot see the second gap](</diagrams/infrastructure-drift-detection-remediation-2026/1-two-gaps.png>)

A drift incident often looks like confidence followed by panic. An engineer checks in code, the pipeline plans, and a resource that has been live for months shows as needing replacement. The resource was modified by hand somewhere in the past, the plan wants to tear it down and rebuild it, and the team now has to decide in the middle of a deploy whether to accept a destructive change or abort. Firefly's engineers describe this exactly: when production is unstable, teams patch things directly so systems keep running, and the edits break alignment with the code that will later be applied on top of them.[^3] The direct patch is rational. The problem is that nothing forces the patch back into code, so it becomes permanent drift with no record.

## Why drift is dangerous

The costs of drift are not theoretical, and they compound in four directions at once.

**Security.** The most expensive form of drift is a security boundary that was relaxed under pressure and never restored. A security group opened to a broad range for testing, an IAM policy widened with a wildcard, an S3 bucket turned public for a quick share. Each is a configuration change made outside the audit trail of code review, so each becomes an invisible exposure. The 2020 Twilio breach is the canonical case: a misconfigured, world-writable S3 bucket path let an attacker inject a Magecart-style script into the Twilio TaskRouter JS SDK, and the tampered asset was served until Twilio detected and contained the compromise the same day, because the deployed state never matched any reviewed, approved template.[^4] Configuration drift does not break functionality most of the time; it breaks security silently, which is worse, because nothing fails loudly to warn you.[^5]

**Reliability.** A drifted fleet stops behaving like a fleet. The SARC journal's analysis of Kubernetes configuration consistency found that performance in drifted clusters varied by up to 28 percent across supposedly identical nodes, with the most severe impact on memory-intensive workloads where inconsistent configurations produced unpredictable behavior.[^1] Recriminations follow: "it works in staging" and "it worked on my machine" become "it broke in production" because production drifted away from both.

**Cost.** Drift does not respect budgets. A database instance type upgraded in the console to survive a peak is never downgraded when the peak passes, because the downgrade requires someone to remember the change existed. Resources created by hand, autoscalers left to grow, and tags applied outside the pipeline all break cost allocation and inflate spend with no owner accountable for retiring them. Unexpected cloud spend is one of the documented business consequences of unmanaged drift.[^2]

**Mean time to repair.** When reality and code disagree, every investigation has to first figure out which version is true. An operator who cannot trust the plan cannot trust the apply, and cannot trust the rollback either, because the rollback target has already drifted. Teams without a single source of truth spend their incidents reconciling systems instead of fixing problems, which pushes mean time to repair up precisely when a fleet's reputation depends on it being short.[^2]

## Where drift comes from

The causes are consistent across every organization that has drift, and naming them tells you where to put your controls. Firefly groups them into a few recurring patterns: emergency console fixes made during incidents, legacy workloads that were never codified, and changes from automation such as scaling policies or security tools that act outside the IaC workflow.[^3] StateGraph's analysis lands on the same list: manual interventions that bypass IaC, console edits, SSH-ing into hosts, and last-minute adjustments that never make it back into code.[^6]

Drill into the top cause, and an uncomfortable truth appears. In Kubernetes environments, one study attributed 47 percent of drift cases to manual hotfixes, 32 percent to inconsistent CI/CD pipelines that produced package version discrepancies, and 21 percent to incomplete update propagation during maintenance windows.[^1] Empty infrastructure is not the origin of drift, people under pressure are. The emergency that justifies the console edit is exactly the moment when the discipline required to route the fix through code is least available. So the design assumption has to be: drift WILL appear, and the system must catch it early enough that triage is cheap.

## Detecting drift: from manual to continuous

Detection comes in three tiers, and each answers a different question.

**On-demand commands.** The native workflow is `terraform refresh` followed by `terraform plan`. The refresh pulls current attributes from provider APIs into state, and the plan then diffs configuration against that refreshed state. OpenTofu exposes the same path through its `plan` and `refresh` commands, plus a focused variant: `tofu plan -refresh-only` shows changes that came from outside the tool without mixing in pending configuration changes, which keeps a drift check from being contaminated by unapplied work on your own branch.[^7][^8] The choice between the open fork and Terraform is its own decision (see the [Terraform-versus-OpenTofu breakdown](/field-notes/opentofu-vs-terraform-2026) for the licensing and drift-detection differences). For scripted checks, `-detailed-exitcode` turns the plan into a test: exit `0` means no changes, `1` means an error, and `2` means changes present, which is drift when the config has not changed.[^7] On-demand detection is essential for troubleshooting, but it is manual, so it catches drift when someone remembers to run it, which is usually during an incident.

**Scheduled CI scans.** The reliable pattern is a scheduled job that runs a refresh-only plan across every environment on a cadence and alerts when the exit code is `2`. OneUptime's continuous drift monitoring setup runs `tofu plan -refresh-only -detailed-exitcode` on a six-hour schedule across dev, staging, and production, and creates a GitHub issue with the drift output when changes are present.[^9] The schedule matters more than the speed. Catching an unauthorized change within six hours is a triage exercise; catching it during an incident is an emergency. A good cadence for most teams is every four to eight hours, closer to the low end for environments that hold customer data or production workloads.[^9]

**Continuous reconciliation.** The strongest detection is not detection at all, it is a control loop that never lets drift accumulate. GitOps controllers such as Argo CD and Flux treat a Git repository as the single source of truth and run a continuous loop: fetch the declared manifests, compare them to the live cluster, and reconcile the difference.[^10] Argo CD does this on a 120-second reconciliation interval by default, with up to 60 seconds of jitter for a maximum of 3 minutes (180 seconds), and can cut that to near-immediate with Git webhooks. It reports each application as Synced or OutOfSync, and its drift detection catches manual `kubectl` edits, failed deploys, and admission-control mutations that act outside the Git workflow.[^11]

The advanced move is self-healing. Argo CD's `selfHeal` option reverts an out-of-band change to a live resource back to the Git-declared state automatically. There is an important distinction between two policy knobs that teams routinely blur. Automated sync reconciles the case where the desired state changed (a new manifest was pushed, the cluster must converge to it). Self-healing reconciles the opposite case, where the desired state did NOT change but someone mutated the live resource anyway, and reverts that mutation.[^11] Both are powerful, and both should be turned on deliberately, not as a side effect of "sync everything," because an aggressive policy can fight a legitimate scaling system that is already managing a field on Terraform's behalf.

## When auto-correction is right and when it is dangerous

Continuous reconciliation naturally raises the question: if the controller can see drift, why not let it fix everything? The answer is that correction is not free, and the risk changes with what you are correcting.

OneUptime's Terraform drift detection guide sets the policy by resource risk. Stateless and reversible resources, IAM policies, S3 bucket configuration, and DNS records, warrant short intervals of about five minutes with automatic correction (`approvePlan: "auto"`), because an unauthorized change to an IAM policy is both high-risk and safe to revert. Stateful resources, databases and compute instances, warrant longer intervals of thirty to sixty minutes with detection that flags the drift but requires manual approval before anything is applied, because a rushed automatic correction on a database can destroy data that a careful triage would have preserved.[^12]

The same principle appears in Kubernetes. Argo CD's self-healing correctly restores resources that changed outside Git, but automated pruning, the deletion of cluster resources no longer defined in the desired state, is disabled by default as a safeguard against accidental removal, and teams are right to keep that default.[^11] The conservative posture has strong support: a recurring theme in production guidance is to never fully auto-apply drift corrections, because the entire point of surfacing drift is to give a human the chance to decide whether the change is intentional. Automatic correction is just continuous reconciliation with the review step removed, and it defeats the safety of the plan-then-approve workflow.[^13]

## The detection decision framework

When drift appears, the working discipline is to classify it before acting. Firefly and the drift-detection guides converge on a short sequence:

![The drift decision framework: classify the change, reconcile state against reality, accept or revert, update code alongside state, import never recreate, and correct targeted resources only](</diagrams/infrastructure-drift-detection-remediation-2026/4-decision-framework.png>)

1. **Classify the change.** Categorize it as a manual emergency fix, an unauthorized alteration, or an expected change from an automated tool. The classification drives urgency: an unauthorized IAM widening is an incident; a benign tag update from the autoscaler is paperwork.[^14]
2. **Reconcile state against reality first.** Run a refresh-only plan to learn exactly how far the state file and the live world have separated. Do not skip this even when you are confident about what changed, because state may hold surprises you do not know about.[^14]
3. **Decide accept or revert.** If the change was intentional, accept it with `tofu apply -refresh-only`, which updates state to match the real world without mutating any resource. If it was unauthorized, revert it with a regular apply that restores the declared configuration.[^8]
4. **Update code alongside state.** Accepting a legitimate change is incomplete until the `.tf` files or manifests reflect it. Fixing only the state file creates a divergence that resurfaces the next time a plan runs, and silently rebuilding the world on a manifest that never matched reality is just drift in a different costume.[^14]
5. **Special case: import, never recreate.** If the change is a resource that was created outside Terraform but is legitimate and valuable, import it into state rather than letting the next apply destroy and recreate it, which would tear down something working for no reason.[^14]
6. **Targeted, not blanket, correction.** Fix specific drifted resources with a targeted apply instead of re-applying the whole environment, to contain the blast radius of a corrective run.[^14]

## Preventing drift: controls that remove the opportunity

Detection is the backstop. Prevention is the cheaper game, and it is the set of choices that removes the openings drift flows through. The prevention playbook has five moves.

**Policy as code.** If the pipeline blocks non-compliant changes before they apply, drift never gets a foot in the door. OPA-style frameworks and platform-enforced policies validate Terraform plans against constraints such as approved instance sizes, required tags, and encryption settings, and they run as part of CI or the deployment platform. The result is both a guardrail and an audit trail, because every policy check records its decision.[^2]

**Least privilege on the console.** The manual console edit is the number-one lever for drift because someone is logged in with permissions to make it. Enforcing strict role-based access control and least-privilege on consoles and APIs removes the visibility, not just the temptation, for ad-hoc changes. Fewer people who can mutate production directly means fewer paths for drift to enter.[^2][^5]

**Immutable infrastructure.** Infrastructures that favor replace-over-mutate are structurally drift-resistant, because there is no running machine to hand-edit. The durable pattern is to build fresh and never patched-in-place servers. The reported effect is concrete: organizations applying immutable infrastructure principles saw 78 percent fewer configuration-related incidents and deployment success rates of 99.3 percent versus 82.7 percent with conventional approaches, and one study measured mean time to recovery shrinking from 76 minutes to 17 minutes during critical incidents.[^1] A machine that can be replaced from code cannot drift, because if it ever does, the fix is to destroy and rebuild the same manifest.

**Remote state with locking.** Local state files and unguarded backends corrode the record that makes drift visible. Storing state in a remote backend with locking prevents the concurrent-write corruption and separated state files that silently create conflicting versions of reality.[^2] When the record itself is protected and versioned, detection has a reliable baseline to compare against.

**Documented intentional drift.** Some attributes are managed by design outside Terraform, an autoscaler that owns a replica count, a cluster manager that rotates a launch template version. Fighting those with a corrector is a self-inflicted outage. Terraform's `lifecycle.ignore_changes` exists to exclude exactly these attributes from drift detection, and the right practice is to use it deliberately and document each exception, so the tools do not war with each other over a field that was never Terraform's to own.[^12] Misused as a blanket, `ignore_changes` hides real drift; used with intent, it puts the automatic reconcilers and the declarative code on the same side.

## What zero-drift actually means

None of this adds up to a promise of zero drift, and it should not. Autoscaling events, cloud-managed version upgrades, and legitimate emergency fixes are part of running software, and each of them moves the live world a little away from the written one. The goal is not to stop all change. It is to make every change visible, classified, and reconciled within hours, while the triage is cheap, instead of discovered during an incident when a wrong plan proposes to destroy production.

The smallest viable decision any team can make today is to schedule a refresh-only drift check against its main environments on a fixed cadence, alert on exit code `2`, and route the result to whoever owns infrastructure review. That alone converts drift from a surprise into a report. From there, policy as code reduces the changes that need triaging, least privilege reduces the people able to create it, and immutable patterns, or GitOps reconciliation, are the point where the pipeline stops waiting to be asked and starts converging the world to the manifest on its own.

The cloud drifts whether you watch it or not. The only choice is whether the next deploy finds out.
