Most teams secure the read side of a multi-tenant Supabase app and leave the realtime side to a hunch. They wrap every table in a row-level security policy, test the REST endpoint until it returns only a tenant's own rows, then subscribe to a channel and assume the same rules hold. They do not. The channel gives back exactly what the underlying RLS policies allow, but the failure feels nothing like a REST `403` and the docs for realtime authorization are easy to miss until a tenant confirms they can see another tenant's rows live. This article is the boundary model you need before you ship that collaboration feature.

Row level security is the enforcement boundary of a Supabase realtime app. Postgres evaluates a policy every time a table is accessed, adding an implicit `WHERE` clause to the operation.[^1] Realtime does not bypass it. When a client subscribes to Postgres Changes on a table, the server filters the stream through the same RLS policies the REST API applies, so a user only ever receives rows their policies allow them to read.[^2] The practical consequence is that securing your database once secures both your REST reads and your realtime writes. The practical trap is that RLS is easy to get subtly wrong on a live stream, because the row filter runs invisibly and a misconfigured policy leaks without an error.

## The enforcement happens per subscriber, not per write

The first mental model to correct is that a realtime stream is a copy of a table. It is not. Postgres Changes authorizes each event against every subscriber, so a single change to a table with one hundred subscribed users triggers one hundred authorization checks, one per user.[^2] Write rate does not set the throughput ceiling; subscriber count does. A lean insert path can still collapse under a broad subscription, because the server pays the policy cost once per connected user rather than once per row.

That per-subscriber check is what makes RLS the correct tool rather than a performance liability you should route around. You cannot precompute two different streams for two tenants and fan them out behind a filter you control, because the authorization must match exactly what that one user is allowed to see under their role and JWT claims. Realtime asks the database with that user's identity, which is the only way to guarantee the live stream and the read API agree.

## Filters run on the server, which is where they belong

Realtime filters are the second enforcement lever, and they run inside the database, not in your browser. A filter is a `column=operator.value` expression such as `id=eq.1` or `status=in.(online,away)`, and Realtime evaluates it on the server so filtered-out events never leave the database.[^2] The operator set mirrors Postgres: `eq`, `neq`, `lt`, `lte`, `gt`, `gte`, `in` (max 100 values), `like`, `ilike`, `match`, `imatch`, `is`, and `isdistinct`, each mapping to a native Postgres operator, with a `not.` prefix to negate and commas to combine under an implicit `AND`.[^2]

Two consequences matter for multi-tenant apps. The first is that your RLS policy and your channel filter do different jobs, and conflating them is a security error. RLS decides which rows a user may possess; the filter trims which of those rows flow to a given channel. A tenant-scoped `id=eq.ROOM_ID` filter is a performance and scoping convenience, not a security control, because the real boundary is the policy that decides the room is visible to this user at all. Rely on the filter alone and you will ship a subtle breach the moment a user subscribes to a different room's id.

Second, column selection keeps a tenant from exfiltrating data they can read but should not hold in memory. By default every change event carries the full row; the `select` option limits the payload to specific columns, always including the primary key so the client can identify the row.[^2] For tables with large `bytea`, `jsonb`, or `text` columns, `select` shrinks both the payload and the surface area, sending each client only the columns its UI renders.

## Deletes are the quiet gap in the boundary

The most dangerous RLS detail in a realtime app is also the least documented. Row level security policies are not applied to `DELETE` statements, because there is no way for Postgres to verify that a user has access to a record that no longer exists.[^2] Any role that can delete a row can delete any row in a tenant column, and Realtime will happily propagate the deletion to subscribers. If you did not write a delete policy that scopes by tenant, you do not have multi-tenant delete isolation; you have an accident waiting to surface as missing data.

The fix is to write an explicit delete policy per table that scopes by the same tenant predicate your select and update policies use, then prove it with a test that asserts a tenant cannot delete another tenant's row. The same discipline applies to `old` records. By default Realtime sends only the `new` row on `UPDATE` and `DELETE`. To receive the previous values, set the table's replica identity to `full`, which makes the old record available on the event, a change with both a payload cost and a subtle leak if the old row contains anything your policy would have hidden.[^2]

## Broadcast and Presence need their own boundary

Postgres Changes is not the only realtime feature, and a [companion piece walks all three modes and their connection limits in detail](/field-notes/realtime-subscription-lifecycle-supabase-2026). The two non-database modes, Broadcast and Presence, do not sit behind your table RLS at all. Broadcast and Presence authorize through row-level policies on a different table, `realtime.messages`, which Realtime locks down to protect its own operation; you cannot create tables or functions in the `realtime` schema, but you can manage RLS policies on `realtime.messages`.[^3] Each policy maps to an action a client can take: who can publish to a channel, who can receive from it, who can publish presence, and who can see other users' presence.[^3]

The `extension` column on `realtime.messages` records the message type, with a value of `broadcast` or `presence`, so a single policy can scope to a feature by filtering on that value and to a topic through the `realtime.topic` helper function, which returns the channel topic the user is trying to join.[^3] To make private channels mean anything, disable the "Allow public access" setting and instantiate the channel client-side with `private: true`.[^3] Without that flag and without disabling public access, an RLS policy on `realtime.messages` never gets the enforcement it was written for.

## The decision that saves the boundary at scale

The subscriber-per-write cost model eventually hits a wall. Postgres Changes authorizes each event per subscriber and processes changes on a single thread to preserve ordering, so adding compute does not meaningfully raise throughput, and per-subscriber authorization scales with connections, not writes.[^2] Supabase's own guidance is a practical number: past roughly three thousand concurrent subscribers to the same set of changes, switch strategy to Broadcast, which sends each change once and fans it out, scaling to far higher connection counts than per-subscriber authorization allows.[^2]

The escape hatch matters because it changes where the enforcement lives. With Broadcast you attach a trigger that calls `realtime.broadcast_changes()`, which sends the change once and lets the channel fan it out, and that path still requires broadcast authorization policies on `realtime.messages` to be met, so a private channel stays gated.[^4] The ceiling you buy against is the authorization cost, not the value of RLS, because RLS now runs once at the trigger and the broadcast policy guards the fan-out. You gave up per-user row filtering (every subscriber gets the same emitted event) in exchange for scale, and that is the correct trade for a high-fanout notification stream where the sensitive rows are already filtered before they reach the channel.

I keep coming back to the same test for any multi-tenant realtime feature we hand to a client at Adroit: open two tenant sessions and watch a row land in the wrong one. That single demo surfaces more realtime authorization bugs than any unit test, because it exercises the whole chain at once, the RLS policy on the underlying table, the filter on the channel, and the broadcast policy on `realtime.messages`. One tenant's insert showing up in another tenant's live view is a deployment you do not want to make twice, so we put that check in the acceptance criteria before a realtime feature ships.

## A concrete multi-tenant shape that holds the boundary

A clean way to keep the boundary honest is a membership table beneath your tenant objects. A shared document lives in `documents`; a `document_members` table maps users to documents; and every policy on `documents` filters through the membership rows the caller can reach. That single discipline, a transferable membership predicate, gives you a check you can repeat on select, insert, update, and delete, because each policy starts from the same question: is this user a member of this row's tenant owner.

The RLS docs themselves steer toward this shape and warn about its one sharp edge. When two tables' policies read each other, Postgres raises `42P17`, infinite recursion detected in policy for relation, and the query fails for every role the policies apply to.[^1] A `documents` policy that checks `document_members` to find who is a member, while a `document_members` policy checks `documents` to find who owns it, is exactly that cycle. Break it with a `security definer` function that reads the membership table as its owner, so the second policy never runs and the cycle resolves; set `search_path = ''` and schema-qualify names inside it so a caller cannot point an unqualified name at their own object.[^1]

Policies also fail silently when the grant is missing. Postgres runs two checks before a client touches a table: grants decide whether a role can run an operation at all, and policies decide which rows that operation applies to.[^1] A missing grant raises `42501` before any policy runs, so a request that should be allowed fails with what looks like a policy bug when the grants were never set. Worse, a table protected only by policies still hands `anon` or `authenticated` a path if you never revoked the automatic grant, because adding policies does not take those grants back.[^1] Every realtime table needs both halves: RLS enabled, grants scoped to what the role does, and a policy per operation.

The `to` clause keeps an anonymous user out of a tenant policy entirely. A policy that reads `to authenticated` stops at that step, so `anon` never reaches the predicate, and a policy written without a role runs for anyone the grants reach.[^1] Name the role in every policy rather than leaving the implied grants to decide who the rule applies to.

A documents table layers a members table underneath, and every RLS policy on documents filters through the membership rows the caller can reach, so a recursive read if the two policies check each other must be broken with a security definer function that reads membership as its owner.](</diagrams/realtime-rls-enforcement-boundary-2026/3-membership-predicate.png>)

## The role mistakes that hand a tenant the whole table

Two role choices break realtime isolation faster than any policy typo. The first is using `service_role` on the client. The `service_role` Postgres role bypasses RLS entirely, and Supabase warns not to expose it in the browser because the role is authorized to bypass row-level security.[^2] A client that carries the service role subscribes to a channel and receives every row in the table, because the role skips the row filter the whole architecture depends on. A secret key has the same problem: it bypasses RLS only when the request carries no user access token, and it runs under the signed-in user's policies when a token is present.[^1] Keep the service role secret-key path strictly server-side and never let it near a realtime subscription.

The second is letting a tenant discover they are over-privileged by subscribing to a broad channel and reading the stream. Because the read API and the realtime stream share the same RLS boundary, you cannot accidentally be safer in one than the other; the wall is the same policy set. That is the property that makes RLS the right boundary rather than a convenience: it closes the gap between what your API returns and what your sockets emit, which is the single most common way multi-tenant data leaks in a collaboration product.

## Verify the boundary the way a tenant would attack it

The final layer of the discipline is proving the policy works, and the Supabase testing path is concrete enough to be a checklist. Put a test file under `supabase/tests/TABLE_RLS.test.sql` and run `supabase test db` after every migration, asserting allow and deny for select, insert, update, and delete, for anon and authenticated.[^1] For a shared table, also assert that a member who is not the owner can perform the operations its policies allow, and that a non-member cannot.[^1] Match the assertion to how the request is denied: a missing grant and a `with check` violation both raise `42501`, but a `using` clause that filters a row out raises nothing and matches zero rows, so assert with `is_empty` over a statement with `returning` rather than assuming the write failed.[^1]

The test shape matters because a policy that silently matches zero rows looks exactly like a correctly denied write. Never prove an allowed write with `lives_ok`, which passes when the write matched zero rows; add `returning` and assert the returned value.[^1] And index the columns your policies filter on, because Postgres evaluates the policy against each candidate row and an unindexed filter column turns a read into a sequential scan.[^1] For a membership table keyed on `(team_id, user_id)`, the composite primary key indexes only the first column, so add a separate index on `user_id` if any policy filters on it.[^1]

The multi-tenant realtime boundary is not one clever rule; it is a repeated habit. Every table in an exposed schema gets RLS enabled, grants revoked except what the role does, one policy per operation scoped to a named role through a membership predicate, a channel filter that trims rather than secures, deletes policed like everything else, Broadcast and Presence gated through `realtime.messages`, no service role anywhere near a client, and a `supabase test db` run that proves a tenant cannot touch another tenant's rows. Stack those and the live stream stops being the soft spot in your architecture and starts being as tight as the read API it already mirrors.
