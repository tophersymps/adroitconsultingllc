The secrets problem got quantified in a way that is hard to wave off. GitGuardian's State of Secrets Sprawl 2026 report counted almost 29 million new secrets exposed in public GitHub commits during 2025, a 34% year-over-year increase, and the fastest-growing category was AI-service credentials, which rose 81% [^1]. Internal repositories were six times more likely than public ones to contain at least one hardcoded secret [^1]. The sprawl is not slowing, and it is not a scanning problem you can buy your way out of. It is a design problem: we keep minting long-lived static credentials and handing them to people, pipelines, and now agents that have no business holding them.

This article is about the shift that actually fixes it. The durable answer is not a bigger vault or a better regex. It is to stop creating the long-lived static secret in the first place, and to give every workload its own short-lived identity that it uses to buy the exact secret it needs, then lets expire. That shift has an infrastructure story (a credible open-source server to run it on), a CI/CD story (GitOps decrypting without a stored token), and now an AI story (agents and non-human identities are multiplying faster than anything can rotate). I will cover all three and give you a concrete migration ladder.

## The static secret is the leak vector

The reason a hardcoded credential is dangerous is not the credential itself. It is that the credential has no expiration and no owner context. A database password committed to a repo in 2024 is still valid in 2026, it still works from any machine that has it, and no one knows which former employee, CI job, or compromised laptop has a copy. When it leaks, the blast radius is the entire access it grants, forever.

Dynamic secrets exist to remove exactly that property. A dynamic secret is generated on demand, lives for a short lease, and is revoked automatically at the end of that lease. The examples OpenBao uses are telling: a Kubernetes service account or a database role can get a fresh credential that the server itself revokes when the lease expires [^2]. Compare that to a static API key. One is a certificate of citizenship that never lapses. The other is a hotel room key that magically stops working the moment you leave.

![The static secret is minted once and valid forever, so a leak grants permanent access. The dynamic secret is issued on request with a short lease and auto-revoked, so a leak expires on its own](</diagrams/secret-sprawl-machine-identity-2026/1-static-vs-dynamic.png>)

The acute version of this is in the AI layer. An agent on your infrastructure needs a token to call a model provider, a database, or an internal API. The fastest way to give it one is a static API key in an environment variable or a mounted file. That is precisely the pattern GitGuardian found accelerating: AI-service credential leaks grew 81% in a year, outpacing every other category [^1]. Agents do not stop at the credential after they finish a task; they hold it in memory across long tool loops, and their prompts and logs are full of places a key can drop into a transcript.

## OpenBao is the open route you can actually run

If the fix is a server that issues short-lived credentials and manages leases, you need a server. For a decade the default was HashiCorp Vault. But Vault's future changed twice in ways that matter to teams with open-source governance requirements.

First, in August 2023 HashiCorp relicensed Vault from the Mozilla Public License 2.0 to the Business Source License 1.1, which is not OSI-approved open source and restricts offering a competing hosted or commercial service on the codebase [^6]. Second, in February 2025 IBM closed its $6.4 billion acquisition of HashiCorp, making Vault an IBM product [^7]. Teams that need a self-managed, OSI-licensed secrets manager, or that simply do not want their security core owned by one vendor, lost the obvious choice.

OpenBao is the community's answer to that gap. It is a fork of the last MPL-licensed Vault series (roughly 1.14.x), governed openly and hosted under the OpenSSF sandbox at the Linux Foundation, licensed MPL 2.0 [^6][^2]. Its stated mission is narrow and steady: maintain and improve an open software solution for storing and distributing secrets, certificates, and keys, under an OSI-approved license and open governance [^2]. It is not a skunkworks copy of Vault. It is the continuation of Vault's open lineage, maintained by a technical steering committee that currently includes ControlPlane, SAP and Liquid Reply, Adfinis, Wallix, IOTech, and GitLab [^3].

![The governance split: HashiCorp Vault moved from MPL 2.0 to BUSL in 2023 and IBM in 2025, while the MPL lineage forked into OpenBao under the OpenSSF and the Linux Foundation, on an independent roadmap](</diagrams/secret-sprawl-machine-identity-2026/2-openbao-lineage.png>)

The release cadence is real and current. OpenBao's latest stable line is 2.x; v2.5.0 shipped horizontal scalability, v2.7.0 landed external KMS keys and ML-DSA signing support, and the current stable tag is v2.7.1 as of early October 2026 [^3][^8]. This is an actively shipped project, not a shelf-ware fork.

## The infrastructure shift: read scales, then namespaces scale

Whatever you choose, understand what running a secrets server honestly costs. A single active node writing and a set of ready standbys was the classic Vault architecture, and it did not scale reads. OpenBao's v2.5.0 changed that: read-enabled standby nodes now serve read requests locally, offloading the single active node for KV reads and other read-mostly operations, while writes still go through the one active leader [^3].

That matters for agent workloads specifically. A fleet of agents and services asking for credentials is a read-heavy, credential-churn pattern: every agent login is a storage write, but a well-designed call path reads far more than it writes. Letting ready standbys absorb that read load is what makes a centralized secrets server viable once you pass a few dozen workloads.

The storage layer is where the open stack gets interesting. OpenBao supports both Raft-based integrated storage and a PostgreSQL storage backend [^3]. On PostgreSQL, any number of OpenBao nodes can run against the same cluster, all racing for a lock in the database, which decouples the OpenBao service from the database in an M:N topology rather than a rigid one-to-one pairing [^3][^4]. The September 2026 CNCF field guide shows the whole thing running side by side with CloudNativePG, a self-healing, synchronously replicated Kubernetes Postgres with certificate authentication and no password anywhere in the connection, for a fully open-source, vendor-neutral secrets platform [^4].

The next step already has a name. Because namespaces are the isolation boundary and few storage operations cross them, OpenBao's roadmap toward write scalability starts with per-namespace storage separation, and plans multi-writer support by letting namespaces designate themselves active against separate storage backends rather than a single global active node [^3]. That is the difference between a tool you run and a platform you can grow.

## The CI/CD shift: GitOps secrets with no stored token

The hardest problem in secrets management has always been the first one, the bootstrap, the so-called secret-zero. You need a secret to talk to the server that holds your secrets. Historically that meant a static token sitting in the cluster, which means you reproduced the exact vulnerability you set out to fix.

Flux closed that loop in 2026. Starting with Flux v2.9, the kustomize-controller can decrypt SOPS-encrypted secrets directly against OpenBao using Kubernetes workload identity, with no static `BAO_TOKEN` or `VAULT_TOKEN` to provision [^5]. The mechanism is the pattern that makes modern secret management cohere: a workload trades its Kubernetes-issued ServiceAccount token, bound to a specific audience and namespace, for a short-lived OpenBao token scoped to a minimal policy (for example, update on exactly `transit/decrypt/sops`) [^5]. The decrypt grant is the only grant, the identity is native to the platform, and no long-lived credential exists anywhere in the cluster.

![A GitOps controller presents its Kubernetes ServiceAccount token to OpenBao's Kubernetes auth, which swaps it for a short-lived token scoped to a minimal decrypt-only policy, and the controller then decrypts the SOPS secret with no static stored token](</diagrams/secret-sprawl-machine-identity-2026/3-workload-identity-login.png>)

The same pattern scales to supply-chain trust. Instead of shipping signing keys to CI machines, you keep them in OpenBao's Transit engine, which performs sign operations on request and never releases the key material. Flux can verify a Cosign signature against the key; run with `--tlog-upload=false`, the entire sign-and-verify chain stays inside your infrastructure, with no public transparency log recording your signing activity [^5]. For regulated or data-sovereignty-sensitive teams, a signing key that never leaves your network, and a GitOps reconciliation that only applies signed, verified artifacts, is a concrete security upgrade rather than a policy aspiration. Secrets that ride through a third-party runner are the same class of exposure we mapped in [our GitHub Actions supply-chain security guide](/field-notes/github-actions-supply-chain-security-2026): a static credential scoped to a public environment is a key you do not control.

## The AI shift: machines need identities, not secrets to share

The agents themselves are the cleanest argument for this whole model. Every agent is a non-human identity (NHI), and each one should carry short-lived, workload-scoped credentials, not a shared API key that half the org knows. This is where the conversation stops being about vaults and becomes about identity infrastructure.

When an agent needs to call a model provider, the ideal flow is not "go read the key you were given." It is "present your own identity, receive a short-lived token, and let it expire." The tools are matching the problem: Infisical's Agent Vault is an open-source credential proxy purpose-built to give agents short-lived credentials, and Akeyless and Teleport Machine ID target the same NHI reality [^7]. You do not have to adopt any one of them to benefit from the principle, which is that an agent should never hold a long-lived static secret at all.

The practical consequence for your stack is that secrets management stops being a storage problem and becomes a rotation and identity problem. The budget you used to spend on scanning for leaks should increasingly go to retiring the static secrets that could leak. Scanning still matters as a safety net; it is just no longer the defense.

## The migration ladder: where to start

You do not need to rip out your stack overnight. The contrapositive is the guide: work down the ladder from the worst habits to the best, and stop wherever the marginal effort stops paying.

1. Find and kill the static defaults. Before adding any new tooling, know what you have. Secrets in repo history, environment files, and mounted volumes are the baseline problem. Scanning (GitGuardian, gitleaks, or the native scanners in your CI) plus a rotation of whatever is found hardcoded is the unglamorous foundation everything else rests on.
2. Centralize on a server that does leases and revocation. A tool that only stores static secrets encrypted at rest does not fix the class of bug; it just moves a static secret behind a UI. The property you want is the dynamic secret and the lease, which is why OpenBao, and Vault before it, emphasize generation plus automatic revocation [^2][^6]. Make sure whatever you run genuinely expires credentials, or you are paying infrastructure cost for a static store.
3. Move GitOps onto workload identity. Replace any static secret used by your deployment and reconciliation controllers with workload identity, the way Flux v2.9 does against OpenBao [^5]. This single change removes the most dangerous long-lived token most teams carry.
4. Give every agent and pipeline its own identity. Stop sharing. A per-workload, short-lived, policy-scoped token means the blast radius of any single leak is one workload, one scope, minutes. This is the fastest security ROI you can get without buying anything.
5. Rotate on a schedule, not after the incident. Because dynamic secrets expire, the rotation happens continuously as a background property. For anything that is still static (an external SaaS root key, a cloud provider master), rotation should be calendared and automated, not deferred until the breach.

![The secret-hygiene ladder works from the worst habit to the best: scan and rotate hardcoded defaults, centralize on a server that leases and revokes, move GitOps to workload identity, give every agent and pipeline its own identity, then rotate continuously until nothing long-lived remains](</diagrams/secret-sprawl-machine-identity-2026/4-migration-ladder.png>)

## The honest cautions

Two cautions before you commit. OpenBao and Vault now evolve on independent roadmaps, so feature parity is not a given; the OpenLogic analysis is explicit that this is a lower-friction migration, not a zero-effort one, and teams should validate their exact secrets engines, auth methods, plugins, and recovery procedures against the target version before cutover [^6]. And some "dynamic" features are not free: Infisical, for example, historically gates database dynamic secrets to higher commercial tiers, while OpenBao's community edition includes them, so read the exact edition's capability table as part of the decision [^6][^7].

The through-line is consistent. Static secrets are a liability you hold indefinitely; short-lived, identity-scoped credentials are a liability that stops existing on its own. Every layer covered here, the open server, GitOps decrypt without a stored token, Cosign without a shipped key, agents with their own identities, is a version of the same move: stop minting things that never expire. The teams that make that move are the ones not reading the next sprawl report with their own name in it.
