OmniStudio is a licensed product, and that single fact drives more rollout failures than any designer bug. A consultant can build a flawless OmniScript, wire a perfect Integration Procedure, and still watch the whole effort stall because the people who need to run it were never given the right license and the right access. This lesson is about the two layers that sit between a finished component and a user who can actually use it: the Permission Set License, which decides whether a user is entitled to the feature at all, and the Permission Set, which decides what that user can do with it. The exam requirement is to explain both and to explain how they differ, and the scenario questions in this domain almost always hinge on that difference. By the end of this lesson you should be able to look at a user who cannot use OmniStudio and name the missing layer, and you should be able to plan a rollout that licenses exactly the right people and no one else.

## Deep Dive

### OmniStudio is a licensed product

The first thing to internalize is that OmniStudio is not a free add-on that ships with every Salesforce org. It is a licensed product, which means a customer must purchase the appropriate OmniStudio license before the toolset can be used at all. This is a planning fact, not a configuration detail. The architect does not discover the license situation on deployment day; the architect confirms it during project planning, because every downstream decision about who can build and who can run depends on the license being in place.

Think about what a license actually is in the Salesforce world. A license is the commercial entitlement to use a feature. It is the thing the customer pays for. When a customer buys OmniStudio, they are buying the right for a defined set of users to use the OmniStudio builders and runtime. Without that purchase, the tools simply are not available, no matter how much configuration you do. You cannot configure your way around a missing license, and you cannot assign your way around it either. The license is the foundation, and everything else in this lesson sits on top of it.

This matters for the exam because the requirement is phrased as "explain OmniStudio license requirements." The exam wants you to know that licensing is a prerequisite, that it is confirmed up front, and that it is separate from the access mechanisms you configure afterward. A question that asks what must be in place before a customer can use OmniStudio is pointing at the license. A question that asks how you grant a specific user the ability to build a FlexCard is pointing at the permission layers, which we cover next.

### The Permission Set License: the right to use the feature

Once the customer has the OmniStudio license, the org still has to decide which individual users get to use it. That decision is made with a Permission Set License, often abbreviated PSL. A Permission Set License grants a user the right to use a licensed feature. In OmniStudio, the PSL is the mechanism that makes the OmniStudio features available to a user beyond the base platform.

The key word is "right." A Permission Set License is an entitlement. It answers the question "is this user allowed to use OmniStudio at all?" It does not, by itself, tell you which builders the user can open or which runtime actions the user can perform. It is the gate that says the user is entitled to the feature. Think of it as the ticket that lets a person into the building. The ticket does not tell you which rooms the person can enter; it only tells you the person is allowed inside.

Permission Set Licenses are a general Salesforce concept, not an OmniStudio invention. Salesforce uses them across many licensed features, and the OmniStudio PSL is one instance of the pattern. The general rule is that a Permission Set License grants the right to use a licensed feature, and the OmniStudio PSL does exactly that for the OmniStudio toolset. When you assign the OmniStudio Permission Set License to a user, you are telling the platform that this user is entitled to use OmniStudio.

### The Permission Set: the actual access

The second layer is the Permission Set. A Permission Set is a collection of permissions and settings that can be assigned to users. Where the Permission Set License answers "is the user entitled," the Permission Set answers "what can the user actually do." In OmniStudio, the Permission Set grants the actual access to the OmniStudio builders and runtime, such as the ability to create FlexCards or run OmniScripts.

A Permission Set is a bundle. It can contain object permissions, field permissions, system permissions, and app settings, all grouped under one name so an admin can assign a coherent set of capabilities with a single action. In OmniStudio, the relevant Permission Sets carry the permissions that let a user open the OmniStudio designers, create and edit components, and run the runtime. The exact set of permissions depends on the user's role, which is why you typically see more than one OmniStudio Permission Set in an org. A builder who creates OmniScripts needs different permissions than an agent who only runs them.

The distinction between the two layers is the heart of this requirement. The Permission Set License determines whether a user is entitled to the feature. The Permission Set determines what the user can actually do with it. Both are typically required for a user to work with OmniStudio. A user with the Permission Set but no Permission Set License is entitled to nothing, because the license is missing. A user with the Permission Set License but no Permission Set has the right to use the feature but no actual access, because the permissions are missing. The two layers work together, and the exam is built around making sure you do not collapse them into one.

### Why the two layers matter

The reason Salesforce splits entitlement from access is that they solve different problems. The Permission Set License is a commercial control. It ties usage to what the customer paid for, so the customer is not giving every user in the org a paid feature for free. The Permission Set is an operational control. It lets the admin grant fine-grained access so that each user can do exactly the job they are assigned and nothing more. One controls cost, the other controls capability, and keeping them separate lets an org manage both independently.

Consider what happens if you treat them as the same thing. If you assign only the Permission Set, users appear to have access in the configuration but cannot actually use the features, because the license is missing. If you assign only the Permission Set License, users are entitled but have no permissions, so they still cannot do anything. The failure mode in both directions is a user who cannot work, and the confusion between the two is the single most common licensing mistake on the exam and in real projects.

### The architect's planning responsibility

Because licensing and access are separate layers, the architect has a concrete planning job. The architect must decide which users need which Permission Set Licenses and which Permission Sets, and must make that decision deliberately. Over-licensing costs money, because every user with the Permission Set License is consuming a paid entitlement. Under-licensing blocks users from the features they need and stalls the rollout. The correct approach is to assign the Permission Set License and the Permission Set only to the users who actually need OmniStudio features.

This is a cost and access balance. A large org might have thousands of users, but only a fraction of them touch OmniStudio. Licensing every user in the org wastes money on people who never open a builder or run an OmniScript. Licensing too few blocks the people who do need it. The architect's job is to map the business roles to the toolset, identify which roles actually use OmniStudio, and license exactly those users. This is why the exam question about the correct approach to licensing has a clear answer: assign the license and the permission set only to the users who actually need the features.

### Verifying before rollout

Because the two layers are separate and both are required, the architect should verify in a sandbox that a user with the intended license and permission set can actually use the intended OmniStudio features before production rollout. Configuration that looks correct in the admin interface can still fail at runtime if a layer is missing, and the only way to catch that is to test as the user.

The verification is a real user test, not a glance at the permission list. You create a test user, assign the intended Permission Set License and the intended Permission Set, log in as that user, and try to do the actual work the user will do. If the user is supposed to run an OmniScript, run it. If the user is supposed to build a FlexCard, open the FlexCard designer. If the user is supposed to run an Integration Procedure, trigger it. A test that exercises the real path catches the missing-license and missing-access failures that a static review cannot.

### A worked scenario: the bank rollout

Put the whole model together with a concrete example. A bank is rolling out OmniStudio to support a loan origination journey. The org has purchased the OmniStudio license, so the toolset is available. Now the architect has to decide who gets what.

The bank has three groups that touch the journey. Loan officers run the OmniScript that walks a customer through the application. Back-office processors run the Integration Procedure that orchestrates the credit check and the data writes. A small team of consultants builds and maintains the components. Each group needs OmniStudio, but they need different access.

The architect assigns the OmniStudio Permission Set License to all three groups, because all three are entitled to use the feature. Then the architect assigns different Permission Sets. The consultants get the builder permissions, so they can open the designers and create and edit components. The loan officers and processors get the runtime permissions, so they can run the OmniScripts and Integration Procedures but cannot modify them. The license is the same for everyone; the access differs by role.

Now test the failure modes against this scenario. Suppose the architect assigns the Permission Set License to the loan officers but forgets the Permission Set. The officers are entitled, but they have no runtime access, so when they open the OmniScript it fails. Suppose instead the architect assigns the Permission Set but forgets the license. The officers have the access configuration, but they are not entitled, so the feature is not available to them at all. In both cases the fix is the missing layer, and the architect catches it by testing in the sandbox as a loan officer before production.

The bank scenario also shows the cost balance. The bank has thousands of employees, but only the loan officers, processors, and consultants touch OmniStudio. Licensing the entire workforce would spend money on people who never use the toolset. Licensing only the three groups is the correct approach, and it is exactly the answer the exam wants when it asks how an architect should plan licensing.

## Configuration Walkthrough

The configuration for this requirement is about planning and assigning the two layers correctly. Walk through it as a sequence of decisions.

1. Confirm the customer has the appropriate OmniStudio license in place before planning the rollout. This is the foundation. Check the license entitlement as part of project planning, not on deployment day, because nothing else works without it.
2. Identify which users need OmniStudio features and assign the appropriate Permission Set License to each. Map the business roles to the toolset, list the users in each role that actually touch OmniStudio, and assign the OmniStudio Permission Set License to exactly those users. Do not license the whole org.
3. Assign the appropriate Permission Set to grant each user access to the specific OmniStudio builders and runtime they need. Choose the Permission Set that matches the user's role. A builder needs the designer permissions; a runtime user needs the permissions to run components. Assign the right set to each user.
4. Verify in a sandbox that a user with the intended license and permission set can use the intended OmniStudio features before production rollout. Create a test user, assign both layers, log in as that user, and exercise the real path. Fix any missing layer you find before going to production.

## Exam Traps

- **Confusing the Permission Set License with the Permission Set.** This is the trap the exam is built around. The Permission Set License grants the right to use the licensed feature; the Permission Set grants the actual access. Assigning one without the other leaves users unable to use the features. When a question describes a user who has access configured but cannot use OmniStudio, the missing piece is the Permission Set License. When a question describes a user who is entitled but cannot do anything, the missing piece is the Permission Set.
- **Over-licensing every user in the org.** Assigning the Permission Set License to every user costs money for users who never touch OmniStudio. The correct approach is to license only the users who actually need the features. A question that asks about the correct licensing approach is looking for the targeted answer, not the license-everyone answer.
- **Under-licensing users who need OmniStudio.** Licensing too few users blocks the people who need the features and stalls the rollout. The architect must identify every role that actually uses OmniStudio and make sure those users are licensed. A rollout that stalls because a key group cannot run the components is an under-licensing failure.
- **Assuming the Permission Set grants the license.** A Permission Set does not grant the Permission Set License. They are separate layers, and both are required. A statement that assigning a Permission Set automatically entitles the user is wrong.
- **Treating the Permission Set License as admin-only.** The Permission Set License is not restricted to admins. It is the entitlement mechanism for any user who needs the feature, and it applies to runtime users and builders alike.

## Exam Tip

Remember the two layers. The Permission Set License entitles the user to the feature, and the Permission Set grants the actual access, and both are needed. When you see a licensing question, ask which layer is missing. A user who cannot use OmniStudio at all is missing the license. A user who is entitled but cannot perform a specific action is missing the access. Hold that two-layer model and the scenario questions resolve quickly.

## Try It

Open a sandbox with OmniStudio enabled and practice the two-layer model. Create a test user and assign only the OmniStudio Permission Set, then log in as that user and try to open an OmniScript. Observe that the feature is not available, because the Permission Set License is missing. Next, assign the OmniStudio Permission Set License to the same user and try again. Observe that the feature becomes available. Then remove the Permission Set and keep the license, and confirm that the user is entitled but cannot perform the actual work. That exercise makes the distinction concrete: the license entitles, the permission set grants access, and both are required.
