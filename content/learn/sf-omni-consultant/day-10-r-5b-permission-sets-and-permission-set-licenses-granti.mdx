OmniStudio is a powerful toolkit, but none of it works until the right people can reach it. A common failure on real projects is not a broken OmniScript or a misconfigured Integration Procedure. It is an org where every user was handed the full builder permission set, so end users can open the designers and edit artifacts they should only run, while the customer's admins have no idea who is entitled to what. This requirement, explaining OmniStudio license requirements, Permission Set Licenses, and Permission Sets, is the access layer that makes the whole toolkit usable and safe. The exam tests whether you understand the two-step nature of granting access, the difference between a license and a permission set, and how to design a maintainable, least-privilege model. The goal of this lesson is to make that access design automatic rather than something you improvise on test day.

## Deep Dive

### The two-step grant: license, then permission set

Granting OmniStudio access is not a single action. It is a two-step process, and the exam expects you to hold both steps separately because they do different jobs.

The first step is assigning the Permission Set License. A Permission Set License is a costed entitlement that makes a feature available to a user at the platform level. It is the "you are allowed to have this feature at all" gate. Without the license, the user is not entitled to the OmniStudio feature set, no matter what permission sets they hold. The license is what the org pays for, and it is what makes the feature appear as available to that user.[^1]

The second step is assigning the Permission Set. A Permission Set is a collection of settings and permissions that grants a user access to specific tools and functions. It is the "you can actually use this feature in this specific way" gate. The permission set controls which builders, which runtime actions, and which data the user can reach. Two users can hold the same Permission Set License and still have very different abilities because their permission sets differ.[^2]

The critical relationship is that both steps are required. Assigning the Permission Set License without the Permission Set leaves a user entitled to the feature but unable to use it, because no permission set grants them the actual access. Assigning the Permission Set without the Permission Set License leaves a user with the access configuration but no entitlement, so the feature is not available to them at all. Either half alone is a broken grant. The exam loves this pairing because it is the single most common conceptual error candidates make: they treat the license and the permission set as interchangeable, when they are two halves of one grant.

Think of it as a building. The Permission Set License is the key card that proves you are allowed inside the building at all. The Permission Set is the specific set of doors that key card opens. You can hold the key card and still be locked out of the server room, and you can be assigned the server room door but have no key card to get into the building. Both must be in place for you to reach the server.

### Least privilege: grant the minimum each role needs

The second idea this requirement tests is least privilege. The architect should grant the minimum access each role needs, no more. This is not a security nicety. It is a design principle that keeps the org safe and the access model understandable.

Consider the three roles that appear throughout this requirement: builder, reviewer, and end user. A builder creates and modifies OmniStudio artifacts, so they need the permission set that allows creating and editing in the designers. A reviewer inspects artifacts, so they need read access to review them but not necessarily the ability to modify. An end user only runs the finished OmniScripts and FlexCards, so they need the permission set that allows running them and nothing more.

The trap is granting the full builder permission set to every user. That gives end users the ability to create and modify artifacts they should only run. It is over-granting, and the exam presents it as a wrong answer in multiple forms. The correct approach is to give each role exactly the access it needs. An end user who only runs an OmniScript gets a permission set that allows running it, paired with the appropriate Permission Set License, and nothing more. They do not get the builder set, and they certainly do not get admin access to the whole org, which is far more than any of these roles needs.

Least privilege also protects the customer after the project ends. If every user can edit artifacts, a well-meaning end user can change a production OmniScript and break a live process. Restricting edit access to builders keeps the artifacts stable and gives the customer's admins a clear boundary between who can change things and who can only use them.

![The three OmniStudio roles and the small set of role-based permission sets that grant each role exactly the actions it needs, with the over-grant trap of handing every user the full builder set](</diagrams/day-10-r-5b-permission-sets-and-permission-set-licenses-granti/2-least-privilege-roles.png>)

### Role-based permission sets: a small, consistent set

The third idea is that Permission Sets are additive and can be assigned to multiple users, so the architect should design a small set of role-based permission sets rather than one-off sets per person.

Permission Sets are additive, meaning they add permissions on top of the user's profile rather than replacing it. A user can hold several permission sets, and the effective access is the union of everything granted. This additive nature is what makes a small set of role-based sets work. You define a builder set, a reviewer set, and an end user set, and you assign the matching set to everyone in that role.

The alternative, creating a separate permission set for every individual user, becomes unmaintainable as the team changes. When a person leaves, you have to find and clean up their personal set. When a new person joins, you create another one. The number of sets grows with headcount, and no one can remember what each one does. A small set of role-based sets stays constant as people come and go. You assign the builder set to the new builder, and you remove it from the departing builder. The set itself never changes.

The exam frames this as a design choice. The correct answer is to create a small set of role-based permission sets, such as builder, reviewer, and end user, assign each the minimum access it needs, and assign the appropriate Permission Set License to each role's users. This is maintainable and least-privilege. The wrong answers are giving everyone the full builder set, creating a set per person, or giving no one any access and relying on the base platform, which fails because OmniStudio needs the license and permission sets to be usable at all.

### Tracking costed entitlements

The fourth idea is that Permission Set Licenses are a costed entitlement, so the architect should track which users hold them and review the assignments periodically.

Because the license is what the org pays for, every assigned license has a cost. A user who leaves the company but keeps their Permission Set License assigned is a wasted cost. A user who changes role from builder to end user may no longer need the builder license, and keeping it assigned is both a waste and an over-grant. The architect or admin should adjust a departing user's license and permission set as part of offboarding, and should review the org's license and permission set assignments periodically.

The exam tests this with a scenario: a user who held an OmniStudio Permission Set License has left the company. The correct action is to adjust the user's license and permission set as part of offboarding and review assignments periodically. The wrong answers are leaving it assigned, which wastes a costed license; assigning it to a random remaining user, which is not a plan; and deleting the license from the org entirely, which removes it for everyone who needs it. The license belongs to the org's entitlement pool, and the right move is to reclaim it from the departing user so it can be reassigned deliberately.

This tracking is part of the architect's responsibility because the customer's admins will inherit the org. If the architect leaves a pile of orphaned licenses, the customer pays for access no one uses. A clean, reviewed assignment list is a deliverable, not an afterthought.

### Verifying access in a sandbox

The fifth idea is that the architect should verify access in a sandbox with a test user that mirrors each role, confirming the user can perform exactly the intended actions and no more, before production rollout.

A permission set that looks right on paper can be wrong in practice. The only reliable way to confirm it is to create a test user for each role, assign the role's license and permission set, and log in as that user to attempt exactly the actions the role should perform. The builder test user should be able to open the OmniScript Designer and create an artifact. The end user test user should be able to run the finished OmniScript but should be blocked from opening the designer. If the end user can edit artifacts, the permission set over-grants and must be tightened before production.

This verification is the difference between a designed access model and a working one. It catches the over-grant that least privilege is meant to prevent, and it catches the under-grant that would block a legitimate user on day one. The exam wants you to know that verification is part of the rollout, not an optional extra.

### Access planning as part of the deployment plan

The sixth idea is that access planning is part of the deployment plan and should be documented, so the customer's admins know which license and permission set each role needs and can maintain it after the project ends.

The architect does not own the org forever. When the project ends, the customer's admins take over. If the access model exists only in the architect's head, the admins cannot maintain it. The deployment plan should include a role-to-license-and-permission-set mapping that names each role, the Permission Set License it needs, the Permission Set it needs, and the actions that set grants. That document is what lets the customer's admins onboard a new builder, offboard a departing end user, and review the license pool without reverse-engineering the org.

This documentation is a professional deliverable. It turns the access design from a one-time configuration into a maintainable system the customer can operate. The exam frames it as part of the deployment plan, and the correct answer to any question about who maintains access after the project is the customer's admins, guided by the documented mapping.

### A worked scenario: the bank rollout

Put the ideas together with a worked scenario. A bank is rolling out OmniStudio for a loan origination process. The org has three groups that need access: three consultants who build the OmniScripts and FlexCards, two reviewers who approve the artifacts before release, and four hundred loan officers who run the finished OmniScript to originate loans.

The architect starts by defining the roles and the actions each needs. The builders need to create and modify artifacts in the designers. The reviewers need to view and approve artifacts but not modify them. The loan officers need to run the finished OmniScript and see the resulting FlexCard, and nothing more.

The architect creates three permission sets. The builder set grants access to the OmniScript Designer, the FlexCard designer, and the other builders. The reviewer set grants read and approve access to the artifacts. The end user set grants the ability to run the OmniScript and view the FlexCard, with no designer access. Each set is assigned the minimum it needs.

The architect assigns the appropriate Permission Set License to each role's users. All three groups need the OmniStudio license because they all interact with OmniStudio features, but the license alone does not differentiate them. The differentiation comes from the permission sets. The three builders get the builder set, the two reviewers get the reviewer set, and the four hundred loan officers get the end user set.

Before production, the architect creates three test users, one per role, and verifies each in the sandbox. The builder test user can create an OmniScript. The reviewer test user can open and approve it but cannot edit it. The loan officer test user can run the OmniScript end to end but is blocked from the designer. The verification passes, and the model is ready.

The architect documents the mapping in the deployment plan: builder maps to the builder set and the OmniStudio license, reviewer maps to the reviewer set and the license, end user maps to the end user set and the license. When a loan officer leaves, the admin removes the end user set and reclaims the license. When a new builder joins, the admin assigns the builder set and the license. The model stays small, consistent, and maintainable for years.

## Configuration Walkthrough

The walkthrough here is the access design you apply when a customer needs OmniStudio access.

1. Define the roles that need OmniStudio access, such as builder, reviewer, and end user, and list the actions each role needs. Write down what each role must be able to do, from creating artifacts to running them, and nothing more.
2. Create a Permission Set for each role that grants exactly the actions that role needs, and assign the appropriate Permission Set License to each role's users. Keep the sets role-based and additive, and pair every set with the matching license so each user has both halves of the grant.
3. Assign the Permission Sets to the users in each role, and verify in a sandbox with a test user that each role can perform exactly its intended actions. Log in as each test user and attempt the role's actions, confirming the user can do what they should and cannot do what they should not.
4. Document the role-to-license-and-permission-set mapping in the deployment plan so the customer's admins can maintain access after the project. Name each role, its license, its permission set, and the actions that set grants, and hand that mapping to the customer's admins.

## Exam Traps

- **Granting the full builder permission set to every user.** This gives end users the ability to create and modify artifacts they should only run. It is the classic over-grant, and the exam presents it as a wrong answer in several forms. Grant each role the minimum it needs instead.
- **Creating a one-off permission set per person.** A separate set for every individual becomes unmaintainable as the team changes. Design a small set of role-based sets, such as builder, reviewer, and end user, and assign them consistently.
- **Assigning the Permission Set without the Permission Set License, or vice versa.** Either half alone is a broken grant. The license entitles the user to the feature; the permission set grants the actual access. Both are required, and the exam tests this pairing directly.
- **Leaving a departing user's license assigned.** Permission Set Licenses are a costed entitlement. Reclaim the license and adjust the permission set as part of offboarding, and review assignments periodically.
- **Deleting a license from the org to clean up.** Removing the license from the org removes it for everyone who needs it. Reclaim it from the individual user instead.

## Exam Tip

Design a small set of role-based permission sets, builder, reviewer, and end user, grant each the minimum access it needs, and pair every Permission Set with the matching Permission Set License. Hold the two-step grant in your head: the license entitles, the permission set enables, and both must be in place. When a question offers the full builder set to everyone, a set per person, or a license without a set, it is testing least privilege and the two-step model.

## Try It

Open a sandbox with OmniStudio enabled and build the access model from the bank scenario. Create three permission sets named Builder, Reviewer, and End User. Grant the Builder set access to the OmniScript and FlexCard designers, the Reviewer set read and approve access to artifacts, and the End User set the ability to run an OmniScript and view a FlexCard. Assign the appropriate Permission Set License to each role's users. Create three test users, one per role, assign each the matching license and permission set, and log in as each to verify the builder can create, the reviewer can approve but not edit, and the end user can run but cannot open the designer. Then simulate an offboarding: remove the end user set from one test user and reclaim the license, and confirm the user can no longer run the OmniScript. That exercise demonstrates the full two-step, least-privilege access model this requirement describes.
