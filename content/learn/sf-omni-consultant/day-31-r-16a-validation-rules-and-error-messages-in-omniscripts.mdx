Requirement r-16a from the OmniScripts domain, worth 17% of the Salesforce OmniStudio Consultant exam, asks you to prescribe solid validation rules, error messages, and conditional steps that guide users and manage unexpected outcomes or data inconsistencies. That is a mouthful, but the job underneath it is simple: keep bad data out, and when something goes wrong, tell the user what happened and how to fix it.

Here is the mindset the exam rewards. Validation is not a wall you build at the end of the form. It is a series of small checks that catch problems at the point of entry, the moment the user makes them. And an error message is not a technical afterthought. It is part of the user experience, and a message that does not say which field is wrong and what to do about it is a message that failed its job.

## Deep Dive

### What a validation rule is

A validation rule checks that the data a user enters meets the requirements before the journey proceeds. A validation rule is attached to an Element or a Step and evaluates a condition against the data JSON. When the condition is true, the rule blocks progress and shows an error. It is the first line of defense against bad data, and it should catch errors at the point of entry, not at the end of the journey.

Think about what that means in practice. A user types a phone number with six digits. If you validate at the point of entry, the user sees the problem the moment they leave the field, fixes it, and moves on. If you wait until the end of the form, the user fills out the whole journey, hits submit, and then has to retrace their steps to find the one field that was wrong. Salesforce's own best practices make this point: try to enforce required data and validations at the current step instead of at the end of a form, because it helps users correct their inputs immediately instead of looking at validations or errors at the end and retracing their steps to fix each one.[^1]

The quiz tests this directly. An OmniScript must ensure a phone number has at least 10 digits before the user advances. The validation belongs at the element level, on the phone number field, firing as the user leaves it. A single-field format check belongs at the element level, firing as the user leaves the field, which catches the error at the point of entry. Step-level validation is for cross-field checks, a Data Mapper transforms data, and a FlexCard displays it. The element level is the answer.

### How a validation rule is configured

A validation rule is configured on the element or step it guards, and it has two parts: the condition and the message. The condition is written against the data JSON, and when it is true, the rule blocks progress and shows the message. Salesforce's docs on conditional display show the shape of these conditions: you pick a condition type, choose a logical operator for the group, add a condition, and enter the left operand, the element name, and the right operand, the value it is compared against.[^3] The right operand even supports merge fields, so a rule can compare one element to another, like `Name = %contactLastName%`.[^3]

The timing of a rule matters as much as its content. Omniscripts run validation when a user clicks out of a field, using the onBlur function, and you can add the `commitOnChange` property to run validation as the user changes a value.[^3] That is the point-of-entry behavior the exam rewards. The rule fires the moment the user leaves the field, not at the end of the journey, so the user fixes the problem while they are still looking at it.

A worked example makes the configuration concrete. A phone number field needs at least 10 digits. You add a validation rule to the element, write the condition against the data JSON node that holds the phone number, and set the message to "Enter a phone number with at least 10 digits." The rule fires as the user leaves the field, the message names the field and states the requirement, and the user fixes it immediately. That is validation done right.

### The Set Error element and validation

The Set Error element is the tool that turns a validation outcome into a guided correction. It assesses a condition and, when the condition is true, sets an error that blocks progress and shows a message. Salesforce's docs on conditional display give a concrete example: a Set Error element assesses whether a Text element is filled before proceeding to the next page, and if the Text element is conditionally hidden, its value is null, and the error is set.[^3]

The Set Error element is where validation and conditional steps meet. A validation rule catches a bad value, and a Set Error element can route the user to a corrective path or block progress with a clear message. The two work together to guide the user to a valid state. When you design a journey, think of the Set Error element as the enforcement point that turns a rule into a user-facing correction.

### Error messages must tell the user what to do

An error message must tell the user what is wrong and how to fix it. A message that says "invalid input" without saying which field or what is expected forces the user to guess. Write messages that name the field, state the requirement, and give the fix, such as "Enter a phone number with at least 10 digits." The message is part of the user experience, not an afterthought.

Compare the two. "Invalid input" tells the user nothing. Which field? What is wrong with it? What should they type instead? The user stares at the form, guesses, and probably gets it wrong again. Now compare "Enter a phone number with at least 10 digits." That names the field, states the requirement, and gives the fix. The user knows exactly what to do. That is the difference between a message that guides and a message that frustrates.

Salesforce gives you the tools to make messages specific. The error message handler lets you replace default error messages from remote Apex calls with more user-friendly messages when errors occur in an Omniscript, and you can set a default error message plus custom error messages that match on a path and value.[^2] So when a remote call returns a cryptic error, you can replace it with a message the user understands. The point is the same everywhere: the message should tell the user what is wrong and how to fix it.

### Validation belongs at the right level

Validation belongs at the right level, and the exam tests this distinction hard. Element-level validation checks a single field and fires as the user leaves it, which is the best place for format and range checks. Step-level validation checks the whole Step and fires when the user tries to advance, which is the right place for cross-field checks that depend on multiple values. Choose the level that matches the check.

The quiz tests this with a cross-field check. A validation rule must check that a start date is before an end date, two fields in the same Step. The validation belongs at the step level, so both fields are present when it fires. A cross-field check needs both values present, so it belongs at the step level, which fires when the user tries to advance after both fields are entered. An element-level rule on one field fires before the other is entered and cannot see both values. The step level is the answer.

Why does the level matter so much? Because of timing. An element-level rule fires as the user leaves a single field. If the check needs two fields, and the rule is on the start date field, it fires the moment the user leaves the start date, before the end date is even entered. The rule cannot see the end date, so it cannot do its job. Put the check at the step level, and it fires when the user tries to advance, after both fields are present. The level has to match the check, or the check cannot work.

### Validation must handle the data the journey actually produces

Validation must handle the data the journey actually produces, not the data you imagine it produces. A rule that assumes a field is always present breaks on a branch that skips it, and a rule that does not account for empty values can block a legitimate path. Test each rule against the empty case and against every branch that can reach it.

This is the trap that bites in production. You write a rule that assumes a field is always populated, because in the happy path it always is. Then a branch skips the field, the rule fires on an empty value, and a legitimate path is blocked. Or a rule does not account for empty values, and a user who legitimately has no value for a field cannot proceed. The rule has to be tested against the empty case and against every branch, or it will break a real journey.

Salesforce's docs on conditional display make the empty case concrete. When you hide an element in an Omniscript, Omnistudio sets the contents of the element to null in the data JSON, and you should consider this behavior if your Omniscript references the hidden field. For example, if a Set Error element assesses whether a Text element is filled before proceeding, and the Text element is conditionally hidden, the Text element value is null, and the error is set.[^3] A hidden field is an empty field, and a rule that does not account for that will fire when it should not.

### Error handling extends beyond validation

Error handling extends beyond validation to unexpected outcomes. A fetch that returns no data, a save that rejects a record, or an integration that times out must surface to the user in a way they can act on. Design the flow to read statuses and route failures to clear messages, and log the details for diagnosis.

The quiz tests this directly. A fetch stage in an OmniScript returns no data for a valid account. The correct error handling is to read the status, show a clear message that no data was found, and log the details for diagnosis. Unexpected outcomes must surface in a way the user can act on: read the status, show a clear message, and log details for diagnosis. A generic message gives no guidance, blocking with no message traps the user, and ignoring it produces wrong results. The clear message plus logging is the answer.

This is the difference between a journey that works and a journey that is dependable. A journey that works on the happy path but breaks when a fetch returns empty is not dependable. The fetch returns a status, the OmniScript reads it, and the flow routes the failure to a message the user understands and a path forward. The details are logged so someone can diagnose what happened. That is error handling done right.

### Validation and conditional steps work together

Validation rules and conditional steps work together. A conditional step can route the user to a corrective path when validation fails, and validation can gate a step that should only proceed with clean data. Design the two together so the user is guided to a valid state rather than blocked with no way forward.

This is the part that turns a form into a journey. Validation catches the problem, and a conditional step gives the user a way out. When a validation fails, a conditional step can appear that asks for the missing data or confirms an override. The user is not trapped; they are guided. Design the corrective path as part of the journey, not as an afterthought, and the user always has a way to a valid state.

The next lesson, lesson 32, goes deep on conditional steps and handling unexpected outcomes. For now, hold the principle: validation and conditional steps are two halves of the same design. Validation keeps bad data out, and conditional steps route the user to a valid state when something goes wrong. Design them together, and the journey guides the user instead of blocking them.

## Config Walkthrough

Add validation and error handling in four steps.

1. To validate a single field, add a validation rule to the Element, write the condition against the data JSON, and set an error message that names the field and states the requirement. The rule fires as the user leaves the field, catching the error at the point of entry.
2. To validate across fields, add a validation rule at the Step level that fires when the user tries to advance, and write a message that explains the cross-field requirement. Both fields are present when the step-level rule fires.
3. Test each validation rule against the empty case and against every branch that can reach it, so a legitimate path is never blocked. Remember that a conditionally hidden field is null in the data JSON.
4. Add error handling to fetch and save stages: read the returned status and route failures to a clear user-facing message, with details logged for diagnosis. Use the error message handler to replace cryptic remote errors with messages the user understands.

## Exam Traps

Three traps account for most misses on this objective.

First, writing an error message that does not say which field or what is expected. "Invalid input" forces the user to guess. Name the field, state the requirement, and give the fix.

Second, putting a cross-field check at the element level. An element-level rule fires as the user leaves one field, before the other field is entered, so the check cannot see both values. Use step-level validation for cross-field checks.

Third, writing a validation rule that assumes a field is always present. On a branch that skips the field, the rule breaks or blocks a legitimate path. Test against the empty case and every branch.
