Requirement r-22b is the one where the exam stops asking what the Data Mapper types are and starts asking which one to recommend. The exam wants you to differentiate and recommend the correct Data Mapper type, Extract, Turbo Extract, Load, or Transform, based on the specific business need. In the Data Mappers domain, worth 17% of the exam, the questions hand you a business need and ask which type serves it [^5]. The organizing idea is simple: identify the operation the need requires, then weigh performance against feature needs, and the type follows.

## Deep Dive

### The recommendation starts with the operation

The recommendation starts with the operation the business need requires. Does the need read data, write data, or reshape data? Extract and Turbo Extract read, Load writes, and Transform reshapes [^1]. Once the consultant names the operation, the type narrows to the pair that serves it.

The exam tests this directly. A business need requires reading data from Salesforce. Which Data Mapper types serve this operation? Extract and Turbo Extract. Extract and Turbo Extract both read data from Salesforce, so a read need narrows to those two types. Load writes, and Transform reshapes, so neither serves a read [^1].

Here is the decision tree in practice. The consultant hears the business need and asks one question: does this need read, write, or reshape? If it reads, the choice is between Extract and Turbo Extract. If it writes, the choice is Load. If it reshapes, the choice is Transform. The operation narrows the field, and the remaining decision is about performance and features.

The exam objective that drives this requirement is to differentiate and recommend the correct Data Mapper type based on the specific business need [^5]. The word recommend is the key. The exam is not asking you to describe what a type does; it is asking you to make a choice for a given business need and to justify it. The way to prepare is to practice the recommendation until it is automatic. When you read a scenario, you should be able to name the operation, weigh the performance and feature needs, and state the type you would recommend and why. That is the skill the exam measures, and it is the skill this lesson builds.

The recommendation is a two-step process, and the exam rewards consultants who do both steps. The first step is to name the operation, because the operation narrows the field to one type or one pair. The second step is to weigh the performance and feature needs, because that decides between the read pair. A consultant who skips the first step and jumps to a type is guessing. A consultant who does both steps is recommending.

### A read need: Extract or Turbo Extract

When the operation is a read, the consultant chooses between Extract and Turbo Extract. The deciding factor is performance versus feature needs. Turbo Extract reads faster, so it is the choice for high-volume or performance-sensitive reads, but it has a more limited feature set [^2]. The standard Extract is slower but supports more features.

The exam tests this directly. A business need requires a high-volume read of simple data. Which Data Mapper type should the consultant recommend? Turbo Extract. A high-volume read of simple data is a performance-sensitive read, and Turbo Extract reads faster than a standard Extract, so it is the right choice [^2].

Here is the decision in practice. A dashboard needs to display a large list of records, and the data is simple, so the consultant recommends Turbo Extract because it reads faster. A complex read needs relationship notation and formulas that Turbo Extract does not support, so the consultant recommends the standard Extract despite the slower performance [^2].

The consultant does not recommend Turbo Extract for every read. The recommendation depends on the business need. High volume and performance-sensitive, with simple data, favors Turbo Extract. Complex features favor the standard Extract.

### A write need: Load

When the operation is a write, the consultant recommends Load. A Data Mapper Load writes data to Salesforce, accepting data in JSON, XML, or a custom format and writing it to Salesforce objects [^3]. Loads handle Salesforce ID mapping, upsert logic, and error management during data creation or updates [^3].

The exam tests this directly. A business need requires creating records in Salesforce. Which Data Mapper type should the consultant recommend? Load. A Load writes data to Salesforce, so it is the type for creating or updating records, and it handles ID mapping, upsert logic, and error management [^3].

Here is the decision in practice. A user finishes entering data in an OmniScript and clicks Save. The business need is to create a record in Salesforce, so the consultant recommends a Load. The Load maps the input data to the object fields and writes the record [^3].

The write need has no performance-versus-feature trade-off the way the read does. There is one write type, Load, and the consultant recommends it whenever the operation is to create or update records in Salesforce.

### A reshape need: Transform

When the operation is a reshape, the consultant recommends Transform. A Data Mapper Transform reshapes data without reading from or writing to Salesforce [^4]. It converts JSON to XML and vice versa, restructures input data, renames fields, and substitutes values, and it is essential for populating DocuSign templates and PDF documents [^4].

The exam tests this directly. A business need requires converting JSON data to XML for an external system. Which Data Mapper type should the consultant recommend? Transform. A Transform converts JSON to XML and vice versa, so it is the type for converting data formats, and it does not read from or write to Salesforce [^4].

Here is the decision in practice. An OmniScript must populate a PDF document, so the consultant recommends a Transform to reshape the data into the PDF's format. The Transform maps the data into the fields the PDF expects, and the PDF fills correctly [^4].

The reshape need is unambiguous. When the operation is to convert, restructure, or rename data, the consultant recommends Transform. It is the only type that reshapes without touching Salesforce.

### Weighing performance against feature needs

The read pair is where the consultant weighs performance against feature needs. Turbo Extract reads faster, so it is the choice for high-volume or performance-sensitive reads, but it has a more limited feature set [^2]. The standard Extract is slower but supports more features. The recommendation balances the two.

The exam tests this directly. A business need requires a read that must be fast, but the data needs complex features. Which Data Mapper type should the consultant recommend? The standard Extract, because Turbo Extract has a more limited feature set. When the read needs complex features that Turbo Extract does not support, the standard Extract is the right choice despite being slower [^2].

Here is the decision in practice. A read needs relationship notation and formulas, which Turbo Extract does not support. The consultant recommends the standard Extract, accepting the slower performance because the features are required. A read of simple data that must be fast gets Turbo Extract [^2].

The consultant does not optimize for speed alone. The recommendation balances speed against the features the business need requires. When the features are required, the standard Extract wins. When the speed is required and the data is simple, Turbo Extract wins.

### The recommendation follows the business need, not a preference

The recommendation follows the business need, not a consultant preference. The consultant does not default to one type for every need. The consultant identifies the operation, weighs performance against features, and recommends the type that serves the specific business need [^1].

The exam tests this directly. Recommending the same Data Mapper type for every business need is a trap, because each type serves a different operation, so the recommendation must follow the specific business need [^1]. A read, a write, and a reshape each need a different type, and the consultant recommends the type that matches the operation.

Here is the failure mode. A consultant who always recommends Turbo Extract for reads, or always recommends Load, will mis-serve the business need. A read that needs complex features gets the wrong type, and a reshape gets a type that cannot reshape. The recommendation must follow the need.

### A worked example: recommending for a field service app

Put the pieces together with a concrete scenario. A field service app needs to read open work orders, create a new work order, and generate a PDF of the work order details.

For the read, the app needs a fast read of a large list of open work orders, and the data is simple, so the consultant recommends Turbo Extract because it reads faster than a standard Extract [^2]. If the read needed complex features, the consultant would recommend the standard Extract instead.

For the write, the app needs to create a new work order, so the consultant recommends a Load to write the data to Salesforce [^3]. The Load maps the app's input to the work order object fields and writes the record.

For the PDF, the app needs to populate a PDF document, so the consultant recommends a Transform to reshape the data into the PDF's format [^4]. The Transform maps the data into the fields the PDF expects.

Each business need maps to a recommendation. The read maps to Turbo Extract, the write maps to Load, and the reshape maps to Transform. The consultant recommends the type that matches the operation and the performance and feature needs.

The same mapping holds when the need is stated in business language. If the business says the app must display a list, the operation is a read, and the recommendation is Extract or Turbo Extract. If the business says the app must save a record, the operation is a write, and the recommendation is Load. If the business says the app must produce a document, the operation is a reshape, and the recommendation is Transform. The consultant translates the business language into the operation, weighs the performance and feature needs, and names the type.

Try it yourself. In a sandbox, take three business needs, a fast read of simple data, a complex read, and a write, and recommend a type for each. Confirm that the fast read gets Turbo Extract, the complex read gets the standard Extract, and the write gets Load. Then explain why each recommendation follows the business need.

## Config Walkthrough

The recommendation process maps onto four concrete steps.

1. Identify the operation the business need requires: read, write, or reshape. Extract and Turbo Extract read, Load writes, and Transform reshapes [^1].

2. For a read, weigh performance against feature needs. Recommend Turbo Extract for a high-volume or performance-sensitive read of simple data, and the standard Extract when the read needs complex features [^2].

3. For a write, recommend Load to write data to Salesforce, handling ID mapping, upsert logic, and error management [^3].

4. For a reshape, recommend Transform to convert, restructure, or rename data without reading or writing, as when populating a DocuSign template or PDF [^4].

## Exam Traps

Three traps dominate this requirement, and each is a specific, avoidable mistake.

**Recommending the same type for every business need.** Each type serves a different operation, so the recommendation must follow the specific business need [^1]. A read, a write, and a reshape each need a different type.

**Choosing Turbo Extract for a read that needs complex features.** Turbo Extract has a more limited feature set, so a read that needs relationship notation or formulas should use the standard Extract despite the slower performance [^2].

**Using a Transform to write data to Salesforce.** A Transform reshapes data without reading or writing, so it cannot create or update records [^4]. Writing data to Salesforce is the Load's job.

The exam tip that ties these together: identify the operation, then weigh performance against features. The recommendation follows the business need, not a consultant preference.
