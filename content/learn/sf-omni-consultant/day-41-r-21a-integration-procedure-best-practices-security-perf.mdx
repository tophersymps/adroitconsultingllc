Requirement r-21a is the one where the exam stops asking what an Integration Procedure does and starts asking how to build one that survives contact with the real world. The exam wants you to discuss best practices for Integration Procedures. In the Integration Procedures domain, worth 17% of the exam, the questions reward consultants who treat security, performance, and error handling as design decisions made up front, not as afterthoughts bolted on when something breaks [^4]. The organizing idea is simple: centralize secrets, filter at the source, and design the error path before you test the happy path.

## Deep Dive

### Security starts with named credentials

Security best practices start with named credentials. All external endpoints and secrets live in named credentials, never in the IP, in Apex, or in custom settings [^1]. The IP references the credential, so connection details and tokens are centralized and can be rotated without touching the IP.

A named credential is a Salesforce object that stores the endpoint URL, the authentication protocol, and the credentials needed to call an external system [^2]. When an HTTP Action in an IP references a named credential, the IP does not need to know the URL or the token. It just calls the named credential, and Salesforce handles the connection and the authentication.

Why does this matter so much? Because the alternative is a security leak waiting to happen. If the endpoint URL and token are hard-coded in the IP, the connection detail lives in the IP, must be changed in every IP when it moves, and can leak through exports and logs [^1]. Every IP that hard-codes a URL is a copy of that secret, and every copy is a place it can leak.

The exam tests this directly. Where should external endpoint URLs and secrets be stored for an Integration Procedure? In named credentials referenced by the HTTP Actions. Named credentials are the security boundary that holds endpoints and secrets, and the HTTP Actions reference them. Output variables, custom labels, and the Data Mapper are not the place for connection details or secrets [^1].

The rotation story is the practical payoff. When the external system rotates its token, the consultant updates the named credential once, and every IP that references it picks up the new token. If the token were hard-coded in ten IPs, the consultant would have to find and update all ten, and would likely miss one. Centralizing in a named credential turns a risky, error-prone change into a single update. The same discipline extends to the security settings that govern how Data Mappers and Integration Procedures handle data, so the consultant reviews those settings as part of the security design [^3].

### Performance centers on minimizing external calls and payload size

Performance best practices center on minimizing external calls and payload size [^1]. The consultant should filter at the source when the external system supports it, request only the fields the client needs, and avoid calling the same endpoint repeatedly in a single IP. Each external call adds latency and consumes API limits.

The exam tests this directly. A consultant wants to minimize the latency and API usage of an external call in an IP. What is the best practice? Filter at the source and request only the fields the client needs. Filtering at the source and requesting only needed fields reduces payload size and external call latency, and it avoids consuming API limits. Calling repeatedly, requesting full payloads, or raising the timeout all make performance worse [^1].

Think about what each bad option does. Calling the endpoint multiple times to get all data multiplies the latency and the API consumption. Requesting the full payload and filtering in the client means the IP carries data across the network that the client will never use. Increasing the timeout to the maximum does not make the call faster; it just makes the IP wait longer when the call is slow. The best practice is to ask the external system for exactly what the client needs, nothing more.

![Filter at the source: passing the account ID as a query parameter and requesting only the balance field returns a small payload in one call, while requesting the full account record carries data across the network the client never uses](</diagrams/day-41-r-21a-integration-procedure-best-practices-security-perf/2-filter-at-the-source.png>)

The same logic applies to repeated calls. If the IP calls the same endpoint twice to get data it could have gotten in one call, that is wasted latency and wasted API quota. The consultant designs the request to get everything needed in as few calls as possible.

### Error handling is designed, not added after the fact

Error handling must be designed, not added after the fact [^1]. Every HTTP Action should have an error path that captures HTTP error codes, timeouts, and malformed responses, and the IP should return a structured error to the client. A generic failure with no detail is a support nightmare.

The exam tests this directly. Skipping the error path and returning a generic failure is a trap, because the client cannot tell whether the endpoint was down, auth failed, or the payload was malformed, and support has no diagnostic signal [^1]. A generic failure gives the user a blank screen and gives support nothing to work with.

The designed error path captures the specifics. When the endpoint returns a 401, the error path knows auth failed. When the call times out, the error path knows the endpoint was slow or down. When the response is malformed, the error path knows the payload did not match the expected shape. Each of these is a different failure with a different fix, and the error path captures the difference so the client and support can act on it.

The IP should return a structured error to the client, an error object with a code and message, so the client can distinguish a real failure from missing data and display a meaningful message. This connects directly to the Response action lesson: the error path produces a structured response the client can handle.

### Timeouts and retries are part of the design

Timeouts and retries are part of the design [^1]. The consultant sets a timeout that matches the external system's expected response time and decides whether a retry is safe. Retrying a non-idempotent operation such as a POST can create duplicate records, so retries must be considered per operation.

The exam tests this directly. Why should a consultant avoid automatically retrying a POST operation on timeout? Because the first call may have succeeded, so a retry can create a duplicate record. A POST is non-idempotent, so if the first call succeeded but the response was lost, a retry creates a duplicate record. Retries must be considered per operation, and non-idempotent calls need special handling [^1].

Here is the failure mode. The IP sends a POST to create a record. The external system receives the call, creates the record, and sends back a response, but the response is lost in transit and the IP times out. The IP retries the POST. The external system creates a second record. Now there are two records where the business wanted one, and the IP has no way to know.

![Why retrying a POST on timeout creates a duplicate: the external system creates record one, the response is lost and the IP times out, the retry creates record two, leaving two records where the business wanted one](</diagrams/day-41-r-21a-integration-procedure-best-practices-security-perf/3-post-retry-duplicate.png>)

The consultant sets a timeout that matches the external system's expected response time, so the IP does not wait forever for a slow endpoint. And the consultant decides per operation whether a retry is safe. A read is idempotent, so a retry is usually safe. A POST that creates a record is not, so the retry must be handled carefully, perhaps by checking whether the record already exists before retrying.

### Observability means the IP is testable and diagnosable

Observability means the IP should be testable and diagnosable [^1]. Consultants should test with real payloads, log enough detail to trace a failure without logging secrets, and keep the IP decomposed so a failure in one step is isolated. A monolithic IP is hard to debug.

Testing with real payloads is the difference between a demo and a working integration. A sample payload that is tidy and complete will not reveal the problems that a real payload does, the optional fields, the nulls, the unexpected types. The IP only proves itself when it runs against the actual data it will see in production.

Logging enough detail without logging secrets is a balance. The consultant logs the endpoint, the error code, the timing, and the shape of the failure, so support can trace what happened. But the consultant does not log the token or the credentials, because those are secrets and logging them creates a leak. The named credential keeps the secret out of the IP, and the log keeps it out of the log.

Keeping the IP decomposed means each action does one job, so a failure in one step is isolated. A monolithic IP that does everything in one action is hard to debug, because a failure anywhere looks like a failure everywhere. A decomposed IP lets the consultant see which step failed and fix that step.

### Governance means versioning, documenting, and reviewing

Governance best practices include versioning the IP, documenting the external contract it depends on, and reviewing it when the external system changes [^1]. An IP that silently depends on a field the endpoint no longer returns fails in production, so the contract must be tracked.

Versioning the IP means the consultant can track changes and roll back when a change breaks something. Documenting the external contract means the consultant knows what fields the endpoint returns and what the IP depends on. Reviewing the IP when the external system changes means the consultant catches a removed field or a changed response shape before it fails in production.

The failure mode is silent. The external system drops a field that the IP's transform maps. The IP does not fail at build time, because the mapping still exists. It fails at runtime, when the field is absent and the transform cannot find it. The consultant who tracks the contract catches this in review, before production.

### A worked example: a secure, fast, resilient IP

Put the pieces together with a concrete scenario. A consultant builds an IP that fetches a customer's account balance from an external billing system. The consultant starts with a named credential that holds the endpoint URL and the token, so the IP references the credential and never hard-codes a secret [^1].

For performance, the consultant filters at the source, passing the account ID as a query parameter so the endpoint returns only that account's balance, and requests only the balance field, not the full account record. The IP makes one call, not several, and the payload is small [^1].

For error handling, the consultant adds an error path to the HTTP Action that captures HTTP error codes, timeouts, and malformed responses, and returns a structured error object to the client. The client displays a meaningful message when the billing system is down [^1].

For timeouts and retries, the consultant sets a timeout that matches the billing system's expected response time. Because this is a read, a retry is safe, so the consultant can allow a retry. If this were a POST that creates a record, the consultant would handle the retry carefully to avoid a duplicate [^1].

The result is an IP that is secure, because the secret lives in the named credential, fast, because it filters at the source and requests only what it needs, and resilient, because the error path and the timeout are designed, not added later.

Try it yourself. In a sandbox, build an IP that calls an external system through a named credential. Filter at the source, request only the fields the client needs, add an error path that returns a structured error, and set a timeout that matches the endpoint. Test the happy path and the error path with real payloads.

## Config Walkthrough

The best practices map onto four concrete steps.

1. Store all external endpoints and secrets in named credentials and reference them from the HTTP Actions, never hard-coding URLs or tokens in the IP. Centralize the connection details so they can be rotated without touching the IP [^1].

2. Filter at the source and request only the fields the client needs to minimize payload size and external call latency. Avoid calling the same endpoint repeatedly in a single IP [^1].

3. Add an error path to every HTTP Action that captures HTTP error codes, timeouts, and malformed responses, and returns a structured error to the client. Design the error path before you test the happy path [^1].

4. Set timeouts that match the external system's expected response time and decide per operation whether a retry is safe, avoiding retries on non-idempotent calls. A POST that succeeded but lost its response creates a duplicate when retried [^1].

## Exam Traps

Three traps dominate this requirement, and each is a specific, avoidable mistake.

**Hard-coding the endpoint URL or token in the IP.** The connection detail then lives in the IP, must be changed in every IP when it moves, and can leak through exports and logs [^1]. Store endpoints and secrets in named credentials and reference them from the HTTP Actions.

**Retrying a POST automatically on timeout.** The first call may have succeeded, so the retry creates a duplicate record [^1]. A POST is non-idempotent, so retries must be considered per operation, not applied blindly.

**Skipping the error path and returning a generic failure.** The client cannot tell whether the endpoint was down, auth failed, or the payload was malformed, and support has no diagnostic signal [^1]. Design the error path to capture the specifics and return a structured error.

The exam tip that ties these together: centralize secrets in named credentials, filter at the source, and design the error path before you test the happy path. Security, performance, and error handling are design decisions, not afterthoughts.
