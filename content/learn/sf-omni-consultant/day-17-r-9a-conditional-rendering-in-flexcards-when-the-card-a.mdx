A warning sign that only appears when a case is past its due date. An action button that vanishes the moment a record is closed. A card that reads differently for a manager and an agent. These all look like different cards, but they are one card definition doing the most useful trick in the FlexCards toolkit: adapting to what the data says. This is the requirement behind Lesson 17, R-9a. It sits in the FlexCards domain, worth 18 percent of the OmniStudio Consultant exam, and it asks you to advise on using conditional rendering and state variables to dynamically adjust a card's appearance or content based on the underlying data or user interaction.[^1]

The core idea is easy to state and genuinely powerful in practice: instead of a static layout that shows the same elements to everyone in every situation, the card evaluates rules against its data and its state, and decides what to show, hide, highlight, or change. This is what turns a single card into something that behaves differently for different records, roles, and moments, without maintaining a pile of separate card definitions. This lesson unpacks what conditional rendering is, how conditions get evaluated, how they adapt a card across roles and content, why the data source and the conditions must be designed together, and when a condition should change appearance instead of hiding an element.[^1]

## Deep Dive

### What conditional rendering is

Conditional rendering is the mechanism that lets a FlexCard show or hide elements, or change their appearance, based on the underlying data or the card's state. Instead of a static layout where every element is always visible and always styled the same way, the card evaluates a condition at render time and adapts. The element exists in the card definition, but whether the user sees it, and how it looks when they do, depends on the rule the card evaluates.

So a card does not just display a payload. It makes decisions about that payload. A service agent looking at a case sees a warning banner only when the case is genuinely at risk, sees the resolve button only while the case is open, and sees the case differently depending on whether it is New, In Progress, or Escalated. The card definition holds all of it, and the conditions decide what surfaces in each moment.

This is the central concept to hold for the exam: conditional rendering turns data into display decisions. The card reads the data and its own state, applies the conditions you define, and produces the layout that fits. The same file, one card definition, adapts its behavior automatically. That adaptation is the whole point, and it separates an adaptive card from a static one.

### Conditions are rules evaluated at render time

A condition is a rule the card evaluates at render time. You define it on an element, you pick which data field it looks at, which operator compares that field, and which value it checks against, and the card decides whether that element shows, hides, or changes appearance based on whether the rule comes out true.

Take a realistic example straight from the Salesforce product documentation. A FlexCard summarizes the terms of a contract, and you want to show a reminder only when the contract's renewal date falls within a certain range. You add a condition to the reminder text element that evaluates the renewal date, set the operator and the range, and now the reminder appears only when the data supports it. The reminder text is in the card definition, but its visibility depends entirely on the renewal date the data source returns.[^1]

A typical condition checks a field value directly. You show a warning banner only when a case is past its due date. You hide an action button when the record is already closed. You show a payment acknowledgment banner only when a payment is due. Each of these is a rule the card evaluates at render time, against the data JSON it received and the state variables it holds. The condition is not a one-time setup decision. It is a live rule that re-evaluates as the data or the state changes, so the card stays correct as the situation underneath it moves.[^1][^2]

### Conditional rendering is the tool for role and context adaptation

From Lesson 14 you know that role and context should drive what a card shows. Conditional rendering is the mechanism that makes that design real. The same card can show different elements to a manager and an agent, or show different content depending on a record's state, without maintaining separate card definitions.

This is the payoff of keeping the logic in one place. When a manager and an agent look at the same card, each sees the slice that serves their task. The agent sees the case number, the SLA deadline, and the actions that advance the workflow. The manager sees the priority, the status, and the portfolio summary, and no workflow buttons, because the manager is reading, not working. Conditional rendering evaluates who is looking and what they are doing, and surfaces the right elements to each.

The alternative is two separate card definitions, one for the manager and one for the agent. That duplicates the logic, the layout, and the maintenance, and it guarantees the two cards drift apart over time. The single adaptive definition keeps the logic in one place and the behavior consistent. When a fix or an improvement needs to happen, you make it once, and every role sees the corrected version. This consistency is a real architectural benefit, and it is exactly why the exam frames conditional rendering as the answer to role-adaptation scenarios.[^3]

### Conditions can change appearance, not just visibility

Here is the distinction that trips many people up, so it is worth the depth. Conditional rendering does not only control visibility. It can also control how an element looks. A condition can change an element's appearance, its color, its emphasis, its styling, based on a value. This is how a card highlights a risk or a priority: the element stays on the card, but its presentation adapts to the data.

This is distinct from hiding. When you hide an element, the element goes away. When you change its appearance, the element stays but it reads differently. A priority indicator can turn red for a high-priority case and green for a low one, while remaining visible in both situations. A status badge can change its color to signal the state. These are conditional appearance changes, and they are as much a part of conditional rendering as show and hide.[^4]

FlexCards support data-driven style rules directly. Through conditional styles you can add logic-based rules to element styles, controlling a combination of colors, borders, background colors, fonts, and other styling based on the data. This lets you add conditional emphasis to an element without building a separate state for every variation, and it keeps the styling consistent across the elements that share it. The card does not need five almost-identical cards to show five levels of priority. It needs one element and a styling rule that adapts to the value it receives.[^4]

The exam wants you to choose the right behavior, though. Hiding removes the element; an appearance change keeps it visible with different styling. If the user should not see the element at all, hide it. If the user should see it but understand its significance, change its appearance. The trap is using an appearance change when you mean to hide, or hiding when you mean to draw attention. Both are mismatches between the tool and the user need, and both come from not asking what the user should actually see in that moment.

![Hide versus change appearance: hiding removes the element entirely, while an appearance change keeps it visible with different styling, so hide what the user must not see and restyle what the user must understand](</diagrams/day-17-r-9a-conditional-rendering-in-flexcards-when-the-card-a/2-hide-vs-appearance.png>)

### The data source and the conditions must be designed together

Now the failure mode that appears on the exam more than any other. A condition can only evaluate a field that the data source actually returns. If you write a condition on a field the source does not provide, the condition never fires. The rule can never evaluate true, because the field it depends on is not there to compare. The element behaves as if the condition does not exist, which usually means it stays in whatever state it was configured in, and the card silently does the wrong thing.

So the source shape and the conditions must be designed together, from the start. When you decide the card needs a condition, you must confirm the data source returns the field that condition depends on. If the source does not, the fix is not to hand-wave the condition and hope. The fix is to change the source, add the field to the data fetch, or choose a condition field the source already provides. Designing the source to feed the conditions is as much a part of the design as writing the conditions themselves.

This is a common real-world failure, and it is the exact scenario the exam uses: a condition on a FlexCard never seems to fire. The most likely cause is not that the element is styled wrong, not that the card is expanded by default, and not that the card has too many actions. It is that the data source does not return the field the condition depends on, so the rule can never evaluate true. Styling problems change how the element looks, the expanded state changes the layout, and the action count has nothing to do with it. The missing field is the cause, because the condition has nothing to evaluate.[^1]

![Why a condition never fires: when the data source omits the field a condition depends on, the rule can never evaluate true, so the element silently stays in its configured state, and the fix is to design the source and the conditions together](</diagrams/day-17-r-9a-conditional-rendering-in-flexcards-when-the-card-a/4-condition-never-fires.png>)

### Conditional rendering reduces noise, not designer complexity

Here is the discipline that separates a good architect from a careless one. Conditional rendering should reduce noise for the user, not hide complexity from the designer. Each condition should serve a real user need: showing a warning only when relevant, showing an action only when the user can act, highlighting a risk only when there is one. Every condition you add should make the card more useful for the person reading it.

The trap is using conditions to bury decisions that the designer simply did not want to resolve. When a card has dozens of conditions, each hiding or revealing an element in a slightly different situation, the card becomes genuinely hard to reason about and hard to test. You cannot trace, at a glance, what the card will show for a given record, because the behavior is spread across a web of interdependent rules. The user sees chaos dressed up as adaptation, and the maintainer inherits a puzzle.

Keep the rules few and meaningful. Before adding a condition, ask whether it serves a user need the card would otherwise fail to meet. A condition that shows a warning only when the case is at risk serves a real need. A condition that hides an element simply because the designer did not want to look at it does not. The exam judges you on this: fewer, meaningful conditions beat a dense tangle of rules every time. Conditions are a tool for reducing the noise the user has to filter, not a tool for hiding the complexity the designer chose to avoid.

## Worked Example: the at-risk case card

Make conditional rendering concrete with a single card built to adapt across records and roles. This is the kind of scenario the exam asks you to design, so work through the reasoning, not just the feature names.

The object is a case. The card sits on the case record page, and its job is to tell the user where the case stands and what to do about it. The card must behave differently depending on the case data, so conditional rendering does the work.

Start with the elements the card always needs. The case number and subject establish the identity whether the case is new or closed, so those stay unconditional. The status and priority give the core state, so they are always visible too.

Now add the conditions that make the card adapt.

Condition one: a warning banner that appears only when the case is past its due date. The condition evaluates the due date field, compares it to today, and shows the banner only when the case is overdue. A case on time shows no banner. An overdue case shows a red banner telling the agent to act. The banner element exists in the definition, but its visibility depends entirely on the due date. This is the answer to the exam scenario about a warning that should appear only when a case is past its due date: add a condition that evaluates the due date and shows the banner only when it is past. Always showing it ignores the data, a static hide removes it entirely, and removing the element defeats the purpose.[^1]

Condition two: a priority emphasis that changes appearance, not visibility. The priority element stays visible for every case, but its styling adapts. A high-priority case shows the priority in red with added emphasis, a low-priority case shows it plainly. One element, one condition that changes its appearance, and the case's risk reads at a glance without the element ever disappearing. This is a conditional appearance change, distinct from hiding, and it is exactly the pattern for highlighting a risk on the card.

Condition three: role adaptation. An agent resolving the case sees the full set of actions: resolve, reassign, escalate. A manager reviewing the same case sees a read-only view, no workflow buttons, and the summary detail instead. The same card definition, one data source, conditional rendering surfaces the relevant elements for each role. This is the answer to the scenario about one card showing different elements to a manager and an agent: use conditional rendering to show the relevant elements for each role, rather than maintaining two separate definitions, showing everything to both, or removing the distinction entirely.[^3]

Now the source must cooperate. This card's conditions depend on the due date, the priority, the status, and likely a role or user property. The data source must return every one of those fields. If the source returns the case number and subject but omits the due date, the warning condition never fires, and the overdue cases silently show no warning. Designing the source and the conditions together means the moment the card gains the overdue condition, the source must gain the due date field. Otherwise the elegant logic is dead code, present in the definition and absent from the behavior.

Here is where the traps show up in a testing pass. A tester opens an overdue case and sees no warning. The instinct is to blame the styling. The real cause, if the source lacks the due date field, is that the condition never had anything to evaluate. A tester opens a high-priority case and the priority does not turn red; the value came through, so the appearance condition should fire. That one, if it fails, points at the appearance configuration, not the source. Distinguishing these tells you whether the failure is a missing source field or a wrongly configured styling rule, which is the difference between a two-minute fix and a long hunt.

## Configuration Walkthrough

Walk through adding conditional rendering to a FlexCard element, from deciding what should change to testing every branch.

1. **Identify the data values that should change what the card shows.** Look at the card and ask which values, if they differed, ought to change the display. A status, a due date, a priority, a role flag. Write each one down as a candidate condition driver. If a value changing would not change what the user should see, it does not need a condition.

2. **In the FlexCard editor, select an element and add a condition that evaluates a field in the data JSON or a state variable.** Open the element's properties, find the Conditions setting, and add a condition. Choose the data field to evaluate, pick the operator, and enter the value to check against. The condition defines the rule the card evaluates at render time. Salesforce's own documentation uses the example of showing reminder text on a contract card only when the renewal date is within a defined range, which is exactly this step: a condition on a field value that decides what the user sees.[^1]

3. **Configure the condition to show or hide the element, or to change its appearance, based on the evaluated value.** Decide whether the rule controls visibility or presentation. If the element should disappear when the rule is true, configure it to hide. If it should stay but look different, configure the appearance. Match the behavior to the user need: hide what must not be seen, restyle what must be understood. Use the conditional style rules when the change is about color, border, or emphasis, so one element adapts without spawning duplicate cards.[^4]

4. **Verify the data source returns the fields the conditions depend on, and test the card with records that exercise each condition branch.** Go through every condition and confirm its field is in the data the source returns. Then test. Open a record that should trigger the condition and confirm it does. Open a record that should not and confirm it does not. Then open a record from a different role and confirm the right elements surface. If a branch never fires in testing, check the source field first, because that is the most common cause of a condition that never evaluates true.[^1]

## Exam Traps

- **Writing a condition on a field the data source does not return.** The condition never fires, because the field it depends on is not there to compare, and the element behaves as if the condition does not exist. Design the source shape and the conditions together, from the start, and confirm every condition's field is in the payload before you rely on it.[^1]
- **Using conditional rendering to hide complexity rather than to serve a user need.** Too many conditions make the card hard to reason about and test, a dense web of interdependent rules that no one can trace. Keep the rules few and meaningful. Each condition should reduce the noise the user filters, not bury the decisions the designer avoided.
- **Using a condition to change appearance when the intent is to hide the element, or vice versa.** Hiding removes the element entirely. An appearance change keeps it visible with different styling. Choose the behavior that matches the user need: hide what the user must not see, restyle what the user must understand. Confusing the two is a mismatch between the tool and the situation.

## Exam Tip

Design the data source and the conditions together. A condition can only fire on a field the source actually returns, so confirm every field before you rely on the rule. Keep the conditions few and meaningful: each one should reduce the noise the user filters, not bury the decisions the designer avoided. Match the behavior to the need: hide what the user must not see, change appearance for what the user must understand. When the same card must serve different records, roles, or moments, conditional rendering keeps one definition consistent instead of spawning a pile of near-identical cards. And when a condition never fires, look at the source field first. It is usually missing, and a missing field, not a styling problem, is why the rule has nothing to evaluate.

## Try It

Open a sandbox with OmniStudio enabled and build the at-risk case card from this lesson. Create a case card that shows the identity and status unconditionally, then add the adaptive layer. Add a warning banner element and condition it to show only when the due date is past. Add a priority element and condition its appearance so a high-priority case shows emphasis while a low-priority one stays plain. Then add the role layer: use conditional rendering so the agent sees the workflow actions and the manager sees a read-only summary. Now make two deliberate mistakes and watch them fail. First, remove the due date field from the data source while leaving the overdue condition in place, and confirm the warning silently never appears: the condition has nothing to evaluate. Second, configure the priority element to hide instead of restyle, and watch it vanish on a high-priority case when the user should still see it, just emphasized. Both failures teach the same lesson the exam tests: a condition is only as good as the field it evaluates and the behavior it is configured to produce.
