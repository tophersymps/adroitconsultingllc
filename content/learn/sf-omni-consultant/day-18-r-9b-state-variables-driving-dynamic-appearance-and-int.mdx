The card on the screen is never quite finished. The user selects a row and the card highlights it. They expand a section and the detail slides open. They type into a field and the card reacts as they type. None of that came from the server. It all came from a set of in-memory values the card holds while it runs, the state variables. This is requirement R-9b from the OmniStudio Consultant exam, sitting in the FlexCards domain worth 18 percent, and it asks you to advise on using conditional rendering and state variables to dynamically adjust a card's appearance or content based on the underlying data or user interaction.[^1]

Lesson 17 gave you the conditions: rules the card evaluates at render time to decide what to show, hide, or restyle. This lesson gives you what those conditions read. A condition on its own has nothing to compare against until a state variable supplies the current value. State variables are the bridge between what the user does and what the card looks like. Understand them and you understand how a single card definition becomes something that reacts, that feels alive, that responds the instant the user acts.

## Deep Dive

### What a state variable is

A state variable is the card's in-memory value that tracks the current state of the interaction. If the data source is the card's memory of the record, the state variable is the card's memory of the moment: which row is selected, whether a section is expanded, what the user just typed, which toggle is on. These values exist on the card, change as the user interacts, and drive what the card shows next.

The naming matters. "State" here is not the record's state. It is the state of the interaction, the transient condition of the card while a person is using it. The card starts with a set of state variables at sensible defaults, and each user action updates one or more of them. The card re-renders against the new values, and the user sees the consequence of their action. This cycle, act, update state, re-render, is the whole engine behind a dynamic card.

The distinction you must hold for the exam is the one between data and state. Data comes from the source and reflects the record. It is the fetched payload: the case number, the status, the priority, the owner. State reflects the user's current interaction with the card: what they selected, what they opened, what they typed. Data is about the thing being shown. State is about the person looking at it and what they are doing right now.[^2]

### State variables drive dynamic appearance

The first job of a state variable is to make the card look different based on interaction. A card can change its look because a state variable changed. Select a row and the card highlights it. Toggle a value and the card changes color. Expand a section and the layout opens up. These are appearance changes driven by state, not by the data alone.

What makes this different from Lesson 17's conditional appearance is that the condition reads a value the user controls. A priority badge turning red when the data says high priority is data-driven appearance. A row highlighting because the user clicked it is state-driven appearance. Both use a condition; the condition's input is the difference. The state variable carries the user's selection, and the appearance rule reads it.

This is how the card responds in real time, without a server round trip, because the state lives on the card. The user clicks, the card updates the state variable in memory, and the card re-renders against the new value. No request, no wait, no loading spinner. The response is immediate because there is nothing to fetch. It already has what it needs; it just changed what it shows. That immediacy is the entire reason state variables exist.

A selectable list makes this concrete. Each selectable item sits on the card, and the card needs to show which one is chosen. A state variable holds the selected item's identifier. The user clicks a row, the state variable updates to that identifier, and every row re-evaluates a condition that compares its own identifier to the state. The clicked row matches and highlights. The rest do not. One state variable, N rows, and the whole card instantly reflects the selection. The highlight is not stored in the data source and it is not hardcoded into the card. It is a condition reading a state variable.[^3]

### State variables also drive interaction logic

Appearance is only half of it. State variables drive interaction logic too. They can hold the value of an input, the result of a user choice, or a flag that controls which elements are active. Conditional rendering reads these variables, so a state variable together with a condition produces the adaptive behavior.

The pattern is the same at every level. A checkbox is a state variable holding whether it is checked. A toggle holds on or off. A set of tabs holds which tab is active. A form field holds what the user typed. Each one is an in-memory value on the card, and each one feeds a condition that decides how the card behaves. The variable and the condition are inseparable partners: the variable stores the user's choice, the condition turns that choice into the card's behavior.

An input field is the clearest example of state driving behavior dynamically. The card needs to validate what the user types, or show a hint based on it, or enable a button only when the input is non-empty. All of that depends on a state variable that holds the current input value. Every keystroke updates it, and every condition that reads it re-evaluates. The card can change its own behavior mid-interaction, live, based on the accumulated typing, without sending a single request to a server.

So the cycle is: the user acts, the state changes, and the card re-renders. That is the sentence to hold. The action updates a state variable, the state variable changes, and the card draws itself again with the new value in place. Every dynamic card in OmniStudio runs on this loop. When the exam describes a card that reacts to the user, it is describing this cycle running.[^4]

### The distinction between data and state

The failure that shows up on the exam more than any other is confusing data with state. Data comes from the source and reflects the record. State reflects the user's current interaction with the card. The two are not the same thing, and neither one belongs in the other's container.

When you confuse them, two bad things happen. First, you try to write interaction state back to the data source. The user toggles a checkbox, and the card tries to persist that toggle into the fetched record, treating a transient interface choice as if it were record data. That is wrong twice over: the toggle is not part of the record, and writing it back implies persistence that has nothing to do with why the user toggled it. Second, you fail to update on interaction. If the selection lives in the data source rather than in a state variable, the card has nothing to re-render against when the user clicks, so it never registers the selection. The user clicks, nothing changes, and the card looks broken.

The rule is clean and worth memorizing: keep data for the record and state for the interaction. The data source holds what the record says. State variables hold what the user is doing. A selection, an expansion, an input value, a flag, those are state. The record's fields, the fetched list, those are data. When you design a card, sort every in-memory value into one of those two buckets, and keep each in its own.[^2]

### State variables are scoped to the card and its children

State is not global. A state variable lives on the card that declares it, and it is visible to that card's children. A parent FlexCard can pass state down to a child FlexCard, and the child can update state that the parent then observes. This is how nested cards coordinate, and it ties state management directly to the composition model you learned in the child-card lesson.

Think of the parent card and child card as cooperating through state. The parent holds a shared value, say the currently selected record. It passes that to the child. The child acts on it and, through its actions, updates it. The parent observes the change and re-renders its own elements accordingly. Neither card holds the whole story. Each holds the piece it owns, and the state flows between them.

This is why the child-card lesson matters here. If state had no scoping rule, nested cards could not coordinate at all; every card would be an island. Because state scopes to a card and flows to its children, a parent can drive a child's behavior and a child can feed a parent's display. The composition model from lesson 16 and the state model from this lesson are two halves of the same design. A nested card that does not coordinate through state is a nested card that cannot react as a unit.

When you design a nested card, decide which card owns which state. The parent owns the values that span both cards; the child owns the values that only the child needs. Do not duplicate a shared value in both cards, because then they drift. Give each value one owner, and let the scoping rules move it where the other card needs it.

### State needs a clear owner and a sensible default

The last discipline is ownership. State should be initialized to a sensible default and updated only by the interactions that should change it. A state variable with no clear owner, or one that is updated in many places, becomes hard to reason about, and the card's behavior slides toward unpredictable.

Start with the default. Every state variable needs a value before it is read, because the card renders on first load against whatever the variables hold. If a selection variable initializes to nothing, the card loads with no row selected, which is usually the right first state. If an expansion variable initializes to false, the card loads collapsed. If it is true, the card loads expanded. The default defines what the card looks like when it first appears, before the user touches anything. A state variable that is read before it is initialized renders in an undefined state, which is a genuine bug and an exam trap.[^4]

Then the owner. Every state variable should have one clear owner: one interaction that sets it, one meaning it carries, one reason it exists. When several interactions update the same variable from different places, you lose the ability to predict its value. You cannot trace why the card looks the way it does, because the value could have been set by any of several paths. The fix is not more variables. The fix is defining what each variable means and exactly which interaction changes it.

The exam trap is specific here. A card behaves unpredictably because a state variable is updated in many places. The wrong fixes are to add more state variables (which compounds the problem), to move all state into the data source (which breaks the data and state separation you just learned), or to remove conditional rendering (which does not fix the ownership at all). The right fix is to define what each state variable means and which interaction changes it, so the card becomes predictable again.[^5]

## Worked Example: the selectable product list card

Make this concrete with a card the exam scenarios love: a selectable list. An OmniStudio consultant builds a card on a policy record that lists the available add-on products and lets the user pick one to include. The card must highlight the picked product, show a summary of the choice, and enable a confirmation action only when a product is selected. All of it runs on state.

The data source fetches the product list. That is data, and it stays in the source. It gives the card the rows to show: each product's name, code, and price. The source does not know which product the user will pick, because the picking happens on the card, after the fetch. So the selection cannot live in the data source.

The card declares a state variable to hold the selected product, initialized to empty. On first load, no product is selected, so no row highlights, the summary reads blank, and the confirmation action is disabled. That is the sensible default. The card renders cleanly before the user does anything, because the state variable has a defined starting value.

Now wire the interaction. Each product row is selectable. When the user clicks a row, an atomic action or interaction updates the state variable to that product's identifier. One owner: the row click. The state variable has a clear meaning, the selected product, and a single interaction, the click, that changes it. Nothing else writes to it, so its value is always traceable.

The appearance follows the state. Every row carries a condition that compares its own identifier to the state variable. The selected row's identifier matches, so it highlights. Every other row's does not, so it stays plain. As the user clicks from row to row, the highlight moves live, because each click updates the state variable and every row re-evaluates against the new value. The card needs no server request to move the highlight. The state lives on the card and the card re-renders instantly.

The interaction logic follows the same state. The summary element reads the state variable and displays the selected product's name, which the data source provided. The confirmation action carries a condition based on the state variable: disabled while it is empty, enabled once it holds a value. Before the user picks anything, the user cannot confirm. The moment they pick, the action becomes available. The enabled state is not added in the data source and it is not a separate card; it is a condition reading a state variable.

Now test what you built, and watch the traps surface. First, remove the initialization from the selection state variable and load the card. It renders with the selection undefined instead of empty, and the highlight behavior gets flaky. That is the "forgot to initialize" trap. Second, try to store the selection back into the data source with each click. The card now treats a transient interface choice as record data, and you have broken the data and state separation. That is the "use the data source for state" trap. Third, let the confirmation action and the summary row both write to the selection variable. Two owners, and now you cannot predict which write lands or when. That is the "no clear owner" trap. All three fail in ways the exam asks you to diagnose.

## Configuration Walkthrough

Walk through setting up state variables on a FlexCard, in the order you would actually do it.

1. **In the FlexCard editor, define the state variables the card needs and set a sensible default for each.** Open the card's setup and add the state variables that track the interaction: a selected item, an expanded flag, an input value, a toggle. For each one, decide its meaning and give it a correct initial state. The default defines what the card looks like on first load, so it must be deliberate. A selection starts empty, an expansion starts collapsed, a toggle starts off, unless the card should load differently. Never leave one uninitialized, because the card would render against an undefined value.

2. **Bind elements to the state variables so the card's appearance and active elements reflect the current state.** Take the elements that should change with the interaction and connect them to the relevant state variable. The row that should highlight reads the selection state. The section that should expand reads the expansion flag. The action that should enable reads the input value. Binding means the element re-evaluates against the state variable every time it changes, so appearance and activity follow the state automatically.

3. **Wire user interactions, such as a click or an input change, to update the relevant state variable.** Attach the interaction to the element and configure it to write to the state variable. The row click sets the selection. The toggle sets the flag. The input change updates the typed value. Give each variable one clear owner, meaning one interaction that updates it, so its value stays traceable. This is the step where the card starts to behave: the user acts, and the state changes.

4. **Add conditions that read the state variables to drive the dynamic behavior, and verify the card re-renders correctly as the state changes.** Every appearance change and every active-element rule is a condition reading a state variable. Add them, then test. Click each row and confirm the highlight moves and the summary updates. Expand and collapse and confirm the layout reacts. Type into the field and confirm the hint and button react. Open the card in its initial state and confirm it renders cleanly at the defaults. The card should respond instantly to every interaction, with no server call, because all of it runs on state the card already holds.

## Exam Traps

- **Using the data source to hold interaction state.** Data reflects the record and should not be written back for a transient user action. A selection, an expansion, or a typed value is not record data and should not be persisted to the source. Keep interaction state in state variables and data in the source; the two do not mix.[^2]
- **Leaving a state variable with no clear owner or updating it in many places.** When several interactions write to the same variable, you cannot trace why the card behaves the way it does, and the behavior becomes unpredictable. Define what each state variable means and which interaction changes it. Adding more variables compounds the problem; it does not fix it.[^5]
- **Forgetting to initialize a state variable to a sensible default.** The card renders on first load against whatever the variables hold. A variable read before it is initialized renders in an undefined state. Initialize every state variable before it is read, and choose the default deliberately, because it defines the card's first appearance.[^4]

## Exam Tip

Keep data for the record and state for the interaction. Data comes from the source and reflects the record; state reflects the user's current interaction with the card, and it lives on the card, driving appearance and interaction logic in real time without a server round trip. Initialize every state variable to a sensible default before it is read, so the card renders cleanly on first load. Give each state variable a single clear owner, one interaction that changes it, so the card's behavior stays predictable. Bind elements to the state, wire the interactions, and let the conditions read the state to produce the dynamic behavior. When you design a nested card, decide which card owns which state and let the scoping rules flow it between parent and child. State is the bridge between what the user does and what the card shows, and keeping it clean, owned, and separate from data is the difference between a card that reacts and a card that misbehaves.

## Try It

Open a sandbox with OmniStudio enabled and build the selectable product list card from this lesson. Add a data source that returns a small list of products. Declare a state variable to hold the selected product, initialized to empty. Make each row selectable and wire its click to update the state variable. Add a condition to each row that highlights it when its identifier matches the state, a summary element that reads the selected product's name, and a confirmation action that enables only when the state variable holds a value. Watch the card react as you click: the highlight moves, the summary updates, and the action enables all instantly, with no server call. Then break it deliberately. Remove the initialization and refresh, and watch the card render against an undefined selection. Write the selection back to the data source on each click and watch the record get polluted with a transient choice. Add a second interaction that also writes to the selection variable and watch the highlighting become unpredictable. Each break teaches you the trap the exam tests: state needs a default, state must not live in the data source, and every state variable needs one clear owner.
