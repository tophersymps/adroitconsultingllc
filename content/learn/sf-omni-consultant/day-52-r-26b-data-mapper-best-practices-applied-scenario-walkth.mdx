Best practices are only useful when you apply them to a real scenario. Requirement r-26b is the applied half of the Data Mapper best practices requirement, and the exam in the Data Mappers domain, worth 17%, rewards consultants who can walk a flow step by step and name the right type and the right habit at each step. The organizing idea is simple: walk every flow step by step, name the operation, pick the type, and apply that step's best practice. The flow is only as good as its weakest step.

## Deep Dive

### A common scenario is a read, reshape, and write flow

A common scenario is a read, reshape, and write flow: an Extract or Turbo Extract reads source data, a Transform reshapes it, and a Load persists it [^1]. The consultant applies the right type to each step and keeps each step lean and explicit.

The read, reshape, write sequence is the backbone of many integrations. Data comes out of one system, gets reshaped into the shape another system expects, and is written where it needs to live. Each step has its own operation, and each operation has its own Data Mapper type [^1].

The exam tests this directly. A flow that reads source data, reshapes it, and writes it to Salesforce should use Extract or Turbo Extract, then Transform, then Load. The flow reads with Extract or Turbo Extract, reshapes with Transform, and writes with Load. The other orders do not match the read, reshape, write sequence [^1].

Why does the order matter? Because each step does a different job. The read pulls data out. The reshape changes its structure. The write persists it. Forcing one type to do all three, or putting them in the wrong order, ignores the need of each step and produces a flow that is wrong or slow.

### In a read-heavy scenario, minimize the read

In a read-heavy scenario, the best practice is to minimize the read. Filter in the query, select only needed fields, and use relationship queries to read related data in one call [^1]. The consultant who applies these keeps the read fast even when the source dataset is large.

The exam tests this directly. A flow that reads a large dataset but only a subset is needed should filter in the query to read only what is needed. Filtering in the query reads only the needed records, keeping the read light. Reading all and filtering later wastes resources, and the other options do not reduce the read [^1].

The performance argument is the same as in the previous lesson, but it matters more at scale. When the source dataset is large, an unfiltered read returns thousands of records the flow does not need. Filtering in the query returns only the subset, so less data crosses the network and less data flows through the rest of the process. A relationship query reads related data in one call, so the flow does not issue a separate query for each related record [^1].

### In a write-heavy scenario, be explicit about the write

In a write-heavy scenario, the best practice is to be explicit about the write. The consultant decides insert, update, or upsert, resolves the target record, and uses a unique external ID for upsert [^1]. Error management is part of the design, so the flow handles partial failures gracefully.

The write operation is a business decision. Whether a record is created, updated, or upserted depends on what the business needs the write to do. The consultant decides the operation, resolves the target record, and uses a unique external ID for upsert so the write is reliable [^3].

Error management is part of the design, not an afterthought. A Load can succeed on some records and fail on others. The consultant designs a branch that handles the failures, so a partial failure does not take down the whole flow and the data is not left in an unknown state [^1].

The exam tests this directly. In a write step of a flow, if some records fail validation, the consultant should have designed a branch that handles the failures. Error handling branches on failures so the flow reacts gracefully. No handling leaves the data unknown, and the other options do not address the failures [^1].

### In a reshape scenario, keep the mapping lean and standardize the data

In a reshape scenario, the best practice is to keep the mapping lean and standardize the data. The consultant maps only needed fields, applies functions and formulas where formats must be normalized, and states null and default behavior [^2]. The output is consistent regardless of the source.

Mapping only needed fields keeps the output small and the transform readable. Applying functions and formulas where formats must be normalized means the transform produces a consistent format even when the source data varies. Stating null and default behavior means the transform behaves predictably when a field is absent [^2].

The output is consistent regardless of the source. A date that arrives in one format becomes the format the downstream consumer expects. A field that is sometimes present and sometimes absent is handled explicitly. The transform normalizes the data so the rest of the flow can rely on a consistent shape [^2].

### A scenario that combines types shows how best practices compose

A scenario that combines types shows how best practices compose. The consultant reads only what is needed, reshapes it into the target shape, and writes it with explicit logic and error handling [^1]. Each step applies its own best practices, and the whole flow is fast, accurate, and reliable.

The composition is the point. Each step applies its own best practice, and the steps work together. The read is lean, so the reshape has less data to handle. The reshape is explicit, so the write receives a clean structure. The write is explicit and handles errors, so the flow survives real data [^1].

The composition also makes the flow easier to test. Because each step has one job and one type, the consultant can test each step in isolation. The Extract is tested to confirm it returns only what is needed. The Transform is tested to confirm it produces the target shape. The Load is tested to confirm it writes with the right logic and handles failures. A flow built from single-purpose steps is a flow whose failures are easy to locate, because the consultant knows which step produced the wrong output [^1].

The exam tests this directly. A flow that reads source data, reshapes it, and writes it to Salesforce should use Extract or Turbo Extract, then Transform, then Load. Each step applies its own best practice, and the whole flow is fast, accurate, and reliable [^1].

### The scenario walkthrough shows where best practices prevent failure

The scenario walkthrough also shows where best practices prevent failure. A consultant who filters early avoids reading too much, who resolves targets avoids wrong updates, and who validates before the write avoids validation failures [^1]. Best practices are the difference between a flow that works and one that fails under real data.

Each best practice prevents a specific failure. Filtering early prevents reading too much, which prevents a slow flow and wasted resources. Resolving targets prevents wrong updates, which prevents corrupting the wrong record. Validating before the write prevents validation failures, which prevents the flow from failing at write time [^1].

The exam tests this directly. In a write step of a flow, if some records fail validation, the consultant should have designed a branch that handles the failures. And a flow that reads a large dataset but only a subset is needed should filter in the query to read only what is needed [^1].

### A worked example: a nightly order sync

Put the pieces together with a concrete scenario. A consultant builds a flow that syncs orders from an external system into Salesforce each night. The flow reads the orders, reshapes them into the Salesforce order shape, and writes them as records.

The consultant starts with the read. The operation is a read, so the consultant uses an Extract. The Extract filters in the query to return only the orders that changed since the last sync, selects only the fields the order record needs, and uses a relationship query to read the related order line items in one call [^1]. The read is lean and fast.

Next, the consultant reshapes the data. The operation is a reshape, so the consultant uses a Transform. The Transform maps only the fields the order record needs, applies functions to normalize the date and currency formats from the external system, and states what happens to nulls and defaults [^2]. The output is consistent regardless of the source format.

Finally, the consultant writes the data. The operation is a write, so the consultant uses a Load. The consultant decides the write operation, resolves the target record, and uses a unique external ID for upsert so the sync is repeatable. The consultant designs error handling so a partial failure does not take down the whole sync [^1].

The result is a flow that is fast, accurate, and reliable. Each step applies its own best practice, and the steps compose. The read is lean, the reshape is explicit, and the write handles errors. The flow works under real data.

The same walkthrough applies to any read, reshape, and write flow, not just a nightly sync. A consultant who builds a customer onboarding flow, a quote generation flow, or a case intake flow names the operation at each step, picks the matching type, and applies that step's best practice. The habit is the same even when the data and the business process differ [^1].

## Config Walkthrough

The scenario walkthrough maps onto four concrete steps.

1. Walk through the scenario step by step, naming the operation at each step and choosing the Data Mapper type that matches it. Read with Extract or Turbo Extract, reshape with Transform, write with Load [^1].

2. For each read step, filter in the query, select only needed fields, and use relationship queries where data spans objects. This keeps the read light and fast [^1].

3. For each write step, decide insert, update, or upsert, resolve the target, and design error handling for partial failures. A Load can fail on some records, so the flow needs a branch that handles the failures [^1].

4. For each reshape step, map only needed fields, standardize with functions and formulas, and state null and default behavior. The output is consistent regardless of the source [^2].

Test the whole flow with real data and confirm each step produces the expected output before you activate the version.

## Exam Traps

Three traps dominate this requirement, and each is a specific, avoidable mistake.

**Applying one Data Mapper type to every step of a multi-step flow.** A read, reshape, and write sequence needs a different type per step, and forcing one type ignores the need of each step. Use Extract or Turbo Extract, then Transform, then Load [^1].

**Skipping error handling in a write step.** A Load can fail on some records, and without a branch the flow leaves the data in an unknown state. Design a branch that handles the failures [^1].

**Reading more data than a step needs.** An unfiltered read wastes resources and slows the flow, even when the later steps are well designed. Filter in the query to read only what is needed [^1].
