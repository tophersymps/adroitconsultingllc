You have seen the OmniScript that feels like a wall of questions. Every field the business could think of, dumped onto one screen, with no sense of order. The user stares at it, and the abandonment rate tells the story. That is what happens when someone builds an OmniScript without designing the journey first.

An OmniScript is a guided interaction, and a guided interaction is only as good as the journey it walks the user through. Requirement r-12a from the OmniScripts domain, worth 17% of the Salesforce OmniStudio Consultant exam, asks you to recommend effective multi-step, conditional, and branched OmniScript designs that align with defined business processes and user journeys, including multi-language support. The exam does not test whether you can add a Step in the builder. It tests whether you can look at a business process and turn it into a sequence of Steps that mirrors how a user actually thinks about the task, with conditions that appear at the right moment and a data JSON that stays coherent for the whole run.

The core idea is that the OmniScript should be a faithful rendering of the user journey, not a field dump. You map the business process to a sequence of user intents, then translate each intent into a Step. If the process has a decision point, that decision becomes a conditional branch or a conditional Step, not a hidden rule. The OmniScript is the journey, and the journey is designed before you open the builder.

## Deep Dive

### A multi-step OmniScript is a sequence of Steps, each holding Elements

A multi-step OmniScript is a linear sequence of Steps, and each Step holds one or more Elements. A Step is a page in the journey, and an Element is a field, a block, a button, or another piece of the page. The design rule is one logical user decision per Step: a Step should collect the inputs a user can answer in one sitting, then move on.

The reason this rule matters is cognitive load. Cramming unrelated fields into a single Step forces the user to re-read context and increases abandonment. If a Step mixes a credit check, an address capture, and a product selection, the user has to hold three unrelated threads at once, and the Step feels like a wall of questions. Decompose the journey into Steps that mirror the natural conversation a sales rep or service agent would have. A rep would verify the account, then update the details, then log the interaction. Each of those is a distinct intent, and each becomes a Step.

The exam tests this decomposition directly. The quiz describes an OmniScript for a service agent who must verify the account, then optionally update contact details, then log the interaction, with the account verification always running first, and asks what the correct Step structure is. The answer is three Steps: verify account, update contact details, log interaction, with the update Step conditional. The journey is three distinct user intents, so three Steps match it. The update Step is conditional because the agent may not need to change contact details, while verification and logging always run. One combined Step forces unrelated work together, and skipping verification violates the process requirement that it always run first.

### Conditional design means an Element or Step appears only when a condition is true

Conditional design means an Element or Step only appears when a data condition is true. Conditions are evaluated against the OmniScript data JSON, so the condition expression must reference the exact JSON path where the triggering value lives. Salesforce's guidance on conditional display is explicit: with the Conditional View property, you can hide an element or a group of elements in a block or step based on certain conditions, and every step, block, or element supports at least one conditional view.[^1]

The common failure is writing a condition against a field that is not yet populated because the Step that captures it sits later in the flow. The condition evaluates when the Element renders, and if the source field is still empty, the condition is false and the Element never appears. The fix is to order the Steps so the condition's source data is captured before the conditional Element is reached. Capture the source data first, then gate the dependent Element.

The quiz tests this failure directly. It describes a conditional Element that must appear only when a customer type field equals Enterprise, where the field is captured in the same Step just before the conditional Element, and asks why the Element might fail to appear. The answer is that the condition references the wrong JSON path for the customer type field. Conditions evaluate against the data JSON, so the expression must reference the exact path where the customer type value is stored. A wrong path evaluates to empty and the condition is false. Read-only Steps, missing labels, and missing translations do not prevent an Element from rendering.

The lesson is that a condition is only as good as the path it references and the timing of the data it reads. The condition must point at the exact JSON node where the value lives, and that node must be populated before the condition evaluates. Both are up-front design decisions, made when you name the Elements and order the Steps.

![A condition is only as good as the data it reads: capturing the source field first lets the conditional Element render, while a condition that reads a later Step evaluates to empty and the Element never appears](</diagrams/day-23-r-12a-multi-step-and-conditional-omniscript-design-align/2-conditional-timing.png>)

### The data JSON is the single source of truth for the whole run

The data JSON is the single source of truth for the whole run. Every Element writes into it, and every condition, formula, and display rule reads from it. Salesforce's guidance on merge fields makes this concrete: a merge field is a variable that references the value of a JSON node, and the syntax wraps a full JSON path with a percent sign on both ends, so a node named FirstName is accessed as %FirstName%.[^2] The data JSON is the living record of every value the journey has touched.

Because everything reads from the data JSON, you design its shape up front. Give Elements stable names, keep related data under a common parent object, and avoid reusing a name for two different meanings. A clean JSON contract makes conditions predictable and makes later Data Mapper and Integration Procedure work straightforward. If the data JSON is a mess, every condition, formula, and save that reads from it is fragile.

The lesson is that the data JSON is a contract, and you agree on it before you build. When you name an Element, you are naming a JSON node, and that name is what every condition and every downstream tool will reference. A stable, well-structured data JSON is the difference between an OmniScript that is easy to extend and one that breaks every time you touch it.

### User journey alignment starts before you open the builder

User journey alignment starts before you open the OmniScript builder. Map the business process to a sequence of user intents, then translate each intent into a Step. If the process has a decision point, that decision becomes a conditional branch or a conditional Step, not a hidden rule. Document the journey as a flow diagram first, and make the OmniScript a faithful rendering of that diagram.

The exam tip for this objective is to draw the user journey as a flow diagram before opening the builder, then make each Step one decision and each decision point a condition. The OmniScript should be a faithful rendering of that diagram. The diagram is where you see the structure of the journey, the sequence of intents, and the decision points. The builder is where you render that structure into Steps and conditions.

The reason this matters is that the diagram forces you to think about the journey before you think about the fields. A consultant who opens the builder and starts adding fields ends up with a field dump, because there is no structure to guide the placement of each field. A consultant who draws the journey first knows exactly where each field belongs, because each field serves a Step that serves an intent.

### Multi-language support is configured per Element

Multi-language support is configured per Element, not per OmniScript. Each Element's label, help text, and placeholder can carry translations, and the runtime picks the language from the user's locale or from a language value set in the data JSON. Salesforce's guidance on multi-language OmniScripts is explicit: allow a single OmniScript to run in multiple languages using Salesforce custom labels, and define translations for custom labels in the OmniScript's Edit Translations window.[^3]

The quiz tests this directly. It describes a consultant who wants the OmniScript to display in Spanish for users whose locale is set to Spanish, and asks where the language selection is handled. The answer is per Element, with the runtime picking the language from the user's locale or a data JSON value. Multi-language support is configured per Element, and the runtime selects the language from the user's locale or a language value in the data JSON. There is no single global language switch for the whole script, and Data Mappers and Integration Procedures do not control display language.

The lesson is to plan the translation set when you define the Element, because retrofitting translations onto a finished OmniScript is tedious and error prone. Every Element you forget becomes a hardcoded English label that leaks to users in other locales. Define the language set when you build the Element, and add the translation for each supported locale at creation time.

### Keep the number of Steps honest

Keep the number of Steps honest. A Step is a container, not a feature. If a Step holds one field, question whether the Step earns its place. Conversely, a Step that mixes a credit check, an address capture, and a product selection forces the user to hold unrelated context. The right granularity is the one that matches the user's mental model of the task, and it is worth iterating on with a real user before locking the design.

The exam tests the over-fragmentation failure. Treating every field as its own Step fragments the journey into dozens of clicks and makes the user re-read context constantly. Group fields that belong to one decision into a single Step. The right number of Steps is the number of distinct user intents, not the number of fields.

The lesson is that Step granularity is a judgment call, and the judgment is the user's mental model. A Step should collect the inputs a user can answer in one sitting. If the user thinks of the account verification as one thing, it is one Step, even if it has several fields. If the user thinks of the update and the log as separate things, they are separate Steps. Iterate with a real user to find the granularity that matches how they think about the task.

## Config Walkthrough

Apply the design with these four steps.

1. In the OmniScript builder, add a Step, then add Elements inside it. Give each Element a stable JSON name that matches the data contract you defined, and set the label to the user-facing text. The JSON name is what every condition and downstream tool will reference, so make it stable and meaningful.

2. To make an Element conditional, open its properties and set a Condition. Write the condition against the data JSON path, for example a field equals a value, and test it by running the OmniScript with data that both satisfies and violates the condition. Confirm the source field is captured before the conditional Element is reached, and confirm the path is the exact JSON node where the value lives.

3. To add translations, open the Element's language settings and add a translation for each supported locale. Set the default language and confirm the runtime picks the locale from the user's profile or the data JSON. Add the translation set when you build the Element, not after, so no Element is left with a hardcoded English label.

4. Reorder Steps by dragging them in the builder, then re-run the OmniScript to confirm the data JSON still populates in the order your conditions expect. Because conditions read from the data JSON, the order of the Steps determines whether the source data exists when a condition evaluates. Confirm the order matches the journey.

## Exam Traps

Three traps account for most misses on this objective.

First, writing a condition against a field captured in a later Step. The condition evaluates when the Element renders, and the source field is still empty, so the Element never appears. The exam will describe a conditional Element that fails to appear, and the correct answer is that the condition references a field that is not yet populated. Capture the source data first, then gate the dependent Element.

Second, treating every field as its own Step. This fragments the journey into dozens of clicks and makes the user re-read context constantly. The exam will describe a journey with distinct intents and expect one Step per intent, not one Step per field. Group fields that belong to one decision into a single Step.

Third, skipping the translation set at Element creation. You can add translations later, but every Element you forget becomes a hardcoded English label that leaks to users in other locales. The exam will describe a multi-language requirement and expect the language selection to be handled per Element, with the runtime picking the language from the user's locale or a data JSON value. Define the language set when you build the Element.
