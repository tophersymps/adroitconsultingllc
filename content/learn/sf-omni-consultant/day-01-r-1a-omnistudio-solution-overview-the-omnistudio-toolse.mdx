The OmniStudio Consultant exam opens with a fundamentals domain that asks you to describe the solution as a whole before you pick apart any single tool. Most candidates skim this area and fail a scenario question later because they never fixed the core mental model: OmniStudio is not four separate products that happen to be sold together. It is one product family whose four tools, FlexCards, OmniScripts, Integration Procedures, and Data Mappers, share a single runtime and a single metadata model and are designed to compose. Get that architectural point locked in your head and nearly every question in this requirement, plus the industry use cases that follow in the next lesson, becomes a mapping exercise rather than a guessing game. This lesson gives you that model, shows you why the design decisions matter, and walks you through proving the whole stack works in a sandbox.

## Deep Dive

### What OmniStudio actually is

OmniStudio is a Salesforce product family that gives consultants a declarative way to build guided, data-driven user journeys. Declarative means you configure behavior in a point-and-click designer instead of writing imperative code line by line. You define what the flow should do, the runtime executes it, and an admin or consultant can change it after release without touching Apex. That framing matters for certification: the consultant role is the person who ships a working flow in days, and OmniStudio exists to make that possible on the common path.

The family converges on four declarative tools, and the exam expects you to know each by name and by job.

The FlexCard is a contextual user interface component. It displays data about the current context, typically the record a user is looking at, and it supports states, drill-down flyouts, and actions. A FlexCard summarizes what is relevant and lets the user expand or act on that summary without leaving the page.

The OmniScript is a guided, multi-step user journey. Think of a form that spans several screens, validates input as the user moves through it, and ends with data written back to Salesforce or to an external system. The OmniScript is the tool for anything that walks a user through a transaction one step at a time.

The Integration Procedure, often shortened to IP, is server-side orchestration of many actions in a single call. Where an OmniScript lives in the browser and walks a person through steps, an IP runs on the server and chains together data operations, external callouts, and business logic with no user interaction in the middle.

The Data Mapper, formerly called the DataRaptor, handles extract, transform, and load of data. A Data Mapper reads from Salesforce, reshapes JSON between steps, and writes records back. It is the tool you reach for whenever data has to move or change shape.

These four are the ones this foundational requirement concentrates on. Later in the course the picture broadens online to Calculation Matrices and Calculation Procedures for decision tables and expression-based logic, but for day 1 the four-tool family is the unit of analysis. A good way to fix them in memory is to attach a verb to each one. An OmniScript is for guiding a flow. A FlexCard is for displaying context. An Integration Procedure is for orchestrating server-side work. A Data Mapper is for moving and reshaping data. When a scenario question asks which tool is the primary fit, the verb in the requirement points at the tool.

### The composition model is the architectural point

The single most important idea in this requirement, and in the whole fundamentals domain, is that the four tools are not isolated widgets. They share one runtime and one metadata model, and they are built to reference each other. A FlexCard can call an OmniScript. An OmniScript can invoke an Integration Procedure. An Integration Procedure can chain Data Mappers. Because everything speaks the same metadata language and runs on the same runtime, the pieces compose into end-to-end flows rather than sitting side by side as unconnected artifacts.

Consider a typical quote journey. The OmniScript collects the user's selections across its guided steps. On submit, it invokes an Integration Procedure. That IP calls a Data Mapper Extract to pull product and pricing data, an HTTP Action to reach an external rating system, and a Data Mapper Load to persist the quote. When the work finishes, a FlexCard on the completion step renders the result back to the user. Every step in that chain is a configured component rather than hand-written code, and the whole chain lives in the same org.

This composition is why the tools overlap at the edges. An OmniScript rarely stands alone; it leans on an IP, which leans on Data Mappers and HTTP Actions, and a FlexCard often closes the loop. Exam scenario questions therefore do not ask which tool touches the flow at all. They ask which tool is the primary fit for the stated action, and the answer follows the verb. A guided multi-step journey is a primary OmniScript fit even though it invokes other tools. A message that reduces the relationship to standalone products with separate runtimes is wrong, and a message that says the tools cannot reference each other is also wrong. The defining strength is that they compose.

The three quiz-style checks in this lesson all ride on that one idea. The first asks how the tools relate, and the correct answer is that they share one runtime and metadata model and are designed to compose. The second asks where OmniStudio's value is strongest, and the correct answer is high-volume, form-heavy, multi-step processes where the declarative tools cover the common path. The third asks why a build-once-install-many partner model works, and the correct answer is that every artifact is metadata that can be versioned, deployed, and reused across orgs. Hold the composition model and all three resolve.

### Where OmniStudio runs: platform and security

OmniStudio is delivered as a managed package on top of the Salesforce platform. That delivery choice carries a consequence the exam tests directly: OmniStudio does not replace the platform's native security model. It inherits it. Object permissions, sharing rules, and profiles still govern what a user can see, and OmniStudio adds its own license and permission-set layer only on top of those standard controls.

This means a user with no read access to the Account object still sees nothing from an Account inside an OmniScript, no matter how the component is configured. The runtime respects the record-level and field-level restrictions already in the org. In practice, to give a user access to the builders and the runtime you assign them the OmniStudio permission sets, and those grant the OmniStudio-specific features while the platform security stays in force underneath.

A common wrong answer on the exam is that OmniStudio bypasses object permissions so any user can see any record. That is false, and it contradicts the managed-package design. Because the package sits on the platform, the security checks happen exactly where they happen for any other Lightning component. The architect's job is to understand that OmniStudio layers on top rather than replaces.

### The declarative boundary and where Apex still fits

OmniStudio is declarative-first, not Apex-free. The declarative tools cover the common path: guided capture, standard data movement, orchestrated callouts, and contextual display. Unusual logic, non-standard integrations, and performance-critical steps can still require Apex. A claim that OmniStudio removes the need for Apex entirely overstates the product, and a claim that every step demands custom Apex understates it.

The architect's real job is to know where that boundary sits. When a use case is a standard transaction that walks a user through steps and writes records, build it declaratively. When the requirement needs logic that the designers cannot express, or an integration that the built-in HTTP actions cannot reach, plan for an Apex extension at the edge. The certification checks that you are not an absolutist: you should neither over-claim that everything is mouse-driven nor assume the toolkit is useless without code.

This boundary also explains where the value concentrates. OmniStudio is positioned for high-volume, form-heavy, multi-step processes such as quotes, applications, onboarding, and case deflection. In those settings the payoff comes from consistent guided steps, reusable components, and fewer custom pages to maintain. A single custom Lightning page replaced by a configurable OmniScript reduces maintenance because behavior changes can be made in the designer rather than shipped as code. For that kind of work the declarative-first design is exactly right.

### Metadata as a delivery asset

Because every OmniStudio artifact is metadata, it can be versioned, deployed through change sets or a DevOps pipeline, and reused across orgs. This is not a footnote; it is what makes the toolset a fit for partners and ISVs who build once and install into many customer orgs.

Contrast this with the wrong mental models. OmniStudio artifacts are not compiled into a single binary that cannot be reused, and they are not stored in the user's browser cache. They live in the org's metadata alongside custom objects, fields, flows, and pages. That means a consultant can move an OmniStudio package from a sandbox to production, or from one customer org to the next, using the same metadata deployment machinery used elsewhere on the platform.

For a partner or ISV this is the difference between a repeatable solution and a rebuild-every-time project. Build the Artifacts once, capture them in metadata, deploy to each customer's org, and adjust configuration at the customer level without rewriting the flow. The related exam point is that a statement claiming each org must rebuild every artifact from scratch contradicts the metadata design and is wrong.

### Why the composition model matters for scenario questions

The fundamentals domain is heavy on scenario questions that describe a customer situation and ask which tool fits or which design statement is true. The composition model is the lens that makes those questions quick. When you read a requirement, first classify it by the verb and the shape of the work.

A guided, multi-step transaction that a person completes screen by screen is an OmniScript job. A requirement about showing contextual data on a record page, with drill-down, is a FlexCard job. A requirement about coordinating several server-side calls in one trip is an Integration Procedure job. A requirement about moving or reshaping data between systems is a Data Mapper job.

Now layer in the platform facts. OmniStudio inherits security, so never accept an answer that claims it bypasses permissions. OmniStudio is declarative-first, so never accept an answer that claims Apex is required for every step, and never accept one that claims OmniStudio eliminates all custom code. OmniStudio artifacts are metadata, so a reuse-across-orgs model is not just possible, it is the design intent. The strongest answers combine the verb-to-tool mapping with one of those platform realities.

## Configuration Walkthrough

Use a sandbox for all four of these steps. Do not configure a production org until you have proven the stack works. The goal of the walkthrough is to confirm that the package, license, and permission layers are all wired before you invest in real artifacts.

1. Install the OmniStudio managed package in a sandbox first. After installation completes, open the App Launcher and confirm the OmniStudio app appears. If your profile shows the app but the OmniStudio tab set is not visible, check the tab visibility assignments for your profile, because tabs must be enabled before you can reach the builders.

2. Open the OmniStudio app and review the four primary builders. You should see the FlexCard, OmniScript, Integration Procedure, and Data Mapper designers. Take a moment to open each one so the artifact types you will create become familiar. You are not configuring anything yet; you are locating the tools you will use for the rest of the course.

3. Assign the base OmniStudio permission set to your user. Most of the day-to-day builders and the runtime are gated behind the OmniStudio permission sets, and a user without them cannot create or even render artifacts. Assign the permission set, confirm the assignment took effect on your user, and sign back in if the designers do not appear.

4. Create a throwaway FlexCard and a throwaway OmniScript in the sandbox and confirm the runtime renders them. The point is not to build something useful; it is to prove that the package, license, and permission layers all work end to end. Save both artifacts, open them in their runtime, and confirm they render without error. If one fails to render, the failure almost always points back to a missing permission set or a license assignment, so fix that layer before building real work.

## Exam Traps

- **Assuming OmniStudio replaces the platform security model.** It does not. OmniStudio runs on top of standard object permissions, sharing rules, and profiles. A user with no object access still sees nothing, even inside an OmniScript. Any answer that says OmniStudio bypasses or replaces security is wrong.

- **Treating the four tools as independent products.** They share a runtime and a metadata model, and the real power comes from composing them. A consultant who builds each in isolation misses the core value. The defining architectural point of OmniStudio is that a FlexCard can call an OmniScript and an OmniScript can invoke an Integration Procedure.

- **Believing OmniStudio removes the need for Apex entirely.** The declarative tools cover the common path, but custom logic, unusual integrations, and performance-critical steps still need Apex. The architect must plan for that boundary. Do not accept a message that claims everything is declarative, and do not accept one that claims custom code is needed for every step.

## Exam Tip

Before building anything in anger, prove the whole stack works in a sandbox with one throwaway FlexCard and one OmniScript. A working render confirms the package, license, and permission layers are all wired. That single verification step, done at the start of a project, saves you from a later failure that looks like an artifact bug but is actually a missing permission set or license assignment. On the exam, carry the same discipline into reading: when a scenario says a component renders nothing or is inaccessible, check the permission and license layer first.

## Try It

Open a sandbox with OmniStudio enabled. Following the walkthrough, install the package, confirm the app appears, assign the permission set, and then build one throwaway FlexCard and one throwaway OmniScript. Render both to confirm the stack works. Then extend the OmniScript to two guided steps: collect a customer name and account in step one, and confirm the transaction in step two with a Data Mapper Load that writes a record. Place a simple FlexCard on the record page that shows the captured field. Run the OmniScript end to end and confirm the FlexCard reflects the captured data. This exercise makes the composition model tangible: a guided capture, a backend data write, and a contextual display, all declarative in one org, all sharing one runtime.
