You can build a perfect FlexCard and still fail the user, if you put it where they never look. The card is data, elements, and actions wrapped in a component, and the component has to sit somewhere in Salesforce for anyone to see it. That somewhere is the placement, and it is a strategic decision before it is a technical one. This is requirement R-10a from the OmniStudio Consultant exam, in the FlexCards domain worth 18 percent, and it asks you to prescribe the optimal placement and methods for embedding FlexCards so they meet strategic user enablement goals.[^1]

Placement decides three things at once: who sees the card, when they see it, and how much room it has. A card on a case record page shows itself to whoever opens that case. A card in a console shows itself to the agent working cases side by side. A card on a tab shows itself to whoever navigates to that tab. Same card definition, different placement, completely different audience and context. The exam wants you to hold the whole map, so you can match each card to the user enablement goal it serves.

## Deep Dive

### What placement means for a FlexCard

When you activate a FlexCard, Salesforce publishes it with a set of targets, and those targets decide where the card is allowed to sit. The Publish Options on the card control which page types in Lightning App Builder can accept it: an App page, a Home page, a Record page, and, for Experience Cloud, a Community page and Community Default. If you uncheck every option and save, the platform automatically re-enables the App, Home, and Record targets as the defaults, so a card is rarely left with nowhere to go.[^2] Once the card is placed, you drag the FlexCard component onto a Lightning page in App Builder, select the card by name, set visibility rules, and activate the page.[^3]

The placement is not a cosmetic choice. It is the contract between the card and the user's task. A record-page card is bound to the record being viewed, so it answers a question about that record. A tab card owns its space and answers a question that spans many records. A console card sits inside the agent's working view and answers a question the agent needs mid-task. When you select a placement, you are declaring what kind of question this card answers and which person it serves.

### A Lightning component on a record page

The most common placement is a Lightning component on a record page. The card is bound to the record context, so it shows data for the exact record the user is viewing. The FlexCard component reads the record ID of the page, its data source resolves against that context, and the card renders whatever that record says. When the user opens a different record on the same page layout, the card follows, because the record anchor drives it.[^3]

This is the right placement when the card's value depends on the record context. A case card on a case record page, an account summary on an account record page, a health dashboard on a patient record page: each one earns its place because the card's entire meaning comes from the specific record the user opened. The user did the work of navigating to the record, so putting the card there means it catches them in the act of caring about that record. That is the strong version of placement following the task.

The quiz tests this directly. A card shows data for the specific record the user is viewing. The best placement is a Lightning component on the record page, because the card is bound to the record and follows it. A tab with no record anchor, a utility panel, or a dashboard with no context would all force the card to source its own context, and none of them would track the record the user is looking at. The record page is the only one of those that anchors the card to the record automatically.

### A tab placement

A tab placement gives the card its own space, independent of any single record. The card lives in a tab on its own, with room to breathe, and it is not anchored to record context. This suits a card that shows aggregate or cross-record data: a dashboard-style card that rolls up numbers across the org, a list of accounts that meet a criterion, a pipeline view that spans many opportunities.[^3]

Here is the trade you must hold. A tab removes the record anchor. The card can no longer assume it knows which record the user cares about, because there is no record. So the card must get its context another way. Its data source has to provide its own context through filters, parameters, or a broader query, instead of leaning on the page's record ID. The freedom of the space and the loss of the anchor come together, and the card's data source is what fills the gap.

The quiz tests this contrast. A card shows cross-record aggregate data for managers. The best placement is a tab that gives the card its own space, because the data is not anchored to one record. A Lightning component on a single record page or a card bound to a case record would anchor it to that one record, which is wrong for aggregate data, and a console view is built for task-driven agent work, not a manager's overview. The tab is the placement that lets cross-record data spread out.

### A console view placement

A console view placement embeds the card in the agent's console, alongside the workspace and its utilities. This is the placement for high-frequency, task-driven work, such as a service agent resolving cases. The console puts the card where the agent already works, so the card is present at the moment of action, not hidden behind a navigation step the agent might skip.[^2]

The console changes the design bar. The space is narrower and task-focused. An agent is mid-flow, juggling records and work items, so the card has to read instantly and act cleanly. It cannot sprawl. Its data source, its elements, and its actions should all be chosen to fit a compact, task-focused context. A card that lays out beautifully on a wide record page can feel cramped and noisy in a console utility, because the context the two placements impose is different.

The quiz pins this down. A service agent resolves cases in the console and needs a card that supports that task. The best placement is a console view alongside the workspace, because it puts the card where the agent already works. A tab the agent rarely opens, a manager dashboard, or a record page for a different object would each fail to put the card in front of the person doing the task. The console placement exists precisely to serve the working agent.

### Placement constrains the card's design

The placement is not a box you drop a finished card into. It is a constraint you design against. A record-page card has a record anchor and can lean on it, so its data source might need only the record ID and its elements can assume record context. A tab card must source its own context, so its data source carries filters and its elements explain what aggregate they show. A console card must fit a compact, task-focused space, so its elements strip down to the essentials and its actions stay within a thumb's reach.

The data source, the elements, and the actions should all be chosen for the placement. This is the difference between designing for the placement and forcing a card into one. If you design the card in isolation, you end up with a wide, record-dependent card that you then squeeze into a console utility, and it does not fit. The discipline is to start from the placement, understand what the placement allows and forbids, and build the card against that reality.

### Placement follows the user enablement goal

The organizing principle is the user enablement goal. Placement should follow the goal, not the card's convenience. If the goal is to help an agent resolve cases faster, the card belongs in the console or on the case record page, because that is where the agent acts. If the goal is to give managers a cross-record view, a tab or a dashboard placement is better, because that is where managers review. Choose the placement that puts the card where the user acts, then design the card for that placement.[^1]

This is why the exam frames placement as "prescribing" rather than just "placing." A consultant is not picking a location; they are making a strategic judgment about the user's workflow. The card that resolves cases fastest is worthless if the sidebar makes it uncomfortable in the console. The manager dashboard is worthless if it sits on a record page where it can only ever describe one record. The enablement goal selects the placement, and the placement selects the design.

## Worked Example: the service desk FlexCard suite

Make it concrete with a service desk that uses OmniStudio to support three different users. The organization resolves customer cases, and a consultant is asked to build FlexCards that help the whole team work. Three cards, three goals, three placements.

The first card is a case summary for the agent working a specific case. It shows the case number, priority, owner, open time, and the customer's recent contact history. The user enablement goal is to speed up resolution on the case in front of the agent. The right placement is a Lightning component on the case record page, because the agent opens the case and the card binds to that case. The data source reads the record ID, the card renders that case's data, and the elements stay focused on what is true of this one record. When the agent moves to the next case, the card follows. This placement scores on record context.[^3]

The second card is a daily workload view for the service manager. It rolls up cases by priority, shows how many are open and overdue, and lists the top accounts by case volume. The goal is a cross-record overview, so the placement is a tab that gives the card its own space. The card cannot lean on a record anchor, because no record is open. Its data source carries the filters and the aggregation, pulling from the case object across the whole org. The elements explain a summary, not a single record. The tab placement is the only one that lets this aggregate spread out.[^3]

The third card is a quick-actions strip for the agent in the middle of a task. It offers the common resolutions and a button to spin up a follow-up OmniScript, all packed to fit the console. The goal is to speed up the agent's task-driven work, so the placement is a console view alongside the workspace. The card reads instantly, the actions are compact, and it sits where the agent already is, so the agent never navigates away to find it. The design is stripped to what the task needs because the console demands it.[^2]

Now reverse a choice and watch it fail, the way the exam asks you to. Move the manager's aggregate card to the case record page, and it collapses to one case's data, which is nonsense for a workload rollup. Move the agent's quick-action strip to a tab the agent never opens, and the card becomes dead weight because the user is not there. Move the case summary to a utility panel, and it loses its record anchor, so it cannot tell which case it describes. Each failure is the same lesson: the placement must match the enablement goal, and the design must match the placement.

## Configuration Walkthrough

Walk through a placement decision and its setup, in the order you would actually do it.

1. **Identify the user enablement goal and the task the card supports, then choose the placement that puts the card where the user acts.** This is the first decision and it drives everything else. Name the goal, whether it is help an agent resolve a case, give a manager a cross-record view, or support a task the user performs. From the goal, pick the placement: a record page for record-bound data, a tab for cross-record views, a console view for task-driven work. Do not skip this step and jump into App Builder, because the placement decides the design that follows.

2. **For a record-page placement, add the FlexCard as a Lightning component on the record page and bind it to the record context.** In Lightning App Builder, open the record page, confirm the card's Publish Options include Record Page, drag the FlexCard component onto the canvas, select the card by name, and activate the page. The card reads the record ID and renders that record's data. This is the placement for any card whose value depends on the record the user is viewing.[^2][^3]

3. **For a tab placement, add the card to a tab and configure its data source to provide its own context, since there is no record anchor.** Place the card in the tab, then adjust the card's data source so it resolves on its own, with the filters and parameters that define what it shows. Because no record is open, the card cannot assume a record ID. Its context must come from the data source. This is the placement for aggregate or cross-record data.

4. **For a console placement, add the card to the console view and design it for the compact, task-focused space of the agent's workspace.** Place the card in the console alongside the utilities, then strip the design to fit: fewer elements, tighter actions, data source scoped to the task. The console demands a compact card because the agent is mid-flow. This is the placement for high-frequency, task-driven work.

## Exam Traps

- **Placing a card in a tab when its value depends on the record the user is viewing.** A tab has no record anchor. A record-bound card placed in a tab has to source its own context or it shows the wrong data, so the card cannot tell which record it describes. Use a record-page placement for any card whose value depends on the record context. The record page anchors the card to the record; a tab releases that anchor.[^2]

- **Designing the card in isolation and then forcing it into a placement it does not fit.** A console card needs a compact, task-focused design; a record-page card relies on the record anchor. If you design the card first without committing to a placement, you end up with a card that is the wrong shape for where it lands. Choose the placement first, then design the data source, elements, and actions to fit it.

- **Placing a task-driven card where the user does not work.** A card that helps an agent resolve cases belongs in the console or on the case record page, not buried in a tab the agent never opens. Placement must follow the user's workflow. If the card is not where the user acts, the user never benefits from it, no matter how well the card is built.

## Exam Tip

Place the card where the user acts, then design it for that placement. Use a record page for record-bound data, where the card is a Lightning component anchored to the record. Use a tab for cross-record or aggregate views, where the card owns its space and its data source provides its own context because there is no record anchor. Use a console view for task-driven work, where the card fits the compact, focused space of the agent's workspace. Let the enablement goal choose the placement, and let the placement constrain the data source, the elements, and the actions, so every card lands where its user works and is built to live there.
