Most OmniStudio exam prep teaches you the tools: the OmniScript, the FlexCard, the Integration Procedure, the Data Mapper. This lesson is different. It asks you to step back from the tools and understand the container they run in. OmniStudio does not run the same way in every org. It can run in a managed package runtime or in a standard runtime, and the difference is not a technical footnote. It decides how the product is installed, how it is upgraded, who controls versioning, and what your customer's admins can do on their own. Requirement R-4A asks you to explain both runtimes and know when each applies, and the exam tests it as a planning decision. The goal of this lesson is to make the runtime the first thing you confirm on a project, before you build a single artifact, because getting it wrong is expensive to undo.

## Deep Dive

### What a runtime is and why it matters

A runtime is the environment that executes your configured artifacts. When you build an OmniScript or a FlexCard, you are not writing code that a compiler turns into a standalone program. You are describing behavior that the platform interprets and runs. The runtime is the layer that does that interpreting. It is the machinery underneath your declarative configuration that turns a saved OmniScript definition into a working, multi-step journey a user can actually complete.

The reason the runtime matters to an architect is that it is not just an execution engine. It is also the delivery and maintenance channel. The runtime determines how the OmniStudio toolset gets into the org, how new versions of that toolset arrive, and how the artifacts you build are versioned and upgraded over time. Two orgs can run the exact same OmniScript definition and still behave differently in upgrade and versioning terms, purely because they run it in different runtimes. That is the core idea this requirement wants you to hold: the runtime is a delivery and maintenance decision as much as an execution one.

### The managed package runtime

The managed package runtime is the delivery model most customers receive. In this model, the OmniStudio code and metadata ship as a managed package. A managed package is a container of code and metadata that a vendor builds, versioned, and releases through the platform's package infrastructure. When a customer installs the managed package, they get the OmniStudio toolset and its runtime together, installed into their org as a package they can see in their installed packages list.

The defining feature of the managed package runtime is who controls upgrades. Because the toolset ships as a managed package, upgrades come through the vendor's package release process. The vendor builds a new version of the package, publishes it, and the customer installs or updates to that version. The customer does not rebuild OmniStudio from source, and they do not maintain the runtime code themselves. They receive the product the way most commercial software is delivered: as a packaged, versioned release that the vendor maintains and the customer installs.

This is the model that makes OmniStudio practical for most customers. It means the toolset arrives complete, it is upgraded by the vendor, and the customer's admins do not have to assemble or maintain the underlying runtime. When you see a customer org that installed OmniStudio as a package and receives updates through the vendor's release cadence, you are looking at the managed package runtime. It is the default assumption for most projects, and it is the model the exam treats as the typical one.

### The standard runtime

The standard runtime is the alternative. In this model, OmniStudio artifacts run on the platform's native runtime without the managed package layer. The toolset is not delivered as a vendor-managed package that the customer installs and updates. Instead, the artifacts run directly on the platform's own runtime, and the delivery and maintenance model changes accordingly.

The key difference is how upgrades and versioning are handled. In the managed package runtime, the vendor controls the release cadence and the customer installs package updates. In the standard runtime, there is no vendor package release process driving upgrades the same way. The customer's environment and delivery model determine how artifacts are versioned and upgraded, and the customer's admins have a different relationship to the runtime. They are not waiting on a package release from the vendor in the same way, because the runtime is native to the platform rather than shipped as a separate package.

The standard runtime applies when the customer's environment or delivery model does not use the managed package. This is not a free choice the architect makes for aesthetic reasons. It is usually dictated by the customer's environment and licensing. Some customers run in environments where the managed package is not the delivery path, and for those orgs the standard runtime is the reality. The architect's job is not to argue for one runtime over the other. It is to recognize which one the org actually uses and plan accordingly.

### Why the architect must know the runtime

The exam does not ask you to prefer one runtime. It asks you to know that the choice exists and that it changes the project. The runtime determines three things the architect owns: the upgrade path, the versioning of artifacts, and what the customer's admins can and cannot do without vendor involvement.

The upgrade path is the most visible. In the managed package runtime, upgrades arrive through the vendor's package release process, and the architect plans around that cadence. In the standard runtime, upgrades and versioning are handled in the environment's own way, and the architect plans around that instead. If you assume the wrong model, you will promise the customer an upgrade timeline that does not match reality, or you will schedule around a package release that is not how their org receives changes.

Versioning is the second consequence. How artifacts are versioned depends on the runtime. The managed package runtime ties artifact versioning to the package and its release process, which is why OmniStudio versioning best practices exist and why the vendor publishes guidance on how to manage versions across releases.[^1] The standard runtime versions artifacts in the environment's own model. If you build artifacts assuming one versioning scheme and the org uses the other, your versioning plan is wrong from the start.

The third consequence is what admins can do without the vendor. In the managed package runtime, the vendor controls the package and its releases, so some maintenance actions sit with the vendor. In the standard runtime, the customer's admins have a different set of capabilities and responsibilities. The architect must know which model applies so the customer's admins are not promised they can do something that the runtime does not let them do, or left unprepared for something they are now responsible for.

### The runtime is usually dictated, not chosen

A common mistake is to treat the runtime as a design decision the architect makes freely. It is not. The choice of runtime is usually dictated by the customer's environment and licensing. The customer's org, their licensing, and their delivery model determine which runtime applies, and the architect confirms it rather than selects it.

This is why the runtime is one of the first things to confirm on a project. Because it shapes deployment and upgrade planning, and because it is usually fixed by the customer's environment, the architect should establish it early. Confirming the runtime before building is not a formality. It is the difference between a deployment plan that matches the org and one that has to be reworked.

### The cost of getting it wrong

The reason the exam emphasizes confirming the runtime early is that reworking artifacts after a runtime change is costly. If you build a set of OmniScripts, FlexCards, and Integration Procedures assuming the managed package runtime, and the org actually uses the standard runtime, the versioning and upgrade model you built around is wrong. The artifacts themselves may still function, but the maintenance plan, the versioning scheme, and the upgrade expectations all have to be redone. That rework is expensive, and it is entirely avoidable by confirming the runtime before building.

The architect should confirm the runtime before building because the runtime affects how artifacts are versioned and upgraded. This is the single most important takeaway of the requirement. Confirm first, build second. The exam tests this directly, and the correct answer to a planning question is always the one that puts runtime confirmation before artifact construction.

### A worked scenario: two banks, two runtimes

Consider two banks, each starting an OmniStudio project to build a loan origination journey. The journeys look identical on paper: an OmniScript collects applicant details, an Integration Procedure runs a credit check, and a FlexCard shows the result. But the two orgs run different runtimes, and the projects diverge immediately.

Bank A runs the managed package runtime. OmniStudio arrived as a managed package, and the bank receives upgrades through the vendor's package release process. The architect plans the deployment around that cadence. When the vendor releases a new package version, the bank's admins install the update, and the architect schedules the loan origination artifacts to be validated against the new version. Versioning follows the package release model, and the architect documents that the vendor controls the runtime's release timeline.

Bank B runs the standard runtime. OmniStudio artifacts run on the platform's native runtime, and there is no vendor package release driving upgrades the same way. The architect confirms how artifacts are versioned and upgraded in that environment before building. The deployment plan reflects the standard runtime's model, and the customer's admins are told exactly what they can do without vendor involvement.

The two architects built the same-looking solution, but their deployment plans, their upgrade timelines, and their versioning schemes are completely different. That is the point of this requirement. The runtime is not decoration. It is the frame that every other planning decision hangs on, and the architect who confirms it first builds a plan that survives contact with the customer's real environment.

## Configuration Walkthrough

The configuration here is not about building an OmniScript. It is about establishing the runtime before you build anything, and recording the decision so the whole project plans around it. Walk through these steps on every new OmniStudio project.

1. Confirm which runtime the target org uses. Check the installed packages in the org to see whether OmniStudio is present as a managed package, and review the OmniStudio setup to see how the toolset is delivered and configured.[^2] This single check tells you which runtime you are planning for.
2. Record the runtime in the project plan. Write down whether the org uses the managed package runtime or the standard runtime, and note the evidence you used to confirm it. This is not busywork. It is the anchor that the upgrade and versioning sections of the plan hang on.
3. If the org uses the managed package runtime, note that upgrades come through the vendor's package release process. Document the release cadence and plan the deployment around it, so the customer's admins know that new versions arrive as package updates and that the vendor controls the runtime's release timeline.
4. If the org uses the standard runtime, confirm how artifacts are versioned and upgraded in that environment before building. Do not assume the managed package model. Ask how the environment handles versioning and upgrades, and record the answer so the plan reflects the standard runtime's reality.
5. Document the runtime decision in the deployment plan. Make the upgrade and versioning expectations explicit so the customer's admins know what they can do on their own and what requires vendor involvement. A runtime decision that lives only in your head is a runtime decision that will be forgotten.
6. Revisit the runtime confirmation before you build the first artifact. Confirm the runtime early, and confirm it again before construction starts, because reworking artifacts after a runtime change is costly and the confirmation is cheap.

## Exam Traps

- **Assuming every org uses the same runtime.** The managed package runtime is typical, but it is not universal. If you assume every org runs the managed package runtime, you will build upgrade and versioning expectations that are wrong for any org that uses the standard runtime. Confirm the runtime per org instead of assuming it.
- **Building artifacts before confirming the runtime.** The runtime determines how artifacts are versioned and upgraded. If you build first and confirm the runtime later, you risk costly rework when the runtime changes the versioning or upgrade model. Confirm the runtime before building, not after.
- **Treating the runtime choice as a free design decision.** The runtime is usually dictated by the customer's environment and licensing, not chosen by the architect for preference. If you treat it as a free choice, you will plan around a runtime the org does not actually use. Confirm what the environment dictates instead of deciding what you would prefer.
- **Confusing the runtime with the tools.** The runtime is the delivery and maintenance layer, not the OmniScript or FlexCard you build. A question about the runtime is a question about installation, upgrades, and versioning, not about which tool fits a use case. Keep the two separate.

## Exam Tip

Confirm the runtime before building anything. It determines the upgrade path and the versioning model, and reworking artifacts after a runtime change is costly. When a planning question asks what to confirm first, the answer is the runtime. When a question describes the managed package runtime, the answer is that the toolset ships as a managed package and is upgraded through the vendor's package release process. When a question describes the standard runtime, the answer is that upgrades and versioning are handled in the environment's own way. Hold those three pairings and the runtime questions resolve quickly.

## Try It

Open a sandbox with OmniStudio enabled and confirm which runtime it uses. Go to the installed packages list and check whether OmniStudio appears as a managed package, then review the OmniStudio setup to see how the toolset is delivered. Write a short project plan entry that records the runtime, the evidence you used to confirm it, and what it means for upgrades and versioning in that org. Then answer this question in your own words: if this org used the other runtime instead, which parts of your plan would have to change? That exercise makes the runtime concrete, because you are not just reading about the two models, you are confirming one in a real org and reasoning about what the alternative would change.
