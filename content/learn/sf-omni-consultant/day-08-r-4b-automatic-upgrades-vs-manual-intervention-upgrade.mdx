Day 7 established the two runtimes OmniStudio can run on and when each applies. This requirement, R-4B, turns from where the package runs to how it changes over time. Every managed package gets new versions, and OmniStudio is no different. The exam wants you to explain the difference between an automatic upgrade and a manual intervention upgrade, and then to make the harder call: which one a given org should use. That decision is not about convenience. It is about the org's tolerance for change, the fragility of its customizations, and how much control the customer wants to keep over when a new version lands. This lesson makes the upgrade decision methodical so that on test day you can read a customer story, weigh the change risk, and pick the path that protects the org instead of the path that is easiest.

## Deep Dive

### What an automatic upgrade is

An automatic upgrade applies a new version of the OmniStudio package without manual steps. When a new release becomes available, the org receives it and the package moves to the new version on its own, with no admin or architect having to review, test, or schedule anything first. The defining trait is that the change happens without deliberate human action at upgrade time.

The reason automatic upgrades exist is that they keep the org current with minimal effort. OmniStudio ships new features, fixes, and platform compatibility updates in each release, and an org that stays on automatic receives all of them as soon as they are available. For a customer that wants the latest behavior and can absorb it, that is a real benefit. The org does not fall behind, does not accumulate a backlog of skipped versions, and does not spend consultant time planning each release. The cost of staying current is effectively zero because the work is done for you.

The word that matters in the definition is behavior. An automatic upgrade applies a new version, and a new version can change how artifacts behave. A release might alter how an OmniScript renders a step, how a Data Mapper transforms a field, or how an Integration Procedure handles an error. None of that is guaranteed to be identical to the previous version. So an automatic upgrade is only safe when the org can accept the new version's behavior without reviewing it first. If the org cannot absorb a silent behavior change, automatic is the wrong path.

### What a manual intervention upgrade is

A manual intervention upgrade requires the admin or architect to take explicit steps before the new version lands. It is the opposite of automatic in one specific way: the change does not happen until a person decides it should. The person reviews, tests, and schedules, and only then does the org move to the new version.

The manual path is not a refusal to upgrade. It is a controlled way to upgrade. The curriculum names the sequence explicitly, and the exam expects you to hold it in order. First, review the release notes for the new version to learn what changed. Second, test the new version in a sandbox against the org's existing artifacts to confirm nothing breaks. Third, schedule the production upgrade at a controlled time. Each step is deliberate, and each one exists to protect the org from a change it did not expect.

The reason to choose manual intervention is control. An org with strict change control, or with customizations that could break on a new version, needs to decide when and how a new version lands. Manual intervention gives it that decision. The org can read the release notes, run its own artifacts against the new version in a sandbox, and pick a production window that does not collide with a busy period. The trade is effort: every upgrade now costs review time, testing time, and scheduling time. That is the price of control, and for a high-risk org it is a price worth paying.

### The decision is driven by tolerance for change

The choice between automatic and manual upgrades is not a preference. It is driven by the org's tolerance for change. Tolerance for change is a measure of how much unplanned or unreviewed change the org can absorb without harm. An org with strict change control, regulated processes, or customizations that could break on a new version has low tolerance. An org with few customizations, no regulatory constraints, and a willingness to take the latest behavior has high tolerance.

The mapping is direct. Low tolerance means manual intervention, because the org must control when and how a new version lands and must test first. High tolerance means automatic, because the org can accept the new version's behavior without review and wants the minimal-effort path to staying current.

The trap is treating the decision as a one-time default. The org's tolerance is not a fixed property. A customer that is low-risk today can become high-risk when it builds fragile customizations, and a customer that is high-risk can become low-risk as it simplifies. The upgrade strategy should be revisited as the org changes, not set once and forgotten.

### Why the architect must understand what a new version changes

Even on automatic upgrades, the architect should understand what the new version changes. This is the point that separates a thoughtful upgrade strategy from a careless one. An automatic upgrade removes the manual steps, but it does not remove the fact that a release can alter artifact behavior. The architect who does not know what changed cannot judge whether the org can absorb it.

Consider what happens when an org on automatic receives a release that changes how a Calculation Matrix evaluates a rule. The org's artifacts now behave differently, and no one reviewed the change before it landed. If the org could absorb that change silently, the automatic path was fine. If it could not, the org just took a breaking change without review, and the automatic path was a mistake. The architect's job is to know which of those two situations the org is in, and that knowledge comes from understanding what each release changes.

This is why the curriculum says an org that cannot absorb a change silently should not be on automatic. The automatic path is not a way to avoid understanding the package. It is a way to avoid the manual steps, and it is only valid when the understanding already exists and the answer is that the org can absorb the change.

### The controlled sequence of a manual upgrade

A manual intervention upgrade follows a controlled sequence, and the exam tests the order. The sequence is review, test, schedule. Each step has a specific job, and skipping one is how upgrades go wrong.

The first step is to review the release notes for the new version. Release notes tell you what changed: new features, changed behavior, fixed defects, and any deprecations. You read them to learn what the new version will do differently before you decide whether to take it. The OmniStudio release notes are the authoritative source for what a given release changes, and the exam expects you to know that review comes first, before any testing or scheduling.[^1]

The second step is to test the new version in a sandbox against the org's existing artifacts. This is where you confirm that the org's OmniScripts, FlexCards, Integration Procedures, Data Mappers, and Calculation Matrices still behave correctly on the new version. You run the artifacts, exercise the flows, and check the outputs. Sandbox testing is the step that catches a breaking change before it reaches production, and it is not optional. The curriculum is explicit that skipping it risks breaking production artifacts on the new version.

The third step is to schedule the production upgrade at a controlled time. You pick a window that works for the org, run the upgrade, and confirm the artifacts behave in production. The controlled time matters because an upgrade is a change, and a change should land when the org is ready to absorb it, not when it happens to be convenient.

### The upgrade strategy is part of the deployment plan

The upgrade strategy is not a standalone decision. It is part of the deployment plan, and it should be decided with the customer. The reason is that the choice affects two things the customer cares about: how quickly the org gets new features, and how much control the customer keeps over change.

An automatic upgrade gets new features quickly, because the org takes every release as it ships. A manual intervention upgrade gets new features more slowly, because each release waits for review, testing, and scheduling. The customer should understand that trade before the strategy is set. Similarly, an automatic upgrade gives the customer little control over when a change lands, while a manual intervention upgrade gives the customer a decision point at every release. The customer should choose which of those it wants.

Deciding the strategy with the customer also prevents a common failure: the architect picking a path and the customer discovering the consequences later. When the customer is part of the decision, the org's tolerance for change is stated up front, the effort of manual upgrades is accepted, and the deployment plan records the choice. The exam wants you to know that the upgrade strategy is a customer decision, not a technical default.

### A worked scenario: two banks, two strategies

To make the decision concrete, consider two banks that both run OmniStudio. The first bank has strict change control. Its compliance team must approve every change, and it has built several customizations that depend on exact artifact behavior, including a Calculation Matrix that drives a regulated pricing decision. A new OmniStudio release that changes how that matrix evaluates would be a serious problem if it landed unannounced.

This bank has low tolerance for change. The right strategy is manual intervention. The architect reviews the release notes for each new version, tests the new version in a sandbox against the bank's artifacts, confirms the pricing matrix still evaluates correctly, and then schedules the production upgrade in a controlled window that the compliance team has approved. The bank gets new features, but only after it has verified they are safe. The cost is effort at every release, and the bank accepts that cost because it needs the control.

The second bank has no fragile customizations. It uses OmniStudio for standard order capture and service journeys, its artifacts are simple, and it has no regulatory requirement to review every change. It wants the latest features as soon as they ship and is happy to take the new behavior without review.

This bank has high tolerance for change. The right strategy is automatic. The org stays current with minimal effort, receives each release as it becomes available, and does not spend consultant time planning every upgrade. The architect still understands what each release changes, because that understanding is what confirms the bank can absorb it, but the bank does not need the manual steps.

The two banks are the same product on the same platform, and they use opposite strategies. The difference is not the package. It is the org's tolerance for change. That is the entire point of this requirement.

## Configuration Walkthrough

The upgrade strategy is decided before the upgrade happens, and it is recorded in the deployment plan. Walk through it as a decision process.

1. Determine the org's tolerance for change. Ask whether the org has strict change control, whether it has customizations that could break on a new version, and whether it can accept a new version's behavior without review. Use those answers to choose automatic or manual upgrades. Low tolerance and fragile customizations point to manual intervention. High tolerance and simple artifacts point to automatic.
2. If you chose manual intervention, review the release notes for the new version before upgrading. Read what changed, what behavior was altered, and what was deprecated, and confirm the org can absorb the changes. Review comes first, before any testing or scheduling.
3. Test the new version in a sandbox against the org's existing artifacts. Run the OmniScripts, FlexCards, Integration Procedures, Data Mappers, and Calculation Matrices on the new version and confirm they behave correctly. This step catches a breaking change before it reaches production, and it is required for a manual upgrade.
4. Schedule the production upgrade at a controlled time and document the upgrade in the deployment plan. Pick a window the org is ready for, run the upgrade, confirm the artifacts behave in production, and record the strategy and the schedule so the decision is traceable.

## Exam Traps

- **Putting an org with strict change control or fragile customizations on automatic upgrades.** Automatic upgrades land a new version without review, and a release can alter artifact behavior. An org that cannot absorb a silent change should not be on automatic. Read the org's tolerance for change before you choose the path.
- **Skipping sandbox testing before a manual upgrade.** The manual sequence is review, test, schedule. Testing the new version in a sandbox against the org's artifacts is the step that catches a breaking change before production. Skipping it risks breaking production artifacts on the new version, and the exam treats it as a required step, not an optional one.
- **Choosing an upgrade path without considering the org's tolerance for change.** The decision is driven by tolerance, not convenience. Ignoring it either blocks new features (if you force manual on a low-risk org that wants automatic) or lets breaking changes through (if you force automatic on a high-risk org that needs manual). Weigh the org's tolerance before you pick.

## Exam Tip

Choose the upgrade path from the org's tolerance for change, not from convenience. Strict change control means manual intervention with sandbox testing first. Low risk and simple artifacts mean automatic. When a question describes a customer, find the change-control and customization clues, map them to tolerance, and let the tolerance pick the path.

## Try It

Open a sandbox with OmniStudio enabled and simulate a manual intervention upgrade. First, read the release notes for the current OmniStudio version and list three things that changed. Second, pick one of your existing artifacts, such as an OmniScript or a Data Mapper, and write down how you would test it against a new version in the sandbox, including the exact flows you would run and the outputs you would check. Third, write a short deployment-plan entry that records the upgrade strategy for a hypothetical customer with strict change control, including the review, test, and schedule steps. That exercise makes the manual sequence concrete: review the release notes, test in a sandbox, and schedule at a controlled time.
