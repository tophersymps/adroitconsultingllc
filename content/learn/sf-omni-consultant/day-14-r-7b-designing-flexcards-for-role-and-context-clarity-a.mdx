Two users look at the same object. A service agent resolving a case needs the case number, the customer's history, the SLA deadline, and the button that advances the workflow. A service manager reviewing the same account needs the trend of cases over the quarter, the average resolution time, and nothing to click, because the manager is reading, not working. If both users see one card that shows every field and every action, both lose: the agent hunts for the one field that matters while a dozen irrelevant actions clutter the screen, and the manager wades through workflow controls they will never use. This is the requirement behind Lesson 14, guiding the design of FlexCards that display relevant information from multiple data sources while ensuring the data is presented clearly and logically based on the user's role and context. It sits in the FlexCards domain, worth 18 percent of the OmniStudio Consultant exam, and it turns the layering skills from Lesson 13 into a judgment about the person on the other side of the screen.[^1]

The core idea is simple to state and easy to get wrong: a FlexCard is only useful if it shows the right data to the right person in the right moment. Role and context drive the design. This lesson unpacks what role and context actually mean for a card, why designing for a single primary role beats designing for everyone at once, and how conditional rendering adapts one card definition for the roles it serves.

## Deep Dive

### Role and context, not the object, drive the card

The instinct when building a card is to show everything the object contains. The object has a name, an owner, a status, a creation date, a description, a set of related records, and a history. Why not show it all? Because the user is not there to review the object. The user is there to accomplish a task, and the card exists to support that task. A card that displays the whole object forces every user to filter the screen mentally, to pick through the noise to find the two fields that advance their work. That filtering is work, and the card should do it for them.

The exam frames this as role and context. Role is who the user is and what they are allowed and expected to do: an agent who resolves cases, a manager who reviews trends, a sales rep who qualifies an opportunity. Context is where the card appears and what the user is doing there: on a record page anchored to that record, in a console while the user works a queue, in a utility panel that stays open while the user moves between records. Together, role and context determine what data the user needs and what actions they can take in the moment the card renders. The design question is not "what does this data source contain." The design question is "what does this user need to decide or do right here, and what subset of the data makes that possible."

This is the answer to the question about what drives which data a FlexCard displays. The full set of fields on the object is a constraint, not a driver. The number of elements available and the size of the data source are constraints too. The driver is the role's task and the context where the user acts. Everything else is material the design works within.[^2]

### Context shapes what the card focuses on

Context is more than a folder a card is dropped into. It defines the anchor of the card and the user's intent. A card placed on a record page has that record as its anchor. The user landed on the page because they are working that specific record, so the card should focus on that record: its key fields, its related records, the actions they can take on it. A card in a console works differently. The user there is often triaging across records, working a queue, deciding which case to grab next. The card that serves that moment may emphasize list-level signals, priority, SLA risk, assignment, rather than the deep detail that matters when the user has already committed to one record. A card in a utility panel may stay open while the user flits between records, so it should be compact and hold the information the user wants to keep visible.

The same card definition can be placed in multiple contexts. That is a legitimate pattern: one account card, placed on the account record page and in a console. But the data and elements should be chosen for the primary context where the user will act, not spread across every place the card could appear. Designing for a secondary context while the primary one suffers is a real mistake. Decide where the user most needs this card, design for that moment, and treat other placements as uses of a card built primarily for the first one. If a second context genuinely needs different data, that is usually a signal for a second card or for heavier conditional logic, not for a card that tries to cover every situation at once.

### Role-based design filters both data and actions

Role-based design is a two-sided discipline. It filters the data a role sees, and it filters the actions a role can take. These two filters are equally important, and both are frequently skipped.

On the data side, a manager may need aggregates and trends, the summary that tells them how a portfolio is performing. An agent may need the specific records they must work, the cases in their queue with the fields that tell them what to do next. The manager does not need the agent's to-do list, and the agent does not need the manager's portfolio rollup. Each role gets the slice of the data that serves its task.

On the actions side, the logic is parallel. An agent needs the action that advances the workflow: resolve the case, reassign it, escalate it, launch the OmniScript that guides the resolution. A manager may need only read-only views, because a manager in a review context is not supposed to be mutating records. Showing every possible action to every role buries the one action that matters. A screen with eleven buttons communicates poorly even when ten of them are technically valid for the current user, because the user must scan eleven buttons to find the one they actually want. The card should show the role the actions it is allowed to take and expected to take, and hide the rest.

The exam trap leans on exactly this. A card that shows actions the role cannot or should not take fails twice: it invites misuse, and it clutters the card. A read-only manager view with workflow actions is a design defect, not a generous feature. Match actions to the role's authority and task.[^1]

### Clarity: every element earns its place

Clarity means each element earns its place on the card. If a field, table, or chart does not help the user decide or act, it is noise, and it should be removed, even when the data source returns it. The data source can hand back a rich payload, one with dozens of fields, a full collection of related records, and several aggregate series. The card is not obligated to show any of it that the role's task does not require. Present only what the role's task needs, regardless of what the source provides.

This is the hard discipline of role-based design. The easy version adds a data table because the source returns an array. The disciplined version asks whether that array helps the intended user complete their task in this context, and leaves the array out of the layout if it does not. Extra fields are not harmless decoration. They are noise that obscures the decision. Every element on the card is competing for the user's attention, and the card wins by removing the competition, not by adding more of it.

The trap here is subtle because the data is real. A card that shows ten fields, all of them accurate, on an object with twenty, does not feel obviously wrong. But it is wrong in the same way as a card that shows all twenty: the user still has to filter, still has to decide what matters, still has to assemble the meaning themselves. Clarity is not achieved by showing fewer fields than the object has. It is achieved by showing the fields that serve the role's task and showing nothing else.

### Logic: the card tells one coherent story

Logic means the card reads as a coherent whole, not as a grab bag of unrelated facts. The elements build on each other. The identity establishes the subject: this is who or what the card is about. The facts establish the state: here is where the subject stands. The actions let the user respond: here is what you can do about it. A card that moves from the record name to an unrelated chart to a deep history table to a disconnected action forces the user to assemble the meaning themselves. That assembly is the designer's job, and offloading it is a design failure.

Think of it as a story the card tells in one glance. Identity opens the story. The facts develop it, giving the user the details that let them judge the situation. The actions close it, offering the response. If an element does not fit that narrative arc, either it does not belong, or it belongs in a different position. A chart of portfolio trends at the top of an agent's case card confuses the story before it starts. The same chart at the bottom of a manager's review card completes it. Logic is about order as much as it is about inclusion.

![The card tells one coherent story: identity opens the card, facts give the state, supporting detail adds depth, and actions close it, so the user assembles nothing](</diagrams/day-14-r-7b-designing-flexcards-for-role-and-context-clarity-a/3-card-story-arc.png>)

### Make role and context explicit, not implicit

Because the same card may serve multiple roles, the design should make role and context explicit rather than leaving the adaptation to chance. This is where conditional rendering and FlexCard state come in. The card definition can evaluate conditions, often against data values or user properties, and show or hide elements, change themes, or switch the visible action set accordingly. The design therefore adapts the card to the user rather than showing one static layout to everyone.

The pattern is: design the card around the primary role's task, then use conditional rendering to adapt it for other roles. The primary role gets the ideal experience, the fields and actions that complete their task. Other roles get a version tuned to them: the manager's read-only view without workflow actions, the escalated view with the escalation action available. The data source must stay flexible enough to support the different views, which often means the source returns enough to feed both the aggregate the manager sees and the record-level detail the agent sees, and the card uses conditional logic to show each role the slice it needs.[^3]

This is the whole answer to the scenario about a service agent and a manager looking at the same case card. The correct approach is not to show the same full set of fields and actions to both roles, which buries what each needs. It is not to remove all actions so neither role can act, which breaks the agent's workflow. It is not to show only the manager's aggregate data to both, which breaks the agent's task. It is to design for the agent's task, then use conditional rendering to adapt the card for the manager's read-only view. The agent gets the fields and actions to resolve cases. The manager gets a read-only summary. One card definition, two role-appropriate experiences.

## Worked Example: the case resolution card

Make role and context concrete with a single card built for the primary role of a service agent, then adapted for a service manager who reviews the same cases.

The object is a case. The agent's task is to resolve it: understand what the customer needs, check the SLA deadline, act. The manager's task is to review how the team is doing: see the workload, the trends, the risk, without making changes.

Start with role and context. The primary role is the agent working the case from the case record page. That is the moment the card must serve best. The manager is a secondary reader, someone who opens the same card to glance at performance. Design for the agent first.

List the data the agent needs to resolve the case: the case number and subject as identity; the priority, status, SLA deadline, and account name as key facts; recent activity or a short list of related items as supporting detail; and the actions that resolve or escalate the case at the bottom. Now list what the manager needs: the identity, the priority and status, and the trend of cases or the average resolution time as supporting detail. The manager needs no workflow actions. It is a read-only view.

Now filter. The source returns a rich payload, many fields on the case, a full activity history, several aggregate series. The card does not show all of it to the agent. It shows the identity, the key facts that tell the agent what to do, the supporting detail that gives context, and the actions that advance the work. The manager's adapted view drops the workflow actions, keeps the identity and a compact set of facts, and adds the summary the manager cares about.

Now order it as one story. Identity first: the case number and subject anchor the card. Facts next: priority, status, SLA deadline give the state. Supporting detail next: the activity that adds depth. Actions last: the buttons that act on the content that precedes them. The story reads cleanly for the agent.

Then make the roles explicit with conditional rendering. The card evaluates who is viewing it and what they are doing, and adapts. The agent sees the full layout with the resolve and escalate actions. The manager sees a read-only layout, no workflow buttons, and the summary detail instead. One card definition serves both, and each role sees a card that looks like it was designed for them, because it was.

![One card definition, two role-appropriate views: the service agent sees identity, key facts, supporting detail, and the resolve and escalate actions, while the service manager sees a read-only view with the summary detail and no workflow buttons](</diagrams/day-14-r-7b-designing-flexcards-for-role-and-context-clarity-a/2-agent-vs-manager-view.png>)

Now apply the trap logic. If the card shows every field and every action to both roles, the agent scans a dozen fields to find the SLA deadline and a row of buttons to find resolve, and the manager sees workflow controls they must not use. If the card removes all actions, the agent cannot resolve the case and the workflow grinds to a halt. If the card shows only the manager's aggregates to both, the agent loses the record-level detail and the actions they need. Each failure is the same mistake: designing for no one's task instead of for the primary role's task with adaptation for the rest.

## Configuration Walkthrough

Walk through building a role- and context-aware FlexCard, from the decision about who the card serves to the published, adaptive card.

1. **Identify the primary role and task.** Name the user whose decision or action the card exists to support, and the task they are completing when they see it. Write it down: "the service agent resolving a case from the case record page." This single sentence becomes the design target for everything that follows. If you cannot articulate the primary role and task, you are not ready to add an element.

2. **List the data that role needs, and remove everything else.** Enumerate the fields, collections, and aggregates the primary role needs to make their decision or take their action: the identity, the key facts, the supporting detail, and the actions. Then go through the payload and consciously leave out everything not on that list, even though the source returns it. The card presents only what the role's task requires.

3. **Choose the elements that present that data clearly.** Match each piece of data to the element that shows it best: data tables for collections of records, charts for aggregates and trends, inputs and menus for discrete values the user selects or enters, and text for the key facts that stand alone. Do not overload one element with data that belongs in another. A collection belongs in a table, an aggregate in a chart, a discrete choice in a menu, a single value in text.

4. **Order the elements into one story, and confirm the actions match the role.** Arrange the elements so the card reads from identity to facts to detail to actions, a coherent arc the user follows in one pass. Then confirm the actions are the ones the role is allowed and expected to take, not every action that is technically available. Where the card serves other roles, add conditional rendering to adapt the data and actions to each one.

## Exam Traps

- **Designing one card that shows every field and every action for every role.** This buries the data and actions that matter and forces each role to filter mentally. Design for the primary role's task, then use conditional rendering to adapt the card for other roles. Never let one static card try to serve everyone.
- **Showing actions the role cannot or should not take.** A read-only manager view with workflow actions invites misuse and clutters the card. Match actions to the role's authority and task. An agent needs the action that advances the workflow; a manager in a review context may need none.
- **Including data the role does not need because the source returns it.** Extra fields are noise that obscure the decision, even when they are accurate. The card presents only what the role's task requires, regardless of what the source provides. The source returning a rich payload is not a reason to display it all.

![Three ways a role-aware card fails: showing every field and action to every role, showing actions the role cannot take, and including data the role does not need, each paired with the right approach of designing for the primary role and adapting for the rest](</diagrams/day-14-r-7b-designing-flexcards-for-role-and-context-clarity-a/4-exam-traps.png>)

## Exam Tip

Design the card around the role's decision, not the object's completeness. Name the primary role and task first. Show only the data that role needs to decide or act, and remove everything else from the layout even when the source returns it. Match each element to the shape of the data: a data table for a collection, a chart for an aggregate, an input or menu for a discrete value, text for a key fact. Order the elements as one story, identity to facts to actions, so the user assembles nothing. Give each role only the actions it is allowed and expected to take. Then make the roles explicit with conditional rendering, adapting a card designed for the primary role to the others who see it. A card is clear and logical when it shows the right data to the right person in the right moment, and nothing else.

## Try It

Open a sandbox with OmniStudio enabled and take the case resolution scenario from this lesson. Define the primary role as the service agent resolving a case from the record page, list the data and actions that role needs, and build the card: identity, key facts, supporting detail, and actions. Bind a data table to a collection, bind a chart to an aggregate, and put the actions at the bottom. Then add a second role: a manager who reviews case trends without acting on records. Use conditional rendering so the manager's view hides the workflow actions and shows the summary detail instead. Now make two deliberate mistakes and watch them fail: add every field and action for both roles and confirm how quickly the card buries the resolve button, and show workflow actions to the manager and confirm how the read-only reader is invited to misuse them. Both failures teach the same lesson: role and context decide what the card shows, and every element must earn its place.
