Requirement r-20b is where the whole Integration Procedure finally pays off. You have fetched data, reshaped it, filtered it, and assigned values, and now the client-side component is waiting for the result. The exam wants you to recommend approaches for strategically using the Data Mapper Transform, Set Values, and Response actions to transform, filter, and structure data before sending it to that client. In the Integration Procedures domain, worth 17% of the exam, the Response action is the last thing the client sees, and it is the place where a clean pipeline either delivers or falls apart [^3]. The organizing idea is simple: the Response action assembles, it does not transform.

## Deep Dive

### The Response action is the final step of the Integration Procedure

The Response action is the last step of an Integration Procedure. It defines the structure of the data that is returned to the client-side component, whether that component is an OmniScript, a FlexCard, or some other consumer [^1]. It is one of the actions that make up an Integration Procedure, alongside the HTTP Action, the Data Mapper actions, and the Set Values action [^2]. Everything that ran before it, the HTTP Actions, the Data Mapper Transforms, the Set Values actions, produced variables inside the IP. The Response action takes those output variables and assembles them into the shape the client expects.

Think of the IP as a kitchen and the Response action as the plate. The kitchen does the cooking, the chopping, the seasoning, and the plating happens at the very end. You do not chop vegetables on the plate. The Response action is the plate, and the Data Mapper Transform and Set Values actions are the chopping and the seasoning. When you understand that division, the whole requirement clicks.

The exam tests this directly. The Response action is the final step of an IP, and it defines the structure of the data returned to the client-side component [^1]. It assembles the output variables into the shape the client expects. It is not the place where the data gets its meaning; it is the place where the data gets its final form.

### The Response action assembles, it does not transform

Here is the strategic heart of the requirement. The Response action should assemble already-shaped data, not perform last-minute transformation [^1]. All reshaping, filtering, and value assignment should happen in the Data Mapper Transform and Set Values actions that run before it. This keeps the Response action simple and the IP testable.

Why does this matter so much? Because a Response action that reshapes is a Response action you cannot easily test. When the transform logic lives inside the Response action, you cannot preview it in isolation, you cannot see the intermediate shape, and you cannot tell whether a failure came from the mapping or from the assembly. When the transform logic lives in the Data Mapper and Set Values actions, each one is independently testable, and the Response action is a thin, predictable final step.

The exam tests this directly. Reshaping and value assignment belong in the Data Mapper Transform and Set Values actions that run before the Response action. The Response action should only assemble the already-shaped data. The named credential and request body are not for response shaping [^1]. If a question asks where the final reshaping happens, the answer is the Data Mapper Transform and Set Values actions that run before the Response action, never inside the Response action itself.

### The response structure is driven by the client component's contract

The response structure is not something you invent. It is driven by the client component's contract [^1]. The consultant must know what fields the client expects, their names, and their types, and the Response action must produce exactly that structure. A mismatch between the response and the client's expectation surfaces as empty or broken UI.

Picture a FlexCard that expects a field named `accountName` as a string. If the Response action returns a field named `name` or returns the value as a number, the card renders blank or throws. The data is correct, the value is there, but the contract is broken, so the UI is broken. The consultant's job is to read the client component's contract first and build the Response action against it.

This is why the Response action is the spec the whole IP is built against. You do not build the IP and then figure out what the client wants. You read the client's contract, and every action in the IP, the HTTP call, the transform, the Set Values, is working toward producing the variables that the Response action will assemble into that contract.

### Cardinality: single object versus collection

The Response action can return a single object or a collection, and the consultant must match the client's expectation [^1]. A client that iterates over a list needs a collection; a client that reads one record needs a single object. Returning the wrong cardinality is a common integration failure.

Here is the concrete failure mode. A client component iterates over a list of records, but the Response action returns a single object. What happens? The client cannot iterate over a single object, so the integration fails at the client even though the underlying data is correct [^1]. The data is all there, the fields are right, but the client expected an array and got an object, so the iteration fails.

The exam tests this directly. A client component iterates over a list of records, but the Response action returns a single object. The result is that the client cannot iterate over a single object, so the integration fails at the client. A client that iterates over a list needs a collection. Returning a single object means the client has nothing to iterate, so the integration fails at the client even though the underlying data is correct [^1].

The reverse is equally broken. A client that reads one record and gets a collection has to reach into the array to find the record, and if the code does not expect the array, it breaks. The consultant reads the client's contract, notes whether it iterates or reads a single record, and sets the Response action's cardinality to match.

### Filtering for the response happens as early as possible

Filtering for the response can happen at multiple points, but the strategic choice is to filter as early as possible [^1]. If the external system can filter, do it in the request. If not, filter in the Data Mapper or in a Set Values-driven condition before the Response action, so the client never receives records it cannot use.

The efficiency argument is the same one you have seen throughout this course. The earlier the filter, the less data the rest of the pipeline has to carry. If the external endpoint supports a query parameter that returns only the matching records, use it, and the IP never sees the records the client does not need. If the external system cannot filter, the Data Mapper Transform or a Set Values-driven condition drops the records before the Response action assembles the result.

The strategic point is that the client should never receive records it cannot use. Filtering before the Response action means the client gets exactly the records it can render, and the Response action assembles a clean, filtered result.

### Error handling produces a structured response

Error handling interacts with the Response action in a way that many consultants miss. When the IP fails, the error path should still produce a structured response the client can handle, such as an error object with a code and message [^1]. A client that receives an unexpected shape on failure is as broken as one that receives no data.

The exam tests this directly. When an Integration Procedure fails, what should the error path return to the client component? A structured error object with a code and message. A structured error object lets the client distinguish a real failure from missing data and handle it gracefully. An empty payload or nothing gives the client no signal, and the raw external response may not match the client's expected shape [^1].

Think about what the client does with each option. An empty payload looks like a successful call that returned no data, so the client renders an empty state and the user has no idea the external system was down. Nothing at all leaves the client waiting or throws an unhandled error. The raw external response may be a SOAP fault or a REST error body that the client component was never designed to parse. A structured error object with a code and message is the one option the client can read, understand, and display to the user.

### A worked example: returning a filtered list to a FlexCard

Put the pieces together with a concrete scenario. A FlexCard needs to display a filtered list of open cases for a customer. The client component iterates over the list, so it needs a collection. The consultant reads the contract first: the card expects an array of case objects, each with a case number, a subject, and a status.

The IP calls the external system, which returns every case for the customer, open and closed. The consultant filters at the source if the endpoint supports it, passing a query parameter for open cases only. If the endpoint cannot filter, the Data Mapper Transform drops the closed cases before the Response action. Either way, the client never receives records it cannot use [^1].

The Data Mapper Transform flattens and renames the fields into the names the card expects. A Set Values action assigns a default status where the source is silent. Then the Response action assembles the already-shaped data into a collection, because the card iterates over a list. The card renders the open cases, and the user sees exactly what they need [^1].

Now add the failure. The external system is down. The IP's error path captures the failure and returns a structured error object with a code and message. The card displays a meaningful message instead of a blank screen, and the user knows the data is temporarily unavailable rather than thinking there are no open cases [^1].

Try it yourself. In a sandbox, build an IP that returns a list to a FlexCard. Read the card's contract, filter the data before the Response action, set the cardinality to a collection, and add an error path that returns a structured error object. Confirm from the debug log that the card receives the collection on success and the error object on failure.

## Config Walkthrough

The Response action configuration maps onto four concrete steps.

1. Confirm the client component's expected response structure, including field names, types, and whether it expects a single object or a collection. Read the contract before you build anything, because the whole IP is built against it [^1].

2. Run the Data Mapper Transform and Set Values actions before the Response action so the data is already shaped. Reshape, filter, and assign values in these actions, and let the Response action stay thin [^1].

3. Configure the Response action to assemble the output variables into the exact structure the client expects. Match the field names, the types, and the cardinality, single object or collection, to the client's contract [^1].

4. Define an error path that returns a structured error object with a code and message so the client can handle failures gracefully. Test the happy path and the error path from the Preview tab, and confirm the client receives the right shape in both cases [^1].

## Exam Traps

Three traps dominate this requirement, and each is a specific, avoidable mistake.

**Doing last-minute reshaping inside the Response action.** The Response action should assemble, not transform, and reshaping there makes the IP hard to test and maintain [^1]. When the transform logic lives in the Response action, you cannot preview it in isolation and you cannot tell where a failure came from. Keep the reshaping in the Data Mapper Transform and Set Values actions.

**Returning a single object when the client iterates over a list, or a collection when the client reads one record.** The cardinality mismatch breaks the client even though the data is correct [^1]. A client that iterates over a list needs a collection, and a client that reads one record needs a single object. Read the contract and match the cardinality.

**Returning an unstructured or empty payload on failure.** The client cannot distinguish a real error from missing data, so the error path must return a structured error object [^1]. An empty payload looks like a successful call with no data, and the raw external response may not match the client's expected shape. Return a structured error object with a code and message.

The exam tip that ties these together: shape the data before the Response action and let the Response action only assemble. The client component's contract, including cardinality, is the spec the whole IP is built against.
