Requirement r-23b continues the Data Mappers domain, worth 17% of the exam [^4], and it asks you to explain the possibilities of complex mapping, filtering, and data manipulation rules, utilizing functions and formulas to ensure data accuracy and standardization. Lesson 45 covered the mapping and filtering half of that sentence. This lesson covers the manipulation half. A Data Mapper can do more than move a value from one field to another. It can compute a new value, convert a format, branch on a condition, and standardize inconsistent input, and it does all of that with functions and formulas defined inside the mapping. The exam wants you to know which function does which job and when a formula is the right tool.

## Deep Dive

### Functions are the manipulation engine of a Data Mapper

Functions are the manipulation engine of a Data Mapper. They take input values, apply a defined operation, and return a result, and they run as data flows through the mapping. The Data Mapper supports a set of functions that cover string, date, number, and conditional operations, and the consultant picks the function that matches the transformation the business needs [^1].

The Salesforce documentation groups these functions by what they do. There are functions for working with text, functions for working with dates and times, functions for working with numbers, and functions that branch on conditions. Each function has a defined input and a defined output, and the mapping calls the function with the source value and uses the result as the target value [^1][^2].

The key idea is that a function transforms a value rather than copying it. A direct field copy moves a value unchanged. A function takes that same value, applies an operation, and produces a different value. That difference is the whole point of the manipulation engine, and it is what lets a single mapping turn inconsistent source data into consistent target data [^1].

### String functions combine and reshape text

String functions combine and reshape text. They concatenate fields, extract substrings, change case, and trim whitespace, and they are the tools you reach for when the target needs a text value that the source does not provide directly [^1][^2].

The most common string operation is concatenation, joining two or more fields into one. A source system sends a first name and a last name as separate fields, and the target needs a single full name. A string concatenation function joins the two fields into one value, and the target receives the full name it expects [^1][^2].

The exam tests this directly. A mapping must combine a first name and last name into a single full name field. Use a string function to concatenate the two fields, and the target receives the full name it expects. Copying the first name only loses the last name, storing both fields separately does not combine them, and a date function is irrelevant to names [^1][^2].

String functions do more than concatenate. They can extract a portion of a value, such as pulling the area code from a phone number. They can change case, normalizing `new york` to `New York`. They can trim whitespace, removing the stray spaces that source systems often leave behind. Each of these is a string function, and each produces a text value the target expects [^1][^2].

### Date functions convert and standardize time values

Date functions convert and standardize time values. They change a date from one format to another, extract a component such as the year or month, and compute the difference between two dates. They are the tools you reach for when the source sends a date in a format the target does not accept [^1][^2].

The conversion case is the one the exam tests most often. A source system sends a date in one format, and the target requires another. A date function converts the format to what the target expects, and the target receives a date it can use [^1][^2].

The exam tests this directly. A source sends a date in one format and the target requires another. Use a date function to convert the format, and the target receives a date it can use. Passing the date through unchanged keeps the wrong format, rejecting the record throws away data, and storing the raw string defers the problem [^1][^2].

Date functions also extract components. A mapping can pull the year from a date to feed a fiscal-year field, or the month to feed a reporting period. They can compute the difference between two dates, such as the number of days between an order date and a ship date. Every one of these is a date function, and every one produces a value the target expects [^1][^2].

### Number functions compute and round values

Number functions compute and round values. They add, subtract, multiply, and divide, they round to a specified number of decimal places, and they return absolute values. They are the tools you reach for when the target needs a computed numeric value [^1][^2].

A common case is a total. A source sends a unit price and a quantity, and the target needs the line total. A number function multiplies the two values, and the target receives the computed total. Another case is rounding. A source sends a price with many decimal places, and the target needs two. A number function rounds the value, and the target receives a clean price [^1][^2].

Number functions are where accuracy and standardization meet. A computed total is accurate only if the function is correct, and a rounded price is standardized only if the rounding rule is consistent. The consultant defines both, and the mapping produces numeric values the business can trust [^1][^2].

Accuracy is the reason the manipulation engine exists. A mapping that copies values unchanged is accurate only when the source is already correct, and source data is rarely correct. It arrives with the wrong case, the wrong format, the wrong units, and the wrong defaults. Functions and formulas are the tools that correct those problems, and a mapping that uses them produces data the business can trust. The exam frames accuracy as the outcome of using the right function in the right place, and the consultant who can name the function for the problem is the consultant who produces accurate data. A full name that is concatenated, a date that is converted, a total that is computed, and a status that is chosen by a condition are all accurate because a function or formula made them so [^1][^2].

### Conditional logic in a formula branches on a condition

Conditional logic in a formula branches on a condition. A formula can return one value when a condition is true and another when it is false, and it is the tool you reach for when a field must behave differently depending on the data [^1][^2].

The exam tests this directly. A field must show one value when a condition is true and another when it is false. The mapping should use conditional logic in a formula. String and date functions do not branch, and a direct field copy ignores the condition entirely [^1][^2].

Picture a field that must show a customer's status. If the customer's account balance is above a threshold, the field shows `Active`. Otherwise, it shows `Past Due`. A formula branches on the balance, returns the right status for each record, and the target receives a value that reflects the condition [^1][^2].

The value of conditional logic is that it keeps the Data Mapper count down. Without it, you would need one Data Mapper for records that meet the condition and another for records that do not. With it, a single formula branches on the data and produces the right result for every shape [^1][^2].

### Formulas combine functions into a single expression

Formulas combine functions into a single expression. A formula can call multiple functions, reference multiple source fields, and apply conditional logic, all in one definition. It is the way to build a complex transformation that no single function can express [^1][^3].

The Salesforce documentation walks through a Data Mapper example that uses a formula, and the pattern is instructive. The formula takes source values, applies functions to them, and produces an output value that the mapping writes to the target. The formula is defined once, and it runs for every record the Data Mapper processes [^3].

A formula is the right tool when the transformation has multiple steps. A field might need a substring extracted, then converted to a number, then rounded, then compared to a threshold. Each step is a function, and the formula chains them into one expression. The result is a single computed value that no single function could produce [^1][^3].

### A worked example: building a standardized customer record

Put the pieces together with a concrete scenario. A client has a feed of customer records, and the target needs a full name, a standard date, a computed total, and a status that depends on a condition. The source provides a first name, a last name, a date in an inconsistent format, a unit price, a quantity, and an account balance [^1][^2].

The consultant builds the mapping field by field. The full name field uses a string function to concatenate the first and last names. The date field uses a date function to convert the incoming format to the target format. The total field uses a number function to multiply the unit price by the quantity. The status field uses conditional logic in a formula to return `Active` or `Past Due` based on the balance [^1][^2].

Every field is computed, not copied, and every field produces a value the target expects. The result is a standardized customer record built from inconsistent source data, and the mapping did all of the work [^1][^2].

Try it yourself. In a sandbox, build a Data Mapper that reads a source with a first name, last name, a nonstandard date, a unit price, a quantity, and a balance. Concatenate the names, convert the date, multiply the price by the quantity, and add a conditional formula for the status. Run it against a sample payload and confirm every computed field is correct.

## Config Walkthrough

The functions and formulas flow maps onto four concrete steps.

1. In the Data Mapper builder, identify which source fields need transformation and which function matches each transformation. Use a string function for text, a date function for time values, and a number function for computed values [^1][^2].

2. For a field that must branch on a condition, define a formula with conditional logic that returns one value when the condition is true and another when it is false [^1][^2].

3. For a transformation with multiple steps, chain the functions into a single formula so the mapping computes the value in one expression [^1][^3].

4. Map the function or formula output to the target field, then test the Data Mapper from the Preview tab with a real payload and confirm every computed field received the expected value [^1].

Activate the version only after the preview confirms the functions and formulas produce accurate, standardized output.

## Exam Traps

Three traps dominate this requirement, and each is a specific, avoidable mistake.

**Reaching for the wrong function type.** A date function does not concatenate names, and a string function does not convert a date. Match the function to the operation: string functions for text, date functions for time values, number functions for computed values [^1][^2].

**Copying a field when the value needs transformation.** A direct copy moves a value unchanged, so it cannot concatenate, convert, or compute. When the target needs a transformed value, apply the function or formula instead of copying [^1][^2].

**Forgetting that conditional logic belongs in a formula.** String and date functions do not branch, so a field that must show different values based on a condition needs conditional logic in a formula, not a function [^1][^2].

The exam tip that ties these together: name the operation first, then pick the tool. If the operation is combine, convert, compute, or branch, there is a function or formula for it, and the exam rewards the consultant who matches the two.
