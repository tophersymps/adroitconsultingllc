You need a location picker. The user has to click a spot on a map, not type one into a box. No standard element in the palette does that, and that is the moment someone says the magic words: call it, we will build a custom component. Sometimes that is exactly right. Sometimes it is a 400-hour detour past a perfectly good picklist that was already sitting on the shelf.

Requirement r-15a from the OmniScripts domain, worth 17% of the Salesforce OmniStudio Consultant exam, asks you to advise on leveraging Lightning Web Component embeds and custom and standard components within OmniScripts, including child OmniScripts for reuse and FlexCards to enhance the user experience and maintain corporate branding. The standard OmniScript elements cover most journeys, but some interactions need more. An LWC Embed brings a Lightning Web Component into an OmniScript Step, and it is the tool you reach for when the standard elements cannot express the interaction.

The exam wants you to know two things about custom components. First, when they are worth the cost. Standard components should be the default, and a custom LWC is warranted only when a standard element cannot do the job. Second, how to keep a custom component honest inside the journey. The LWC reads from and writes to the data JSON, so the data contract between the component and the JSON must be explicit, and the component must respect the OmniScript's data flow and branding.

## Deep Dive

### What an LWC Embed is

An LWC Embed brings a Lightning Web Component into an OmniScript Step. The Salesforce documentation on the Custom LWC element describes the mechanics: you add a custom Lightning web component to an OmniScript using the Custom LWC element, and you enter the name of the component in the Lightning Web Component Name field.[^1] The component renders inside the Step, receives data from the data JSON, and can write results back, so it participates in the journey like any other element.

Use an LWC Embed when the standard OmniScript elements cannot express the interaction. The classic examples are a custom picker, a map, or a specialized data view. A map picker that lets the user click a location on a map is not something a standard picklist or text input can provide. A custom data view that renders a complex relationship is not something a standard table can show. When the interaction is genuinely beyond the standard elements, the LWC Embed is the right tool.

The quiz tests this directly. An OmniScript needs a custom map picker that standard elements cannot provide. The appropriate approach is to add an LWC Embed that renders the custom map picker and writes the selection to the data JSON. A standard picklist cannot provide a map picker, and neither can a text Input for the location. A FlexCard is a display component, not an input. The LWC Embed is the answer because when a standard element cannot express the interaction, the LWC renders the custom component and writes the result to the data JSON.

### The LWC is a bridge, so define the contract

The LWC Embed is a bridge between the OmniScript and custom code, and a bridge needs an agreed contract. Define the data contract between the LWC and the data JSON explicitly: what the component reads, what it writes, and under what names. The Salesforce documentation on the Custom LWC element shows the mechanism: you pass a property into the custom component using a property name in HTML attribute format, and the component reads from and writes to the data JSON through that contract.[^1]

![The LWC Embed is a bridge: the OmniScript Step renders the custom LWC, which reads input from the data JSON and writes results back through an agreed contract that names the fields](</diagrams/day-29-r-15a-lwc-embeds-and-custom-standard-components-in-omnis/1-lwc-embed-bridge.png>)

A mismatch between the LWC's expected input and the data JSON shape is a common integration failure. The component reads from the data JSON, so if the shape does not match, it renders empty or breaks. The quiz tests this with an LWC Embed that writes its result to the data JSON under a name that does not match what the save logic expects. The result is that the value is stored but the save logic reads a different or empty value, so the data is lost or wrong. The save logic does not read the correct value automatically. The OmniScript does not fail to deploy; it deploys and then loses the data at runtime. The LWC is not ignored; it writes, but to the wrong key. The data JSON name is the contract, and the contract must be agreed and matched before building.

The way to prevent this is to agree on the contract before the component is built. Write down what the LWC reads, what it writes, and under what names, and confirm the downstream logic expects exactly those names. A mismatch found after the component is built is expensive to fix; a contract agreed up front is cheap.

A worked example makes the contract concrete. A journey needs a map picker so a field technician can select the service location. The LWC reads the account address from the data JSON under the name accountAddress, renders a map centered on it, and lets the technician click a point. When the technician clicks, the LWC writes the chosen latitude and longitude back to the data JSON under the names selectedLatitude and selectedLongitude. The save mapping expects exactly those two names, so the record is written with the correct coordinates. If the component team had instead written the result under lat and lng, the save mapping would read selectedLatitude and selectedLongitude, find them empty, and the record would lose the location. The contract, agreed before the component was built, is what keeps the two sides aligned.

### Standard components are the default

Standard components cover most needs, and they should be the default. Reach for an LWC only when a standard element cannot do the job, because custom components add build, test, and maintenance cost. Before commissioning an LWC, ask whether a standard picklist, table, or block already solves the interaction.

![Standard components are the default: if a standard element can express the interaction, use it; a custom LWC is warranted only when no standard element can do the job](</diagrams/day-29-r-15a-lwc-embeds-and-custom-standard-components-in-omnis/2-standard-vs-custom.png>)

The quiz tests this with a simple picklist. A consultant is deciding whether to build a custom LWC or use a standard element for a simple picklist. The better choice is to use the standard picklist, since it already solves the interaction with less cost. Building the custom LWC for more control adds cost without adding value, because the standard picklist already does the job. A FlexCard is a display component, not an input. A Formula computes a value, it does not capture a picklist choice. The standard picklist is the answer because standard components should be the default, and a custom LWC is warranted only when a standard element cannot do the job.

This is a cost discipline. Every custom component is code that has to be written, tested, and maintained, and it has to be kept in sync with the OmniScript's data flow. The standard elements are maintained by Salesforce and cover the common cases. Default to standard, and treat a custom LWC as an exception that has to earn its place.

### Custom components must respect the data flow

When you do use a custom component, it must respect the OmniScript's data flow. An LWC that writes to the data JSON must write under the names the downstream logic expects, and it must handle the empty and loading states. A component that assumes its data is always present breaks on branches that skip the source, exactly like a Formula that assumes a field is always present.

The empty and loading states matter because the data JSON is populated over the course of the journey. A component rendered early may see empty data before a fetch completes, and a component on a branch may see a field that another branch never populated. The component must render gracefully in those states, showing a loading indicator or an empty state instead of breaking. Test the component with empty and loading data, not just with the happy path.

### Branding lives in the component layer

Branding and user experience are maintained through the component layer. Standard OmniScript elements inherit the org's styling, so they look consistent by default. Custom LWCs should follow the same design tokens so the journey looks consistent with the rest of the product. A custom component that ignores the design system breaks the corporate look, and the user notices the mismatch even if they cannot name it.

The Salesforce documentation on embedding FlexCards in an OmniScript makes the branding point concrete: you can embed a FlexCard Lightning Web Component in an OmniScript using the Custom LWC element, and the FlexCard can receive data from the OmniScript and perform any action available in the FlexCard.[^2] FlexCards are a way to bring branded, reusable display into a journey. The principle applies to any custom component: style it with the org's design tokens, and keep it consistent with the rest of the product so the journey feels like part of the same system.

The branding check is simple to apply. When a custom component renders, ask whether a user who knows the product would recognize it as part of the same system. If the component uses the org's colors, spacing, and type, it does. If it introduces a different palette or layout, it breaks the corporate look, and the journey feels bolted on. Standard elements inherit the styling for free; a custom component has to opt in to the design tokens. That opt-in is part of the build, not an afterthought, and it is what keeps the journey consistent with the rest of the product.

### Performance matters with custom components

The last consideration is performance. An LWC that fetches its own data on top of the OmniScript's fetch adds round trips and can slow the journey. The OmniScript already has a data flow, and the component should ride on it. Prefer passing data through the data JSON and letting the component render it, and keep the component's own calls minimal.

This connects back to the fetch discipline from the data flow lesson. The OmniScript fetches once and stores the result in the data JSON. The LWC should read that stored data, not issue its own fetch for the same information. A component that fetches its own copy of data the journey already has is duplicating work, adding latency, and risking inconsistency. Pass data through the data JSON, and let the component render what it is given.

The performance rule is a judgment call the exam rewards. A component that renders a list of options the journey already fetched should read them from the data JSON. A component that genuinely needs data the journey does not have, such as a live map tile set, may make its own call, but that call should be scoped and minimal, not a duplicate of the journey's fetch. The consultant who keeps the component's own calls minimal and rides on the data JSON ships a faster journey, and that is the answer the exam is looking for.

## Config Walkthrough

Add a custom component in four steps.

1. In the OmniScript builder, add an LWC Embed element and select the Lightning Web Component to render. Define the data contract first: what the component reads from the data JSON and what it writes back, and under what names.
2. Confirm the LWC writes results back to the data JSON under the names the downstream logic expects, and test the component with empty and loading data so it renders gracefully before a fetch completes and on branches that skip the source.
3. Before building a custom component, confirm a standard element cannot do the job, to avoid unnecessary build and maintenance cost. Default to standard, and treat a custom LWC as an exception that earns its place.
4. Style the custom component with the org's design tokens so it matches the rest of the product and maintains corporate branding. Confirm the journey looks consistent with the rest of the system.

## Exam Traps

Three traps account for most misses on this objective.

First, using an LWC where a standard element would do. Custom components add build, test, and maintenance cost, so reach for one only when a standard element cannot express the interaction. Default to standard.

Second, mismatching the LWC's expected input to the data JSON shape. The component reads from the data JSON, so if the shape does not match, it renders empty or breaks. Agree on the contract before building, and confirm the names match what the downstream logic expects.

Third, letting the LWC fetch its own data on top of the OmniScript's fetch. This adds round trips and slows the journey. Pass data through the data JSON and keep the component's own calls minimal.
