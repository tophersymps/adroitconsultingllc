A FlexCard that shows one object is a display. A FlexCard that shows an object and everything that belongs to it, drawn from several places at once, is a decision-support tool. The requirement behind this lesson, guiding the design of FlexCards that display relevant information from multiple data sources using available elements, sits in the FlexCards domain that makes up 18 percent of the OmniStudio Consultant exam, and it is where a candidate graduates from placing fields to designing an information surface. A single source hands you one flat object. A multi-source card hands you a reason: the account at the top, its contacts in the middle, its opportunities by stage drawn as a chart, and an action menu at the bottom. None of that comes from one query, and none of it should be forced into one element type. This lesson covers how to decide what belongs on the card, how to assemble the payload that feeds it, and how to bind each element to the right part of that payload so the result is clear and logical rather than crowded.[^1]

## Deep Dive

### One card is not one query

The first thing to unlearn is the idea that a FlexCard has a single data source in the same way that a related list has a table. A card's data comes as one JSON payload that the card binds to, but that payload can be assembled from several sources. The most common way to assemble it is an Integration Procedure, which pulls data from multiple internal and external sources and returns them in one nested structure. The card then binds to that single response. So the card is not making three independent calls to three objects; it is binding to one payload that an Integration Procedure assembled for it.[^2]

That distinction matters for the exam because it reframes the design task. The question is not "which query should this card run." The question is "what should the card ultimately show, and how do I get all of that into one payload." The card's job is to render a coherent view. The Integration Procedure's job is to make that view possible by merging the account, its contacts, and its aggregated opportunity data into one nested JSON the card can bind to without re-shaping anything client-side.

Why does this arrangement win over the alternatives? Because it keeps the data shape explicit and the binding simple. When an Integration Procedure merges everything up front, the card binds to a payload that already looks like what the layout needs. If instead the card tried to fetch each data shape with independent extracts, the developer would have to stitch them together, reconcile the shapes, and deal with nested collections that no single flat extract produces cleanly. The integration layer exists exactly to absorb that complexity. The consultant's job is to know when to use it.

### Decide what belongs on the card before touching an element

Before adding a single element, define the card's information hierarchy. The guiding principle is that a card reads top to bottom in a logical order: identity first, then key facts, then supporting detail, then actions. Identity is who or what this card is about, usually the record name and the one or two fields that identify it. Key facts are the values the user needs immediately, the reason they opened the card. Supporting detail is the deeper material behind those facts, often a collection or an aggregate. And actions are what the user can do about any of it.

This order is not a stylistic preference. It is how a reader makes sense of a screen. A card that leads with a chart before the user knows what the record is forces them to hunt for context, to work backward from the data to the subject. A card that leads with identity gives the reader an anchor immediately, then builds meaning on top of it. When the exam asks you to choose the correct layout, the identity-to-actions order is the pattern you are expected to name. Lead with what the card is about, then let the facts and detail build on that foundation, and let actions come last because actions act on the content that precedes them.

### Match the element to the data

The available elements are the building blocks of the card: text for a single value, inputs and menus for capturing or selecting discrete values, data tables for collections of records, charts for aggregates, images, and more. The design principle is one element per logical piece of information. A data table shows a collection. A chart shows an aggregate. An input or menu captures or selects a value. Do not overload a single element with data that belongs in another.

This matching of element type to data type is where clarity comes from, and it is a distinct concept from having correct data. You can feed a card perfect data and still obscure it by choosing the wrong element. Cramming a collection into a single text field flattens N records into a string nobody can read. Binding a chart to raw rows instead of an aggregated series produces a broken or meaningless visual. Routing discrete options through a text field instead of a menu forces the user to type instead of choose. Each element has a job, and the job is defined by the shape of the data, not by convenience.

![Each FlexCard element matches a data shape: a text element holds a single scalar value, a data table holds a collection of records, a chart holds an aggregate or series, and a menu or input holds discrete options the user selects.](</diagrams/day-13-r-7a-multi-source-flexcard-design-layering-data-and-ele/2-element-matching.png>)

So the rule for the exam is: match the element to the shape of the data. A small set of discrete values belongs in a menu or a set of chips. A tabular collection belongs in a data table. A trend or distribution belongs in a chart. This is the reasoning behind the question about which element shows a collection of related records: the collection is tabular, so the data table is the correct element, not a text field, not a single input, and not a menu.

### The source and the layout are designed together

The deepest insight of this requirement is that the data source and the element layout cannot be designed independently. They are two halves of one decision. If the card needs a chart of opportunities by stage, the Integration Procedure must return the aggregated series, not raw opportunity rows. If it needs a data table of contacts, the Integration Procedure must return the collection. Decide the layout first, then shape the source to feed it, so the card never has to reshape data client-side.

This is the trap the exam leans on hardest. A developer who decides the chart is needed, then feeds the chart whatever rows happen to be available, gets a broken visual because the chart element expects aggregated data. The fix is not to hack the card; it is to go back to the source and have the Integration Procedure do the aggregation. The card should bind to a payload that already matches the layout. Shape the source to the layout, not the other way around.[^3]

### Why the Integration Procedure is the natural assembler

For this requirement, the Integration Procedure is the natural tool because it exists to pull from multiple places and merge the results. It can reach into the account, pull its contacts, aggregate its opportunities, and return one nested JSON. That is exactly the shape a multi-source FlexCard needs. The card binds to that payload, and each element binds to the field within it that holds the right slice.

This keeps the card simple. The card is a renderer; it lays out elements and binds them to JSON paths. It does not run three queries and reconcile them. The complexity of assembling multiple sources lives in the Integration Procedure, where it belongs, and the card stays focused on presentation. That division of labor is the whole reason the multi-source FlexCard works. You design the layout to read logically, and you design the Integration Procedure to feed exactly that layout.

## Worked Example: the account command center

Walk through a real card to make the layering concrete. A service manager wants a single card showing an account: the account name, the account owner and industry up top, a table of its five most recent open cases in the middle, and a chart of open opportunities grouped by stage near the bottom. All of it should read in one glance, and it should not feel like three unrelated widgets bolted together.

Start with the hierarchy, before any element. Identity is the account name. Key facts are the owner and industry, the two fields that answer "what is this account and who owns it." Supporting detail is the case table, because a list of cases is a collection that adds depth. The chart of opportunities by stage is also supporting detail, an aggregate that summarizes the pipeline. Actions, such as a button to create a new case, come at the bottom. That is the order: name, owner and industry, cases, stage chart, action.

Now shape the source to feed that layout. This card needs three different data shapes in one payload. It needs scalar account fields, so the Integration Procedure pulls the account's owner and industry as flat values. It needs a collection, so it pulls the five recent open cases as an array. And it needs an aggregated series, so it groups the open opportunities by stage and returns the counts as chart-ready points. The Integration Procedure merges all three into one nested JSON. The card binds to that payload, and nothing is re-shaped in the card.

Then bind the elements. A text element shows the account name. A second text element, or a pair of them, shows owner and industry. A data table element binds to the cases array and defines its columns against the fields in each case. A chart element binds to the aggregated opportunity series. An action element creates the new case button. Each element binds to the part of the payload that matches its purpose, and the card reads top to bottom exactly as the hierarchy planned it.

![The account command center: one Integration Procedure merges the account's scalar fields, its recent open cases array, and its opportunities aggregated by stage into a single payload, and the card binds each element top to bottom without re-shaping anything client-side.](</diagrams/day-13-r-7a-multi-source-flexcard-design-layering-data-and-ele/3-command-center.png>)

Now apply the trap logic. If the developer instead binds the chart to the raw opportunities array, the chart breaks, because it expects aggregated points and receives unaggregated rows. If they try to show the cases in a text field, the collection flattens into an unreadable string. If they design one data table for everything, the account scalars, the scalar collection, and the aggregate all collide in one element that cannot represent all three shapes. Each of those failures is a different version of the same mistake: choosing an element that does not match the data, or shaping a source that does not match the layout.

## Configuration Walkthrough

Walk through building a multi-source FlexCard in the OmniStudio FlexCard editor, from content decisions to published card.

1. **Define the information hierarchy.** Write down what the card is about (identity), the immediate facts the user needs (key facts), the deeper material behind them (supporting detail), and what the user can do (actions). List the data each section needs before you choose a single element. This is the blueprint for everything after it.

2. **Design the Integration Procedure to assemble the payload.** In the Integration Procedure, pull each object or system the card needs: the account, its contacts, its opportunities, or any external source. Merge the results into one nested JSON, and shape it to match the planned layout. If the layout has a chart, aggregate the series here. If it has a data table, return the collection here. The payload should look like the layout before the card ever binds to it.[^2]

3. **Add the elements in the planned order.** Open the FlexCard editor and add the elements top to bottom as the hierarchy defined them. Bind each element to the corresponding field in the data JSON. Use a text element for each scalar value, a data table for a collection, a chart for an aggregate, and inputs or menus for discrete values that the user selects or enters. Bind elements to the payload fields, not to reconstructed client-side values.

4. **Review the card top to bottom.** Read the card as the intended user would, from the first element to the last, and confirm the flow is logical. Does the user know what the record is before they reach the detail? Do the actions sit after the content they act on? Where the order is unclear, adjust the source shape or the element order until the card reads cleanly. A card that requires the user to hunt for context has failed its design even when every value is correct.

## Exam Traps

- **Binding a chart to raw rows instead of an aggregated series.** A chart element expects aggregated data, so feeding it unaggregated rows produces a broken or meaningless visual. Aggregate in the Integration Procedure before the card binds. Do not expect the card to know how to roll up the rows itself.
- **Overloading one element with data that belongs in another.** Cramming a collection into a single text field, or putting mixed data types in one element, obscures the information. Each element should show one logical piece of information. Match the element to the shape of the data: collections go in data tables, aggregates in charts, discrete values in menus or inputs, single values in text.
- **Designing the layout without considering the source shape.** Deciding the layout, then expecting the source to conform or forcing the card to re-shape data client-side, produces cards that fight their data. The card should bind to a payload that already matches the layout. Shape the source to the layout first.

## Exam Tip

Decide the layout first, then shape the Integration Procedure to feed it. Write the information hierarchy before you add an element: identity, then key facts, then supporting detail, then actions. Give each element exactly one logical piece of information, and match the element to the data shape, a data table for a collection, a chart for an aggregate, a menu or input for a discrete value. Aggregate anything a chart needs in the Integration Procedure, never in the card. A multi-source card is coherent when its payload matches its layout and every element binds to the part of the payload that fits it.

## Try It

Open a sandbox with OmniStudio enabled and define the hierarchy for a contact card: the contact's name and account name as identity, phone and email as key facts, the account's recent opportunities as a data table, and a button to log a call as the action. Build an Integration Procedure that pulls the contact fields, pulls the account's recent opportunities as an array, and returns them as one nested JSON. In the FlexCard editor, add the elements in the planned order and bind each to the payload. Then make two deliberate breaks and watch them fail: bind the chart to the raw opportunity rows and confirm the visual comes apart, and force the opportunity list into a text field and confirm it becomes unreadable. Both failures teach the same lesson: the element must match the data, and the source must match the layout.
