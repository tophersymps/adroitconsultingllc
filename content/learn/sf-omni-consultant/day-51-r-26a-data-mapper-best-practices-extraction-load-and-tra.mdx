Best practices for Data Mappers are not a list of nice-to-haves. They are the difference between a mapper that works and one that is slow, brittle, and impossible to maintain. Requirement r-26a asks you to discuss those best practices, and the exam in the Data Mappers domain, worth 17%, rewards consultants who can name the right habit for the right operation. The organizing idea is simple: match the type to the operation, read and map only what you need, and reuse instead of duplicating. Those three habits cover most of what the exam asks.

## Deep Dive

### Best practices start with choosing the right type for the operation

Best practices for Data Mappers start with choosing the right type for the operation. Read with Extract or Turbo Extract, write with Load, and reshape with Transform [^1]. A consultant who matches the type to the operation avoids the performance and correctness problems that come from using the wrong tool.

The four Data Mapper types each have one job. An Extract reads data from Salesforce. A Turbo Extract reads data faster by using a different query path. A Load writes data into Salesforce, creating or updating records. A Transform reshapes data between two structures without touching the database [^1]. When you match the type to the operation, each mapper does exactly what it is built for.

The exam tests this directly. A consultant designing a Data Mapper that reads related records in one call should use a relationship query in an Extract. Reading each record separately adds reads, a Load writes, and mapping every field wastes resources [^1].

Why does the type matter so much? Because using the wrong type produces wrong behavior and poor performance. Reading with a Load writes instead of reads. Reshaping with an Extract queries the database when you only wanted to restructure data. The mismatch is the source of both correctness bugs and slow mappers.

### For extraction, read only what you need

For extraction, the best practice is to read only what you need. Filter in the query, select only the fields the mapping uses, and use relationship queries to read related data in one call [^1]. This keeps the read light and fast, and it is the foundation of Data Mapper performance.

Filtering in the query means the database returns only the records you actually need, not the whole object. Selecting only the fields the mapping uses means the response carries only the data that matters. A relationship query reads related data in one call, so you do not issue a separate query for each related record [^1].

The exam tests this directly. A consultant designing a Data Mapper that reads related records in one call should use a relationship query in an Extract. A relationship query reads related data in one call, reducing queries. Reading separately adds reads, a Load writes, and mapping every field wastes resources [^1].

The performance argument is straightforward. Every field you select and every record you return costs resources. An unfiltered read that returns a thousand records when you need ten is a thousand records of wasted work. A read that maps every field on the object carries data the mapping never uses. Reading only what you need is the cheapest possible read.

### For loads, be explicit about the write

For loads, the best practice is to be explicit about the write. Know whether the operation is insert, update, or upsert, resolve the target record reliably, and use a unique, populated external ID for upsert [^1]. A Load that is explicit about its write logic is correct and repeatable.

The write operation is a business decision, not a technical one. Whether a record is created, updated, or upserted depends on what the business needs the Load to do. The consultant decides insert, update, or upsert, resolves the target record, and uses a unique external ID for upsert [^1].

The exam tests this directly. A consultant building a Load and deciding between insert, update, and upsert should let the business need for the write guide the choice. The business need determines whether records are created, updated, or upserted. Field count, name, and output structure do not drive the write operation [^1].

The upsert key deserves care. The Load uses the key to decide whether it updates an existing record or inserts a new one. A unique, populated external ID makes the upsert reliable. A key that is not unique or not populated breaks the upsert logic, because the Load cannot tell records apart or has nothing to match on [^3].

### For transforms, keep the mapping lean and explicit

For transforms, the best practice is to keep the mapping lean and explicit. Map only the fields downstream consumers need, apply functions and formulas where data must be standardized, and state what happens to nulls and defaults [^1]. A lean, explicit transform is accurate and easy to maintain.

Mapping only the fields downstream consumers need keeps the output small and the transform readable. Applying functions and formulas where data must be standardized means the transform normalizes formats instead of passing them through raw. Stating what happens to nulls and defaults means the transform behaves predictably when a field is absent [^2].

The exam tests this directly. A consultant designing a Data Mapper that reads related records in one call should use a relationship query in an Extract, and a consultant building a Load should let the business need guide the write. For transforms, the same discipline applies: map only what you need, standardize the data, and state the null and default behavior [^1].

Why does a lean transform matter? Because every extra field in the output is a field a downstream consumer has to understand and a field that can drift out of sync. A transform that maps only what is needed is accurate because it carries no dead weight, and it is easy to maintain because a consultant can see exactly what it produces.

### Naming and documentation are best practices across all types

Naming and documentation are best practices across all types. A Data Mapper should have a descriptive name that states what it does, and its mapping should be understandable by a consultant who did not build it [^1]. Data Mappers are often maintained by a different team, and clear naming is the documentation many teams have.

A mapper named `AccountExtract` tells you nothing. A mapper named `AccountExtractByExternalIdForOmniScript` tells you what it reads, how it finds the record, and where it is used. The descriptive name is the first line of documentation, and it is the documentation that survives when the original builder moves on [^1].

The exam tests this directly. A consultant designing a Data Mapper that reads related records in one call should use a relationship query in an Extract, and a consultant building a Load should let the business need guide the write. Naming and documentation are the habits that make a mapper maintainable by a team that did not build it [^1].

### Best practices also cover reuse

Best practices also cover reuse. If the same read or transform is needed in multiple places, reuse the Data Mapper rather than duplicating it [^1]. Reuse reduces maintenance and keeps behavior consistent, and it is a sign of a well-designed integration.

The exam tests this directly. A Data Mapper used in multiple places in an integration should be reused as the single Data Mapper. Reusing a single Data Mapper keeps behavior consistent and reduces maintenance. Duplicating creates drift, renaming does not help, and converting to a Load changes the operation [^1].

Why does duplication hurt? Because the copies drift apart over time. A change to the mapping must be made in several places, and the copies slowly become inconsistent. One copy gets a fix, another does not, and the integration behaves differently depending on which copy runs. Reuse keeps the behavior consistent because there is only one mapper to change.

### A worked example: a customer profile read

Put the pieces together with a concrete scenario. A consultant builds an OmniScript that displays a customer profile. The profile needs the account, its contacts, and its open cases. The consultant applies the best practices to each part of the read.

The consultant starts by choosing the right type. The operation is a read, so the consultant uses an Extract, not a Load and not a Transform [^1]. The type matches the operation.

Next, the consultant reads only what is needed. The Extract filters in the query to return only the account the user selected, selects only the fields the profile displays, and uses a relationship query to read the contacts and open cases in one call instead of issuing a separate query for each [^1]. The read is light and fast.

The consultant names the mapper descriptively. It is called `CustomerProfileExtractByAccountId`, which states what it reads, how it finds the record, and what it returns. A consultant who did not build it can understand it from the name [^1].

Finally, the consultant checks for reuse. The same profile read is needed by a FlexCard on the account record page. Instead of building a second mapper, the consultant reuses the single Extract. The behavior stays consistent, and there is one mapper to maintain [^1].

The result is a read that is fast, correct, and maintainable. The type matches the operation, the read is lean, the name is descriptive, and the mapper is reused.

Try it yourself. In a sandbox, build an Extract that reads an account and its related records in one call, filter in the query, select only the fields you need, name it descriptively, and reuse it in a second component instead of duplicating it.

## Config Walkthrough

The best practices map onto four concrete steps.

1. Choose the Data Mapper type that matches the operation, and name it descriptively so its purpose is clear to any consultant. Read with Extract or Turbo Extract, write with Load, and reshape with Transform [^1].

2. For extraction, filter in the query, select only needed fields, and use relationship queries to read related data in one call. This keeps the read light and fast [^1].

3. For loads, be explicit about insert, update, or upsert, resolve the target record, and use a unique external ID for upsert. The business need drives the write operation [^1].

4. For transforms, map only needed fields, standardize data with functions and formulas, and state null and default behavior. Keep the mapping lean and explicit [^1].

Test each mapper with real data and confirm the read returns only what you need, the write does what the business needs, and the transform produces the expected output before you activate the version.

## Exam Traps

Three traps dominate this requirement, and each is a specific, avoidable mistake.

**Using a Data Mapper type that does not match the operation.** Reading with a Load or reshaping with an Extract produces wrong behavior and poor performance. Match the type to the operation: read with Extract, write with Load, reshape with Transform [^1].

**Reading or mapping more data than needed.** Extra fields and unfiltered reads waste resources and slow the mapper for no benefit. Filter in the query, select only needed fields, and use relationship queries [^1].

**Duplicating a Data Mapper instead of reusing it.** Duplicates drift apart and create inconsistent behavior; reuse keeps the integration consistent and easier to maintain. Reuse the single Data Mapper [^1].

The exam tip that ties these together: match the type to the operation, read and map only what you need, and reuse instead of duplicating. These three habits cover most Data Mapper best practices.
