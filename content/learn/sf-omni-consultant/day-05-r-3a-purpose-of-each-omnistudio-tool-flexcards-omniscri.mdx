The OmniStudio Consultant exam opens its Fundamentals domain with a requirement that sounds deceptively simple: explain the purpose of FlexCards, OmniScripts, Integration Procedures, and Data Mappers. Candidates read that and assume it is a vocabulary check, four definitions to memorize and move on. It is not. The exam does not ask you to recite what each tool is. It hands you a business need and asks which tool fits, and it does that across the whole exam, not just in this domain. Every scenario question, every architecture question, every "what would you use here" question reduces to the same judgment this requirement teaches. If you can name the four tools but cannot say which one a given need calls for, you will lose points in every domain. This lesson makes that mapping automatic.

The core idea is a decision rule, and it is worth stating up front because everything else in this lesson is a refinement of it. Match the tool to the nature of the need. Display is a FlexCard. Guided capture is an OmniScript. System orchestration is an Integration Procedure. Data transform is a Data Mapper. Hold those four pairings and the scenario questions resolve quickly, because nearly every item in this requirement reduces to which verb the use case uses.

## Deep Dive

### FlexCard: the display tool

A FlexCard is a reusable, data-driven UI component that renders a record or a set of records in a compact card. It is the tool you reach for when the need is to show information, not to guide a user through steps. Think of an account summary on a record page, a case status panel, an asset list, or a customer's recent activity. Each of those is a display need, and a FlexCard is the right shape for it.

The word "data-driven" matters. A FlexCard is not a static image or a hard-coded block of text. It is bound to a data source, typically the record the user is currently viewing, and it renders whatever that record contains. When the record changes, the card changes. When the user navigates to a different account, the same card shows that account's data. That is what makes it reusable: you build the card once, bind it to a record context, and it works for every record of that type.

A FlexCard is also compact by design. It is meant to summarize what is relevant in a small space, with the ability to expand. A card can have states, so it can show a loading state, an empty state, and a populated state. It can have drill-down flyouts, so a user can click into more detail without leaving the page. It can carry actions, so a user can act on the data directly from the card. But the primary job is display. The card shows the user what is going on, and it does that without forcing them through a journey.

The exam trap on FlexCards is the opposite of the trap on OmniScripts. Because a FlexCard can carry actions and drill-downs, candidates sometimes reach for it to drive a process. That is the wrong instinct. A FlexCard is for showing. When the need is to walk a user through a multi-step capture with validation and branching, a FlexCard is the wrong tool, because it has no concept of a guided step sequence. It displays a state; it does not shepherd a user from step one to step two to step three.

### OmniScript: the guided capture tool

An OmniScript is a guided, multi-step user journey that walks a user through a business process. It is the tool for a quote, an application, an onboarding flow, a repair journey, a claim, any process where a user moves through a sequence of steps and the order matters. Where a FlexCard shows a snapshot, an OmniScript conducts a transaction.

The defining features are validation and branching. An OmniScript is built from steps and elements. Each step collects input, and the OmniScript validates that input as the user moves, so a required field cannot be skipped and a malformed value is caught before it reaches the next step. Branching lets the journey adapt to what the user tells it. If a customer selects a business account, the OmniScript can branch to business-specific questions. If a customer selects a personal account, it takes a different path. The journey is not a fixed form. It is a decision tree that responds to the user's answers.

This is what separates an OmniScript from a FlexCard and from a plain form. A FlexCard has no steps. A plain form collects fields but does not guide. An OmniScript collects fields, validates them, branches on the answers, and carries the user through a complete process to a defined end, typically writing the result back to Salesforce or to an external system.

The exam trap on OmniScripts is overuse. Because the OmniScript is the most visible OmniStudio tool, candidates reach for it for everything, including simple display needs. That is the trap the requirement names explicitly. Using an OmniScript to display a simple record summary adds a full guided journey where a lightweight FlexCard would do, increasing maintenance for no benefit. The OmniScript is the right tool when the need is step-by-step data capture. When the need is just to show data, it is the wrong tool, and the exam rewards the candidate who resists the instinct to make everything a journey.

### Integration Procedure: the system orchestration tool

An Integration Procedure, often shortened to IP, is a server-side orchestration that calls external systems and other OmniStudio artifacts. It is the tool for a system-to-system call, such as fetching pricing from a billing system or submitting a record to an external service, and it runs without a user interface.

The phrase "server-side" is the key. An OmniScript lives in the browser and walks a user through steps. An Integration Procedure runs on the server and chains together actions without a user in front of it. It can call an external system over HTTP, it can invoke a Data Mapper to read from or write to Salesforce, it can call another Integration Procedure, and it can run business logic, all in a single orchestrated call. The browser does not have to make five round trips. It makes one call to the IP, and the IP does the rest.

This is the tool for anything that happens behind the scenes. Fetching a price, checking a credit bureau, submitting to a billing system, validating an address against an external service, all of these are Integration Procedure work. They are system-to-system calls, and they have no user interface because no user is completing them. The user may have triggered the process, but the IP runs the orchestration.

The exam trap on Integration Procedures is coupling. Candidates sometimes put a system-to-system call directly inside an OmniScript, wiring the HTTP call into the user journey. That couples the UI to the integration. The call becomes hard to reuse, because it is buried inside one journey, and hard to test, because you cannot exercise the integration without running the whole user flow. The correct pattern is to put the call in an Integration Procedure and have the OmniScript invoke it. The IP is reusable across journeys, and it is testable on its own. The requirement names this trap explicitly, so expect a question that offers a direct call inside an OmniScript as a wrong answer.

### Data Mapper: the data transform tool

A Data Mapper is a declarative tool for transforming data between shapes. It is the tool for a field-to-field or object-to-object data transform, such as mapping an OmniScript's fields into an external system's payload, or reading data out of Salesforce and reshaping it for a FlexCard.

The word "declarative" matters. A Data Mapper is configured, not coded. You define the source, you define the target, and you map the fields between them, and the platform executes the transform. You do not write a loop to copy each field. You declare that the source's account name maps to the target's customer name, and the Data Mapper handles the rest. That makes it fast to build and easy to change after release.

A Data Mapper does two broad jobs. It extracts data, reading it out of Salesforce and reshaping it into the shape a consumer needs. And it loads data, taking an incoming payload and writing it into Salesforce records. In OmniStudio terms these are often called the Extract and Load operations, and both are Data Mapper work. The common thread is transformation: data is moving from one shape to another, and the Data Mapper is the tool that reshapes it.

The exam trap on Data Mappers is scope. A Data Mapper transforms data. It does not display data, it does not guide a user, and it does not orchestrate a system call. When a question asks which tool displays a summary, the answer is not a Data Mapper. When a question asks which tool makes a system call, the answer is not a Data Mapper. The Data Mapper is the supporting actor that moves and reshapes data between the other tools, and the exam tests whether you know it is a transform tool, not a catch-all.

### The four tools compose

The most important idea in this requirement is that the four tools are not isolated. They compose into end-to-end flows, and a real process usually needs more than one. The requirement names the composition explicitly: a FlexCard can launch an OmniScript, an OmniScript can call an Integration Procedure, and an Integration Procedure can use a Data Mapper. The architect chooses the tool that matches each layer of the process rather than one tool for everything.

Work one representative flow end to end. A customer opens an account record and sees a FlexCard that summarizes the account and offers a "Start Application" action. The user clicks the action, and the FlexCard launches an OmniScript. The OmniScript walks the user through the application steps, collecting input and validating it. At the point of submission, the OmniScript invokes an Integration Procedure. The IP calls a Data Mapper to read the customer's existing records, calls an external system over HTTP to run a check, and calls another Data Mapper to write the result back to Salesforce. The IP returns a status to the OmniScript, which shows a completion step, and a FlexCard on that step confirms what was created.

Every layer of that flow uses a different tool, and each tool is the right one for its layer. The FlexCard displays. The OmniScript guides. The IP orchestrates. The Data Mappers transform. No single tool could do the whole job well, and the architect who tried to force one tool to do everything would build something fragile. The composition is why the tools overlap at the edges, and it is why the exam asks you to pick the primary fit for a stated need rather than the tool that touches the flow at all.

### The decision rule

All of this converges on the decision rule the requirement states. The choice is driven by the nature of the need. Display is a FlexCard. Guided capture is an OmniScript. System orchestration is an Integration Procedure. Data transform is a Data Mapper. And a real process usually needs more than one.

The way to apply the rule on the exam is to read the requirement and underline the verb. Is the need to show data? That is display, so the primary fit is a FlexCard. Is the need to walk a user through steps with validation and branching? That is guided capture, so the primary fit is an OmniScript. Is the need a system-to-system call with no user interface? That is orchestration, so the primary fit is an Integration Procedure. Is the need to reshape data between two shapes? That is transform, so the primary fit is a Data Mapper.

The verb is the signal. The exam phrases each scenario around a verb, and the verb points at one tool first. When a question says a client needs to display a compact account summary with no user input, the verb is display, and the answer is a FlexCard. When a question says a client needs a guided, multi-step onboarding flow with validation and branching, the verbs are guide and validate, and the answer is an OmniScript. When a question says a client needs to call an external billing system to fetch pricing with no user interface, the verb is call, and the answer is an Integration Procedure. The verb resolves the question.

### Worked example: a quote flow

Working one scenario end to end makes the decision rule concrete. A customer asks for a quote flow. A sales rep opens an account record and needs to see a summary of the account's current plan and usage. The rep then starts a quote, walks through selecting a new plan, and the system calls a billing system to price it. The quote is saved back to the account.

Read for the verbs and the tools fall out. The account summary on the record page is display, so that is a FlexCard. The quote journey, where the rep selects a plan and moves through steps, is guided capture, so that is an OmniScript. The pricing call to the billing system is a system-to-system call with no user interface, so that is an Integration Procedure. And the data that moves between the OmniScript's fields and the billing system's payload is a transform, so that is a Data Mapper.

Now compose them. The FlexCard on the account page shows the current plan and usage, and it carries a "Start Quote" action. The rep clicks it, and the FlexCard launches the OmniScript. The OmniScript walks the rep through the quote steps, collecting the new plan and validating the selection. On submission, the OmniScript invokes the Integration Procedure. The IP calls a Data Mapper to reshape the quote fields into the billing system's payload, makes the HTTP call to fetch the price, and calls a Data Mapper to write the quote back to the account. The IP returns the price to the OmniScript, which shows the result, and a FlexCard on the completion step confirms the quote.

Every tool is the right one for its layer, and no single tool could carry the whole flow. That is the composition the requirement teaches, and it is the pattern behind most real OmniStudio solutions.

## Configuration Walkthrough

The curriculum gives a four-step walkthrough that maps each tool to a concrete build. Work through it in order.

1. To display an account summary on a record page, create a FlexCard, bind it to the record, and add the fields you want to show. In the FlexCard designer, choose the object, bind the card to the record context, and drag the fields onto the card layout. The card renders those fields for whatever record the user is viewing.
2. To capture a multi-step application, create an OmniScript, add steps and elements, and configure validation and branching between them. In the OmniScript designer, add a step, add the input elements to it, set the required and validation rules, and add a second step with a branch that routes based on an earlier answer.
3. To call an external pricing system, create an Integration Procedure, add the HTTP call, and map the request and response. In the Integration Procedure designer, add an HTTP Action, configure the endpoint and method, and use Data Mappers to shape the request payload and parse the response.
4. To transform an OmniScript's output into an external system's payload, create a Data Mapper and map the source fields to the target fields. In the Data Mapper designer, set the source and target, and drag each source field to its target field so the transform is declared rather than coded.

## Exam Traps

- **Using an OmniScript to display a simple record summary.** A record summary is a display need, and a FlexCard is the lightweight tool for it. Wrapping it in an OmniScript adds a full guided journey where none is needed, increasing maintenance for no benefit. When the need is to show data, reach for the FlexCard, not the journey.
- **Using a FlexCard to drive a multi-step data-capture process.** A FlexCard displays a state; it has no concept of a guided step sequence. Forcing a multi-step capture into a FlexCard loses the step-by-step validation and branching that an OmniScript provides. When the need is guided capture, the OmniScript is the tool.
- **Putting a system-to-system call directly in an OmniScript.** Wiring an HTTP call into a user journey couples the UI to the integration, making the call hard to reuse and hard to test. The correct pattern is to put the call in an Integration Procedure and have the OmniScript invoke it, so the integration is reusable and testable on its own.

## Exam Tip

Match the tool to the nature of the need. Display is a FlexCard. Guided capture is an OmniScript. System orchestration is an Integration Procedure. Data transform is a Data Mapper. Read the scenario, underline the verb, and let the verb point at the tool. A real process usually needs more than one, so expect the correct answer to name the primary fit for the stated need, not the tool that merely touches the flow.

## Try It

Open a sandbox with OmniStudio enabled and build the quote flow from the worked example. Create a FlexCard on the Account record page that shows the account name, plan, and usage, and add a "Start Quote" action. Create an OmniScript with two steps: step one collects the plan selection, and step two confirms the quote. Create an Integration Procedure with an HTTP Action that returns a mock price, and a Data Mapper that reshapes the OmniScript's fields into the payload the HTTP call expects. Wire the OmniScript to invoke the Integration Procedure on submission, and the FlexCard to launch the OmniScript. Run the flow end to end and confirm each layer uses the right tool: the FlexCard displays, the OmniScript guides, the IP orchestrates, and the Data Mapper transforms. That exercise demonstrates the composition this requirement teaches.
