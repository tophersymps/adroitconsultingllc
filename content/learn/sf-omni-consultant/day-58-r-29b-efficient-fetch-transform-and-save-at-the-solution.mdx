A fast fetch followed by a slow transform is still a slow solution. A clean transform followed by a fragile save is still a fragile one. You can polish each stage until it shines and still ship a journey that wastes the user's time, because efficiency was never a property of any single step. It is a property of the whole pattern.

That is the idea this lesson is built on. Requirement r-29b, part of the Best Fit Solutions domain worth 15% of the Salesforce OmniStudio Consultant exam, asks you to provide guidance on the appropriate Data Mappers and Integration Procedures to use within an OmniScript to efficiently fetch, transform, and save data to meet specific business outcomes. The exam wants you to design the three stages together, so the data flows from source to destination with the least work and the fewest failure points.

## Deep Dive

### The fetch, transform, and save pattern is the spine of every OmniScript

The fetch, transform, and save pattern is the spine of every OmniScript, and efficiency is a property of the whole pattern, not of any single step. A fast fetch followed by a slow transform or a fragile save is still a slow, fragile solution. The architect should design the three stages together so the data flows from source to destination with the least work and the fewest failure points.

This is the same pipeline view that runs through the whole OmniStudio curriculum. Every OmniScript, no matter how complex, moves data through the same three stages. Fetch brings data in. Transform reshapes it. Save writes it out. The exam rewards the architect who designs that flow as a single pattern, where each stage reads from and writes to the data JSON, and the shape of the JSON is the contract that holds the stages together.

### Efficient fetch means asking for the minimum

Efficient fetch means asking for the minimum. The architect should identify the exact records and fields the business outcome needs, filter on indexed fields, and bound the result set. Fetching more than the outcome needs wastes bandwidth, memory, and query budget, and it makes every downstream stage slower. The fetch should be designed against the outcome, not against what is convenient to query.

The quiz tests this directly. One question describes an architect tracing a data element through an OmniScript and finding it is fetched but never displayed or saved, and asks what should be done. The answer is to remove it from the fetch to reduce waste. Keeping it in the fetch in case it is needed later is speculative and inefficient. Moving it to a separate Integration Procedure adds a round trip for unused data. Storing it in a custom setting is wrong, because a custom setting is for configuration, not for unused fetched data. A data element that is fetched but never used is waste, and removing it from the fetch reduces bandwidth, memory, and query budget.

Salesforce's Data Mapper best practices reinforce the same discipline. Create targeted Data Mappers that only extract or load the data needed for one operation, and ensure that all filtering and sorting happens on indexed fields, because the Id and Name fields are always indexed.[^1] A fetch that returns a wide result set because it is convenient forces the OmniScript to carry data it never uses, and the extra load slows every downstream stage and risks query limits.

A concrete example makes the waste visible. A quote journey fetches the full account object, all its contacts, and its entire order history, because the developer found it convenient to pull everything at once. The journey displays the account name, the primary contact, and the last order date. Everything else sits in the JSON, consuming memory and bandwidth, and every downstream stage has to carry it. The efficiency audit catches this: trace each fetched element to where it is displayed or saved, and the unused fields stand out immediately. Cut them, and the fetch, the transform, and the save all get lighter.

### Efficient transform means doing the work in the right place

Efficient transform means doing the work in the right place. Light field mapping and formatting belong in the Data Raptor or the OmniScript's JSON, where they are cheap and visible. Complex aggregation, cross-system logic, and transformations that must be consistent across consumers belong in an Integration Procedure, written once and reused.

The architect should keep transformation logic out of the browser when it is heavy, and out of duplicated scripts when it is shared. The quiz tests this directly. One question describes a complex transformation that must produce identical results for three OmniScripts, and asks where it should live. The answer is in a single shared Integration Procedure. Duplicating it inside each OmniScript risks drift. Putting it in the browser's JavaScript for each script has the same drift problem. A custom label that stores the output is wrong, because a custom label stores text, not a transformation result. A single shared Integration Procedure guarantees identical results and is written and tested once.

The drift is the real cost. Three OmniScripts each compute a customer's eligibility with their own copy of the rules. Someone tightens the eligibility criteria in one script and misses the other two. Now the same customer is eligible in one journey and not in another, and the inconsistency is invisible until a user hits it. A single shared Integration Procedure holds the rules in one place, so the change is made once and every consumer gets the same result. That is why shared transformation belongs in a shared IP, not in three copies.

### Efficient save means writing once, correctly, and transactionally

Efficient save means writing once, correctly, and transactionally. The architect should confirm the target object, the fields, the sharing model, and the error handling before the write. A save that can partially fail must be orchestrated so the data stays consistent. The save should also avoid redundant writes: if the data did not change, it should not be written again, and the architect should design the save to touch only the records and fields that actually changed.

The quiz tests this directly. One question describes a save operation that writes a record even when none of its fields changed, and asks for the best improvement. The answer is to design the save to write only the records and fields that changed. Writing the record anyway to keep it simple is the inefficiency being fixed. Adding more fields to the save makes the problem worse. Moving the save to a FlexCard does not work, because a FlexCard is a display component and does not perform saves. Writing only what changed avoids redundant writes, which waste time and trigger unnecessary triggers and workflows.

The redundant write has a hidden cost beyond the wasted time. Every write can fire triggers, workflows, and validation rules, and each of those does its own work. A save that writes a record whose fields did not change still triggers all of that, for no benefit. Design the save to compare the incoming values against the stored record and write only what actually changed. The journey does less work, the triggers fire only when they should, and the data stays consistent. That is the efficient save, and it is the answer the exam rewards.

### The solution-level view connects the stages to the business outcome

The solution-level view connects the stages to the business outcome. The architect should trace each data element from its source, through the transform, to its destination, and confirm that every element is needed and every step adds value. A data element that is fetched but never used, or transformed but never saved, is waste.

This trace is the efficiency audit that catches over-fetching and over-engineering before they ship. It is the cheapest optimization you will ever run, because it costs nothing but attention and it removes work at the source. Trace every data element from source to destination and cut anything that is fetched but never used. The exam rewards the architect who runs this audit, because it is the difference between a solution that does the work and a solution that does the work plus a lot of waste.

### Failure handling is part of efficiency

Failure handling is part of efficiency. A fetch that can fail, a transform that can error, or a save that can be rejected should have a defined response: a retry, a fallback, or a clear message to the user. The architect should design the pattern so a failure in one stage does not cascade into a corrupt or incomplete result, and so the user is told what happened and what to do next.

A data flow that cannot fail is a fiction. The fetch can fail when an external service is down. The transform can produce unexpected output when a field is empty. The save can reject a record when a validation fails. The design question is not whether these happen, but what the journey does when they do. The honest design surfaces the failure, tells the user what happened, and gives them a path forward, instead of failing silently and leaving the user staring at a blank field.

A concrete example makes the failure handling real. A fetch calls an external credit bureau, and the bureau is down. The journey has two options. It can fail silently, leave the credit fields blank, and let the user continue as if nothing happened, which produces a record that looks complete but is missing real data. Or it can read the returned status, tell the user the credit check is unavailable, and offer a retry or a path forward. The second option is the efficient one, because it does not let a failure in one stage cascade into a corrupt result. The user knows what happened and what to do next, and the data stays honest.

## Config Walkthrough

Apply the solution-level efficiency in four steps.

1. Design the three stages together. For each data element, trace it from source through transform to destination, and confirm every element is needed and every step adds value. This is the efficiency audit, and it is where waste is cheapest to cut.
2. Fetch the minimum. Identify the exact records and fields the outcome needs, filter on indexed fields, and bound the result set. Remove any element that is fetched but never used.
3. Place the transform where it is cheapest. Keep light mapping in the Data Raptor or the JSON, and put complex or shared logic in a single reusable Integration Procedure. Do not duplicate the same transform across scripts.
4. Design the save for correctness and minimal writes. Confirm the object, fields, and sharing model, orchestrate multi-record saves, and write only what changed. A save that touches only the records and fields that changed avoids redundant writes and the triggers they fire.

## Exam Traps

Three traps dominate this objective.

First, fetching a wide result set because it is convenient. The OmniScript carries data it never uses, and the extra load slows every downstream stage and risks query limits. Fetch the minimum that satisfies the outcome, and remove anything fetched but never used.

Second, putting heavy transformation in the browser or duplicating it across scripts. The browser is the wrong place for heavy logic, and duplicated copies drift apart. Put complex or shared transformation in a single reusable Integration Procedure.

Third, writing records that did not change. Redundant writes waste time and trigger unnecessary triggers and workflows, and a save that can partially fail leaves the data inconsistent. Design the save to write only the records and fields that changed, and orchestrate multi-record saves so a partial write does not corrupt the data.
