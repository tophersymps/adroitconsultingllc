You can recite every best practice from the last lesson in your sleep. Then the exam hands you a scenario, and suddenly the rules feel like they belong to someone else's problem. That gap, between knowing a practice and applying it, is exactly what this lesson closes.

Requirement r-11b from the FlexCards domain, worth 18% of the Salesforce OmniStudio Consultant exam, asks you to discuss best practices for FlexCards, and the exam tests that discussion through scenarios. It does not ask you to define a best practice. It describes a situation and asks you to apply the practices to it. This lesson walks five scenarios end to end, and in each one the method is the same: identify the user and their workflow, choose the data source, design the layout, add the actions, and place the card. Every decision follows from the one before.

The method is the point. Walk a scenario in order and the right choices tend to reveal themselves, because each decision constrains the next. Name the user and the workflow, and the data source follows from the data complexity and performance need. The data source and the layout follow from the workflow, and the placement follows from where the user actually works. Skip a step and the later decisions have no foundation, which is exactly how a card ends up well built and useless.

## Deep Dive

### The method: walk the scenario in order

Applying best practices means walking a real scenario end to end. The order is fixed: identify the user and their workflow, choose the data source, design the layout, add the actions, and place the card. Each decision follows from the one before, and the exam rewards the consultant who can state that order and justify each step.

Start with the user and the workflow. Who is the user, what are they trying to do, and at what moment does the card's information become necessary? This is the foundation. A card for a service agent resolving cases is a different card than one for a manager reviewing the queue, even if both show case data. The user and the workflow determine what data matters, what actions make sense, and where the card belongs.

Then choose the data source. The source follows from the data complexity and the performance requirement of the scenario. A small set of fields for one record needs a light source. Data merged from several systems needs an Integration Procedure. The source is not chosen in a vacuum. It is chosen to serve the workflow you just named.

Then design the layout and add the actions. The layout leads with the decision data and groups related information, and the actions keep the user in context. Then place the card where the user works and test it with real data in that placement. The placement is the last decision, and it is the one that determines whether the card is ever seen.

### Record-centric scenario: the card on the record page

In a record-centric scenario, the user works on a single record, and the card lives on the record page. The card shows a small set of fields for that record and offers actions that keep the user in context.

Consider a service agent who needs to see the key facts about a case and take a quick action without leaving the case. The user is the agent, the workflow is resolving the case, and the moment the card's information is needed is when the agent opens the case. The data source is a Turbo Extract, because the card shows a small set of fields for a single record, and a Turbo Extract is fast and returns a flat result set. The layout leads with the decision data, the priority, the age, and the customer, and groups the rest. The actions keep the user in context, such as launching an OmniScript to update the case without leaving the page.

The quiz tests this scenario directly. It describes a record-centric card on a record page that shows a small set of fields and offers in-context actions, and asks which data source is most appropriate. The answer is a DataRaptor Turbo Extract, because a record-centric card on a record page with a small set of fields is best served by a Turbo Extract, which is fast and returns a flat result set. An Integration Procedure is heavier than needed, static JSON cannot pull live record data, and a child FlexCard is a composition choice, not a data source.

The placement is the record page, because that is where the agent works on the record. The record page provides the record anchor the card needs, and the card's data source uses that anchor to pull the record's data. Everything about the card, the source, the layout, the actions, and the placement, follows from the single fact that the user works on one record at a time.

### Multi-source scenario: the card that merges data

In a multi-source scenario, the card must show data that comes from more than one place, and it uses an Integration Procedure to merge it. The card groups the results into clear sections and uses a data table and a chart for the list and trend data.

Consider a manager who needs a single view of an account that combines Salesforce data with external data, such as the account's open cases from Salesforce and a credit score from an external service. The user is the manager, the workflow is assessing the account, and the moment the card's information is needed is when the manager opens the account. The data source is an Integration Procedure, because the card must merge data from several sources, and an Integration Procedure executes multiple actions in a single server call, which is exactly what merging data from Salesforce and an external service requires.[^1]

The layout groups the results into clear sections, one for the Salesforce data and one for the external data, and uses a data table for the list of cases and a chart for the trend. The actions let the manager act on the view, such as drilling into a case. The placement is wherever the manager works, which for a cross-record view is likely a tab or dashboard, because the manager is not anchored to a single record.

The lesson is that the data source drives the design. Because the card merges multiple sources, it needs an Integration Procedure, and because it has list and trend data, it uses a data table and a chart. The scenario determines the source, and the source determines the layout.

### Role-based scenario: the card that tailors sections

In a role-based scenario, the card shows different sections to different roles, and it uses conditional rendering to do it. The data source returns all the fields the conditions reference, so no section is hidden for the wrong reason.

Consider a card that shows an account to both a sales rep and a manager. The rep needs the opportunity pipeline and the next steps. The manager needs the revenue summary and the risk indicators. The card uses conditional rendering to show the rep sections to the rep and the manager sections to the manager. The data source returns all the fields the conditions reference, because a condition on a field the data source does not return evaluates to false, and the section is permanently hidden.

The quiz tests this failure directly. It describes a role-based scenario where an architect uses conditional rendering to show different sections by role, but one section never appears, and asks what the most likely cause is. The answer is that the data source does not return the field the condition references. A condition on a field the data source does not return evaluates to false, so the section is permanently hidden. The theme, the element count, and the placement do not cause a hidden section when the referenced field is missing.

The lesson is that conditional rendering and the data source are coupled. Every condition references a field, and that field has to be in the data source for the condition to work. When you design a role-based card, you list every condition, collect every field those conditions reference, and make sure the data source returns all of them. A missing field is the classic silent failure, because the card renders fine in the editor with test data and only the missing section reveals the gap.

### Interactive scenario: the card that adapts as the user works

In an interactive scenario, the card tracks the user's interaction and adapts. It uses state variables to track the interaction, updates them from actions, and reads them in conditional rules so the card changes as the user works.

Consider a card that lets a user filter a list by category. The user selects a category, and the card shows only the records in that category. The card uses a state variable to remember the selected category, an action updates the state variable when the user selects a category, and a conditional rule reads the state variable to show the matching records. The card adapts as the user works, because the state variable is the single source of truth for the interaction.

The lesson is that state variables make the card dynamic, but they have to be managed deliberately. The state has to be initialized before it is read, the actions have to update it consistently, and the conditions have to read it correctly. Salesforce's guidance is to use FlexCard states when several elements have similar conditions or are laid out differently based on a condition, because states load the card faster and format elements correctly.[^2] The practice is to keep the state few and well-defined, and to prefer states over a tangle of individual conditions.

### Console scenario: the card that follows the selected record

In a console scenario, the agent works entirely in the console, and the card is placed in the console so it follows the selected record and supports the agent's workflow without forcing navigation. The placement is chosen because it matches how the user actually works.

Consider a service agent who works through a queue of cases in the console. The agent selects a case, and the card shows the case's key facts and offers actions, all without the agent leaving the console. The card is placed in a console view, because that is where the agent works, and the console view can follow the selected record.

The quiz tests this placement directly. It describes a console scenario where an agent works entirely in the console and needs a card that follows the selected record, and asks what the most appropriate placement is. The answer is a console view. A console view embeds the card in the console where the agent works and can follow the selected record, matching the workflow. A tab and a utility bar are not tied to the console's record context, and a record page component is outside the console.

The lesson is that placement is the last decision and the one that determines whether the card is used. A card that is well designed but placed where the user does not work does not enable anyone. The console scenario is the clearest example, because the agent never leaves the console, so a card anywhere else is effectively invisible. The placement matches how the user actually works, which is the whole point of the placement decision.

## Config Walkthrough

Apply the method to any scenario with these four steps.

1. For each scenario, start by naming the user, their workflow, and the moment the card's information is needed. Write down who the user is, what they are trying to do, and when the card becomes relevant. This is the foundation every later decision builds on.

2. Choose the data source that matches the data complexity and performance requirement of the scenario. For a small set of fields on one record, use a Turbo Extract. For more logic, use a standard Extract. For data merged from several sources or external data, use an Integration Procedure. Confirm the source returns every field the card displays and every field the conditions reference.

3. Design the layout to lead with the decision data and group related information, adding actions that keep the user in context. Put the decision data at the top, group related fields in blocks, and add actions that let the user act without leaving the context. For a role-based card, list every condition and confirm the data source returns every referenced field.

4. Place the card where the user works and test it with real data in that placement. Put the card on the record page, in the console, or on a tab or dashboard to match the workflow, and test it with representative data in that placement before release.

## Exam Traps

Three traps account for most misses on this objective.

First, applying a generic template to every scenario. Each scenario has different data, role, and placement needs, and a one-size-fits-all card fails them all. The exam will describe a scenario and expect you to apply the practices to that specific scenario, not to a generic card. Walk the scenario in order and let each decision follow from the one before.

Second, choosing the data source before understanding the scenario. The source must follow from the data complexity and performance need, not the other way around. The exam will describe a record-centric card and expect a Turbo Extract, and a multi-source card and expect an Integration Procedure. Understand the scenario first, then name the source.

Third, skipping the placement decision. A card that is well designed but placed where the user does not work does not enable anyone. The exam will describe a console scenario and expect a console view, because that is where the agent works. The placement is the last decision, and it is the one that determines whether the card is ever seen.
