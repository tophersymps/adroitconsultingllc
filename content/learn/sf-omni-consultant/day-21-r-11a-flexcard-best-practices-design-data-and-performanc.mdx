Here is a scene you have probably lived. The card looks perfect in the editor. Fields line up, the theme is right, the preview renders clean. You publish it, and production hands you empty data. No error, no crash, just nothing where the numbers should be. That is not bad luck. That is the predictable bill for skipping the practices that make a card reliable.

Requirement r-11a from the FlexCards domain, worth 18% of the Salesforce OmniStudio Consultant exam, asks you to discuss best practices for FlexCards. Notice the verb. The exam is not asking whether you can drag a card together. It is asking whether you know the practices that keep a card lean, clear, deliberate, and tested, and whether you can look at a scenario and name the practice that got violated. That second skill is the one that shows up in the questions.

The practices cluster into four areas: data, design, logic, and testing. Get all four right and the card is fast because its data source is lean, clear because the layout leads with what matters, maintainable because the logic is deliberate, and reliable because it was tested where it actually runs. Get any one wrong and you pay for it in a specific, predictable way. The exam wants you to name that way.

## Deep Dive

### Match the data source to the card's real need

Start with the data source, because everything else leans on it. A FlexCard can pull from several kinds of sources, and the right one depends on what the card actually has to do. Salesforce's guidance on setting up a data source on a FlexCard lays out the menu: pull directly from Salesforce objects with Data Mappers, SOQL queries, and SOSL searches, use an external source with REST methods, or use an Apex remote method or an Integration Procedure for complex business processes.[^1]

The decision rule is simple once you frame it as complexity. Use a Turbo Extract for simple, single-record lookups. It is fast and returns a flat result set, which is exactly what you want when the card shows a small set of fields for one record. Move to a standard Extract when the query needs more logic, filters, joins, or data formatting that a Turbo Extract cannot express. Reach for an Integration Procedure only when orchestration or external data is required, when the card must merge data from several sources or call an external service as part of fetching its data.

The exam turns this into a matching exercise. A card that shows a few fields for a single record is best served by a Turbo Extract, because it is fast and returns a flat result set. An Integration Procedure is heavier than the card needs. Static JSON cannot pull live record data. A child FlexCard is a composition choice, not a data source. Match the source to the need and the card stays simple. Reach for the heaviest tool and you add a server round trip and configuration complexity for no benefit.

![Choosing a data source by what the card needs to fetch: a Turbo Extract for a simple single-record lookup, a standard Extract for more logic, and an Integration Procedure only for orchestration or external data](</diagrams/day-21-r-11a-flexcard-best-practices-design-data-and-performanc/1-data-source-decision.png>)

### Design the card around the user's job and context

A FlexCard shows contextual information at a glance and provides access to relevant tasks for the displayed data.[^2] Hold that definition up against your card and ask a hard question: does the layout lead with the information the user needs to make the decision this card exists to support?

Lead with the decision data. Picture a service agent deciding whether to escalate a case. The priority, the age, and the customer's history are the decision data, and they belong at the top. Now picture a sales rep deciding whether to follow up. The opportunity stage, the close date, and the next step belong at the top. Everything else is secondary, and it should be grouped below or tucked into a flyout.

Group related information. Related fields belong together in a block, and unrelated fields should not be mixed. Salesforce's FlexCard best practices make this concrete: group elements with similar conditions together using blocks, which improves performance and makes the card easier to develop and manage, and use flyouts or collapsible blocks to show additional information.[^3] Grouping is not a visual nicety. It is a performance and maintainability practice, because a block of elements with the same condition renders and updates as a unit.

Use conditional rendering to tailor sections by role. A card that shows everything to everyone serves no one. A manager and a frontline agent looking at the same card need different information, and conditional rendering lets the card show the right sections to the right people. The card becomes a set of role-appropriate views rather than a single undifferentiated wall of data.

### Keep the data source lean

Here is the practice the exam tests most directly, so pay attention. Return only the fields the card displays or uses in logic, because every extra field adds payload and render cost. A card that pulls a wide record when it shows three fields wastes performance for no benefit.

The quiz puts it in front of you: a FlexCard displays three fields, but its data source returns a wide record with dozens of fields. What best practice is violated? The answer is that the data source is not lean, adding payload and render cost. The theme is not the issue. The card does not have too few elements. The output variables are not the problem. The data source is over-fetching, and over-fetching is a performance violation.

Why does it matter? Every field the data source returns has to travel from the server to the browser and sit in memory, even if the card never renders it. On a record page with many cards, or in a console with several cards visible, the waste multiplies. Salesforce's own guidance reinforces this: when you pull data into a FlexCard through any data source, impose a low limit on the amount of data you fetch, and increase it only after the card is developed and published.[^1] Start lean. Pull more only when the card actually needs it.

### Use state variables and conditional rendering deliberately

State variables and conditional rendering make the card dynamic, and that is their purpose. Overuse them and the card becomes hard to test and maintain. The practice is restraint: keep the conditions few, the state initialized, and the logic clear.

State variables let the card track the user's interaction and adapt. A card can use a state variable to remember which tab the user selected, or whether a section is expanded, and read that variable in a conditional rule so the card changes as the user works. Conditional rendering lets elements appear or hide based on a condition, so the card tailors itself to the situation.

The discipline is restraint. Every condition is a place where the card can behave unexpectedly, and every state variable is a value that has to be initialized and kept consistent. Salesforce's guidance is to use FlexCard states when several elements have similar conditions or are laid out differently based on a condition, because states load the card faster and format elements correctly, and to consider states over conditional displays of elements in a single state.[^3] Prefer a small number of well-defined states over a tangle of individual conditions. Keep the conditions few, initialize the state, and keep the logic readable.

### Reuse child FlexCards, but resist over-nesting

A child FlexCard is a reusable card embedded in a parent, and it earns its place when the same section appears in several cards or when a card needs multiple data sources.[^4] But each child adds render and data-fetch cost, so a flat card is often the better choice.

The exam tests the over-nesting failure directly. The quiz describes an architect who nests many child cards when a single flat card would display the same data, and asks what the primary concern is. The answer is that each child adds render and data-fetch cost, slowing the card. Each child FlexCard is a separate instance with its own render and data-fetch cost, so over-nesting slows the card. Render speed, theme, and a lean data source are not the concern. The nesting itself is.

Salesforce's guidance is explicit about the cost of unnecessary nesting. Avoid creating a child FlexCard solely to display a single text block, and instead consolidate that text into the parent or an existing child, managing its visibility with native states or conditions rather than component nesting.[^3] Use a child card when it earns its place, meaning it is genuinely reusable or genuinely needs its own data source. Keep the card flat when a single card can do the job.

### Test the card in its real placement with real data

This is the practice that would have saved you from the empty-data scene at the top of this lesson. A card that works in the editor can fail in production because of input mapping, missing fields, or placement context, so verification in the target environment is part of the build.

The editor gives you a controlled preview. It lets you add test parameters and see how the card looks on multiple devices, and it gives you a debug pane to inspect the data JSON and detect issues at run time.[^3] But the editor cannot reproduce the real placement. It cannot reproduce the exact input mapping the page provides, the exact fields available in the production data, or the exact context of the placement. Those are the things that break in production.

The quiz tests this directly. A FlexCard works in the editor but fails in production with empty data. What best practice was most likely skipped? The answer is testing the card in its real placement with real data. A card can fail in production because of input mapping, missing fields, or placement context, so testing in the target environment with real data is a best practice. Choosing a theme, adding more elements, and using a chart do not address production failures.

The practice is to test with representative data in the actual placement before release. Confirm the input mapping the page provides matches what the card expects. Confirm the fields the card references exist in the production data. Confirm the placement supplies the context the card needs. That verification is what turns a card that works in the editor into a card that works for the user.

## Config Walkthrough

Apply the best practices with these four review steps.

1. Review the data source and confirm it returns only the fields the card needs. Open the card's data source and check every field it returns. If a field is not displayed and not used in a condition or a formula, remove it. Confirm the source type matches the need: a Turbo Extract for a simple single-record lookup, a standard Extract for more logic, and an Integration Procedure only for orchestration or external data.

2. Review the layout to confirm it leads with the most important information and groups related data. Check that the decision data is at the top, that related fields are grouped in blocks, and that secondary information is tucked into flyouts or collapsible blocks. Confirm the card shows different sections to different roles through conditional rendering rather than showing everything to everyone.

3. Review conditional rules and state variables to confirm they are few, initialized, and testable. Count the conditions and confirm each one is necessary. Confirm every state variable is initialized before it is read. Prefer a small number of well-defined states over a tangle of individual conditions, and confirm no child FlexCard is doing work a flat card could do.

4. Test the card in its target placement with representative data before release. Add the card to the actual page or console, feed it representative data, and confirm the input mapping, the fields, and the placement context all line up. Fix anything that fails in the real environment, not just in the editor.

## Exam Traps

Three traps account for most misses on this objective.

![The three exam traps for FlexCard best practices: over-fetching a wide data source, over-nesting child cards, and shipping a card never tested in its real placement](</diagrams/day-21-r-11a-flexcard-best-practices-design-data-and-performanc/3-exam-traps.png>)

First, pulling a wide data source when the card shows few fields. The extra payload slows the card for no benefit. The exam will describe a card that over-fetches, and the correct answer is that the data source is not lean, adding payload and render cost. Return only the fields the card displays or uses in logic.

Second, over-nesting child cards. Each child adds cost, and a flat card is often simpler and faster. The exam will describe an architect who nests many child cards when a flat card would do, and the correct answer is that each child adds render and data-fetch cost, slowing the card. Use a child card only when it is genuinely reusable or genuinely needs its own data source.

Third, shipping a card that works in the editor but fails in production because it was never tested in its real placement with real data. The exam will describe a card that works in the editor and fails in production with empty data, and the correct answer is that testing in the target environment with real data was skipped. Input mapping, missing fields, and placement context are the things that break in production, and only real-placement testing catches them.
