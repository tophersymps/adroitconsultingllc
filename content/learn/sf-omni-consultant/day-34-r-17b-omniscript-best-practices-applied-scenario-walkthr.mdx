Requirement r-17b from the OmniScripts domain, worth 17% of the Salesforce OmniStudio Consultant exam, asks you to discuss best practices for Omniscripts, and this lesson is where those practices stop being abstract and become a working design. A scenario walkthrough takes a real business journey and traces it through the design decisions: the Steps, the conditions, the data flow, and the error handling.

Here is the mindset. A walkthrough is not a summary. It is a concrete, reviewable, testable design. You name the Steps, the elements, and the tools. You walk every branch and every failure path. ## Deep Dive

### What a scenario walkthrough is

A scenario walkthrough applies the best practices to a concrete business case. Take a real journey, such as a service agent resolving a case, and trace it through the design decisions: the Steps, the conditions, the data flow, and the error handling. The walkthrough is where the practices stop being abstract and become a working design.

The practices from lesson 33 are the raw material. Define the data JSON contract first. Fetch once and reuse. Match the tool to the scope. Test every branch and failure path. Salesforce's own best practices doc is the source for these, and it frames them around performance and usability.[^1] A walkthrough takes those practices and applies them to a specific journey, so you can see what they mean in practice. The case resolution journey is a good example, because it has real branches, real data flow, and real failure paths.

The value of a walkthrough is that it forces the design to be concrete. You cannot hand-wave a Step; you have to name it. You cannot assume a branch works; you have to walk it. The walkthrough surfaces gaps that a high-level description hides, and it produces a design that can be reviewed and tested.

### Start by mapping the business process to user intents

Start a walkthrough by mapping the business process to user intents. For a case resolution journey, the intents might be verify the account, review the case, capture the resolution, and log the outcome. Each intent becomes a Step, and the decision points become conditions. This mapping is the first and most important design act.

The quiz tests this directly. A consultant is walking through a case resolution OmniScript. The first design act is to map the business process to user intents, then translate each intent into a Step. Adding inputs first skips the structure, deploying before design is premature, and an LWC is a component choice, not the starting point. The intent mapping is the answer.

Why does the intent mapping come first? Because it gives the journey its structure. The user is not filling out a form; they are accomplishing intents. Verify the account. Review the case. Capture the resolution. Log the outcome. Each intent becomes a Step, and the decision points become conditions. The structure comes from the intents, not from the inputs. Add the inputs first, and you have a pile of fields with no structure. Map the intents first, and the structure falls out.

### Cover the branches and the failure paths

A walkthrough must cover the branches and the failure paths. For a case resolution, what happens if the case is already closed, if the account fetch returns nothing, or if the save rejects? Each case gets a conditional step or an error path. The walkthrough is not complete until every branch and every failure has a defined behavior.

The quiz tests this directly. During a walkthrough, the consultant reaches the case where the account fetch returns no data. The design must define a defined behavior: a clear message and a corrective path. A walkthrough is not complete until every failure path has a defined behavior. Assuming it is unlikely, silent retry, or ignoring it leaves the journey broken for a real case. The defined behavior is the answer.

This is the failure-path discipline from lesson 32, applied to the walkthrough. Every branch and every failure gets a defined behavior. If the case is already closed, a conditional step routes the user to a message and a path forward. If the account fetch returns nothing, the user sees a clear message and a corrective path. If the save rejects, the user sees the rule and a way forward. The walkthrough is not complete until every case has a defined behavior.

### Name the specific elements and tools

A walkthrough should name the specific elements and tools. Which Steps, which Blocks, which Inputs, which Data Mapper or Integration Procedure, which validation rules, which error messages. Naming them forces the design to be concrete and reviewable, and it surfaces gaps that a high-level description hides.

This is the concreteness that separates a design from a sketch. You do not say "the journey fetches the case." You say the case is fetched by a Data Mapper Extract into the data JSON under the name caseRecord, and the account is fetched by an Integration Procedure that also validates the account status. You name the validation rules and the error messages. Naming them forces the design to be concrete and reviewable.

The tool choice matters here, and it connects to lesson 33. A single deterministic transform is a Data Mapper's job. Multi-step, multi-system orchestration is an Integration Procedure's job. The walkthrough names which tool does which job, and that naming surfaces gaps. If you cannot name the tool for a Step, you have not designed that Step yet.

### A worked example: the case resolution journey

A worked example makes the walkthrough concrete. A service agent resolves a case. The journey starts by mapping the business process to user intents: verify the account, review the case, capture the resolution, and log the outcome. Each intent becomes a Step, and the decision points become conditions.

The first Step, verify the account, fetches the account by the case's account ID. The data flow is explicit: the account is fetched into the data JSON under the name accountRecord, and the case is fetched into the data JSON under the name caseRecord. Both are fetched early and stored, so later Steps reference them instead of re-fetching. The second Step, review the case, displays the case details and the account summary, and it is where the agent confirms the case is still open.

The branches and failure paths get defined behavior. If the case is already closed, a conditional step routes the agent to a message that the case is closed and offers a path to reopen it or view the history. If the account fetch returns nothing, the agent sees a clear message that no account was found and a corrective path to search for the account manually. If the save rejects because of a downstream rule, the agent sees the rule explained and a path to correct the data.

The elements and tools are named. The account fetch is a Data Mapper Extract. The case fetch is an Integration Procedure that also validates the case status. The resolution capture is a set of Inputs in a Step. The save is a Data Mapper Load. The validation rules and error messages are named for each field. Naming them forces the design to be concrete and reviewable, and it surfaces gaps that a high-level description hides.

### The test matrix ends the walkthrough

The test matrix is the deliverable that proves the design. Each branch, each boundary, the empty case, and each unexpected outcome becomes a test case. For the case resolution journey, the matrix covers the happy path, the closed case, the empty account fetch, the rejected save, and the boundary where the account name changed mid-journey. Each case lists the expected behavior and the result.

## Config Walkthrough

Walk a concrete journey through the design in four steps.

1. Pick a concrete business journey and map it to user intents, then translate each intent into a Step and each decision point into a condition. For a case resolution, the intents are verify the account, review the case, capture the resolution, and log the outcome.
2. Trace the data flow explicitly: what is fetched, when, into which data JSON names, what is transformed and where, and what is saved and how. Fetch the case and account early, store them in the data JSON, and save the resolution at the end.
3. Walk every branch and failure path, defining a conditional step or error path for each, so no case is undefined. Cover the closed case, the empty fetch, and the rejected save.
4. Name the specific elements and tools for each Step, then turn the design into a test matrix and validate it. End the walkthrough with the test cases that prove the journey works.

## Exam Traps

Three traps account for most misses on this objective.

First, stopping the walkthrough at the happy path. A design that does not define behavior for closed cases, empty fetches, or rejected saves is incomplete. Walk every branch and failure.

Second, keeping the walkthrough high level. A design that does not name the Steps, elements, and tools cannot be reviewed or tested. Make it concrete.

Third, ending the walkthrough without test cases. A design that cannot be tested is a sketch. Turn the design into a test matrix and validate it.
