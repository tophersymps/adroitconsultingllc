A FlexCard that only shows data is a report. The moment you add an action to it, a button that does something when a user clicks, the card stops describing the work and starts driving it. This is the shift this lesson is about. A service agent does not look at a case card to admire the case number. The agent looks at it to decide what to do next, and the card should carry that decision forward: assign it, escalate it, resolve it, or hand it off. The features that let the card do that are its actions, and they are what Lesson 15 (requirement R-8a) asks you to design well. The requirement sits in the FlexCards domain, worth 18 percent of the OmniStudio Consultant exam, and it asks you to recommend the implementation of necessary actions (links, modals, launching OmniScripts, calling Integration Procedures, and child FlexCards) that drive user workflows and business processes. In plain terms: given a card, which action should the user be able to take, and which action type gets the user to the next step without breaking their flow.[^1]

Lesson 14 gave you the filter for deciding which actions belong on a card at all, and to whom to show them. This lesson is about the actions themselves: what each type does, when it is the right tool, and how you configure it. Together they are the design layer that makes a card part of a real workflow rather than a passive readout.

## Deep Dive

### What an action is, and the types you choose from

An action is wired to an element on the card, usually a button, a link, or a row in a data table, and it fires when the user interacts with that element. The element is the trigger and the action is the behavior. That separation matters because the same card can have several triggers that point at different behaviors, and each element can carry its own action configuration.

The action types you will recommend are: navigating to a link, opening a modal, launching an OmniScript, calling an Integration Procedure, and opening a child FlexCard. That list is the exam's framing of the requirement, and it is worth holding on to because it sets the design decision you are making every time you add an action: not which feature exists, but which one moves this user's next step forward cleanly.[^1]

Each type answers a different question about where the next step happens. A link answers "the next step lives somewhere else." A modal answers "the next step is short and should happen right here." Launching an OmniScript answers "the next step is a guided, multi-step process." Calling an Integration Procedure answers "the next step is work the server should do, and the card should show the result." A child FlexCard answers "the next step is more detail rendered by another card." Picking the right one is a design decision about how the user should complete the step, and it is the judgment the exam will test.

There is a useful split across the list that the exam traps rely on. Links and modals are about presentation and context: do you leave the page or stay on it? OmniScripts and Integration Procedures are about process and work: does the user walk through a guided flow, or does the server run logic and report back? And a child FlexCard is about composition: nesting another card to show more detail or host a sub-workflow. Matching the action to the user's next step means reading the step by that split before you reach for a type.

### Link action: go somewhere else, deliberately

A link action navigates the user to a URL or to a record, which takes them out of the current context. The click may open another record page, an external system, a document, or a portal. Because the user leaves the card and the page it sits on, a link is the right choice only when the next step genuinely lives elsewhere.

That last clause is the trap. A link is easy to add, so it is the default reach when a designer wants the user to do something. But the cost of a link is interruption. The user's page context changes, the card they were reading is gone or reloaded, and getting back means more navigation. When the next step can happen in place, a link is the wrong tool even though it is the easiest one.

Use a link when the destination is a different object, an external system, or a full record page where the user starts a separate task. A sales agent finishing a quick contact check on an account card might link out to the contact's own record page because that page is where the real work begins. Use a link when leaving is the point. Do not use it to avoid building a modal for a step that belongs inside the current flow, because you have traded a small interruption for a large one and made the user chase their place.

### Modal action: keep the user in context for a short step

A modal action opens a dialog on top of the current card, which keeps the user in context. The page does not change under them. The card is still there behind the dialog, and when the dialog closes the user is exactly where they were.

This makes the modal the right tool for a short, focused interaction that should not interrupt the flow: a quick capture, a confirmation, a one-field update, a choice between a couple of options. The modal can host a small form or a child FlexCard, so it is not limited to a single field. But its strength is the same in all cases: the user accomplishes a small thing in place and continues.

The contrast with a link is the point the exam draws. Entering a single short value is a modal's job, because navigating away to reach a separate page that hosts that one field forces the user to move their whole context for a trivial amount of work. The modal keeps them where the card is useful.

A modal is also the right home for a confirmation that should not take the user anywhere: "this will recalculate the quote, continue?" in a dialog, not a page change. When you design a modal, decide what the dialog will contain, how the user completes it, how it closes, and whether the parent card refreshes after the interaction. The last two are configuration details that commonly get skipped, and a modal that does not close cleanly or a card that does not reflect the change is a broken workflow even though the dialog itself opened fine.[^3]

### Launching an OmniScript: drive a guided process

Launching an OmniScript is the action that drives a guided business process. When the user needs to complete a multi-step flow such as building a quote, resolving a case through steps, or capturing a lengthy set of inputs, the card action launches the OmniScript so the flow runs in the guided, step-by-step interface that OmniScripts provide.

This is the action that connects the card to the broader OmniStudio process layer. A card can surface the entry point to a process without trying to host the whole process in the card. That division of labor is the architect's move: the card gives the user the context and the trigger, and the OmniScript owns the guided steps that follow.

The load-bearing detail when you launch an OmniScript is the context record. The flow is only useful if it starts with the right data, which means the card must pass the context record and any needed parameters into the launch. The card already holds the record the user is looking at; the launch action must hand that record to the OmniScript so the flow opens pre-filled and pre-targeted. Launching the OmniScript without that context is the exam trap: the flow starts empty, and the user must re-enter data the card already had, which is exactly the friction the action was meant to remove.[^2]

### Calling an Integration Procedure: server-side work that reflects back

Calling an Integration Procedure (IP) from an action lets the card trigger server-side orchestration without navigating anywhere. The user clicks, the IP runs a business operation, and the card reflects the result. IPs are declarative, server-side processes that can execute several actions inside a single server call, so they are the right home for a calculation, a data update, or a multi-step back-end operation that should not live in the user's browser or in the card's data source.

The cleanest IP action pattern is two beats in sequence: the click runs the IP, then the card refreshes to show the new state. The card is not a navigator here, it is a remote control for work done elsewhere, and its job after the work completes is to show the updated result. That refresh step (often an Update Datasource or Append Record card action in OmniStudio) is part of the design, not an afterthought. A calculation that runs and then leaves the card stale is an action the user cannot trust, because the result the card shows no longer matches the state the server computed.[^4]

As a data source, an IP also needs the context record so it knows which record to operate on. The card passes the context (for example the recordId) as an input to the IP, and the IP uses it in its logic. Without that binding, the IP runs against the wrong target or none at all, and the workflow breaks in a way that is easy to miss because the click itself succeeds.

### Child FlexCards: more detail and nested workflows, in context

The last action type is opening a child FlexCard. A child FlexCard renders another card, either inside a flyout or as part of the parent's composition, to show more detail or to host a focused sub-interaction without building a separate page or leaving the workflow. This is how a summary card reveals its detail: the parent holds the key facts and the actions, and a child card holds the deeper information or a nested action flow that appears on demand.

The child FlexCard is distinct from the other types because it reuses the card machinery itself as the destination of the action. Its value is composition and reuse: build the detail once as a card, and surface it from wherever a user needs it. Because a child card can also appear inside a modal, it pairs with the modal action to give a short in-context dialog real substance (a form or a nested view) rather than a single field.[^3]

### Design the action layer with data source and role in mind

Two constraints shape every action you wire, and they come up together in the requirement. First, the action needs the context record so it can pass that record to the OmniScript or IP it launches. Almost every action type depends on having the right data in hand: a link to a record needs the record's ID, an OmniScript launch needs the context, an IP call needs the input it operates on. If the action is not wired to the element that holds that data, or the card's data source does not return the needed context, the action fails silently: the click does nothing useful, and the workflow stalls without an error to explain why.

Second, expose an action only to the roles that should take it. Role-based design from Lesson 14 applies to actions directly. An action that a role cannot take, or should not take, clutters the card and invites misuse. An escalation button shown to a manager who never escalates is noise; a deactivation button shown to an agent who lacks the authority is a hazard. Match the action set to the role and the context, exactly as you matched the data.[^1]

There is a governance angle to hold for the exam: the action layer is part of the card's contract with the workflow, so it must be intentional. Every action should earn its place (it advances a specific step), carry its context (so the step it triggers starts correct), and respect its audience (so only the right roles see it). A card that satisfies those three is doing real work. One that does not is a display with buttons that happen to be there.

## Worked Example: the case resolution card

Put the action types together on one card so the split is concrete. A service agent opens a case record page that renders a FlexCard showing case identity, the SLA deadline, the customer's history, and a set of actions. Each action is a different type because each drives a different next step.

- **Resolve case** is a button that launches an OmniScript. Resolving a case is a multi-step guided process (capture the resolution, route for approval, notify the customer), so it is exactly what an OmniScript is for. The launch action passes the case context record, and the flow opens already pointed at this case.
- **Escalate** opens a modal. Escalation is a short, focused interaction: pick the reason and an owner. Nothing about that step justifies leaving the card, so a modal holds the small form in context. If the escalation form needs structure, the modal hosts a child FlexCard that renders the fields.
- **Re-run SLA calc** calls an Integration Procedure. The click runs a server-side calculation against the case, and when it returns, the card refreshes to show the recalculated deadline. The user never leaves; the card updates in place.
- **View customer portal** is a link to an external portal. Leaving is the point, so a link is correct: the agent genuinely needs to be in the other system.

Now make the deliberate mistakes the exam traps warn about, and watch how each breaks the workflow. Make **Resolve case** a link to the case record page: the agent leaves the card, loses the context, and there is no guided resolution flow, so the multi-step process never runs. Make **Escalate** a full OmniScript launch: for a two-field update the agent is walked through a heavy multi-step flow, which is overkill and interrupts their rhythm. Make **Re-run SLA calc** an IP call that never refreshes the card: the calculation runs, the deadline on screen stays stale, and the agent decides on outdated data. And launch the resolution OmniScript without passing the context record: the flow opens empty and the agent re-enters the case details the card already displayed. Each choice looks minor and each one degrades an otherwise sound action layer.

## Configuration Walkthrough

Configuring an action follows the same shape no matter which type you choose. Use the FlexCard Designer's element configuration panel.

1. **Select the trigger element.** In the FlexCard editor, select the element that should trigger the action, such as a button, a link, or a data table row, and open its action configuration. An action element is the most direct trigger; an element like a table row or a block can also carry an action through its properties.
2. **Choose the action type.** Pick the type that matches the user's next step: link for navigation, modal for an in-context dialog, OmniScript to launch a guided flow, Integration Procedure to call server-side orchestration, or a child FlexCard for nested detail. The properties panel changes to present the fields for that type.
3. **Pass the context record and parameters.** For an OmniScript or Integration Procedure action, pass the context record and any needed parameters so the flow or procedure starts with the correct data. This is the step most often skipped, and it is the one that determines whether the launched process actually applies to the record the user is looking at.
4. **Configure the modal content and the after-state.** For a modal action, configure what the modal contains (a form or a child FlexCard), then verify the modal closes after the interaction and the card refreshes to reflect it. For an IP action, confirm the card updates its data source after the call returns so the new state is visible.

## Exam Traps

Three traps recur on the exam, and each is a judgment about matching the action to the step.

- **A link where a modal belongs.** Using a link action to navigate away when the next step could happen in a modal. Leaving the page interrupts the user's flow. A modal keeps them in context for a short, focused interaction. Reach for a link only when the destination genuinely lives elsewhere, not because it is the path of least resistance.
- **Launching an OmniScript without the context record.** If the flow starts empty, the user must re-enter data the card already held. Always pass the context so the guided process opens with the right record and parameters. An OmniScript that opens blank is a broken handoff from card to process.
- **Exposing an action to every role.** Showing an action to roles that cannot or should not take it clutters the card and invites misuse. Match the action set to role and context, the same way you matched the card's data, so each role sees only the actions it is allowed and expected to use.

## Exam Tip

Match the action to the next step, and the type follows: a link to go elsewhere, a modal to stay in context, an OmniScript for a guided multi-step flow, and an Integration Procedure call to run server-side work and refresh the card. When you read a scenario, identify where the user's next step happens (elsewhere, in place, as a guided process, or as server work) and the correct action type is usually the one that matches that location without extra friction.

## Try It

Open a sandbox with OmniStudio enabled and rebuild the case resolution card from this lesson. Create the card with a case data source, then add each action type: a button that launches a resolution OmniScript and passes the case context, a button that opens a modal for escalation, an action that calls an Integration Procedure to recalculate an SLA and then refreshes the card, and a link out to a portal. Verify each one starts from the record on screen: the OmniScript opens on the right case, the IP runs against the right record and updates the deadline, and the modal closes back to the card. Then break it deliberately. Launch the OmniScript without the context and watch it open empty. Wire the same escalation action to every role and watch it clutter a read-only view. Both failures teach the same lesson: an action is only as good as the element it is wired to, the data it carries, and the role it is shown to.
