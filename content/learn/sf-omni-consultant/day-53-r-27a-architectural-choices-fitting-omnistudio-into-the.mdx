OmniStudio is not a single product. It is a family of declarative tools, and the architect's first job is to place each one on the right layer of the stack. Requirement r-27a asks you to justify and recommend architectural choices, showing how OmniStudio components fit into the overall Salesforce and enterprise system landscape. In the Best Fit Solutions domain, worth 15% of the exam, the questions reward consultants who can name the layer a component serves and the artifact it displaces. The organizing idea is simple: before recommending any OmniStudio component, write one sentence naming the layer it serves and the artifact it displaces. If you cannot write that sentence, you have not made an architectural choice yet.

## Deep Dive

### OmniStudio is a family of declarative tools, not a single product

OmniStudio is not a single product. It is a family of declarative tools: OmniScripts for guided user journeys, FlexCards for embedded display, Data Mappers for data movement, Integration Procedures for server-side orchestration, and Document Generation for templated output [^1]. The architect's first job is to place each component on the right layer of the stack.

The layer placement is the core of the architectural choice. OmniScripts and FlexCards live in the presentation and interaction layer, where users see and touch the interface. Data Mappers and Integration Procedures live in the integration and service layer, where data moves and logic runs off the browser. Document Generation sits at the boundary where structured data becomes deliverable artifacts [^1].

Recommending a component means naming the layer it serves, not just the feature it provides. An OmniScript is not "the thing that collects an application." It is the component that lives in the presentation layer and guides a user through a multi-step journey. An Integration Procedure is not "the thing that calls an API." It is the component that lives in the service layer and orchestrates server-side work [^1].

The exam tests this directly. An architect asked to replace a Visualforce page that guides a user through a five-step application with a guided flow that reads and writes Salesforce records should recommend an OmniScript with Data Mappers for the reads and writes. An OmniScript is purpose-built for guided, stateful user journeys and reads and writes records under the user's context, which matches the requirement. A Lightning Web Component would require hand-built state management and offers no advantage here. A FlexCard is for embedded display, not multi-step input. An Apex batch job is for background processing, not interactive guidance [^1].

### The enterprise landscape has three concentric contexts

The enterprise landscape has three concentric contexts the architect must reconcile: the Salesforce org itself, the surrounding SaaS and on-premise systems, and the business process the solution automates [^1]. OmniStudio earns its place when the interaction is guided and stateful, and it is the wrong tool when a lighter native option serves the need.

The three contexts are the frame for every recommendation. The Salesforce org is where the components run. The surrounding systems are where the data and services live. The business process is what the solution automates. The architect reconciles all three before choosing a component [^1].

OmniStudio earns its place when the interaction is guided and stateful: a multi-step application, a quote, a case intake. It is the wrong tool when the requirement is a lightweight read-only widget that a Lightning Web Component serves more cheaply, or a high-volume batch integration that a platform event and Apex batch job handle more predictably [^1].

The exam tests this directly. A solution that needs a read-only summary of a customer's open cases displayed on the account record page, where the data is already in Salesforce, should use a FlexCard with a Data Raptor that reads the cases. A FlexCard is designed for embedded, read-only display and a Data Raptor reads the cases directly from Salesforce, which is the lightest correct fit. An OmniScript is overkill for a display-only widget. An Integration Procedure adds a server round trip for data that is already local. A scheduled job introduces staleness and extra writes for a read-only need [^1].

### Fit decisions hinge on where the source of truth lives

Fit decisions hinge on where the source of truth lives. If the record of record is in Salesforce, OmniStudio components can read and write it directly with minimal ceremony [^1]. If the source of truth is an external ERP, CRM, or data warehouse, the architect must decide whether to synchronize data into Salesforce or call out to the external system on demand through an Integration Procedure.

The source-of-truth decision drives latency, data freshness, and failure handling, and it should be made before any OmniScript is built [^1]. If the record of record is in Salesforce, the components read and write local copies with predictable latency. If it is external, the architect chooses between synchronizing data into Salesforce, so OmniStudio reads local copies, or calling out on demand through an Integration Procedure.

The exam tests this directly. An OmniScript that must display data whose source of truth is an external ERP should synchronize the needed ERP data into Salesforce and read it locally. Synchronizing the needed data into Salesforce lets the OmniScript read local copies with predictable latency and failure handling, which is the defensible enterprise pattern. Calling the ERP on each step multiplies latency and failure points. A custom setting is for configuration, not transactional data. Manual entry is error-prone and defeats the purpose of integration [^1].

### OmniStudio components are declarative, which changes the governance model

OmniStudio components are declarative, which changes the governance and delivery model versus code. A Data Mapper or Integration Procedure is metadata, so it deploys through the same change-set, package, or source-of-truth pipeline as other metadata, but it also carries runtime behavior that is easy to change without review [^1]. The architect must treat OmniStudio artifacts as production code for review and testing purposes even though they are built without Apex.

The governance point is subtle and important. Because the components are declarative, they are easy to change, and that ease is a risk. A Data Mapper that writes to the wrong object or an Integration Procedure with a misconfigured credential can corrupt data or expose secrets. The architect treats OmniStudio metadata as production code, with the same review and testing, so a declarative platform does not become an ungoverned shadow-IT surface [^1]. Following the OmniStudio naming conventions is part of that discipline, because a descriptive name is the first line of documentation for a component another team will maintain [^2].

The exam tests this directly. Treating OmniStudio metadata as low-risk because it is not Apex is a trap. A Data Mapper that writes to the wrong object or an Integration Procedure with a misconfigured credential can corrupt data or expose secrets, so it needs the same review and testing as code [^1].

### The enterprise landscape includes identity, security, and audit expectations

The enterprise landscape includes identity, security, and audit expectations. OmniScripts run under the user's context, so sharing rules, field-level security, and CRUD permissions apply to every read and write the script performs [^1]. Integration Procedures that call external systems must carry credentials and handle secrets without exposing them to the browser.

The security context is part of the architectural choice. An OmniScript runs under the user's context, so the sharing model and field-level security apply to every read and write it performs. An Integration Procedure that calls an external system must carry credentials and handle secrets without exposing them to the browser. The architect maps each component to the org's security model and to the enterprise's audit requirements, because a guided flow that bypasses sharing rules is a compliance incident waiting to happen [^1]. An Integration Procedure is the right home for that external call because it is a declarative, server-side process that can read and write data from Salesforce and from external systems using REST calls, and it can be called from an OmniScript, an API, or an Apex method [^3].

### Recommendation is a trade-off statement, not a feature list

Recommendation is a trade-off statement, not a feature list. For each candidate component the architect should state what it buys, what it costs in maintenance and runtime, and what it displaces [^1]. The recommendation is defensible when it names the displaced artifact, the retained capability, and the operational cost of the new component over its lifetime.

A FlexCard embedded on a record page may replace a custom Lightning component and a chunk of Apex. An OmniScript may replace a Visualforce page and its controller. The recommendation names the displaced artifact, the retained capability, and the operational cost [^1].

The exam tests this directly. An architect asked to replace a Visualforce page that guides a user through a five-step application should recommend an OmniScript with Data Mappers for the reads and writes. The OmniScript displaces the Visualforce page and its controller, retains the guided journey, and carries the operational cost of maintaining the OmniScript metadata [^1].

### A worked example: a claims intake solution

Put the pieces together with a concrete scenario. An architect is asked to design a claims intake solution for an insurance company. The solution must guide an adjuster through a multi-step claim submission, display a summary of the claimant's open claims, and write the claim to Salesforce.

The architect starts by mapping the business process to a component matrix. The claim submission is a guided, stateful interaction, so it belongs in an OmniScript. The open-claims summary is a read-only display, so it belongs in a FlexCard. The reads and writes are data movement, so they belong in Data Mappers. The architect names the layer each component serves [^1].

![Claims intake mapped to a component matrix: claim submission to an OmniScript, the open-claims summary to a FlexCard, reads and writes to Data Mappers, and policy data sync to an Integration Procedure, each with its named layer](</diagrams/day-53-r-27a-architectural-choices-fitting-omnistudio-into-the/3-claims-intake-matrix.png>)

Next, the architect decides the source-of-truth strategy. The claim record of record is in Salesforce, so the OmniScript reads and writes it directly. The claimant's policy data lives in an external system, so the architect decides to synchronize the needed policy data into Salesforce and read it locally, rather than calling the external system on every step [^1].

The architect documents the security context. The OmniScript runs under the adjuster's context, so sharing rules and field-level security apply to every read and write. The Integration Procedure that synchronizes the policy data carries credentials and handles secrets without exposing them to the browser [^1].

Finally, the architect produces a one-page fit rationale. The OmniScript displaces a Visualforce page and its controller, retains the guided journey, and costs the maintenance of the OmniScript metadata. The FlexCard displaces a custom Lightning component and a chunk of Apex. The recommendation names the displaced artifact, the retained capability, and the operational cost for each component [^1].

The result is a defensible architecture. Each component serves a named layer, the source-of-truth strategy is explicit, the security context is documented, and the recommendation names what it displaces.

Try it yourself. Take a business process you know, map it to a component matrix, decide the source-of-truth strategy, document the security context, and write a one-page fit rationale that names the displaced artifact and the operational cost for each component.

## Config Walkthrough

The architectural choice maps onto four concrete steps.

1. Map the business process to a component matrix before building: list each user interaction, the data it reads, the data it writes, and the external system involved, then assign an OmniStudio component or a native Salesforce tool to each cell [^1].

2. Decide the source-of-truth strategy first: for each data element the solution touches, record whether Salesforce is authoritative, the external system is authoritative, or the value is derived, and write that decision into the design notes [^1].

3. Document the security context for every component: confirm the running user, the sharing model, the field-level security on every object the OmniScript touches, and the credential store for every external call [^1].

4. Produce a one-page fit rationale for the solution that names the displaced artifact, the retained capability, and the operational cost for each OmniStudio component you recommend [^1].

Test the architecture against the business process and confirm each component serves a named layer before you build.

## Exam Traps

Three traps dominate this requirement, and each is a specific, avoidable mistake.

**Choosing OmniStudio for every interaction because it is declarative.** A simple read-only display is cheaper as a Lightning Web Component, and forcing it into a FlexCard adds metadata to maintain without adding value. Use a FlexCard with a Data Raptor for embedded read-only display [^1].

**Building an OmniScript that reads directly from an external system on every step.** Each synchronous call adds latency and a failure point; the architect should batch external reads into a single Integration Procedure or synchronize data into Salesforce. Synchronize the needed data and read it locally [^1].

**Treating OmniStudio metadata as low-risk because it is not Apex.** A Data Mapper that writes to the wrong object or an Integration Procedure with a misconfigured credential can corrupt data or expose secrets, so it needs the same review and testing as code [^1].

The exam tip that ties these together: before recommending any OmniStudio component, write one sentence naming the layer it serves and the artifact it displaces. If you cannot write that sentence, you have not made an architectural choice yet.
