Lesson 33 taught you to scale a sharing model so the share table stays lean. Today's requirement, i-2a, stops at the gate in front of every scaling decision: what are the org and its users licensed to do at all? The exam wording is blunt: given a set of conditions, determine the license limitations that will impact the intended sharing solution.[^1]

This is the requirement where a "missing" feature is usually not a misconfiguration. A checkbox you cannot find in Setup, a permission set that assigns to some users and errors on others, a premium object that exists in the metadata but is hidden for the people who need it, these are nearly always license questions. The architect who treats them as config questions burns hours hunting for a toggle that was never licensed in the first place. Learn to read the license problem first and most sharing design work untangles itself.

The frame to carry through the whole lesson is this: every user holds exactly one user license, that license fixes the baseline of features the user is entitled to, and neither a profile nor a permission set can hand the user a capability the platform has not licensed at the org level. Features sit behind tiers. When a feature looks unavailable, ask which license tier owns it, then ask whether the org and each target user hold that tier.[^4]

## Define the terms

**User license.** The license assigned to a single user that fixes the baseline of features that user can access. Salesforce licenses are organized as definitions that describe what the org as a whole can do and what each user can do, and each user is assigned exactly one user license. The user license controls which standard objects, custom objects, and features the user is entitled to, and it determines which profiles and permission sets are even available to that user.[^2][^4]

**Platform license.** A class of user license for internal users who need access to custom apps and objects but not the full range of standard CRM functionality. The Lightning Platform user license is the seat-based example, and Lightning Platform Starter, Lightning Platform Plus, and Salesforce Platform Login are variations that each carry the Salesforce Platform user license at their core. These licenses bound how much platform the org can assign: the number of custom objects per license, file and data storage, and API calls per day all differ across the tiers.[^5][^6]

**Permission set license (PSL).** A license that entitles a user to access additional features not included in their user license. A user can hold several permission set licenses on top of their single user license. The critical mechanical detail is that a feature gated by a permission set license is only usable by a user who both holds the permission set license AND has a permission set containing the feature permissions assigned. Granting the permission set without the supporting permission set license produces an assignment error, because the underlying license is what actually entitles the user to the feature.[^2]

**Permission set.** A bundle of object, field, and system permissions that extends what a user can do beyond their profile, without changing their base user license. It is the vehicle that carries feature permissions, and it is the place where the license check surfaces: to grant a user a permission via a permission set or permission set group, the user must hold a user license or permission set license that supports that permission. If the license does not support it, the grant is blocked.[^3]

**Feature gating.** The practice of making a platform feature available only to orgs and users that hold a specific license tier. Experience Cloud, Shield Platform Encryption, Field Audit Trail, Einstein, and premium objects are the flagship examples. When feature gating blocks a capability, the feature is genuinely absent for that org or those users, and no amount of permission-set work reaches it, because the license, not the configuration, is the barrier.[^6][^7][^9]

**Premium object.** An object whose use is tied to a premium license or feature, so that a standard user cannot meaningfully access it even if metadata seems to expose it. Access via a permission set to a premium object depends on the user holding the underlying license. When assignment to a standard user errors, the root cause is almost always that the user's license does not support the premium feature the permission set depends on.[^2][^3]

**Add-on and entitlement.** A separately purchased capacity grant the org holds on top of its base user licenses, such as additional file and data storage, additional report subscriptions, or additional Experience Cloud logins. Entitlements are finite. They constrain how broadly a sharing feature can be rolled out, because granting a feature to more users than the org has capacity for is not a config problem, it is a capacity problem that must be purchased.[^5][^8]

## Why it matters for the exam and for real builds

Requirement i-2a is a diagnostic objective. The exam hands you a set of conditions, an org with certain licenses and certain features, and asks whether the intended sharing solution will hold up under those licenses. The modern Salesforce exam guide, and the platform it reflects, treats licensing as a first-class constraint on security design, not as an afterthought an architect can hand off to procurement.[^1]

The realistic version is worse than the exam. A sharing design that ignores licensing looks correct on paper, passes every visibility check in a demo, and then fails in production for reasons that have nothing to do with sharing rules, role hierarchy, or OWD. I have watched a team design an Experience Cloud rollout for customer case access, only to discover the org's external users carried Customer Community licenses that did not include the reports-and-dashboards and standard-sharing capacity the design assumed, and the solution had to be re-architected around a different license tier. The sharing was correct; the license assumption was not.

So the exam wants a two-step habit. Before you touch a share rule, inventory what the org is licensed to do and what each target user's single user license supports. Then design only with features those licenses include, and when a requirement genuinely needs a feature the org has not licensed, flag it, name the license or add-on that would satisfy it, and choose a license-compatible alternative in the meantime. That is the whole of i-2a in one paragraph.[^2][^3]

## Platform licenses bound the org's ceiling

The first layer of the license question is the org's platform licensing. Platform user license types define which objects, features, and user counts an org has, and a sharing solution simply cannot use features the assigned licenses do not include. If the intended sharing mechanism depends on an object or a feature that none of the platform licenses cover, the mechanism is not available, and it does not matter how many share rows a lean design would have created, because the feature never exists to create them.[^5]

Concretely, Lightning Platform Starter and Lightning Platform Plus users hold the Salesforce Platform user license, and the two tiers differ in what platform they grant. Take custom objects: Lightning Platform Starter allows 10 custom objects per license, while Lightning Platform Plus allows 110 custom objects per license. Take API capacity: Lightning Platform Starter grants 200 API calls per member per day in Enterprise or Unlimited orgs, while the Plus tier grants more generous call volumes. Take storage: both user-based tiers include 20 MB of additional data storage per user. These are not cosmetic differences. If a sharing design assumes an org full of custom objects on many records, but the org holds the Starter tier at 10 custom objects per license, the design starts over-subscribed before a single share rule is written.[^6]

![Platform license tiers compared: Lightning Platform Starter allows 10 custom objects per license and 200 API calls per member per day, while Plus allows 110 custom objects and more generous call volumes, with 20 MB of additional data storage per user in both](</diagrams/day-34-i-2a-license-limitations-platform-license-types-permiss/2-platform-tiers.png>)

The platform-license ceiling is why the architect inventories licenses early. An org that intends to open a sharing-heavy custom app to a broad population needs to know whether its platform seats can hold the number of users and custom objects that app requires. When the intended sharing solution spans fields, objects, and users the platform licenses do not cover, the honest move is to document the license purchase or redesign around what the licenses include, not to assume the platform will accommodate it.[^6]

## Permission-set licensing is where the assign error lives

The second layer is permission-set licensing, and this is where the exam concentrates its traps. The mechanical rule is exact: to access functionality that sits behind a permission set license, a user must BOTH hold that permission set license AND have a permission set containing the feature permissions assigned to them. When you assign permissions through a permission set to users who do not hold the required license, you get an assignment error. The permission set license is the thing that actually entitles the user to the feature; the permission set is the bundle that turns the entitlement on.[^2]

This is quiz question one. A permission set grants access to a premium object, and assigning it to a standard user produces an error. The root cause is not the object having sharing rules, not OWD being Private, and not the profile lacking a tab. Those are sharing, visibility, and UI concerns, and none of them produces a license assignment error. The root cause is that the user's license does not support the premium feature the permission set depends on, so the assignment fails (or the feature stays hidden) because the required underlying license is absent.[^3]

Here is the concrete shape of the problem in Setup. A permission set can be associated with a permission set license, or its License field can be set to None. When you create a permission set and select a specific permission set license in the License field, any user assigned to that permission set is auto-assigned the permission set license as well. That makes administration easy: the permission set both carries the feature and carries the entitlement. But when you create a permission set with License set to None and it still tries to grant a licensed feature, you must manually assign the permission set license to users before you add them to the permission set, or the assignment errors because the user does not yet hold the entitlement the feature requires.[^2][^3]

![Permission-set licensing: a permission set with its License field set to a permission set license auto-assigns that license to assigned users, while a permission set with License set to None requires manually assigning the permission set license first or the assignment errors](</diagrams/day-34-i-2a-license-limitations-platform-license-types-permiss/3-permission-set-licensing.png>)

The trap is the silent version of the same failure. Some license-gated features do not hard-fail on assignment; they simply hide the feature for users who lack the supporting license. A user gets the permission set, the feature checkbox appear untouched, but the premium object or the gated field never becomes usable, because the user's license does not include it. The architect must check the user's license and the permission set license, not just whether the permission set is assigned, because an assigned permission set can still leave a feature hidden when the entitlement is missing underneath it.[^3]

## Feature gating by license tier explains most "missing" features

The third layer is feature gating, and it is the answer to the most common diagnostic the exam runs. When a feature like Experience Cloud, Shield encryption, or Field Audit Trail is unavailable for an org or for its users, that scenario is most likely a LICENSE limitation, not a sharing-configuration error. A criteria rule not sharing a record, OWD set to Public, or a page layout missing a field are all config or behavior issues with a config fix. An Enterprise-grade licensed feature being absent, though, is the signature of a missing license tier.[^7][^9]

Take Shield Platform Encryption. The Q&A for the feature states plainly that it is available in Enterprise, Performance, and Unlimited editions with the Salesforce Shield or Shield Platform Encryption licenses, and free only in Developer Edition. If the org holds a lower edition, or holds Enterprise without the Shield add-on, the encryption feature is not there. It cannot be enabled, not because the admin is looking in the wrong place, but because the license gate is closed.[^7]

Field Audit Trail tells the same story in slightly different words. It is available in Enterprise, Performance, and Unlimited editions with the purchase of the Salesforce Shield or Field Audit Trail licenses. It extends Field History Tracking so you can keep field-level history indefinitely, up to 200 tracked fields per object, and that history does not count against standard data storage. But the feature is gated: you need the Shield or Field Audit Trail license to use it in a production org at all.[^9]

Experience Cloud follows the tier pattern for external users. The external-user licenses are Customer Community, Customer Community Plus, Partner Community, External Apps, External Identity, and Channel Account. They are not interchangeable. Customer Community licenses give a basic pass, suited to business-to-consumer experiences where large numbers of external users need access to case objects or knowledge. Customer Community Plus adds reports, dashboards, and standard sharing, the capabilities that make it the right choice when external users need richer visibility. Partner Community is the business-to-business tier, for access to sales data such as partner relationship management, and it cannot be used with person accounts. Each tier exposes a different feature set, and choosing the wrong one silently removes the sharing mechanisms the design depends on.[^8]

![Experience Cloud external-user tiers compared: Customer Community gives a basic pass for case objects and knowledge, Customer Community Plus adds reports, dashboards, and standard sharing, and Partner Community is the business-to-business tier that cannot be used with person accounts](</diagrams/day-34-i-2a-license-limitations-platform-license-types-permiss/4-experience-cloud-tiers.png>)

Einstein and the premium objects are the same class. Einstein features are gated by license, and premium objects sit behind entitlement. When a sharing design needs a premium object or an Einstein capability, the org must hold that product, and the users who need it must hold the permission set license tied to it. A design that assumes these are universally available is assuming a license the org may not hold.[^2][^6]

## User-license interplay: one user, one license, no out-granting

The fourth layer is the interplay between a user's single license and every permission mechanism. Each user has exactly one user license, and that user license establishes the baseline of what the user is entitled to. Profiles and permission sets refine that baseline, but they cannot replace it. Object and system permissions in a permission set must be compatible with the user's single assigned license, and feature gating blocks any grant that would exceed that license's capability.[^4]

![The license stack: an org platform license sets the ceiling, a single user license fixes the baseline, a permission set refines it but cannot out-grant it, and feature gating blocks any grant that exceeds the license](</diagrams/day-34-i-2a-license-limitations-platform-license-types-permiss/1-license-stack.png>)

This is quiz question three, and it is the cleanest expression of why a permission set cannot bypass a license. A permission set cannot grant a capability to a user who lacks the supporting license because permission sets do not ignore licenses, licenses do not affect only profiles, and no hierarchy is involved at all. The reason is that object and system permissions in a permission set must be compatible with the user's single assigned license, and feature gating blocks incompatible grants. The permission set is a refinement layer on top of the license, not an override of it.[^2][^3][^4]

The same principle shows up in proactive terms in the permission-set assignment flow. Salesforce documents it directly: to grant a user a permission via a permission set or permission set group, the user must have a user license or permission set license that supports the permission. The example the docs use is Apex authoring: if you create a permission set without a license, include the Author Apex permission, and try to assign it to a standard Salesforce Platform user, the assignment fails, because that user license does not allow Apex authoring. Substitute a premium-object permission for Author Apex and the mechanic is identical.[^3]

The exam's version of this trap is subtle. A candidate sees that a permission set, when checked alone, appears to grant a premium feature, and concludes the feature should work. It appears to grant it because the metadata describes it. But the user's license is the binding constraint, and the platform enforces that constraint at assignment and at runtime. The permission set is necessary to turn the feature on, but it is not sufficient; the user must hold the entitlement that licenses it.[^2][^3]

## Capacity and add-on entitlements bound the rollout

The fifth layer is capacity. Add-on licenses, such as additional report subscriptions, additional file and data storage, or additional Experience Cloud logins, carry limits that constrain how broadly a sharing feature can be rolled out. A sharing mechanism may be licensed and permission-compatible, and still fail to reach the whole intended population because the org does not hold enough of the entitlement to cover them.[^5]

Consider the report-and-dashboard story from earlier. Customer Community Plus is the tier that includes reports, dashboards, and standard sharing, but Experience Cloud user licenses are purchased, meaning the org holds a finite number. If a design intends to expose reporting to five thousand external users but the org has purchased three thousand Customer Community Plus logins, the design does not scale to the population it promised. That is a capacity problem. The solution is to purchase more logins, or to redesign so the dashboard population is smaller, or to move some users to a tier that fits their actual access needs. No sharing rule fixes a login-count ceiling.[^8]

File and data storage are the same kind of constraint. Platform licenses include a baseline of additional data storage, and add-on storage is purchased separately. A sharing design that pushes large files out to a broad external population must account for whether the org holds enough storage to satisfy them, because archiving-scale files will exhaust a small storage entitlement quickly. The architect's job is to count the capacity the intended rollout will consume and compare it to the entitlements the org holds, before promising a rollout the org has no entitlement to serve.[^6]

## Design implication: validate licenses before you design

The practical design implication is that validation comes before design, not after. An architect who proposes a feature the org's licenses do not include must flag it, not silently hope it appears, and must choose a license-compatible alternative. This is the exam's strongest behavioral signal: it wants you to read a requirement and a license set, spot the mismatch, and name the fix, rather than building the sharing rule and discovering the license problem after deploy.[^1][^2]

The workflow is an inventory and a confirmation loop. First inventory who has which user licenses and what add-on entitlements the org holds that are relevant to the intended sharing features. Then confirm the proposed features, Shield, Experience, premium objects, Field Audit Trail, are covered by current licenses. Then check that any permission set carrying the feature is license-compatible for the target users, using the permission set's license field. If a feature is license-gated, identify a license-compatible alternative or document the license purchase. Finally, validate assignment by logging in as a representative user and confirming the feature works under their license.[^2][^3]

That last step is worth emphasizing because it is the only verification that proves the design under real conditions. A permission set can pass inspection in the metadata and still fail for a specific user whose license does not support it. Logging in as a user with each distinct license type, and confirming the gated feature actually renders and functions for them, is how the architect catches a license mismatch that never surfaced in Setup. The Share Model, component by component, works only when every user's license supports the features that component grants them.[^3]

## Validating licenses before designing, step by step

Walk the validation in order so each step hands the next its input.

![The five-step license validation loop: inventory user licenses and add-on entitlements, confirm the proposed features are covered by current licenses, check permission-set license compatibility, resolve license-gated gaps or document the purchase, and validate by logging in as a representative user](</diagrams/day-34-i-2a-license-limitations-platform-license-types-permiss/5-validation-workflow.png>)

**Step 1: Inventory user licenses and add-on entitlements.** In Setup, list the org's users and their user licenses, and record the add-on entitlements the org holds that are relevant to the intended sharing features: file and data storage, additional report subscriptions, and Experience Cloud logins. Write down the distinct license types present and how many users hold each, because the design has to work for every distinct type, not just the majority.[^2][^5]

**Step 2: Confirm the proposed features are covered by current licenses.** Take each feature the sharing solution depends on, Shield Platform Encryption, Field Audit Trail, Experience Cloud tiers, premium objects, Einstein, and check the org's edition and add-ons against the feature's licensing requirement. Flag any feature the org does not hold. This is the step that catches the class of problem where the feature is absent not because of config but because of a closed license gate.[^7][^9]

**Step 3: Check permission-set license compatibility.** For every permission set that carries a feature the design grants, open the permission set's License field and confirm it matches the target users' licenses. Where the permission set is associated with a permission set license, assignment auto-grants that license; where the License field is None but the feature is licensed, confirm the target users already hold the permission set license, or assign it first. This step is where assignment errors and silent feature absence originate.[^2][^3]

**Step 4: Resolve license-gated gaps or document the purchase.** When a required feature is not licensed, choose a license-compatible alternative that still satisfies the access requirement, or document the license purchase needed. Decide explicitly which one, and write the decision down, because a design that silently assumes an unlicensed feature will fail in production and blame the sharing configuration.[^2][^6]

**Step 5: Validate by logging in as a representative user.** For each distinct user license type in the target population, locate a user, log in, and confirm the intended feature renders and functions under that license. If a permission set or a gated feature fails for one license type, return to steps 3 and 4 before you consider the design complete.[^3]

## Worked example: a case-sharing rollout hits three license limits at once

Put the workflow together in a scenario the exam likes to build. A services org wants external customers to open cases against their accounts and, importantly, see a customer-facing dashboard with case status over time. The org holds Enterprise edition with Salesforce Platform licenses for a set of internal users, and the external population currently carries a pool of base Customer Community licenses.

Run step one, the inventory. Internal users hold the Salesforce Platform user license, which affords access to custom apps and objects but not the full standard CRM surface, and the external customers hold Customer Community licenses. The org has purchased Customer Community Plus logins for a small pilot group but plans a broad rollout on the base Community tier to keep cost down. Both tiers carry the Salesforce Platform user license at their core, so the platform mechanics are consistent, but the two tiers expose different feature sets.[^6][^8]

Now step two, confirm the features. The design depends on two licensed things: an Experience Cloud site so customers can open cases, and the case-status dashboard. Experience Cloud is covered by both tiers at the site level, so the community works. But access to reports and dashboards, and to standard sharing, is a Customer Community Plus capability. The base Customer Community license exposes case objects and knowledge but does not give the pilot group's dashboard surface to a base-tier user. The dashboard feature is gated against the base tier, and the org has only a small pool of Plus logins. That is the first license limit, and it is the exact shape of quiz question two: an Experience Cloud capability being unavailable is a license-tier limitation, not a criteria-rule or OWD problem.[^8]

Step three, check permission sets. The design assigns a permission set that grants signed customers access to their case records, and it references a premium reporting object behind the dashboard. For a user holding only the base Customer Community license, assigning that permission set either errors or silently leaves the reporting surface hidden, because the user's license does not support the premium object the permission set depends on. That is the second limit, and it is quiz question one: premium-object access via permission set fails for a license that does not support the feature. The pilot group already assigned the Plus license inherits the entitlement and sees the dashboard; base-tier users do not.[^2][^3]

Step four, resolve the gaps. Two honest options exist. Purchase enough Customer Community Plus logins to cover every customer who needs the dashboard, which satisfies the requirement as designed. Or redesign so customer-visible reporting is not required, and let the base Community tier serve case access only, which keeps every target user license-compatible without additional purchase. The architect must pick one and document it. The base-license alternative is valid only if the business can give up the dashboard; if it cannot, the purchase is the answer, and the design should say so explicitly rather than assume it is free.[^8]

Step five, validate. Log in as a representative base-Customer Community user and as a Plus user. The Plus pilot user sees the dashboard; the base user does not. The validation confirms the design holds under the license set only for Plus users, which forces the purchase-or-redesign decision in step four to be made explicitly. That is the entire i-2a loop working: inventory, confirm, check permission sets, resolve or document, and validate by logging in under each license type.[^3]

## Exam traps to avoid

**Trap: treating a "missing" feature as a config problem.** When Experience Cloud, Shield encryption, Field Audit Trail, or premium objects are unavailable for an org or its users, the scenario is most likely a license-tier limitation, not a sharing-configuration error. The alternative answers, a criteria rule not sharing a record, OWD set to Public, or a page layout missing a field, are all config issues with a config fix. A licensed feature being absent is the signature of a closed license gate, and the fix is a license, not a toggle.[^7][^9]

**Trap: ignoring the permission set's license requirement.** A permission set's feature requires the user's license to support it. Ignoring the permission set license causes assignment errors or silent feature absence, because the user must both hold the permission set license and have a permission set containing the feature permissions. Always check the permission set's License field against each target user's license before assigning, and remember that License set to None on a licensed feature still requires a manually-assigned permission set license.[^2][^3]

**Trap: assuming a permission set can out-grant a user's license.** Each user has exactly one user license, and you cannot grant another user license's features via a permission set alone. Object and system permissions in a permission set must be compatible with the user's single assigned license, and feature gating blocks incompatible grants. The permission set refines the license; it does not override it. Design the sharing solution to the licenses the users actually hold, and flag the mismatch rather than letting the design silently fail at runtime.[^2][^3][^4]

## Try it yourself

In a scratch org, prove the permission-set-license mechanic in miniature. Create a user with a standard license whose profile does not include a sales-adjacent premium feature, create a permission set that carries that feature, and attempt to assign it. Watch what happens at assignment time: the platform either errors because the license is unsupported or silently declines to expose the feature, depending on how the specific feature gates. Then create a second permission set associated with the correct permission set license, assign that license to the same user, and confirm the difference in what the user can now access. That one comparison makes the license-versus-config split concrete.[^2][^3]

Next, check the org's editions and add-ons. Open Company Information in Setup and read which editions and permission set licenses the org holds. Pick two of the gated features mentioned here, say Field Audit Trail and an Experience Cloud tier, and confirm from the licensing documentation whether your org holds the licenses those features require. Then verify it for real by looking for the feature in Setup and confirming it is present or absent for that reason. Finally, test your diagnostic instinct in your own words: a customer asks why the dashboard data is missing for one group of external users but present for another, and you must decide whether it is a sharing rule or a license tier. Explain the two checks that tell you which, and which skill from the exam guide makes the answer confident. Each step makes i-2a a habit instead of a guess.

## The design frame, in one screen

Keep requirement i-2a in one frame. Every sharing solution runs inside the licenses its org and users hold: platform license types set the ceiling of objects, features, and user counts the org has, and the solution cannot use features those licenses do not include. Permission-set licensing ties certain features to a user holding a specific license before a permission set can grant them, so confirm the permission set's license field matches each target user's license before assigning, because an incompatible grant errors or silently hides the feature. Experience, Shield Platform Encryption, Field Audit Trail, Einstein, and premium objects are all gated by license tier, so a "missing" sharing option is usually a license limitation, not a misconfiguration. Each user holds exactly one user license, and a permission set cannot out-grant it; object and system permissions in a permission set must be compatible with that single license. Add-on entitlements, in production, file and data storage, and Experience logins, are finite and bound how broadly a rollout scales. So validate licenses before designing: inventory user licenses and entitlements, confirm the proposed features are covered, check permission-set compatibility, resolve license-gated gaps or document the purchase, and validate by logging in as a representative user under each license type. Do those and the sharing solution you propose is one the org can actually run.[^1][^2][^3][^5][^8]
