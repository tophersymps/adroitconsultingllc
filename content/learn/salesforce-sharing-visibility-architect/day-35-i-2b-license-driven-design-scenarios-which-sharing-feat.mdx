Lesson 34 taught you to read the license constraints that hide or block sharing features. Today's requirement, i-2b, turns that reading into the decision the exam actually scores: given a set of conditions, determine which sharing features are license-required and design the solution within license constraints.[^1] Where i-2a said "recognize this feature is licensed," i-2b says "given the org and its users, produce a sharing design that the licenses can actually run."

The distinction matters because the exam builds these as scenario questions, not vocabulary questions. You get an org with a certain edition, a certain mix of user licenses, and a list of add-ons, then a set of access requirements, and you must design the sharing solution that fits inside that license reality. The wrong answer is not usually a false mechanism; it is a real mechanism the org cannot run because the license it needs was never purchased. That is the gap requirement i-2b is built to catch.

Keep the whole lesson in one frame. Every sharing feature sits behind a license, and you can group almost all of them into three buckets. External-user portal access, sharing sets, sharing groups, and guest-user sharing rules are Experience Cloud features that need community or Experience licenses, and without those licenses no amount of internal configuration creates external access. Shield Platform Encryption and Field Audit Trail are Shield and compliance features that need the Shield license, independent of any sharing configuration. The standard sharing model, OWD, role hierarchy, sharing rules, manual sharing, and Apex managed sharing, runs on full Salesforce CRM licenses, and limited licenses like some portal and platform variants have reduced object and feature sets that constrain what a sharing solution can use. Get those three buckets in your head and most license-scenario questions become a matching exercise.[^2][^3][^6]

This lesson walks the design method: inventory the licenses, map each requirement to a mechanism and its license, flag any gap, confirm the permission sets are license-compatible, and re-test under the actual license mix. It closes with the worked scenarios the exam favors and the traps that pull a candidate toward a license-free answer.

## Define the terms

**License inventory.** The structured list of the org's user license types, the count of users holding each, and the add-on entitlements (Experience Cloud logins, Shield, storage, additional licenses) the org holds. It is the compulsory first input to any sharing design, because every license-scenario decision is made against what the org is actually licensed to do. An architect who designs before producing this inventory is guessing.[^2][^4]

**Experience Cloud license.** A license that lets an org run Experience Cloud sites and grant external users access to portal content. The external-user tiers are Customer Community, Customer Community Plus, Partner Community, External Apps, External Identity, and Channel Account. They are not interchangeable: Customer Community gives a basic pass for case objects and knowledge, Customer Community Plus adds reports, dashboards, and standard sharing, and Partner Community is the business-to-business tier for access to sales data such as partner relationship management, and it cannot be used with person accounts. The tier decides which objects and features external users can actually reach, so choosing the wrong tier silently removes the sharing mechanism your design depends on.[^5]

**Sharing set.** An Experience Cloud feature that grants record access to external users by matching user and record attributes through a Sharing Set, so external users see only the records that match their profile attributes. Sharing sets are a licensed Experience Cloud capability; the internal org with only CRM licenses cannot configure them, because there is no external-user context for them to operate on without portal licenses.[^3][^6]

**Sharing group.** In Experience Cloud, a group that lets an org grant a single external guest access to multiple records through a sharing group, which is especially useful when you need a guest to reach a related set of records in one grant rather than many individual shares. Like sharing sets, Sharing Groups are an Experience Cloud feature and therefore sit behind Experience licenses.[^6]

**Guest-user sharing rule.** A sharing rule that grants access to a specific guest user so that unauthenticated or lightly authenticated visitors to a portal can see chosen records. Because the guest user is a construct of the Experience Cloud site, guest-user sharing rules are Experience-licensed and only exist where a community is licensed and configured.[^3][^5]

**Shield / Compliance license.** An add-on license that enables Shield Platform Encryption and Field Audit Trail in production orgs on Enterprise, Performance, and Unlimited editions (and free only in Developer Edition). Shield is purchased independently of every sharing mechanism, so an org can have a flawless sharing model and still have no encryption or extended audit retention because it never bought Shield.[^7][^8]

**Field Audit Trail.** A Shield (compliance) feature that extends Field History Tracking to keep field-level history indefinitely, up to 200 tracked fields per object, without counting against standard data storage. It is a good example of a sharing-adjacent requirement: the need is often security-related, but satisfying it is a license decision, not a sharing decision.[^8]

**Full CRM license.** The class of user license that includes the standard sharing model: they support OWD, role hierarchy, sharing rules, manual sharing, teams, and Apex managed sharing on standard objects. A user on a limited license that lacks these capabilities is a user the standard sharing model cannot fully reach, so a sharing design must confirm its target users actually hold licenses that support the mechanisms being used.[^4]

**Permission-set license.** A license that entitles a user to access features not included in their base user license. A user can hold several permission set licenses on top of their single user license, and a feature behind a permission set license is usable only by a user who both holds the license and has a permission set with the feature permissions assigned. When a permission set grants a premium object or feature to a user whose license does not support it, the assignment errors or the feature silently stays hidden.[^2]

## Why it matters for the exam and for real builds

Requirement i-2b is the applied twin of i-2a and one of the highest-signal design objectives on the Sharing and Visibility Architect exam. The exam guide is explicit that the objective is to determine which sharing features are license-required and to design the solution within license constraints, and a stated exam topic is that record access for external users flows through sharing sets, which is a licensed Experience feature.[^1][^3] That is the tell. The exam is not asking whether you know sharing rules; it is asking whether you know that sharing rules for external users need a license you may not have assumed.

The realistic version makes the point sharper. I have watched a team build a partner-facing portal on the assumption that their existing sharing rules for internal users would simply carry over to portal users, only to find that portal access at the partner tier required licenses the org had not purchased, and that the elegant internal sharing design had no reach into the external population they were trying to serve. The sharing model was correct. The license assumption was not, and the design had to stop and let procurement untangle it.

So the exam wants a decision habit, not a fact table alone. Faced with a set of conditions, the architect inventories the licenses, then maps each sharing requirement to the mechanism that satisfies it and to the license that mechanism needs, flags any requirement whose license the org does not hold, and either documents the purchase or redesigns within the licenses the org has. That loop, run reliably, is the whole of i-2b.[^1][^2]

## The three-bucket map: which sharing feature needs which license

Build the map early because every scenario reduces to it. When you see a sharing requirement, sort it into one of three license buckets.

![Three license buckets gate every sharing feature: Experience Cloud needs community or Experience licenses for external-user portal access, sharing sets, sharing groups, and guest-user sharing rules, Shield and compliance needs the Shield license for encryption and extended audit retention, and standard sharing needs full CRM licenses for OWD, role hierarchy, sharing rules, manual sharing, and Apex managed sharing.](</diagrams/day-35-i-2b-license-driven-design-scenarios-which-sharing-feat/1-three-bucket-license-map.png>)

**Bucket one: Experience Cloud.** Anything that extends a portal to external users is an Experience Cloud feature and needs Experience licenses. This covers sharing sets, sharing groups, guest-user sharing rules, and the general mechanism of granting record access to portal users at all. If the org has only internal CRM licenses, it does not have a licensed way to give a partner or customer portal access, because record access for external users is an Experience-licensed capability that does not exist outside a community. This is the exam's most reliable license trap, because it is the answer that feels like it should be free: external users already exist conceptually, so why would sharing rules need a license? They need one because external record access is delivered by a licensed Experience feature, not by the standard sharing model.[^3][^6]

The portal tier within Bucket one decides the object and feature availability for external users. A Customer Community user can reach case objects and knowledge, which suits business-to-consumer access. A Customer Community Plus user adds reports, dashboards, and standard sharing, which suits a richer customer experience. A Partner Community user reaches sales data such as opportunity records for partner relationship management. So the design question is not only "do we have Experience licenses," it is "does the tier we hold expose the objects and features this requirement demands." A design that needs external users to see a dashboard but holds only base Customer Community licenses is over-subscribed at the tier level.[^5]

![The Experience Cloud tier decides what external users can actually reach: Customer Community gives a basic pass for case objects and knowledge, Customer Community Plus adds reports, dashboards, and standard sharing, and Partner Community is the business-to-business tier for sales data such as opportunity records and cannot be used with person accounts.](</diagrams/day-35-i-2b-license-driven-design-scenarios-which-sharing-feat/2-experience-cloud-tiers.png>)

**Bucket two: Shield and compliance.** Encryption and extended audit retention belong here and are independent of the sharing configuration. Shield Platform Encryption encrypts data at rest and is available in Enterprise, Performance, and Unlimited editions with the Shield or Platform Encryption licenses, free only in Developer Edition. Field Audit Trail extends history retention and needs the Shield or Field Audit Trail license in the same editions. No sharing rule, OWD setting, or permission set grants these features, because they are not sharing features at all; they are compliance features that gate on the Shield license. If the org has never bought Shield, encryption and a five-year audit trail are simply not available, regardless of how otherwise complete the sharing model is.[^7][^8]

**Bucket three: standard sharing on full CRM.** OWD, role hierarchy, sharing rules, manual sharing, account and opportunity teams, Apex managed sharing, and the standard object grant model all require a user license that actually carries the standard CRM sharing features. Full Salesforce licenses carry them. Limited licenses, some portal and platform variants, have reduced object and feature sets, and a user on such a license may not be able to hold the object permissions, use the standard sharing model, or reach the premium objects a given sharing design expects. This is the bucket where the phrase "license-compatible" bites: a full-CRM sharing mechanism designed for full-license users silently underserves users on reduced seats.[^4][^6]

## The design method: walk it in order

Turn the three buckets into a repeatable method. The exam hands you conditions; you produce the license-compatible design, so run these steps in sequence so each one feeds the next.

![The five-step license-driven design method runs in order: document the license inventory, map each requirement to a mechanism and the license that mechanism needs, flag any requirement whose license the org lacks with a purchase or redesign, validate the permission sets are license-compatible for their assigned users, then re-test the solution under the actual license mix.](</diagrams/day-35-i-2b-license-driven-design-scenarios-which-sharing-feat/3-five-step-design-method.png>)

**Step 1: Document the license inventory.** List the user license types present and how many users hold each, and record the add-on entitlements the org holds that are relevant to the sharing design: Experience Cloud logins and tiers, Shield, storage, additional subscription licenses. Write down every distinct license type because the design must work for every type in the target population, not just the majority. This step is the foundation; a map built on a guessed inventory is unreliable.[^2][^4]

**Step 2: Map each sharing requirement to a mechanism and confirm the license that mechanism needs.** Take each access requirement and name the sharing mechanism that satisfies it, then name the license that mechanism requires. External-user portal access maps to an Experience Cloud site and community licenses. External record access through attribute or relationship matching maps to a Sharing Set, which is Experience-licensed. Encryption of sensitive fields maps to Shield Platform Encryption, which is Shield-licensed. Extended audit retention maps to Field Audit Trail, which is Shield-licensed. Internal standard-object access maps to the standard sharing model, which needs full CRM licenses. Writing the requirement-to-mechanism-to-license triplet for every requirement is what turns a vague scenario into a checkable design.[^2][^3]

**Step 3: For any requirement needing a license the org lacks, note the purchase or redesign within available licenses.** When a requirement maps to a mechanism whose license the org does not hold, the design has one of two valid continuations: document the license purchase that satisfies the requirement as designed, or redesign so the requirement is met within the licenses the org has. Decide explicitly which, and write it down. The trap to avoid is silently assuming the unlicensed mechanism will appear; a design that assumes an unlicensed Experience site is a design that fails at deploy, not a design that flags a purchase.[^6][^8]

**Step 4: Validate that the permission sets used are license-compatible for their assigned users.** For every permission set that carries a feature the design grants, open the permission set's License field and confirm it matches the target users' licenses. Where the permission set is associated with a permission set license, assignment auto-grants that license. Where the License field is None but the feature is licensed, confirm the target users already hold the required permission set license or assign it first. This is where a sharing design that is otherwise license-correct still fails, because an incompatible permission set either errors on assignment or silently leaves the gated feature hidden.[^2]

**Step 5: Re-test the sharing solution under the actual license mix.** Log in as a representative user for each distinct license type and confirm the intended features render and function under that license. A validated-under-one-license design is not a validated design. The re-test is the only check that proves the mechanism works for every user type the org actually holds, and it is what catches a license mismatch that never surfaced in Setup.[^2][^4]

## Worked scenario one: an internal-only org must open a partner portal

This is the exam's favorite move, and quiz question one. An org holds only internal Salesforce CRM licenses and must give partners portal access to their accounts. Read the conditions, run the method.

Step one, inventory: the org's users all hold full Salesforce CRM licenses, and there are no Experience Cloud user licenses purchased and no community built. Step two, map: the requirement, partners viewing their accounts through a portal, maps to an Experience Cloud site with external-user record access, which is delivered on Bucket-one licenses. The specific tier for a partner relationship is Partner Community. The mechanism is Experience-licensed, and the org has no Experience licenses. Step three, gap: the gap is explicit, the org must purchase Experience licenses such as Partner Community for the external population, or it cannot run a portal at all. Step four, permission sets: any permission set that grants signed partners their account records must be license-compatible with the partner license tier, which supports the assignment. Step five, validate: after licenses are in place, log in as a partner user and confirm the account records render.

The key implication, and the quiz answer, is that external-user portal access is an Experience Cloud community feature requiring the corresponding licenses, and without them sharing sets and portal access cannot be configured. A Shield license, the correct-trap answer, provides encryption and compliance features, not portal access. A Platform Starter license provides a limited internal platform seat, not external-user portal capacity. No internal license, no matter how full, creates external portal access, because the external-user mechanism is Experience-licensed and simply does not exist without it.[^3][^4][^5]

## Worked scenario two: Field Audit Trail for five-year retention

Another exam pattern, and quiz question two. An architect proposes Field Audit Trail for five-year retention. Which license is required? The answer is the Shield or Compliance license, because Field Audit Trail is a compliance feature that requires the Shield license, independent of the sharing configuration.

Run the method and the reasoning holds. Field Audit Trail is Bucket two, a Shield feature. The org must hold the Shield license (or the Field Audit Trail license in supported editions) before the feature is available at all. A Customer Community license, the licensing of a portal, does not provide it. A standard Salesforce license alone does not provide it. A permission set cannot grant it, because the permission set is the vehicle that turns entitlement on, but the entitlement itself sits behind the Shield license, and no compliant feature is usable without the license holding the entitlement. So the architect who proposes a five-year audit trail must first confirm the Shield or Field Audit Trail license exists in the org, and if it does not, the proposal is a license question to raise before any design proceeds.[^2][^8]

## Worked scenario three: a case portal where base-tier users miss the dashboard

Build a combined scenario that uses all three buckets. A services org runs Enterprise edition and wants external customers to open cases through a community and see a customer-facing dashboard of case status over time. The internal users hold full CRM licenses, and there is a small pool of Customer Community Plus logins plus a large pool of base Customer Community logins.

![A case portal scenario maps requirement to mechanism to license: opening cases through a community maps to an Experience Cloud community on Customer Community licensing, the case-status dashboard maps to reports and dashboards on the Customer Community Plus tier, a base Community user opens a case but sees no dashboard, so the org buys enough Community Plus logins or drops the reporting requirement.](</diagrams/day-35-i-2b-license-driven-design-scenarios-which-sharing-feat/4-case-portal-scenario.png>)

Step one, inventory: internal users are full CRM, external users split between base Community and Community Plus. Step two, map: the ability to open cases through a community maps to the Experience Cloud site and to Customer Community licensing, which covers case access. The dashboard maps to reports and dashboards, which are a Customer Community Plus capability, on the Community Plus tier. Step three, gap: a base Community user can open a case but cannot see the dashboard, because the dashboard surface is gated to the Plus tier. The org has two continuations: purchase enough Community Plus logins to cover every customer who needs the dashboard, or redesign so the external reporting requirement is dropped and base Community serves case access only. The base-tier alternative is valid only if the business gives up the dashboard; if it cannot, the purchase is the design answer. Step four, permission sets: a permission set that grants the dashboard's reporting surface must be license-compatible, Community Plus users inherit the entitlement, base users do not and assignment fails or hides it. Step five, validate: log in as a base user and a Plus user and confirm the base user can open a case but sees no dashboard while the Plus user sees both.

This scenario is the union of quiz question three and the exam's favorite complication: sharing-set-based access must be flagged as a licensing concern before design because sharing sets are an Experience Cloud feature requiring external-user licenses, so an internal-only org must buy those licenses to use them. The sharing-set-based access to the portal is the Experience licensing concern; the dashboard narrows within the Experience tier. Both are license constraints on the design, not sharing misconfigurations, and both must be resolved before the design is valid.[^3][^5]

## Feature-dependent sharing choices and the licensing consequence

The exam wants you to see one more class of decision: feature-dependent sharing choices, where the choice of an access mechanism itself carries a licensing consequence. A classic example is the portal-by-sharing-sets decision. Because record access for external users flows through sharing sets, which is a licensed Experience feature, an org with only internal CRM licenses cannot deliver partner portal access without purchasing Experience licenses. The moment the design decides to serve external users through a portal, the design has committed to Experience licensing, and that is a consequence the architect must name, not discover after the fact.[^3]

The same logic applies inward. A design that grants external users standard sharing through their portal tickets is committing to a tier that includes standard sharing, Customer Community Plus, not a tier that omits it. A design that uses Apex managed sharing to expose premium objects is committing to the users holding licenses that support those premium objects. The architect's discipline is to make every licensing consequence explicit at the point of mechanism choice, so that the design reads as a complete license plan rather than a sharing-rule list that silently outruns the org's entitlements.[^2][^6]

## Exam traps to avoid

![Three exam traps pull a candidate toward a license-free answer: assuming standard-object sharing features reach portal or limited-license users, proposing Shield encryption or audit without confirming the Shield license exists, and believing a permission set on an incompatible license simply needs to be re-assigned instead of securing the license that entitles the user.](</diagrams/day-35-i-2b-license-driven-design-scenarios-which-sharing-feat/5-exam-traps.png>)

**Trap: assuming standard-object sharing features are available to portal or limited-license users.** External features are Experience-licensed, and standard sharing mechanisms only reach users whose licenses carry them. When a scenario hands you portal users and standard sharing, the correct reading is that the portal is Experience-licensed and the portal tier decides the object and feature availability, not that the standard sharing model silently applies to every user regardless of license. Check the bucket before you apply the mechanism.[^3][^5]

**Trap: proposing Shield encryption or audit without confirming the Shield license exists.** Field Audit Trail and Shield Platform Encryption are compliance features gated on the Shield or Compliance license in Enterprise, Performance, and Unlimited editions, independent of the sharing configuration. A proposal that assumes encryption or five-year retention will just work is a proposal that skipped the license check. Confirm the Shield license before you design either feature.[^7][^8]

**Trap: believing a permission set on an incompatible license simply needs to be re-assigned.** A permission set on an incompatible license silently fails to grant the premium object or feature, and re-assigning it will not help, because the underlying user license is the binding constraint and feature gating blocks the incompatible grant. The fix is not another assignment; it is securing the license that entitles the user to the feature, by assigning the correct permission set license, not by repeatedly assigning a permission set whose entitlement the user does not hold.[^2]

## Try it yourself

In a scratch org, walk the design method on your own scenario. Create a set of users, some on full CRM licenses and some on a limited seat if your edition offers one, and define an access requirement, say partners viewing their accounts. Open Company Information in Setup and read which editions, user licenses, and permission set licenses the org holds. Map the requirement to the mechanism (an Experience Cloud site, a Share Set) and check the licensing documentation for the tier of Experience license that mechanism needs, then confirm whether your scratch org holds it or must be granted it. This is Bucket-one practice in one loop.

Next, prove the permission-set mechanic. Create a permission set that carries a gated premium feature and attempt to assign it to a user on a license that does not support it. Observe whether the platform errors at assignment or hides the feature at runtime, so you can predict which failure mode your own org uses. Then create the permission set associated with the correct permission-set license, assign that license, and confirm the difference in what the user can now reach.

Finally, test your diagnostic instinct in your own words. A requirements document asks for a five-year field audit trail on case data, and the org holds Enterprise without Shield. Name the license the requirement needs, the editions in which it is available, and what the architect must do before designing the retention feature. Then re-read the i-2b objective, map the requirement to its bucket, and run the two checks that tell you whether the design is license-complete: does the org hold the license each mechanism needs, and is every permission set license-compatible for the users it is assigned to. Each run makes the method a habit instead of a lookup.

## The design frame, in one screen

Keep requirement i-2b in one frame. Given a set of conditions, determine which sharing features are license-required and design within license constraints. Sort every requirement into three buckets: Experience Cloud covers external-user portal access, sharing sets, sharing groups, and guest-user sharing rules, and needs community licenses whose tier decides which objects and features external users reach; Shield and compliance covers encryption and extended audit retention and needs the Shield license independent of the sharing configuration; and standard sharing on full CRM licenses covers OWD, role hierarchy, sharing rules, manual sharing, and Apex managed sharing on standard objects. Run the method in order: document the license inventory, map each requirement to a mechanism and its license, flag any requirement whose license the org lacks and note the purchase or redesign, validate that the permission sets used are license-compatible for their assigned users, and re-test the solution under the actual license mix by logging in as a representative user of each type. Because record access for external users flows through sharing sets, an Experience-licensed feature, an internal-only org cannot deliver partner portal access without purchasing Experience licenses, and no permission set out-grants a user's underlying license. Match the feature to its license before you trust the mechanism, and the sharing solution you propose is one the org can actually run.[^1][^2][^3][^6]
