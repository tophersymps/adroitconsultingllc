Every lesson so far has assumed the data lives inside Salesforce as standard or custom records, governed by the sharing machinery you have spent thirty lessons mastering. Lesson 31 removes that assumption. This is the encore to objective o-1c, Access to Other Data, where the exam hands you a scenario and asks you to pick the right access control for data that does not live in an ordinary object at all. Big objects, external objects, and the audit and monitoring exposure are the three escapees, and answers them all with the same instinct you sharpened yesterday: these artifacts do not follow the record model, so you reach for their dedicated control, not the sharing machinery.[^1]

The trap that frames this whole lesson is the belief that everything that looks like a table of records is governed the same way. A big object holds billions of rows, yet it does not support org-wide defaults, sharing rules, or a role hierarchy. An external object exposes rows from a partner's system, yet the record inside it is not a Salesforce record at all, and Salesforce cannot enforce sharing it never owns. An event log is a record too, yet the log itself reveals query and access patterns that are more sensitive than the records it describes. And a report or dashboard that runs as a powerful user shows every caller data the caller would never see on their own. Four different escapees, four different controls, and one shared lesson: name what the artifact is, and the control that governs it follows.[^1]

## Define the terms

**Big object.** A Salesforce object optimized to store and query huge volumes of data, on the order of hundreds of millions or billions of records, in a horizontally scalable distributed database rather than the relational database that backs ordinary sObjects. Big objects exist to hold data you no longer work with transactionally: historical transaction logs, usage archives, customer 360 views assembled from external feeds, and audit history. The scale defines the object, and the scale also defines what it gives up: features like triggers, flows, processes, and the mobile app are not supported, and the full sharing model is not either.[^2]

**Object permission.** The profile or permission set grant that lets a user read, create, edit, or delete records of an object. For big objects this is the whole game. A big object supports object and field permissions and nothing more in the way of record-level control, so the decision about who can touch a big object is made at the object level, through profiles and permission sets, and the partition of what any one user can see is your job to design.[^2]

**External object.** An object whose record data is stored outside Salesforce, in an external system, and surfaced in real time through a web service callout. Each external object is tied to an external data source definition, which specifies how Salesforce reaches the external system, most commonly through the OData 2.0 or OData 4.0 adapter over Salesforce Connect. An external object behaves like a custom object to a user on the surface, but underneath it is a window onto data Salesforce does not own.[^3]

**External data source.** The definition that describes how to reach an external system: the adapter type, the service root URL, and the authentication. The authentication model is where a lot of the security story lives. A named principal applies one shared credential for every user in the org, while a per-user principal carries the external system's identity for each individual Salesforce user and requires that user to authenticate on their own.[^5]

**Restriction rule.** A filter you can apply to an external object record set so that certain users see only the external records essential to their work. Restriction rules work on external objects created with the OData 2.0, OData 4.0, and Cross-Org adapters, and they are an internal layer you control, distinct from the external system's own enforcement. They do not change the fundamental division of duties, which is that the external system owns record-level identity and you own who gets to query at all.[^4]

**Event monitoring.** The Salesforce capability that captures activity in event log files, each one keyed to an event type such as login, API calls, query runs, and Lightning component events. The logs are represented by the EventLogFile object, which holds encoded CSV data describing the activity, and they are consumed through the SOAP and REST APIs. Event monitoring data is the audit trail for your org, and it is sensitive by its very nature.[^6][^7]

**View Event Log Files.** The user permission that gates access to event log files. Reading the EventLogFile object requires View Event Log Files and API Enabled, and a user with View All Data can also read event monitoring data. This is the explicit, narrow gate the objective wants you to know: audit data does not ride along with a general "view reports" or "view dashboards" permission, it is its own named permission you grant deliberately.[^6][^7]

**Security Health Check.** A Setup page that scores your org's security settings against a baseline, the Salesforce Baseline Standard by default, and groups the settings into high-risk, medium-risk, low-risk, and informational categories. The score drops as you make settings less restrictive than the baseline, and the page is where you see at a glance whether firewall rules, session settings, password policies, and similar controls have drifted to risky values.[^8]

**Run-as context.** The identity under which a piece of Salesforce work executes. A dashboard can run as its creator, as another specified user, or as each viewer; a scheduled report runs as the user who scheduled it; an Apex class declared without sharing runs in system mode and ignores sharing rules the way the Modify All Data permission would. Anything a run-as context produces inherits the executing identity's data view, and that view can be far wider than the view of any single person who reads the output.[^9][^10]

**Without sharing.** The Apex class keyword that tells the platform to ignore sharing rules for code in the class, executing as if the context user held the Modify All Data permission. It is legitimate in a narrow set of design patterns, such as a privileged service that sandboxes its own object and field checks, and it is a standing exposure if you leave it on a class that ordinary users can reach. You pair it with explicit object and field security checks so the bypass is deliberate, not accidental.[^10]

## Why it matters for the exam and for real builds

Requirement o-1c wants you to look at a scenario, name the data artifact, and pick the control that actually governs it. The exam returns to a small set of scenarios, and each is designed to punish the reflex that reaches for the sharing machinery. A big object holds two years of historical transactions and an architect is asked how analysts should access it. An external object surfaces a partner's inventory and an architect is asked who enforces record-level access. A security team wants to know why audit logs must be locked down. And a dashboard shows every recipient more data than they are entitled to because it runs as a vice president. Each scenario has one correct control, and each is answered by remembering what the artifact is.[^1]

In production this is where least privilege quietly unravels. Record sharing can be perfect, and then a single system-mode Apex class or a single run-as dashboard re-exposes every record in the org to someone who should not see it. Big objects look like ordinary objects, so a well-meaning admin sets org-wide defaults on one and is surprised to learn there is no org-wide default to set. External objects look like custom objects, so an admin assumes the record-level rules they wrote for Accounts protect the partner's data too, when the partner's system is the only thing that actually filters rows. These failures are invisible to a record-level audit, because no record was ever shared; the leak happened on the object permission, the external system's trust boundary, or the run-as identity.[^1]

The exam also rewards knowing the defensive posture that runs through every detail. Treat big objects, external objects, and event logs as sensitive artifacts with explicit, narrow permissions. Question who can query the big object at all, question which users or services can reach the external object, question which admins can read the audit logs, and question every identity a report, dashboard, or Apex job runs as. The objective is not a set of one-off facts; it is a discipline for the data the sharing model cannot see, and it holds this lesson together. It is the framework you keep reaching for whenever a scenario names data that does not behave like a standard record.[^1]

## Big Objects are governed by object permissions, not sharing

Hold the scale and the access model together and the big object half of the objective falls into place. A big object stores massive data for high-performance queries, and to do that it drops the transactional machinery and the sharing machinery with it. The implementation guide is explicit: big objects support only object and field permissions, not regular or standard sharing rules. There is no org-wide default to set to Private, no sharing rule to write, and no role hierarchy to climb. Access is coarse by design, decided at the object level through profiles and permission sets.[^2]

This is exactly what question one in the quiz tests. The scenario is a big object storing two years of historical transaction logs for analysts, and the question is how access should be governed. The correct answer is object-level permissions via profiles and permission sets, because a big object does not support the full OWD, sharing rule, and role model of standard objects. The wrong answers are the reflexes: setting OWD to Private plus sharing rules, building a role hierarchy, or relying on manual record sharing, each of which assumes a sharing mechanism a big object does not have. When a big object is in the scenario, you reach for object permissions and you design your data partitioning yourself.[^2]

The phrase data partitioning is doing real work here, and the exam expects you to understand it. Because a big object cannot hide individual rows from individual users through sharing, the way you separate what one analyst can read from what another can read is to put the data in separate constructs, or to limit which users hold object permission at all, not to try to share rows within a single big object. A common pattern is to partition historical logs by business unit or by region into separate big objects, then grant each analyst group read access only to the big object that holds its slice. That is coarse-grained access turned into a deliberate design choice, and it is the correct big object answer where fine-grained sharing would be impossible anyway.

The other big object facts the exam leans on: there is no record-level access the way sObjects have it, so a query from a user with object read returns the rows the user's query asks for, bounded by the object permission rather than by per-row sharing. And the object and field permissions are still the entry gate, so the discipline is to grant big object read to the specific analysts who genuinely need the historical data, and to keep everyone else out entirely. Big objects earn their place by holding data you rarely touch, so the default should be that almost nobody can touch it at all.[^2]

## External Objects delegate record enforcement to the external system

External objects refract the sharing problem in a different direction. The record data is not in Salesforce, so the sharing machinery that would normally decide who sees which row has nothing to work on. What Salesforce controls is the object itself: the profile and permission set grants that decide who may query the external object at all, plus the external data source's authentication model, plus optional restriction rules. What Salesforce cannot control is which rows the external system returns for a given identity, because the external system is the only thing that knows the full record set and can filter it.[^3]

This is the heart of question two in the quiz. An external object surfaces data from a partner's system, and the question is who ultimately enforces record-level access to that data. The answer is the external data source's own authentication and authorization, with the internal external-object permissions gating who may query the external object at all. Salesforce org-wide defaults cannot secure data outside Salesforce, a sharing rule on an external object cannot create a row-level grant for rows Salesforce does not own, and a role hierarchy cannot climb to rows that live in the partner's system. If the partner's system returns a full inventory to whoever calls it, then your external object exposes a full inventory; no internal rule can retroactively hide what the external system already sent.[^3]

The design consequence is that you must design the trust boundary explicitly, and the exam wants you to think in two layers. Layer one is internal: the external object's profile and permission grants decide which Salesforce users and services may query it at all, and you grant that narrowly. Layer two is external: the external data source's authentication identifies the caller and the external system enforces whatever record-level rules apply to that identity. A named principal, one shared credential for every user, means every caller is the same external identity and the external system returns the same view regardless of who the Salesforce user is. A per-user principal means each Salesforce user carries their own external identity and the external system can return per-user records, which gives you a real path to record-level control but only if the external system actually enforces it.[^5]

Restriction rules add a layer you own, and the exam appreciates knowing they exist. You can set a restriction rule on an external object record set so certain users see only the external records essential to their work, with the rule driven by indexed external object fields. This gives record-level filtering on the Salesforce side for external objects created with the OData 2.0, OData 4.0, and Cross-Org adapters. The limits matter for the architect: only those adapters support restriction rules, and each rule evaluation can add a database call to the external system, which can add cost when the external source bills per call, so you weigh enforcement against the external system's bill and the added query latency. Restriction rules are a real tool, not a universal one, and they never replace the external system's own identity enforcement.[^4]

The way to think about the whole external object story: Salesforce controls the doorway and the external system controls the rooms. Salesforce decides who is allowed to knock at all, through profile permissions, and which visitors the org deems acceptable, through the authentication model and optional restriction rules. The external system decides what each visitor is allowed to see once inside, through its own authentication and authorization. Secure the doorway narrowly, choose an authentication model that matches the record-level granularity you need, confirm the external source enforces it, and do not assume an internal sharing rule can protect data you have never owned.[^3][^5]

## Event Monitoring and audit data are sensitive artifacts, not routine

The audit trail is where the discipline takes its sharpest turn, because here the security artifact is the data about the data. Event monitoring captures who logged in, what API calls were made, what queries ran, and how different components behaved, all in event log files exposed through the EventLogFile object. That log is itself sensitive: it reveals query patterns, data-access behavior, the volume of records someone pulled, and the identities doing it. If a log says a user downloaded your entire Account table every night, the log has just exposed a data-access pattern that is itself a vulnerability, whether or not the underlying Accounts were sensitive.[^6][^7]

This is why question three in the quiz asks why access to Event Monitoring logs must be tightly restricted. It is not because they consume storage, not because they are ordinary records, and not because they need sharing rules. It is because audit logs reveal query patterns and data-access behavior that is sensitive exposure in its own right, so access to them must be limited to designated admins and security analysts. The correct answer is the one that names the exposure: the log tells an attacker how the org uses its data, and a broad read of the audit trail leaks more about the org than any single record does.[^6]

The gate is a named permission, and the exam expects you to know it precisely. Reading event monitoring data requires the View Event Log Files user permission plus API Enabled, and a user with View All Data can also view it. There is no general-purpose "everyone who can view reports" path in; the object is gated behind a specific permission that an admin grants only to the people whose job is to analyze security and usage. The architect's move is to keep that permission on a short list, grant it through a permission set assigned to your security and analyst group rather than to a broad profile, and review who holds it on a regular cadence.[^6][^7]

Real-time and log-based event monitoring are both sensitive, and the control habit is the same: narrow. The EventLogFile object is read through the SOAP and REST APIs, which is how an external SIEM or a query tool pulls the logs, and every path into that data should route through the same named permissions. Confining event logs to designated admins and analysts is not an inconvenience; it is the point, because the audit trail is only trustworthy if the people who can read it are themselves trusted and few.[^6][^7]

Security Health Check rounds out the audit side of the objective. It is the Setup page that scores your org against a baseline and groups security settings into high, medium, low, and informational risk, and it is where the architect watches whether firewall rules, session settings, and password policies have drifted. Health Check is an admin tool, gated behind the View Health Check or Manage Health Check permissions plus Customize Application in some flows, so it sits in the same narrow class as the audit data. You review it as part of the same cadence in which you review who can query big objects, who can reach external objects, and who can read the event logs.[^8]

## Run-as exposure amplifies whatever identity executes

Run-as exposure is the fourth escapee, and it is the one that turns an otherwise-scoped identity into a broader one. Whenever a report, dashboard, scheduled job, or Apex class runs as a specific user, everything it produces carries that user's data view. If that user has broad access, the output carries broad access, and everyone who reads the output or calls the code sees the broadened view whether they are entitled to it or not. The UI is not the only surface that leaks; the running context is the surface, and the architect controls the context, not just the buttons.[^9][^10]

Question four in the quiz puts it plainly. A scheduled report or Apex job that runs as a high-privilege user can expose to its recipients and callers exactly that high-privilege user's data view, a broader data set than any single viewer would otherwise see. It is not nothing, not only the report's fields, and not only public data. The output inherits the executing user's access, full stop. A dashboard that runs as a vice president shows every viewer the vice president's view of every opportunity, and a scheduled report that runs as an admin emails the admin's view to a distribution list that includes people who should never see it.[^9]

The dashboard mechanism is a clean worked example. You edit a dashboard, open its properties, and under View Dashboard As you choose the running user. Running as Me shows every viewer the creator's access, so a viewer who can only see Canadian opportunities sees the creator's view, which might be every country. Running as Another person shows every viewer that specified person's data access, which can be wider still. Running as the dashboard viewer makes it a dynamic dashboard that shows each viewer data according to their own access, which is the least-privilege choice of the three. When a scenario asks how to stop a run-as dashboard from leaking, the answer is to change the running user to the viewer, or to run as a user with an intentionally narrow view, never to leave it on the broadest identity because it was convenient.[^9]

Apex is the code-side version of the same rule. A class declared without sharing ignores sharing rules and executes as if the context user held Modify All Data. A scheduled Apex job that runs without sharing, or a service class marked without sharing that an unprivileged user can reach through a flow or a trigger, runs with a broader view than the caller. The defense is to scope the running context to least privilege: keep without sharing off classes that ordinary users can reach, pair it with explicit object and field security checks when a deliberate bypass is required, and audit every scheduled job's executing user before it goes live. The same question you ask of a dashboard, who runs this and what do they see, is the question you ask of every piece of asynchronous and system-mode code.[^10]

## Configuring least-privilege access, step by step

Walk the configuration in order; each step produces the input the next one reads.

**Step 1: Grant big object object-level permissions to the specific analysts who need them.** From Setup, find the big object, open its profiles and permission sets, and grant read (and write only where genuinely needed) to the specific analysts and services that must query the historical data. Design the data partitioning before you grant: if the data must be separated by region or business unit, put each slice in its own big object or use field permissions, because you cannot fall back to sharing rules. Keep the grant list narrow, and keep everyone else out.[^2]

**Step 2: Configure the external object's profile permissions and verify the external source's authentication.** Grant the external object's profile and permission-set read only to the users and services that must see the external data. Then open the external data source and confirm the authentication model: a named principal means one shared external identity for everyone, while a per-user principal means each user carries an external identity the external system can enforce per-user. Confirm with the external system's owner that it enforces the record-level rules your trust boundary depends on, and add a restriction rule on the external object where record-level filtering on the Salesforce side is needed and the adapter supports it.[^3][^4][^5]

**Step 3: Enable Event Monitoring and grant access only to designated admins and analysts.** Turn on the event monitoring features, then grant the View Event Log Files permission plus API Enabled through a permission set assigned to your small security and analyst group. Keep it off broad profiles. Confirm which users hold View All Data, since that permission also opens event monitoring, and decide whether that is acceptable. Pull the event log files through the REST or SOAP API into your SIEM or audit tooling, and keep every route behind the same named permissions.[^6][^7]

**Step 4: Review Security Health Check and audit every run-as configuration.** Open Security Health Check in Setup, review the score and the high-risk settings against your baseline, and remediate the risky ones. Then audit every run-as path: each dashboard's View Dashboard As setting, the running user on scheduled reports, the executing user on scheduled jobs, and every Apex class declared without sharing. For each one, confirm the running context has least privilege, changing run-as dashboards to run as the viewer and moving scheduled work to a user with a narrow, dedicated view.[^8][^9][^10]

**Step 5: Test with a low-privilege user that nothing leaks.** Log in as a user with none of the special permissions and confirm that user cannot query the big object (no object permission), cannot reach the external object (no profile grant), cannot read event log files (no View Event Log Files, no View All Data), and cannot see broader data through any run-as report, dashboard, or Apex path. Confirm a run-as dashboard shows only the running user's allowed view to a low-privilege viewer, and confirm a without sharing class reached through a flow does not hand the low user data beyond their access. That single test proves the whole objective end to end.[^2][^6][^9][^10]

## Exam traps to avoid

**Trap: setting OWD, sharing rules, or a role hierarchy on a Big Object.** A big object does not support the standard sharing model. It supports object and field permissions only, so the correct control is object-level access through profiles and permission sets, plus your own data partitioning. Any answer that reaches for org-wide defaults, sharing rules, or role hierarchy assumes sharing a big object does not have.[^2]

**Trap: assuming an internal sharing rule can secure records in an external object.** External objects delegate record-level enforcement to the external data source. The external system's authentication and authorization returns the rows; your profile permissions only decide who may query at all. An org-wide default, a sharing rule, or a role hierarchy cannot hide external records the external system already returned, so design the trust boundary at the external source and secure the doorway with your own narrow object permissions.[^3][^5]

**Trap: treating event logs and run-as contexts as routine.** Event monitoring logs reveal query patterns and data-access behavior that is sensitive in its own right, so access must sit behind the View Event Log Files plus API Enabled permissions, assigned to designated admins and analysts. Run-as contexts execute with the executing user's broader view, so a dashboard that runs as a powerful user hands that view to every viewer and a without sharing class hands it to every caller. Control the running context to least privilege; broad access to audit data or a broad running identity is itself an exposure.[^6][^7][^9][^10]

## Try it yourself

In a sandbox, build the whole objective end to end. Create a custom big object, load a few historical records into it, and grant read only to one test group. Create a second group with no access, log in as a member of it, and confirm the big object tab and its records are absent without object permission, and confirm a member of the first group can query the records with no per-row sharing in place.

Then create an external data source with an OData adapter against a small test source and expose an external object. Grant read to one group and confirm the other group cannot query it, then confirm what record-level filtering actually happens depends on what the external source returns for the shared identity. Add a restriction rule on the external object if your adapter supports it and watch it trim the returned rows on the Salesforce side.

Enable event monitoring, grant View Event Log Files and API Enabled to a single admin, and confirm a user without those permissions cannot query the EventLogFile object. Then open your dashboard's properties, set View Dashboard As to run as a broad user, and log in as a low user to watch their view show the broad user's data, then switch the dashboard to run as the viewer and watch the same low user suddenly see only their own data. Each test turns one of this lesson's four escapees into something you have watched behave in real time, which is the fastest way to trust the design rules.

## The design frame, in one screen

Keep the four escapees straight and objective o-1c is half done. Big objects are governed by object permissions, not by OWD, sharing rules, or role hierarchy, because they do not support the standard sharing model, so grant object-level read to the specific analysts who need them and design your data partitioning yourself. External objects are governed by your profile permissions at the doorway and by the external data source's own authentication and authorization at the record level, because internal sharing cannot secure records Salesforce never owned, so secure the doorway narrow and confirm the external system enforces the record rules. Event monitoring logs and Security Health Check results are sensitive artifacts in their own right, gated behind the View Event Log Files and API Enabled permissions and confined to designated admins and analysts, because the audit trail reveals query and access patterns. And every run-as context, dashboard, scheduled report, scheduled job, and without sharing class, executes with the running user's broader view, so audit and scope each one to least privilege. Get these four right and the data outside the sharing model stays safe, even though no record was ever shared.[^1][^2][^7][^9]
