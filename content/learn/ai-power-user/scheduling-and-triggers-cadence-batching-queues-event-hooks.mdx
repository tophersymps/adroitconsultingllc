You have built the history of your workflow across the last few lessons. Lesson 9 gave you the changelog that records what changed. Lesson 10 gave you the testing that checks a change before it ships. Lesson 11 gave you the failure plan for when a run goes wrong. There is one thing left before your workflow is truly yours. It still only runs when you start it.

A workflow you have to remember to run is a workflow you have not finished building. You built it, you tested it, you planned for its failures, and then every Monday you open the tool and press start. That last step is the automation you forgot to automate. This lesson is about giving your workflow a rhythm so it runs the way it should, on your schedule, at the right pace, without you standing over it.

That rhythm has a name and a set of controls. Cadence is how often something runs. Batching is whether you process work one item at a time or in a group. A queue is how the workflow handles work that arrives faster than it can process. An event hook is what makes a workflow start on an event rather than on a clock. Together these four decide how your workflow lives in the day, and this lesson is about choosing them on purpose instead of accepting the defaults.

## Cadence: how often your workflow runs

Cadence is the schedule that decides how often a workflow runs. It is the answer to the question, how frequently does this need to happen. Daily. Weekly. Every hour. Every time something changes. The word comes from the idea of a beat, a regular pattern of timing, and that is exactly what cadence is for a workflow: the regular pattern you want your automation to follow.

For decades, scheduled computer tasks have been described with a format built for exactly this. Cron is a time-based job scheduler that runs jobs on a schedule you specify, and the schedule is written as a five-field expression that names the minute, the hour, the day of the month, the month, and the day of the week. [^1] You have almost certainly seen one of these without knowing what it meant, a string like `0 0 * * 1`, which reads, in plain language, as run at midnight on Monday. [^1]

You do not need to learn to write those expressions by heart. The five fields matter because they are the vocabulary of cadence. Any schedule you can imagine is some combination of those five: the minute, the hour, the day of the month, the month, and the day of the week. When a tool asks you to say how often something runs, it is almost always asking you to pick values for a few of those five. The skill is not memorizing the format. It is being able to say what you want in those terms: this runs every morning before the team starts, this runs on the last Friday of the month, this runs on the first day of every quarter.

![Reading a cron expression: the five fields of cadence are the minute, the hour, the day of the month, the month, and the day of the week, and the expression 0 0 * * 1 reads in plain language as run at midnight on Monday](</diagrams/scheduling-and-triggers-cadence-batching-queues-event-hooks/4-cron-five-fields.png>)

Here is the decision behind every cadence. A schedule is a promise that the workflow runs, but it is also a promise about how fresh its output needs to be. If a report feeds a decision that gets made every week, a weekly cadence is enough. If it feeds a decision made daily, weekly is too slow and daily is right. If the underlying thing changes rarely, a daily run just produces the same result over and over. The right cadence is not the fastest one. It is the one that matches how often the output actually gets used. Running more often than the decision needs does not make the output better, it just burns time and attention on runs nobody needs.

## Scheduled or triggered: two kinds of start

A cadence is one way to start a workflow, but it is not the only way. The line that matters most in this lesson is the one between a scheduled run and a triggered run.

A scheduled run starts on a clock. At this time, on this day, the workflow runs, whether or not anything changed since the last run. This is the cadence you just set. It is predictable, which is its strength. You know exactly when it runs, you can plan around it, you can check it after it runs.

A triggered run starts on an event. Something happens, a form is submitted, a message arrives, a file is added to a folder, a payment is received, and that event starts the workflow. It does not run because a clock said so. It runs because something actually changed. This is the difference between a workflow that checks on the hour whether anything is new and a workflow that starts the moment something is new. The first polls. The second gets told.

That second kind deserves its name, because it is the reason to use an event hook. In web development, a webhook is a callback you give another system, a way for one application to notify yours when a specified event occurs, usually by sending it a message over the web. [^2] The workflow does not need to check for changes. The other system tells it the change happened by firing the hook. You set the hook once, and from then on the event itself starts the workflow.

The practical difference shows up as speed and as waste. With a schedule, a new item that arrives one minute after a run waits until the next run, which could be a day away. With an event hook, it is processed the moment it arrives. With a schedule, the workflow runs at its fixed time whether anything changed or not, so a quiet day produces a run that finds nothing. With an event hook, a quiet day produces no run at all, because nothing triggered it. The event hook trades the predictability of the clock for the immediacy and economy of only working when there is actually work.

![Scheduled run versus triggered run: a scheduled run starts on a clock, is predictable, and polls, so a quiet day still produces a run that finds nothing, while a triggered run starts on an event, is immediate, and gets told, so a quiet day produces no run at all](</diagrams/scheduling-and-triggers-cadence-batching-queues-event-hooks/1-scheduled-vs-triggered.png>)

## Batching: one at a time, or all at once

Once a workflow starts, there is a second decision you make without always noticing: whether it processes work one item at a time or in a group. That is batching. In computing, batch processing is the running of a job in an automated and unattended way, often on a set schedule, handling a group of items together rather than interactively as each one appears. [^3]

Here is the trade you are really making. Process each item the moment it arrives, and you get immediate results but you pay the whole cost of a separate run for every single item. Wait and process several together, and you spread that cost across the group, but you get results in batches rather than continuously. If the work arrives steadily all day and each item matters the moment it shows up, item by item is right. If the work accumulates during the day and nobody reads it until evening, a batch at the close of the day is just as good and a lot cheaper.

Batch processing is where the fixed schedule from earlier meets the arrival of new work. A lot of the workflows you will build are naturally batch-shaped. You collect the week's vendor deliveries and process them on Friday. You gather the day's leads and qualify them overnight. You let the submissions pile up in a folder and run one pass over them at a set time. The schedule gives the batch its rhythm, and the batch gives the schedule its reason to exist.

The lesson is to pick batching on purpose. Do not default to item by item just because it is the tool's default, and do not default to a giant batch just because it is efficient. Match it to how the output is used. If a customer is waiting on the result of each submission, batch is a bad idea, because it makes every customer wait for the whole group. If the team reads the results once a day, batching is free efficiency. The question is never which is simpler. It is which matches the pace at which the work is actually consumed.

## Queues: when work arrives faster than you can process it

There is a stretch where batching and a schedule are not enough. That is when new work arrives faster than the workflow can process it, and a big pile builds up faster than you clear it. The name for that pile, and for the thing that handles it, is a queue.

A message queue is the name computer systems give to a store of work that is waiting to be processed. In its simplest form it is a line. Items are added to one end and taken off the other, in the order they arrived. Message queues exist to let a sender hand off work and a receiver take it and process it at its own pace, without the two having to be ready at the same moment. [^4] The sender does not wait. The receiver does not get flooded. The queue absorbs the difference between how fast work arrives and how fast it gets done.

The reason a queue matters for your own workflows is the thing that happens on a spike. Most of the time, work arrives at a pace the workflow handles easily. Then one day it does not. A form goes viral and two hundred submissions land in an hour. A promotion ends and the order volume doubles. A single tool update resends everything at once. If the workflow has no queue, that spike either gets processed all at once, which can break things, or some of it gets dropped. A queue says, no, the work can wait. It lines up, and the workflow works through it in order, at a pace it can handle, until the backlog is clear.

You have used this principle your whole life. The queue at the checkout works exactly this way. Customers arrive at any pace, but the cashier processes one at a time, and when a rush hits, the queue grows instead of the line collapsing. The same shape protects your workflow. When the tool presents batching or queueing options, what it is really offering is the difference between trying to process a spike all at once and letting the work line up and clear at a sustainable pace. Choosing the queue is choosing not to fall over when things get busy.

## The worked example: Priya gives her summary a rhythm

Priya is back from Lesson 11, where her monthly vendor summary survived a silent error, a hallucination, and a mid-flow break. She fixed all three and the summary is running. There is one problem left. It only runs because she starts it. Every month she opens the tool, runs the summary, and waits.

So this month she makes a deliberate set of choices about the rhythm, and each choice maps to one of the four ideas in this lesson.

Cadence first. Her summary feeds a monthly procurement review that the whole team attends on the first Tuesday. It does not need to run daily, because nothing about it is used daily. It does not help to run it hourly, because the source data changes weekly at most. So she sets the cadence to match the decision it feeds: she schedules it to run the morning of the review, a few hours before the meeting, on the first Tuesday of the month. She writes the schedule in the tool's calendar terms rather than a five-field string, but she is making exactly the cron decision: pick the day of the month and the day of the week and the time, and let the workflow handle the rest. The cadence is not the fastest it could run. It is the one that matches when the output gets used.

Batching second. Her summary covers a dozen vendors, and it processes each one. She has a choice: run twelve separate jobs, one per vendor, or one job that works through all twelve. The review does not read vendor updates as they happen. It reads them all together, in one report, at the meeting. So she batches. One run pulls all twelve vendors, processes them as a group, and produces a single summary. She is accepting that a vendor whose data updates on the third of the month sits in the summary until the review. That is fine, because the review is where the data gets consumed, and batching means she pays for one run instead of twelve.

Event hook third. Her procurement group gets new vendor contracts signed throughout the month, and right now a signed contract waits in a folder until the next monthly review. Some of those contracts have dates that matter within days. So she adds one event hook: when a contract file is added to the folder, a short workflow runs immediately to check the key dates and flag anything that needs attention before the review. This is a triggered run, separate from the scheduled one. It does not wait for the monthly cadence. The event itself starts it, the moment the contract lands. The schedule handles the monthly rhythm. The event hook handles the urgent arrivals. Both run, and each runs when it is needed.

Queue last. During a busy close-out, her group once uploaded thirty contracts in a single afternoon, and the per-item workflow that checks each one could not keep up. A couple got flagged late. She sets the checking workflow to process through a queue instead of trying to handle the whole pile at once. The contracts line up in arrival order, and the workflow works through them at a steady pace until the backlog clears, without a single one dropping. A rush that would once have overwhelmed the workflow now just grows the queue for an hour while it catches up.

At the end of the month she does almost nothing. The cadence ran the monthly summary. The batch processed the vendors as one job. The event hook caught the urgent contract the day it landed. The queue absorbed the busy afternoon. She set the rhythm once, she tested it the way Lessons 10 and 11 taught her, and the workflow now runs itself on a schedule she chose instead of a habit she had to remember.

## Define the cadence for your own workflow

Pick one workflow you actually run more than once, the same one you have been improving since Lesson 9. Give it a rhythm you choose on purpose, walking each of the four decisions. The prompt below turns the choice into words you can give a tool or use to set up the schedule in the tool you already use.

> I want to give my workflow a rhythm instead of starting it by hand every time. I will describe the workflow and how its output is used. Ask me four questions. First, cadence: how often does anyone actually read or use the output, and what day and time should the workflow run to feed that? Second, batching: does the output get consumed as an ongoing stream or as a periodic group, and should I process items one at a time or in a batch? Third, events: is there any input that cannot wait for the next scheduled run, and if so, what event should start the workflow immediately when it arrives? Fourth, queueing: if new input ever arrives faster than the workflow can process it, how should the extra work line up and clear without being dropped? Answer each with the choice that matches when the work is actually used, not the fastest option.

Run that once for the workflow you care about, and you will have set its cadence, its batching, its event hooks, and its queue, the whole rhythm, by answering four questions. The rhythm is what turns a workflow you run into a workflow that runs you, or rather, that runs for you.

*Note: cadence, batching, queues, and event hooks are patterns, not features of any one tool. Nearly every automation tool you use offers scheduled runs, a way to trigger a workflow from an event in another app, and a way to handle more work than the workflow can process at once, and they use different names for them (schedules, triggers, runs, steps, queues). The transferable part is the decision, not the interface: choose how often it runs, whether it runs on a clock or on an event, whether it processes one item or a batch, and how it handles a rush, so the workflow runs at the pace the work is actually used.
