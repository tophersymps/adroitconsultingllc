Lesson 3 gave you a four-part design for your task: input, tool, output, and review. You named the tool part, but you have not built it yet. This lesson is the build. It takes the tool part of your design and turns it into something concrete you control, so the next time you run the workflow the setup does the re-deciding and you do the reviewing.

The move here is straightforward and worth stating plainly. You want to stop telling the tool what you want every single time, and start telling it once. The way you do that is a custom tool: a saved setup inside a chat application that holds the instructions, the background, and the reference material your task needs, so each new chat starts already knowing the job.

## What a custom tool is

A custom tool is a saved, reusable setup inside a chat application. It is not a separate product and it is not code. It is configuration, the stuff the AI tool remembers so you do not have to repeat it. The exact name varies by vendor, and the labels matter less than the function, so resist getting married to any one app's terminology. The pattern repeats everywhere: you set it up once, and from then on the tool starts every conversation already carrying what you told it.

The OpenAI help center says it plainly for one popular implementation: custom instructions allow you to share anything you would like the chat assistant to consider in its responses, and your instructions are applied to all chats. [^1] Set them once, and they travel with you. The Claude help center describes the same idea another way: project instructions help the model understand the specific context and requirements for a particular project, and they apply to chats within that project. [^2] Same function, different name.

The important part is the pattern, not the label. Inside most chat tools you will find some version of three capabilities. First, a place to store standing instructions that shape how the tool responds. Second, a place to hold reference material, files, notes, or links the tool can consult. Third, a container, usually called a project, that keeps those instructions and that reference material together, so every chat in it starts the same way. Nail those three and the specific vendor is a detail.

## Why a custom tool beats retyping the same prompt

The case for building one is the same as the case for any workflow, which you met in Lessons 2 and 3. The work you do is often the same shape, and the shape is the thing you can automate. When you retype a prompt from scratch each time, you re-decide the prompt, the format, the tone, and the background every single week. You are remaking decisions you already made. A custom tool is the decision you make once and then stop making.

Marcus from Lesson 3 felt this immediately. His weekly status email had a fixed input, the week's numbers and notes, a fixed output, a short email with the sections his director expects, and a fixed review, check the numbers before sending. The only part he had not pinned down was the tool. He would paste "write my weekly status email, under 150 words, with what happened, what is at risk, and what needs a decision" every Monday, along with enough background for the tool to understand his project. Half of every prompt was context it should have already known. That is the waste a custom tool removes.

Build it right and you reach the same state Marcus is heading toward. The tool holds the standing instruction, the format, the tone, and his project's background. What he feeds in shrinks to just the week's fresh facts, the numbers and the notes. What comes out is a draft he reviews, the same workflow shape, but the re-deciding is gone.

## The three pieces of a custom tool

Every custom tool worth building has three parts, and they map to the words in this lesson's title: tailored instructions, saved context, and your own project.

![The three pieces of a custom tool: tailored instructions set the standing prompt, saved context holds the reference material, and your own project is the container that holds them together so every chat starts the same way](</diagrams/building-a-custom-tool-tailored-instructions-saved-context-your-own-project/1-three-pieces.png>)

**Tailored instructions.** This is the standing prompt, written once and saved. It tells the tool how to behave for your task: the format, the length, the tone, the sections, the things to always include and the things to avoid. The OpenAI help center describes these as instructions applied to all chats, and notes that changes you make apply to future conversations, meaning the saved instruction is a living document you can refine. [^1] Tailored means it is written for your task specifically, not a generic "be helpful" line. It is the tool part of your four-part design, set down in words.

**Saved context.** This is the reference material the tool can consult. Your task almost never starts from nothing. You have files, past examples, notes about how your team communicates, a list of the jargon that matters, a template you like. Claude's project feature calls this the project knowledge base, and the support docs say anything you add to it is used as context across chats in that project. [^2] Saved context is what makes the tool feel like it knows your world instead of meeting it fresh each time. It is the answer to "why do I have to re-explain my department every Monday."

**Your own project.** This is the container that holds the first two together. A project is a bounded space where each chat starts with the same instructions and the same reference material, so every conversation in it is a fresh run of the same workflow rather than a meandering one-off. The Claude support docs describe project instructions as working alongside a project knowledge base, both present across the chats in that project. [^2] The project is what makes the setup repeatable. It is your four-part design made into a place.

None of this requires you to know which vendor you will use, and you should not decide that yet. The pattern is the point. You want standing instructions for your task, reference material your task needs, and a container that holds them together. Whatever chat tool you already use, it almost certainly supports some version of all three.

## A worked example: Marcus builds his tool

Marcus's design from Lesson 3 was: input the numbers and notes, tool his chat with a saved instruction, output a short status email with the three sections, review the numbers before sending. Lesson 4 is where the tool gets built, and he does it by writing the three pieces.

![Marcus's weekly status flow: the week's fresh facts go into his custom tool, which produces a status email draft under 150 words, and he checks the numbers against his notes before sending](</diagrams/building-a-custom-tool-tailored-instructions-saved-context-your-own-project/3-marcus-flow.png>)

**His tailored instructions.** He writes one block of standing instructions, short and specific, that says roughly this: I draft a weekly status email to my director. Keep it under 150 words. Always include these sections: what happened this week, what is at risk, and what needs a decision. Use plain, direct language. Flag anything that needs my decision clearly so I can check it. Do not invent numbers that are not in the inputs I give you; if a number is missing, say so instead of guessing. That instruction is the whole tool part of his design, written down, and it will never need to be retyped.

**His saved context.** He uploads three things once: a recent example of a status email his director liked, so the tool knows the house style; a short note explaining what the project is and who the key stakeholders are, so he stops explaining his department every time; and his current program tracker overview, so the tool can make sense of the numbers he pastes each week. From then on, every new chat in the project starts knowing his world. [^2]

**His project.** He creates a project named after the workflow, his weekly status, and puts the instructions and the reference files inside it. (His tool's docs call the project knowledge base the space where uploaded content is used across all chats in the project, which is exactly the behavior he is after. [^2]) Each Monday he opens the project, pastes only the week's fresh numbers and notes, and gets a draft in the right shape. The review is unchanged: he checks the numbers against his notes before sending, the same human-in-the-loop check from Lesson 3. [^3]

The difference lands hard. Before, his Monday prompt was half context and half request, and the output still came out generic because the tool did not know his project. Now the tool starts knowing the instructions, the style, and the background. What he types each week is a sentence or two of fresh facts. The output is shaped, and the review catches what the tool still gets wrong, because it will still get some things wrong. That is the design.

## Where to go from here

Two notes before you build your own.

First, a custom tool is not a magic button. It is the tool part of a flow that still ends in your review. You built it to save the re-deciding, not to remove the checking. Conveying the tool has your instructions memorized just means it makes better drafts faster, it does not mean it stops making mistakes. Keep the review. [^3]

Second, the tools themselves change fast, and features get renamed, moved, or retired. The concrete names and buttons in this lesson could be different by the time you read it, and your company may have its own data and acceptable-use policies that are more restrictive than the defaults. Treat those as the binding rules, check your tool's current documentation, and build the pattern, instructions, context, project, using whatever your tool actually offers today. The pattern is what transfers.

## Try it

Take the tool part of your Lesson 3 design and build your own custom tool. Give yourself twenty minutes, more if your task needs reference material.

First, write your tailored instruction. On a blank note, answer these in a short block: What is the task the tool should run? What does the output need to look like, the format, the length, the sections? What tone should it use? What must it never do, for example, invent numbers or skip the risk section? What should it flag for your review? The OpenAI help center's description is the model to hold: your instructions are applied to all chats, so write them as the standing contract you want every run to follow. [^1]

Second, collect your saved context. List the reference material your task needs: a past example it should imitate, a note about your project or audience, a template, a glossary. Gather the two or three most useful things and add them to your project's knowledge base, using whatever your tool calls that space. [^2]

Third, create the project and put both pieces inside it, then run your workflow once for real. The output is a contract with yourself. You can write it with any chat tool you already use, and if your tool does not have a project yet, keep one note with your instruction and another with your context, and paste both at the top of a fresh chat. The container matters, but the pieces matter more.

## What's next

You have built the tool part of your workflow: tailored instructions, saved context, and a project of your own that holds them together. That was the leap from decomposing a task to turning it into something you control, and the setup now does the re-deciding while you keep the review.

The next lesson turns outward. Where you have been building one self-contained tool, Lesson 5 is about connected tools, stitching the apps you already use into one flow. The pattern is what you have been doing this whole time: fixed inputs, a tool, an output, a review, but now the tool hands off to the next app in the chain instead of stopping at the chat window. It stays tool-agnostic, teaching the handoff pattern rather than any one vendor's buttons, because the idea of one app feeding the next transfers no matter what you use.

Come to the next lesson with the custom tool you just built, because it is the first link in those chains. A connected flow is only as good as the tools it connects, and you now have one that is worth connecting.
