Lesson 10 gave you the routine to catch a bad output before it ships. Dry run, probe the edges, read the result like a critic. That routine is real and it works. It is also not a guarantee. No amount of testing makes failure impossible, because the failures that matter most do not announce themselves. A step fails and the workflow keeps going as if nothing happened. The tool produces a confident answer that is simply wrong. The automation stops halfway and leaves the job half done with no one the wiser.

This lesson is the plan for those moments. It is not about preventing failure, which you already started in Lesson 10. It is about handling failure when it happens anyway: recognizing the three ways a workflow can go wrong without telling you, and knowing what to do in each case. The skill here is not optimism. It is the opposite. It is assuming the workflow will fail, deciding in advance what you will do, and making the failure cheap to find and cheap to fix.

## A silent error: the failure that never tells you

A silent error is the most dangerous kind, because it does not look like a failure at all. The Ministry of Testing defines a silent failure as a situation where a system fails to behave as expected but does not surface any visible error, alert, or warning. [^1] The program does not crash. No error message appears. The workflow runs to completion and reports success. It just did not do the thing it was supposed to do.

The defining feature is not the bug. It is the absence of signal. A loud failure, a crash, an error message, is unpleasant but legible. You know something is wrong and you can go look. A silent error is the same problem minus the announcement. The report gets written, but with the wrong number. The email gets sent, but to the wrong list. The file gets saved, but with last month's data. Everything looks healthy from the outside, and the only way you find out is when the wrong result reaches someone who notices.

This is why the testing routine from Lesson 10 matters so much. A silent error is exactly the failure that a dry run and a critic's read are built to catch, because they check the output against what it should be, not against whether the tool reported success. The tool will tell you it succeeded. The question is whether the output is actually right.

## A hallucination: the confident wrong answer

A hallucination is a specific kind of silent error, and it deserves its own name because it is so common in AI tools. In the field of artificial intelligence, a hallucination is a response that presents fabricated information as fact. [^2] The term has been used since at least 2021, when Meta warned that its chatbot was prone to "confident statements that are not true." [^2] That phrase is the whole problem in four words. The output is not hesitant or uncertain. It is confident, smooth, and wrong.

The practical shape of a hallucination is what makes it dangerous. A large language model may embed plausible-sounding random falsehoods within its generated content, such as fabricated citations. [^2] That is the signature move. The tool does not produce a page of nonsense. It produces a page that reads perfectly, with a citation to a source that does not exist, a quote that was never said, a statistic that was never measured. The structure is flawless. The content is invented.

This is why the critic's check from Lesson 10 is not optional. A hallucination is designed to pass a casual read. It only fails when you check the specific claim against something you can verify, the actual source, the actual number, the actual date. The model's confidence is not evidence. It is the tell.

## A mid-flow break: the tool that stops partway

The third failure is different from the first two. A silent error and a hallucination are about wrong output. A mid-flow break is about no output, or half of it. The workflow starts, does some of its steps, and then stops. The tool times out, the connection drops, the source app is unavailable, the run is interrupted. The job is left half done, and depending on the tool, it may or may not tell you.

The danger of a mid-flow break is not the break itself. It is what happens when you retry. If the workflow already did half its work, running it again from the start can duplicate the part that finished. The software world has a name for the property that prevents this. An idempotent operation is one where a request can be retried with no additional side effects, so that the result happens only once even if the call is made multiple times. [^3] AWS describes this as the simplifying assumption that any error that is not a validation error can be overcome by retrying until it succeeds, without creating a duplicate. [^3]

You do not need the jargon. You need the question it answers. When a workflow breaks mid-flow and you run it again, does the second run make things worse? If the first run already sent the email and the second run sends it again, you have a problem. If the first run already posted the update and the second run posts it twice, you have a problem. The fix is to make your workflow safe to re-run, so that a retry finishes the job instead of doubling it.

## The worked example: Priya meets all three failures

Priya is back from Lesson 10, and her monthly vendor summary is running clean. She dry-runs it, probes the edges, reads the output like a critic, and it has shipped on time for two months. Then, in the space of one week, all three failures show up, and each one teaches her something different.

The first is a silent error. She runs her summary and the tool reports success. The output looks normal. But she has made the critic's read a habit, so she checks the headline total against her column, and it is off. Not by much, a few hundred dollars, but off. Nothing flagged it. The tool said it succeeded. The number was simply wrong, and only her check caught it. She traces it to a source file that updated late, so the tool pulled a stale version of one vendor's numbers. The fix is a check that the source file is current before the run starts.

The second is a hallucination. She asks the tool to add a short section on a new vendor she is considering, and the tool writes a confident paragraph about the vendor's track record, complete with a citation to a case study. She has learned not to trust the citation, so she clicks it. The case study does not exist. The vendor's actual track record is thinner than the paragraph suggested. The tool invented the support. She rewrites the section from the vendor's real materials and adds a standing instruction: never cite a source you cannot verify.

The third is a mid-flow break. She sets the summary to run overnight, and in the morning she finds it stopped partway. It pulled the data and drafted the report, but it never sent it. The tool logged a timeout, but nothing reached her. She re-runs it, and this time she watches. The re-run does not duplicate the draft. It picks up where it stopped and sends. The tool was built to be safe to re-run, so the retry finished the job instead of doubling it. She adds one habit to her routine: after any overnight run, check that it actually completed, not just that it started.

Three failures, three lessons. A silent error taught her to check the source is current. A hallucination taught her to verify every citation. A mid-flow break taught her to confirm a run finished, not just that it began. None of them stopped her workflow. Each one made it a little more honest about what it actually did.

## A failure plan for your own workflow

You cannot predict which failure will hit, but you can decide in advance how you will respond to each of the three. That is the whole of handling failure. It is a short plan you write once and reuse, and it fits around any tool you already use.

Step one, name the silent errors. For each step in your workflow, ask what it means for that step to fail without telling you. A summary that pulls stale data. An email that goes to the wrong list. A file saved with the wrong version. Write down the two or three you most fear, and for each one, name the check that would catch it. The check is usually a number you can verify or a source you can confirm is current.

Step two, name the hallucination risk. For any step where the tool generates text, decide what you will verify before you trust it. The citations, the numbers, the names, the dates. Pick the specific claims that matter and make verifying them part of the run, not an afterthought.

Step three, make the workflow safe to re-run. Before you rely on a workflow that can break mid-flow, test what happens when you run it twice. If the second run duplicates the first, fix that before you trust it. A workflow you can safely re-run is a workflow you can recover.

![The three-step failure plan: name the silent errors, name the hallucination risk, and make the workflow safe to re-run](</diagrams/handling-failure-silent-errors-hallucinations-tools-that-break-mid-flow/3-failure-plan.png>)

Below is a try-it prompt you can adapt to write a failure plan for one of your own workflows. It turns the plan into words you give the tool, which forces you to think through the failures before they happen.

> You are helping me write a failure plan for a workflow. I will describe the workflow and its steps. For each step, tell me three things. First, how could this step fail without telling me, and what check would catch it. Second, if this step generates text, what specific claims would I need to verify before trusting it. Third, if this step stopped halfway, would re-running it make things worse, and how could I make it safe to re-run. Do not reassure me. Assume the workflow will fail and tell me exactly how I would find out and what I would do.

Run that once for a workflow you actually use, and you will have a plan for the failures before they happen. The plan is not paranoia. It is the difference between a workflow that surprises you and a workflow you can recover.
