Here is the moment that separates a trusted workflow from a risky one. You set up a process. It has run clean for weeks. Then one week it does not, and you do not find out right away. You find out later, when the number is already in someone's inbox, or the email already went out, or the calendar already filled with the wrong times. The workflow did not fail loudly. It failed quietly, producing output that looked normal and was simply wrong.

Nobody enjoys that discovery, and the usual reaction is to blame the tool or to blame yourself for trusting it. Both miss the point. The mistake was not the bad output. The mistake was that the output reached anyone before you checked it. A reliable workflow is not one that never makes mistakes. It is one you test before it acts for real, so that a mistake in week four is caught in week four, on your desk, not in someone else's calendar.

This is the missing skill between the last lesson and the next one. Lesson 9 gave you a record of changes so you can diagnose a failure after it happens and undo it. This lesson gives you a way to catch a bad version before it reaches anyone. It is the skill of testing your workflow: running it somewhere safe, poking at the awkward inputs, and reading the output like something that might be lying to you. Do this and you stop discovering your mistakes later, in front of other people, and start catching them first, alone.

## What testing means for a workflow

Testing, in the classic sense, is the process of evaluating and verifying that something works correctly, securely, and efficiently according to its requirements. [^2] That general definition transfers cleanly to a workflow you built. You are not running a software test suite. You are asking one question: does this process do what I intend before I let its output do anything?

The software world found, the hard way, that testing belongs early and often, not as a single gate at the end. IBM's own guidance puts it plainly: testing is no longer a final step before release, it begins at the design phase and continues after deployment. [^2] The reason matters more than the phrasing. If you wait until the end to check, checking is expensive and easy to skip when you are tired or in a hurry. If you test as part of every run, checking becomes a reflex, not a chore.

So testing is not a phase you bolt on. It is three small habits you do every time you run a workflow: run it in a safe mode first, push the edges of what you feed it, and read the output as if it might be wrong. Each one catches a different class of problem, and together they are cheap enough to actually do.

## A dry run: run it somewhere safe first

A dry run is a run of a workflow that looks at what it would produce and do, without actually doing it. It is the rehearsal before the performance. Adobe's journey tool describes its dry-run mode exactly this way: it executes the journey against real production data without sending any communications or updating any profile information. [^3] Strip away the specifics and the pattern is universal. A dry run uses your real input, produces the real output, and then stops before anything reaches the outside world. Nothing is sent, nothing is changed, nothing is scheduled. You get to see the result with none of the consequences.

Why is that so powerful? Because most of what a workflow does is invisible until you hold the output in your hands. The tool does not tell you "this report has a wrong number" and it does not catch "I sent the email to the wrong address." A dry run lets you see those before they matter, with the stakes still at zero.

Every automation tool in your life offers some version of this, even if it calls it something else. A draft is a dry run of an email. A preview is a dry run of a document. A test send is a dry run of a campaign. A "check your work" pass before you submit is a dry run of a delivery. The feature is hiding right where you already work. The skill is making it the default, not the extra step you take when you remember.

The habit to build is boring and powerful: before a workflow sends, posts, schedules, or changes anything, run it in a mode where it does none of that, and look at the output. What you are buying is the chance to be wrong without anyone else ever knowing.

## Edge cases: the inputs that break a well-behaved workflow

A dry run catches the mistake that is already there. Edge cases help you find the mistake that shows up only under the right awkward conditions. An edge case is a problem that occurs only at an extreme operating parameter, the boundary of what a process can handle, rather than in its normal range. [^1] Wikipedia's example is a stereo that plays fine at normal volume and distorts at maximum. [^1] The workflow behaved. The input did not.

Common edge cases are not exotic. Wikipedia lists unreliable user behavior, limited coverage, and product complexity as recurring causes, and the everyday examples are things you have already seen: a field left empty, a number that is unexpectedly large or small, a name that is unusually long, a date like February 29, a source that comes through blank or with the columns in the wrong order. [^1]

For an AI workflow, the classic edge cases are the ones that make the tool fill in the gap confidently. An empty input, so the tool invents content rather than flagging that nothing was provided. A tiny sample, so the tool generalizes from one row. A missing value inside the data, so the tool quietly skips it and the total comes up short. A brand-new acronym that is not in its background, so it guesses the meaning. None of these will announce themselves. Each produces output that looks fine unless you feed the awkward input deliberately and watch.

The thinking behind edge cases transfers direct from software: if it behaves correctly at the edges, it should behave everywhere in between. [^1] This is the reason testing just the happy path, the normal input where everything is in order, is not enough. The happy path is where a workflow always behaves. The edges are where it breaks. So test the edges.

## What "bad output" looks like

You can dry run and probe edge cases all day and still miss the bad output if you do not know what to look for. Bad output from an AI workflow is rarely obviously wrong. It is wrong the way a confident person can be wrong, smooth and plausible right up to the fact that does not survive a second look.

Here is the list worth running down every time, because it maps to the failures that actually bite.

Numbers in the wrong place first. A total that does not add up, a figure pasted from the wrong month, a count that is off by one. Numbers are the fastest thing to check and the easiest to trust without checking, which makes them the most dangerous.

Invented support. A citation to a source that does not exist, a quote that was never said, a fact stated with no foundation. This is the signature failure of a fluent model, and the only defense is to check the specific claim against something you can verify, never to take it on the model's confidence.

Tone that drifted. The output says the right things in the wrong voice, hedged where you wanted direct, cheery where you wanted serious, corporate where you wanted plain. It is not a factual error, but it is still a quality failure that will embarrass you after it ships.

A placeholder waiting to be caught. A field that was supposed to be filled with real data and got a stand-in, a fake example standing in for the real one, a bracketed [insert here] that was meant to be replaced.

And the sneakiest one, the confident empty. The output looks complete but a section is factually empty, padded with agreeable filler because the input gave the tool nothing specific to do. This is the one Lesson 9's Priya saw in her vendor report, and it is the one you will miss unless you read for what is not there.

The discipline that catches all of these is the same: read the output like a critic, not a friend. Assume it could be wrong and look for where. You are not being paranoid, you are being the human the workflow depends on.

## The worked example: Priya catches a wrong total before it ships

Priya is back from Lesson 9, still running her monthly vendor summary. She fixed the version problem, moved the overdue flag back where it belonged, and her changelog is clean. This month she decided to do the other half of the job. Instead of regenerating and sending, she tested the workflow first.

Her tool offers a draft mode that produces the full output without sending anything. That is her dry run. She runs it with this month's real numbers and reads the result the way she now reads everything: looking for where it could be wrong.

The draft looks right at a glance. Clean structure, correct tone, the overdue flag back in place. She checks the headline total first, because she learned that lesson the hard way. She adds the line items in her head, then adds them on paper, then adds them a third time in the spreadsheet. The total in the draft is three hundred and forty dollars short of what her column adds up to.

Nothing flagged it. The draft presented the wrong total with complete confidence. A submission without checking would have shipped that number to procurement, and the correction would have been someone else's problem two weeks later.

Priya goes hunting for the cause, and this is where edge cases pay for themselves. She re-runs the dry run with this month's data slightly changed, and she tries the awkward versions of her inputs. A month with no overdues. A month with an unusually large line item. A vendor name that is long and oddly formatted. The third run cracks it. One of her vendor rows this month has a description field with a long, hyphenated name, and the tool truncates that line at the hyphen and drops the tail of the amount, so the row total comes in under. The edge case, an input longer than the tool's comfortable range, is what broke the total.

The fix is one line in her prompt: instruct the tool to preserve full vendor names and never truncate a line, and to note if any platform truncates a field. She adds it, dry-runs again, and the total matches her column. Then she lets it run for real.

![Priya's testing routine: a dry run shows a total three hundred forty dollars short, probing edge cases reveals a hyphenated vendor name truncates the line, a one-line prompt fix resolves it, and the total matches before it ships](</diagrams/testing-a-workflow-dry-runs-edge-cases-catching-bad-output/3-priya-example.png>)

Two dry runs and three awkward inputs later, Priya has caught a wrong number that would have shipped, found the exact input shape that causes it, and fixed the instruction so it does not recur. That is the whole value of testing compressed into one afternoon, and it leans on work she already did. The dry run showed her the wrong total at zero cost. The edge case showed her why. The instruction fix, logged in her lesson-nine changelog, means the whole class of problem stops happening.

## A check-before-you-trust routine for your own workflow

You do not need a testing department. You need a short routine you actually run. Here is one that fits around a tool you already use, whether it drafts, summarizes, schedules, or posts.

Step one, find the dry run. Locate the safest mode your tool offers, the draft, the preview, the test send, the sandbox, whatever stops output from reaching anyone. Make it the default way you run the workflow.

Step two, name your edges. For the inputs your workflow takes, write down the extremes you know could occur: an empty field, a huge number, a tiny number, a blank column, a long name, a missing value, a date that is not a normal date. Pick three of them.

Step three, run the edges. Feed your workflow its real input, then feed it a couple of the awkward inputs, and watch what changes in the output. Whatever breaks, that is your edge case, and it tells you what to add to your instruction.

Step four, check like a critic. Before the output ships, verify the specific claims you can verify: the numbers, the names, the dates, the citations. Read for tone drift and for the confident empty. Treat the output as unverified until your checks pass.

Below is a try-it prompt you can adapt to wrap your own tool in this routine. It turns the check into words you give the tool, which keeps you honest about doing it.

> You are testing a workflow before it ships. Run it twice. First, produce the output for my real input and flag anything that looks wrong or unsupported, especially sums, names, dates, and citations. Second, I will give you an edge-case input that is deliberately awkward, an empty field, an all-capitals string, a number with no decimal, fill one in. Show me what changes and where the output breaks. Do not smooth things over. Point out every place the output could be wrong before I trust it.

Run that once for real, once for an edge case, and you have done more testing than most people who trust a workflow. The slope from there is gentle. You learn your workflow's edges over time and you approach its output with a critic's eye every single run.
