Lesson 13 put a human in your workflow at the moments that matter. You paused the process where the cost of a miss justified it, and you let the steps without consequences run untouched. The review gate is the discipline around the output. This lesson looks one level deeper, at the words you feed the tool. Because a workflow is only as good as the prompting that drives it, and a prompt is only as good as how well it survives being changed.

The idea to hold onto is this: a prompt is a written thing you will edit. You will add a rule next month when the tool gets something wrong. You will remove a rule when the process changes. You will hand the prompt to a teammate or, six months from now, to yourself. A prompt that gets edited and reused is no longer a throwaway message. It is an artifact a future reader must understand, which is exactly what code is, and it deserves the same care a developer gives a file they know they will maintain.

## What it means to treat a prompt like code

Treating a prompt like code does not mean learning a programming language. It means borrowing three habits from people who write code, because code has the same problem a prompt has: it is written once and read many times, by machines and by the people who come after. The three habits are structure, maintainability, and comments.

Structure is how you divide the prompt into clear, labeled parts so a reader can tell what is instruction, what is context, and what is data. Maintainability is the property that lets you change one part without damaging the others, that a single edit does not quietly break the whole thing. Comments are the notes you leave in the prompt that explain why a rule is there, not just what the rule says.

These three are really one idea seen from three angles. A prompt with no structure is hard to maintain because you cannot see which part does what. A prompt with no comments is hard to maintain because when you return to it you no longer remember why a strange rule exists. Structure, maintainability, and comments are the same care applied to different surfaces, and together they decide whether a prompt is a liability you have to reverse-engineer or a tool you can pick up and change in seconds.

![Three habits, one idea: structure, maintainability, and comments each make a prompt you can read and change, instead of a liability you have to reverse-engineer](</diagrams/treating-prompts-like-code-structure-maintainability-comments/1-three-habits.png>)

The payoff is not cosmetic. OpenAI now tells developers to keep their production prompts in application code instead of as isolated prompt objects, so that the prompts get the same typing, code review, tests, and deployment process as the rest of the software. [^2] Development teams do this because they learned the hard way: unmanged prompts drift, nobody notices which version is live, and changing one silently breaks another part of the system. Your personal workflow is not a production system, but the failure is identical. A prompt you cannot read, you cannot change. A prompt you cannot change, you cannot maintain.

## Structure: divide the prompt into parts a reader can parse

The first habit is structure, and the move is to separate the different kinds of content in your prompt so nothing is ambiguous. A well built prompt has discernible parts: the role, the task, the instructions, the context, and the variable input. When these are all run together in one undifferentiated paragraph, your tool has to guess where one ends and the next begins, and your reviewer has to do the same.

Anthropic's guidance makes the separation explicit. Use XML tags to mark the parts of a prompt, so the model can tell instruction from context from input, and show the prompt to a colleague with minimal context to see if they could follow it. [^1] The two halves of that advice work together. Tagging the parts tells the machine which text is a rule and which text is tonight's data. Showing it to a reader tells you whether the structure is actually legible to the humans who also have to use it.

The mechanism does not have to be XML tags. LaunchDarkly's practical summary of prompt structure is that you separate your request into sections with delimiters, simple lines, quoted blocks, or named sections, number your steps for anything more than a trivial task, and state the exact output format you want. [^3] The delimiter is just a signal, and what matters is that the signal is consistent and visible. Three dashes, a quoted section, a heading. You pick a marker and use it the same way every time.

![A structured prompt divided into labeled sections, role, task, instructions, context, and variable input, so the model and the reader can parse each part](</diagrams/treating-prompts-like-code-structure-maintainability-comments/2-structured-prompt.png>)

The structure serves the machine and the human at once. The tool reads the section breaks to know what is instruction and what is data, which reduces exactly the failure the earlier lesson on templates warned about, the model treating your variable input as a rule to follow rather than material to process. [^7] And you read the same section breaks to know where to make an edit without re-reading the whole prompt. A structured prompt is not prettier. It is easier to change correctly, which is the definition of maintainable.

## Maintainability: build it so one change does not break the rest

The second habit is maintainability, and it is about the relationship between the parts. A prompt is maintainable when a single, small edit does not silently damage the rest. The fatal opposite is the fragile blob, the whole prompt as one long wall of text where every rule is entangled with every other, so that touching any part means worrying about the whole.

The warning sign is coupling. When the same fact, a tone, a format, a constraint, appears in three different sentences scattered through the prompt, you have coupled the rules. Changing the tone means finding and editing all three places, and if you miss one, the prompt now contradicts itself in a way that only shows up in the output. Maintainable prompts state each rule once, in one place, so an edit has one target.

![The fragile blob entangles every rule with every other, while a maintainable prompt states each rule once with the variable input in its own slot](</diagrams/treating-prompts-like-code-structure-maintainability-comments/3-fragile-vs-maintainable.png>)

Maintainability also means keeping the versioned, replaceable parts separate from the stable parts. The variable input, this week's numbers, this project's details, should sit in one clearly marked slot, not woven through the instructions. The stable parts, the role, the rules, the format, should be the frame that stays put. When you update the workflow, you change the frame in one place and leave the slot alone. When you run it, you drop fresh material in the slot and touch nothing else. This is the same division the templates lesson built, and here it is doing double duty as a maintenance pattern: the separation that makes a prompt reusable is the same separation that makes it editable.

OpenAI frames this as a discipline worth borrowing from software. Keep the prompt builder in a small module near the feature it supports, version the prompt in code, and add representative fixtures, tests, and evaluation checks before you change a production prompt. [^2] The point for your own workflow is not to adopt the machinery. It is the habit underneath: before you change a prompt that is working, you should be able to say what the change is for, and you should have a way to tell whether the change made things better or worse. The versioning lesson in this course gave you the record-keeping. This lesson gives you the reason the record matters, so you can tell what changed and why it went wrong, which is impossible with a prompt that is one unlabeled blob.

## Comments: record why, not just what

The third habit is comments, and it is the one people skip because it feels like extra work on top of work. A comment is a note you leave in the prompt that explains why a rule exists. The instruction itself says what to do. The comment says why you made the model do it, which is knowledge that will be gone in a month if you do not write it down.

The failure comments prevent is the one where you inherit a rule and do not dare remove it. Months go by, you or a teammate add a line to the prompt, and nobody remembers that one of the constraints exists because of a specific incident, an output a client flagged, a format a downstream step could not read, a tone a sponsor disliked. The rule looks arbitrary, so nobody touches it, and the prompt accumulates dead weight no one understands. A comment breaks that. Right next to the rule you write the reason: do not shorten the executive summary because the sponsor reads only the first page, or keep section labels stable because the next step parses them. Now the rule has a reason, and the reader can judge whether the reason still holds.

The why is more valuable than the what because it does not age. The rule may change, the reason usually describes a constraint that decided the rule. When the situation shifts and the reason stops being true, the comment is what tells you the rule can now go. A prompt with only instructions is something you maintain by memory. A prompt with comments is something you can maintain by reading.

There is a second audience for the comments, and it is the model itself. A short why-line next to a rule, phrased as context rather than as ordering, can help the model weigh the rule correctly instead of treating every constraint as equally load-bearing. You are not telling the model to follow a new instruction, you are explaining the intent so it does not dutifully apply a rule to a case the reason never covered. The comment makes the reasoning visible, which is usually worth more than another absolute.

The reference to keep in mind: GitHub's prompt guidance makes the same point about intent, that the value of a prompt is showing the model a complete, self-explanatory intent rather than a vague command. [^4] A comment is the fastest way to make an intent self-explanatory, because it says out loud what a bare instruction leaves for the reader to infer.

## A worked example: Dev restores a prompt that went soft

Dev built a workflow that turns a pile of customer support tickets into a weekly priority list for his team. It had run fine for two months. Then his company renamed a product line, the names showed up in every ticket, and his weekly list started coming back with two separate headings for what was one product, splitting the counts and annoying his manager.

Dev opened the prompt to fix it. This was the moment that exposed every habit at once, because the prompt had none of them. It was a single long paragraph, three years of edits stacked on top of each other with no section breaks and no notes. He could see that several sentences said related things, but he could not tell which line guarded the product names, which one set the section order he liked, or why one odd sentence about the executive summary existed at all. Every edit he tried felt like it could break something else. He spent an afternoon and nearly rewrote the workflow from scratch out of frustration before stopping.

He rebuilt the prompt the way he would tidy a file he had to keep. First, structure. He divided it into labeled sections: role, the audience it writes for, the weekly task, the exact heading order, and a clearly marked slot for this week's ticket export. Next, maintainability. He stated each rule once and only once, so the product-name rule had a single home next to a note that the two names were the same line and must be merged. He moved the variable ticket data to its own slot, separated from the instructions, so a bad paste could not read as a new rule. Last, comments. Where the prompt had rules that looked arbitrary, he wrote the why in short lines: the section order must stay fixed because his manager reads them in that order, the summary must not be cut because his manager skips to it, keep the executive summary to one line because it becomes the email subject.

![Dev rebuilds a fragile prompt into labeled sections with each rule stated once and why-lines, turning an afternoon fix into a ten minute one](</diagrams/treating-prompts-like-code-structure-maintainability-comments/4-dev-restores-prompt.png>)

When he ran it the next Monday, the product split was gone. But the bigger test was what happened a month later, when the team merged two ticket categories. Dev opened the prompt, and because it was structured he found the category rule in seconds. Because it was maintained he changed one rule without touching the frame. Because it was commented he knew, instantly, that the reason for one old line had stopped being true, and he deleted it rather than leaving it to whisper bad directions. The fix that used to cost him an afternoon took ten minutes. Structure, maintainability, and comments did not make the prompt clever. They made it legible to exactly one person, himself a month later, and that is the entire trade.

## When the habits cost more than they save

Like every habit in this course, treating a prompt like code is not free, and it is worth naming when the effort does not pay. The care pays when the prompt will be reused, edited, or read by someone other than the you of the next ten minutes. That is most of the prompts in a real workflow, because a workflow is by definition a task you run on a schedule.

The care does not pay for a true one-off. A single question you ask and never repeat does not need sections, versioning, or a comment. Structuring it is ceremony with no future reader. The judgment is the same one the choosing lesson gave you for workflows, and it transplants cleanly here: the more a prompt recurs, and the more likely it is to change, the more the read-cleanliness is worth. [^8] A weekly prompt is worth the structure. A prompt you will hand to a teammate or revisit in a quarter is worth the comments. A one-time question is not.

There is also a limit to how much comment you should write. A comment on every line buries the rules under your own meta-noise, and a prompt bloated with notes is as hard to maintain as one with none. Comment the rules whose reason is not obvious from the instruction, the constraint that exists because of a specific incident, the format a downstream step depends on. Leave the self-explanatory rules alone. The why-line earns its place when it prevents a future you from making a mistake, not every time it adds a word.

## Try it

Give yourself half an hour and refactor one prompt you actually use on a schedule. Do not write a new one. Take an existing prompt that has been working, ideally the one from the workflow you have been building through this course, and give it the treatment.

Step one, impose structure. Read the prompt and sort its sentences into buckets: role, audience, task, instructions, format, and variable input. Then rewrite it in labeled sections, choosing a delimiter you will use consistently, three dashes, a heading, named tags. Separate the variable input into its own slot so it stops sharing space with the rules.

Step two, check maintainability. Look for the same rule stated in more than one place and collapse it to one. Move the variable material out of the instructions. Ask whether you can now change exactly one rule without reading the whole prompt, and if the answer is no, keep separating until it is yes.

Step three, add comments. For each rule that does not explain itself, add a short why-line: why the format is fixed, why a constraint exists, which downside a line is guarding against. Write it for the teammate or the future you who has no memory of the incident that created the rule.

Then run the refactored prompt against real input and check that the output did not change for the worse. That check is the safety net, and it is the one step that makes the refactor safe instead of risky.

Below is a try-it prompt structured so the tool will audit your rewrite rather than reassure you. The trap in refactoring is that you break something in the name of tidiness, so you want the tool to look for regressions and untested assumptions, not to pat you on the back.

> You are helping me harden a prompt I use on a schedule. I will paste it in, then I will paste a refactored version. Be critical. Check these things: does the refactored version change any behavior versus the original, does it move or drop any constraint, is any rule now stated in two places, and is the variable input fully separated from the instructions. Tell me which specific edits in my rewrite could change the output and why. If a rule in the original looks like it exists because of an older incident, ask me what that reason was and whether it still holds. Do not reassure me that the rewrite is good. I want to find the break before my next real run does.<!-- --> 

Run that once against one real prompt, and you will have the experience this lesson is really teaching: the confidence that you can change a tool you own without tearing it down to rebuild it.
