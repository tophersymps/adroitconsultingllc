For two lessons straight you have been moving data. Lesson 31 taught you to archive cold records into a Big Object, lesson 32 taught you to decide what to archive, when, and how to satisfy compliance. Both of those lessons answered one question: how do I get data out of the hot object and into a store I can afford? This lesson, requirement lv-3a of the Large Data Volume (LDV) Considerations domain, answers a different question entirely. [^1] What if the data never needs to live in Salesforce at all?

The exam guide phrase the requirement as a decision: given a customer scenario, decide when to use virtualized data and describe the virtualized data options, which include External Objects, Salesforce Connect adapters, and Data Connect for sharing without copying. [^1] Everything in this lesson is a way of making that decision well. You will learn what virtualization actually is, what Salesforce Connect and External Objects give you, what each adapter is for, what constraints you inherit the moment you choose an External Object, and when the whole approach is the wrong call and you should copy instead. That last part matters. An architect who can only virtualize is as limited as one who can only copy. The skill is choosing between them.

## What virtualization is and the problem it solves

Virtualization exposes data that lives outside the Salesforce database as if it were Salesforce data, without copying it into the org. [^2] The data stays where it physically lives, in an ERP, a warehouse, a data lake, or another Salesforce org, and Salesforce reaches it on demand through a live connection. From the user's point of view, they open a tab, run a list view, pull up a record detail page, see a related list, and the external data looks like any other Salesforce object. Behind the scenes there is no copy being kept in sync. Every access goes out to the external system and comes back.

The problem virtualization solves is specific and worth stating precisely: I need to see and act on external data inside Salesforce, and I either cannot copy it or I should not. [^2] You cannot copy it when it is too large to copy economically, or when residency rules say the data has to stay on premises or in its country of origin, or when the source owns the data and will not release a copy. You should not copy it when the data changes so often that any copy is stale the moment it lands, or when the whole point is to show a real-time number rather than a snapshot. Salesforce's own integration guidance makes the bias explicit: avoid unnecessary data replication, and unless the data absolutely needs to reside in Salesforce, consider data virtualization first. [^3] More data in the org means larger data volumes, slower performance, and technical debt. Virtualization keeps the org small by keeping the data out of it.

The trade-off is that virtualization is not free. You are trading storage cost and sync complexity for a live dependency on an external system. Every query that touches an External Object crosses a network boundary, so latency, the external source's performance, and its rate limits are now part of your Salesforce experience. [^4] That is the price of not copying, and a good architect prices it before committing.

## Salesforce Connect and External Objects

Salesforce Connect is the mechanism that makes virtualization real. It lets users view, search, and modify data stored outside the org by mapping data in an external system to External Objects inside Salesforce. [^2] Instead of copying rows into a standard or custom object, Salesforce Connect accesses the external data on demand through web service callouts. Each External Object maps to a table in the external system, and each External Object field maps to an accessible column in that table. [^4]

An External Object looks and feels like a custom object. It appears in tabs, list views, record detail pages, global search, lookup relationships, and the mobile app. You can query it with SOQL and SOSL, reach it through Apex and the Salesforce APIs, and deploy it with the Metadata API, change sets, or packages. [^2] Where it differs from a custom object is the hard set of constraints that come with mapping data you do not own. Those constraints are an exam favorite, and the next section takes them one by one.

By default External Object records are read-only. [^2] You can enable writable External Objects if the external data source supports writes, which turns on create, edit, and delete for users who have permission. But write support is adapter-dependent and not guaranteed. The OData adapter can support writes when the OData service supports them, the cross-org adapter can write back to the other org, and a custom Apex adapter can do whatever you code the Apex Connector Framework to do. [^4] For the exam, hold this baseline: external objects are read by default, each adapter decides whether writes are possible, and a read-only External Object is the common case.

## The adapters: OData, cross-org, and custom

Salesforce Connect does not talk to every external system the same way. It uses a protocol-specific adapter, and you choose the adapter when you define the external data source. [^2] The requirement names OData, cross-org, and custom adapters explicitly, so know all three and the scenarios each fits. [^1]

The OData adapter connects Salesforce to any external system that exposes its data as an OData service. [^2] Salesforce Connect supports OData versions 2.0, 4.0, and 4.01. [^5] When a user (or a flow, a process, Apex, SOQL, SOSL, a report, or the APIs) touches an External Object that maps to an OData source, Salesforce converts the interaction into an OData query and sends it as a callout to the OData producer. [^5] With OData 4.0 and 4.01 you can also use External Change Data Capture to track changes to data stored outside the org and build automation in response to those changes. [^5] This is the adapter you reach for when your external system can publish an OData producer, which covers many ERP and legacy platforms such as SAP and Microsoft systems.

The cross-org adapter exposes objects from another Salesforce org as External Objects in the current org. [^2] Salesforce Connect uses Lightning Platform REST API calls to reach the records in the other org, and setup is point-and-click. [^6] This is the native way to view and work with another org's data without writing integration code and without copying it. You point the current org at the provider org, sync the objects you need, and users in the subscriber org see the provider org's Accounts, Orders, or custom objects as live External Objects. This is the right answer whenever the second system is itself a Salesforce org and you want a live view of its data rather than a periodic copy.

The custom adapter, built with the Apex Connector Framework, connects to any data store that none of the packaged adapters can reach. [^2] You write Apex that implements Salesforce Connect's interfaces, and you decide how the adapter pulls, queries, and (if you support it) writes the data. [^4] This is the most flexible adapter and the most work. The exam lists it as a valid option, but the practical guidance is to prefer a packaged adapter when one matches your source, and to reach for a custom adapter only when none does.

Salesforce has since added other adapters that the exam guide, written against an earlier release, names more loosely. There is now an adapter for Amazon DynamoDB, an adapter for SQL sources such as Snowflake and Amazon Athena, an adapter for GraphQL, and adapters for Salesforce Archive and Privacy Center stores. [^2] The exam's list of "etc." admits these. Know the three named in the requirement cold, and recognize that Salesforce keeps extending the family as new external stores appear.

## The cross-org adapter in depth

The cross-org adapter deserves its own section because it is the cleanest answer to a very common scenario: you have two (or twenty) Salesforce orgs, and one of them needs to see another's data without duplicating it. Lesson 24 covered consolidating versus integrating across multiple orgs. The cross-org adapter is the live, no-copy option in that toolset.

The way it works is a subscriber-provider relationship. One org, the provider, owns the data. The other org, the subscriber, sets up a cross-org external data source pointing at the provider. When you synchronize the data source, the provider's objects become External Objects in the subscriber org. [^6] Users in the subscriber org then see the provider's records in list views, record pages, lookups, and reports, and the data is live. There is no copy sitting in the subscriber org going stale.

A key detail to teach because the exam loves it: relationship and lookup fields between objects in the provider org get synchronized by the cross-org adapter, but they arrive in the subscriber org as text fields whose values are record IDs, not names. [^7] A lookup relationship field becomes a text field holding the parent's 18-character ID. To restore a real relationship in the subscriber org you create an external lookup relationship, sync the parent and child objects so both exist as External Objects, and change the text field to an External Lookup Relationship field pointing at the parent External Object. [^7] If that sounds like unnecessary friction, you are right, but it is the price of not copying. The exam expects you to know that the cross-org adapter turns provider lookup fields into ID text fields and that external lookups reconstruct the relationship.

Writes through the cross-org adapter are possible but carry consequences. When you update an External Object that maps to a provider org, the write goes to the provider as if it came through the REST or SOAP API, so the provider's validation rules and flows fire normally. [^3] That is usually what you want, but it means an update from the subscriber org can trigger provider-side automation you need to plan for.

## The hard constraints of External Objects

External Objects behave like custom objects right up to the point where they do not. The constraint list is one of the most directly testable facts in this lesson, and the exam's Q2 is built on exactly it. Walk through each limit and know why it exists.

Every External Object must have an External ID. [^1] The External ID standard field carries the external primary key, the value that uniquely identifies each record in the source system. [^8] For the OData adapter the External ID comes from the entity key defined in the OData service metadata. [^5] For a custom adapter it comes from the `DataSource.Column` named `ExternalId` that the Apex code declares and fills. [^8] This ID is the anchor of the whole integration: it is what the external lookups match against, and it is how Salesforce knows a row it just fetched is the same record it showed a minute ago. [^8] If a source has no natural unique key you can use, you must synthesize one before you can virtualize it. This is the constraint behind Q2's answer A.

External Objects cannot be the child side of a master-detail relationship with standard or custom objects. [^4] The relationship types an External Object can participate in are limited to three: lookup, external lookup, and indirect lookup. [^9] There is no master-detail option. That is the constraint behind Q2's answer C. It has a real consequence: because roll-up summary fields live on the master side of a master-detail relationship, and External Objects cannot be details, External Objects have no roll-up summary fields. [^4] Formulas and roll-up summary fields cannot reference fields on External Objects. This is the constraint behind Q2's answer B being wrong: roll-ups are a feature External Objects lack, not one they have.

Let me pause on the relationship types because they are specific. A standard lookup relationship links records by the 18-character Salesforce record ID, and it works when the external data happens to include a column holding Salesforce IDs. [^9] An external lookup relationship links a child object to a parent External Object by matching the child's external lookup field against the parent's External ID standard field. [^9] An indirect lookup relationship links an External Object child to a standard or custom parent, and instead of Salesforce IDs it matches the child field against a custom field on the parent that carries both the External ID and Unique attributes. [^9] Indirect lookups are the bridge you use when the external data has no Salesforce record IDs at all, only its own keys, and you need to relate it to your native records. That is how you map external inventory to your Products, external orders to your Accounts, external entitlements to your Opportunities.

The next constraint is performance, and it is the one people forget. An External Object is not inherently fast, and Q2's answer D (they are always faster than native objects) is a trap built on that misreading. [^4] Every access to an External Object is a live callout to the external system. [^4] Query performance depends entirely on the external source: its response time, its rate limits, and how well its API or OData service handles filtered queries. [^4] Reports over large External Objects can be slow or limited, and list views over high volumes surface latency in the UI. [^5] If your source is slow, your Salesforce users feel it on every lookup. Virtualization does not make external data fast; it makes external data present, and the speed is a property of the source.

There is a fuller list of unsupported features worth having in your head even though the exam will not ask about all of them: no validation rules, no formula fields, no record types, no merge fields, no Schema Builder, no activities, tasks, or events, no attachments, no roll-up summaries, no record-level security that lets you control external data access in the normal sharing sense, and no encrypted fields. [^4] Some of these flip on for the cross-org adapter specifically, which supports auto-number, currency, and picklists for synced objects. [^4] The point is not to memorize every line. It is to hold the pattern: an External Object trades the full object feature set for the ability to reach data you do not own, and the moment you rely on a feature that is not supported, you have built the wrong tool into the design.

## When to virtualize, when to copy

With the constraints laid out, the decision itself becomes clear. The exam tip for this lesson states it as a compact rule: virtualize volatile, remote, or residency-bound data, and copy stable data that needs native speed, validation, automation, and reporting. [^1] Expand that into the reasoning the scenario questions reward.

Virtualize when the data changes frequently in the source. A nightly copy of inventory that changes every hour is wrong by definition. You want the live number, so you virtualize and accept the latency. [^1] Virtualize when the data must remain in the source, for residency, ownership, compliance, or country-of-origin reasons. A copy would violate the constraint, so virtualization is the only option. [^1] Virtualize when the volume is too large to copy economically. Copying ten billion rows into Salesforce just to read a few thousand per day wastes storage and damages performance, and the integration guidance explicitly says to avoid that replication. [^3] And virtualize when the requirement is real-time access. If the business question is what is the current value right now, a copy cannot answer it.

Copy when the platform needs to own the data natively at speed. If Salesforce must report on it at high performance, run validation and automation against it, or serve it to users in list views fast, a copied record in a custom object gives you native indexes, reporting, sharing, and flows that an External Object cannot. [^1] Copy when the data is stable and used heavily. Stable data does not lose value by sitting in a copy, and it gains all the native features the platform provides. Copy when the external source is slow or unreliable enough that a live dependency would degrade the user experience; a scheduled copy decouples Salesforce from the source's availability. [^1] Copy when the data genuinely must reside in Salesforce to be served or integrated.

Notice where the boundary snap is. Volatile and remote trends push to virtualization. Stable, high-use, platform-critical data pushes to copying. Q1 and Q3 are built on exactly this tension, and the next section works both through worked scenarios.

## Data Connect: zero-copy analytics sharing

Salesforce Connect handles the operational data access problem: a user, a flow, or a report pulls a live record. It is transactional and interactive. There is a second, larger class of sharing that the requirement calls out separately: Data Connect, for sharing large-scale analytical data without copying. [^1] This is the complement to Connectivity, targeting the analytics side of the house rather than the record-by-record side.

Product naming here moves with releases, so hold the capability and confirm the current name in the release you are working against. Historically the exam guide calls this Data Connect, and it sits in the Data Cloud (now branded Data 360) platform as part of its zero-copy data-sharing story. [^3] The capability is zero-copy data sharing and federation: Salesforce shares data with external data lakes and warehouses such as Snowflake, Google BigQuery, Databricks, and Amazon Redshift, or reads from them, without duplicating the data in a second store. [^10] Data shares, data share targets, and data pipelines drive the integration flow, letting you mount a store as if it were native and query it without copying it. [^10] Because Data 360 naming and feature specifics change every few releases, check the current product documentation for exactly what the feature is called and what it supports in your release.

The reason this matters for the Platform Data Architect is that virtualization is not only about a user clicking a record. When a data warehouse must consume Salesforce data at analytical scale, or Salesforce analytics must consume a warehouse at scale, you do not want to duplicate tens of billions of rows into a second store. Zero-copy sharing lets both sides read the same data in place. [^10] It is virtualization at the analytics tier rather than the record tier, and a complete virtualization answer on this exam names both tiers: Salesforce Connect for live record access, Data Connect / zero-copy for analytical-scale sharing without copying.

## Config walkthrough: standing up virtualized data

Here is the numbered walkthrough the exam expects you to reason through when you take a scenario and decide on virtualization.

1. Decide per data set whether to virtualize or copy. Run each dataset through the four deciding variables: change frequency, residency, volume, and required features. [^1] Volatile, residency-bound, or huge data that just needs to be seen virtualizes. Stable, high-use, platform-critical data that needs native speed, validation, automation, and reporting copies. [^1] Do this before reaching for a tool.

2. For datasets you virtualize, configure Salesforce Connect with the right adapter. Pick the OData adapter for an OData producer, the cross-org adapter for another Salesforce org, the DynamoDB, SQL, or GraphQL adapter for those sources, or a custom Apex adapter when none match. [^2] Create the external data source, set the adapter in its Type field, and connect it to the source system.

3. Synchronize the data source and define External Objects. Each External Object maps to a table in the source, and you set the External ID standard field to the external primary key. [^4][^8] If the source has no unique natural key, synthesize one in the source before synchronizing.

4. Map relationships within the adapter's constraints. [^9] Link native standard and custom data to External Objects with indirect lookups, using a Unique External ID field on the parent as the match target. [^9] Link External Objects to parent External Objects with external lookups that match on the parent's External ID. [^9] Reconstruct cross-org relationships by syncing both objects and changing the ID text fields to external lookups. [^7] Remember you cannot make an External Object a master-detail child. [^4]

5. For analytics-scale sharing, use Data Connect and data pipelines to share without copying. Create the share, attach the share target for the external warehouse, link them, and query the shared store in place rather than replicating into a second store. [^10] Confirm the current product naming and features in your release before you present it to a stakeholder.

6. Monitor external latency, rate limits, and source performance, and design caching and pagination where the source is slow. [^5] Because every External Object access is a live callout, plan the query patterns, the paging behavior, and any caching so the user experience holds up. [^5]

## The three exam traps

Trap one, expecting an External Object to behave like a native object. An architect who builds a list view on an External Object they never intended to be read live, or relies on a roll-up over external data, or makes an External Object the detail in a master-detail, will be surprised at deploy time. [^4] The fix is to design within the constraints from the start: no roll-ups, limited relationship types, no master-detail child, and an external-performance dependency that shows up in the UI. The exam's Q2 is this trap in multiple-choice form.

Trap two, virtualizing data that the platform must automate, validate, or report on heavily at speed. If the requirement is native validation and automation, flows and triggers, or high-speed reporting over the data, virtualization gives you a live dependency instead of the native engine. [^1] External Objects have no validation rules and no roll-up summaries, and reports over large External Objects can be slow. [^4] Those needs argue for copying, and the scenario question is checking whether you see that. The exam's Q3 is this trap: the correct answer is the case where the platform must own stable data for speed, validation, automation, and reporting. [^1]

Trap three, forgetting that external systems need an External ID and that latency surfaces in the UI. [^1] If you stand up an External Object without a unique external key, the integration has no anchor. If you ignore rate limits and source response time, your users experience the slowness on every lookup, list view, and report. [^4][^5] The fix is to establish the External ID up front and to design for latency: filtered queries, pagination, monitoring, and caching where the source cannot keep up. The exam's Q1 is the mirror image of good practice: live, volatile external data that changes constantly is exactly what virtualization (not a nightly copy, not a Big Object) is for. [^1]

## Worked example: live inventory from an OData source

Work the exam's Q1 scenario for real. A company must show real-time inventory from a remote OData service inside Salesforce without storing the inventory, and the data changes constantly. [^1]

Read the deciding variables. Change frequency is high, the inventory shifts throughout the day. Residency is remote, the data lives on an external service the company does not want to duplicate. Volume is whatever the warehouse holds, maybe large. Required features are modest: users need to see current stock on hand, likely next to a Product or Order in Salesforce. Nothing here demands native validation or heavy in-platform reporting on the raw inventory rows.

That profile is a textbook virtualize. The OData adapter is correct because the source is an OData producer. [^5] You create an external data source with the OData adapter, synchronize it to map the inventory table to an External Object, and set the External ID to the inventory item's unique key in the OData service. [^4][^5] You relate the External Object to your native Product records with an indirect lookup, matching on the product's Unique External ID field. Users open a Product, see the related live inventory list, and get the current stock for a given SKU on demand. No copy exists, so there is nothing to go stale. [^2]

Now the wrong answers, because the question tests the distinction. A nightly copy into a custom object is stale by construction. [^1] The inventory changes constantly, so a snapshot from last night answers last night's question, not today's order. Big Objects do not virtualize external sources at all. A Big Object stores data inside Salesforce and is queried with Async SOQL; it cannot reach out to an OData service. [^11] Moving Salesforce to a Big Object, or storing inventory in a Big Object, changes where data lives inside the org but does nothing to bring in the external source. So the only approach that satisfies show real-time, without storing it, from a changing external source is virtualization via Salesforce Connect with the OData adapter. That is Q1's answer, and the reasoning the exam rewards.

Counter it with Q3's scenario to see the other side of the coin. If that same company needed the platform to validate inventory against business rules, run automated allocation flows, and report on it at high speed, the external dependency would fight them. [^1] External Objects have no validation rules, no roll-up summaries, and reports over them depend on the source's speed. [^4] You would copy the inventory (even though it changes) into a custom object, because the platform must own it. The lesson is not "virtualize everything". It is "virtualize what volatility, residency, and remote location make un-copyable, and copy what the platform must own." [^1]

## Try it for yourself

In a Developer Edition org with Salesforce Connect available, stand up a miniature version of the Q1 pattern with the cross-org adapter, which is the easiest adapter to reach in a sandbox because the provider is another org you control. Create a simple custom object in a second Developer Edition org to act as the inventory source, give it a unique external key, and populate a few rows. In your subscriber org, create a cross-org external data source pointing at the provider, synchronize it so the source object becomes an External Object, and confirm the External ID defaulted to the source object's key.

Then test a relationship. Add an indirect lookup field on the External Object and relate it to a native parent whose Unique External ID field you populated to match the source keys. Open a parent record and confirm the related External Object list resolves live. Now change a value in the provider org and refresh: the subscriber shows the new value, because there is no copy. Finally, try the write path if your cross-org source supports it, update an External Object record from the subscriber, and confirm the change landed in the provider (and fired its validation rules). The point is to feel the whole stack, the adapter choice, the External ID anchor, the indirect lookup bridge, the live no-copy freshness, and the constraints that come with them, on data small enough to inspect. That identical sequence on production inventory is the entire lesson.

## What's next

You can now decide when to virtualize and describe the virtualized data options. You know virtualization exposes data that lives outside the Salesforce database as if it were native, without copying it, and that it exists precisely for the data you cannot or should not copy. You know Salesforce Connect uses External Objects and adapters to reach that data, in real time through live callouts. You know the adapters: OData 2.0, 4.0, and 4.01 for any OData producer, cross-org for another Salesforce org, and custom Apex for everything else, plus the newer DynamoDB, SQL, GraphQL, Archive, and Privacy Center adapters. You know the cross-org adapter turns provider relationships into ID text fields that you rebuild with external lookups. You know the hard constraints of External Objects: the required External ID, the absence of roll-up summaries, the limited lookup relationship types, the inability to be a master-detail child, and the total performance dependency on the external source. You know when to virtualize, volatile and residency-bound and remote data that must stay put, and when to copy, stable data the platform must own for speed, validation, automation, and reporting. And you know Data Connect and zero-copy sharing as the analytics-tier complement, sharing data with warehouses and lakes without duplicating it.
