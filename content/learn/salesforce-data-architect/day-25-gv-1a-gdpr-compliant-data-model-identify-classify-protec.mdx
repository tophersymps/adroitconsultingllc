The architecture work up to this point has been about how to shape data: where records live, how they share, how they stay consistent. Requirement gv-1a changes the register. It asks you to design a data model that is defensible in law, not just sound in structure. The full requirement is: given a customer scenario, recommend an approach for designing a GDPR-compliant data model, discussing the various options to identify, classify, and protect personal and sensitive information, including the right to erasure.[^1]

GDPR is the law the exam uses to stand for the whole class of privacy regulation. What it codifies is the central idea that an individual owns her personal data and a controller may only process it when there is a lawful basis. The architect's job is not to give legal advice. It is to build a model that can prove where personal data lives, why it is processed, who can reach it, and how an erasure request can be honored. The exam wants you to translate GDPR's obligations into concrete data-modeling decisions across identify, classify, protect, consent, retention, and erase.

This lesson teaches that translation. We define personal and special-category data and why location is the first problem, work the data inventory you build to find that data, walk the classification tiers you maintain as metadata, cover the protection layer and its encryption trade-offs, model consent and retention, and close on the erasure patterns the requirement names. The right-to-erasure quiz question is reinforced at every step.

![The five-stage GDPR data model pipeline: identify, classify, protect, record consent and retention, then erase](</diagrams/day-25-gv-1a-gdpr-compliant-data-model-identify-classify-protec/1-gdpr-model-pipeline.png>)

## Personal data, special-category data, and why location is the first problem

GDPR defines personal data very broadly. It is any information relating to an identified or identifiable natural person. The classic test is whether you can point at a specific human. A name, an email address, a phone number, an IP address, a device identifier, a customer account number that maps to one person, all of it is personal data when it can identify someone. The definition is what floods the model with obligations: nearly every standard object in a Salesforce org, Account, Contact, Lead, Case, Opportunity with a primary contact, holds at least one field that can identify a person.[^2]

Special-category data is narrower and far more restricted. GDPR Article 9 covers data revealing racial or ethnic origin, political opinions, religious or philosophical beliefs, trade-union membership, genetic data, biometric data used to uniquely identify a person, health data, and data concerning sex life or sexual orientation. Processing special-category data is prohibited unless an explicit lawful basis applies, and it generally needs a higher standard of protection and tighter access than ordinary personal data. A health-cloud case that records a diagnosis, a field capturing ethnicity for a demographic study, a biometric attendance field, these are special-category and the model must treat them with stricter controls than a name field.[^3]

Why is location the first problem? Because a control you can apply to a field you cannot see is a control you cannot apply at all. Encryption, field-level security, retention, and erasure all act on data you have located and tagged. Before you can protect personal data, you must know exactly which objects, which fields, which files, and which free-text containers hold it. A model that never inventoried its data cannot answer the regulator's basic question, where does personal data live? GDPR's accountability principle makes that answer mandatory. The first deliverable of a compliant model is therefore not a permission set or an encryption key. It is a map.[^4]

![Personal data versus special-category data, with the examples and the protection standard each carries](</diagrams/day-25-gv-1a-gdpr-compliant-data-model-identify-classify-protec/2-personal-vs-special-category.png>)

## Identify: the data inventory that finds personal data, including in free text

Identification is the discipline of building a complete data inventory of everywhere personal or sensitive data can live. You walk every object, every field, every attachment and file type, and every piece of free text, and you record which ones hold personal data and which hold special-category data. The inventory is the source document that every downstream control, classification tag, encryption decision, and erasure job reads from.[^5]

Start with the obvious structured fields. Name, email, phone, mailing and shipping street and postal code, birthdate, social-security or national-id equivalents, nationality, languages spoken, device IDs on custom objects, geolocation fields, IP addresses captured by an app, any lookup or text field that holds an identifier the org uses to recognize a person. Each gets a row in the inventory that says which object, which field, what type of data, and what sensitivity tier it carries.

The subtle part, and the part the exam targets directly, is free text. Notes, case descriptions, work-order comments, chatter posts, email-to-case bodies, the subject and description on a custom record, all of these can hold personal data that no field definition would ever label. A support rep writes a customer's complaint into a Case description and includes her medical condition; that free-text field has just become a container of special-category data the inventory never knew about. The model must treat free-text containers as potential personal-data reservoirs and handle them accordingly: classify them, restrict who can read them, encrypt where the sensitive content justifies it, and design erasure that can find and scrub personal values inside them.

The inventory also covers files and attachments. A customer's uploaded ID document, a scanned receipt attached to a transaction, a personalized PDF, these are personal data even though no field-level tool can classify their internal content. The retention and erasure plan must include the filesystem, because a subject's erasure request that stops at fields but leaves an attached identifying document is incomplete. When you design the inventory, include the files and the largest free-text objects explicitly.

Running a real inventory in Salesforce combines several tools. Data export and the metadata API give you the schema to walk object by object. Field audit trail logs and event monitoring show you which fields are actually being written to and read, which reveals the fields in real use rather than just the ones defined. Data dictionaries and the metadata governance program the series has covered give the inventory a place to live and stay current. The inventory is not a one-time project. It is a living artifact that changes when the model changes, and the governance program is what keeps it honest.[^6]

## Classify: sensitivity tiers you maintain as metadata

Once you have located the data, classification assigns it a sensitivity tier. The simplest model uses two dimensions. The first is a business-confidentiality scale such as Public, Internal, Confidential, and Restricted, which says how far the data may spread. The second is a privacy scale of PII and Sensitive-PII, which says whether the data identifies a person and whether it is special-category.

Classification is what makes decisions consistent at scale. Instead of reasoning field by field whether a given value is sensitive, which is slow and error-prone, you tag a field once and every downstream control reads the tag. Encryption policies, field-level security defaults, retention schedules, and erasure patterns all key off the classification. Two fields that hold the same type of value must carry the same tag, or the governance program leaks at the edges.

The exam wants you to treat classification as metadata, tied to the data dictionary and the governance program rather than scattered as informal notes. A field is Confidential because a decision recorded it as Confidential, in a controlled catalog that is versioned and auditable. When someone adds a field that holds personal data and does not classify it, that is a governance failure, not a model detail. The classification catalog is the source that lets the org prove its data was protected deliberately. Buy-in from the business matters here, because only the business knows whether a given field is genuinely sensitive and how long its data must be kept.

## Protect: the layered controls of a compliant model

Protection is a combination of platform capabilities, not a single switch. The exam describes the layer as the union of field-level security and profiles or permission sets for access control, Shield Platform Encryption for encryption at rest of sensitive fields, Classic and Deterministic encryption where the trade-offs fit, Event Monitoring and Field Audit Trail for access and change logging, Data Mask for sandboxes, and sharing and org-wide defaults to limit record visibility. Each control does one job, and a compliant model uses the right mix.

Access control comes first because it is the cheapest and the most universal. Field-level security makes a field invisible or read-only to a profile or permission set, and it combines with object-level and record-level sharing to decide who sees what. A permission set that grants a support user the read on a health-diagnosis field that no support workflow needs is a leak a classification tier exists to prevent. The rule is simple: grant the least access a role needs, and let classification tell you which fields are too sensitive for broad distribution. Page layouts and record types support workflows but do not protect data, which is exactly the distinction the quiz draws between a real protection control and a layout choice.[^7]

Shield Platform Encryption provides encryption at rest for a wide range of standard and custom fields. You choose an encryption scheme per field, and at rest the field's value on disk and in backups is unreadable without the tenant's managed keys. Shield supports deterministic and probabilistic encryption for strings. Deterministic encryption keeps the same plaintext value mapping to the same ciphertext, which preserves equality filters, match, and group-by semantics, so that an Email field stays usable for lookups. Probabilistic encryption produces different ciphertext every time, which is stronger against pattern analysis but loses equality search. Knowing the trade is the core of choosing a scheme.

The trade-offs matter enough to test. With Shield, some functions behave differently on encrypted fields. Sorting, some filters, index lookups, and roll-up summary fields can be affected depending on the field type and scheme, and certain features such as unique constraints and external IDs are handles to think through carefully. You confirm the current behavior per release, because Salesforce may extend what encryption supports, and you design encrypted fields with their functional limits in mind rather than discovering them in production. Shield is a control, not a compliance badge. Encrypting a field does not by itself classify it, restrict who reads it, or record the legal basis, and a regulator wants all of those, not a certificate that the disk is encrypted.[^8]

Classic and Deterministic encryption are the older at-rest options. Classic encryption applies to a narrower set of standard fields such as Street, City, Postal Code, and Phone, and it has its own functional limits, for example it cannot filter or sort, so its use is confined to fields where the value is stored but not queried. Deterministic encryption is the newer, broader scheme that supports advanced encryption algorithms and keeps equality semantics for matches and lookups. Your choice among them follows what the field has to do: a field that must be matched exactly gets a deterministic scheme, a field that only needs storage gets probabilistic or the simplest fit, and a field that must be searched by range or pattern may need to stay plaintext behind strict access rather than be encrypted at all.

![Choosing between deterministic and probabilistic encryption based on what the field must do](</diagrams/day-25-gv-1a-gdpr-compliant-data-model-identify-classify-protec/5-encryption-scheme-choice.png>)

Two more protections round out the layer. Event Monitoring and Field Audit Trail log access and changes to records and fields, which is how the org proves who read or changed personal data and when. Field Audit Trail retains history for up to ten years, and event monitoring captures field-level read and write events, both of which the accountability principle effectively requires for sensitive data. Data Mask replaces sensitive values with fictional substitutes in sandboxes, so that developers and testers do not work against real customer personal data, which extends the protection boundary from production to every environment that copies it.[^9]

## Consent and lawful basis: the model must be able to prove why it processes

GDPR does not ban processing personal data. It requires a lawful basis. The six bases include consent, contract performance, legal obligation, vital interests, public interest, and legitimate interests. The model's job is to record, for each personal-data processing it performs, which basis applies, when consent was given or revoked, and what the retention schedule is. Without that record the org cannot answer the second regulator question, why are you holding this?

In the data model that means a Consent object. A Consent record ties a data subject, typically a Contact or an individual Account, to a data-use purpose and a consent status such as granted, revoked, or expired, with the date consent was obtained and the version of the consent statement the person agreed to. Salesforce reaches this through a Contact Point Type Consent object and the consent subsystem, where you model each data-use purpose and record the data subject's grant or withdrawal against it. Recording withdrawal is as important as recording the grant, because a withdrawal changes the lawful basis for future processing and should trigger retention and erasure review.[^10]

Consent is not only for marketing. If the org's processing rests on consent, the model must be able to prove a current, informed, specific, and freely given consent for each processing. If processing rests on contract or legal obligation, the model must be able to point at the basis. The exam rewards you for modeling the basis explicitly rather than assuming consent is always the answer. In many customer scenarios contract performance or legitimate interest is the honest basis, and consent is narrower than non-technical teams assume.

Retention is the time dimension of the model. GDPR's storage-limitation principle says you keep personal data no longer than needed for the purposes you stated. Retention schedules must be defined per data category, then enforced. That enforcement is operational, purge and archive jobs that delete or archive records that have passed their retention date, governed per category rather than run ad hoc. The retention schedule is what reconciles the right to erasure with the org's legal duty to keep certain records, and the erasure patterns in the next section exist in that tension.

## Erasure: the four patterns and when each fits

The right to erasure, sometimes called the right to be forgotten, lets a data subject request deletion of her personal data. The exam frames the architect's job as supporting two things: finding all records for a subject across objects, files, and systems, and erasing or anonymizing them while balancing legal retention obligations. The finding problem is the part most models undersell. Personal data about one person can sit in Contacts, their related accounts, their cases, their orders, their log files, their notes, their attachments, and their export copies in downstream systems. An erasure request that deletes the Contact but leaves the case description full of her details has only half-erased her.

The requirement names four erasure patterns, and the skill is knowing which fits a given record.

![Decision tree for choosing an erasure pattern based on whether a legal retention obligation attaches](</diagrams/day-25-gv-1a-gdpr-compliant-data-model-identify-classify-protec/3-erasure-pattern-decision.png>)

Hard delete is the destructive erasure you perform when no retention obligation attaches. You physically remove the records, or the personal fields, from the object. It is the cleanest erasure but the least available, because it is subject to retention law and to referential constraints. If government or contract law requires keeping transactions for seven years, you cannot hard-delete the transaction records that create a personal-data footprint, and if other objects reference the record you delete, referential integrity breaks. Hard delete belongs to data you may lawfully forget.

Anonymization and pseudonymization replace personal values with non-identifying tokens while keeping the record. Anonymization removes any link back to the individual, so the remaining data is no longer personal data, while pseudonymization replaces direct identifiers with tokens that can, under controlled keys, be mapped back. When retention law requires keeping transactional history, anonymization is the pattern that satisfies both masters: the record stays for financial and analytical integrity, but the personal values that identify a human are replaced and the subject is no longer identifiable from it. This is the answer the right-to-erasure quiz question tests: legally retained transaction history means you anonymize its personal fields, you do not hard-delete records you are required to keep, ignore the request, or archive everything with its personal data intact.[^11]

Deletion of the personal fields while retaining the transactional shell is the third pattern. You null out or scrub the fields that identify the person, Name, email, phone, notes that name her, but you keep the transactional shell, the order, the amount, the date, the product, so the business record survives without the identifying attachments. It overlaps with anonymization in spirit but applies at the field level to a chosen subset rather than through a dedicated masking routine.

Right-to-be-forgotten declarative tools are the fourth. Some platforms provide managed tools for deletion-of-data-subject workflows, and where they exist you use them to orchestrate the deletion across the defined scope rather than hand-rolling a partial delete. The point of naming the pattern is that the platform offers structured deletion support you should reach for before building your own.

Whichever pattern applies, the model must make it reliable. A deletion job that finds a subject has to search every object and file the inventory identified as holding her data, not just the obvious Contact, and it has to run inside the same governance and audit framework that governs every other sensitive-data change.[^12]

## Worked example: the retention-bound erasure request

Here is the applied scenario the exam is shaped like, and the reasoning it wants to see.

A financial-services customer holds a GDPR data-subject request from a former client. The client asks that all his personal data be erased. The company is legally required to retain transaction records for seven years under financial-regulation rules, and those transaction records carry the client's name, account references, and contact details. The teams first instinctively reach for hard delete, because an erasure request sounds like deletion.

The correct design does not hard-delete. Score it against the obligations. The erasure right extends to personal data wherever it lives, so the company must find the client across every object: the former Contact (if one remains), the opportunity and order history, the notes and case descriptions, the account record that carries his identity, any files or attachments that name him, and the downstream analytics copies if they hold identifiable values. But the seven-year retention requirement is a legal obligation that outranks the deletion instinct, because the company is forbidden from destroying the transactional records. Destroying them would break the law the erasure request is trying to satisfy.

So the design applies anonymization to the retained transactional records. The company keeps the seven years of order and trade history for financial integrity and audit, but it scrubs the personal fields, the name, the contact identifiers, the account references in that context, replacing them with non-identifying tokens so the retained history can no longer be tied to the individual. Where no retention obligation attaches, such as an old marketing preference and the consent record behind it, the company hard-deletes those records outright. It also scrubs or removes the notes, case descriptions, and files that name him, because those are personal-data containers sitting outside the transactional obligation. The result honors both masters: the client gets his erasure, because he is no longer identifiable from anything the company holds, and the company keeps the records the law forces it to keep. That tension, and the anonymization bridge across it, is the exam's idea of a correct erasure answer.

![The retention-bound erasure request: anonymize retained transaction history, hard delete records with no retention](</diagrams/day-25-gv-1a-gdpr-compliant-data-model-identify-classify-protec/4-retention-bound-erasure.png>)

## Config walkthrough: building the compliant model

Here is the numbered walkthrough the exam expects you to be able to reason through, start to finish.

1. Identify and inventory. Walk every object, field, file type, and free-text container, and record where personal and special-category data lives. Include Notes, Case descriptions, and attachments explicitly, because free text is where identification silently fails. Write the result into the data dictionary as a living inventory owned by the governance program.

2. Classify every entry. Assign each inventoried field a sensitivity tier using a confidentiality scale (Public, Internal, Confidential, Restricted) and a privacy scale (PII, Sensitive-PII), and store the classification as metadata in the catalog. Free-text containers receive the tier their contents can reach, which for a health or personal topic is Sensitive-PII.

3. Restrict access with FLS and sharing. Set org-wide defaults and sharing rules so records are visible only to the roles that need them, and apply field-level security and permission sets so sensitive fields are invisible or read-only to everyone else. Grant the least access a role's workflow needs, and let classification veto a field being too widely granted.

4. Encrypt the sensitive fields. For each sensitive field, choose a Shield or Classic scheme that matches what the field must do: deterministic where equality lookup and matching are needed, probabilistic where only storage matters, and confirm the current per-release behavior of sorting, filters, roll-ups, and indexes on encrypted fields before relying on them. Encrypt special-category fields as a baseline.

5. Enable the audit trail. Turn on Field Audit Trail for the sensitive objects and fields, and enable the Event Monitoring licensing that captures access and change events, so the org can prove who read or modified personal data and when. Mask personal data in sandboxes with Data Mask so test environments never copy real protected values.

6. Model consent and lawful basis. Add a Consent object that ties each data subject to each data-use purpose with a status (granted, revoked, expired), the date obtained, and the consent-version, and record the lawful basis for each processing the org performs. Define a retention schedule per data category.

7. Implement erasure patterns. Build deletion or anonymization jobs that find every record for a subject across the objects, files, and free-text containers the inventory named, and apply the right pattern record-by-record: hard delete where no retention attaches, anonymize or scrub personal fields where the record must be retained, using declared right-to-be-forgotten tooling where the platform provides it. Schedule purge and archive jobs to enforce the retention schedule automatically.

## The three exam traps

Trap one, equating deleting the record with erasure. Personal data about one subject can live in related objects, files, audit history, apps that write contact details, and downstream systems, and a request that hard-deletes the Contact alone leaves the identifier in the Case description, the attached document, and the log. Erasure is complete only when the subject is no longer identifiable from anything the org holds within the legal retention exceptions. The finding job, not the delete button, is the erasure.

Trap two, assuming Shield Platform Encryption alone makes the org compliant. Encryption protects data at rest, and it is one control. Classification tells you what to encrypt, field-level security and sharing say who may read it, consent and retention records say why it is processed and how long it stays, and erasure jobs say how it is forgotten. A fully encrypted org with no inventory, no access restriction, no recorded basis, and no erasure path is encrypted but not compliant. The quiz's protection question tests exactly this: encryption plus field-level security and permission sets are the real at-rest and access-control protections, while a read-only layout and a duplicate rule are not protection controls at all.

Trap three, forgetting free-text fields. Notes, case descriptions, and email-to-case bodies routinely hold personal and special-category data that no field definition labels, so they are missed by inventory, left unclassified, unencrypted, and unincluded in erasure. The model must treat free text as a first-class container of personal data, because unclassified free text is precisely where identification and erasure both fail.

## Try it for yourself

In a Developer edition, reproduce the free-text risk. Create a Case, add a Contact for a customer, write a description that names the customer and records a personal detail, and attach a file that names her. Run a manual inventory and confirm the Case description, the note, and the file are not flagged by any field definition. Then classify them as Sensitive-PII in the catalog, restrict the Case object and Notes to the roles that need them with FLS and sharing, and encrypt a sensitive custom field with Shield, choosing a deterministic scheme for a field you must match exactly. This makes concrete why identification has to look beyond the declared schema.

Then reproduce the erasure decision. Create an object that simulates a transaction carrying the customer's name and a seven-year retention requirement, and a separate consent record with no retention. Run a hard delete on the consent record and confirm it disappears cleanly. For the retained transaction, write a small job or use a masked copy to replace the Name and contact fields with a token like SUBJ-0001, and confirm the record survives for reporting while no longer identifying the individual. Run an erasure-scope query across the Contact, the Case, and the note container to see how much related personal data a single subject request has to cover before the org can honestly answer that the erasure is complete.

## What's next

You can now design the model that satisfies the GDPR requirements: inventory where personal and special-category data lives, classify it into sensitivity tiers maintained as metadata, protect it with field-level security, encryption, audit trails, and masking, record consent and lawful basis, define retention, and honor erasure with the pattern each record's obligations allow. Lesson 26 turns this design vocabulary into decision scenarios: GDPR contexts for consent, retention, field-level controls, encryption, and deletion patterns, where you read a customer situation and pick the compliant design (gv-1b). The identification and classification discipline you built here is the frame every one of those scenario decisions hangs on.
