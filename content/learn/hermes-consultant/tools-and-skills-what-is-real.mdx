# Lesson 9: Tools and Skills: What Ships with Hermes, How to Extend It, and How to Know What's Real

Lesson 8 configured an agent so it survives leaving your machine. This lesson answers the question you carry into every client conversation once the agent is running: what can it actually do, and how do I make it do more, and how do I know any of it is true? Those three questions are the whole of this lesson. An agent does not have one vague blob of ability. It has a concrete set of things it can reach, which are its tools, and a concrete set of procedures it knows how to follow, which are its skills. Both are finite and inspectable, and both are where the difference between a demo and a deliverable is decided.

The skills here transfer to any agent platform, because they are not really about Hermes. They are about three disciplines. Naming the difference between what an agent can do and how it does it well. Separating the capabilities an agent merely claims from the capabilities you have watched it actually exercise. And extending an agent the right way, by teaching it rather than by assuming it knows. Hermes Agent is the concrete vehicle, because it makes all three visible, and visible is exactly what a consultant needs when a client asks, with every right, what this thing really does.

## Define the terms before you promise anything

Two words get treated as if they were the same thing, and the consultant who cannot tell them apart will over-promise in every demo. Tools are the actions an agent can take. They are verbs. Read a file, run a command, search the web, call a model, send a message. A tool is a function the agent can reach for and execute, and its result comes back into the conversation as something the agent can then reason about. Skills are the knowledge documents that tell the agent how to do a recurring task well. They are the accumulated judgment about a job: when to reach for it, what the steps are, where it goes wrong, and how to confirm it worked.

A tool is what lets an agent act. A skill is what lets an agent act the way your client wants. The distinction matters because they serve different consulting goals and they fail in different ways. A missing tool means the agent physically cannot do the task. A missing skill means the agent can do the task but does not know this client's rules for doing it right, which in practice is just as disqualifying. The client does not care that the agent technically can draft a reply. They care that it drafts the reply the way their compliance team requires, and that is a skill, not a tool.

Hermes makes the split concrete and inspectable. Tools come from a built-in registry organized into toolsets, each of which can be enabled or disabled per platform, and you can see them all with `hermes tools list`.[^1] Skills are on-demand documents that live in the profile's skills directory and are loaded only when the agent actually needs them.[^2] The agent does not carry every skill in its head at once. It carries a list of what exists, with a one-line description of each, and loads the full procedure only when the moment calls for it. That pattern, where the agent knows what it knows without carrying all of it, is the design that keeps a capable agent fast.

## What ships with Hermes, and what that really tells you

Here is the first place the honest consultant slows down. When you read that an agent "ships with" a broad set of tools, it is easy to hear a promise that all of them are available all the time. They are not. The tool registry is a catalog of what the software knows how to do, not a guarantee of what any given running agent can do in the moment you test it. The authoritative reference says it plainly: availability varies by platform, by credentials, and by which toolsets are enabled.[^3] That sentence is not a technical footnote. It is the whole lesson in one line.

Several things sit between a tool existing in the registry and that tool being real for a specific session. The toolset must be enabled for the platform you are actually using, and an agent on a locked-down messaging channel may have a narrower toolset than the same agent in a full desktop session. The tool's requirements must be met. Many tools only register when their credentials are present, so a web or vision or generation tool quietly disappears if the key that powers it is not configured. Some tools register only in specific circumstances, when a particular endpoint is reachable or when the agent was spawned for a particular kind of work. The word "ships with" is doing a lot of work in that sentence, and it is the consultant's job to refuse the ambiguity.

The consulting discipline is to treat the registry as a claim and the running agent as the evidence. When a client asks what the agent can do, you answer from what you have watched it do in the configuration you are handing over, not from the marketing list of what the software is capable of. That single habit, answering capability questions from observed behavior instead of from catalog prose, is what separates the consultant whose demos hold up from the one whose demos evaporate on a client machine.

## The three ways a capability turns out not to be real

Name the failure modes and you will see them in the field. The first is the tool that is listed but not enabled. The registry knows the tool, but the platform's toolset excludes it, so the agent cannot reach it no matter how plainly it was "shipped." The second is the tool that needs a credential it does not have. The tool exists and the toolset includes it, but the key is missing, so the tool never registers and the agent behaves as if it were not there. Both of these you can catch by inspecting the running configuration, which is exactly the verification reflex lesson 8 drilled into you.

The third failure is the one that most damages a consultant's reputation, because it is not a configuration problem at all. It is the model claiming to have done something it did not do. An agent asked to check a source can answer with a confident summary and never call the web tool. An agent asked to verify a fact can assert the fact is true and never run the check. In an interactive session you might not notice, because the reply reads smoothly and you were not watching the tool calls. The capability was never exercised, and yet the agent reported a result as if it had been.

That is why the consultant's standard for "real" has to be higher than the agent's own report. A capability is real only when you have evidence it fired: a tool call happened, or an artifact exists, or a command returned output you can look at. The moment you accept an agent's word about its own work without checking the trace, you have stopped being a consultant and started being an audience. Your persona in every client relationship should be the person who verifies, because the client is paying you to be exactly that on their behalf.

## How to extend an agent, and what each extension is for

Once you can see what an agent can do, the next question is how to give it more. There are two very different kinds of "more," and picking the wrong one is how consultants waste a client's budget on the wrong lever.

The first kind of extension changes what the agent can reach, its tools. You enable a toolset that was off, add credentials so a tool registers, or connect the agent to external systems that expose new actions. That kind of work is covered across this series, and the richest form of it, wiring an agent into a client's own stack through MCP servers and third-party integrations, is exactly where this course goes next. Reaching is about increasing the surface the agent can act on.

The second kind of extension changes what the agent knows how to do well, its skills, and it is the one most consultants underuse because it does not feel like engineering. A skill is how you teach an agent the procedures that are specific to your client's business without writing any code. You encode the way the client wants a recurring task done, the steps, the pitfalls, the way to confirm it worked, and the agent loads that procedure when the task comes up and follows it. The agent gets better at your client's particular work over time, and the knowledge persists across sessions rather than evaporating when the conversation ends.[^2]

The consulting power of skills is that they capture the part of your expertise that a model could never guess. A generic agent knows how to draft an email. It does not know that this client's outbound messages require a compliance sign-off, that a certain phrase is banned, that the reference number belongs in the subject line, that a promise about delivery must never be made without a status check. Those rules are not in the model. They are in your head and in the client's handbook, and a skill is the mechanism for getting them out of your head and into the agent so the client keeps them after you leave. That is the difference between handing over a tool and handing over an agent that does the job the client's way.

## How to know a skill is real, not just present

Skills need the same reality check as tools, and they rot in a quieter way. A skill can be installed and listed and still be wrong, because its content describes a procedure that no longer matches the current state of the thing it governs. A command changes, an endpoint moves, a process is retired, and the skill keeps telling the agent to do the old thing with quiet confidence. The skill is present. It is not real.

The discipline is to treat a skill the way you treat a tool and a memory the way this series has treated every assumption: as a claim to verify against the live system before you act on it. When a skill tells you a command or a version or an endpoint, confirm it still holds in the current state rather than trusting the document because it exists. When you inherit an engagement, audit the skills the previous consultant left behind the way you would audit their code, because stale procedures are how an agent confidently does the wrong thing for months while everyone assumes it is following current rules.

And be honest about what a skill is not. A skill is not a substitute for a capability the agent lacks. Teaching an agent the perfect procedure for sending a message does nothing if the agent has no tool that can send a message, any more than handing an employee the best manual in the world helps if you took away their phone. Tools and skills are complements. The consultant who extends an agent well checks both sides: can it reach what the task needs, and does it know this client's way of doing the task. Missing either one, the task fails.

## Worked example: checking what is real before you hand over

Put the disciplines together on the engagement you have carried through this series. You scoped it, deployed it isolated, configured it for the client's machine, and now you are at the point where you must tell the client what the agent can do and stand behind every word.

A claims-intake agent that drafts responses to customer queries is about to be handed to the client, and it will run on a messaging channel where the client's team talks to it all day. Before the handover you run the capability audit, and you do not trust the registry. You list the tools and check what is actually enabled on the channel the client will use, not on your full desktop session. You confirm the web and file toolsets are present there, because the agent needs to look up policy and read the account history. You check that the tools that require credentials are registering, because a search tool with no key behind it will quietly not exist when the agent reaches for it. Each tool you intend to claim for the client, you confirm is real in the running configuration.

Then you extend the agent the way the client's business actually works. You write the client's reply standards into a skill: the mandatory compliance review, the phrase that is never used, the rule that no delivery promise ships without a status check. You do not expect the model to know these. You teach them, because they are the part of this client's job that no generic agent would ever guess, and because teaching them is what makes the agent useful after you are gone.

Then the reality test, the one that decides the handover. You do not accept the agent's word that it now follows the rules. You give it a real query, the kind the team actually gets, and you watch it work end to end. You check that the agent loaded the skill when the task called for it, that it reached the status system before it promised anything, that it flagged the message for review instead of sending it, and that the output on the screen is what you told the client to expect. The capability you present at handover is the one you watched succeed, not the one the catalog promised and not the one the agent described.

The handover speech reflects the audit. When the client asks what the agent can do, you answer from the list you verified: it reads the account history, it looks up current policy, it drafts replies that follow your review rule, and it never ships a promise without a status check. Every item on that list is a thing you watched it do. There is no item on it that is true only because a brochure said so. That is the whole difference between a consultant who describes an agent and a consultant who has proven one.

## The pitfalls to avoid

**Answering from the catalog instead of the running agent.** "It ships with" and "it can, in this configuration, right now" are different claims, and only the second survives contact with a client. Verify what is enabled and what has its credentials before you promise it.

**Confusing a tool with a skill.** A tool lets the agent act. A skill tells it how to act the client's way. Promise the reach and teach the rules, and know which one a gap is on when the task fails.

**Trusting the agent's report of its own work.** A smooth answer is not evidence a tool ran. Check the trace, look for the artifact, confirm the command returned. A capability is real when you have watched it fire, not when the agent says it did.

**Treating an installed skill as a current one.** Skills rot as the world they describe changes. Verify a procedure against the live system before you rely on it, and audit inherited skills the way you audit inherited code.

**Teaching skills but forgetting the reach.** A perfect procedure is useless if the agent lacks the tool to carry it out. Extend both sides, what the agent can reach and what it knows how to do, or the task still fails.

## Try it

Take the engagement you have been carrying and run the capability audit on paper before you touch anything:

1. Name the tools. What does the agent need to reach for the task, and which toolsets and credentials make those real in the configuration the client will use?
2. Name the skills. What does the agent need to know about this client's business that no generic model would guess, and where would you encode those rules?
3. Name the evidence. For each capability you intend to claim, how do you watch it succeed, and what artifact or trace proves it fired?
4. Name the boundary. Which catalog capabilities are you deliberately not claiming, and why?

If you can answer all four, you can tell a client what an agent really does and be right. If your instinct is to open the agent and show a flashy demo before you have named what is real and what is only claimed, that is the builder reflex again, and it is the exact reflex this lesson exists to catch.
