# Lesson 17: Packaging Reusable Skills: Turning What You Build Once Into Assets You Reuse Everywhere

Lesson 16 taught you to size work into 30 to 45 minute windows you can actually finish and verify. That leaves an obvious question hanging. When the same shape of work shows up a second time, why are you solving it from scratch? In the last engagement you paid for every dead end and every wrong assumption out of your own budget. If none of that survived the engagement, you will pay for it again, and the client pays for it again through your hours. This lesson is about the discipline that stops that: capturing what you built as a reusable skill, written so it travels to the next client without leaking the last one.

## Reuse is a margin decision, not a convenience

Consulting sells time. That makes anything that lowers the hours a delivery costs, without lowering its quality, a direct change to your economics. It also makes reuse the difference between a practice and a series of one-off gigs.

Think about where the hours actually go on a first delivery. A small slice goes to the part the client asked for. The rest goes to discovery you had to do yourself, dead ends you had to walk into to rule out, integration details nobody documented, and assumptions you made that turned out to be wrong. On a second delivery of the same shape, almost none of that work should repeat. The parts that do repeat are the client's specifics: their systems, their names, their policies. Everything else should already be written down.

That split is the whole game. Client specifics belong in configuration and a handover document for that client. The decision path belongs nowhere in particular until you package it, which is why it gets lost. The procedure that worked, the order it has to happen in, the checks that proved it worked, and the pitfall that cost you an afternoon are not facts about a client. They are facts about the work, and they apply to the next client too.

The pitfall is the expensive part. Anyone can write down the happy path from a tool's documentation. What a client is really buying when they buy a proven delivery is that you already made the mistakes and the path avoids them. Every one of those mistakes you fail to capture, you will make again on someone else's invoice.

## What a skill is in the running system

A skill is an on-demand knowledge document the agent loads when the work calls for it. Hermes structures this in layers so the knowledge costs almost nothing until it is needed: the skill index carries names and descriptions, the full body loads only when a skill is triggered, and each additional reference file loads only when a question needs it. [^1]

That layering has one practical consequence worth internalizing before you write a word. The description is the trigger. It is the only part loaded when the agent is deciding whether this skill is relevant, so a description that names the situation ("use when a client's inbox needs triage rules") earns the skill a chance to load, and a description that names the topic ("inbox stuff") does not. Write the description for the decision, not for the table of contents.

The second thing to internalize is what belongs in the body. Skills hold lessons, not logs. A pitfall is a general rule plus a short clause of why, attached to the step it affects, stated once. Incident narration, ticket numbers, dates, and quoted conversations are not skill content, because they do not help the next person decide anything. The test is simple: if the rule cannot stand without the story behind it, it is not a rule yet. [^3]

## The test for what deserves to be a skill

Not everything should be packaged. A skill you never load is worse than no skill, because it costs index space and attention. Four gates, in order.

Has the shape repeated, or will it? Once is an anecdote. Twice, or a known recurrence, is a pattern. If you catch yourself reconstructing the same sequence for the second time, stop and write it down while the reconstruction is still in your head.

Is it non-trivial? If the procedure is one obvious command, it does not need a skill. It needs a line in the handover document. Skills are for work where getting the order wrong, or skipping a step, produces a failure that is not obvious at the time.

Did it cost you something to learn? A skill with no pitfall is usually a restatement of a manual. The pitfall section is where your value lives.

Can you verify it? If you cannot say how you know the procedure worked, you are writing down a ritual. Verification is not optional; it is what lets the next person trust the asset.

One more filter, and it is the one consultants get wrong most often. Strip the client before you decide the skill exists at all. "How we onboarded Acme's mail server" is not a skill; it is an engagement note. "How to onboard an agent to a client's mail server, in order, with the checks" is a skill, and Acme is one configuration of it. If a candidate skill reads as client-specific all the way down, the transferable core is thin, and you should write a checklist for the handover instead.

## What goes in the file

A skill is one markdown file with a small frontmatter block and a body with a fixed shape. The frontmatter carries the name, a short description that starts with the trigger, optional platform restrictions so a macOS-only procedure does not confuse a Linux client, and optional categories and tags for organization. The body carries the procedure in the order it has to happen, the pitfalls tied to the steps they affect, and the verification that proves the result. [^2]

```
---
name: client-inbox-triage
description: Use when a client wants staged inbox triage rules.
platforms: [macos, linux]
---

# Client inbox triage

## When to Use
## Procedure
## Pitfalls
## Verification
```

Two details in that shape are doing more work than they look like. Keeping the procedure ordered matters because a lot of agent work is order-sensitive: wiring an integration before the credentials exist produces a failure that reads like a broken integration. And the verification section is what makes the asset honest. "The alert landed in the client's channel and the message text matched" is verification. "The job ran" is not, because a job that runs and delivers nowhere looks identical to a job that works until someone checks where the message went.

## Capture it while the lesson is still fresh

The most common way reuse dies is timing. People plan to write the skill at the end of the engagement, then write it from memory, and what comes out is the happy path with the pain removed. The pitfall that cost two hours gets compressed into a sentence that no longer explains the mechanism, so the next person reads it, does not believe it, and walks into the same wall.

Write the skill the moment the thing works. You wanted to package it right after the dead end, while you still remember what you believed that was wrong. If you cannot write it then, write the raw notes then and package later, but never reconstruct the pitfall from memory after the fact.

This is a place where an agent pulls its weight on the consultant's behalf. In Hermes the agent can create, patch, and delete its own skills through a dedicated tool, which is how it records a non-trivial workflow for reuse. The system prompt asks it to capture a procedure when it works out a multi-step workflow, when it resolves an error or a dead end, and when the user corrects its approach. Those three triggers are exactly the moments worth capturing on a client engagement too. In an environment where someone needs to review what lands, a write-approval gate can require sign-off before any skill change takes effect. [^3] [^6]

## Stripping the client out

An asset that carries one client's secrets or names is a liability, not a reusable skill. Three rules cover almost every case.

Never put a credential in a skill file. Reference the variable name, not the value, and let the environment hold the secret. Hermes skills can declare the environment variables they need without making the skill disappear from discovery, and the values are passed through to the sandbox the skill's scripts run in, so the file stays shareable while the secret stays out of it. [^2]

Parameterize paths and preferences instead of hardcoding them. A skill that declares non-secret settings (a data directory, a default recipient, a retention window) in configuration can be reused across clients unchanged, with the difference living in each client's config rather than in a fork of the procedure. [^2]

Scrub names, hostnames, and account identifiers. If the example in the skill is a real client's system, a reader you hand the file to learns something they should not, and the file becomes something you cannot share. Write examples with placeholder names. A useful side effect is that placeholders make the general shape of the procedure visible, which is the part you are actually shipping.

## Making the asset reachable

A skill nobody can load is still a loss. Four delivery shapes, and the choice is about who needs it.

Per-profile skills. Hermes profiles each carry their own skills directory, along with their own configuration and credentials. That isolation is what makes a per-engagement profile a clean unit: the client's agent has the skills and the secrets for their systems and nothing from anyone else. Keep the durable, transferable skills in your working profile and let the client's profile carry the client-specific ones. [^7]

A shared external directory. If you maintain skills outside the profile, a shared team directory checked into version control can be scanned alongside the local skills and behaves exactly like a local one, including showing up in the index and as a slash command. That is the shape for a practice asset you and your team both use: one copy, one place to fix it. Note that it is not a read-only boundary, so treat write access as a real permission decision. [^5]

A bundle. A bundle is a named group of skills plus optional standing instructions, invoked with one short command, and it can be checked into a shared repo and linked into place so a whole team gets the same "task profile" without remembering four individual commands. Bundles do not install anything; they alias skills that must already be present, and missing skills are skipped rather than fatal. [^4]

A hub install. For third-party skills, installation goes through a scanned path with a lock file recording the source and content hash, and organizations can publish their own tap so their standard skills install the same way a public one does. [^6]

Pick the smallest shape that solves the problem. A two-person practice does not need a tap. A client team that will keep using the agent after you leave probably does need the skills sitting in their own repo, because that is what survives you.

## Worked example: packaging the second inbox engagement

Take the engagement from last lesson, where a client asked for an agent that watches an inbox for urgent mail and alerts the team in chat. You scoped it as five slices: install and verify, profile and skill, chat wiring, schedule, handover. It shipped. Now a second client asks for something close.

If you did nothing after the first engagement, you repeat all five slices and rediscover every pitfall at full price. If you packaged while it was fresh, the second engagement looks different. The install and verify slice collapses into a checklist you have already proven. The profile and skill slice becomes: copy the profile pattern, add this client's configuration. The chat wiring is the same wiring with a different destination. The schedule is the same job with a different target, and the failure you paid for the first time (a job that ran cleanly and delivered to a target nobody set) is now a verification step that runs every time. What is genuinely new is the client's specifics: their mail taxonomy, their urgency rules, their channel.

So the reusable asset is not "the inbox agent." It is four things: a provisioning checklist, the ordered procedure for wiring a chat integration and confirming a test alert lands, the scheduling pattern with its pitfall written as a rule, and a verification block. That is one skill file and its reference files, maybe two, and it turns five slices of uncertain work into two slices of work plus configuration.

![Worked example of packaging the second inbox engagement: five slices of uncertain work become two slices of work plus configuration](</diagrams/packaging-reusable-skills/3-worked-example.png>)

The economics are the point. The second delivery takes a fraction of the hours and carries less risk, and the client is buying a path with a known failure mode already closed rather than a first attempt. That is the difference between selling your time and selling a proven method, and it only exists if you packaged it.

## Try it

Take the work you finished most recently, ideally the thing you are proudest of finishing quickly, and package it:

1. Write the trigger situation in one line, in the form "use when...". If you cannot write it as a situation, you are not ready to package.
2. List the steps in the exact order they have to happen. Mark any step that only works after an earlier one.
3. Add one pitfall per step where the failure was not obvious at the time, each as a rule plus a short why.
4. Write the verification: how a stranger confirms the procedure worked, without trusting anyone's summary.
5. Strip it. Remove every credential, client name, hostname, and account identifier, and replace the ones you need with placeholders or declared configuration.

Then decide where it lives. If it is yours to reuse, it belongs in your working profile. If it is the client's to keep, it belongs in their repo, and it becomes part of the handover.

## What's next

You can now turn a solved problem into an asset: decide what deserves packaging, capture it while the lesson is fresh, strip the client out, and put it where the next person can actually load it. The next lesson is about the other half of leaving a client better off than you found them. It is about documentation and handover: making the client self-sufficient after you leave. Where this lesson taught you to package what you built so you can reuse it, the next one teaches you to package it so the client can run it without you, which is the difference between a dependency and a deliverable.
