# Lesson 14: Testing and Verification: Proving It Works Before You Claim It Does

Every previous lesson in this series handed you a sharper version of the same warning. Lesson 9 told you a capability is real only when you have watched it fire, not when the agent says it did. Lesson 12 told you the deliverable is a working artifact, not a plan. Lesson 13 told you to prove the refusal, to watch the guardrail work before you trust it. This lesson is where all of that becomes a method. It is about testing and verification, the craft of proving an agent does what you say it does, before you say it to the client.

The stakes are the whole engagement. When you hand a client an agent and tell them it works, you are making a claim they will act on. They will point real customers at it, or turn it loose on real data, or schedule it to run with no one watching. If your claim is wrong, you have not just made an honest mistake. You have sold trust you did not earn. The only way to earn it is to test the work, verify it against the live system, and carry the evidence into the handover. That discipline is not a Hermes feature. It is a consulting skill you take to any platform, and Hermes is simply a good place to learn it because the tools make proof visible.

## Define the terms: a claim is not a result, and a result is not proof

Start with words, because consultants lose credibility in the gap between them. An agent produces two kinds of things. The first is a claim, which is what the agent says about its work: a summary, an answer, a sentence that begins with "done" or "it should work." A claim can be smooth and confident and entirely wrong. The second is a result, which is what actually happened in the world: a file that now exists, a command that returned output, a tool that fired and left a trace. The gap between the claim and the result is where fabrication lives, and it is the consultant's job to close that gap.

Testing is running the agent's work and watching it happen. Verification is checking the result against what you expected, using the system rather than the agent's word. They are two halves of one habit. You test to see whether the agent does the task, and you verify to confirm the task actually took effect. A test that shows no error is not proof the result is correct, and a result that looks right is not proof the test ran. You need both, and you need each one grounded in something you can point at.

The rule that holds all of it together is simple enough to write on a sticky note: a claim is only as good as the evidence behind it, and the evidence is never the agent's description of its own work. When an agent tells you it updated a record, you do not update the client. You read the record and check. When an agent tells you a command ran, you look at the output and the exit code, not the summary sentence. Your persona in every client relationship is the person who verifies. That is the persona you have been building since lesson 9, and this lesson makes it systematic.

## The first tier of proof: run it and watch the tool fire

The cheapest proof is watching the work happen. In an agent, the work happens through tools, and a tool that fires leaves evidence you can read. Lesson 9 introduced the habit of checking the trace to confirm a tool ran. This lesson pushes that habit further, because Hermes makes the evidence unusually explicit.

When the agent runs a command through the terminal tool, it does not just receive a polite summary. It receives the command's actual output and its exit code. An exit code of zero tells you the command completed; a nonzero code tells you it failed. And when a command is killed rather than failing cleanly, the result carries a plain-language note instead of a bare number, so a process that died by signal, by the out-of-memory killer, or by an explicit kill is labeled for what it is rather than handed to you as an ambiguous digit. [^1] That annotation exists precisely so the agent, and you, can tell a real failure from a quiet one. Read the exit code and the output. Do not read the sentence the agent wrote about them.

The same discipline applies to the tools that do not run commands. A web tool returns the page it actually fetched, not a claim that it fetched one. A file tool returns a diff or the on-disk content, not an assertion that an edit landed. The consulting reflex is to look at what the tool handed back and judge it against what the task needed, instead of accepting the agent's framing. Every tool is a witness, and the witness's account is the output, not the summary paragraph that follows it.

## The second tier of proof: verify the result, not the report

Watching a tool fire proves the agent tried. It does not prove the result is right. A command can succeed and still do the wrong thing. A file edit can return a clean diff and still be the wrong content. The second tier of proof is verifying the result in the system, reading it back the way a customer would, and confirming it matches what you promised.

This is where the running engagement in this series finally gets tested. Across lessons 10 and 11 you wired a claims-intake agent to the client's ticketing platform and their customer data service, and you scheduled a weekly summary that pulls the intake queue and reports on it. In lesson 13 you secured those credentials and set the guardrails. Now you are at the moment every engagement reaches: the agent claims it can produce the summary, and you are about to tell the client it can. Before you do, you test it, and you do not test it with a cheerful prompt that lets the agent describe what it would do.

You give it a real run against the real source. You ask it to pull the current intake queue and produce the weekly summary, and then you check the three things that prove it. First, did it actually reach the data service, which you confirm by watching the read happen rather than trusting that it did. Second, is the summary accurate against the source, which you confirm by pulling the raw numbers yourself and comparing them, not by trusting the agent's arithmetic. Third, is the output in the format the client's team actually reads, which you confirm by opening the file, not by taking the agent's word that the file looks right.

That read-back is the whole lesson in miniature. The agent is a generator of drafts, and every draft, however confident, is a hypothesis until you check it against the source. Your value as a consultant is that you are the one who checks. When the summary's count matches the count you pulled yourself, and the file renders the way the team expects, then you have evidence, and only then do you have a claim you can take to the client.

## The third tier of proof: make the test repeatable

Watching one run succeed proves it worked once. Clients, and your reputation, need it to work every time, which is a different problem. The third tier of proof is turning the one-off test into a repeatable gate, a check that can be run again after any change and that fails loudly when something silently breaks.

Two Hermes capabilities make the gate practical, and both are transferable ideas. The first is a reproducible environment for running the test. The terminal tool does not have to run on your machine. It can run against an isolated container, a remote server, or a cloud sandbox, so the test exercises the same code in the same way on a clean surface instead of depending on whatever your laptop happens to have installed. [^1] When a test passes in the same environment the client will actually use, it means more than a test that only passes on your setup. That is the lesson 8 lesson, applied to testing.

The second capability is encoding the verification step so it does not depend on the agent remembering to do it. The skill format carries a dedicated Verification section, where you write down how to confirm the work succeeded, and the agent loads that procedure when the task comes up and follows it. [^2] You are not trusting a model to improvise a quality check every week. You are writing the check down once, in the same place as the procedure, so the agent runs it the way you taught it. That is the difference between an agent that happens to produce good work and an agent that can be trusted to keep producing it.

A repeatable gate also changes how you handle a failed run. When the check fails, you do not smooth it over and push anyway. You read the failure, fix the cause, and run the gate again until it passes. The gate is not a formality you satisfy to get a green tick. It is the mechanism that keeps a silently broken agent from being handed to a client as if it were fine.

## The pitfalls to avoid

**Trusting the agent's summary instead of the tool's output.** A smooth "done" is not evidence. Read the exit code, the returned content, and the diff, and judge those against the task. When the agent's prose and the tool's output disagree, the output wins.

**Testing once and calling it verified.** A single successful run proves one run. Reproduce the test in a clean environment and turn it into a gate that can be rerun after any change, or you are one edit away from handing the client something broken and not knowing it.

**Verifying the report instead of the result.** Watching a tool fire shows effort, not correctness. Read the result back in the system, compare it to the source, and confirm it matches what you promised, the way the client's own team would use it.

**Leaving the quality check to the agent's memory.** A model improvising a verification step will skip it. Write the verification down in the skill where the procedure lives, so the agent runs your check instead of hoping to remember it.

## Try it

Take the engagement you have been carrying and build its proof, on paper, before you run anything:

1. Name the claims. What are you about to tell the client the agent can do, in plain sentences?
2. Name the evidence for each claim. Which tool fires, and what does it return, that you can point at as proof?
3. Name the read-back. For the claim that matters most, how would you check the result in the source yourself, independent of the agent?
4. Name the gate. What repeatable check would catch a future change that silently breaks this behavior, and where would you write it down so the agent runs it every time?

If you can answer all four, you can make a claim to the client and stand behind it. If your answer to number three is that you would trust the agent's report because the tool call looked clean, you are not verifying yet. You are still taking the claim on faith, and that is exactly the gap this lesson exists to close.

## What's next

You can now prove an agent works before you claim it does, by watching the tool fire, reading the result back against the source, and turning the test into a repeatable gate. Testing tells you whether the work is true. The next lesson takes up what you do with that truth in the last stretch of delivery. It is about the finishing-the-job discipline: delivering working artifacts instead of plans, and reporting honest blockers instead of fabricating output when something fails. Where this lesson asked how you know an agent's work is right, the next one asks how you close out the work, hand over something that actually runs, and tell the client the truth when it does not.
