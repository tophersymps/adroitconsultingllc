# Lesson 15: The Finishing-the-Job Discipline: Working Artifacts Over Plans, Honest Blockers Over Fabrication

By this point in the series you have scoped an engagement, mapped the stakeholders, wired the agent to the client's systems, and proven each piece works in the running environment. You have the capability. This lesson is about the harder thing: reliably finishing. When a client asks for a deliverable, the risk is not that your agent cannot do the work. The risk is that it will produce something that reads like the work, that looks complete, and that is not actually done. The discipline that kills that risk is the subject of this lesson, and it transfers to any agent you build or review, on any platform.

The rule is simple to state and hard to keep. A consultant's job is to deliver working artifacts backed by real evidence, not descriptions of what could be done. And when a task genuinely cannot be finished, the consultant's job is to say so plainly and state the blocker, never to fill the gap with plausible-looking output. Hermes Agent is the concrete vehicle because it makes both halves of that discipline visible: it hands the agent tools that actually execute work, and its collaboration surface treats an unverified claim the same way a sharp client does, as a claim, not a result.

## Define the terms: what finishing actually means

Name the difference before you rely on it. A plan is a description of work someone intends to do. An artifact is the work itself, the thing a user can touch, run, read, or verify. A requirements document is a plan. The configured system that fulfills those requirements is the artifact. A writeup that says "the agent will monitor the feed and alert on anomalies" is a plan. The agent that monitors the feed, and the verified alert that landed, are the artifact. The consulting value sits entirely in the artifact. Nobody pays to read a more detailed description of the work they already asked for.

Hermes makes the distinction concrete by giving the agent tools that do the work rather than talk about it. It has a terminal tool that runs real commands against the live system, a patch tool that edits files in place, a code-execution tool that runs Python against the actual environment, and file tools that write the deliverable to disk.[^1] None of these are optional flourishes. They are the difference between an agent that can finish and an agent that can only narrate. When you review an agent's work, you are not looking for a good explanation of what it did. You are looking for the artifact it left behind, and the evidence that the artifact works.

The second term is the honest blocker. A blocker is a genuine obstacle that prevents completion: a credential you do not have, a system that will not accept the change, a network path that times out, a fact you cannot verify. Fabrication is the act of inventing output to hide the blocker, producing a plausible-looking answer that fills the gap without being true. The discipline requires you to report the blocker as a blocker, with the actual reason, rather than converting it into a confident guess. A client would far rather hear "this step is blocked because the test environment is down" than receive a finished-looking deliverable built on an unverified assumption.

## Working artifacts over plans

The habit to build is one of execution before narration. When you or your agent take on a task, the deliverable is the working result, not a description of the steps. Hermes enforces this in its own behavior: it uses its tools to make real changes, runs the verification, and reports what the tool output actually showed. The pattern is worth copying into every engagement you touch, whether the agent is Hermes or any other tool.

The concrete move is to run the thing, not summarize the thing. If the task is to check that a service is healthy, run the check and record its output. If the task is to reconfigure a workflow, apply the change through the tool that makes it, then confirm the new state in the running system. If the task is to compute a number, compute it. Every one of these has a real tool in Hermes that does exactly that.[^1] The moment you catch yourself or your agent about to describe an action instead of taking it, stop and reach for the tool. A summary of a command you have not run is not a result. It is a plan wearing a result's clothes.

This is where the small, high-trust tools matter as much as the big ones. Reading a file, searching a codebase, listing the running processes: these are cheap, and doing them grounds every claim you make in what is actually true on the client's system rather than what you assume to be true. An agent that reaches for the real state instead of recalling it is an agent whose answers survive contact with reality. You cannot finish a task you have only half observed, because you do not yet know what is there to change.

## Honest blockers over fabrication

The second half of the discipline is what you do when you cannot finish. It is the more important half, because it is where trust is either built or destroyed, and it is the failure mode clients have learned to expect from AI work.

The failure is fabrication: inventing a plausible-looking result to cover the gap. An agent that cannot reach the client's database does not say "I could not reach the database, and here is why." It is tempted to say "the database returned 128 new records," picking a number that sounds reasonable. This is the worst possible failure, worse than an obvious crash, because it is invisible. The client builds decisions on the invented number. They discover it is fake days or weeks later, after they have acted on it. At that point, the agent has not just failed the task. It has made the entire engagement suspect, because if one invented number was presented as real, the client can no longer trust anything else the agent produced without checking it themselves. That is the end of the value the agent provides.

So the honest blocker is a positive discipline, not a confession. You report, precisely and without drama, what is blocked, why, and what would unblock it. Hermes models this on its own collaboration surface. On a kanban board, a task that needs something the agent cannot supply is moved to a blocked state with an explicit comment, rather than being marked done with invented evidence. The system even refuses to let a worker mark a task complete until the task contract is verified; a commit or a diff alone never counts as done, and when human action is needed the right move is to block the task and surface it rather than fake completion.[^2] That is the discipline made structural. When you cannot verify, you do not claim done. You say what stands in the way.

The same honesty extends to uncertainty about your own knowledge. When you do not know a fact, a version, or an endpoint, the professional answer is to say you do not know and go find it, not to supply the most likely guess. A guessed API endpoint or a guessed release date is fabrication with better grammar. The reader of your deliverable cannot tell the difference between a guess you did not label and a fact you verified. Label your uncertainties, or remove them, but never dress them up as findings.

## Verification is the finish line

A claim is not finished until it is verified. This is the bridge between the two halves of the discipline, and it is worth its own section because it is where the discipline becomes observable to the client.

The standard to hold is simple. "It should work" is not a status. "It works, here is the proof" is a status. The proof is the actual tool output, the actual returned value, the actual rendered page, the actual run log. Hermes is built around this: its agent has a verification habit that checks the result of a change against the system before reporting success, and it treats a tool call that succeeded as a completed step rather than a described one.[^1] When you hand over work, you should be able to point at the artifact and at the evidence that it does what you say it does. Everything short of that is intent, not delivery.

There is a sharpness to this that matters in consulting. A client who hears "I think it should work" has to decide whether to believe you, which means they have to trust you, which means the relationship is carrying the weight that verification should carry. A client who hears "here is the run, here is the output, here is the artifact" has nothing to weigh. They check the evidence themselves, or they accept it, and either way the claim rests on something real rather than on your say-so. The discipline converts your credibility from a reputation you ask the client to take on faith into a set of artifacts they can examine.

This is also why the discipline compounds. Every time you finish a task by verifying it, you produce a small piece of evidence. Every time you hit a real blocker and report it, you produce a small piece of trust. Over the arc of an engagement, those accumulate into a working relationship where the client stops bracing for the other shoe. That is a commercial advantage you cannot get by being charming in the status update.

## The learning loop: finish, then get better

There is a third move that separates a consultant from a professional, and it comes after the artifact is done. The finishing-the-job discipline is not just about the current task. It is about making the next task finish faster.

Hermes makes the loop explicit. When the agent solves a problem, discovers a workflow, or gets corrected, it can save what it learned as a skill, a reusable procedure that loads into future sessions so it does not rediscover the same thing twice.[^3] It can also save durable facts about the engagement and the environment to its persistent memory, so the next session starts with the context the last one earned.[^4] These are the finishing habits applied to your own improvement: you do not finish a task and walk away. You finish it, you verify it, and you capture the part worth keeping so the next engagement starts one step further along.

For you as the consultant, this is the same reflex, and it does not depend on the platform. After a deliverable, ask what you learned that is reusable: the client's conventions, the quirk in their environment, the integration detail that took an hour to find. Write it down where the next engagement can find it. A professional who finishes a job and forgets everything it taught them has done the job once. A professional who captures the lesson has done it once and gets paid for it again in speed and accuracy on the next one.

## Worked example: closing out the claims-intake engagement

Put the discipline on the engagement you have carried through this series. In lesson 14 you turned the claims-intake win into a weekly report that fires on a schedule. This lesson is about the quality of every run of that report, and about how you close out the engagement cleanly.

Take a Friday when the report fires. The honest-blocker test is immediate: if the ticketing platform is unreachable, the report cannot pull the week's intake. The wrong behavior is for the report to invent the numbers it could not retrieve, delivering a confident-looking weekly summary that has no basis in the data. The right behavior is for the report to fail loudly, state that the platform was unreachable, and deliver nothing rather than fiction. That is the discipline in its purest form, and it is exactly the design you want to hand to the client, because it means they can trust every number that does land.

The working-artifact test is just as direct. Before you hand over the report as a finished deliverable, you watch it run on its own and you read the delivered output against what you know should be there. You verify the counts, you confirm the summary landed in the right channel, and you have evidence that the process works without you. That evidence is the artifact. When you tell the client "the report fires Friday at five, covers the week's intake, flags what it could not verify, and lands in your channel," every word of it is something you watched happen, not something you hoped would.[^2]

Then you close out by capturing what the engagement taught you. The client's ticketing conventions, the shape of their data, the one integration that always needs a retry: these go into your notes and your reusable procedures, so that the next engagement for this client, or the next client with the same stack, starts from the hard-won details instead of from zero.[^3][^4]

## The pitfalls to avoid

**Describing instead of doing.** If you or your agent have written a paragraph about what a task involves but have not produced the artifact, you have not started delivering. Reach for the tool that does the work, then report the result.

**Inventing output to look busy.** Fabricated numbers, guessed endpoints, and confident unknowns are the one failure that costs a client real money, because they build decisions on fake ground. An honest blocker is always cheaper than a confident fabrication.

**Confusing intent with delivery.** "I think it should work" is intent. "Here is the run and here is the output" is delivery. The client should never have to take your delivery on faith.

**Treating "it ran" as "it worked."** A scheduled job that fires and produces garbage has not succeeded. Verification means the output is right, not just that a process completed.

**Walking away without learning.** Finishing a task and forgetting what it taught you means the next engagement pays full price for the same lesson. Capture the reusable part while it is fresh.

## Try it

Take the last piece of work you finished and run it through this audit:

1. Name the artifact. What concrete thing did you produce that a user can run, read, or verify?
2. Name the plan. What did you describe that you did not build? For each one, why did you stop short?
3. Name the verification. What did you actually run, and what did its output show, that proves the artifact works?
4. Name the blocker. Was there anything you could not do? If so, did you report it honestly, or did you fill the gap with a guess?
5. Name the evidence. If a client asked you to prove the work was done, what would you point at? A run log, a file, a screenshot, a passed check?
6. Name the lesson. What did this task teach you that the next one could reuse?

If you can answer all six with specific evidence, you finished. If any answer is vague or leans on what you meant to do, that is the gap the discipline exists to close. Go do the work, then come back and answer again.

## What's next

You now have a discipline for finishing: deliver verified artifacts, report blockers honestly, and capture what you learn. That discipline collides with a practical question as soon as you are working inside an engagement with real constraints. How do you know, up front, that a task fits the time you have, and why does working in small, scoped windows make the finishing discipline easier to honor? The next lesson is about estimation. It covers scoping a task to a 30 to 45 minute work window, and why small tasks ship reliably, because a task you can actually finish in one sitting is a task you can verify, and a task you can verify is a task you can truthfully report as done. Where this lesson taught you to finish, the next one teaches you to size the work so finishing is achievable.
