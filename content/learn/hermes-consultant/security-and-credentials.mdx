# Lesson 13: Security and Credentials: Secrets, Least Privilege, and Keeping the Client Safe

By this point in the series you can install agents, wire them to the client's systems, and turn wins into recurring work. Those wins all have a price, and the price is access. The claims-intake agent in the earlier lessons reached the client's ticketing platform and their customer data service, which means somewhere in the setup there is an API key, a token, or a credential that lets it do that. That credential is now the most sensitive thing in the engagement. It is worth more to a thief than the agent itself, and how you store, scope, and hand it over is a security decision that outlives your time on the project.

This lesson is about that responsibility. It teaches the transferable craft of keeping the client safe: treating secrets as a liability, granting the least access the work actually needs, and building guardrails so a mistake or a malicious input cannot become a breach. Hermes Agent is the concrete vehicle because it exposes every layer of the problem clearly, from where credentials live to how commands are approved to how a hostile file gets scanned before it reaches the model.

## Define the terms: secrets, least privilege, and the guardrails that back them

Start by naming the three ideas, because consultants who skip the definitions usually skip the security too.

**A secret** is any credential that unlocks access: an API key, a personal access token, a service account password, an OAuth token, a database connection string. The defining property is not what it looks like. It is what it can do. A token that can read a client's customer records is a secret even if it is short and unremarkable. The moment you treat credentials by their looks instead of their power, you start making the mistakes this lesson warns against.

**Least privilege** is the principle that any actor, human or agent, gets only the minimum access required to do its job, and nothing more. The agent that drafts email replies does not need write access to the billing database. The agent that reads the intake queue does not need the ability to deploy to production. Least privilege is not one configuration. It is a habit you apply at every boundary: which tool can run, which command is allowed, which file can be written, which website can be reached.

**Guardrails** are the enforced limits that make least privilege real even when the agent or the human makes a mistake. A guardrail is not a promise to behave. It is a mechanism that refuses. This distinction matters, because consultants who rely on the agent being careful are relying on something that fails. A compromised prompt, a wrong model output, an over-permissive habit, and the careful-agent assumption is gone. The guardrail is what is left standing.

Hermes Agent is built on defense in depth, meaning no single control is trusted alone. It layers user authorization, command approval, file write safety, container isolation, credential filtering, input scanning, cross-session isolation, and input sanitization. That layering is the professional's model: never one lock, always several, so that a failure in any one layer does not become a breach. [^1]

## The consultant's job starts with how you hold secrets

The first test of your security discipline happens before you configure anything. It is in how you handle the credential the client hands you. Most breaches in agent engagements do not start with a sophisticated attack. They start with a secret being stored, logged, or pasted somewhere it can be read.

The hard rule is this. A secret never goes in a file that is committed, pushed, or shared. It never goes in chat, because chat is logged and logs leak. It never goes in a document you will send the client as a deliverable. It does not belong in the prompt, in a code comment, or in a skill you will publish. The moment a secret touches any of those places, treat it as compromised and rotate it.

The professional pattern is to keep secrets out of the agent's code and prompts entirely, and to store them in a dedicated secrets location with restricted file permissions. In Hermes, that place is `~/.hermes/.env`, loaded by the process and read by the agent through the environment rather than written into any instruction. The security guide is explicit about it: keep API keys in the env file with proper file permissions, and do not let the agent write into the credential stores at all. Writing to `~/.hermes/.env`, `auth.json`, SSH keys, and other credential paths is hard-blocked regardless of any other setting. The platform refuses before the agent can even try. [^4][^8]

The corollary is that you never paste a real secret into a conversation just to test whether it works, and you never ask the model to print one back to you. Secrets stay in the env file, the agent reads them from the environment, and they are never echoed into the session where a log could capture them. When the model's own error handling meets a secret, Hermes redacts the value before the error reaches the model, so a tool that fails with a leaked token in its message does not hand that token to the agent. [^5]

## Grant the least access the work needs

Least privilege is where security becomes a design decision rather than a storage decision. When you scope an agent for a client, you make a series of access choices, and every one of them should be the minimum that still lets the work happen.

The first choice is which commands the agent may run. A capable agent has tools that can do real damage: recursive deletes, disk writes, system service changes, dropping tables. Hermes meets this with an approval system. Dangerous commands are classified, and in interactive sessions a human approves or denies them. The important part for the consultant is the default for unattended work. In cron jobs, in one-shot sessions, and on programmatic surfaces, the default is deny, meaning a scheduled agent that hits a dangerous command is blocked rather than auto-approved. [^2]

That default matters because it is the least-privilege answer to a real question. When you hand the client a recurring agent, do you want it able to delete files and stop services with no one watching? The deny default says no. It forces the agent to find a safe path or fail, and a failure you can see is better than a destructive command no one approved. There is also a floor that no setting can lower. A small set of catastrophic commands, irreversible filesystem wipes and fork bombs among them, is refused outright even when approval mode is off, because no amount of trust makes wiping the client's disk a good idea. [^3]

The second choice is what the agent can write. A file write sandbox confines the agent to a directory root you choose, and anything outside it is hard-blocked. Set it to the project directory and the agent cannot touch system files, other projects, or the agent's own control files. [^4]

The third choice is what the agent can reach on the network. A blocklist restricts which domains the web and browser tools can access, which is how you keep an agent away from internal admin panels and sensitive internal services. URL-capable tools also refuse private network and loopback addresses by default, a protection called SSRF prevention that stops an agent from using one server to probe or fetch the internal network behind it. [^6]

The discipline is to set these before the agent does anything, and to justify each grant. If you cannot say why the agent needs a given command, a given write target, or a given domain, it does not get it. This is the same muscle as the scoping discipline from lesson 3. You would not scope a project vaguely, and you should not scope an agent's power vaguely either.

## Keep the guardrails between a mistake and a breach

Least privilege limits what a well-behaved agent can do. Guardrails matter even more when the agent is not well-behaved, and the most common cause is input you did not expect: a file the agent reads that tries to steer it. This is prompt injection, and it is the attack every agent implementation eventually meets.

The threat is concrete. A context file like an AGENTS.md or a project readme can contain instructions that look like commands to a model, telling it to ignore its real instructions, read secret files, or exfiltrate data over the network. Because the agent treats that text as context, a hostile or just sloppy file can hijack it.

Hermes scans context files for prompt injection before they enter the system prompt, looking for instructions to disregard prior guidance, hidden comments, attempts to read credentials, exfiltration patterns, and invisible Unicode tricks. A file that triggers the scanner is blocked entirely and never loaded. [^7] This is a guardrail, not a suggestion. You cannot stop a model from being suggestible, but you can stop a hostile file from reaching it.

The same layering protects the sandbox. When a credential is passed to an MCP server subprocess, Hermes strips the environment down to a safe allowlist and only forwards what the server's config explicitly declares. A tool does not inherit every environment variable on the host, so an API key sitting in your shell does not leak into a subprocess that has no business seeing it. [^5]

## Worked example: hardening the claims-intake engagement

Bring it together on the engagement you have carried through this series. In lesson 10 you wired the claims-intake agent to the client's ticketing platform and their internal customer data service, and in lesson 11 you scheduled a weekly summary. Access was the price of all of that. This lesson is where you secure it.

Start with the secrets. The client gives you two tokens: one that reads the ticketing platform and one that reads the customer data service. You never paste them into chat. You do not put them in a config file you will commit. You put each in the env file with restricted permissions, and you confirm the agent reads them from the environment. You write down, in your own private notes, which service each token unlocks and where it lives, so you can document it at handover and rotate it if anything changes. You check that neither token appears in any file in the repo. [^8]

Then least privilege. The weekly summary agent reads the intake queue and composes a report. It does not need write access to the ticketing platform, and it does not need to send anything. So you give it a read-only scope and you confirm its dangerous commands default to deny, because a scheduled job that can modify tickets or stop services is more power than the job needs. You set the write sandbox to the project directory so the agent cannot touch anything outside it. You add the client's internal admin host to the blocklist so the agent cannot reach a surface that should stay human-only. [^2][^4][^6]

Then the guardrails. You scan the context files the agent will read and you fix or quarantine anything that looks like injection. You confirm the web tools refuse the client's internal network by default, so a prompt-injected instruction cannot turn the agent into a bridge into the client's private systems. You test the failure mode: you give the agent a prompt that tries to make it read the env file, and you watch the platform refuse. That refusal is your proof, the same way the earlier lessons proved a capability by watching it run. [^6][^7]

When you hand the system over, security is part of the handover, not an appendix. You document where each secret lives, what each token can and cannot do, and how the client rotates one if they suspect exposure. You tell them which commands are denied by default, which writes are sandboxed, and which domains are blocked, so the client knows the boundaries they are inheriting. You hand over a system whose safety does not depend on anyone being careful, because it is enforced by the guardrails you set.

## The pitfalls to avoid

**Treating security as a storage problem only.** Where the secret lives matters, but least privilege and guardrails matter just as much. A secret in the right file that unlocks far more than the agent needs is still a liability. Scope the access and keep the guardrails, or the storage is doing half the job.

**Pasting secrets into chat.** Chat is logged and logs leak. A token pasted into a conversation, a prompt, or a document is a token you should assume is compromised. Rotate it and keep the real value in the env file.

**Relying on the agent to behave.** Careful agents fail. A hostile file, a wrong model output, an over-permissive habit, and the assumption is gone. Guardrails are what is left when careful fails, so set them instead of hoping.

**Auto-approving unattended work.** A scheduled agent that can run destructive commands with no one watching is more power than any recurring job needs. Keep the deny default and design the job to work within it.

**Handing over without documenting the access.** The client inherits the secrets and the boundaries whether you document them or not. Document where the secrets live, what they can do, and how to rotate them, so the client can operate and audit the system after you leave.

## Try it

Take the engagement you have been carrying and run a security review of it, on paper, before you change anything:

1. List every secret the engagement uses, and name exactly what each one unlocks.
2. Check where each secret lives. Is any of them in chat, a prompt, a committed file, or a document? Treat any yes as a rotation.
3. For each agent, name the minimum access it needs, then list what it actually has. Flag every gap where it has more.
4. Name the guardrails in place: which commands are denied by default, what the write sandbox confines, which domains are blocked, what the context scanner caught.
5. Describe the rotation procedure for one secret, in three steps, so a client could follow it without you.
6. Name the proof. How would you demonstrate, live, that a hostile input cannot make the agent read a secret or reach an internal network?

If you can answer all six, you can hand the client an agent that is not just capable but safe. If your instinct is to configure the access and move on without auditing the secrets or the guardrails, that is the builder reflex again. Stop, and run the review first.

## What's next

You can now store secrets safely, grant the least access the work needs, and hand over a system whose boundaries are enforced rather than assumed. But security is not the last discipline an engagement needs. The next lesson takes the hardest promise a consultant makes: claiming the agent works. It teaches testing and verification, the craft of proving an agent does what you say it does before you say it to the client. Where this lesson kept the client safe from what the agent could misuse, the next one keeps the client safe from what the agent gets wrong, by giving you the tools to demonstrate the truth instead of asserting it.
