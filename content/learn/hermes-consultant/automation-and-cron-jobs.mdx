# Lesson 11: Automation and Cron Jobs: Turning One-Off Wins Into Reliable Recurring Value

Every lesson so far has built a capability. The agent can research, it can draft, it can reach the client's systems, and it can prove each of those things works. But there is a gap between a capability and a deliverable, and this lesson closes it. A capability works when you ask it to work. A deliverable works on its own, on a schedule, whether anyone is there to ask or not. The move that separates a consultant who builds demos from one who ships recurring value is the habit of asking, after every one-off win, "should this run every day, and can I make it run without me?"

That habit is the subject of this lesson. It is not a technical trick. It is a consulting discipline that transfers to any agent platform, because it is really about three things. Deciding which wins deserve to become recurring. Writing the instructions so they survive a fresh run with no human to clarify. And making the unattended work loud when it goes wrong. Hermes Agent is the concrete vehicle because it makes all three concrete, and because the way it treats scheduled work exposes the exact questions a consultant has to answer anyway.

## Define the terms: what automation means, and why it is the point

Before you promise a client that "the agent runs our weekly report," slow down and name what you are describing. Automation, in this context, means the agent performs a defined task on a schedule, without a human initiating each run and without a human supervising the whole thing. It is the difference between a tool you use and a process that runs. A tool you use is a demo. A process that runs is the thing the client can stop paying attention to, and the thing they can hand to their team when you leave.

The consulting value is not in building the automation. It is in knowing when a win has earned the right to become recurring. A one-off task that worked once, that you ran by hand and that produced a good result, is a candidate. A task that was barely stitched together, that needed your judgment at three points, or that you are not sure will behave the same next week, is not a candidate yet. Automate a proven win, never a hope. If you schedule something before it works reliably by hand, you have not automated value. You have automated a failure on a fixed timetable.

When a task has earned recurring status, you translate it into a scheduled job. In Hermes, a cron job is a prompt attached to a schedule. You say when it runs, in plain language or as a cron expression, and you say what it does. The scheduler holds the job, fires it at the right time, runs it in a fresh agent session, and delivers the result. A job can be one-shot, a single run at a future time, or recurring, a cadence like every two hours or every morning at nine. It can deliver to the chat where it was created, to a local file, or to a configured channel. That delivery step matters, and this lesson returns to it, because a job that produces output nobody sees has not delivered anything.[^1]

The important shift is mental. When you schedule a task, you stop being the person who runs it and become the person who designed it. The design has to carry everything: what the task is, what it needs, where the result goes. A client does not buy an agent that answers questions. They buy a pipeline that produces a report every Friday at five, or a check that flags anomalies every morning, or a digest that lands in the team channel before standup. Those are the recurring wins, and they are what this lesson teaches you to build and hand over.

## Two kinds of recurring work, and what each one costs

Not every scheduled task needs the full agent. This is a cost question, and it is a consulting question, because the client's recurring spend is your design decision. There are two kinds of recurring work, and they differ in what they cost to run and in what they can do.

The first is an agent job. The scheduler starts a fresh agent session, gives it the prompt, and the agent reasons, uses its tools, and produces a response. Reach for this when the task needs judgment: summarize the week's findings, assess whether a metric changed meaningfully, draft a reply that needs context. An agent job can attach skills so the fresh session inherits reusable workflows, and it can reach the client's systems through the integrations you built in lesson 10. It is flexible, and it costs an inference call on every run, because a model has to reason each time.[^1]

The second is script-only work. Hermes calls it no-agent mode: a script on a schedule, its output delivered verbatim, with zero model involvement. Reach for this when the task is deterministic: query a database, check that a service is up, copy a file, compute a number. It costs almost nothing, because there is no reasoning step. The same recurring cadence that would spend tokens on an agent run every time costs only the price of running a script.[^1]

The consulting discipline is to sort your recurring wins into the right bucket. If a task produces the same output from the same inputs every time, it does not need a model to think about it, and giving it one is token waste that compounds on every run. If a task genuinely needs judgment, a script cannot replace it, and forcing it into a script gives you a brittle, wrong artifact. You decide per task, deliberately, and you write the decision down so the client understands what each recurring process costs them and why.

There is a middle pattern worth knowing. Hermes lets a job attach a cheap pre-run script that decides whether to wake the agent at all. The script emits a signal, and if nothing has changed, the scheduler skips the model run entirely for that tick. A poll that runs every few minutes can check a file's modification time or count new rows in a database, and only spend an inference call when there is something new to process. This is the cost discipline made concrete: you never pay for a thinking turn on a run that has nothing to say.[^2]

## The self-contained prompt: the discipline that makes a schedule survivable

Here is the failure mode that takes down more scheduled work than any other, and it is not a technical one. A one-off task works because you are there. When you run a task by hand, you carry the context in your head. You know which server, which file, which account, which "the issue" refers to. The moment you schedule that task, that context has to live somewhere else, because the fresh run has none of it.

Hermes runs each cron job in a completely fresh agent session. Nothing from your conversation carries over. The prompt is the whole world the scheduled run sees, plus whatever attached skills provide. If the prompt says "check on that server issue," the fresh agent has no idea which server or which issue. It will guess, and a guessing agent on a schedule is a machine for producing confidently wrong output on a fixed timetable.[^3]

The rule is brutal and simple: the prompt must be self-contained. It has to specify the target, the action, the exact commands or tools, and the shape of the output. Instead of "check on that server issue," you write "connect to server 192.168.1.100 as user deploy, check whether nginx is running with systemctl status nginx, and verify that https://example.com returns HTTP 200." Every fact the run needs, the run has, because you put it there.[^3]

The same rule extends to judgment work. A scheduled weekly report cannot say "summarize the findings." It has to say which data to pull, from where, over what window, and what the report should include. The consultant's craft here is writing the prompt as if a new colleague who has never met the client will run it tomorrow, because that is exactly what happens on every scheduled tick. A prompt that reads well to you because you remember the project is not a good prompt. A prompt a stranger could execute to a consistent result is the one you can schedule and hand over.

## The observability reflex: make unattended work loud when it fails

This is the discipline that most separates professionals from hobbyists, and it transfers to any automation you will build. Unattended work fails silently unless you design it to be loud. A task that runs while nobody is watching can fail, and if its failure is quiet, it is discovered when the client notices the report did not arrive, or worse, when they notice it is wrong.

The first habit is to separate the two things that can go wrong, because they fail differently. The run can fail, meaning the agent did not complete the work. The delivery can fail, meaning the work completed but the output never reached the person who needed it. Hermes tracks them separately and reports them separately, so a job whose run succeeded but whose message did not land is flagged as a delivery failure, not passed off as a success. If you treat "it ran" as "it delivered," you will confidently tell the client the process is healthy while their team has not received a report in a week.[^4]

The second habit is to check the fleet, not just the one job. An engagement that ships automation ships several recurring jobs, and each one can break on its own. The professional checks the whole set the way they would check any service they are responsible for: what ran, what failed, what is about to fire, what has not fired when it should. A health check that surfaces every job with a failed last run, a failed delivery, or a schedule that has silently stopped firing is the difference between maintaining recurring value and letting it quietly decay.[^5]

The third habit is to design the failure to be caught early, not discovered late. A recurring job that fails the same way every run will ping on every run unless someone acknowledges it. That nudge is not noise. It is the system refusing to let a broken job be forgotten. The consultant's job is not to disable the noise but to act on it: fix the job, pause it, or remove it, deliberately, rather than letting a failing process accumulate silent damage. A scheduled job that has failed several times in a row is a design you own, and you resolve it instead of letting it run on.[^5]

There is also a configuration discipline that prevents whole classes of failure. Hermes validates a job's configuration before it ever makes an inference call, checking that the provider key resolves, that attached skills are ready, and that delivery targets are reachable. If the config is broken, the job is marked blocked and alerts once, and it spends no tokens. This is the honest-blocker principle applied to automation: a misconfigured job does not burn money discovering it is misconfigured. It tells you, cheaply, before it runs.[^6]

## The verification reflex, applied to recurring work

Lessons 8 and 9 drilled a reflex into you: never claim a thing works because you configured it; prove it in the running system. Recurring work has the same rule, with one extra layer. A scheduled job is not proven the day you create it. It is proven the day it fires on its own and produces the right output, and then again the next day, and the day after.

So the handover test for an automated win is not "I scheduled it." It is "I watched it run unattended and deliver the right result to the right place." You do not hand the client a job and tell them it works because you typed the command that created it. You let it fire on its own, you check the delivered output, you confirm the delivery landed where they expect, and you show them the run that happened with nobody involved. That run is the evidence the process is real. Everything before it is intent.

This is also where the consulting value shows itself at handover. When you hand over a recurring job, you hand over something the client's team does not have to run. The value is not the prompt or the schedule. It is the proof that the process fires on time, delivers to the right place, and tells someone loudly if it breaks. That is what the client is paying for, and it is exactly what you should be able to demonstrate.

## Worked example: turning the intake win into a weekly report

Put it together on the engagement you have carried through this series. In lesson 10 you wired the claims-intake agent to the client's ticketing platform and internal customer-data service, and you watched it draft replies against the live systems. That was a win, but it was a one-off win. You ran it, you verified it, you showed the client. Then you left, and the value left with you, because nobody was scheduled to run it again.

This lesson asks the next question: which of those wins should run without you? The claims-intake work itself is a candidate, but it is the one that needs a human in the loop, because its output is a draft for a person to review. Automating the whole reply-and-send loop would remove the human the client explicitly wanted in it. So you scope the automation to the parts that genuinely recur and genuinely need no judgment.

The weekly summary is the natural first automation. Every Friday, someone has to answer "what came in this week, and what did we flag?" That is exactly the recurring, judgment-light win worth scheduling. You write a self-contained prompt. Pull the week's intake from the ticketing platform, note anything the agent flagged as unverifiable, and produce a summary with counts and open items. You name the window, you name the tool it should call, you name the shape of the output, because the fresh Friday session will have none of that context. You schedule it, and you choose where it delivers: the client's team channel, so the report lands before the Friday standup.

Then you do not stop at creating it. You let it fire on its own. You check the delivered output against what you know should be there, and you confirm it landed in the channel. You add a fleet check to your own recurring habit, so a job's failure reaches you before it reaches the client's inbox. When you hand it over, you tell the client exactly what you verified. The report fires Friday at five. It covers the week's intake and flags what it could not verify. It lands in their channel. If it ever fails, it will tell someone. Every word of that is something you watched happen, not something you hoped would.

## The pitfalls to avoid

**Scheduling before the win is proven.** Automate a proven win, never a hope. If a task needed your judgment at three points the one time you ran it, or you are not sure it will behave the same next week, it is not ready to run unattended. Schedule it and you have automated a failure on a timetable.

**Writing prompts that assume your memory.** A scheduled run is a fresh session with none of your context. "Check on the server issue" means nothing to it. Write every prompt as if a stranger will execute it tomorrow, because that is literally what happens every tick.

**Treating "it ran" as "it delivered."** A job can run and the output can never reach anyone. Delivery fails separately from execution, so check that the report actually landed where the team expects, not just that the job completed.

**Letting unattended work fail silently.** A quiet failure is discovered by the client, which is the worst place to discover it. Make recurring work loud: check the whole fleet on a schedule of your own, and act on a job that keeps failing instead of letting it accumulate.

**Spending model tokens on deterministic work.** If a task produces the same output from the same inputs, it does not need a model to think about it every run. Use script-only work for deterministic tasks, and reserve agent runs for the judgment they exist to provide. An unnecessary reasoning call is token waste that compounds on every scheduled run.

## Try it

Take the engagement you have been carrying and turn one proven win into a scheduled job, on paper, before you touch a scheduler:

1. Name the win. Which task produced a reliably good result when you ran it by hand?
2. Name the cadence. How often should it run, and why that cadence?
3. Name the bucket. Does it need judgment, in which case it is an agent job, or is it deterministic, in which case it is a script?
4. Write the prompt as a stranger would need it. Does it name the target, the action, the tool, and the output shape, so a fresh session has everything?
5. Name the delivery. Where does the result need to land, and how will you know it actually landed there?
6. Name the proof. How will you watch it run unattended, verify the output, and demonstrate that to the client before you hand it over?

If you can answer all six, you can convert a one-off win into recurring value the client can stop supervising. If your instinct is to schedule the first thing that worked and call it done, that is the builder reflex again. Stop, and design the self-contained prompt and the proof of the unattended run first.

## What's next

You can now take a proven win and turn it into work that fires on a schedule, delivers to the right place, and tells someone loudly when it breaks. But scheduling a single job raises a question this lesson only touches. As an engagement grows, you stop having one recurring job and start having several, each doing a piece of a larger goal, and each needing to be scoped, dispatched, and finished cleanly. The next lesson is about that coordination. It covers kanban and orchestration patterns: scoping work so it fits a real work window, dispatching it so the right worker picks it up, and knowing when a job is actually done rather than merely started. Where this lesson made a single win run on its own, the next one makes a whole portfolio of work coordinate without you holding every thread.
