The first domain on the OmniStudio Developer exam is the one candidates skim and then regret. OmniStudio Fundamentals asks you to describe the solution as a whole before you can reason about any single tool. This requirement in particular, describing the OmniStudio solution as it applies to common customer use cases across industries, is really about knowing what each tool does and which one fits a given scenario. Scenario questions dominate this domain, so the goal of this lesson is to make tool-to-use-case mapping automatic rather than something you reason through slowly on test day.

## Deep Dive

### The five core tools

OmniStudio is a declarative toolkit on the Salesforce platform. Declarative means you configure behavior with clicks in a designer instead of writing imperative code line by line. You define the shape of the work, the platform executes it, and an admin or consultant can change it after release without touching Apex. The toolkit is organized around five core tools, and the exam expects you to know each one by name and by job.

The first is the OmniScript, a guided, multi-step user journey. Think of a form that spans several screens, validates input as the user moves, and ends with data written back to Salesforce or to an external system. The OmniScript is the tool for anything that walks a user through a transaction one step at a time.

The second is the FlexCard, a contextual UI card. FlexCards display data about the current context, typically the record a user is looking at, with states, drill-down flyouts, and actions. They summarize what is relevant and let the user expand or act on it without leaving the page.

The third is the Integration Procedure, often shortened to IP. It is server-side orchestration of many actions in one call. Where an OmniScript lives in the browser and walks the user through steps, an IP runs on the server and chains together data operations, external callouts, and business logic without user interaction.

The fourth is the Data Mapper, formerly called DataRaptor. It handles extract, transform, and load of data. A Data Mapper reads from Salesforce, reshapes JSON, and writes records back, and it is the tool you reach for whenever data has to move or change shape.

The fifth is Calculation Matrices and Calculation Procedures. Matrices are decision tables that map input values to output values, like a rate table that turns a customer's plan and usage into a price. Calculation Procedures are expression-based logic that compute a value from inputs. Together they move rules that would otherwise live in code into declarative tables and expressions.

One more piece belongs in the picture. Industry Consoles tie these components together into role-based workspaces. A console gives a service agent a layout that combines FlexCards for account details, an OmniScript for a repair journey, and quick access to the data behind both. The consoles are where the five tools become a usable workspace for a person doing a job.

### What each tool is for

The core skill this requirement tests is knowing when each tool applies, and the cleanest way to hold it is to attach a job to each name. An OmniScript is for guided flows: anything where a user moves through a sequence of steps and the order matters. A FlexCard is for display: showing a summary of contextual data with the ability to drill in. An Integration Procedure is for orchestration: coordinating several server-side actions so a browser does not have to make five round trips. A Data Mapper is for moving and transforming data, either reading it out of Salesforce, writing it in, or reshaping it between steps. A Calculation Matrix or Procedure is for rules and expressions that compute a value from inputs.

The trap in scenario questions is that the four UI and data tools overlap at the edges, so the exam asks you to pick the primary fit. When a process must be walked through step by step, the OmniScript wins even though it invokes other tools. When the task is purely to show data on a page, the FlexCard wins even though it can read from an Integration Procedure. The primary fit is driven by the verb in the requirement.

### Industry mapping

The requirement names several industries, and the exam expects you to know the representative use case for each. Commit these pairings because scenario questions borrow directly from them.

![Industry use case map pairing each of the five industries with its representative use cases and the guided step it captures, with the shared guided capture, display, and backend orchestration pattern underneath](</diagrams/day-01-f1-omnistudio-solution-and-industry-use-cases/2-industry-use-case-map.png>)

For telecom, the canonical use cases are offer and order capture plus service and repair journeys. A customer adds a line, picks a device, chooses a plan, and confirms the order, which is a textbook OmniScript. A field technician runs a repair journey against a service case, which again is a guided flow.

For energy and utilities, the uses are meter-to-cash, outage management, and field service. Meter-to-cash captures the sequence from meter reading to billing. Outage management tracks an outage from report to restoration. Field service schedules and completes on-site work, with OmniScripts capturing the steps and FlexCards showing asset and outage context.

For healthcare and life sciences, the uses are member enrollment, prior authorization, and claims intake. A member enrolls in a plan through a guided OmniScript. A provider requests prior authorization for a procedure, and the request flows through approval logic. Claims intake captures a submitted claim and routes it, with data moved in and out by Data Mappers and orchestrated by Integration Procedures.

For the public sector, the uses are case and license intake plus benefits eligibility. A citizen applies for a license through a guided form. An eligibility worker runs an OmniScript that collects facts and calls an Integration Procedure which evaluates them against rules, often with Calculation Matrices driving the eligibility decision.

For financial services, the uses are customer onboarding, loan origination, and claims. Onboarding collects customer details and runs background checks. Loan origination guides an applicant through identity, property, and credit steps, calls external systems for verification, and produces a decision. Claims intake captures an event and starts the assessment.

The pattern across all five industries is the same. Each has a guided capture step, a display step, and a backend orchestration step. Once you recognize that, the industry names become decoration and the tool choice becomes obvious.

### How components compose

The tools are not isolated. They compose into end-to-end flows, and the exam wants you to describe that composition. A representative flow runs like this. An OmniScript collects the user's inputs across its steps. At the point of submission it invokes an Integration Procedure. That IP calls Data Mappers to read from and write to Salesforce, and it calls HTTP Actions to reach external systems. When the work finishes, a FlexCard renders the result back to the user. The whole chain is declarative, and it all lives in the same org.

Consider a bank onboarding a new customer. The OmniScript gathers name, address, and employment. On submit it invokes an Integration Procedure. The IP runs a Data Mapper Extract to check for an existing account, an HTTP Action to run a credit check against an external bureau, and a Data Mapper Load to create the Account and Contact records. The IP returns a status, and a FlexCard on the completion step confirms what was created and what happens next. Every piece of that chain is a configured component rather than hand-written code.

![Composition sequence for a bank onboarding a customer: an OmniScript gathers name, address, and employment, then on submit invokes an Integration Procedure that runs a Data Mapper Extract to check for an existing account, an HTTP Action for a credit check against an external bureau, and a Data Mapper Load to create the Account and Contact records, and a FlexCard on the completion step confirms what was created](</diagrams/day-01-f1-omnistudio-solution-and-industry-use-cases/3-bank-onboarding-composition.png>)

This composition matters for the exam because it explains why the tools overlap. An OmniScript rarely stands alone. It leans on an IP, which leans on Data Mappers and HTTP Actions, and a FlexCard often closes the loop. The scenario question asks which tool is the primary fit for the stated verb, not which tool touches the flow at all.

### Where OmniStudio runs

OmniStudio components run on the standard platform surfaces. You can place them on Lightning pages, inside Experience Cloud sites, on mobile, and in embedded web contexts. A single component can be reused across channels, so the FlexCard built for an agent's Lightning console can also appear on a customer-facing Experience Cloud page without being rebuilt.

The channel is worth tracking because it feeds the third quiz question's central claim. OmniStudio is channel-agnostic. It does not run only on Experience Cloud, and it does not require a community to function. Lightning is the most common home, mobile is supported, and embedded contexts let you drop a component into an existing web experience. A statement that limits OmniStudio to a single channel is wrong.

### What the candidate is not expected to do

This requirement also draws the boundary of the role. The exam asks you to know the tool suite and when each applies. It does not ask you to write Apex or LWC, and it does not ask you to tune performance. When a question is about which tool fits a use case, the answer is a component, not a code solution. That boundary keeps this domain answerable from declarative knowledge alone.

## Configuration Walkthrough

The curriculum has no explicit configuration steps for this requirement, so the walkthrough here is the thought process you apply in the designer when a use case arrives.

1. Read the requirement and underline the verb. Is it a guided journey, a display, a backend orchestration, or a data movement? That verb points at one tool first.
2. Identify the data touched. If Salesforce data flows in, note the objects. If an external system is involved, note that an HTTP Action inside an Integration Procedure will reach it.
3. Choose the primary tool. For a multi-step user journey, open the OmniScript Designer and sketch the steps. For a summary card on a record page, open the FlexCard designer instead.
4. Layer the supporting tools. Decide which data operations belong in Data Mappers and which orchestration belongs in an Integration Procedure that the primary component invokes.
5. Confirm the channel. Verify the component will be placed on the surface the requirement names, whether Lightning, Experience Cloud, or mobile.
6. Map it to the industry context. Confirm the steps you sketched match the industry's representative journey, such as order capture for telco or enrollment for healthcare.

## Exam Traps

- **Choosing an Integration Procedure for a user-facing guided flow.** IPs are server-side. They orchestrate actions without a user in front of them. When the requirement describes a guided, multi-step journey that a person completes, the primary fit is an OmniScript, not an IP.
- **Assuming OmniStudio replaces all custom code.** OmniStudio is declarative-first, but Apex and LWC still fill gaps that declarative configuration cannot reach. A statement that OmniStudio eliminates all custom development is false.
- **Thinking OmniStudio is single-industry.** The same five tools serve telco, energy, healthcare, public sector, and financial services. There is no OmniStudio variant that belongs to only one industry, and the scenarios in each industry reuse the same toolkit.

## Exam Tip

Map the verb to the tool. Guided flow means OmniScript. Display means FlexCard. Orchestrate means Integration Procedure. Move or transform data means Data Mapper. Hold those four pairings and scenario questions resolve quickly, because nearly every item in this requirement reduces to which verb the use case uses.

## Try It

Open a sandbox with OmniStudio enabled and build a small telco order capture OmniScript with two steps. In step one collect the customer's account and the plan they want, and in step two confirm the order and write a custom object record with a Data Mapper Load. Then build a FlexCard on that object's record page that shows the plan, the status, and a drill-down flyout with order details. Run the OmniScript end to end and confirm the FlexCard reflects the captured data. That exercise demonstrates the composition this requirement describes: a guided capture, a backend data write, and a contextual display, all declarative in one org.
