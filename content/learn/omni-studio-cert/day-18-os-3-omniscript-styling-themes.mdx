Appearance questions look like the soft part of the exam, and that is exactly why they are worth preparing. The requirement is short, customize OmniScript appearance using styling or themes, but the scenarios behind it are the ones where a designer and a developer disagree about where a color should live. The exam wants you to know that OmniScript appearance is controlled at two levels, that one of those levels is authoritative, and that responsive behavior is a property you verify rather than assume. Get those three ideas straight and every question in this requirement answers itself.

## Deep Dive

### Two layers of appearance control

OmniScript appearance is controlled at two levels, and the first job is knowing which one a requirement belongs to.

**Themes are the system.** A theme is a shared definition of look and feel that you apply to an OmniScript. It is the same object you can apply to FlexCards, which is what makes a unified brand possible: the card on a Lightning record page and the OmniScript launched from it can read from one visual definition instead of two. A theme sets the colors, the fonts, the button styles, and the spacing.

**Element-level styling is the exception.** Any individual element can carry its own style overrides. An emphasized field, a highlighted section, a callout box that needs to stand out from the rest of the page. Element-level styling changes one thing and leaves the theme untouched.

That relationship is the whole requirement in miniature: **theme equals system, inline equals exception.** Everything else in this lesson is a consequence of applying that rule consistently.

![Two layers of appearance control: the theme is the shared system applied to OmniScripts and FlexCards, while element-level styling is the exception for one-off overrides](</diagrams/day-18-os-3-omniscript-styling-themes/1-two-layers-appearance-control.png>)

### What a theme actually defines

Think of a theme as the design tokens for the flow, expressed as a configured object rather than as values typed into each element. The categories it governs are the ones you would expect from a design system:

- **Colors.** Background, text, accent, primary action, and the semantic colors for states a user needs to read at a glance.
- **Fonts.** Family, sizing, and weight for headings, labels, and body text.
- **Button styles.** The visual treatment of the buttons a user clicks to move through the script, including the primary and secondary hierarchy.
- **Spacing.** The padding and margins that control how dense or airy a step feels.

The important consequence of centralizing these is scale. If a bank has twelve OmniScripts in production and rebrands its primary accent color, the difference between "one theme edit" and "twelve scripts' worth of element edits" is the difference between an afternoon and a project. That is why the exam frames consistency across many scripts as a theme question. When a scenario says "many OmniScripts must share consistent branding," it is describing a shared theme, and inline styling reapplied to every element is the wrong answer for the obvious reason: it is not shared, it is duplicated.

Themes also carry beyond OmniScripts. Because the same visual definitions can be applied to FlexCards, applying a theme is how you keep a card and a script that appear on the same page from looking like they came from two different companies.

### Element-level styling: the exception lane

Element-level styling exists for the case the theme does not cover: a single field or section that needs to read differently from everything around it.

The realistic examples are small and specific. A field that must be visually flagged because getting it wrong causes a rejection. A disclosure section that needs to look distinct from the data entry around it. A confirmation panel on the final step. In each of those, the requirement is genuinely local, and an element-level override is the right tool.

The exam question here is direct: the preferred approach for a one-off emphasis on a single field is element-level styling. The wrong answers are instructive. "A new theme per field" treats a shared system as a per-element artifact, which is the opposite of what a theme is for. "Hardcoded colors" bypasses the configuration layer entirely and produces values nobody can trace or maintain. "A FlexCard" is a display component, not a styling mechanism, and reaching for one to change how a field looks means adding a data-driven element to solve a visual problem.

Two guardrails keep element-level styling from undermining the theme.

**Use it sparingly.** Every inline override is a place where the theme is no longer the truth. Ten overrides in a script is a script where the theme has stopped describing reality, and the next person to edit the theme will be surprised by what did not change.

**Do not restyle what the theme already covers.** Applying explicit colors or spacing to elements the theme already handles is redundant at best. It is worse than redundant when the theme changes later, because the element keeps rendering the old values and the script becomes visually inconsistent with its siblings.

### Why inline-everything is the trap

The failure mode the exam calls theme drift deserves a name and a mechanism, because it is easy to do accidentally and hard to unwind.

Theme drift happens when appearance decisions accumulate on elements instead of in the theme. It starts innocently: someone needs the submit button to be green and sets it on the element. Someone else wants their form's inputs to be slightly taller and sets padding on each of nine inputs. Six months later, the brand refresh lands, the theme is updated, and eleven scripts pick up the change while the two that were styled element by element do not. The result is a product that looks inconsistent, and the fix now requires auditing every element in every affected script to find the overrides, which is far more expensive than it would have been to put the values in the theme at the start.

![How theme drift happens: appearance decisions accumulate on elements instead of in the theme, so a brand refresh reaches eleven scripts but not the two styled element by element](</diagrams/day-18-os-3-omniscript-styling-themes/2-theme-drift-mechanism.png>)

There is also a maintenance angle that shows up in reviews. A reviewer looking at a script full of inline styling cannot tell which choices are deliberate exceptions and which are leftovers. When the theme is authoritative, any deviation is a signal worth examining.

### Responsive behavior has to be verified

The same OmniScript definition renders on desktop, tablet, and mobile. That is a feature of the platform and a hazard for the person who designs on a wide monitor.

Response layouts change shape as the viewport narrows. Rows that sit side by side on a laptop stack into a column on a phone. Label placement moves from beside a field to above it. Content that fits comfortably inside a wide container starts to wrap, and multi-column groups that looked balanced at full width can become long vertical strips. Long steps become substantially longer, and anything that depended on vertical proximity stops being easy to read.

![Responsive layouts render differently at narrow widths: rows that sit side by side on desktop stack into a column on mobile, and labels move from beside a field to above it](</diagrams/day-18-os-3-omniscript-styling-themes/3-responsive-desktop-mobile.png>)

None of this means the OmniScript broke. The layout is doing what responsive layouts do. It means the design was never verified at that width, which is why the exam's rationale for mobile testing is not "mobile has different licensing" and not "themes do not apply on mobile" and not "inputs are disabled on mobile." None of those are true. The reason to test on mobile is that responsive layouts render differently at narrow widths, so the only way to know what your users will see is to look at it.

Practical habits that follow from this:

- **Preview at more than one width.** Set the preview to a phone-sized viewport and walk the steps. Complex steps with several columns are the ones most likely to surprise you.
- **Be suspicious of fixed widths.** A layout that depends on elements being a specific number of pixels wide will not survive a narrow screen.
- **Check the long steps first.** A five-field step is unlikely to be a problem. A step with three groups, a card, and a table is where narrow-width rendering gets uncomfortable.
- **Treat touch as part of the test.** Buttons and tap targets that are fine with a mouse cursor can be cramped with a thumb. Responsive verification includes how easily a person can hit the control.

The exam phrasing matters here. When a question asks why an OmniScript should be tested on mobile, the answer is about rendering differences at narrow widths. Distractors that invent licensing, theming, or input-disabled behavior are all false.

### A worked example: carrying a brand refresh

Suppose the bank in the earlier exercise replaces its primary color and adopts a new typeface across all customer-facing digital properties. Its OmniStudio estate contains nine OmniScripts and four FlexCards.

The work goes like this. The team updates the shared theme with the new accent color, the new font definitions, and any adjusted button treatments. The OmniScripts and FlexCards that read from that theme pick up the change without being individually edited. The team then greps the estate for element-level color and font overrides, because those are the places the theme update will not reach. Most overrides turn out to be leftovers and get removed, which brings those elements back under the theme permanently. A small number are genuine exceptions, such as a compliance disclosure that must stay visually distinct, and those are kept and documented as intentional. Finally the team previews each affected script at desktop and phone widths, because a new typeface changes text height and text height changes how a narrow layout wraps.

That sequence is the exam's worldview applied to a real task: the theme does the heavy lifting, inline overrides are the small known set, and responsive verification is the last step rather than an afterthought.

## Configuration Walkthrough

1. **Apply a theme to the OmniScript.** Associate the shared theme so the script inherits the design system rather than starting from defaults. Prefer an existing theme that other scripts already use, since a theme applied to one script is a theme that will drift.
2. **Confirm what the theme already covers before you touch anything.** If the requirement is a color, a font, or spacing that belongs to the whole estate, the theme is where the change belongs. Only requirements that are genuinely local to one element belong in the next step.
3. **Override specific element styles where needed.** Apply element-level styling to the individual elements that are true exceptions, and keep a short mental list of which ones they are and why. Do not override elements the theme already handles.
4. **Preview at desktop width first.** Walk the steps at full width and confirm the theme is rendering as expected and the overrides read as deliberate emphasis rather than as errors.
5. **Preview at mobile and tablet widths.** Re-walk the same steps at narrow widths. Watch for columns that stack badly, labels that crowd inputs, and steps that became unreasonably long. Adjust the layout structure rather than adding inline styles to compensate.
6. **Re-check after any theme change.** Every theme edit is a chance for previously invisible inline overrides to become visible inconsistencies. Sweep the scripts that use the theme when the theme changes.

## Exam Traps

- **Inline-styling everything.** Putting colors, fonts, and spacing on elements instead of in the theme produces theme drift and a maintenance problem that compounds with every new script. The theme is the system; inline is the exception.
- **Ignoring mobile rendering of complex steps.** The definition renders everywhere, but that does not mean the layout was designed to. Complex steps with multiple columns are where narrow widths get ugly.
- **Applying styles to elements the theme already covers.** Redundant overrides hide the theme's effect and confuse the next person who edits the theme.
- **Creating a new theme as a one-off fix.** A theme per field, or a theme per script, defeats the purpose of a shared design system.
- **Treating mobile testing as a licensing or capability question.** It is not. Themes apply on mobile, inputs work on mobile, and there is nothing special about mobile licensing. The reason to test is responsive rendering.

## Exam Tip

Theme equals system, inline equals exception, and responsive widths must be verified. When a scenario says many OmniScripts must look consistently branded, the answer is a shared theme. When it says one field needs to stand out, the answer is element-level styling. When it asks why you test on a phone, the answer is that responsive layouts render differently at narrow widths. Keep those three mappings and this requirement is free points.

## Try It

In a sandbox, take any OmniScript you built in an earlier lesson and apply a shared theme to it. Open preview mode at full desktop width and note the colors, fonts, and spacing the theme is supplying.

Now switch the preview to a phone-sized viewport and walk the same steps. Write down the first thing that looks wrong. It is usually a multi-column group that has collapsed into an awkward stack or a step that now requires far more scrolling than it did at desktop width. Fix that problem in the layout structure, not by adding an inline style to widen an element.

Then practice the exception rule. Pick exactly one element, a field that genuinely deserves emphasis, and give it an element-level style. Confirm in preview at both widths that it reads as deliberate emphasis and that nothing else in the script changed. Finally, review the script and ask honestly how many inline styles it now has. If the answer is more than a small handful, you have found theme drift starting, and moving those values into the theme is the correct fix.
