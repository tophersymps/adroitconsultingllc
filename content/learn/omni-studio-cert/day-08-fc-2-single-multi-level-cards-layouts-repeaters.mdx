Two cards can show the same account and feel completely different. One shows a name, an industry, and a revenue figure. The other shows the same account plus its twelve open cases and its three contacts. The difference is not styling and it is not a second card. It is that the second card's data source returns arrays nested inside each record, and the card knows how to walk those arrays. That mechanism is the repeater, and it is the dividing line between a single-level and a multi-level FlexCard.

## Deep Dive

### Single-level cards: one flat record set

A single-level FlexCard renders one record per card with flat fields. "Flat" means every field you display sits directly on the record: `Name`, `Industry`, `AnnualRevenue`, `Phone`. There is no array between the record and the field.

A worked example. A customer summary card is placed on the Account record page. Its data source returns the account Id passed in as a parameter, and the payload is one record:

```json
[
  {
    "Id": "0018c00002ABCDEAA1",
    "Name": "Northwind Logistics",
    "Industry": "Transportation",
    "AnnualRevenue": 48200000,
    "Phone": "+1 617 555 0142"
  }
]
```

You drop four text elements and a currency element onto the card body and bind each to `Name`, `Industry`, `AnnualRevenue`, and `Phone`. Because the source returns a single record, the card renders once. That is a single-level card.

The important property is not that it is simple. It is that the data is not nested. If the payload had no arrays in it, repeaters never enter the picture.

### Multi-level cards: nested data rendered inside one card

A multi-level FlexCard displays nested or repeated data inside the same card. The nested data arrives the same way the flat fields did, as part of the data source's payload, but it arrives as an array inside the record.

The same account card, upgraded. The data source now returns the account plus its open cases and its contacts, both as arrays inside the record:

```json
[
  {
    "Id": "0018c00002ABCDEAA1",
    "Name": "Northwind Logistics",
    "Industry": "Transportation",
    "Cases": [
      { "CaseNumber": "00001041", "Subject": "Late shipment", "Status": "Escalated" },
      { "CaseNumber": "00001039", "Subject": "Invoice mismatch", "Status": "New" }
    ],
    "Contacts": [
      { "Name": "Dana Whitfield", "Title": "Operations Manager" }
    ]
  }
]
```

To render that, the card needs a repeater for `Cases` and a repeater for `Contacts`, each containing the elements that describe one item. The card body still describes one account, so the card is still one card. The repeated content sits inside it.

This is the definition the exam tests. Multi-level supports nested and repeated data structures; single-level renders one flat record set. Multi-level does not require Apex, it is not achieved by placing two cards next to each other, and a single-level card is perfectly capable of using a data source. The distinguishing feature is nesting. [^3]

### Repeaters: the mechanism for lists inside cards

A repeater is an OmniStudio element that iterates over an array in the data JSON and renders the elements inside it once per item. Point it at an array path and it produces one block per element of that array.

To render the open cases above, you add a repeater to the card body, bind the repeater to the array path `Cases`, and place inside it a text element bound to `Subject` and another bound to `Status`. With two cases in the array, the card draws the subject and status lines twice, once per case.

Two rules govern the binding, and both are exam traps. [^1]

**The repeater binds to an array, not an object.** A repeater pointed at an object has nothing to iterate, so it renders once, or renders nothing, depending on the implementation. If your repeater outputs a single block when you expected five, check whether the path resolves to an array or to a single object. A related shape problem: if the payload wraps the array in a node, such as `{"records": [...]}`, the repeater path has to include that wrapper.

**Elements inside the repeater bind relative to the current item.** Once a repeater is set to `Cases`, an element inside it binds to `Subject`, not to `Cases.Subject`. The element is already inside the iteration; the path is relative to the item it is rendering. An absolute path inside a repeater is one of the most common reasons a nested field comes back blank while the surrounding card looks fine.

![The Cases array flows into a repeater that iterates it and draws one block per case, with child elements bound to Subject and Status relative to the current item rather than to Cases.Subject.](</diagrams/day-08-fc-2-single-multi-level-cards-layouts-repeaters/2-repeater-walks-array.png>)

### Walking a multi-level card end to end

Take the account card with open cases and follow the whole configuration, because the pieces only make sense together.

The data source is one call. It returns the account fields the card needs plus a `Cases` array, and each element of that array carries the case number, subject, and status. Nothing about the layout has been decided yet.

The card body holds the account-level elements: a text element for the name, a text element for the industry, a currency element for annual revenue. These bind to `Name`, `Industry`, and `AnnualRevenue`, taking the paths straight from the payload.

Below them, a section holds the case list. Inside the section, one repeater is bound to `Cases`. Inside the repeater, two text elements bind to `Subject` and `Status`. Those two elements appear once per case in the array, so two cases draw two rows and twelve cases draw twelve.

That is the entire anatomy of a multi-level card: a flat outer record, one repeater per nested array, and child elements bound relative to the item. There is no second card, no child component, and no Apex in the pattern. If the requirement added a list of contacts, you would add a second repeater bound to `Contacts` alongside the first, and the card would render both lists without the two interfering.

The layout then decides how the two lists sit relative to each other and to the account fields, which is the job of the grid.

### Failure modes when nesting goes wrong

Nesting produces a small family of recognizable failures, and knowing the symptom saves the diagnostic time.

- **The repeater renders once when you expected many.** The path resolves to an object rather than an array. Confirm the shape in the payload preview.
- **The repeater renders nothing at all, and the card otherwise looks fine.** The array is empty for that record, which is a data outcome rather than a configuration error. A record with no cases should render a card with no case rows, and the design should say what the user sees in that case.
- **The repeater renders the right number of blocks with empty children.** The repeater path is correct and the child paths are not. Check that the children are relative to the item rather than absolute from the root.
- **The nested list appears once per card, but the card itself repeated.** The data source returned many records where you expected one, so you are looking at the outer loop rather than the inner one. Filter the source to the record the card is for.

Each symptom points at one layer: the payload shape, the data, the child binding, or the source's cardinality. Naming the layer is most of the fix.

### Layout: the twelve-column grid

The FlexCard editor lays elements out on a twelve-column grid. You drop an element into a region, and you set how many of the twelve columns it spans. A half-width element spans six columns. Three equal cards side by side are four columns each. A full-width element spans twelve. [^1]

Columns and sections group content so the grid has structure: you place a section, then place elements inside it, and set widths within that section. The widths are responsive, which means the card adjusts across device sizes rather than rendering at one fixed pixel width.

Responsive does not mean you stop thinking about mobile. A row of three six-column elements that reads well on a desktop may collapse into a cramped single column on a phone. When a card is going to a mobile channel, decide deliberately which elements keep their width and which stack. The exam's trap here is simply forgetting that widths exist: a layout with no considered widths is a layout that will look wrong somewhere.

One more reason the grid matters for a multi-level card: the repeated block inherits the width you gave the repeater or the section that holds it, not the width of the outer card elements. A list of twelve cases rendered inside a repeater set to full width produces twelve full-width rows, which is a wall of text on a desktop and unusable on a phone. Set the repeated block's width with the same intent you set the account fields, and consider whether the list should be capped or scrolled rather than allowed to run.

### Design for the data shape

The rule that ties this lesson together: the layout has to match the payload. If the data source returns a nested array and your card has no repeater bound to it, the nested content does not appear. Nothing errors. The card just renders the flat fields and ignores the array, so a reviewer sees a card that is missing half its content with no diagnostic to explain why.

So the build order is the reverse of what most people do:

1. Read the payload and identify the arrays.
2. Count the arrays and note their paths.
3. Add one repeater per array you intend to display.
4. Bind the elements inside each repeater to relative item fields.
5. Only then arrange widths on the grid.

Missing repeaters equal missing nested content. There is no other explanation to look for first.

## Configuration Walkthrough

1. **Add the data source and preview its JSON.** Note every array inside each record and its path. This is where the multi-level design is decided.
2. **Drop elements onto the twelve-column grid.** Set the width of each element in columns, and use sections to group related content.
3. **For each nested list you want to show, add a repeater** and bind it to the array path. One repeater per array.
4. **Bind the repeater's child elements to item fields**, using paths relative to the current item rather than absolute paths from the root.
5. **Preview the card with real data** and count the rendered blocks against the array length. If the counts disagree, check the repeater's path shape first.
6. **Check the widths on a narrow viewport.** Adjust column spans so a mobile user does not get a broken single column.

## Exam Traps

- **Binding a repeater to an object instead of an array.** It will not iterate. A repeater needs an array to walk.
- **Using absolute paths inside a repeater.** Elements inside a repeater bind relative to the current item, so `Subject` is correct and `Cases.Subject` is not.
- **Treating multi-level as two cards.** A multi-level card is one card with nested content rendered through repeaters, not two FlexCards placed together.
- **Forgetting widths on mobile.** Element widths are set on the grid and respond to viewport size. A three-across layout with no mobile thought becomes cramped and unreadable.
- **Designing the layout before reading the payload.** If you skip the preview, you build a flat card over nested data and cannot see why content is missing.

## Exam Tip

Array inside the JSON means repeater. Repeaters are how multi-level cards happen. Single-level means one flat record set; multi-level means nested and repeated data rendered inside the same card, and the twelve-column grid is what positions the elements around them. [^4]

## Try It

In a sandbox, build a FlexCard over Account whose data source uses a Data Mapper Extract or Integration Procedure that returns each account with a nested array of its contacts. [^2] Preview the JSON and write down the array path. Add a repeater bound to that path and place two text elements inside it, one for the contact name and one for the title. Confirm the repeater draws one block per contact. Now change the repeater binding to the parent record path instead of the array and watch the behavior change, which makes the array-versus-object rule concrete. Finally, arrange the account fields on the top half of the grid at six columns each and set a mobile width for the repeated block. [^5]
