Lesson 23 gave you the actions you can place inside an Integration Procedure (IP). This lesson is about the control flow that decides which of those actions run, in what order, and how many times. An IP that runs every action exactly once, in the order you placed them, is only good for a single fixed scenario. Real integrations have branches: an order above a threshold needs a credit check, a cart with multiple line items needs per-item work, and a payment can route down one of several paths depending on what the caller sent. Conditional logic, loops, and branching turn a linear list of steps into a decision-making procedure, and that is exactly requirement IP-3: apply these to control the execution path.

The good news is that all three tools evaluate against the same thing: the IP's data JSON. Every condition you write reads a value out of the JSON, every loop you define points at a node that holds an array, and every branch you build chooses a path based on those same values. If you keep a clear picture of what your data JSON looks like at any point, the control flow writes itself. If you let the JSON drift and grow messy, the conditions become brittle and the exam traps in this lesson start firing. The way to stay safe is to design and shape your input JSON up front, an idea this lesson returns to in the design section. The in-lesson quiz for this requirement tests three concrete capabilities: gating an action with conditional logic on a data value, iterating an array one item at a time with a loop, and choosing between action paths with branching. Teach each of those so you can answer the question it tests, then walk the full configuration through once.

## Deep Dive

### Conditionals: gating an action on a data value

A conditional, in an IP, is a gate you hang on a single action or a group that decides whether that step runs at all. The mechanism is the Execution Conditional Formula, a property common to every Integration Procedure action. It is a formula that runs before the step executes. If the formula returns TRUE, the step executes. If it returns FALSE, the step is skipped. If you set no formula, the step always runs. [^1]

The most common use is a comparison against a value in the input JSON. Say your procedure takes an order that includes an amount. A credit check should only run when the amount is high, because running it on a small order wastes a callout and adds latency for no benefit. You put the credit check inside an action, then set that action's Execution Conditional Formula to something like checking that the amount path is greater than a threshold. When the condition is true, the credit check runs. When it is false, the step is skipped and the flow moves on. That behavior is the whole point of the property, and it is quiz question 1: an IP should call a credit-check API only for amounts over a threshold, and that control comes from the conditional logic on the amount JSON path. [^1]

Two details matter for the exam. First, the formula reads the data JSON by path, and the path syntax for JSON nodes uses colons to delimit levels, so a value nested several levels down looks like `Order:Amount` rather than a dotted path. [^1][^3] Second, conditions evaluate before the step runs. That means a condition can look at anything the IP already holds when it reaches that step, but it cannot depend on output a later action has not produced yet. If your condition references a node that does not exist yet, a trap this lesson covers below, it evaluates to false and the action is silently skipped.

Place one condition on one action whenever a single step should run conditionally. Use the same approach one level up when a whole batch of related actions should run only under a condition: attach the Execution Conditional Formula to a Group, and every action inside it is governed by the group's gate. This is how you gate a phase of work without repeating the same formula on each of five actions. The formula you put on the group is the single source of truth for whether that phase runs, and the formulas you put on individual actions inside it still work as additional gates. A group formula and an action formula combine: the action runs only when both pass. That layering is how you keep logic readable: one condition says run this phase for high-value orders, and the conditions inside it split that phase by finer distinctions.

### Loops: iterating over an array

A loop in an IP is a Loop Block. Drag it into the structure panel, and configure it to iterate over the items in a data array. [^3] The block holds the actions that should repeat, and those actions execute once for every item in the array. The reason loops exist is that an external request often carries many things to process: a cart with several products, an order with many line items, a list of records to update. Without a loop, you would either run the per-item action once for a single item, or duplicate the action once per item, if you knew its count in advance. With a Loop Block, one action inside the block processes every item, no matter how many arrive. [^3]

Under the hood, the Loop Block passes each iteration a single item. The array input to the block is processed so that each iteration receives only one item from the array. So when your input JSON has a `LineItems` array, configure the Loop List property to point at that array, and the actions inside the block see one line item at a time, not the whole list. That is what makes per-item work possible: each iteration, the Remote Action that calls an availability API runs with exactly one product Id, or the Data Mapper Load that persists an order line runs with exactly one line to write. [^3]

Which node holds the array is controlled by the Loop List property. You enter the name of a JSON node that contains an array of data. The node name does not need merge field syntax. If your array is nested, enter the full path to it, like `Products:Ids` to reach an `Ids` array inside `Products`. The action inside the loop then receives that one item, and you pass the full path to the array into the action as needed. For example, if the Loop List is set to an array named `Products:Ids` that holds key-value pairs, the full path in the action would be `Products:Ids:Id`. [^3]

The exam tests this loop concept directly. Quiz question 2 asks how an IP processes a list of line items one at a time, and the answer is a loop over the line items array. [^3] A single HTTP Action would hit one endpoint once, not per item. A formula and a theme have nothing to do with iterating lists. Only the Loop Block walks the array one element at a time so per-item actions can run. When you see process each item, a list, or an array in an IP question, reach for the Loop Block.

Two structural limits shape how you design with loops. Nested Loop Blocks are not supported, a limitation the docs state plainly. You cannot drag one Loop Block inside another to handle a nested array. The supported workaround is to split the nested case: call one Integration Procedure that contains a Loop Block from another. The outer procedure handles the outer array, and the sub-procedure the inner one. Second, a Loop Block that calls a Data Mapper Transform degrades performance once the list passes about one thousand items. For lists that large, use a paging strategy to break up the work rather than loading everything into one pass. [^3] These limits are why the design section below pushes you to shape the input array before it hits your loop.

### Branching: routing between distinct input states

Branching is the IP's way of choosing between different paths of execution based on the state of the input. Where a single conditional simply skips a step, a branch decides which of two or more alternative sequences runs. The tool for this is a Conditional Block, a block whose only job is to control the IP flow. It groups actions and blocks behind a formula, and it can execute in its entirety if an expression is true, or run one of a set of mutually exclusive conditions defined in the steps it contains, or both. [^2]

A Conditional Block has two properties that matter. The Execution Conditional Formula specifies that the entire block runs only if that formula evaluates to true, which gates the whole block like a group gate. The `Is If Else Block` property changes how the steps inside it behave. When it is checked, all actions within the block, except optionally the last, have mutually exclusive Execution Conditional Formula values. If the last action has a blank Execution Conditional Formula, it runs only if the formulas of all the other actions evaluate to false. [^2] That is an if, else-if, else structure: each branch has its own condition, exactly one of them runs, and the trailing element with no condition is the default that catches every case the earlier conditions missed.

This is quiz question 3: which IP capability chooses between different action paths for different inputs? The answer is branching, and the mechanism is the Conditional Block. A Response Action returns output but does not choose a path. A Sub-IP composes procedures but does not branch. Caching stores data but does not route. Only the Conditional Block inspects the input state and sends the flow down one of several alternative paths. [^2] When a question describes two or more distinct inbound scenarios that need different handling, you are looking at branching.

Branching and single-condition gating feel similar, because both rest on Execution Conditional Formulas. The difference is intent. A condition on an ordinary action or group decides whether that step contributes to a flow that otherwise proceeds linearly. A Conditional Block exists to split the flow into branches that decide which of several mutually exclusive sequences runs, so exactly one of them does the work for this input. Keep that distinction straight: conditions skip, branches branch.

### The data JSON drives everything

Every control construct in this lesson reads the same source: the IP's data JSON. Conditions evaluate formulas against JSON values. [^1] Loops point at a node that holds an array. [^3] Branches compare input state paths against expected values. [^2] Nothing here is stateful or implicit: there is no hidden variable, and no automatically remembered conversation. Everything the flow reacts to must be visible as a node in the data JSON at the moment the control point runs. That single fact is the key to the whole requirement and to the design section next. Grow familiar with reading a JSON path as get the value at this location in the object I currently hold, such as `Order:Amount` for the amount, and `LineItems` for the list, and `Payment:Method` for which payment path to take. The accuracy of your conditions, the completeness of your loops, and the reliability of your branches all hinge on you pointing at the right path. Misspell the path, and the condition never matches; a missing node, and the branch silently takes the wrong route. Since everything flows from the data, control that stays honest means you must know what data you have at every step, and that is a design discipline, and not just a rule of thumb.

### Design implication: shape your input JSON so conditions stay simple

Because conditions, and loops, and branches all read the data JSON, the shape of that JSON genuinely determines how hard your IP is to write, and test. A normalized, and predictable input makes the control flow trivial to write, and easy to reason about. A messy input, nesting the same value at different depths, or leaving fields absent on some records, makes every condition a judgement call about which path to use and when, and every trap in this lesson easier to trip. The implication is: do your shaping as early as possible, preferably before the IP's control flow kicks in. Use a Data Mapper Transform, or a Set Values action, and normalize, and populate the input before you branch, and loop. Take an order payload that sometimes includes cash, check, or card, and sometimes omits the payment method. Before you build branches on `Payment:Method`, normalize it so `Payment:Method` always exists, and always holds one of the three known values, defaulting missing cases to something explicit. Then the branch formula is a plain equals comparison, and not a defensive null-handling expression. Similarly, turn the list you need to loop over into a flat array of the records you actually process, and their fields into named, present nodes, so your loops, and conditions read clean paths instead of zigzagging through variable structure. When the data is well shaped, the formula is readable, and the flow is testable, because there are a small number of known states, and each maps to an obvious branch. That is what the exam tip means: conditions, and loops read the IP's JSON; keep the input shape clean, and your logic becomes trivial.

## Configuration Walkthrough

Building a controlled IP follows a consistent path. Walk through it in this order, with an order-processing IP as the running example.

1. **Add conditional gates on actions, and groups.** Start with the gates you know you need. Look at each action, and ask whether it should always run, or only under a condition. In the order example, the credit-check API action runs only when the order amount exceeds your threshold, so set its Execution Conditional Formula to evaluate the amount JSON path against that bound. If a whole phase, say validate payment, should run only when a payment method is present, attach a condition to that Group instead of each action inside it. Keep single-step gates on the action, and phase gates on the group.

2. **Add loops over arrays with nested actions.** Identify the lists you process one item at a time. For the order, that is the `LineItems` array. Drag a Loop Block into the structure panel, set its Loop List to the node holding the array, like `Order:LineItems`, and add the actions that should repeat inside the block. If each line needs an availability check, and then a persistence write, place both actions inside the loop so both run once per item. Pass the full path to the array into the actions as needed, so each iteration receives one line item to process. [^3]

3. **Define branches for distinct input states.** Map the distinct inbound scenarios, one branch each. In the order IP, payment can route three ways: cash, check, or card. Add a Conditional Block, and check `Is If Else Block` so the actions inside form mutually exclusive branches. Give the first two branch actions conditions like `Payment:Method == "Cash"` and `Payment:Method == "Check"`, and leave the last one's condition blank so it serves as the else that catches card, and any unexpected value. Exactly one branch runs per input, so each inbound state gets its handled path, and the flow does not fall through multiple alternatives. [^2]

4. **Test each path with representative inputs.** The configuration is not done when the diagram is wired, and the logic is defined. A control-heavy IP earns its keep when every path behaves correctly, which you verify in the test tool by feeding representative input for each state. Run the IP once with a high-value order to confirm the credit check fires, and once with a low-value order to confirm it is skipped. Feed a cart with three line items to confirm the loop runs three times, and each per-item action gets one item. Feed a cash payment, and a card payment, and confirm each routes to its own branch, and that the else branch catches the cases that the first conditions miss. Every trap below is caught by a passing test for exactly that input shape, so build the test matrix from the states you designed.

## Exam Traps

- **A condition on a null or absent JSON path is never true, the action is silently skipped.** This is the most dangerous trap in this requirement, because it fails quietly. If your Execution Conditional Formula references a node that does not exist in the data JSON at that point, or that holds a null, the comparison never evaluates to a usable TRUE, and the step is skipped without error. The flow completes, and the user gets a result, the missing work just does not happen. When you write a condition, confirm the path exists, and is populated, before it runs. Prefer input shapes where the values you condition on always exist, and are explicit, rather than conditions that depend on optional fields being present.

- **Looping over an object instead of an array.** A Loop Block iterates an array, and only an array. Its Loop List property must point at a node that holds an array of data. If you point it at an object, or at a scalar, the iteration does not behave the way you expect, and the actions inside the block do not run once per real item. The input must arrive with the list you want as an array node, so the block can hand one element to each iteration. [^3] If your source data does not already hold that array, shape it into one with a Transform or Set Values action before the loop, rather than trying to loop over an object that happens to contain a list.

- **No branch for the empty case, and downstream actions fail on empty arrays.** A loop that processes zero items is a real possible state, not an edge case you can ignore. If the `LineItems` array arrives empty, and your flow sends an empty list straight into a downstream action that expects records, the downstream action can fail, or produce a meaningless result. Design the empty case explicitly: branch, via a Conditional Block or a group condition, so that when the array is empty, the IP either skips the per-item work entirely, or defaults to an empty-result path, and does not push an empty array into a step that cannot handle one. Test the zero-item input as deliberately as you test the three-line-item input. The empty case is as much a designed path as every other branch, not an afterthought.

## Exam Tip

Keep the three tools straight by the job each does, and you can answer the pattern-heavy questions in this domain at speed. A condition, an Execution Conditional Formula, gates one action or group: run this only when a data value holds. A loop, a Loop Block, iterates an array: run these actions once for every item. A branch, a Conditional Block, ideally an If Else block, chooses between alternative paths: route the flow by input state. All three read the IP's data JSON, so the surest way to make the pattern questions easy is to keep the JSON clean. When you see over a threshold, only when, skip if, think condition. When you see each item, iterate, process the list, think loop. When you see different handling for different inputs, route, alternative path, think branch. Point at the path that holds the value or array, and the right answer falls out.

## Try It

Open the Integration Procedure Designer in a sandbox. Feed it a JSON input with an `Order` object holding an `Amount`, an `LineItems` array, and a `Payment:Method` value. Add a credit-check action gated by an Execution Conditional Formula on the amount, so it fires only over your threshold. Wrap per-line work in a Loop Block set to the `LineItems` array, something like an availability call or a write, so it runs once per item. Add a Conditional Block checked as an If Else block: routing the cash, check, and default, else branches off `Payment:Method`. Then run the IP four times: high amount with three line items, low amount with zero line items, cash, and card. Watch the JSON flow, and confirm the credit check fires in case one only, and the loop runs three times in case one, and zero times in case two, and that each payment value lands in exactly one branch. That exercise turns the three control tools from concepts you read into mechanics you can build, and as the habits you need to test every path.
