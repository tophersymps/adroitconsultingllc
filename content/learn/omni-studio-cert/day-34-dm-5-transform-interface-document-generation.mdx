Lessons 30 through 33 built the reading and writing sides of the Data Mapper domain. Lesson 30 gave you the fundamentals and the four interface types, lesson 31 built the multi-object Extract, lesson 32 covered Turbo Extract, the optimized single-object reader, and lesson 33 covered Load, the interface that writes records to one or more objects. [^1] This lesson sits at a different point in the flow. Requirement DM-5 asks you to configure the Transform interface type to prepare data for downstream use, such as JSON, or for document generation, such as PDF and DocuSign. [^1]

Transform is the shape-shifter of the Data Mapper family. Extract and Turbo Extract read data out of Salesforce. Load writes data into Salesforce. Transform does neither of those things. It manipulates data that is handed to it, changes the structure, the field names, and the format, and produces an output that some other consumer is ready to accept. [^2] In a platform definition, a Data Mapper Transform performs intermediate data transformations without reading from or writing to Salesforce. [^1] You feed it data from another Data Mapper or an Integration Procedure, and it reshapes that data into the exact structure a downstream system expects.

Three facts anchor the entire requirement, and each one maps to a quiz question. Transform prepares an exact output structure for downstream use, which is why an external API that expects a specific JSON payload gets its data from Transform rather than Extract. Transform produces the data model consumed by document generation, which is why PDF and DocuSign templates are fed by Transform output. And the primary purpose of Transform is to reshape or map input data into a required output structure. [^2] Hold onto those three and the DM-5 questions are nearly free.

## Deep Dive

### What Transform actually is, and where it sits in the data flow

Start with the definition so the rest of the lesson has a solid base. Data Mapper Transforms do not extract data. Instead, they manipulate any data from inside or outside Salesforce, and that data is passed to them by other Data Mappers or Integration Procedures. [^2] They perform intermediate data transformations without reading from or writing to Salesforce objects. [^1][^2]

The word intermediate is the key to understanding the role. Transform does not sit at the start of a flow, pulling data from the database, and it does not sit at the end, writing records back. It sits in the middle, between a data source and a consumer, reshaping whatever passes through. [^2] In a typical integration, data flows from an Extract (which reads from Salesforce), through a Transform (which reshapes it), and on to an external API, a document template, or some other downstream system. [^2] Transform is the stage where the format gets corrected before the data reaches someone who cares about the format.

![Transform sits between a data source and a consumer, reshaping data passed to it without reading from or writing to Salesforce](</diagrams/day-34-dm-5-transform-interface-document-generation/1-transform-in-data-flow.png>)

The platform documentation lists Transform alongside the other three types with a clear distinction. Turbo Extract reads a single object with related fields. Extract reads multiple objects with complex mappings. Load writes data from JSON or XML input into Salesforce. Transform performs intermediate data transformations without touching the database. [^1] Each interface has one job, and Transform's job is reshaping, not moving data in or out.

![The four Data Mapper interface types and their output types, with only Transform able to target PDF and DocuSign](</diagrams/day-34-dm-5-transform-interface-document-generation/2-interface-types.png>)

That distinction matters for the exam because wrong answers will try to blur the lines. Quiz Q1 asks which interface prepares an external API payload built from Salesforce data, and the correct answer is Transform. [^1][^2] Extract and Turbo Extract read, and while you could pull data out of Salesforce with an Extract, building a specific payload shape for a consumer is Transform's job, not Extract's. [^1][^2] The read interfaces give you data loosely shaped by your mappings. Transform gives you a payload that matches someone else's contract. When a question describes preparing a specific output structure for a downstream consumer, reach for Transform.

### The output structure is the contract, not the data

The single most useful way to think about Transform is that it satisfies the consumer's format. Every downstream system carries an expectation about what it will receive: an external API expects certain field names at certain nesting levels, an OmniScript expects a specific JSON shape it can bind against, and a document template expects its placeholder fields to be present in the data. [^2] Transform is where that expectation gets satisfied. It reshapes the data you have into the shape the consumer accepts.

That framing changes how you reason about a Transform. You build it backward from the expectation. You look at what the consumer needs, define that as the target structure, and then work out how to map the data you have into that structure. [^2] The output JSON template defines the structure, and input fields map into it, with formulas where you need to calculate or reformat a value. [^2] Transform gives you the output shape you define, not some natural shape of the source data.

This is exactly why the manager's overview describes Transform's capabilities the way it does. Data Mapper Transforms take the data they receive and change its structure, content, and format. [^2] They can rename fields by mapping input paths to define output paths. They can substitute values using key-value pairs, such as converting Y to True. They can apply formulas to add new calculated values. And they can convert data to different outputs, such as JSON, XML, or a custom format. [^2] Each of those capabilities is a tool for making the output match the consumer's expectation.

Rename is the most basic and the most common. The source data calls a field one thing, the consumer expects another, so you map the input path to a different output path. [^2] Value substitution handles the case where the source uses one representation and the consumer needs another, like a Y that must become True. [^2] Formulas let you derive values the source does not contain, turning a pair of source fields into a computed output field. [^2] And the output format conversion is what lets a single Transform feed a JSON API and a document template from the same reshaped data. [^2]

Quiz Q3 tests this identity directly. The question asks what the primary purpose of Transform is, and the correct answer is that it reshapes or maps input data into a required output structure. [^2] The wrong answers, "query multiple objects," "insert records," and "stream events," describe other roles. Querying multiple objects is an Extract. Inserting records is a Load. Streaming events is not a Data Mapper job at all. [^1] Transform is the interface whose whole reason to exist is matching a target structure, which is why the exam tip in the requirement is phrased the way it is: shape data for someone else's contract. [^2]

### Downstream use cases: APIs, OmniScript pre-fill, and documents

The requirement names several downstream uses for Transform output, and understanding them tells you why Transform exists. The three it calls out are external API contracts, OmniScript pre-fill, and document generation. [^1]

The external API case is the cleanest example of the contract idea. When you call a third-party API, you do not get to send data however you like. The API specifies which fields it accepts, what those fields are called, and how they nest within the payload. [^2] A Transform builds that payload precisely. It takes the data you pulled from Salesforce or collected in an OmniScript, renames the fields to match the API's contract, nests them at the levels the API expects, and outputs the exact JSON the API will accept. [^2] This is the case quiz Q1 describes, and the reason the answer is Transform rather than Extract is that Extract gives you Salesforce-shaped data while Transform gives you the API's contract shape. [^1][^2]

The OmniScript pre-fill case uses the same reshaping idea to feed the user interface. An OmniScript expects its data in a specific JSON structure it can bind against its elements. [^2] A Transform reshapes data into that structure so the OmniScript can populate its fields. [^2] Where extraction would give you a data-shaped-any-old-way, the Transform gives the OmniScript exactly the keys it knows how to render.

The document case is the third downstream use, and the requirement gives it special weight because Transform output feeds document generation. [^1] You will build Transform mappers whose only job is to produce the data model a PDF or DocuSign template consumes. [^2] When an OmniScript collects a customer's details for an agreement they must sign, a Transform formats that data into the specific JSON that populates the PDF or DocuSign template. [^2] Field values, tables, and signature data all land in the output so the document generator can fill the template.

### Document generation: Transform output is the data model

The document generation case deserves its own section because quiz Q2 lives here, and because it ties Transform to an output type the read and write interfaces cannot produce. Quiz Q2 asks which Data Mapper capability feeds PDF and DocuSign generation, and the correct answer is Transform output. [^1][^2]

The reason Transform, and only Transform, feeds documents is that document generation needs a pre-shaped data model. A PDF or DocuSign template is not filled ad hoc. It contains placeholders for specific fields, and the generation engine pulls values for those fields from a data source. [^2] That data source is the Transform output, which supplies field values, tables, and signature data in the exact structure the template expects. [^2] Without that pre-shaped output, the template has nothing to bind against.

The way to hold this in your head is to connect it to the output type matrix for the interface types. Extract and Load write to sObject, and Turbo Extract writes to JSON or custom. Transform is the one whose output types include JSON, XML, custom, PDF, DocuSign, and document template. [^3] Only Transform can target PDF and DocuSign output, because only Transform produces the document-ready data model those generators consume. [^1][^3]

Quiz Q2's wrong answers reinforce the point. Load writes records to objects, it does not feed documents. Turbo Extract reads a single object with related fields, it does not shape document data. And SOQL data sources are not a Data Mapper capability at all; SOQL lives in the world of queries, not in the list of things that feeds a document template. [^1][^2] When a question describes feeding PDF or DocuSign generation, the answer is Transform output.

### The output template drives the structure

A Transform does not guess its output shape. You define it. The output JSON template defines the target structure, and input fields map into it, with formulas where you need them. [^2] This is the difference between a Transform and a simple pass-through. A pass-through would echo the input. A Transform produces the structure you declare in its output template.

Building the template comes first. You lay out the JSON shape the consumer expects, with the field names, nesting, and array structures they require. [^2][^1] Then you map input fields from whatever source you have into the slots in that template. [^2] Where the source field is already what the target needs, the mapping is a straight copy. [^2] Where the target needs a derived or reformatted value, you drop in a formula. [^2]

This backward design is why the exam wants you to care about field names. If your output template uses a different field name than the consumer's contract, the payload fails even though the values are all there. [^3] The contract is the target. Transform maps input into that target, and the mapping is what makes the data match the contract.

## Configuration Walkthrough

Build a Transform on a concrete case: an external API that expects a customer profile payload, then extend it to feed a PDF template. Walk through the numbered steps.

1. **Create a Transform Data Mapper.** In the OmniStudio Data Mapper designer, create a new mapper and pick Transform as the interface type. [^3] Name it for what it produces, for example `BuildCustomerProfilePayload`. Because this mapper reshapes data for a consumer without reading from or writing to the org, Transform is the correct interface, not Extract, Turbo Extract, or Load. [^1][^2]

2. **Define the output JSON template.** Lay out the target structure the API expects. For the profile case, that is a JSON object with `customer` as the top-level key, containing `firstName`, `lastName`, and a nested `contact` object with `email` and `phone`. [^2] This is the consumer's contract, so the field names here must match the API's expectations exactly. [^3] Every placeholder the API requires must appear, or the payload will be rejected.

3. **Map input fields into the template slots.** Open the mapping and connect each output field to a source field from the incoming data. The source may call the field `Name` while the API calls it `firstName`, so you map the input path to the output path, which is Transform's rename capability in action. [^2] For the nested `contact` object, define the mapping so `email` and `phone` land inside it rather than at the top level. [^2]

4. **Add formulas where the target needs a derived value.** When the output needs a value the source does not directly contain, define a formula. [^2][^4] Suppose the API expects a `fullName` computed from separate first and last fields, or a formatted date. Map the formula's output to a slot in the output JSON so the calculated value lands in the right place. [^4] This is how a Transform adds values the source never carried.

5. **For documents, wire the transform output to the PDF and DocuSign template.** Once the profile payload is correct for the API, reuse the same reshaping to feed a document. Create the PDF or DocuSign template with placeholders that match the Transform's output fields, then configure the document generation step to pull its data from this Transform. [^2][^3] The Transform output becomes the data model for the template, supplying field values where the placeholders sit. [^1][^3]

![The customer profile output JSON template maps input fields into its slots and feeds both an external API and a PDF or DocuSign template](</diagrams/day-34-dm-5-transform-interface-document-generation/3-customer-profile-payload.png>)

6. **Test the output against the consumer's expected shape.** Open the preview, paste a sample input, and run the Transform. [^2] Compare the output field by field against what the consumer expects: names match, nesting is correct, derived values are present, no fields are missing. [^3] For the document case, generate a sample PDF or DocuSign envelope and confirm every placeholder is populated from the Transform output. [^3]

That is the full build, and the steps worth re-reading are two and five. The output template defines the contract you are satisfying, and the document wiring is what turns a reshaping mapper into the data model for a PDF or DocuSign envelope. [^2][^3] Get the shape right and the same Transform can feed an API and a document. Get it wrong and the payload bounces or the template renders with empty fields.

## Exam Traps

![Route an exam question to the right Data Mapper interface and avoid the common exam traps](</diagrams/day-34-dm-5-transform-interface-document-generation/4-which-interface.png>)

- **Using Extract to build an API payload.** Extract is the read interface, and it produces data shaped by your Extract mappings, not by a consumer's contract. [^1][^2] Transform is the shaper. [^2] When a question describes preparing a specific JSON payload for a downstream API, the answer is Transform, not Extract. [^1][^2] Quiz Q1 exists to catch this.

- **Output template that mismatches the consumer's contract.** The output template defines the structure, and it must match what the consumer expects, field names included. [^2][^3] A template that uses a different field name than the API's contract produces a payload without the values where the contract expects them. [^3] Define the template against the contract and verify the output before shipping it. [^3]

- **Forgetting that document templates consume Transform output.** PDF and DocuSign templates are filled from a pre-shaped data model, and that data model is Transform output. [^1][^2][^3] The shape matters, because the document generator binds template placeholders to the fields in that data. [^2][^3] When a question asks which capability feeds PDF and DocuSign generation, the answer is Transform output. [^1][^3]

- **Treating Transform as a read or write interface.** Transform does not extract data and it does not write to Salesforce. It performs intermediate data transformations without touching the org. [^1][^2] Extract and Turbo Extract read, Load writes, and Transform reshapes. [^1] Quiz Q3 tests this identity, and it maps cleanly to the shapes elsewhere in the series.

- **Confusing the write interfaces with document feeds.** Load writes records to objects, it does not feed documents. [^1] Only Transform produces the PDF, DocuSign, and document-template output types the document generators consume. [^3] If a question pairs a PDF or DocuSign template with a Data Mapper, the mapper is a Transform.

## Try It

Open the Data Mapper designer in a sandbox and build a Transform mapper that produces a customer profile payload. [^2][^3] Define the output JSON template with a `customer` object and a nested `contact` object, map input fields into the slots so names and nesting match the contract, and add one formula that derives a value the source does not carry. [^2][^4] Run it with a sample input and compare the output to your target structure field by field. [^2][^3]

Then extend it to feed a document. Create a PDF template whose placeholders match the Transform's output fields, wire the transform output to the template, and generate a sample document to confirm every placeholder is populated. [^2][^3] Finally, change one field name in the output template so it disagrees with the contract, re-run, and watch the payload lose that value, to feel exactly why the target shape is the whole point of Transform. [^3] That deliberate break makes the contract idea memorable.
