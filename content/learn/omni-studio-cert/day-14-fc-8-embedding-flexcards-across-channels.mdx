The value of a FlexCard is not that it renders data, it is that one definition renders that data wherever you need it. FC-8 is about placing a single card across Lightning pages, Experience Cloud sites, OmniScripts, and mobile without rebuilding it per channel. The exam asks which channels are supported, what makes one card work in a console and a portal at the same time, and what the platform generates so you can drag the card onto a page. Underneath those three questions is a single design principle: build the card around context it receives rather than context it assumes, and it will travel.

## Deep Dive

### One definition, many channels

An OmniStudio FlexCard is channel-agnostic. The same card definition, with the same data sources, layout, and states, can be embedded in four families of host:

- **Lightning pages** via App Builder, including record pages, app pages, and home pages.
- **Experience Cloud sites** via Experience Builder, so the card can appear to customers and partners in a portal or community.
- **OmniScripts**, where the card appears as a contextual element inside a guided flow, showing data alongside the questions the script asks.
- **Mobile**, through the Salesforce mobile app and mobile experiences built on the same components.

Because the card is a definition and not a page, what changes between channels is the *host*: what context the host supplies, what the user's permissions are, what the screen size is, and what the network can be relied upon to do. What does not change is the card. That is the reuse story, and everything else in FC-8 exists to protect it.

**Worked example.** A telecom builds one `CustomerPlan` FlexCard showing plan name, monthly cost, data allowance, and contract end date. Internally, it sits on the Account record page in a service console so agents can answer billing questions instantly. Externally, the same card sits on an Experience Cloud page so customers see their own plan details after logging in. The card is not duplicated between the two. The only differences are the context the two hosts supply and the data the two user profiles are permitted to see.

### How channel context differs, and why it breaks things

The single most common reason a card that works internally fails in a portal is context. Embedding on a Lightning record page passes record context automatically: the page already knows which record is open, and the card receives that record's id without any explicit wiring. That automatic behaviour is a convenience that hides a dependency. The card gets its id from the host, and the host happens to be a record page.

Move the same card to Experience Cloud and the automatic record context is gone. A portal page is not necessarily bound to a single record, and the user's relationship to the data is different. The card now needs the id to arrive some other way: a public attribute supplied by the page, a value read from the URL, a session-scoped value for the logged-in user, or an input the user selects. If the card was built with the record id baked in or assumed, there is nothing to supply and the card renders nothing useful.

Mobile adds a further layer. The context may be available, but the rendering environment is narrower: less horizontal space, touch rather than pointer input, and the possibility of intermittent connectivity. A card designed at desktop width with dense rows and small action buttons may be technically working on mobile while being unusable there.

The lesson is to treat context as an input the card declares rather than a fact it assumes. A card whose only dependency is a declared public attribute can be hosted anywhere, because every host has some way to supply that attribute.

### Public attributes are what make reuse real

This is the same mechanism covered in FC-5, restated for a different purpose. A public attribute is a named value the card exposes for its host to fill. On a record page, the host fills it from the record. In Experience Builder, the page configuration or a URL parameter fills it. In an OmniScript, a data node from the script fills it. As a nested card, the parent fills it.

Designing for reuse therefore means sitting down before the build and asking what context this card needs in every place it will appear, then declaring each of those as a public attribute. An `AccountHealth` card might declare `accountId` and `isPortal`. A `CaseSummary` card might declare `caseId` and `readOnly`. With those declared, the same card renders correctly internally and externally, and a new host is a wiring task rather than a rebuild.

The exam phrases the reusable pattern as "public attributes for context plus per-channel verification". Both halves matter. Public attributes make the card *capable* of working across channels; verification makes you *sure* it does.

### Channel constraints you have to plan for

Reuse across channels is not free, and three constraints come up repeatedly.

**Licensing.** Experience Cloud requires the appropriate license to host the experience and for the users who access it. Confirming that licensing exists before promising a portal embed is the difference between a plan and a problem. A card that renders beautifully in a sandbox says nothing about whether the portal it is destined for is licensed to serve it.

**Data source availability and behaviour.** Some data sources behave differently depending on the channel, and some depend on services that must be enabled for the environment. A card that reads data through a service that is not available in a portal will fail there while working perfectly in the console. When a card behaves differently per channel but the layout is identical, the data source is the first suspect.

**Component behaviour per channel.** Mobile touch targets need to be larger than pointer targets. Offline and slow-network handling affects how a card should load. Long lists that scroll comfortably on a desktop may need a tighter layout on a phone. These are not bugs in the card, they are the card meeting a different environment.

There is also the question of *what the user should see*, which is a security question rather than a rendering one. The same card serving an internal agent and an external customer may need to hide fields for the external case. That is handled by the data source respecting field-level security, not by building two cards.

### The generated LWC wrapper

FlexCards auto-generate a Lightning web component wrapper. That wrapper is what you drag onto a Lightning page in App Builder and onto an Experience Cloud page in Experience Builder. It is also why embedding does not require you to write Apex or hand-author a component: the generated wrapper presents the card as a standard Lightning component to the page builder, and the page builder treats it like any other component with properties to configure.

The practical consequences are worth holding onto. First, the wrapper is generated from the card definition, so it reflects the card's current public attributes as configurable properties in the page builder. Declaring an attribute on the card is what makes it appear as something you can wire in App Builder or Experience Builder. Second, because the wrapper is a Lightning component, it composes with the page the way other components do, which is why event listeners and session variables work across a page that mixes FlexCards, OmniScripts, and custom LWCs.

The exam question that tests this asks what a FlexCard auto-generates for App Builder and Experience Builder embedding, and the answer is the LWC wrapper. An Apex class, a Flow, and a report are the distractors, and none of them is the drag-and-drop unit.

### Embedding inside an OmniScript and inside another card

Two of the four channels deserve a closer look because they are not page builders.

**Inside an OmniScript.** A FlexCard can be embedded as a contextual element in an OmniScript, which is how a guided flow shows the user relevant data without leaving the flow. The card receives its context from the script's data, so attributes such as the current record id are bound to script variables. This is the natural pattern for a flow that collects information while the user can see the record it affects.

**Inside another FlexCard.** A child FlexCard is embedded inside a parent card, as covered in FC-5. The parent supplies the child's public attributes from its own data, and the child renders as part of the parent's layout. This is composition rather than a separate channel, but it follows the same rule: the child declares what it needs and the parent supplies it.

Both cases reinforce the same discipline. The card is not reaching out for context, it is declaring context it needs and letting the host supply it. That is why the same card works in a console, a portal, a script, and a phone.

## Configuration Walkthrough

1. **Design the card with public attributes for context.** Decide what the card needs to know (`recordId`, `accountId`, `isPortal`) and declare each attribute before building the layout. This is the step that makes every later step possible.
2. **Add the FlexCard LWC to a Lightning page in App Builder.** Drag the generated wrapper onto the page, then wire each public attribute to a page context or property. Confirm it renders with real data.
3. **Add it to an Experience Cloud page in Experience Builder.** Place the same wrapper on the portal page and supply the attributes the way that channel allows, whether through page configuration, a URL parameter, or the logged-in user's context. Confirm the licensed experience serves it.
4. **Embed inside an OmniScript or another card as needed.** Bind the card's attributes to the script's data nodes or to the parent card's data, and verify the card renders the right record.
5. **Verify per channel (desktop, mobile, portal).** Check rendering, data, and permissions in each channel rather than assuming that working in one means working in all. Channel verification is half of the answer to the reuse question.

## Exam Traps

- **Building for Lightning only, then discovering portal or mobile context gaps.** A card built around a record page's automatic context has no way to receive context elsewhere. Design for the least automatic channel first.
- **Forgetting Experience Cloud licensing before promising a portal embed.** The embed requires a licensed Experience Cloud environment. Confirm it early rather than during the portal build.
- **Hardcoding record context instead of using public attributes.** Hardcoded context breaks reuse and is the direct cause of the "works internally, blank in the portal" failure.
- **Assuming data sources behave identically per channel.** They may depend on services or context that differ by channel, so verify the data, not just the layout.
- **Treating one successful embed as proof.** Verify each channel. They are not identical, which is exactly the phrase the exam tip uses.

## Exam Tip

Design for context with public attributes, then embed everywhere; verify each channel because they are not identical. For any FC-8 question, remember that FlexCards are channel-agnostic (Lightning, Experience Cloud, OmniScripts, mobile), that the public-attribute-plus-verification combination is what makes one card serve an internal console and a customer portal, and that the drag-and-drop unit in App Builder and Experience Builder is the auto-generated LWC wrapper.

## Try It

In a sandbox with OmniStudio, create a `RecordSnapshot` FlexCard with two public attributes, `recordId` and `isPortal`, and one data source that reads Name and two other fields for `Id = recordId`.

Embed it on a Lightning record page in App Builder and wire `recordId` from the record context, setting `isPortal` to false. Confirm it renders the open record.

Now add the same card to an Experience Cloud page in Experience Builder. Supply `recordId` the way that page allows and set `isPortal` to true. If the portal is licensed, the card should render the same layout against the portal user's permitted data. Note the two places verification mattered: the context you had to supply manually, and the fields the portal user can actually see.

Finally, embed the card inside an OmniScript as a contextual element, binding `recordId` to a script node, and open the script in preview to confirm the card renders inside the flow. One card, three hosts, no duplicate definitions. If any host fails, the failure is context or permissions, not the card.
