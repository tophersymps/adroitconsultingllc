The Integration Procedure is a machine that does work, but none of that work matters to the rest of the system until the procedure hands its result back. The person on the other end, which is usually a FlexCard, an OmniScript, or an external API call, asked the IP to get some data or do a job, and it expects a reply it can act on. That reply is a JSON payload, and the shape of that payload is decided by exactly one action: the Response Action. [^1] This lesson is about that action, because it is the whole output layer of an IP. Get it right and every consumer of the procedure gets a reliable, parseable contract. Get it wrong and the callers chase a moving target, the UI breaks on failure, and you re-publish a procedure to fix a shape you should have designed up front.

Requirement IP-7 reads: configure the Response Action to return specific data. [^1] Plain words, but they carry a rigour you need to hear. The Response Action does not just say "return something." It deliberately defines which specific data goes back, in which structure, on success and on failure. The exam tests three claims built on that idea, and it expects you to defend them. First, what an IP returns to its caller is defined by the Response Action's configured output, not by the IP's name, not by its first action, and not by some HTTP action. Second, success and error shapes should stay consistent so that the same caller can handle both outcomes the same way. Third, an IP with no Response Action gives its callers no defined output at all, which is a broken contract. Every section below teaches toward those three claims, because they are the exam's way of checking that you understand the output contract and not just where the Response Action sits in the palette.

## Deep Dive

### The Response Action is the only way an IP speaks

Start with the simplest fact, because it answers quiz question one outright. The Response Action ends an Integration Procedure and returns data to the entity that called it. [^1] That is the entire job: it is the terminal step that converts the IP's internal data JSON into the external payload a caller receives. Every Integration Procedure you give to a FlexCard or OmniScript ends with one, and knowing that makes the first quiz question almost trivial. When asked what defines the data an IP returns to its caller, the answer is the Response Action's configured output. [^1] Not the HTTP Action, which is a step that makes an outbound call somewhere else. Not the first action, which just kicks the flow off. Not the name you gave the IP, which is metadata a human reads. The Response Action is the contract, because it is the action that says "here is what this call delivered." [^1]

The Response Action does more than pass a blob through. It can add data to the data JSON, and it can end conditionally. [^1] Those two capabilities are the keys to shaping an output contract. Adding data means you can inject computed values, identifiers, or merge-field results into the payload just before it ships. Ending conditionally, via an Execution Conditional Formula, means the IP stops and returns only when a condition you specify is true, which lets you gate the response on the state of the data. [^1] So the Response Action is not a passive "return everything I built" step. It is an active finalizer that trims, augments, and gates what the caller sees.

There is a useful way to think about it that ties several earlier lessons together. Everything an IP does, a Data Mapper extract, an HTTP call, a Remote Action, a Loop, a Try-Catch Block, builds up the internal data JSON. Think of that as the warehouse: it contains every field, every intermediate value, every raw response that any step touched. The caller does not want the warehouse. The caller wants the one box of things it asked for. The Response Action is the packing slip that decides what leaves the warehouse and what stays behind. Requirement IP-7 is the skill of writing that packing slip carefully. [^1]

### Response shaping is explicit, and that is a feature

Here is the design principle that separates a well-built IP from a lazy one: only what you explicitly map into the response gets returned. [^2] Salesforce's own documentation frames the whole job around it. The Response Actions are useful for trimming the data response, and trimming means intentionally deciding which parts of the data JSON the caller receives. [^1] It is not an accident and it is not a loss. It is the core safety and cleanliness property of the output contract.

Three concrete benefits come out of "only what you map is returned." Cleaner, because a caller that returns customer account data does not get the raw HTTP headers, the temporary merge fields, and the intermediate error messages from earlier steps. Smaller, because the payload carries exactly the fields the consumer binds to, which matters on a mobile device or over a constrained API gateway. Safer, because you control what leaves the org. If a step pulled in a field that happens to be sensitive, an internal ID, a raw credential, a piece of PII, and you never map it into the response, it does not ship. The contract is an explicit allowlist, and allowlists are how you control what goes out. [^1][^2]

The direct trade to remember, and it is a favorite exam idea, is the flip side: an IP that does not deliberately trim the response returns far more than its callers need. You saw this concern approached in the earlier loop and branching lessons, where a loop pumps arrays into the data JSON and an extract can pull whole record sets. A Response Action that ships the entire data JSON back to a FlexCard that binds to three fields is the kind of over-return that wastes bandwidth, adds parsing risk, and can trip the traps in this requirement. The correct instinct is to return specific data, which is literally the wording of IP-7.

### The four properties that shape the output

The Response Action gives you four properties, and knowing what each does is most of this requirement. [^1]

Additional Output holds key/value pairs to add to the data JSON, and the values can be formulas and merge fields. [^1] This is how you inject computed fields, like a formatted total, a derived status, or a value pulled from an earlier step's output. The property is also how you write to a nested level: to place a pair below the top level, use a colon-delimited path in the Key field, so `Key1:Key2` lands the value at the second level of the JSON. [^1] That is the mechanism behind "computed fields" in the lesson: if you need a derived node that no single action produced on its own, you add it here with a merge field or formula chain.

Return Full Data JSON returns the entire data JSON. [^1] Think of this as the "I want everything" switch. It is easy and it is sometimes right, when a consumer genuinely needs the whole assembled payload. But it is the coarse option, and overusing it is the over-return trap.

Return Only Additional Output discards everything except the key/value pairs you defined in the Additional Output property. [^1] This is the surgical allowlist. You pair it with Additional Output to say "the response is exactly these nodes, nothing else." The platform is explicit that you should not enable both this and Return Full Data JSON at once; they are mutually exclusive intents, and the docs tell you to disable one when you enable the other. [^1] So in practice you choose: full payload, trimmed to a specific set, or everything except something specific.

Response Headers holds key/value pairs that go into the response header, and it is how you control the HTTP status code the caller sees. [^1] To override the status code, create a key named StatusCode and assign it a valid HTTP response value. [^1] This matters for the error branch. A procedure that catches a failure and wants the caller's HTTP layer to see a 400 or 500, not a 200 that happens to carry an error body, sets StatusCode in the Response Headers. That is how a FlexCard or API gateway branches on the transport-level result instead of only parsing the body. [^1]

### Combining the response action with response transformations

There is a second set of controls that trims the output at the level of how JSON is restructured, and you should know it because it is exactly the "map the output JSON" idea from the walkthrough. The Response JSON Path and Response JSON Node properties, which apply to the response side of the Send/Response Transformation properties, trim and reparent the output JSON. [^2] This is a distinct mechanism from the Response Action's own properties, though both shape what the caller receives. [^2]

The mental model comes straight from the doc table. Setting a Response JSON Path drills down on a node so you send a subset instead of the entire JSON. Setting a Response JSON Node reparents the output under a new node name, and you can nest it by using colons, so `node1:node2` wraps the data under a two-level key. [^2] Merge-field syntax works too: a JSON Node of `%NewNode%` uses a runtime value as the node name, which is how you make the wrapper key dynamic. [^2] The practical upshot is that you have two complementary tools. The Response Action's Additional Output and Return Only Additional Output control which values exist. The Response JSON Path and Node control the container structure they sit in. A well-designed IP uses both deliberately to hit an exact shape.

### The error branch: same structure, every time

An IP that only handles success is not finished. The response contract has two halves, success and failure, and both must look planned. This is the point behind the requirement's deep-dive on configuring a consistent contract that includes error information. When the IP throws, when a remote call fails, when a Data Mapper finds no record, the caller still gets a payload, and that payload should follow the same structural rules as the success one. [^3]

Why does consistency matter? Because the consumer is written against one response shape. A FlexCard binds to JSON paths declared in the card, and it renders states, like the error state you saw in the conditional rendering lesson, based on what the data source returns. If the success payload is `{data: {...}}` and the failure payload is an unstructured exception dump, the card has no reliable path to bind the error to, so it cannot decide which state to show. If instead both success and failure return a payload where the same wrapper carries either the result or an error node with a code and a message, the card handles both with the same binding logic. [^3] That is the substance of quiz question two: keep success and error shapes consistent so callers, FlexCards and OmniScripts alike, can handle both reliably. It is not about aesthetics, and errors absolutely matter, and no theming system demands it. It is about making the contract uniform so every consumer reacts to outcomes the same way. [^3]

The failure shape should carry the same kind of information every time: a status or outcome flag, an error code when relevant, and a readable message. In the exception handling lesson you saw how a Try-Catch Block sets Failure Response key/value pairs that flow into the output, and how a controlled error includes an ErrorCode, a Message, and a Detail. [^3] That is the error branch feeding this lesson's contract. The Response Action then ships that structured error to the caller, optionally with a StatusCode header so the transport layer agrees that this was a failure. [^1] Success and error are two routes to the same destination: a predictable JSON contract the caller can parse with confidence.

### Test before you wire consumers

The last discipline in this requirement is sequencing: test the response contract before you connect anything to it. [^1] Every IP has a built-in test tool, the Preview, where you supply sample inputs, run the procedure, and read the exact JSON it returns. The lesson's walkthrough and the "Try It" section drive this hard, because the cost of skipping it is real. Once a FlexCard or an OmniScript binds to a response shape, changing that shape breaks every caller that depends on it. A card that binds to `data.LookupResults` stops rendering the moment you rename the node. An OmniScript that reads `total` breaks when you move it under a wrapper. [^1][^2]

So the rule is: lock the shape before you consume it. Run the response through the Preview with representative success input, then with failure input, confirm both come back as you designed them, then and only then wire the FlexCard data source, the OmniScript Integration Procedure Action, or the API consumer. This is the same "test before you wire" instinct you apply to axioms and to chained procedures, applied to the last step in the path. [^1]

## Configuration Walkthrough

Work through a concrete build. You are writing an IP that looks up a customer's account by an account number and returns a small set of fields plus a computed balance, with a clean error when the account is not found. This exercises exactly the four numbered steps the requirement calls for.

1. **Add a Response Action as the final action.** In the Integration Procedure Designer Structure panel, drag a Response Action into the structure as the last step so the procedure ends by returning its output. [^1] Open its properties. Decide on your trimming strategy first: you want to return specific data, so plan to use Additional Output combined with Return Only Additional Output, not the coarse Return Full Data JSON, for the default path. [^1]

2. **Map the output JSON: the data paths to include.** In the Response Action properties, add the fields the caller needs. Each becomes a key/value pair under Additional Output, and the value uses a merge field that points at the data path produced by the earlier extract step, so `AccountName` maps to the extracted name, `Status` maps to the account status, and a computed `balanceDue` maps to a formula or a merge field that carries the current balance. [^1] For a value that should sit at a nested level, give the Key a colon-delimited path, such as `billing:street`, so it lands in the right spot in the JSON. [^1] Confirm the exact node names now, because the FlexCard you wire later will bind to these exact paths. [^2]

3. **Add an error branch returning a consistent error shape.** Design the failure route to return the same wrapper structure as success. If an earlier step, such as the extract, finds no matching account, route execution so the error branch produces a payload with an outcome flag, an error code, and a message, in the same shape the success path uses. [^3] Use the controlled error mechanism you learned in the Try-Catch lesson, where Failure Response key/value pairs carry the code and message, and let the Response Action ship them out. [^3] If callers need the HTTP layer to register the failure, add a Response Headers key named StatusCode with a valid error value such as 404, so the transport agrees the call did not succeed. [^1] Never let the failure path return a raw, unstructured exception while the success path returns a tidy object; the whole point is that both routes obey the same contract. [^3]

4. **Test with sample inputs; verify the response in the test tool.** Open the Preview, enter an account number that hits a real account, and run it. Read the returned JSON and confirm it contains exactly the mapped fields in the exact structure, and that nothing extraneous from the internal data JSON leaked out. [^1][^2] Then enter an account number that matches nothing and run again. Confirm the error branch returns your structured shape with the expected code and message, and check that the StatusCode header, if you set one, is what you intended. [^1] These two runs are the contract test. Only after both come back as designed do you wire the FlexCard data source or the OmniScript action, because the shape is now locked and verified. [^1]

## Exam Traps

- **No Response Action at all.** The most direct failure this requirement warns about, and it answers quiz question three. If an IP has no Response Action, the callers receive no defined output, and the IP fails to deliver its contract. [^1] Nothing is returned by default, it does not magically return everything, and it does not echo the first input. The IP ends and no payload is defined for the caller, which is a broken contract. Any IP you hand to a consumer needs its Response Action. [^1]

- **Inconsistent success and error shapes.** If success returns a tidy object but failure returns an unstructured dump, the caller cannot reliably handle failures, because it has no stable path to bind the error to. [^3] This is quiz question two: keep success and error shapes consistent so FlexCards and OmniScripts can handle both reliably. Design a single wrapper that carries either the result or a coded error, and return it on both routes. [^1][^3]

- **Returning the entire data JSON when callers need specific fields.** Reaching for Return Full Data JSON when the consumer binds to three fields ships the whole warehouse: intermediate values, raw step responses, and fields nothing asked for. [^1][^2] Over-returning is the anti-pattern. Match the response to what the caller reads, using Additional Output with Return Only Additional Output for a tight allowlist, and trimming the wrapper with Response JSON Path and Node where structure matters. [^1][^2]

- **Binding callers before the shape is verified.** Wiring a FlexCard to an IP whose response you have not tested means the first feedback is a card that fails to render, and the fix re-publishes a procedure a consumer already depends on. [^1] Test the contract in the Preview on both success and failure paths before you connect a single consumer, because test-before-wire is how you keep the shape from breaking callers later. [^1]

- **Setting StatusCode to a body value instead of an HTTP value.** The Response Headers StatusCode key expects a valid HTTP response value, not a payload field. [^1] Putting a business string there, or expecting the header to be set by a merge field that contains a message, produces an invalid transport result. Use StatusCode for the HTTP code and keep the human-readable message in the body. [^1]

## Exam Tip

Hold one phrase in front of you: the Response Action is the IP's API. [^1] When you see a question about what an IP returns, the answer always routes back to the Response Action, which maps the output contract and nothing else. When you see a scenario where success and failure must be handled by one caller, the fix is a consistent shape on both routes so the UI can react to success and failure alike. [^3] When you see an IP with no Response Action, callers have no defined output and the contract is broken. [^1] And when you are configuring one, be deliberate: map only what the caller needs, use the Return Only Additional Output allowlist to keep the payload clean, small, and safe, add a consistent error branch with an optional StatusCode override, and test the whole shape in the Preview before you wire a FlexCard or OmniScript to it. Map it deliberately, keep the shapes consistent, and test before wiring consumers. Those instincts answer every question in this requirement, because they are the whole discipline of the output contract. [^1][^2][^3]

## Try It

Open the Integration Procedure Designer in a sandbox. Name the IP `LookupAccountByNumber` and give it an input of an account number. Add a Data Mapper Extract that reads the Account object by that number and returns a small set of fields, say Name, Status, and BillingStreet. Then add a Response Action as the final step. In its properties, use Additional Output to map the account's Name, Status, and a nested `billing:street` value using colon-delimited keys, enable Return Only Additional Output, and confirm Return Full Data JSON stays off. Run it in the Preview with a valid account number and read the returned JSON. Confirm it contains exactly the mapped fields and nothing else. [^1][^2] Now build the failure route. For the case where the extract finds no matching account, make the flow return the same wrapper structure with an outcome of `error`, a code such as `ACCOUNT_NOT_FOUND`, and a readable message, and if you want to check transport-level signalling, add a Response Headers key named StatusCode with value 404. Run the failure case in the Preview and confirm the structured error comes back in the same shape as success. [^1][^3] Then, as the final experiment, create a throwaway IP with no Response Action, run it, and observe that the caller receives no defined output. That empty result is the whole reason IP-7 exists, and it is the lesson that makes the contract real. [^1]
