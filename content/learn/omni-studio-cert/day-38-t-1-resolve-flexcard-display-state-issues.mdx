A FlexCard that renders blank is the most common troubleshooting moment in this domain, and the instinct to reach for the designer and rebuild is almost always wrong. [^1] The card is not broken because of its layout. It is broken because the data feeding it does not match what the card expects. [^1][^4] Requirement T-1 asks you to resolve FlexCard display and state issues, and the whole skill compresses into one habit: read the payload before you change anything. [^1][^3]

This lesson gives you the exact order of diagnosis that separates a fix from a futile rebuild. Data JSON first, then bindings, then states, then styling. [^1] That order is load bearing. A blank card, a field that will not show, a state that never triggers, all of them trace back to the data and how the card reads it, so you resolve them in the same sequence you would use to find them. [^1][^4] Work a full diagnosis with me and you will walk into the exam knowing the first question to ask when a card looks wrong.

## Deep Dive

### Read the data JSON first, because the payload explains most blanks

Start with the definition. A FlexCard gets everything it shows from a data source, and that source returns JSON. [^2][^4] The FlexCard maps JSON paths to the fields and elements on the canvas; if a path has no value, the card has nothing to render there. [^4][^5] That is why the very first diagnostic step for a blank card is to inspect the data JSON that the card's data source returns, not to change the theme, disable security, or rebuild the card. [^1][^3] The data JSON is the ground truth, and a blank almost always means the ground truth is wrong.

Three data-level problems cause blanks before any layout issue can. [^1] First, a wrong shape. The card binds to `account.name`, but the source returns a flat `name` with no account wrapper, so the binding points at nothing and the field renders empty. [^4] Second, missing fields. The JSON is otherwise fine, but the query never selected the field the card displays, so there is no value to show. [^1][^4] Third, an empty result set. The source ran fine and returned no records, and because the card has no empty state, the user sees a blank card instead of a "no records" message. [^1][^3] Notice that none of these are styling problems. You can restyle a blank card all day and it stays blank. [^1]

![Three data-level problems render a FlexCard blank: a wrong shape where the binding points at nothing, a missing field the query never selected, and an empty result set with no empty state to show a message](</diagrams/day-38-t-1-resolve-flexcard-display-state-issues/2-three-data-problems.png>)

The order of diagnosis rule covers this directly. Inspect the card's data JSON first and you find the shape, missing, or empty problem in the first minute. [^1][^3] The exam measures this too. When a question asks what the first diagnostic step is for a FlexCard that renders blank, the answer is to inspect the data JSON from its data source, because wrong shape or missing fields cause blanks before any layout problem. [^1][^3] The other options, rebuild the card, change the theme, disable security, all address symptoms, not the cause. [^1]

### A state that never triggers is usually a condition that never evaluates true

A FlexCard can have multiple states, each with its own layout, and conditions decide which state shows. [^3][^6] The card evaluates its states in order, and the first state whose condition is true renders. [^3][^6] A common failure is a state that never displays even though the data exists, and the likely cause is that the condition does not match the actual data values. [^1][^3][^6]

The condition is an expression over card data, and for it to fire it must evaluate true against the live values. [^1][^6] Three mismatches hide a state. [^1] A path mismatch: the condition reads `case.Priority`, but the JSON stores priority at `case.priorityLevel`, so the path resolves to nothing and the comparison is never true. [^1][^6] A type mismatch: the condition compares a string field to a number literal, or a text value to a numeric operator, and the comparison is always false even though the data "looks right" in the JSON. [^1][^3][^6] A casing mismatch: `Priority` versus `priority`, where the condition points at a key the JSON never produces. [^1] All three share the same root cause, the condition is written against an assumption, not against the actual returned JSON, so it never evaluates true and the state silently stays hidden. [^1][^6]

![Three state-condition mismatches keep a state hidden: a path mismatch where the condition reads case.Priority but the JSON stores case.priorityLevel, a type mismatch comparing a string to a number, and a casing mismatch between Priority and priority](</diagrams/day-38-t-1-resolve-flexcard-display-state-issues/3-state-condition-mismatches.png>)

This is why the diagnostic order points you at the data JSON before the condition. [^1] You cannot judge whether a condition is right until you have seen the real path, the real type, and the real casing in the payload. [^1][^6] The exam taps this directly. A card state that never displays even though data exists is most likely caused by a condition that does not match actual data values, not by a dark theme, a missing data source, or the page being in a Community. [^1][^3] The state logic is the suspect, and the condition-to-data mismatch is the first thing to verify. [^1][^6]

### Binding path typos hide fields and break repeaters

Element bindings connect a field on the canvas to a value in the JSON, and the binding must match the JSON key exactly. [^4] Case matters, nesting matters, and a typo produces a field that renders empty with no obvious error. [^1][^4] A card that binds to `Account.Name` while the JSON key is `account.name` shows nothing in that field even though the record is right there in the payload. [^1][^4] So the diagnostic habit is to compare the returned fields to the bindings, path by path, key by key, and fix the side that is wrong. [^1][^4]

Repeaters add a second layer. A repeater iterates over an array, and its child fields bind relative to each repeated item. [^5] A binding inside a repeater that points at the root object instead of at the current item resolves to nothing per row, so each row renders empty. [^1][^5] When you check repeater bindings, verify the paths are relative to the repeated record, not absolute against the top of the payload. [^1][^5] Bindings, states, and the JSON are the middle of the diagnostic order, and the binding check is a direct comparison: returned field, spelling, case, nesting. [^1][^4]

### Data source errors surface in the Debug Console, not the page

Sometimes the data is the problem at the source, not the mapping. The data source makes a call to a Data Mapper, an Integration Procedure, or a custom Apex method, and that call can fail on auth, on filters, or on the server. [^2][^4][^7] Those failures rarely announce themselves on the card; they surface as a blank or a broken render. [^1] The tool that captures the request and response logs for OmniStudio components, including the card's data source, is the Debug Console. [^1][^7]

The FlexCard Designer documentation is explicit about this: you debug a FlexCard by viewing its data JSON and the response and request logs for its actions and events. [^1] In the Debug Console you read the request the card made and the response it got back. [^7] The evidence is in the payloads. [^1][^7] A request that failed authentication shows an auth error in the response. [^7] A Data Mapper that filtered wrong returns an empty array instead of the expected records. [^2] A server-side exception returns an error body. [^7] Each of those tells you where to fix it, and all of them you see in the Debug Console before you touch a single element on the card. [^1][^7]

The exam ties the Debug Console to exactly this. When a question asks which tool shows the request and response logs for the card's data source, the answer is the Debug Console. [^1][^7] Reports, Data Loader, and Workbench all serve other purposes; the Debug Console is the OmniStudio-specific tool that logs what each component sent and received. [^7] Lesson 46 goes deep on the Debug Console itself, but the piece you need here is that it is where a data source error becomes visible. [^1][^7]

### Order of diagnosis: data JSON, then bindings, then states, then styling

Compress the whole requirement into a sequence and it fits in four steps. [^1] Data JSON first, because wrong shape, missing fields, and empty result sets cause blanks before anything else. [^1][^3] Bindings second, because a binding path that does not match the JSON hides a field even when the data is present. [^1][^4] States third, because a condition that never evaluates true silently hides content. [^1][^6] Styling last, because you only reach for the style panel once you know the data, the bindings, and the states are correct. [^1] Do not rebuild the card before reading the payload. [^1]

![The order of diagnosis for a misbehaving FlexCard runs data JSON first, then bindings, then states, and styling last, with the rule to never rebuild before reading the payload](</diagrams/day-38-t-1-resolve-flexcard-display-state-issues/1-order-of-diagnosis.png>)

That order is the exam tip in one line: FlexCard debugging runs data JSON to bindings to states, and the payload explains most blanks. [^1][^3] Hold it and nearly every display or state question becomes a sequencing question, which step comes first, which tool reads the evidence, where does the mismatch live. [^1] The discipline is what the exam grades. [^1]

## Configuration Walkthrough

Work one concrete failure end to end. You open a record page and the FlexCard is blank. Run the numbered diagnosis below and land on the fix in minutes, not hours. [^1][^3]

1. **Open the Debug Console and inspect the card's data JSON.** The FlexCard Designer exposes the card's data JSON, and the Debug Console logs the request and response for the source. [^1][^7] Read the returned payload first and answer one question: does the JSON contain the records and fields the card is supposed to show? [^1][^3] If the result set is empty, you already know the source returned nothing, and you move to step four to find out why. [^1][^3] If the result set has records but the card still shows nothing, the shape is wrong and you move to step two. [^1]

2. **Compare the returned fields to the bindings, path by path and case by case.** Take the actual keys from the JSON and check each element binding against them. [^1][^4] Is the binding `account.name` and the key `account.name`? Is `Priority` actually lowercase `priority` in the payload? [^1][^4] Inside a repeater, are the bindings relative to each repeated item, not absolute against the root? [^1][^5] Fix any path, case, or nesting mismatch. [^4] A field that binds to a key that does not exist stays blank even though the data is sitting in the payload. [^1][^4]

3. **Verify the state conditions against the real values, including types.** Now that you have the real keys, check each state condition against the actual value in the JSON. [^1][^6] A condition that tests `Priority == 'High'` must see a string `High`, not a number or a differently cased value. [^1][^6] A condition on a numeric field must compare like types. [^3] If the state is meant to appear for a value the data does not actually contain, the condition is never true and the state stays hidden. [^1][^6] Confirm the empty state exists at all, because a card with no empty state renders blank on an empty result set. [^1][^3]

4. **Check the data source request and response in the Debug Console for errors.** The data is empty or malformed, so read the source's call. [^1][^7] Look at the request: did the card pass the right input parameters and filters? [^2][^7] Look at the response: is there an auth error, a server error, or a filter that returned nothing? [^7] The Debug Console shows you exactly what the card sent and what the source answered. [^1][^7] Fix the source, the parameter, or the filter, then re-run and re-read the JSON. [^1][^7]

That is the whole walkthrough, and the order is the point. [^1] You inspected the JSON, checked the bindings, verified the conditions, and only then looked at the source. [^1] When you fix the underlying data or mapping, the card renders without a rebuild. [^1][^3]

## Exam Traps

- **Rebuilding the card instead of reading the JSON.** The most expensive wrong move. A blank card is usually a data or binding problem, and rebuilding discards the very evidence that names the cause. [^1] Read the data JSON first, and you find wrong shape, missing fields, or an empty result set before you change anything. [^1][^3] The exam rewards the reader, not the rebuild. [^1]

- **Type mismatch in state conditions.** A condition that compares a string to a number, or tests text against a numeric operator, is never true, so the state silently never shows. [^1][^3][^6] Verify the condition against the actual value and type in the JSON, not against what you think the field holds. [^1][^6]

- **Testing only as an admin.** Admin tests run with a permission layer that real users do not have, so a card can look perfect for you and fail for everyone else. [^1] Permission differences on the data source, the record, or the component can hide real failures. [^1][^7] Test with a non-admin user and check the Debug Console as that user to surface what the admin view masked. [^1][^7]

## Exam Tip

Compress T-1 into the diagnostic sequence and the lesson writes itself. [^1] Data JSON first, because wrong shape, missing fields, and an empty result set cause blanks before any layout problem. [^1][^3] Bindings second, because element bindings must match JSON keys exactly in path, case, and nesting, and repeater fields bind relative to each repeated item. [^1][^4][^5] States third, because a condition that never evaluates true against the real values and types silently hides content. [^1][^6] Data source errors fourth, read in the Debug Console, which logs the request and response for the card's source. [^1][^7] Never rebuild before reading the payload. [^1] The payload explains most blanks, and the first question to ask about any wrong-looking card is what its data JSON actually contains. [^1][^3]

## Try It

Open a FlexCard in a sandbox and force each failure so you learn to read it. [^1][^3] Start by building a card that binds to a field, then change the Data Mapper so it returns a differently named or differently cased key, and watch the field render empty with the value sitting right in the JSON. [^4] Fix the binding to match the real key. [^4]

Then add a state whose condition compares a string field to a numeric literal, run the card, and see the state never fire even though the data is present. [^1][^6] Change the condition to match the real type and value, and watch the state appear. [^1][^6] Remove the empty state, load a record with no related data, and see the blank card that users report. [^1][^3] Re-add the empty state and give it a "no records" message. [^3]

Finally, break the data source, an auth setting or a filter that returns nothing, and read the request and response in the Debug Console. [^1][^7] Name out loud where each of the four problems lived: the JSON, the binding, the state condition, or the source call. [^1] If you can say that for a card that misbehaves, you can resolve any display or state issue on the exam. [^1]
