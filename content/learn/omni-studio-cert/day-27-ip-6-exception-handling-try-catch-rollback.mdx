An Integration Procedure orchestrates work across systems, and some of that work will fail. The remote service you call goes down. A Load action hits a validation rule you did not see coming. A Data Mapper returns zero records when the caller expected at least one. None of these are exotic. They happen in normal operation, and the difference between a robust IP and a fragile one is what the procedure does at that exact moment. A fragile procedure dies mid-flow, leaves a stack trace in a caller's face, and may have already written half its data before it stopped. A robust procedure catches the failure where it happens, records why, returns a predictable error to whoever called it, and leaves the system in a state you can reason about. Requirement IP-6 asks you to build the second kind. [^1]

Requirement IP-6 reads: implement robust exception handling using Try/Catch blocks to manage failures and ensure proper rollback. [^1] The exam tests it through three claims you need to be able to defend, and the in-lesson quiz maps directly to them. First, when an IP calls an external system that may be down, the correct handling is to wrap the call in a Try/Catch block and return a controlled error, not to let the IP crash, not to ignore the error, and not to reach for a FlexCard state. Second, Load and write actions belong after risky calls because that ordering avoids partial persistence and keeps the procedure rollback friendly. Third, a Catch block logs the failure and produces a controlled error response; it never swallows the error silently. Every section below teaches toward those three claims, because they are the exam's way of checking that you understand the failure model and not just where the Try-Catch element sits in the palette. [^1]

## Deep Dive

### What Try/Catch means in an Integration Procedure

A Try-Catch Block is a container you drag into the Structure panel of an Integration Procedure. It wraps a set of steps, and it changes what happens when one of those steps fails. [^2] Salesforce puts it plainly: a Try-Catch Block lets you "try" running the steps inside it and then "catch" the error if a step fails. [^2] That is the whole mental model, and it is worth unpacking because the two halves do very different jobs.

The Try half is the risky work. Steps inside the block run normally, in order, exactly as they would without the block. The container does not make those steps more likely to succeed. It changes the consequence of failure. When a step inside a Try-Catch Block fails, execution does not abort the entire procedure the way it would outside the block. Control moves to the Catch branch, and the procedure gets a chance to respond. [^2]

The Catch half is the recovery. It decides what the procedure does now that a step has failed. In OmniStudio you configure the Catch behavior in two ways, and you can use either or both. [^2] Under Failure Response you specify a key-value pair to return as the response, and the value can be a formula or, in Spring '20 and later releases, a merge field. [^2] Under Custom Failure Response you specify a Remote Class and a Remote Method to execute an Apex class, and that Apex class must implement Callable. [^2] The first option shapes the JSON that goes back to the caller. The second option runs real Apex logic, which is how you do heavier recovery work such as updating a status record or calling a fallback endpoint.

Two checkboxes make the block behave. The block itself has a Fail on Block Error checkbox, which you must have checked for the Catch behavior to fire when any step inside fails. [^2] And each individual step you put inside has a Fail on Step Error checkbox, which you check on each step that must trigger the Catch behavior if it fails. [^2] If a step inside the block does not have Fail on Step Error checked, a failure in that step does not route into the Catch branch the way you expect. You are choosing, step by step, which failures are catchable. This granularity matters on the job: you do not always want the first hiccup in a block to throw everything into the Catch branch. Sometimes a step can be allowed to fail quietly and let the next step decide, and the checkbox is how you make that call.

### The option that gates it: Fail On Step Error

There is a companion property that lives on every action, independent of any Try-Catch Block, and you need it to understand how failures propagate in OmniStudio's standard runtime. In the current runtime the property is called Fail On Step Error, and enabling it terminates the Integration Procedure if the conditional formula determines that the step has failed. [^1] In the managed-package designer the same control was surfaced as Fail on Step Error, and the doc also refers to a "Terminate when step fails" behavior on actions. [^3] The name drifted across runtimes, so on the exam treat "the procedure ends if this step fails" as the concept and do not let yourself be caught out by which label a question uses.

The companion to it is the Failure Conditional Formula, which you set per step. [^1] A Failure Conditional Formula specifies a custom condition that runs after the step executes, and it returns TRUE if that step failed. [^3] The subtle point, and it is a favorite exam idea, is that some failures are not technical errors at all. Consider a Data Mapper Extract that finds no matching records. The extract executed without throwing an exception, so the platform does not treat it as a failure. But for your business flow, returning zero records when the caller needs a record is a failure. You express that judgment with a Failure Conditional Formula that evaluates to TRUE when the result is empty, and that formula is what turns "no records found" into a step failure you can catch and handle. [^2][^3] Salesforce's own documented example builds exactly this: an IP that finds Contacts by name and returns an error message when none are found, using a Failure Condition Formula on the extract because returning no records is not normally a failure. [^4] Without that formula, the IP would quietly proceed as if success, and the caller would never learn the lookup came up empty.

### Rollback: the second half of the requirement

The exam phrase in requirement IP-6 is "ensure proper rollback," and it points at a real hazard. [^1] Consider an IP that first creates an Account, then creates an Opportunity under that Account, then calls an external credit system. If the external call fails after both records were written, you have created orphaned data: an Account and an Opportunity that represent a transaction the external system never accepted. The write actions already ran. Unless something rolls them back, they stay.

The mechanism Salesforce documents is Rollback On Error, and it lives in two places you should know. First, a Data Mapper Load (a post action that writes to Salesforce objects) has a Rollback On Error option on its Options tab. [^5] When an error occurs during the Load, that option rolls back all the updates the Load was making, so a parent record is not left behind when its child fails. Trailhead's example is direct: a Load creates Account and Opportunity records, the Opportunity save fails because a closing date is missing, and because Rollback On Error is set, the transaction rolls back the Account record too. [^5] Second, the Integration Procedure itself can carry Rollback On Error in its Procedure Configuration. [^5] That setting treats the operations inside the transaction boundary as one unit: all changes are committed only after every operation in the transaction finishes without error, and if any intermediate step fails with the option enabled, all database changes are rolled back and the transaction is not committed. [^5]

Hold onto a precise model of what rollback can and cannot do, because it determines the whole design rule in this requirement. Salesforce is explicit that changes are committed to the database only after all operations in the transaction finish running without errors, and when an error occurs with Rollback On Error enabled, the database changes are rolled back. [^5] So the protection is real for the writes inside that transaction boundary. But the cleanest way to guarantee you never leave partial data is to avoid the situation entirely: catch failures before you write, and order the procedure so the fallible work comes first and the writes come last. That ordering is the second quiz claim, and it is not about speed or caching or licensing. It is about making partial persistence impossible by construction. [^5]

### Why writes go after the risky calls

The Load-write-after-risky-call rule is the single most practical idea in this requirement, and it follows directly from the rollback model. If you write data and then call something that can fail, a failure leaves the write committed and the procedure unable to complete its intent. If you call the fallible thing first and write only after it succeeds, a failure happens before any write, so there is nothing partial to clean up. [^5]

Think through a concrete ordering. Bad ordering: extract the payload, create the Account, create the Opportunity, then call the external payment system. If the payment call fails, both records exist and the transaction is half done. Good ordering: extract the payload, call the external payment system, and only after it confirms do you create the Account and Opportunity. If the payment call fails, nothing was written, so the only work is returning the error. This is why the exam pairs Try/Catch with ordering: the Try/Catch handles the failure, and the ordering decides whether handling that failure requires a rollback at all or whether it is a clean stop before any persistence. [^1][^5]

There are legitimate cases where you must write before a call, such as posting a status that a callout depends on. In a single synchronous transaction Salesforce also forbids doing DML before an HTTP callout, a rule you saw in the chaining lesson. Those cases get solved with Chain On Step so the write commits in its own transaction before the callout, not by abandoning rollback thinking. The general rule stands: when you control the order, put the fallible external work first and the writes after it, and use a Try-Catch Block plus Rollback On Error for the writes that genuinely must precede a call.

### The controlled error shape

Robust handling is not just about not crashing. It is about giving the caller something it can act on. When a Try-Catch Block catches a failure, you shape that response with the Failure Response key-value pairs. [^2] Trailhead's ClearLight walkthrough is the canonical example. The architect sets the Failure Response keys to carry an error code and a message, plus a Detail value that pulls the actual error via a merge field into the underlying step's error path. [^5] The caller then receives JSON with an ErrorCode, a Message, and a Detail node, which is a predictable contract it can parse and display instead of choking on an unstructured failure. [^5]

You can go further with the action-level Failure Response that every Integration Procedure action exposes. [^3] The common action properties include Failure Response, described as key-value pairs to be returned in the output JSON data if the action fails, with values that can include formulas and merge fields, and a companion Send Only Failure Response that returns only those pairs if the action fails. [^3] That is how a single step communicates a controlled error even without a surrounding block. And the Failure Conditional Formula ties it together: when the formula returns TRUE, the key-value pairs in the Failure Response list are added to the JSON data. [^3]

The shape you return is your choice, but it should be consistent and it should be truthful. A caller that gets back a clean node saying "the credit check failed with this code and this message" can branch on it, retry, or show a friendly error. A caller that gets back an unhandled exception has to guess. The exam phrase "return a controlled error shape" is really about that consistency: same structure on every failure, so every consumer of the IP handles errors the same way.

### Never swallow errors

The quiet failure is the one that costs the most, because nothing tells you it happened. A Catch block that does nothing, an error that is caught and discarded, a failure that is logged nowhere: each of these leaves the system in a state nobody knows is wrong. [^1] Salesforce is explicit about the discipline that prevents it: to capture detailed information about failed Integration Procedure steps, configure error logging, and the platform writes all Integration Procedure errors to OmniComponentErrorLog records. [^1][^6] That is the logging half of the contract. When a step fails, there should be a durable record of which step, on which invocation, with what message, so that a support engineer or an audit can find it after the fact.

The other half is the response. The Catch branch must return why, not just that something failed. A controlled error with a code, a message, and a detail is the observable contract; the log entry is the durable contract. Robust IPs hold both. They log what failed, they return why, and they leave the system in a known state, whether that state is "nothing was written" because the writes never ran or "everything was rolled back" because Rollback On Error undid a partial write. [^1]

## Configuration Walkthrough

Work through a concrete build. You are writing an IP that accepts a request to open a customer account, runs a credit check against an external system, and if the check passes, creates the Account and an Opportunity. The credit system is occasionally down, and your customer wants a clean error when it is. This is the ClearLight pattern from Trailhead. [^5]

1. **Wrap the risky actions in a Try-Catch Block.** Drag a Try-Catch Block into the Structure panel. [^2] Place the actions that can fail inside it, and the most failure-prone actions are external calls: the HTTP action that hits the credit system, and any Remote Action that invokes an Apex class doing its own callout. In this IP, the credit check HTTP action goes in the block. Make sure the Try-Catch Block's Fail on Block Error checkbox is checked so a failure inside triggers the Catch behavior. [^2]

2. **Check Fail On Step Error on the steps that must trigger the Catch.** For each step inside the block whose failure should route into the Catch branch, enable Fail On Step Error. [^1][^2] The credit check HTTP call is the one that must trigger it, so enable it there. Add a Failure Conditional Formula where a business condition, not just a technical crash, counts as failure. If the credit system returns a response that means "declined," decide whether that is a failure you catch or a normal result you branch on. If a data lookup that returns nothing should fail the flow, give that extract a Failure Conditional Formula that returns TRUE when its result is empty. [^3][^4]

3. **In the Catch branch, log the error and set an error path or flag.** Configure the block's Failure Response with key-value pairs that name the failure. [^2] Add an ErrorCode, a Message, and a Detail that pulls the underlying error text via a merge field into the failing step's error node. [^5] Separately, enable error logging for the procedure so the platform writes the failure detail to OmniComponentErrorLog records, giving you a durable record that does not depend on the caller reading the response. [^1][^6]

4. **Ensure writes happen only after the risky work succeeds.** Structure the procedure so the credit check runs before any Load action writes the Account or Opportunity. Because the write actions come after the fallible call, a credit-system failure is caught before anything is persisted, so there is no partial data to clean up. [^5] If your procedure has Load actions that genuinely must run before a call, set Rollback On Error on those Loads, and consider Rollback On Error in the Procedure Configuration, so that a later failure rolls back the earlier writes instead of leaving them orphaned. [^5]

5. **Return a controlled error shape via the Response Action.** After the Try-Catch Block, add a Response Action that returns the result to the caller. [^7] On the success path, return the account and opportunity data. On the failure path, the Failure Response pairs from the block flow into the output so the caller sees a structured error. Set the Response Action's properties deliberately: use Additional Output to control exactly which nodes go back, or Return Full Data JSON to send the whole payload, and if you want a non-200 status, add a Response Headers key-value pair named StatusCode with the HTTP value you want the caller to see. [^7] The Response Action is what turns the caught failure into a clean, parseable contract, which is precisely the "controlled error shape" the requirement wants. [^1][^7]

6. **Test both paths.** Open the Preview, run the success path and confirm the Account and Opportunity are created. Then simulate the credit system being down (point the HTTP action at an unreachable endpoint or a URL that returns a failure) and run again. Confirm the procedure does not crash, the error code and message come back in the response, the error appears in the log, and no Account or Opportunity was created. That last check is the proof that your ordering plus your rollback settings did their job. [^5]

## Exam Traps

- **No Try/Catch around an external call.** The most direct failure mode the requirement warns about. An external system going down is not a question of if but when, and without a Try-Catch Block a failed HTTP call kills the whole IP mid-flow. [^1] Wrap external calls in a Try-Catch Block, check Fail On Block Error and Fail On Step Error, and return a controlled error. That is the entire answer to quiz question 1, and it rules out both "let the IP crash" and the tempting wrong answer "use a FlexCard state," because a FlexCard state is a UI rendering concept, not a server-side failure handler.

- **Swallowing the error.** A Catch branch that catches and does nothing is worse than no Catch at all, because the failure becomes invisible. [^1] Silent data inconsistency is the result: a step failed, nothing wrote, and nobody knows. The Catch branch must log (so the platform records the failure, by default to OmniComponentErrorLog) and must return a controlled error response. [^1][^6] This is the trap behind quiz question 3, where the correct Catch behavior is to log the failure and produce a controlled error, never to do nothing, retry forever, or delete data.

- **Writes before risky calls.** If a Load action creates the Account before the credit check runs, a credit-check failure leaves an orphaned Account. [^5] Ordering is rollback safety: put the fallible external work first and the writes after it, so a failure happens before anything is persisted. Where a write must precede a call, enable Rollback On Error so a later failure undoes the earlier write. This is quiz question 2: Load/write actions go after risky calls specifically to avoid partial persistence and keep the procedure rollback friendly, not because it is faster, not for caching, and not for licensing. [^5]

- **Misreading a business condition as a non-failure.** A Data Mapper that returns zero records does not throw, so it is not a technical failure. If your flow needs those records, a zero-result is a failure and it needs a Failure Conditional Formula that turns it into one. [^3][^4] Without it the procedure proceeds as if everything is fine, and the caller never learns the lookup failed.

- **Letting a step failure abort the whole procedure by default.** Outside a Try-Catch Block, a step configured with Fail On Step Error terminates the IP. [^1] If you want a procedure to survive a failure in one step and continue or respond gracefully, that step belongs inside a Try-Catch Block. Know which property ends the procedure and which routes failure into a Catch branch, because a question will hand you a scenario and ask which behavior actually applies.

## Exam Tip

Keep one sentence in front of you: Try is risk, Catch is controlled failure, order is rollback safety, and no silent swallows. [^1] When you see an IP that calls an external system, wrap it in a Try-Catch Block and return a controlled error. When you see Load actions near external calls, check that the writes come after the fallible work, and add Rollback On Error where a write must precede a call. When you see a Catch branch, make sure it logs the failure and produces a predictable error shape instead of doing nothing. If a step can fail for a business reason rather than a technical crash, reach for a Failure Conditional Formula. Those four reflexes answer every question in this requirement, because they are the whole content of robust exception handling: contain the failure, record it, report it, and never leave partial data behind. [^1][^5]

## Try It

Open the Integration Procedure Designer in a sandbox and build the account-opening IP described above. Give it an input carrying an account name and a credit check payload. Add a Try-Catch Block. Inside it, put an HTTP action that calls a deliberately unreachable URL to stand in for a downed credit system. Check Fail on Block Error on the block and Fail on Step Error on the HTTP action. Configure the block's Failure Response with an ErrorCode, a Message, and a Detail that merges in the step's error. After the block, add a Response Action. Then build the success path: a Data Mapper Load that creates an Account after the credit call, with the credit call pointed at a URL that returns 200. Run the success path in the Preview and confirm the Account is created and the response is clean. Point the credit call at the failing URL and run again. Confirm the procedure returns your structured error instead of crashing, confirm nothing was written, and check the log for the failure. Then deliberately place a Load before the credit call, add Rollback On Error to it, and run the failure case to watch the earlier write roll back. That last experiment is the one that makes the ordering rule and the rollback mechanism stick. [^5]

## What's Next

This lesson was about containing a failure inside a procedure and deciding whether it rolls back. But a controlled error is only useful if the caller can read it, and that turns on what the Response Action actually sends back. Lesson 28, Response Action: The IP Output Contract (IP-7), is the next requirement in the Integration Procedures domain, and it teaches how the Response Action defines the shape of everything an IP returns: which nodes go out, how to trim the response, how to return additional output, and how headers and status codes round out the contract a caller depends on. Exception handling decides what happens on the way out; the Response Action decides what the caller sees when the procedure ends, and the two together are how a production IP fails and reports cleanly.
