This requirement asks you to explain two runtimes and two kinds of upgrades, and it is a favorite source of easy points because the distinction is clean once you see the one axis underneath it. OmniStudio components can be delivered and upgraded one of two ways. Either they ride inside a managed package, which is the legacy Vlocity model, or they live as native platform metadata that arrives with Salesforce releases, which is the modern model. Everything else in this lesson, from how you version to how you deploy to what happens on release day, follows from that single choice.

## Deep Dive

### The one axis: package delivery versus native metadata

Hold a single axis and the rest falls into place. On one side is Managed Package Runtime. On the other is Standard Runtime. The difference is not cosmetic and it is not about the designer. It is about whether OmniStudio components are packaged and installed or treated as first-class platform metadata.

Managed Package Runtime is the legacy Vlocity delivery model. OmniStudio components ride inside a managed package with a namespace, typically a Vlocity or OmniStudio namespace. The org installs the package, and upgrades arrive as new package versions. This is the model that predates the acquisition of Vlocity by Salesforce, and many industry cloud orgs that adopted OmniStudio years ago still run on it.

Standard Runtime is the modern model. OmniStudio components are native platform metadata delivered with Salesforce releases. They deploy via source format using the Salesforce CLI, and they upgrade automatically with platform releases. There is no package install and no manual upgrade step. A Standard Runtime org has no Vlocity namespace. The components are native to the platform.

The exam tells you the runtime by the delivery mechanics. If a statement says components ship inside a managed package, that is Managed Package Runtime. If it says components are native metadata that ride platform releases and deploy via source format, that is Standard Runtime. Once you can place any statement on this axis, the runtime questions stop being about memorizing two definitions and become about recognizing the delivery clue in the wording.

### Why the runtime exists as a choice

The two runtimes are not arbitrary alternatives. They represent two eras of OmniStudio delivery. Managed Package Runtime is the architecture inherited from Vlocity, where the entire product, components and engine together, shipped as an installable package with a namespace. That model predates OmniStudio becoming native to the platform, and it is why long-standing industry cloud orgs carry a Vlocity or OmniStudio namespace in their installed packages.

Standard Runtime reflects OmniStudio being rebuilt as part of the Salesforce platform itself. The components are metadata the same way a Flow or an Apex class is metadata, delivered with the release train and deployed with ordinary source tooling. Understanding that the runtime is an architectural era, not a cosmetic toggle, explains every downstream difference. It explains why Standard Runtime upgrades automatically, why it uses source-format deployment, and why migrating to it is a project rather than a checkbox.

### Automatic versus manual-intervention upgrades

The two runtimes produce two kinds of upgrade, and this distinction is a favorite exam point because candidates blur the words. An automatic upgrade applies seamlessly when the platform updates. Nothing a human must approve, re-publish, or validate. The new version lands and the org is on it.

A manual-intervention upgrade requires human action before it completes. The curriculum lists the steps: approve, re-publish changed components, validate customizations. When an upgrade is described as "requiring manual intervention," it does not mean the org upgrades itself with no action. It means people must review the change, re-publish the affected components, and validate that customizations still behave before the org is considered upgraded.

Keep the two separate from each other and from deployment. Upgrades come from the vendor or the platform. Deploys are your own moves between your own environments. Mixing "upgrade" with "deploy" is a classic trap. An upgrade is something that happens to the software you use. A deploy is something you perform with your changes.

### What runtime choice affects downstream

The runtime you are on changes everything after the build. Versioning is the first downstream difference. In Standard Runtime, components are metadata you retrieve into source format and store in version control, so git is your history. In Managed Package Runtime, components travel as DataPacks and the package is the unit you track.

Deployment differs too. Standard Runtime uses the Salesforce CLI source-format deployment, the `sf project deploy` family of commands. Managed Package Runtime uses package installs, often driven by the Vlocity Build Tool. The exam will hand you a command and ask which runtime it implies. `sf project deploy` implies Standard Runtime, because source-format CLI deployment is the Standard Runtime pattern and packages use package installs instead.

Testing and release day change as well. With automatic upgrades, the platform advances under you and you validate that your components still work with each release. With manual-intervention upgrades, a release is an event you schedule, staff, and review. The exam wants you to connect the runtime to these behaviors, not just name the two models.

### Why Standard Runtime is the strategic direction

The two runtimes are not equal in longevity. Standard Runtime is the modern, strategic direction for OmniStudio, and Salesforce has said so directly. It is the native environment on the platform, offers faster performance, and receives the newest innovations. Managed Package Runtime is the legacy environment that remains in place for existing customers but does not get the same forward investment. Candidates are expected to know which model the platform is steering toward, because it explains why orgs are encouraged to migrate.

The advantages of Standard Runtime flow from its being native metadata. Components upgrade automatically with platform releases, so the org does not fall behind on a vendor release calendar. Deployment is standard source-format work with the Salesforce CLI, so components integrate with the same CI/CD tooling as every other piece of metadata. The designer is the modern Lightning-based designer rather than a legacy wrapper. Each of these is a direct consequence of the same fact: the components are part of the platform.

Managed Package Runtime keeps the older architecture. It is highly flexible, which is why long-standing industry cloud orgs still rely on it, but it depends on a package installation model and a Vlocity namespace. New features arrive as package versions that must be installed, and major upgrades can require manual intervention. The distinction the exam draws is not that one is bad and the other is good, but that one is the strategic modern path and the other is the legacy path with different mechanics.

### Worked example: a release day on each runtime

To see why the distinction is not academic, compare release day on the two runtimes. On Standard Runtime, a new Salesforce release arrives and your OmniScripts and FlexCards ride along. They were already native metadata, so the platform update applies automatically. Your work after release is validation, confirming that your components still behave as expected on the new platform version. There is no package to install and no manual upgrade step to schedule.

On Managed Package Runtime, the same release day is an event. The vendor ships a new package version. Someone must install it, approve the change, re-publish the components that the upgrade touched, and validate that your customizations still work. Until those human steps complete, the org is not on the new version. That is the manual-intervention upgrade in action, and it is exactly why the exam asks you to distinguish the two kinds of upgrades.

![Release day on each runtime: Standard Runtime upgrades automatically while Managed Package Runtime requires install, approval, re-publish, and validation](</diagrams/day-03-f3-managed-package-vs-standard-runtime-upgrades/2-release-day.png>)

The exam can test this either as a definition or as a scenario. As a definition, you explain what manual intervention means. As a scenario, you are told an upgrade requires manual intervention and asked what must happen, and the answer is human review and actions before completion, not a self-upgrading org and not a full rebuild.

### Why runtime matters beyond the build

The runtime shapes the delivery practice as much as the technology. Consider how a team works on each model. On Standard Runtime, an OmniScript is a source file in a repository. A developer edits it, opens a pull request, and a pipeline deploys it through sandbox, UAT, and production using the Salesforce CLI. The history is in git, and any environment can be rebuilt from the repository.

On Managed Package Runtime, the component is a DataPack inside a package. The unit you version and deploy is the package, and the Vlocity Build Tool handles the movement. The history lives in the DataPack and the package manifest rather than in ordinary source control. This is why lesson five treats the toolchain as a direct consequence of the runtime. The runtime tells you whether you are on the source-driven path or the package-driven path, and that single fact determines the deployment tooling you will use.

### Migration between runtimes

An org can run both models during a transition, and migration is a real project rather than a setting. Migrating from Managed Package Runtime to Standard Runtime means re-deploying components as metadata, re-validating behaviors such as JSON keys and action types, and verifying data packs and dependencies. Salesforce provides the OmniStudio Migration Assistant to automate much of the heavy lifting, converting metadata and switching the org to the standard data model.

The detail that matters for the exam is that a migration is not the same as an upgrade, and it is not a single toggle. It touches the data model, the deployment tooling, and the runtime execution. The curriculum's point that an org can run both during transition reflects the reality that a phased migration keeps the old model alive while the new one comes up. The exam asks you to explain the two runtimes and their upgrades, and knowing that migration sits on top of that framework is enough.

## Configuration Walkthrough

The configuration here is not about building a component. It is about identifying where you are and planning accordingly.

1. Identify the runtime in the org. Check the installed packages for an OmniStudio or Vlocity managed package, or check whether components are source-tracked metadata. A namespace in the installed package list points to Managed Package Runtime.
2. For Standard Runtime, enable source tracking and retrieve components via the Salesforce CLI, then store them in version control.
3. For upgrade planning, classify each incoming upgrade as automatic or manual-intervention. Schedule manual reviews for the manual-intervention ones.
4. If migrating, re-deploy components as metadata, re-validate JSON keys and action types, and verify data packs and dependencies before decommissioning the old runtime.

## Exam Traps

- **Saying Standard Runtime still ships as a managed package.** It does not. Standard Runtime treats components as native metadata that ride platform releases and deploy via source format. Managed Package Runtime is the model that ships in a package.
- **Believing manual-intervention upgrades happen without human action.** They require human review and actions such as re-publishing and validating before the upgrade completes. Automatic upgrades are the ones that need no action.
- **Mixing up upgrade with deploy.** Upgrades come from the vendor or the platform. Deploys are your own moves between your environments. The two words describe different events, and the exam uses them precisely.

## Exam Tip

Hold one axis. Native metadata plus automatic upgrades equals Standard Runtime. Package delivery plus manual steps equals Managed Package Runtime. Whenever a question describes how a component is delivered or how an upgrade arrives, place it on that axis and the answer follows.

## Try It

In a sandbox, open Setup and check the installed packages. Note whether an OmniStudio or Vlocity namespace appears, which tells you the runtime. If the org is on Standard Runtime, enable source tracking and run `sf project retrieve start` against the OmniStudio metadata types, then commit the result to a git repository. Write a short table that lists each environment you manage, marks it as Standard or Managed Package Runtime, and states whether incoming upgrades are automatic or manual-intervention. That table is the upgrade plan the exam expects you to be able to reason about.
