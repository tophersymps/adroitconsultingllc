Every rule in the earlier Integration Procedures lessons exists because someone built an IP that worked in a demo and fell apart in production. The procedure that fires six data calls because it was easier to paste them together than to split them. The IP with no error handling on its external call, so a partner outage surfaced as a blank FlexCard and a cryptic log. The reusable lookup logic copied into eleven different procedures, so a change to how accounts resolve required eleven edits, and the eleventh one got missed. Requirement IP-8, describe best practices for Integration Procedures, is the lesson that turns those anti-patterns into a set of habits you apply before you build, not after something breaks. [^1] It is the summary requirement of the Integration Procedures domain, the one that consolidates IP-1 through IP-7 into design judgment, and it is where the exam checks that you can look at an IP and tell whether it was built to be maintained or built to be replaced. [^1]

Requirement IP-8 reads as a description, but it is a judgment test in disguise. The exam does not hand you a definition to recite. It hands you a scenario, or a set of claims, and asks which one reflects how production IPs are actually built. [^1] The in-lesson quiz asks three such questions, and each maps to a claim you must be ready to defend. First, best practices favor focused, well-named IPs with consistent contracts and robust error handling, never a single massive IP that does everything. Second, reusable data logic belongs in Data Mappers that IPs reuse, not duplicated inline in every procedure, because reuse keeps that logic single-sourced. Third, an IP should be chainable when the process is long-running and exceeds synchronous limits, and not only because chaining is available, which means short orchestrations stay synchronous. Every section below teaches toward those three claims, because they are the exam's way of checking that you absorbed the domain's practices and not just its mechanics. [^1]

## Deep Dive

### Focused IPs: one logical operation, one procedure

The best practices doc is blunt about the first habit: keep an Integration Procedure to a small group of related functions, using a modular approach, to maximize reuse and performance. [^1] The plain reading of that guidance is the load-bearing one. An IP should not be a kitchen sink. It should implement one logical operation, cleanly named, with each of its actions contributing to that operation and nothing else.

Two warnings in the official material back this up, and both are about what happens when you overstuff a procedure. Use Integration Procedures for all data calls to Salesforce, and to avoid SOQL limit errors, do not put too many data calls in the same Integration Procedure. [^1] Notice the pairing. The first sentence pushes you toward IPs as your standard data-access layer, which you saw in the IP design lesson. The second sentence is the brake on that instinct. An IP that makes every data call in your org, in one giant procedure, is exactly the sort that runs out of SOQL budget and fails. The guidance is not "fewer IPs." It is "IPs for your data calls, but each one small enough to stay inside its limits."

Why does focus matter beyond the SOQL cap? Three reasons, and each is a maintainability argument. A focused IP is testable, because you can reason about what one operation should produce and verify it against a sample. A focused IP is reusable, because a small, well-named procedure that does one thing can be called from many OmniScripts, FlexCards, and other IPs without dragging unrelated work along. And a focused IP is maintainable, because when the behavior of that one operation changes, you change one procedure, not a monolith that also happens to do four other things you were afraid to touch. The name should say what the operation does, LookupOrderWithLineItems, not a vague ProcessEverything, because the name is how another developer finds and trusts it.

The monolithic alternative is the trap, and it is the first one the requirement calls out. One massive IP that extracts data, calls three external systems, writes five objects, formats a document, and sends an email is hard to test, because its inputs and outputs are entangled across every step. It is hard to maintain, because a change to any one responsibility risks the others. And it is hard to reuse, because no caller wants all of it, so each caller either over-requests or you build workarounds. The best practice is the opposite: split responsibilities into focused procedures, each owning one logical operation, and let them call one another when an operation genuinely needs several phases. [^1]

### Consistent contracts: the IP as a dependable building block

A focused IP is only useful if the things around it can rely on its shape. That is the second habit, and it comes straight from the design principle you met in the Response Action lesson: the shape of what an IP accepts and returns is a contract, and a contract only works if it is stable. [^2] Best-practice IPs keep consistent input and output JSON contracts, and they design the error branch into that contract so a failure comes back in a shape callers already know how to parse. [^1][^2]

Unpack input first. Every caller that invokes the IP, whether an OmniScript, a FlexCard data source, or another IP, passes a defined JSON structure. When that structure is documented and stable, callers are built once against it and keep working. When it drifts, every caller that referenced the old node names breaks, often silently. The discipline is to decide the input contract up front, name the nodes clearly, and treat a change to that contract as a change that ripples to every consumer.

Output is where the contract really earns its keep, and the reason is the error branch. A best-practice IP does not return a tidy object on success and a raw exception dump on failure. It returns a consistent structure on both routes, with the same wrapper carrying either the result or an error node that holds a code and a readable message. [^3] That consistency is what makes the IP a dependable building block: a FlexCard or OmniScript binds to one response shape, and it handles both outcomes with the same logic instead of special-casing an unstructured failure. You saw the mechanics in the Response Action and exception handling lessons. What IP-8 adds is the judgment that this consistency is a best practice you apply to every IP you build, not an option you reach for on the hard ones. [^2][^3]

The Response Action is the enforcement point for the output contract, because it is the action that decides exactly what leaves the procedure. [^2] Trimming the response to only what the caller needs is itself listed as a best practice, and it pairs with the consistency rule: map the success fields deliberately, map the error branch in the same shape, and let the Response Action ship a clean, predictable payload. [^1][^2] An IP with a stable contract behaves like a library function. Callers trust it, reuse it, and stop re-implementing its work themselves.

### Error handling everywhere: no silent failures

A focused IP with a good contract is still only as trustworthy as its failure behavior, and that is the third habit. Best-practice IPs handle errors at every external boundary, with no silent failures. [^1] You configured the mechanism in the exception handling lesson, Try/Catch blocks, controlled errors, Failure Conditional Formulas, and Failure Responses. What IP-8 contributes is the across-the-procedure stance: error handling is not a single Try/Catch you add at the end. It is a decision you make for every step that can fail, which in practice means every external call, every data operation, every step whose output a later step depends on. [^1]

The rule against silent failures is the sharpest part of this habit. A step that fails and passes nothing onward does not make the problem disappear. It makes the next step operate on empty or missing data, which produces a confusing downstream error or, worse, a plausible-looking but wrong result. The best practice is to make failure visible and structured: catch it where it happens, decide what the rest of the procedure should do, and surface a controlled error with a code and a message in the response contract. [^3] A caller should never have to guess whether a step worked. The response should tell it, on both the success and the failure route, in a shape it can act on. [^3]

The trap that pairs with this habit is inconsistent error handling across IPs. One procedure returns a structured error with a code and message; another returns a bare "Error" string; a third fails silently. A team that depends on all three cannot write one handler, because each procedure speaks a different failure dialect. Best practice standardizes the dialect: the same error structure, the same kinds of codes and messages, the same habit of never swallowing a failure, across every IP in the integration layer. [^3] Consistency in errors is the same argument as consistency in success shapes, applied to the failure path.

### Cache judiciously: store what is stable, cheaply

The fourth habit is restraint. Caching is a performance tool, and best practices tell you to use it to store frequently accessed, infrequently updated data. [^1][^4] You configured the mechanics, Org Cache versus Session Cache, Time To Live, whole-procedure caching versus Cache Blocks, in the caching lesson. What IP-8 adds is the judgment about when caching is worth it at all.

The two adjectives in the official guidance are the test: frequently accessed and infrequently updated. [^1][^4] A product catalog that a thousand users request each day and that changes weekly clears both bars, so it is a strong cache candidate. A user's private session data changes with the user, so it belongs in Session Cache or nowhere. A value that changes every read is disqualified outright, because a cached copy is wrong the instant it is stored. The corollary that trips people up is that caching is not free. Every cached entry consumes platform cache capacity that other features share, and every cached value carries the risk of serving stale data if its Time To Live outlives the source's relevance. [^4]

The best practice is therefore a deliberate choice, not a default. Cache stable, shared reference data with a Time To Live that matches how often the source changes, invalidate the cache when the source updates, and keep user-specific and sensitive data out of the shared org cache. [^1][^4] When the guidance is unclear, the safe default is no cache at all, because an IP that re-fetches is slower but correct, while an IP that serves a stale cached value is fast and wrong. [^4]

### Chain when long: split the work, keep short calls synchronous

The fifth habit is about matching the execution model to the length of the work. The settings for long-running Integration Procedures exist to avoid hitting Salesforce governor limits, and the best practice is to use them exactly when a process is long-running and would exceed what a single synchronous transaction can carry. [^1][^5] Chainable, Queueable Chainable, and Chain On Step, which you configured in the chaining lesson, split a long procedure across multiple transactions, each with its own fresh governor budget. [^5]

The judgment here is the part the exam tests, and it is the substance of quiz question three. Chaining is not a default and it is not always right. It is the correct choice when the process is long-running and exceeds synchronous limits. [^5] Breaking execution into chunks and saving interim results can reduce performance, the docs warn, so you chain when you must, not when you can. [^5] A short orchestration, a quick lookup that returns in a handful of queries, a simple transform, none of those need chaining, and adding it is complexity and latency you do not need. The best practice keeps short orchestrations synchronous, where they run in one transaction with one rollback and the simplest possible behavior, and reserves chaining for the long-running processes that genuinely cannot fit in one transaction. [^5]

There is a design consequence that should shape how you plan long procedures. When you split work across transactions, each link commits independently, so there is no shared rollback across links. [^5] A failure in link three does not undo link one. That is exactly why the chaining lesson paired with per-link error handling: each link needs its own failure path, and each link should be idempotent where possible so re-running it does not duplicate work. [^5] The best practice for long procedures is not just to enable chaining. It is to design the procedure so that its links are independently safe, because the transaction boundary that saves you from governor limits also removes the safety net of a single rollback. [^3][^5]

### Reuse Data Mappers: single-source your data logic

The sixth habit is where reusable data logic lives, and it answers quiz question two outright. Best-practice IPs reuse Data Mappers instead of duplicating data logic inline, because an IP usually calls one or more Data Mappers, and those Data Mappers are the single source of truth for reading and writing SObject data. [^1][^6]

The architecture rule is worth stating clearly. Data Mappers read or write Salesforce SObject data or perform single-step data structure transformations. [^6] Integration Procedures orchestrate: they call Data Mappers, hit REST endpoints, invoke Apex, apply flow control, and assemble the result. [^6] So the natural division of labor is that the Data Mapper owns the data operation, the extract that pulls records, the load that writes them, the transform that reshapes a structure, and the IP owns the orchestration that decides when and in what order those operations run. [^6]

The anti-pattern the requirement warns about is duplicating data logic inline in every IP. If an IP builds its own account-extraction logic, and a second IP re-implements the same extraction a slightly different way, and a third pastes a third variant, then the org now has three sources of truth for "how we look up an account." When the account lookup changes, the developer must find and fix all three, and the one they miss becomes the bug that only surfaces in production. [^6]

The best practice keeps that logic in one Data Mapper and has every IP that needs it call that Data Mapper. [^1][^6] Reuse is not just less typing. It is single-sourcing: one definition of the data operation, one place to fix it, one behavior every caller shares. The IP best practices doc pushes exactly this when it says to use IPs for all data calls to Salesforce and to keep IPs modular for reuse. [^1] The Data Mapper is the reusable data module; the IP is the thin orchestrator that assembles modules into an operation. [^6] If you find yourself writing the same data logic inside two different IPs, the best practice says stop, extract it into a Data Mapper both procedures can call, and delete the inline duplicates. [^1][^6]

### Test before you promote: verify each action's input and output

The seventh habit is the gate that keeps the other six honest. Best-practice IPs are tested with the IP test tool and the Debug Console, verifying each action's input and output before the procedure is promoted to production. [^1][^7] You have a built-in way to do this in every IP: the Preview, where you supply sample input, run the procedure, and watch the JSON build action by action, and the Action Debugger, which opens a debug console showing the request and response data of each step. [^7]

The reason testing is a best practice and not a nice-to-have is the specific failure it prevents: action ordering bugs that slip through when you never look at what each step actually produced. [^7] An IP can look correct in the designer and still fail because a step consumed a node that a previous step never produced, because a transform dropped a field a later step expected, or because the response shipped a shape no caller can bind to. [^7] You only catch those by running the procedure with real sample input and reading what each action put into and took out of the JSON.

The discipline is to test each action, not just the final result. When you run an IP in the Preview and open the Action Debugger, you can inspect every step's input and output, confirm each produced what the next one expects, and catch a bad field reference or a dropped node at the step where it happened rather than as a confusing final failure. [^7] This is the "test before you wire consumers" instinct from the Response Action lesson, applied across the whole procedure. Run it on the success path, run it on the failure path, confirm both behave as designed, and only then activate the version and let OmniScripts, FlexCards, and APIs depend on it. [^2][^7]

## Configuration Walkthrough

None of these practices live in a single property. They are a design discipline you apply while you build, and a review checklist you run before you activate. Walk through the sequence on a concrete example: an IP that looks up an order and its line items, resolves each line's product through a shared lookup, and returns a tidy summary to a FlexCard.

1. **Scope the procedure to one logical operation and name it.** Decide what the IP owns before you add anything. This IP owns "lookup an order and summarize its line items," so name it `GetOrderSummary`, not `ProcessOrderStuff`. [^1] Resist the urge to fold in the email that gets sent after the order is confirmed or the write that updates the order status; those belong in separate focused procedures that a caller can invoke when it actually needs them. [^1]

2. **Define the input and output contracts up front.** Write down what the IP receives, an order Id, and what it returns, the order header plus an array of line items, each with its product name and unit price. [^1][^2] Decide the error branch now too: when the order is not found or a line cannot resolve, the IP returns the same wrapper with an outcome flag, a code, and a message. [^3] Naming these contracts before you build means every action and every downstream caller agrees on the shape from the start.

3. **Reuse a Data Mapper for the data operation.** The order and its line items come out of Salesforce, so add a Data Mapper Extract Action that pulls the order with its related line items in one call. [^6] If a second procedure also needs to resolve products, and it likely does, that product resolution is a separate Data Mapper you reuse, so both procedures share one source of truth for "how we look up a product" instead of each implementing it. [^1][^6]

4. **Add error handling around every external boundary.** The extract can find no order. The product resolution can find no match. Each of those is a controlled failure, so route them through error handling that produces a structured error with a code and a message, and use Failure Conditional Formulas where a "no records" result is not a native error but should still fail the step. [^3] The goal is no silent failures: every step that can go wrong has a defined, visible failure path that feeds the consistent error contract. [^1][^3]

5. **Cache the stable reference data, not the request.** If the product resolution hits a catalog that changes rarely and is shared across users, that is a legitimate cache candidate, so give it a cache treatment with a sensible Time To Live. [^1][^4] The order data itself is per-request and should not be cached as if it were shared reference data. Caching here is judicious, applied to what is stable and shared, not blanket-applied to everything. [^4]

6. **Decide synchronous versus chainable by the length of the work.** This lookup is short, a handful of queries, so it stays synchronous, in one transaction with one rollback and the simplest possible behavior. [^5] It does not need chaining. Reserve that for the long-running process, such as a batch that resolves and writes thousands of line items, where a single transaction would cross governor limits. [^5]

7. **Test each action in the Preview and Debug Console before activating.** Run the IP with a valid order Id and inspect, via the Action Debugger, each action's input and output to confirm the extract returned the fields the transform expected and the response shipped exactly the nodes the FlexCard binds to. [^7] Then run it with an order Id that matches nothing and confirm the error branch returns your structured shape. [^7] Only when both paths behave as designed do you activate the version and wire the FlexCard data source to it, because the contract is now locked and verified. [^2][^7]

## Exam Traps

- **Monolithic IPs that do everything.** One massive IP that extracts, calls external systems, writes objects, formats documents, and sends email is hard to test, hard to maintain, and hard to reuse, and it is the first anti-pattern the requirement names. [^1] Best practices favor focused, well-named IPs that own one logical operation. When a question offers "one massive IP for everything" as a design, it is testing that you reject it. [^1]

- **Inconsistent error handling across IPs.** If some IPs return a structured error with a code and message and others return bare strings or fail silently, no caller can write one reliable handler. [^3] The best practice is a consistent error dialect across the integration layer, with no silent failures anywhere. [^3]

- **No testing before production.** An IP activated without running its actions against sample input lets action ordering bugs, a step consuming a node a previous step never produced, or a response shape no caller can bind to slip straight into production. [^7] Testing each action's input and output with the Preview and Action Debugger before you promote is the gate that catches these, and skipping it is a trap the requirement exists to prevent. [^7]

- **Duplicating data logic inline.** Re-implementing the same extract or transform inside several IPs creates multiple sources of truth for one data operation, so a change to that operation requires finding and fixing every copy. [^6] The best practice is to keep data logic in a reusable Data Mapper that IPs call, which single-sources it. [^1][^6]

- **Chaining everything, or caching everything, by default.** Both chaining and caching are conditional tools, not defaults. Chaining splits work across transactions, which can reduce performance, so it belongs on long-running processes that exceed synchronous limits, and short orchestrations should stay synchronous. [^5] Caching serves frequently accessed, infrequently updated data, so volatile or user-specific data should not be cached, and a short procedure needs neither. [^1][^4]

## Exam Tip

Hold the five habits as your memory hook: focused, contracted, cached, chained, and tested. [^1][^7] Focused means one well-named logical operation per IP, because a monolithic IP is hard to test and maintain. [^1] Contracted means stable input and output JSON with the error branch built into that same shape, so every caller handles success and failure with one piece of logic. [^2][^3] Cached means store the frequently accessed, infrequently updated data and nothing else, with a Time To Live that matches how often the source changes. [^1][^4] Chained means split long-running processes that exceed synchronous limits, and keep short orchestrations synchronous. [^5] Tested means verify each action's input and output with the Preview and Debug Console before you promote anything, so ordering bugs and contract mismatches never reach production. [^7] Reuse Data Mappers for data logic so it stays single-sourced, keep errors consistent and never silent, and you have turned the entire Integration Procedures domain into the dependable building blocks a real integration layer is made of. [^1][^3][^6]

## Try It

Open the Integration Procedure Designer in a sandbox and audit an existing IP with the five habits. Find a procedure you have built in earlier lessons, or build a fresh `GetOrderSummary` IP. Ask it the best-practice questions in order. Is it scoped to one logical operation, or does it do several unrelated jobs? [^1] Does it have a defined input and output contract, and does the error branch return the same wrapper as success? [^2][^3] Does its reusable data logic live in a Data Mapper both this IP and others call, or is it duplicated inline? [^6] Does it cache only stable, shared reference data with a sane Time To Live? [^4] If it is long-running, is it designed to chain with per-link handling, and if it is short, does it stay synchronous? [^5] Then run it in the Preview with valid sample input, open the Action Debugger, and inspect each action's input and output to confirm nothing is dropped and the final response matches the contract. [^7] Run the failure case and confirm the error comes back in the same shape. That audit is the whole requirement in practice: looking at a procedure and judging, against the five habits, whether it was built to be reliable in production. [^1][^7]
