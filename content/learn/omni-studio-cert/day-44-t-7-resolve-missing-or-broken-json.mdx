A binding points at `account.Name` and the value that should show a customer name renders blank. An OmniScript action completes without an error and its field stays empty. A FlexCard loads clean and still shows nothing in the spot where one field should be. These three reports share a root cause, though it hides behind three different-looking symptoms: the data the component expects is either not valid JSON, so no parser can read a reliable value out of it, or it is not sitting where the component believes it is. [^1]

Requirement T-7 is about resolving missing or broken JSON. It sits in the Troubleshooting and Debugging domain and pairs naturally with Day 39 on OmniScript errors and Day 40 on Data Mapper output. It also sets up Day 46, which is the Debug Console lesson, because the habit you learn here, read the raw payload before you change anything, is exactly what the Debug Console is built to show you. [^2][^3]

The two words in the title are not the same problem, and naming them correctly is half the fix. Broken JSON is a malformed payload: syntax errors, unescaped characters, truncated responses. Missing JSON is an empty or absent value inside a payload that may otherwise be perfectly formed. Both strip data off a page, and both get filed as "the component is broken." Neither usually is. [^1] This lesson gives you the diagnostic sequence that tells them apart, starting with the raw JSON and ending with the path that is actually wrong.

## Deep Dive

### Broken JSON is a malformed payload

Broken JSON is a payload that no longer conforms to the JSON grammar. [^1] Any parser that tries to read it stops, and the most common forms in OmniStudio work are a syntax error, an unescaped special character, and a truncated response. Between them they eat values the same way: the parser cannot find the value the component asked for, because it cannot trust the structure around it. [^1][^2]

A syntax error is the simplest case. A comma is missing between two fields, a closing brace is doubled, a colon is typed as a semicolon. The payload might be readable by a human who knows what was intended, but a computer cannot resolve a value out of a structure it cannot parse, and OmniStudio components resolve values out of the structure. [^1][^4]

An unescaped character is the sneaky case, because the payload often still looks valid at a quick glance. JSON strings wrap values in double quotes. Any double quote inside the value has to be escaped as `\"`, and control characters like a newline have to be escaped as `\n`. When a service sends a name like `O'Brien` back raw, or a multi-line address with a literal line break, and nothing escapes those characters, the string ends early. Everything after that point is either a syntax error or, worse, valid JSON that just means something different from what the component expected. [^1]

A truncated response is the third form. The service started to answer and then stopped. The payload cuts off mid-object, missing its closing braces, or it is not valid JSON at all because the response was clipped. This happens when an external callout times out, when a response body is larger than a limit and gets cut, or when a server error returns a body that is not JSON but the component is still handed it. [^1][^2]

All three have the same tell. The log, the Debug Console, the Action Debugger, whichever one recorded the exchange, holds the raw payload, and the payload fails when you try to parse it. [^2][^3] That is the defining move for "broken": you validate the raw JSON and it does not parse. Until you know that, you are guessing.

### Missing JSON is an empty or absent value

Missing JSON is the other family, and it is more common in practice. The payload is valid. It parses cleanly. But the value the component expects is not there, which produces the same blank field the malformed case produces. [^1] Three reasons account for nearly all of it: the data source returned nothing, the field path is wrong, or an action did not produce the output it was supposed to.

A data source returning nothing is the honest failure. A SOQL query finds no rows for the context it was passed, an HTTP callout returns an empty body, a Data Mapper Extract maps nothing because its input parameters were empty. [^4] The JSON is well formed, it is just `[]` or an object with no usable members, and the component finds no value because there is none. This is the case where fixing the data source, not the component, is the right move.

A wrong field path looks identical to a missing value, and this is the one that sends people down the wrong road. The data is there, the data source worked, but the path the component uses to reach the value does not match the actual keys in the payload. A binding that reads `customer.Address.City` when the payload nests the city under `data.customer.address` finds nothing, not because the data is absent but because the path is wrong. [^4][^7] The value being missing from the rendered page and the value being absent from the JSON are two different facts, and only one of them means the data is gone.

An action that did not produce expected output is the third reason, and it is the one the exam leans on. A Data Mapper action runs without raising an error and still writes nothing to the output key a later element reads. [^1] The merge field comes back empty even though the action session looks clean. The output was never written, usually because the mapping for that output key pointed at a source that had no value, or because the output key itself got overwritten elsewhere (below). The component is fine. The JSON it was given simply lacks the value.

### Path typos are the number one cause of missing values

Of the three missing-value causes, the wrong path is the one people hit most and the one most likely to be on your exam. [^1][^7] A path has to match the JSON key exactly: the case, the nesting, and the repeater context all have to line up. JSON keys are case-sensitive, and Salesforce JSON output keys are frequently not what you assume. A field stored as `Account_Name` in a mapper output is not reachable through `account.Name`, no matter how close it looks. [^1][^7]

Three kinds of mismatch cover most of it. Case is the first, `name` versus `Name`. Nesting is the second, a path that skips a level or adds one the payload does not have. Repeater context is the third, and it is the tricky one. When data comes back as an array, each element is a particular item, and a path has to point at the array and then at the element the field lives on, not at a field that only exists on individual items as if it were a top-level key. [^4][^7]

The exam distinguishes a path mismatch from a broken data source cleanly: one element references `account.Name`, the JSON key is `Account_Name`, and the question asks what is wrong. The data source is fine. The key is simply a different string. [^1] The disciplined habit is to read the keys as they really are, not as you think they are, and to copy them rather than retype them. The Data Mapper type-ahead guidance gives the exact technique: take the key from the Response node in the Action Debugger so you can never type it wrong. [^7]

### Duplicate keys overwrite values silently

Some levels only allow you to have a bit of text in your output. When two elements in an OmniScript produce the same JSON node, or a Data Mapper writes the same output key twice, the JSON object cannot hold both. [^1] JSON objects are key to value maps, and a map can only store one value per key. The standard parser behavior is to keep the last value it saw for a duplicate key and let the earlier one go, with no error and no warning. [^1]

This is the quietest destroyer of data in the whole requirement, because nothing prints an error. A mapper that writes `CustomerId` in one step and then writes `CustomerId` again later with a value you did not want simply replaces the first. An element named the same as an output key from an earlier action does the same thing. The component reads the surviving value, which is the one from lower in the order, and the data you expected to win has been silently dropped. [^1][^4]

The diagnosis is to look for the duplicate, not to hunt for an error. When a field is blank or holds the wrong value and the source data is fine and the path is exact, ask whether another key with the same name is overwriting it. The Action Debugger shows the request and response for each action, and scanning the emitted keys for repeats is faster than any other check. [^2][^7]

### Escaping and encoding break payloads before they reach the parser

Escaping is the bridge between the broken and missing families, because it decides whether a payload parses at all. [^1] The raw data a mapper or a callout produces is full of characters that are legal in a plain string and illegal inside a JSON string unless they are escaped: double quotes, backslashes, newlines, tabs. Data that flows out of Salesforce through a transform, then through a callout, then back, is exactly the path where escaping errors creep in, because each hop can reformat the value. [^1][^4]

A quoted value that is not escaped splits its JSON string and turns a valid payload into a broken one. A newline that is passed through literally instead of as `\n` does the same. And an encoding shift, a value that comes back in one character set and is placed into a payload the component parses as another, turns recognizable text into mojibake or, worse, into characters the parser treats as structure. [^1]

The check is to follow how the value flows rather than to fix what you can see on the page. When data passes through a transform and then a callout, escaping can be added, dropped, or doubled at each stage, and the payload is the only place all of it is visible. [^1][^4] Validate the raw JSON, and if it fails at a value that contains a quote or a line break, the escaping is the story.

### The diagnostic habit: capture, validate, then trace

Everything above collapses into one sequence, and it is the sequence the config walkthrough runs step by step. [^2][^3] Open the Debug Console, or its FlexCard and OmniScript equivalents, the Data JSON panel and the Action Debugger, and copy the raw JSON payload exactly as it arrived. Then validate it, which means actually parsing it, so that syntax errors and escaping failures surface immediately. Only after the payload parses do you trace each referenced path against the real keys, one at a time, checking case, nesting, and repeater context. [^7] Then you look for duplicates and escaping issues in the values you are about to trust. That order separates "the data is broken" from "the data is fine, the path is wrong," and it is the whole of T-7 in four moves.

## Configuration Walkthrough

Walk a real report end to end, in order. A FlexCard shows a claim number that should come from a data source, and the claim-number field is blank. [^2]

1. **Open the Debug Console and copy the raw JSON payload.** Open the FlexCard preview and let the card render, then open the Debug pane. The Data JSON tab shows how the data source populated the elements, and the Action Debugger shows the request and response for the action that fetched the claim. [^2][^3] Copy the response body exactly, do not reformat it first. You want the raw payload, because formatting or retyping it can hide the very problem you are looking for. [^2]
2. **Validate it, parse it.** Paste the raw payload into a JSON validator and run it. [^1][^2] If it fails with a syntax error, a missing comma, a stray character, or an unclosed string, you have broken JSON and the blank field is explained. Look at the failing line, decide whether it is a syntax slip, an unescaped quote or newline, or a truncated response, and fix the source that produced the bad payload. [^1]
3. **Trace each referenced path against the actual keys.** If the payload parses, the data is structurally sound and you move to paths. Read the keys as they are in the payload, not as you remember them. [^7] For the binding that reads the claim number, confirm the exact key: its case, its nesting level, and whether it sits inside an array that needs repeater context. Copy the key from the Response node of the Action Debugger so you are working from the real string. [^2][^7]
4. **Check for duplicates and escaping issues.** With the paths confirmed, scan the emitted keys for repeats that could silently overwrite a value. [^1] Then look at the string values you are about to display, especially any that contain quotes or line breaks, and confirm they are escaped for the payload that carries them. [^1]

Worked example: a claims review card reads a policy-holder name from a SOQL-backed source and renders the field blank, with no error. [^2] Step 1, the Data JSON panel shows the response arrived and the source returned rows, so the data source is not the question. Step 2, you paste the payload into a validator and it parses clean, which rules out broken JSON. Step 3 is the reveal: the binding reads `PolicyHolder.Name` but the payload key, confirmed in the Response node, is `policyholder_name`. The data is present and valid, and the path simply does not match it. You correct the binding to the real key, copy the value from the actual JSON, and re-run. The field populates. You never reopened the card's layout, because it was never the problem. [^1][^7]

## Exam Traps

- **Fixing the UI when the JSON payload is malformed.** When the log shows a malformed payload and a field is blank, the instinct is to open the component and look for a layout bug. [^1] The payload cannot be fixed in the UI, and the UI was never broken. Validate the raw JSON first, and fix the source that emitted the malformed payload. [^1][^2]
- **Guessing paths instead of reading the actual keys.** The most common way to get a blank field is to type a path you assume is correct. [^7] JSON keys are case-sensitive and usually not what you would guess. Read the keys from the Response node and copy them, never retype them by memory. [^7]
- **Ignoring escaping.** Values carrying quotes or line breaks break payloads when nothing escapes them. [^1] If a value round-trips through a transform and a callout and the payload stops parsing, the escaping at each hop is the suspect, not the component. [^1][^4]

## Exam Tip

Hold T-7 in one sentence: broken means the payload is malformed, missing means the value is absent or the path is wrong, and you tell them apart by reading the raw JSON. [^1] Capture the raw payload in the Debug Console, validate it so syntax and escaping failures surface, then trace each referenced path against the real keys, checking case, nesting, and repeater context. [^2][^3][^7] Path typos are the most common cause of a missing value. [^7] Duplicate keys overwrite values silently, so scan for repeats before you trust an output. [^1] Fix the source of the broken payload or the path that does not match, not the component, and the exam's malformed, mismatched, and duplicate scenarios all resolve to the same habit.

## Try It

Reproduce each failure on purpose in a sandbox so you recognize it with the clock running. [^1][^2]

First, break a payload on purpose. Point a FlexCard at a Data Mapper output that writes a value with an unescaped quote, and watch the field render blank while the log shows the raw payload. [^3] Run the exact JSON through an online validator and confirm it fails, then fix the escaping and confirm the field returns. That is broken JSON, seen and fixed. [^1]

Second, create a path mismatch. Keep the data working, then deliberately change a key in the binding to the wrong case, `name` instead of `Name`, and confirm the field drops out even though the payload parses cleanly. [^7] Copy the real key back from the Response node, confirm it returns, and you have internalized that paths must match exactly. [^7]

Third, force a duplicate. Have a mapper emit the same output key twice with different values, and confirm the later value survives and the earlier one silently disappears with no error. [^1] That is the duplicate-key overwrite, and once you have reproduced it you will scan for it in every blank-output investigation. After those three, missing and broken JSON are things you can name from the first look at a payload. [^1]
