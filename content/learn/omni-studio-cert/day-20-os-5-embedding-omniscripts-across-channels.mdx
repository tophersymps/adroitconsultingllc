A well-built OmniScript is an asset, and like any asset its value depends on where it can be used. The requirement here is short, embed OmniScripts across UI components and different channels, but the scenarios behind it are where implementations go wrong: a flow that opens blank because nobody passed the record context, a portal promise made before anyone checked licensing, a desktop layout that collapses on a phone. The exam tests three specific facts and a cluster of constraints around them. Know the surfaces, know how context travels, and know what each channel asks of you.

## Deep Dive

### One definition, many surfaces

The core idea is that a single OmniScript definition can be placed on several different surfaces without being rebuilt for each one. The script you tested in the designer is the same script a support agent launches from a record page, the same script a customer launches from a portal, and the same script that appears inside a mobile experience. You are not maintaining four scripts. You are placing one in four contexts.

The surfaces the exam names are Lightning pages built in App Builder, Experience Cloud sites, mobile, and external or standalone web contexts. A question that asks where an OmniScript can be embedded is looking for that list as a group, and every distractor that restricts it is wrong. OmniScripts are not confined to being embedded inside other OmniScripts. They are not limited to Aura applications. They are not desktop-only. The list is broad precisely because the script is a self-contained definition rather than a page-specific artifact.

![One OmniScript definition placed on four surfaces: a Lightning page, an Experience Cloud site, the mobile app, and external web, each with its own setup step and constraint](</diagrams/day-20-os-5-embedding-omniscripts-across-channels/1-one-definition-many-surfaces.png>)

The value of the "one definition, many surfaces" property is not aesthetic. It means a defect fixed in the script is fixed everywhere it appears, and a change in business rules rolls out to every channel at once. It also means the design decisions you make for one surface become constraints for the others, which is where the rest of this lesson lives.

### Context is what makes the embedding useful

Dropping a script onto a page produces a working, empty flow. In almost every real case, that is not what you want. An agent clicking "File a claim" on an account record expects the flow to already know which account it is working with. A customer opening a cancellation flow from their own account should not have to type their own customer number.

Context is how that happens. You pass values into the script when it is launched, and the script reads them as data it already has. The most quoted example is `recordId`: the identifier of the record the host page is showing. With `recordId` in hand, the script can run an Extract on entry and pre-fill the applicant's details, the account balance, the policy details, or whatever else the process needs. Without it, the script has no idea which record the user was looking at and has to ask.

The mechanisms that carry context differ by surface. On a Lightning record page, the wrapper component reads the current record's identifier from the page and hands it to the script as an input. In an Experience Cloud or external web context, context can arrive through URL parameters along with a script's published attributes. The design discipline that matters is the same in all of them: decide deliberately which values the script accepts from outside, declare them so the host can set them, and never rely on the script somehow inferring the record. When an OmniScript opens blank for the selected record, the diagnosis is almost always that the context was not passed, not that the script is broken.

![How record context travels: the host record page passes its identifier through the LWC wrapper into the OmniScript, which extracts on entry and opens pre-populated](</diagrams/day-20-os-5-embedding-omniscripts-across-channels/2-context-travels-into-script.png>)

There is a second-order benefit to parameterized context. A script that takes its context as input is a script that can be reused on any page that can supply it. A script that hardcodes the record it works with is a script you have to edit every time you place it somewhere new, which is the definition of duplication.

### LWC wrappers make embedding a drag-and-drop operation

The reason an OmniScript can be dropped onto an App Builder page at all is that it generates a Lightning Web Component wrapper. That wrapper is a real component in the org, it appears in the component palette of App Builder and Experience Builder, and an admin can drag it onto a page, pick which OmniScript it should run, and set the context attributes it passes in.

This is the mechanism behind the exam question about what makes embedding drag-and-drop on App Builder pages possible. The answer is the auto-generated LWC wrappers. The distractors are all things that exist in Salesforce but do not do this job: an Apex class is not draggable onto a Lightning page, manual HTML is not how Lightning pages are composed, and a Flow is a different automation tool entirely.

The practical consequence is that deployment includes the wrapper. If the wrapper component is not present in the target org or not available in the builder, the script exists and cannot be placed. It also means that when the script's expected inputs change, the pages that embed it may need their attribute mappings revisited. A wrapper that is passing `recordId` into a script that no longer accepts it is a page that looks fine and behaves strangely.

### Channel-specific constraints

Each surface adds a specific setup step and a specific constraint. The exam frames them as traps, and they are worth knowing as a list.

![Comparison of the four embedding surfaces by setup step and constraint, with the Experience Cloud license and the mobile layout as the named traps](</diagrams/day-20-os-5-embedding-omniscripts-across-channels/3-channel-constraints.png>)

**Lightning pages through App Builder.** The friendliest surface. Drop the wrapper, choose the script, map the record identifier, save and activate. No licensing question arises because the user is already an authenticated internal user, and the record context is readily available from the page.

**Experience Cloud sites.** Embedding an OmniScript on a portal or site requires the right licensing to be in place before anything renders. This is the trap the exam names explicitly: promising a portal without the Experience Cloud license. The order of operations matters too, since the site has to be configured to expose the OmniScript wrapper before the component is available to place on an Experience Builder page. Skip the licensing and configuration and the script simply never renders for portal users, which tends to be discovered late in a project.

**Mobile.** The same definition renders on the Salesforce mobile app, but only well if the steps were laid out with responsive behavior in mind. Fixed-width layouts that look crisp on a monitor break at phone widths. Touch targets that are comfortable with a mouse cursor are cramped with a thumb. Verify the flow on a narrow screen rather than assuming the desktop layout carries over.

**External and standalone web contexts.** When the script is embedded in a web context outside the Salesforce UI, it runs inside a session that has to carry the right context in. Authentication and record context both have to arrive with the launch, so the script knows who the user is and which record is in scope. Without that, an embedded script cannot resolve the user or the record and has nothing to work with.

**Reuse-first design closes the loop.** A script written with parameterized context and responsive steps embeds anywhere with no duplication. Every constraint in the list above is easier to satisfy at build time than at deployment time. If, while building, you find yourself asking whether the layout will survive a phone or whether the record identifier will be available at the launch point, that question is cheaper to answer then than in the channel that discovers it.

### A worked example: one script, three surfaces

Consider a service cancellation process.

On the internal Lightning record page for a customer account, an agent clicks a component that runs the cancellation script. The wrapper is placed on the account page and passes the account's `recordId`, so the script loads the account and its active subscriptions on entry and the agent starts on a populated screen.

On the customer portal, the same script appears on an authenticated page in the Experience Cloud site. The site is licensed appropriately and configured to expose the wrapper before anyone builds the page. Context arrives from the page, so the customer sees their own subscriptions and never types an account number.

In the mobile experience, an agent uses the same script from a phone while on a customer visit. The steps were designed with fluid layouts and reasonably large controls, so the narrow screen remains usable, and the record context travels the same way it does on desktop.

One script definition, three surfaces, one place to change the cancellation rules. The differences between the three are setup and constraints rather than content, which is exactly the point the requirement is making.

## Configuration Walkthrough

1. **Design the script to accept context parameters.** In the script's properties, define the input parameters the script will accept from a host page, such as `recordId` and any values the process needs. Treat these as the script's public interface and keep the list small and deliberate.
2. **Pre-populate from context on entry.** Add the Extract or Set Values actions that use the context to fill the script before the user reaches the first input, so the flow opens with real data instead of empty fields.
3. **Embed via the LWC wrapper on a Lightning page.** In App Builder, drag the OmniScript wrapper component onto the page, select the script, and map the host page values into the wrapper's attributes so they arrive as the script's context. Activate and test on a real record.
4. **Verify context actually arrives.** Open the embedded script from a record and confirm the pre-populated values are the right record's values. A script that opens with stale or empty data is a mapping problem, not a script problem.
5. **Embed on Experience Cloud or mobile as required.** For a site, confirm the licensing and site configuration that exposes the wrapper before you build the page. For mobile, place the same definition and check the layout at a narrow width.
6. **Handle external web auth context.** Where the script runs outside the Salesforce UI, ensure authentication and record context travel in with the launch so the script can resolve the user and the record.
7. **Verify context per channel.** Repeat the check from step four on every surface. Context that works on a Lightning page does not automatically work the same way in a portal or an external embed, because the source of the context is different.

## Exam Traps

- **Embedding without passing record context.** The flow opens empty, and users conclude the feature is broken. Pass the identifier in and let the script pre-fill.
- **Promising a portal without the Experience Cloud license.** Licensing is a prerequisite, not a detail. Without it the script never renders for portal users no matter how correctly it is built.
- **Designing desktop-only layouts that break on mobile.** The same definition renders on a phone, which means a fixed-width desktop layout will be used on a phone.
- **Assuming context is automatic across channels.** Each surface supplies context from a different place. Verify per channel rather than testing once on Lightning and shipping everywhere.
- **Hardcoding values instead of parameterizing context.** A hardcoded record reference makes the script single-use and forces duplication for the next placement.
- **Forgetting the wrapper in the deployment.** The script and its wrapper component both have to exist in the target org before an admin can drag the component onto a page.

## Exam Tip

Parameterize context, embed via the LWC wrapper, verify per channel. One script, many surfaces. If a question asks where OmniScripts can be embedded, the answer is the broad list: Lightning pages, Experience Cloud, mobile, and web. If it asks what makes a script open pre-populated for a selected record, the answer is context passed in, with `recordId` as the canonical example. If it asks what makes drag-and-drop embedding possible in App Builder, the answer is the auto-generated LWC wrappers.

## Try It

In a sandbox, take a script that already extracts data and embed it on an account record page.

First, declare the context parameter the script needs and add an Extract action that uses it on the first step. Then open the page in App Builder, drag the OmniScript wrapper component onto the layout, select your script, and map the page's record identifier into the wrapper's attribute. Save, activate, and open a specific account record. If the first step arrives pre-populated with that account's data, the context path works end to end.

Now break it deliberately. Clear the wrapper's attribute mapping and reload the record page. Note exactly what an embedded script looks like when it receives no context. That blank, unhelpful screen is the single most common embedding failure in production, and recognizing it on sight saves hours.

Finally, switch your preview to a narrow, phone-sized viewport and walk the flow at that width. Whatever looks wrong there is the work required before the same script can be promised on a mobile channel. If your sandbox includes a site, repeat the placement on an Experience Builder page and confirm that everything the site needs, licensing and configuration included, is in place before the component becomes available.
