# Licensing, Permission Set Licenses & Permission Sets

**Exam guide requirement:** Explain OmniStudio license requirements, Permission Set licenses and Permission Sets.

**Domain:** OmniStudio Fundamentals (18%)

## Deep Dive

- OmniStudio is an add-on feature license on top of the base Salesforce license. The org must hold it to use the tools at all. No license, no components, regardless of profile.
- Permission Set Licenses (PSLs) enable the OmniStudio feature set for users. Without the PSL assigned, a user cannot access the feature even with a permission set that references it.
- Permission Sets then grant granular access: builder/admin permission sets (create, edit, publish components, open the OmniStudio admin tools) vs user-level permission sets (run components, see data).
- The layering matters for troubleshooting: License (org-level) → PSL (feature enabled for user) → Permission Set (what they can do) → object CRUD/FLS (what data they see). Failure at any layer blocks the component.
- End users typically need only run-time access via profile/permission set; only builders need the admin tooling. 'Works for admin, not for the user' usually means a PSL/permission-set gap, not a component bug.

## Configuration Walkthrough

1. Verify org has the OmniStudio license (Setup → Installed Packages / feature licenses).
2. Assign the OmniStudio PSL to users who need the feature.
3. Assign permission sets: admin/builder for developers, run-time for end users.
4. When access fails, walk the chain: license → PSL → permission set → CRUD/FLS.

## Exam Traps

- **Trap:** Assuming a System Administrator profile alone grants OmniStudio access. License + PSL are still required.
- **Trap:** Confusing PSL (enables feature) with Permission Set (granular grants).
- **Trap:** Diagnosing 'can't see data' as a component bug when it's a permission-layer issue.

## Exam Tip

Access chain: License → PSL → Permission Set → CRUD/FLS. Diagnose from the top down.
