## Deep Dive

**Validate the JSON before you build anything.** Most FlexCard defects trace back to a data source that has the wrong shape or is missing fields. Check the source output first. If the shape is wrong, the card fights you the whole way through.

**Keep data sources lean.** Use filters and parameters to limit records. Avoid N+1-style heavy queries that hammer the server. Push complex logic to a Data Mapper or Integration Procedure instead of trying to do it in the card. The card should render, not compute.

**Cache with intent.** Caching is for expensive data that does not change often. For multi-source orchestration, prefer an Integration Procedure that returns one consolidated call over piling several data sources onto the card. Fewer round trips, easier to reason about.

**Respect security.** Use Data Mapper data sources when field-level security matters. Do not expose sensitive fields through SOQL on a low-privilege channel. FLS is easy to bypass by accident with raw queries, so choose the data source deliberately.

**Test every state on every channel.** Default, empty, error, custom. A card that only works when data is perfect will go blank on edge cases. Name elements and bindings consistently so the card stays maintainable when you come back to it.

**Compose, don't duplicate.** If multiple cards share a piece of UI, use a child FlexCard or a custom LWC rather than copying the layout. Use actions and events for coordination. Duplication is where drift and bugs come from.

## Exam Traps

- A heavy SOQL query with no filter that returns thousands of records.
- No empty or error states, so cards go blank on edge data.
- Duplicating card logic instead of composing with child cards and LWCs.

## Practice Questions

**Q1.** Which is a documented FlexCard best practice?

A. Validate JSON, keep data sources lean, test all states<br/>
B. Return thousands of records unfiltered<br/>
C. Skip state testing<br/>
D. Hardcode all values

<details>
  <summary>Show answer</summary>
  **Correct: A.** Best practices: validated JSON, lean sources, caching, state and channel testing.
</details>

**Q2.** When does a Data Mapper data source beat SOQL in a FlexCard?

A. When field-level security or transformation is needed<br/>
B. Always. SOQL never works<br/>
C. Never<br/>
D. Only on mobile

<details>
  <summary>Show answer</summary>
  **Correct: A.** Data Mappers respect FLS and transform data. SOQL is simpler but insecure for restricted users.
</details>

**Q3.** How should complex multi-source data reach a FlexCard?

A. Via an Integration Procedure in one call<br/>
B. Multiple SOQL data sources<br/>
C. Custom JSON<br/>
D. A formula

<details>
  <summary>Show answer</summary>
  **Correct: A.** IPs consolidate orchestration into one server call. This is the recommended pattern for complex data.
</details>

## Exam Tip

Lean source + validated JSON + all states tested + FLS respected = a card that survives production.
