A single store cannot hold everything an agent eventually has to remember. Lesson 14 gave you the taxonomy: working memory in the context window, long-term stores for what survives the session, episodic memory for what happened, and semantic memory for what you know. What it did not answer is the storage question underneath. When an agent runs for months, talks to a thousand customers, or reasons across an entire codebase, where does that memory physically live, and how does the agent find the right sliver of it fast enough to answer the current question?

That storage layer is the subject of this lesson. You meet three ways to build it: vector memory, knowledge graphs, and hybrids that combine the two. Each is good at a different kind of recall, and the mistake most teams make is committing to one before they know the shape of the questions they are asking. I am going to keep one question running through the whole lesson: what is the agent really being asked to remember and retrieve? Broad and fuzzy, precise and relational, or both?

## Vector memory: the default for a reason

Vector memory is the closest thing the field has to a default. The idea is the one you already met in the embedding and RAG lessons. An embedding model maps text to a high-dimensional vector, and nearby vectors mean similar meaning. Store those vectors in a vector database and retrieval becomes a nearest-neighbor search: give me the memories most similar to this query. [^4]

This approach has real strengths, which is why so many teams reach for it first. [^4]

- It searches fast, even across very large collections. The reference material notes speed across billions of vectors.
- It tolerates fuzzy input. Paraphrase, loose wording, and typos do not break the search, because matching happens on meaning rather than exact keywords.
- The setup cost is low. Chunk, embed, index, retrieve, and you are live almost immediately. A vector store is useful the moment you embed your first piece of text.

It also has a structural blind spot, and you should know it before you bet the whole memory layer on similarity. [^4] Vector search reasons over semantic closeness, not over explicit relationships. If the agent needs to answer "who approved the budget attached to this project, and which direct reports of that person touched it?", a similarity search over floating point embeddings has no good way to follow the approval chain, because that chain is explicit structure, not proximity. The reference material spells out the consequence: a simple similarity search can miss the link between entity A and entity C when the data only shows that A connects to B and B connects to C. [^4] Vector search can also pull in related-but-irrelevant material that crowds the context window with noise, exactly the failure mode that drags reasoning quality down. [^4]

The honest summary is that vector memory is the right foundation for most agents, and the wrong only tool for agents whose questions depend on relationships.

## Knowledge graphs: memory as typed relationships

A knowledge graph stores facts as entities connected by named relationships. Picture nodes and edges. A node for a customer, a node for a contract, an edge labeled signed between them, another labeled owned-by tying the contract to a team. Neo4j puts the model plainly: facts and entities are nodes with attributes, connected by typed relationships that carry their own attributes. [^3]

The retrieval language is different as well. Instead of a similarity score you run graph traversal, following a pattern such as `(customer)-[signed]->(contract)-[owned-by]->(team)` in a query language like Cypher or the newer GQL. [^3] Precision is the whole point. If an edge does not exist in the graph, the agent does not invent it; the answer is grounded in what the graph actually contains. [^4]

That precision comes with upfront cost. Someone has to design the ontology or schema, which can be rigid and hard to evolve as the domain grows. Raw text has to pass through an entity-extraction pipeline to become nodes and edges, a step that often needs carefully tuned prompts or specialized models. [^4] And there is a cold-start problem: a graph answers nothing well until it is populated, unlike a vector store that works the moment the first chunk is embedded. [^4]

The payoff is multi-hop reasoning and explainability. Following an approval chain, mapping a dependency tree, tracing who reported to whom, these are plain graph traversals that vector search struggles to reproduce. Because the retrieval path is a clear, auditable sequence of nodes and edges rather than an opaque similarity score, you can show exactly why a fact surfaced, which matters where compliance and transparency are required. [^4]

Temporal graphs push this further by recording not just a fact but when it was true. The Zep team's Graphiti is a temporally-aware knowledge graph engine that synthesizes unstructured conversational data and structured business data while preserving historical relationships, so the agent can distinguish "this customer is on the enterprise plan" from "this customer was on the enterprise plan last quarter." [^1] In the Deep Memory Retrieval benchmark Zep scored 94.8% to MemGPT's 93.4%, and on the harder LongMemEval it reported accuracy improvements of up to 18.5% while cutting response latency by 90% relative to baselines, with the largest gains on cross-session synthesis and long-term context maintenance. [^1] The design note worth keeping: memory that forgets its own history cannot tell you when a rule stopped applying.

## Hybrid stores: vectors for the entry point, graphs for the depth

Pick one store and you inherit the other's blind spot. The pattern production teams actually converge on is a hybrid: use vectors to find the entry points, then traverse the graph outward from those points to pull the precise relational context. [^4]

GraphRAG is the clearest illustration. It builds a knowledge graph from documents, finds starting points with vector, full-text, or spatial search, then follows relevant relationships outward to gather context that a flat chunk search would miss. [^3] Neo4j's own summary is direct: basic RAG that relies solely on semantic search is poorly equipped for complex multi-hop questions, and graph-based retrieval surfaces hidden connections that improve accuracy and explainability. [^3]

Mem0, the widely used open-source memory layer, ships the same shape. Its backend pairs vector similarity search with knowledge graph traversal to capture the relational structure among conversational elements. [^2] Evaluated on the LOCOMO benchmark, Mem0 outperformed every baseline category it was tested against, including full-context and retrieval-augmented approaches, across single-hop, temporal, multi-hop, and open-domain questions, and its graph variant was reported as the strongest configuration. The authors wrote of a 26% relative improvement on an LLM-as-a-Judge metric over OpenAI's baseline, 91% lower p95 latency, and a token-cost reduction of over 90% versus a full-context approach. [^2] Notice what the numbers reward: accuracy and efficiency together, not one at the expense of the other.

The most ambitious version takes the hybrid idea further and stops trying to fit memory into one graph at all. MAGMA represents each remembered item across four orthogonal views, semantic, temporal, causal, and entity, then treats retrieval as a policy-guided traversal over whichever view best matches the question. [^5] On the LoCoMo and LongMemEval benchmarks it reported consistent wins over earlier agentic memory systems while keeping retrieval cheap enough to run at inference time. [^5] The transparent reasoning path is the point. By separating how memory is stored from how it is retrieved, you can trace exactly why a memory surfaced, which is precisely the property enterprise users keep asking for.

## A decision pattern, not a religion

Reading surveys in this space, the least useful posture is asking which store is best and expecting one answer. The useful posture is matching the store to the question. [^4]

- Broad and fuzzy beats precise and relational. The user once asked about Kubernetes, the agent should recall that even when the reminder is phrased differently, or it should hold a general draft of a topic. That is vector memory's lane.
- Precise and relational beats broad and fuzzy. Who reports to whom, what depends on what, which approvals chain leads to this record. That is the knowledge graph's lane.
- Both, which describes most agent workloads past a modest size. Vectors find the region, the graph resolves the exact path.

![Match the store to the question: broad and fuzzy questions go to vector memory, precise and relational questions go to a knowledge graph, and questions that need both go to a hybrid store](</diagrams/agent-memory-at-scale-vector-kg-hybrid-stores/2-match-store-to-question.png>)

The practical recommendation from the MachineLearningMastery survey is layered and honest: start agent memory with a vector store for conversational grounding, then introduce a knowledge graph for high-value entities and core operational relationships as the reasoning demands grow. [^4] It is a growth path, not a rewrite, and that is the reason it survives contact with real roadmaps.

## Worked example: routing a support agent's memory to the right store

Let me make it concrete with a support agent that has handled tickets for three months. The point is to see the three stores each carrying the memory they are good at, not a single store trying to do everything.

Step 1: name the questions. Split the agent's workload into the two question shapes from the decision pattern. "Has this customer contacted us before about billing?" is broad and fuzzy; a paraphrase of the query should still surface the past conversation. "Who owns this contract, and who approved the price on it?" is precise and relational; it needs the chain, not a nearest neighbor.

Step 2: put broad recall in vectors. Past conversations, product documentation, and resolved ticket threads get embedded and stored in a vector database. Retrieval here answers the fuzzy questions, and it does so fast and cheap. This is the grounding layer, and it is the one your agent uses on most turns. [^4]

Step 3: put relational facts in a graph. Extract the entities that matter for the business: customers, contracts, teams, approvers, products. Model them as nodes and the relationships between them as typed edges. Write the traversal queries that resolve "who approved this" and "what does this team own." This is the precision layer, and it answers a class of question the vector store cannot. [^4]

Step 4: wire the hybrid. At query time, send the question to a router that decides which store answers it. Fuzzy recall questions go to vectors; relational questions go to the graph. For the genuinely mixed ones, do a vector search to find relevant entities, then traverse the graph outward from those entities to assemble the full picture. That is GraphRAG in miniature, and it covers more of the workload than either store alone. [^3] [^4]

![Routing a support agent's memory: a router sends fuzzy recall questions to the vector store, relational questions to the knowledge graph, and mixed questions through a vector search followed by graph traversal](</diagrams/agent-memory-at-scale-vector-kg-hybrid-stores/3-support-agent-routing.png>)

Step 5: keep the memory honest at scale. Add a consolidation pass so the small fact that the customer moved to the enterprise plan last week actually demotes the older fact in the graph, and prune episodic records that no longer earn their retrieval cost. Lesson 14's consolidation loop does not disappear at scale; it gets more important, because a larger store keeps more stale facts alive. [^1]

That five-step picture is not exotic. It is the memory stack a serious agent eventually needs, and starting with a vector store, then bolting on a graph for the high-value relationships, is the cheapest path to it.

## The other failure mode: a graph with nothing to connect

Vector-at-all-costs is the common failure, but the mirror image bites as well: building a knowledge graph for data that has no meaningful relationships in it. If your agent only ever answers simple recall questions, a graph is overhead. You pay for entity extraction, schema design, and graph maintenance, and you get back precision you did not need. [^4] The tell is whether your questions follow paths. If they do, the graph earns its complexity. If they do not, it is a more expensive way to do what a vector store already did, and the cold-start cost will sting every time someone waits for it to populate. [^4]

## Summary

Memory at scale is a routing problem as much as a storage problem. Vector memory is the fast, fuzzy default, and it is right for broad semantic recall. Knowledge graphs bring typed relationships and auditable traversal, and they are right when questions run along explicit paths. Hybrid stores are the production standard because most workloads need both: vectors find the entry point, the graph resolves the depth. Start with a vector store, add a graph for the high-value relationships your questions actually traverse, and let a router or a two-step retrieval decide which one answers each turn.

## Try it

1. Classify your questions. Write down ten questions your agent genuinely gets. Mark each one fuzzy (survives paraphrase, no path) or relational (follows an explicit chain). Count both columns. Most teams find the split is not as lopsided as they assumed, which is the first hint that a hybrid is coming.

2. Draw the graph before building it. Pick the two most relational questions from step one and sketch the entities and typed edges they need. A customer, a contract, an approver, and the edges signed, approved-by, owned-by are enough to see the shape. If you cannot name the edges, the question may not actually be relational. [^4]

3. Route one query end to end. Take a real question, run a vector search to find candidate entities, then traverse one hop outward from the top match and write down what the graph adds that the vector result alone did not. The answer to "what did the graph add" is your justification for keeping it. [^3]
