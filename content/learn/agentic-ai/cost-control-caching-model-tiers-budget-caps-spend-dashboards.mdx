# Lesson 27: Cost Control, Caching, Model Tiers, Budget Caps, and Spend Dashboards

Lesson 26 put boundaries around a running agent: a serving layer, a stable API, and rate limits and quotas that stop any single consumer from overwhelming the system. That protected the infrastructure. This lesson protects the bill, which is a different job. A rate limit of 30,000 tokens per minute keeps the GPU from melting, but it does nothing to stop a fleet of agents that are each, individually, within every limit, from collectively spending more in a quarter than the project was funded for. Cost control is the discipline of making that bill a number you watch and steer rather than a number you discover at the end of the month.

The one idea to carry out of this lesson: **cost control is three levers, applied in a fixed order. First you cache, so you never pay twice for the same answer. Then you route across model tiers, so you pay frontier prices only for the fraction of tasks that genuinely need a frontier model. Then you cap budgets and watch a spend dashboard, so that whatever you do not catch with the first two levers gets caught by a hard stop and an early warning instead of a surprise.** [^1] Most teams try the third lever first, buy a dashboard, and wonder why the bill is still big. The dashboard tells you where the money went; the first two levers decide how much money goes anywhere at all.

## Caching: do not pay twice for the same answer

Agents reuse a lot of text across calls. The system prompt rarely changes. The company policy document loaded into context is identical every time. The chunk of retrieved documentation that anchors a question comes back unchanged. Caching is the technique that recognizes that repetition and prices the repeated part at a fraction of the fresh part.

Provider-side prompt caching is the first and easiest lever. Anthropic's prompt caching lets you mark a prefix of the context, the system prompt or a shared document, as cacheable. The first call that includes that prefix pays a premium to write it into the cache, and every later call that reuses the prefix reads it back at a steep discount. Anthropic prices a cache write at 25 percent above the normal input rate and a cache read at 90 percent below it. [^1] The economics are deliberately front-loaded: you spend more once, then far less for every repeat. OpenAI's prompt caching works on the same principle and prices cached input at roughly half the normal input cost, while Google's Gemini charges a storage fee for cached tokens plus a read discount of about 75 percent. [^2] The exact percentages shift as providers republish their rate cards, so the numbers to carry are the shapes: cache reads are an order of magnitude cheaper than fresh input, and the savings only show up once the same prefix is reused.

The practical rule is that caching pays off in proportion to how much of your context is stable. An agent whose prompt is a thousand tokens of instructions, all cached, sees almost nothing happen. An agent that loads an 8,000-token policy manual into every call sees the input cost for that manual drop by roughly an order of magnitude. At the extreme, the medium post that documents a real system reports a monthly API bill falling from $720 to $72, eleven times, once a long stable prompt was cached. [^3] The caveat is that the first call in any cache window still pays the write premium, so caching is a win for sustained, repetitive traffic, not for a stream of one-off queries that each carry a fresh context.

Semantic caching is the second, higher-level lever, and it lives in your application rather than in the provider. Prompt caching only saves you when the exact same tokens appear again. Semantic caching saves you when the meaning is the same even though the words are not. The idea is to store the embedding of a question and its answer, then, on an incoming request, compute the new question's embedding and return the stored answer if the similarity is above a threshold. [^4] The value is that semantically equivalent traffic, the same support question asked six different ways, hits the cache instead of the model. Redis markets this as cutting LLM costs and latency by up to 90 percent on workloads with repeated, similar requests, because a cache hit costs almost nothing and answers in milliseconds. [^4]

The two caches are not competitors; they stack. Prompt caching handles the stable prefix at the provider, and semantic caching handles the repeated question at the application. Both have a failure mode worth naming. Prompt caching only engages when you actually mark the prefix and keep it stable, and a small prompt edit invalidates the cached prefix for everyone. Semantic caching can silently serve a wrong answer if your similarity threshold is loose, so the threshold is a correctness decision, not just a cost one. Caching is the cheapest lever and the first one you should turn, because it changes nothing about your model quality and cuts spend directly.

## Model tiers: pay frontier prices only when you must

The second lever is deciding which model handles which request. The prices per token across model tiers differ by an order of magnitude or more, and most agent traffic does not need the top tier. A support agent resolving a billing question and a research agent synthesizing across forty sources are not the same workload, and paying the same per-token rate for both is how budgets leak.

The clean way to think about it is tiers and routing. You define a small set of model tiers: a cheap high-throughput tier for classification, extraction, and simple answers, a mid tier for general work, and a frontier tier reserved for the hard synthesis and planning steps. Routing is the logic that sends each request to the cheapest tier that can do the job. The two dominant routing patterns are rule-based and cascade. Cascade routing sends every request to the cheapest model first and only escalates to the next tier when the cheap model fails or signals low confidence. [^5] It is the closest to a default because it is simple to implement and it makes the failure safe: you start cheap and only pay for expensive compute when the cheap model cannot handle the task. [^5]

The payoff is documented. Research using RouteLLM, an open framework for training and evaluating routers, reports that a good router keeps about 95 percent of frontier-model quality while routing 85 percent of queries to cheaper models, cutting cost by 45 to 85 percent depending on the workload. [^6] Those numbers are not free: a router is itself an inference or classification call, and a poorly designed one can cost more than it saves, which is why rule-based intent routing, where you classify the request type and map it to a tier explicitly, is the practical place to start. The cost of unnecessarily routing a mid-tier task to a frontier model is small; the cost of routing a frontier task to a small model is a bad answer that a human has to fix or that goes out to a customer. [^6]

The failure mode here is the one that quietly erases the savings. A cheaper model lowers cost per token but can raise cost per finished task, when the cheap model makes mistakes that cost retries, escalation, or human review. [^7] The metric that matters is cost per completed task, not cost per token, and that is measured with the evals from Lesson 19 and the observability from Lesson 20. Tiering is only a saving if the cheap tier keeps quality high enough that you are not paying for its mistakes somewhere downstream. The other thing to resist is over-routing to save cents: routing 60 percent of traffic to a cheaper model can silently split one product into two behaviors, and the aggregate accuracy number hides which specific queries got worse. [^7] Route with the quality boundary in mind, and watch the tasks that matter most, not the aggregate.

## Budget caps: the hard stop

Caching and tiering shrink the bill. Budget caps make sure it cannot escape. A cap is a dollar- or token-denominated ceiling that turns off spending when it is reached, and it belongs in the gateway layer from Lesson 26, in front of every provider, where a single key can carry its own limit.

The gateway is the natural home because it already holds the virtual keys. In a gateway like LiteLLM you can set a budget per virtual key, per user, per team, or per model, and the gateway enforces it before a request ever reaches a provider. [^8] A virtual key can carry a monthly budget, a daily budget, a per-model budget such as a small daily allowance on the expensive model, and an expiration period. When the budget is exhausted the gateway returns a budget-exceeded error and refuses the request rather than letting it through. [^8] The structural point is that a runaway agent, the one that burns forty turns re-asking itself the same question, is bounded by a budget even when it is politely within every rate limit, because a rate limit controls speed and a budget controls total spend.

The operational pattern is soft thresholds with a hard stop, and the response ladder is the same shape a good incident runbook uses. Watch usage at 50 percent and review whether the growth is expected. At 80 percent, review routing, token usage, retries, and caching before the trend becomes a problem. At 95 percent, escalate to the service owner or on-call. At 100 percent, block the request or route it to an explicitly approved fallback model. [^9] The point of the soft thresholds is that they give a human time to act on the trend, so the hard stop at the top is a backstop, not the only guardrail. The most effective budgets nest: an organization cap, team caps inside it, and individual key caps inside those, so that one engineer's experimental loop cannot spend the whole org's month. [^9]

## Spend dashboards: the early warning system

Caching, tiering, and caps make the spend small and bounded. The dashboard makes it visible, which is the difference between a cost you steer and a cost you discover. But a dashboard is only as good as its attribution, and attribution is the part that fails first.

The gateway is where the clean attribution lives, because it sees every request. LiteLLM's spend tracking records spend per key, user, team, and tag, so a request tagged with a job ID or a task name shows up under that initiative in the usage view. [^10] That is the same gateway, from Lesson 26, that already tracks rate limits and quotas, so the spend and the traffic come from the same source of truth and agree with each other. The discipline is to tag from the start. A request with no tag is a line item nobody can own, and unattributed spend is exactly how a bill becomes a surprise.

When you move beyond the gateway to the infrastructure that serves your own models, the attribution problem gets harder and the answer comes from FinOps. The lesson from the GPU FinOps work that Adroit published is that a shared inference cluster shows up in a billing console as a single line item owned by the team that provisioned it, not the teams that generated the tokens. [^11] The fix is an allocation model and a tagging schema. Per-tenant allocation, where a proxy injects tenant headers before requests reach the serving layer and cost is weighted by tokens, is the most accurate for multi-tenant inference, because a long retrieval request consumes far more GPU time than a short classification task. [^11] The tags that matter, team, project, environment, model, and cost center, must survive the whole journey from pod labels through the exporter into Prometheus, and that join is the step most teams skip. [^11]

The rollout discipline is showback before chargeback. Showback is attribution-only reporting: teams see what they would be charged, but no money moves. Run it for four to six weeks to surface tagging gaps, then move to chargeback once tagging coverage is above 80 percent. [^11] The insight is that visibility itself changes behavior, which is the whole reason to build a dashboard in the first place. You are not building a bill; you are building a number that the owners of the cost actually look at.

## Worked example: the three levers on one agent

Put the levers together on a concrete internal agent, a document support bot that answers questions against the company policy manual.

The manual is 8,000 tokens and it is loaded into every request as context. At an illustrative frontier input rate of $15 per million tokens, that prefix costs about $0.12 per call uncached. The bot fields 5,000 questions a month, so the manual prefix alone is about $600 a month, and it is the same 8,000 tokens every single time. Marking it cacheable changes the arithmetic: the first call pays a write premium, and the other 4,999 read the cached prefix at about a tenth of the price. That one change cuts the biggest single line item by roughly an order of magnitude, and it took ten minutes. [^2] [^1]

Now route the questions by tier. About 70 percent of the traffic is simple lookups, where does the policy say X, that a cheap model answers correctly. The other 30 percent, ambiguous questions and synthesis across multiple sections, needs the frontier tier. Routing the 70 percent cheap while keeping the frontier for the rest preserves the quality on the hard cases and cuts the per-token cost on the easy ones, which is the RouteLLM shape of keeping most quality while paying frontier prices for a minority of the traffic. [^6]

Then cap it. Give the bot a team budget of $250 a month in the gateway, with alerts firing at 50, 80, and 95 percent and a hard stop at 100 percent. [^9] [^8] Now a documentation update that doubles the manual, or a new feature that triples traffic, cannot silently multiply the bill; it trips the 80 percent alert and a human reviews the routing before the cap blocks anything. And because the gateway tags every request by team and job, the dashboard shows the month's spend attributed to the initiative that owns it. The three levers answer three questions in order: how do we stop paying for the same thing twice, how do we avoid paying frontier prices for easy work, and how do we find out, early, if either of those has drifted.

## The Fortress angle: a hybrid stack running all three levers

Adroit runs this exact stack in miniature on its own inference setup, and the cost decisions are documented in the local infrastructure work. The Fortress runs a hybrid two-tier architecture: cloud models for the agentic workloads that need reliable tool-calling and structured output, and a local llama.cpp server running a 35B Qwen model for background subsystems such as context compression, title generation, triage, and monitoring. [^12] That split is a model-tier decision made the honest way: the local tier was tested for structured tool-calling, failed it outright by emitting empty JSON for nested tool arguments, and so every structured workload moved to cloud while free-text background work stayed local. [^12]

The economics of that tiering are the reason it exists. Adroit's published analysis is blunt that a workload costing $50,000 a month at frontier rates can fall to $8,000 to $15,000 when 70 percent of calls route to smaller local models with quality-equivalent outputs. [^12] That is the tiering lever running on real traffic, and it only holds because the local tier was validated to be quality-equivalent for the tasks that stay on it, which is the cost-per-task rule from earlier in this lesson, measured the hard way.

The spend discipline is the third lever and it is a real FinOps practice, not a dashboard. Adroit's GPU FinOps work documents per-tenant token-weighted allocation, where a proxy injects tenant headers before requests reach the serving layer, so a shared inference cluster attributes its $20,000-plus monthly bill to the teams whose requests generated the tokens instead of to the platform team that provisioned the node. [^11] It insists on showback for four to six weeks before any chargeback, so tagging gaps surface as reporting artifacts instead of as disputed budget lines. [^11] Lesson 26 showed you the serving and quota boundaries around the stack. This lesson shows you how the same stack decides what it costs and who owns it.

## The pitfall to avoid

The most common mistake is reaching for the dashboard first. A team buys a spend dashboard, sees the bill is large, and has no lever to pull, because the dashboard attributes cost but does not reduce it. The order of operations matters: cache first, then tier, then cap, then watch. [^1] [^4]

The second failure is measuring cost per token instead of cost per task. A cheap model that hallucinates a config value, sends the agent down a wrong path, and burns four more calls to recover has made the whole run more expensive than the frontier model would have been in one shot. [^7] Tiering decisions belong in the evaluation suite from Lesson 19, where you measure whether the cheap tier actually holds quality on the tasks you route to it.

The third is a cache correctness bug. A semantic cache with a loose similarity threshold will start serving answers that merely resemble the question, and a prompt cache that silently serves a stale prefix, after the policy manual was edited and the cache was not invalidated, is a correctness failure wearing a cost-saving disguise. [^4] Caching is a quality decision as much as a money decision, and it needs the same testing as the model it replaces.

## Try it

1. **Enable prompt caching on a repeated prefix.** Take an agent with a stable system prompt or a loaded document, mark the prefix cacheable with the cache control flag for your provider, and run the same call twice. [^1] Compare the usage on the first call against the second, and compute the monthly saving if the traffic stayed at that rate.
2. **Add a semantic cache.** Store the embedding of a question and its answer, then return the stored answer when a new question's embedding clears a similarity threshold. [^4] Log the cache hit rate and confirm the threshold does not serve wrong answers on your real traffic.
3. **Route by intent.** Classify requests into a simple tier and a hard tier, send the simple ones to a cheap model, and measure cost per completed task before and after, using your evals to confirm quality held. [^5] [^6]
4. **Set a budget with soft thresholds in a gateway.** Configure a team budget in a gateway like LiteLLM with alerts at 50, 80, and 95 percent and a hard stop at 100 percent, then run your agent against it and watch an alert fire. [^8] [^9]
5. **Tag from the start.** Add team, project, environment, model, and cost-center tags to your requests and confirm the gateway's spend view attributes every dollar to an owner. [^10] [^11]
