By this point in the series you have built a platform with a policy layer, wired it with authentication and secrets, and put a gateway in the traffic path. This lesson asks the question those controls exist to answer: what can actually be made to go wrong with this agent, and how do you audit a system against that list? The deliverable is a security review, a written threat model that names the assets you protect, the paths an attacker can reach them, and the control that stops each one.

The one idea to carry out of this lesson: **a threat model is a working system, not a binder. Start with what you are protecting, map the trust boundaries in the agent's chain, run a defined threat set against each one, tier by the damage a success would do, and write down the risk you choose to accept.** An agent makes that discipline harder than a normal service, because everything it reads, the user prompt, a retrieved document, a tool result, becomes part of the same context that decides its next action. Untrusted data and standing instructions blend by default, and that is the structural fact every threat in this lesson leans on. [^2]

## What threat modeling means for an agent

Threat modeling is a structured, repeatable way to understand the security characteristics of a system from an attacker's point of view. The OWASP threat modeling cheat sheet frames the whole process with four questions every session must answer: what are we working on, what can go wrong, what are we going to do about it, and did we do a good enough job. [^1] Those four questions have driven threat modeling across decades of conventional software, and they still apply. What has changed is what the answers look like.

Traditional software treats untrusted input as data, something separate from the program that consumes it. An agent treats conversation and retrieved content as part of a single input stream, and text, including adversarial text, can be interpreted as executable intent. [^2] Microsoft's threat modeling guidance for AI systems names the three properties that make this different from a normal service. Nondeterminism, because the same input can produce different outputs and you must reason about a range of behavior rather than one path. Instruction-following bias, because models are trained to be helpful and compliant, which makes prompt injection and coercion easier when data and instructions are blended by default. And system expansion through tools and memory, because an agent invokes APIs and persists state autonomously, so a failure in one component compounds into the next within a single run. [^2]

Those three properties do not create brand-new categories of attack. They take familiar risks and give them unfamiliar forms. Microsoft names the results directly: prompt injection and indirect prompt injection through external data, misuse of tools, privilege escalation through chaining, silent data exfiltration, and confidently wrong outputs treated as fact. [^2] Read that sentence again, because it is the syllabus of this lesson.

## Start with assets, not attacks

The most common mistake in agent threat modeling is jumping straight to the attack list. You cannot decide what to protect against prompt injection until you have said what the injection is meant to reach. Microsoft's guidance is explicit on the order: effective AI threat modeling starts by being explicit about what you are protecting, and in an AI system the assets extend well beyond databases and credentials. [^2] The asset list for an agent includes user safety, because an agent can generate guidance that influences a real action; user trust in the outputs; the privacy of sensitive user and business data; the integrity of the prompts, instructions, and contextual data the agent reasons over; and the integrity of the agent's actions and their downstream effects. [^2]

The assets exercise forces the honest question that most teams never ask: what action should this system never take? Some risks are unacceptable regardless of any benefit, and a threat model should surface those boundaries before anyone writes a model call. [^2] A customer support agent should never be able to send money, issue a refund for a purchase it cannot verify, or read the balance sheet of an account it was not shown. Naming those never-boundaries first gives the threat set something concrete to attach to.

Because agents are probabilistic and act through tools, the asset list also has to include the things that are easy to under-protect: correctness of the agent's actions and the hidden state it accumulates. A leaked credential in a log file is a confidentiality failure you can see. A poisoned instruction quietly riding inside a retrieved policy document is an integrity failure that changes every decision that follows, and it is far easier to miss.

## Map the trust boundaries in the chain

Once the assets are named, draw the system as it actually operates, not as the design doc describes it. An agent is a chain, and the OWASP cheat sheet's advice to model with data flow diagrams and mark every trust boundary applies to agents with one crucial addition: the trust boundary sits inside the agent itself. [^1]

The chain looks like this. The user prompt enters. Retrieved data, from a RAG index, a web page, a support ticket, merges in. The model assembles a context from the system prompt, the conversation, and those retrieved chunks, and it picks a tool. The tool runs against a downstream system, a database, an API, a payment service, and its result comes back into the context to shape the next decision. Microsoft's guidance puts the boundary where the control actually lives: the prompt assembly pipeline is a first-class security boundary, because context retrieval, transformation, persistence, and reuse are where trust assumptions quietly accumulate, and teams usually fail in the gaps between components rather than at the most obvious boundaries. [^2]

![An agent is a chain, and every hop is an attack surface: the user prompt, retrieved data, and memory merge into the model context that decides the next action, with the trust boundary sitting inside the model and attacks arriving both on the agent and through it](</diagrams/security-threat-model-full-review-for-agent-systems/1-execution-chain-attack-surface.png>)

The boundary matters because of how the trust question gets answered on each side. Anything the model reads, a document it retrieves, a web page it was asked to summarize, a tool result from a compromised API, arrives inside the same context window as its standing instructions, and the model has no native way to tell which is which. That is the structural weakness the OWASP 2025 Top 10 ranks as number one: a prompt injection vulnerability occurs when user or prompt inputs alter the intended behavior of the system in ways the system designer did not intend. [^3] When that injected instruction arrives not in the user prompt but inside retrieved content a document, a ticket, a web page, it is indirect prompt injection, and it is the attack an agent is structurally most exposed to. [^3]

Each trust boundary in the chain gets its own read. The boundary between an external caller and the agent decides who can talk to it at all. The boundary between a retrieved data source and the context decides whether that source's words can steer the agent. The boundary between the model and a tool decides whether the model's output, which can be coaxed, is checked before it becomes an action. The boundary between a tool and its downstream system decides what that tool is allowed to do. Mark all of them, and for each one ask where injected or attacker-controlled content could cross it.

## Run the threat set

With the assets and boundaries drawn, you need a defined list of what to test against them. The OWASP LLM Top 10 for 2025 is the checklist, and the two that dominate an agent's risk surface are the ones this lesson leans on hardest. Prompt injection, LLM01, is ranked the top vulnerability in AI systems, and in an agent it is amplified because every tool call is a chance for the injected instruction to become an action. [^3][^6] Excessive agency, LLM06, is the gap between what the agent is technically able to do and what it should be allowed to do, and it is the reason a single injection can become a damaging action. [^6] An agent that has too many tools, too-broad permissions, or too much autonomy converts every injection or every mistake into a wider blast radius. AWS's prescriptive guidance for agentic security treats this as the first-line control: determine agent scoping and use deterministic execution logic unless AI is needed, so the design starts with the smallest viable capability surface. [^5]

STRIDE gives you a way to make sure you are not only thinking about injections. The six classic categories, spoofing, tampering, repudiation, information disclosure, denial of service, and elevation of privilege, each name a desirable security property that a threat can violate, and the OWASP threat modeling cheat sheet uses them as prompts to brainstorm threats systematically. [^1] The trick for an agent is not to abandon STRIDE but to re-read each letter in agent terms. I did that in the previous lesson's security architecture, and the reframing holds here.

![STRIDE, reread as threats to an agent rather than to a process: each classic category stays, but running the agent chain reframes what the example looks like](</diagrams/security-threat-model-full-review-for-agent-systems/2-stride-reread-as-agent-threats.png>)

Spoofing becomes agent implied identity: one agent presents itself as another, or a tool returns data as though it came from a trusted system, and the model cannot tell who it is really talking to. Tampering becomes context and tool state: retrieved documents, earlier tool output, and logs are rewritten or reordered, so the next decision is built on attacker-controlled truth. Repudiation becomes fuzzy accountability: the agent took an action and nobody can prove which prompt, tool result, or retrieval produced it, so nobody signs for it. Information disclosure becomes context exfiltration: secrets and user data that were never meant to leave leave anyway, carried out in a tool call, a log line, or a model response. Denial of service becomes unbounded consumption: a loop that never stops spending tokens, a retrieval that never returns, a tool called until its quota is gone. Elevation of privilege becomes excessive agency: the agent acts with more authority than the human behind it, chaining tools to reach systems none of them may reach alone. [^1][^6]

MITRE ATLAS is the companion vocabulary for the same exercise, because it maps the real attack techniques and tactics against AI systems the way MITRE ATT&CK maps conventional malware, from reconnaissance through initial access right down to exfiltration and impact. [^4] Where STRIDE makes you brainstorm by security property, ATLAS makes you check whether the actual techniques an adversary would use, prompt injection, tool poisoning, exfiltration through a tool call, are covered. In the piece I read for the previous lesson, one real-world threat-modeling exercise used a knowledge base of these techniques and found nine distinct threats on a small agent scaffold, the most dangerous of which was a prompt injection that flowed straight into a tool dispatcher with no permission model, effectively giving a crafted message an authenticated reach into file read, shell execution, and database queries. [^7] That is the finding a proper boundary map is built to surface: the injected input crossed from the context into the action plane with nothing in between.

## The four threat classes an autonomous agent invites

The broad taxonomy collapses into four classes that cover most of what will actually hurt your agent, and each maps to a control you already met earlier in this series.

**Prompt injection, direct and indirect.** The user or retrieved content alters the intended behavior. [^3] The defense you built in lesson 17 still holds: keep untrusted content out of the instruction plane, treat prompts as code artifacts that are versioned and reviewed, and validate inputs at multiple layers. [^5] For an agent the sharp edge is indirect injection, because the content arrives through retrieval, where nobody is looking at it.

**Tool misuse.** The model calls a tool it should not, or calls one in a way that exceeds intent. AWS's agentic guidance maps this straight to the OWASP injection and agency risks and answers it with agent scoping and access-control granularity. [^5] The gateway and policy layer from lesson 72 is where this control becomes enforceable: the agent can only call what the allowlist says, and every call is checked, not just the first one.

**Excessive agency.** The system has more capability, permission, or autonomy than the task needs, so an influenced model can take harmful actions. [^6] This is a design property before it is a runtime check. Grant the fewest tools for the narrowest job, use read-only access where read is all that is needed, and gate the actions that would actually hurt behind an approval. [^6]

**Data exfiltration.** Sensitive data leaves the system through the agent's own action chain, carried in a tool argument, a generated file, an outbound web call, or a model response that repeats what it read. [^2][^4] The previous lesson's data-loss control, watching what crosses the boundary in each direction, is the direct answer, paired with the secrets discipline from lesson 28 that keeps credentials out of the context window so they cannot be repeated back out.

![The four threat classes an autonomous agent invites, each mapped to the control this series already built: prompt injection to injection defense, tool misuse to the policy-layer allowlist, excessive agency to least-privilege scoping, and data exfiltration to boundary data-loss watching](</diagrams/security-threat-model-full-review-for-agent-systems/3-four-threat-classes-controls.png>)

## Worked example: the refund agent, attacked and defended

Put the whole model on one concrete system we have visited before: a customer support agent. The form is small. It can read the incoming request, retrieve a policy document, update a CRM row, and call a refund tool against the payment system. The user side is a customer email. The policy document is the retrieved content.

Now run the attack. An attacker registers a scenario where the support agent is asked to handle a refund that has already been issued. The attacker plants instructions inside a document the agent will retrieve, a forum post, a seeded support ticket, a page the RAG index ingested, with text that reads like a legitimate system update but tells the agent to proceed to issue a new refund and to record no trace. This is indirect prompt injection, and the agent has no native way to tell a policy instruction from a hostile one inside its context. [^3]

The agent reads the incoming email, retrieves the poisoned document, and the document's embedded instruction rides into the context that drives the tool decision. The agent decides to call the refund tool. That call crosses three boundaries in one move: the boundary between retrieved content and context, the boundary between context and tool dispatch, and the boundary between the tool and the payment system. At the moment of the call, the outcome depends entirely on what sits at those boundaries, and here is where the controls from earlier lessons decide it.

The refund tool is gated behind a hard condition that no prompt can override: a refund is only callable when there is a verified, copied receipt in the referenced order record, and the refund amount must match the original charge. The agent cannot invent either, because the verify step is deterministic code, not model judgment. [^5] The support-tier agent identity from lesson 28 has no refund permission at all, so even a correct call is denied; refund is a higher-grant identity only. [^5] The gateway from lesson 72 applies the policy: default deny, the refund call is allowed only for the human escalation path, and every attempt is logged with the reason lineage so the injection attempt leaves a trace that survives the agent's own narrative. [^5]

![Worked example: the refund agent attacked and defended. An injected instruction rides into the context from a retrieved document, but the refund tool is gated behind a deterministic verify step, a support-tier identity with no refund permission, and a default-deny policy that logs every call](</diagrams/security-threat-model-full-review-for-agent-systems/4-worked-example-refund-agent-attack-chain.png>)

What stops the attack is not the model being told to be careful. What stops it is that the action the injection wanted, issuing a refund, is unachievable from where the agent sits. The injection can move the model's intent, and it cannot move the deterministic boundaries the model cannot override. That is the whole lesson in practice: the injection targets the model, and the defense lives in the wiring around the model. [^6]

## Turn it into a written security review

A threat model that stays inside your head is a conversation, not a system. The audit output is a written review with a row per threat, and the discipline of writing it down is what makes it auditable and re-runnable. Each row names the threat, the trust boundary it crosses, the asset it reaches, the control that stops it, and the residual risk you accept if you choose not to control it.

The residual-risk column is the one most teams skip, and it is the most important. OWASP's guidance is blunt that a threat model needs to rank threats and drive responses, and that ranking has to be by impact, how bad a success actually is, not by how loud the scanner gets. [^1] For each threat, decide one of three responses: mitigate it with a control, accept the risk with a named owner who writes down why, or transfer it. A review that ends with every row mitigated is a review that was not being honest, because no agent is fully hardened. A review that records who accepted each remaining risk, and why, is the record a governance board and an auditor actually want. That is the connection to the governance lesson: this model gives the review board something concrete to sign.

The review re-runs on change, not on a calendar alone. OWASP is clear that threat modeling is not a one-time step but a practice you hold to as the system evolves, because the system keeps changing. [^1] Add a tool, switch a model, change a retrieval source, and the threat surface moves. The trigger for a re-review is any change to the agent's boundary, not the arrival of a date on a roadmap.

![The security review as a written, re-runnable audit: map the boundaries, run the threat set, tier by actual risk, write the residual risk you accept, and re-run whenever the agent grows a tool or a boundary moves](</diagrams/security-threat-model-full-review-for-agent-systems/5-security-review-audit-pipeline.png>)

## The pitfalls to avoid

The first is modeling the design doc instead of the running system. If you draw the architecture the way it was intended and the retrieval source, the tool grant, or the identity is different in production, every threat after that is aimed at a system that does not exist. Ground the review in the data flow as it actually operates. [^2]

The second is protecting only the obvious asset. If your asset list stops at databases and credentials, you will protect confidentiality and miss the two that do the lasting damage in an agent: the integrity of the context the model reasons over, and the integrity of the actions it takes. A poisoned instruction is an integrity failure that silently compromises every later decision.

The third is treating the model as the control. Telling the system prompt to refuse dangerous actions is not a control, because the component being told to decide is the component that can be influenced. The bound must be in deterministic code that the injection cannot reach. This is the excessive-agency lesson from OWASP and the repeated theme of this course: constrain the capability, and the influence has nowhere to land. [^6]

The fourth is skipping the residual-risk record. A threat model where someone says we will deal with it later and nobody writes down who owns that decision is a plan to forget the risk on purpose. Every accepted risk needs a name and a reason, or it is not a decision, it is an omission.

## How to run the review, step by step

1. **Draw the boundary a data flow diagram** of the agent as it actually runs, and mark every trust boundary with the direction data crosses it and where untrusted content can enter. [^1][^2]
2. **Name the assets and the never-boundaries.** Write the thing this agent must never do, and the assets, including context integrity and action integrity, that a success would reach. [^2]
3. **Run the threat set against each boundary.** Walk prompt injection, tool misuse, excessive agency, and data exfiltration, and check them with STRIDE and against the MITRE ATLAS technique list. One row per threat, one boundary each. [^1][^3][^4][^6]
4. **Assign a control to every threat you mitigate.** Point each one at a real mechanism from this series: a policy-layer allowlist, an identity with no permission, a deterministic verify step, a data-loss watch on the boundary, a token budget. [^5]
5. **Tier by impact and decide the residual.** Rank by the damage a success would do, and for anything you do not control, write the accepting owner and the reason. [^1]
6. **Re-run on change.** Any change to a tool, a model, a retrieval source, or an identity reopens the review, because the boundary moved. [^1]

## The pattern to take away

1. **A threat model names what to protect before it names what to fear.** Start with assets and never-boundaries, then map the trust boundaries in the actual chain. [^2]
2. **The trust boundary sits inside the model.** Everything the agent reads joins the context that chooses its next action, and untrusted data and standing instructions blend by default. [^2][^3]
3. **Run a defined threat set.** Prompt injection, tool misuse, excessive agency, and data exfiltration, cross-checked with STRIDE and MITRE ATLAS, cover the realistic surface. [^3][^4][^6]
4. **Constrain the capability, not the model's mood.** The injection moves model intent; only deterministic boundaries can stop the action it wants. [^6]
5. **Write the residual risk down.** A review that records who accepted each remaining risk is the auditable system; a review that mitigates everything is theater. [^1]

If you walk away with one skill, it is the ability to produce, on demand, a written threat model for a given agent: name the assets, draw the boundaries, run the threat set, and record what you chose to accept. That single document, current and owned, is what separates an agent that happens to be secure from an operation that can prove it, and audit it, and re-run it the day the agent grows a tool.

## Try it

Take an agent you have running or a design you are about to build, and produce its security review on paper before you touch another line of configuration. Start by drawing the boundary as a data flow diagram and marking, in red, each place where untrusted content can enter the context. Then write the assets and the one never-boundary: the single action this agent must be structurally unable to take. Next, run the four threat classes against each boundary and write a row for each: threat, boundary, asset reached, and the control from this series that stops it. Where you find a threat with no clean control, decide between accepting it with a named owner and redesigning the scope, and write that decision down. Last, list the three changes, a new tool, a model switch, a new retrieval source, that would each force a re-review. You should end with a one-page threat model: the boundary map, the never-boundary, the threat rows, and the recorded residual risk, the document a real security review is supposed to produce.

## What's next

This lesson gave you the threat model that says what can go wrong and how to audit against it. The controls you bound your agent with will not always hold, an injection will land, a model will be confidently wrong, data will move. Lesson 75 turns to what happens after that. It covers incident response for agent systems: how to detect and contain hallucinations that produce a harmful action, how to trace and limit a data leak once the boundary has been crossed, how to roll an agent or its state back to a known-good point, and how to run a postmortem that turns one failure into a fix across the whole operation. Where this lesson asked what an attacker could make the agent do, the next one asks what you do when it happens anyway, and how you make sure it does not happen the same way twice. Ship your threat model now, so the incident-response playbook has a boundary map to point at.
