Every serious agent project reaches the same fork. You have a model that is broadly capable and a set of enterprise documents, a required output format, or a niche domain where the off-the-shelf model underperforms. You have two ways to close that gap, and they sound similar until you look at what each one actually does. RAG, retrieval augmented generation, leaves the model untouched and feeds it the right context at answer time. Fine-tuning leaves the served context alone and changes the model itself.

That distinction is the whole lesson. It is worth spending the time to get it crisp, because the framework for choosing between them follows directly from it. RAG changes what the model sees. Fine-tuning changes how it behaves. Pick the wrong one and you spend serious money training a model to do something retrieval did for free, or you build a retrieval pipeline to solve a behavior problem the weights needed to absorb.[^1]

## The core distinction: what changes

Start with the mechanism, because everything else is a consequence.

Retrieval augmented generation connects a model to an external knowledge base at inference time. Rather than baking knowledge into weights, a RAG pipeline retrieves relevant chunks from a vector store or document index and augments the prompt before the model generates. The model's weights are never touched. [^2] You can think of it as an open book exam: the model performs the reasoning, and the retrieved text is the material it is allowed to cite. The answer is as good as the retrieval that feeds it, and it can point at the specific document it read.

Fine-tuning is the opposite: it continues training a pretrained model on a curated set of examples to permanently adapt its internal parameters. [^2] The model carries whatever it learned directly in its weights, so at inference time it answers from those weights alone, with no retrieval stage in the call path. [^2] This is a closed book exam: the behavior lives inside the model, and nothing is fetched at runtime.

The one-line rule that the sources converge on: fine-tuning changes behavior, style, and format, while retrieval is the better tool once the model needs current or proprietary facts. [^1][^3] Knowledge that must stay fresh belongs in a retrieval layer you can update with an edit. Behavior that must stay consistent belongs in the weights, where it cannot drift between calls. When you classify a message, you want a behavior. When you write a support answer grounded in today's policy, you want a fact.

## The framework: five questions, in order

Do not ask "RAG or fine-tuning?" as if it were one global decision. The answer changes per use case, and the framework below is per-use-case too. Walk it in order, and each answer narrows the choice.

![The five-question decision framework walks in sequence from whether the gap is knowledge or behavior, through how fast the data changes, whether answers must cite and honor per-user access, what labeled data exists, and where the costs land, resolving toward RAG first, fine-tune first, or the hybrid](</diagrams/fine-tuning-vs-rag-decision-framework/2-decision-framework.png>)

**1. Is the gap about what the model knows, or how it behaves?** This is the closest question to the mechanism. If the model produces fluent but wrong or stale answers because it does not have your documents, that is a knowledge gap, and RAG is the natural fit. If the model knows the material but formats the output wrong, talks in the wrong register, or fumbles the terminology specific to your niche, that is a behavior gap, and fine-tuning deserves a look. [^1][^3] The Databricks framing lines up exactly: RAG is used primarily to inject new knowledge into a model, while fine-tuning is best for changing behavior, tone, or task structure. [^2]

**2. How fast does the source knowledge change?** Retrieval reflects new data as soon as it is indexed, with no retraining. Fine-tuned models are locked to the snapshot they trained on, and updating them means gathering fresh data and running another training cycle. [^2] If your policy documents, pricing, or product catalogs change weekly or monthly, RAG wins on freshness alone. If the domain is stable for quarters at a time, the weighting shifts. The rule of thumb from one decision framework: if knowledge changes more than monthly, prioritize RAG; if it is stable for multiple months, evaluate fine-tuning. [^4]

**3. Must the answers be traceable, and must access be controlled per user?** RAG has a structural advantage in provenance. Because the retrieved text is passed explicitly to the model, a RAG pipeline can cite the specific source document behind each claim, which is exactly what regulated industries need. [^2][^5] A fine-tuned model synthesizes answers from parameters and cannot point at a source passage, making auditability hard. [^2] Data privacy follows the same line. Fine-tuning bakes your data into the weights of a model, which means a commercial fine-tuning service receives that data and the trained model carries it. RAG keeps the data in a controlled retrieval layer, so you can grant, restrict, or revoke access and delete content without retraining. [^2][^5] Vectara makes the granular point: with fine-tuning you either include a folder of files or you do not, but with retrieval the search itself can be directed to withhold segments a user is not permitted to see. [^5] If per-user access control or deleting a document matters, that alone may force RAG.

**4. What data do you actually have?** Fine-tuning needs labeled example pairs: inputs with the exact outputs you want the model to produce, on the order of a few hundred to a few thousand curated examples for a solid start. [^1] If you only have a pile of documents and no labeled question-answer set, you cannot fine-tune today, and RAG over what you already have is the thing you can ship this week. [^1] Labelling is slow and expensive, so the presence or absence of a usable training set is often the deciding constraint in practice.

**5. How do the costs land?** RAG carries no training cost but an ongoing operational one: vector databases, embedding pipelines, retrieval infrastructure, and a retriever that quietly caps your answer quality if it is weak. [^1][^2] Fine-tuning is the mirror image: a significant upfront training bill, then cheaper per-query serving, because a smaller, specialized, fine-tuned model can replace a larger generalist one and there is no retrieval stage in the path. [^2] The economics favor fine-tuning when query volume is high enough to amortize the training cost. [^2] In practice, most teams do not have to choose by foresight. Build the RAG version first, watch the queries, and let the observed failure patterns tell you which flows are worth fine-tuning. That is the phased path the decision sources recommend: start with RAG for the quick win, then fine-tune the highest-value, highest-volume flows while keeping retrieval for knowledge currency. [^2][^4]

## Worked example: a support agent, both gaps at once

A decision framework stays abstract until you run it on a real case. Take the support assistant you have probably glimpsed in earlier lessons in this course: it routes tickets, drafts replies, and drafts summaries.

Apply question one. The system has two distinct weaknesses. It writes replies in a flat, off-brand voice and sometimes formats the summary as prose when the downstream tool needs a strict structure. That is a behavior gap. It also has no idea what the current refund policy is, because the policy changed last quarter and the model was trained before then. That is a knowledge gap. One system, two different gaps, and the framework says they want two different tools.

Question two settles the knowledge side fast. The policy, pricing, and product docs change on a rolling basis. Any fact baked into weights would go stale the moment a policy updates, and refreshing it would mean a training cycle every time. So the factual half belongs in RAG. Question three agrees: every support answer must cite the policy it is based on, and a tiered account plan means some documents are visible to some users only, which retrieval can enforce and baked-in weights cannot. [^5]

The behavior side points the other way. The tone and the strict output format are stable. They are exactly the kind of durable behavior that a small fine-tuned model can carry reliably, and for the volume this agent handles, the training cost amortizes cleanly. [^1]

So the honest answer for this agent is not a choice. It is the hybrid: a fine-tuned model that knows how to write in the brand voice and emit the strict summary structure, with RAG supplying the current policy, pricing, and per-user document access at answer time. That is the pattern the sources describe as the mature enterprise default: fine-tuning for domain understanding and output format, RAG for current facts at inference time, and the two together beating either alone for complex use cases. [^2][^3]

![The support agent splits into a fine-tuned model that carries the brand voice and strict summary format, paired with a RAG layer that supplies the current refund policy, pricing, and per-user access, so the grounded reply writes in the right voice and cites the current policy](</diagrams/fine-tuning-vs-rag-decision-framework/3-hybrid-support-agent.png>)

You can encode the framework as a small Python function, which makes it repeatable across every use case your team proposes. It is a decision helper, not a substitute for judgment, but it forces the questions in the right order and makes the reasoning visible.

```python
def recommend(query_volume, change_freq_months, needs_citations,
              needs_user_scoped_access, have_labeled_pairs, problem_is_behavior):
    score_rag, score_ft = 0, 0

    # knowledge vs behavior gap
    if problem_is_behavior:
        score_ft += 2
    else:
        score_rag += 2

    # how often the underlying facts change
    if change_freq_months <= 1:
        score_rag += 3        # fresh facts favor retrieval
    else:
        score_ft += 1         # stable facts can live in weights

    # traceability and scoped access
    if needs_citations or needs_user_scoped_access:
        score_rag += 3        # retrieval cites and gates by user

    # what data exists today
    if have_labeled_pairs:
        score_ft += 1
    else:
        score_rag += 2        # no labeled set -> RAG ships now

    # economics: high volume amortizes training
    if query_volume > 100_000 and have_labeled_pairs:
        score_ft += 1

    if score_rag > score_ft:
        return "RAG first"
    if score_ft > score_rag:
        return "fine-tune first"
    return "hybrid: fine-tune behavior, RAG for facts"
```

Run it on the support agent: behavior gap (fine-tuning +2), facts change monthly (RAG +3), citations and per-user scope required (RAG +3), labeled pairs exist at volume (fine-tuning +2). RAG leads clearly, with a strong fine-tuning tail, which is the hybrid verdict, the same one the qualitative read reached.

## The watchouts on each side

The framework picks a side, but both sides carry traps, and knowing them keeps you honest.

RAG is bounded by the quality of its retrieval, full stop. If the retriever returns the wrong chunks, or the knowledge base contains bad data, the model produces bad answers with perfect confidence, because its job is to reason over whatever it was handed. [^2] A weak retriever silently caps quality regardless of how good the generation model is, and the pipeline brings permanent operational surface: vector stores, chunking, embedding refresh, and monitoring. [^1][^2] The failure is also structural: basic RAG with static batch-uploaded documents drifts stale when the source changes and nobody re-ingests, which is why freshness has to be a designed pipeline, not a hope, a failure mode earlier lessons in this course covered.

Fine-tuning has traps of its own, and they are less visible to the teams doing it. It is expensive and demands ML expertise and GPU access, so the bar to run it well is real. [^5] It can suffer catastrophic forgetting, where the model unlearns part of its general capability while specialising, especially under repeated fine-tuning, and that loss is hard to catch until something breaks. [^5] Most important, fine-tuning is a poor way to add facts. OpenAI's own guidance is that it adjusts behavior, style, and format, and retrieval is the tool for current or proprietary knowledge, because anything learned into weights at training time freezes at that moment and only another training run can update it. [^1][^3] Teams that fine-tune a model to "teach it" the contents of a changing document set are solving the wrong problem with the expensive tool.

There is also a newer pattern worth having in your vocabulary: RAFT, from UC Berkeley in 2024, fine-tunes a model specifically to read retrieved documents well and ignore the irrelevant ones, so it sharpens how a model consumes RAG context rather than replacing retrieval. [^1] If a hybrid system underperforms because the model argues back against good retrieved evidence, RAFT-style training is one direction to look. But that is a lesson for another day. For today, the point is that retrieval and fine-tuning are not rivals. They operate on different layers, and the strongest systems use both.

## The pattern to take away

The whole framework reduces to one move. Separate the two questions your system must answer: what should the model know, and how should it behave. Give the first to retrieval, which can cite and stay current. Give the second to fine-tuning, which can hold a durable skill in its weights.

1. If the gap is missing or stale knowledge, and it changes or must be cited, start with RAG.
2. If the gap is a fixed output format, a consistent voice, or a narrow domain skill, and you have labeled examples, consider fine-tuning.
3. If you have both gaps, run both: fine-tune the behavior, retrieve the facts. That is the mature enterprise pattern. [^2]
4. When in doubt, ship RAG first. It is an afternoon to stand up over documents you already have, and the observed queries it produces are exactly the data you need to design a fine-tuning set later. [^1][^4]

## Try it

Pick a system you work on or want to build and take it through the five questions on paper. Name the gap in one sentence: is it about what the model knows or how it behaves? Then answer the other four with real numbers where you can, how often the underlying data changes, whether answers must cite sources or honor per-user access, how many labeled examples you could assemble this quarter, and roughly how many queries the system will serve. Write the verdict, then check it against the worked example above. If your reasoning produced "hybrid," say which gap each half solves. The value of the exercise is not the label. It is that you now know which half of a system is a retrieval problem and which is an engineering-versus-model problem, before you spend money solving the wrong one.

## Summary

Fine-tuning and RAG solve different problems. RAG changes what the model sees, injecting current or proprietary knowledge at answer time without touching a weight, so it can cite sources, honor per-user access, and stay fresh with an edit instead of a training run. Fine-tuning changes how the model behaves, baking a durable skill, tone, or output structure into the weights so it answers reliably with no retrieval stage in the path, at the cost of an upfront training bill and a knowledge snapshot that freezes at training time. The decision framework is five questions asked in order: is the gap knowledge or behavior, how fast does the data change, do answers need citations and scoped access, what labeled data exists, and where do the costs land. When both gaps are present, the mature pattern is the hybrid: fine-tune the behavior, retrieve the facts, so the system is behaviorally consistent and factually current at once. [^1][^2][^5]
