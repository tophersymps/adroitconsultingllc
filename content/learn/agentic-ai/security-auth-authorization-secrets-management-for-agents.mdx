# Lesson 28: Security: Authentication, Authorization, and Secrets Management for Agents

By now an agent in this series can call tools, keep state, observe itself, and coordinate with other agents. This lesson is about the gate that sits in front of all of it: proving who is acting and stopping that actor from doing more than it is allowed to do. It is the difference between an agent that quietly does its job and an agent that becomes the thing attackers talk to.

The one idea to carry out of this lesson: **an agent's security is decided before it acts, in three separate systems that must not be conflated. Authentication proves who is acting. Authorization decides what that actor may do. Secrets management keeps the credentials that prove identity short-lived, tightly scoped, and away from the model's context.** The failure mode to design against is an agent that authenticates once with a long-lived, over-privileged secret, then acts with all of it forever.

## The two identities an agent carries

A person logs into an app once and the session carries their identity. An agent is not that. An agent makes many independent requests across its run, each one a tool call, and each one has to carry proof of who is acting. Worse, an agent usually acts on behalf of a human who is not present for most of those calls. So it inherits two distinct identity problems at once.

The OWASP authorization cheat sheet draws the line cleanly. Authentication is verifying an entity's identity. Authorization is the process of verifying that a requested action or service is approved for that specific entity. [^2] A user who has logged in is not automatically allowed to do everything the system can technically do. The two checks are separate, and treating them as one is where access control breaks. [^2]

For an agent, that separation matters twice over. The agent authenticates as some principal, and it also has to be authorized per action, because the actions themselves are being chosen by a model that can be steered. The classic distinction, a logged-in admin who is not authorized to touch payroll, becomes an agent that authenticated as a service account and is not authorized to delete anything. Same shape, different stakes, because the agent fires actions on its own.

## Three authentication patterns for agents

Authentication answers the question "who is making this call." For agents, the answer is not one thing. AWS's Bedrock AgentCore documentation names three patterns that cover the realistic space, and picking the right one per resource is the first real decision. [^4]

**User-delegated access.** When the agent needs a specific person's data, it uses the OAuth 2.0 authorization code grant. The user consents once, through the provider's consent screen, and the agent gets scoped access to that user's resources. This keeps a clean separation between the agent's identity and the user's authorization, and it is the right call for personal assistants and customer service agents that touch individual records. [^4]

**Machine-to-machine authentication.** When the agent is acting as itself against system-owned resources, with no user present, it uses the OAuth 2.0 client credentials grant. The agent authenticates directly with its own credentials and pre-configured permissions. This is the pattern for background jobs, scheduled tasks, and data-processing pipelines that run headless. [^4] Both of these grant types are defined in RFC 6749, the OAuth 2.0 specification, where the client credentials grant is described as being for cases where the client is acting on its own behalf. [^7]

**On-behalf-of token exchange.** When a user is already authenticated to the agent and the agent must call a downstream service that enforces per-user access, the agent exchanges the inbound user token for a new, audience-scoped token. That token carries both the user's identity and the agent's, so the downstream service can make its own authorization decision without a second consent prompt. [^4]

The practical takeaway is that a real agent often uses all three at once. A customer service agent reads a customer's account with delegated access, queries an internal knowledge base with machine credentials, and calls a per-user HR service through token exchange. [^4] Do not build one identity for the whole agent. Build the identity that fits each resource the agent reaches.

## Authorization is a per-action check, not a login step

Authorization fails in agents for a structural reason: the thing choosing the actions, the model, is the least trustworthy component in the chain. It can be tricked into asking for an action it should not want. So you cannot let the model be the one to enforce its own permissions. The system has to.

The OWASP authorization cheat sheet gives the rules that carry over directly, and they are worth reading as a checklist. Enforce least privilege, both horizontally across peers and vertically across roles. Deny by default, so that a request matching no rule is refused rather than allowed. And validate permissions on every request, not once at the start of a session. [^2] The last one is the one that trips up agent builders. An agent session can run dozens of tool calls, and each one needs its own authorization check. A single missed check is enough, because an attacker only needs one way in. [^2]

Least privilege is where the OWASP Gen AI project lands the agent-specific version of this. Its LLM06 risk, Excessive Agency, is defined as the system giving the model too much functionality, permission, or autonomy, so that an influenced model can take harmful actions. [^5] The fix is not more refusal training. It is fewer tools, narrower tools, read-only access where read is all that is needed, and approval gates on the actions that would actually hurt. [^5] Authorization has to be enforced at the boundary, in code, for every tool call the agent makes.

## Secrets management, with the agent twist

A secret is any credential the agent uses to prove identity: an API key, a database password, an OAuth token, a signing key. The OWASP secrets management cheat sheet is the reference for how to handle them, and its core principles apply to any system. Never hardcode secrets. Store them in a designated secrets management system, not in code, config files, or spreadsheets. Centralize, because scattered secrets are harder to protect, rotate, and audit. [^3]

The cheat sheet pushes toward short-lived credentials. Use dynamic secrets where possible, credentials generated on demand for a single session that expire on their own, so a stolen one is worthless soon after. Rotate static secrets on an automated schedule, because a key that never turns over is a key that works forever once leaked. Give every secret an expiration, and make applications verify the secret is still active before trusting it. [^3]

Now the agent twist, and it is the part most generic guidance misses. In a normal service, a secret is a configuration value handed to a process at startup. In an agent, the process it is handed to is a model whose entire job is to turn tokens into actions, and everything the agent reads ends up in its context window. A secret that lands in the model's context is not a configuration value anymore. It is exfiltrated data, because the model can repeat it or act on it, and it can be steered into revealing it by a prompt injection riding in on some document the agent was asked to summarize. [^3]

That changes where you put secrets. Do not put them in the system prompt, do not put them in tool schemas, and do not let them appear in tool arguments or logs. Inject them at the boundary, in the environment or the credential store, so the model never sees them. This is the same containment logic this series used for prompt injection in lesson 17: keep the credential out of the sandbox entirely, and it cannot be exfiltrated no matter what the model is persuaded to do.

## Worked example: how Hermes bounds an agent's reach

This is not hypothetical at Adroit. The Fortress runs Hermes agents, and the Hermes documentation spells out a defense-in-depth model that is a working version of everything in this lesson. [^6]

Authentication and authorization start at the platform boundary. Hermes uses user authorization with allowlists and DM pairing to decide who can talk to an agent at all, and it gates tools by toolset and platform policy. [^6] That is the "who may act, and how far" question answered before the model sees a request.

File write safety is a direct example of deny-by-default. A denylist plus an optional write sandbox controls what `write_file` and `patch` can touch, and the sandbox is exactly the boundary concept from lesson 17. [^6] This very lesson is being written under a restricted write-safe root that only allows writes inside the working tree, and a write outside it is denied outright rather than attempted. That is least privilege applied to the tool itself.

Secrets management has its own layer. Hermes filters credentials for MCP subprocesses and isolates environment variables, and it supports credential file passthrough for OAuth tokens so the secret reaches the process without being exposed in the agent's context. [^6] Container isolation adds a hard floor: an agent running in a sandboxed container cannot reach the host, so a leaked credential inside the container is bounded. [^6]

The headless case matters most. Hermes cron jobs run with `cron_mode: deny`, meaning when an unattended job hits a dangerous command, it is blocked rather than auto-approved, because no human is waiting to review it. [^6] That is the fail-closed default this lesson keeps coming back to: when there is no one to ask, the safe answer is no.

## The pitfalls to avoid

The first and most common mistake is conflating authentication with authorization. The agent proved who it is, so the system assumes it can do anything. That is broken access control, and OWASP's authorization cheat sheet is explicit that an authenticated user is often not authorized for everything. [^2] For an agent, prove identity and enforce scope as two separate decisions.

The second is a long-lived, broadly scoped secret doing all the work. A static service account token with access to every table, rotated never, is a single point of failure. If it leaks, the attacker inherits the whole agent. The defense is scoped, short-lived, rotating credentials, with the blast radius sized to the task. [^3]

The third is letting the model hold the secrets. A credential in the system prompt, a tool schema, or an echoed log line is a credential the model can be steered into revealing. Keep secrets out of the context window entirely and inject them at the boundary. [^6]

The fourth is checking authorization once at session start and trusting it for the whole run. Agents make many calls, and each one needs its own check. [^2] A single unchecked call is the one an attacker finds.

## Try it

1. **Draw the identity map.** Take an agent you have built. For every system it reaches, write down the authentication pattern it uses (delegated, machine, or on-behalf-of) and the identity it presents. Then ask whether the identity matches the resource. An agent reading a user's private file with a machine credential is a red flag.

2. **Find the excessive agency.** For each tool the agent can call, list the functionality, the permission, and the autonomy behind it. OWASP's LLM06 names those three dimensions. [^5] Mark any tool that can do more than its task needs, any connection with broader rights than the task requires, and any action that runs without approval.

3. **Move one secret out of reach.** Pick one credential that currently sits in a prompt, a config file, or a tool argument. Move it to an environment variable or a secrets store, inject it at the boundary, and confirm the agent's context never shows it. Then set an expiration or rotation on it if it does not have one. [^3]
