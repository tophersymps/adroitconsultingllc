Lesson 75 was about the moment the fire starts: notice the agent acted wrong, freeze the trace, contain, roll back, and run a postmortem that ships a fix. It told you to export the trace tree before you touched anything, because recovery destroys evidence. This lesson steps back and asks a harder question that has no fire at all. When the smoke cleared, what did you actually have? A snapshot you took in a hurry, or a standing record that a stranger can read three weeks later and reconstruct what the agent did, why it did it, and prove that nothing was altered in between?

That is the difference between freezing evidence and auditing an agent. This lesson builds the audit system you should have had running before lesson 75 happened.

## What auditing an agent actually means

Start with the definition, because it does most of the work. The ClickHouse engineering team describes AI agent observability as the practice of capturing every step an autonomous agent takes, the LLM calls, the tool calls, the retrievals, the sub-agent spawns, as spans in a single trace, so engineers can reconstruct why the agent did what it did. [^1] Auditing is that same record read backward, on demand, as the answer to a specific question: what did this agent do with this input, and can you prove it.

That definition quietly explains why normal application logging lets you down. A web service is deterministic: the same request hits the same code path and produces the same logs, so "reproduce the bug" is a reasonable first move. An agent is not. [^1] One request becomes a variable tree of model calls, tool calls, and sub-agent invocations whose count and order differ run to run. The control flow, which branch to take, how many times to loop, is chosen by the model at runtime, not by your code. And the failures are often semantic: the agent confidently returns a wrong answer, so the trace shows HTTP 200 everywhere and nothing ever trips an error handler. [^1] To that, add the property that matters most for auditing: every tool call is a side effect that mutates a real system, a database row, an email, a support ticket. [^1] You are not logging a request, you are documenting an action someone will eventually ask about.

So the audit record is not your application log with a prompt pasted in. It is a structured, complete, tamper-evident account of the agent's whole run, written to a store the agent cannot rewrite.

## What the audit record must capture

The reliable way to design it is to start from the worst question someone will ask and record what answering it takes. A consumer is angry, a customer has filed a privacy complaint, a regulator wants documentation. The question is almost always some form of: what did the agent do, on what authority, with what input, through which tools, and what changed as a result. [^9]

Engineers who run observability on real agents converge on the same short list of things to record per step. ClickHouse names five: the prompts and completions exchanged with the model, the inputs and outputs of every tool call, token counts per call, latency per span, and the decision trace, meaning which action the agent chose and what alternatives it saw. [^1] Each of the five closes a gap an investigation would otherwise hit. Without the prompt you cannot know what the agent was asked; without tool inputs and outputs you cannot see where the side effect came from; without the decision trace you cannot tell whether the wrong output came from a bad retrieval, a bad tool result, or a bad model judgment.

To those five, the forensics view adds two properties that decide whether the record is evidence or decoration, and both come back later in this lesson. First, helpers writing about agent forensics push the one-run-one-trace discipline: give every run a single trace ID, attach every model call, tool call, policy decision, and approval to it, and keep the before and after values of any records the agent changed. Then an investigator can walk backward from a bad outcome to its cause. [^9] Second, the record must be complete in a way monitoring often is not. ClickHouse is blunt that sampling or rolling up agent telemetry destroys exactly the context debugging and auditing depend on, because a semantic failure is only visible in the raw payload, not in an aggregated number. [^1] Replay-grade capture means verbatim, not occasional, and not truncated.

There is a real tension with privacy that belongs in the design, not after it. OpenTelemetry's GenAI instrumentation records model names, token counts, and durations by default and treats the full content of prompts, completions, and tool results as opt-in, precisely because that content can contain user data. [^2] The practical rule: capture the metadata always, and capture content as a deliberate, PII-controlled decision, redacting at the SDK or the collector the way you would for any log pipeline. [^1] An audit record full of customer data that nobody redacted is a compliance incident of its own.

## Trace structure: a span tree that names every step

Once you record the right things, you need a structure that makes them legible, both to humans and to the replay engine you will build. The emerging standard is the OpenTelemetry Semantic Conventions for Generative AI, which give the industry a shared vocabulary for naming GenAI operations. [^1] [^3] Under those conventions an agent run is a span tree. The agent invocation is the root span, and every LLM call, tool execution, retrieval, and sub-agent spawn is a child span joined into one tree by standard trace propagation. [^1]

A support agent that looks up an order, checks a refund policy, and drafts a reply renders roughly like this, from the ClickHouse walkthrough: an `invoke_agent` root span at 12.4 seconds, with a child `chat` span for the model planning the next step, an `execute_tool` span for `lookup_order`, a second `chat` span interpreting the result, an `execute_tool` span for `get_refund_policy`, a nested `invoke_agent` for a refund-calculator sub-agent with its own children, and a final `chat` span drafting the reply. [^1] The shape alone tells you the order of operations, which is most of an audit.

The spans carry typed attributes that turn the shape into evidence. An `execute_tool` span records the tool name, the exact arguments the agent constructed, and the exact result the tool returned. [^1] A model-call span records `gen_ai.request.model`, the input and output token counts, and the finish reason, whether the model stopped cleanly or because it wanted to call a tool. [^2] That last one, the finish reason, is the detail that separates a fully reasoned stop from the model bailing out to loop again. Cost attribution becomes a single sum over the trace, which matters when an audit question is "how much did this run spend." [^1]

## Replay: turning the log into a reproducible witness

Recording everything solves half the problem. The other half is that an agent's behavior is not reproducible by rerunning it. The instinct to "just set temperature to zero" fails, and it fails for a reason that is worth understanding because it is structural, not a bug you can fix. Temperature only controls the token sampling step. The logits that feed that choice are the output of billions of floating point operations on a GPU, and they are not bit-identical run to run, partly because cloud providers bundle your request onto the same GPU as other people's and the exact batch you land in changes the intermediate results, and partly because a provider's fleet spans different GPU architectures with slightly different numerics. [^4] OpenAI's seed parameter improves reproducibility but does not guarantee it, and Anthropic's documentation says even temperature zero is not fully deterministic. [^4] In other words, a failing run usually cannot be reproduced by running the agent again, no matter how you configure it.

The answer is to stop making the model repeat itself and make the run reconstructable instead. That is the deterministic replay pattern, borrowed from record-replay debugging in game engines and distributed systems. [^4] It has two modes. Record mode runs the agent normally against real models and real tools, and intercepts and logs every external interaction. Replay mode feeds those logged interactions back to the agent in exact sequence, replacing live calls with recordings. [^4] During replay you do not re-invoke the model or the tools. Proxy stubs return the recorded response verbatim when called with the same input, and if the agent reaches for a call that was not in the recording, the engine fails loudly instead of silently falling back to a live system. [^4] A replay that reproduces the run byte-for-byte, without paying a model bill or touching a live API, is a reproducible witness that no amount of "run it again" can produce.

To make replay work you record the exact request, not a template. That means the fully rendered prompt as sent, the tool schemas as sent, the resolved model snapshot, and every tool call with its arguments and its result, and for time-dependent logic you capture timestamps and random seeds because a prompt that says "today is" produces different behavior if replayed on a later date. [^4] [^10] There are two flavors. Full replay walks every step from the start, which is slow for a forty-step run if the failure is at step thirty-seven. Checkpoint replay persists the complete agent state at each step boundary so you can jump straight to any point, fork from a saved checkpoint, and try alternate inputs. LangGraph's Time Travel is the canonical example. [^4] The practical hybrid is to store the compact event log for every run and store full checkpoints only for runs that failed, tripped an alert, or were flagged for review. [^4]

Replay is not just a debugging convenience. It is the unit of audit. The Trust3 guide to agent observability makes the standard explicit: the right test of observability is whether an analyst can reconstruct what an agent did, end to end, from the record alone, without interviewing the engineer who built it. [^8] Every question, which user initiated the chain, what the original request was, which retrievals informed the reasoning, which tool call produced the action, what data moved, should be answerable from the telemetry. [^8] When it is, the audit is reproducible. When it is not, you are back to interviewing people and calling it an investigation.

## Digital forensics: treating the log like evidence

At some point the difference between good logging and audit-grade evidence becomes legal, and that is where digital forensics, the discipline built to preserve evidence from computers, has a direct method to hand to agent auditing. The NIST guide to integrating forensic techniques into incident response, SP 800-86, frames the work as a consistent four-step process: collection, examination, analysis, and reporting. [^5] For an agent, collection is the export of the trace tree under the incident's run IDs, examination is reading which steps happened and in what order, analysis is the reconstruction of cause, and reporting is the written account. That is the same arc lesson 75 gave you in the heat of the moment, now formalized as a discipline with admissibility in view.

Two forensic practices are the load-bearing ones for agents. The first is the chain of custody. NIST is explicit that when evidence may end up in legal or disciplinary proceedings, you keep a clearly defined chain of custody to avoid allegations of mishandling or tampering: log every person who handled the evidence, document the actions they performed and when, store the evidence securely, examine it only on copies, and verify the integrity of original and copy. [^5] For a trace, that means a record of who exported what, when, and to where, and an investigation that never runs queries directly against the live append-only store. The second practice is integrity hashing. Compute the message digest of the original data at the moment you collect it, store that hash somewhere it cannot be changed, work only on copies, and re-hash to confirm the values still match. [^5] A single changed bit produces a completely different digest, which is exactly the property that proves the evidence was not altered. [^5]

Apply that to an agent run and the design becomes concrete. Hash each run's trace at write time and store the hashes out of band, or write the traces to an append-only store that commits to a hash chain. Queue the export of a flagged run to read-only storage before anyone starts replaying. Log who opens it. An investigator who questions the record gets a hash that matches the hash recorded the night the run happened, which is the strongest thing an audit trail can offer: proof it is unchanged since it was written. [^5] This is also the answer to the concern from lesson 75, where a rollback before the export starts to look like spoliation. Build the hash-on-write habit and the record is already sealed before any incident starts, so there is nothing a later rollback can destroy.

## Compliance evidence: what regulators actually ask for

Auditing is not only for your own debugging. It is the mechanism by which you demonstrate compliance, and two obligations in particular give the shape concrete teeth.

The EU AI Act, in Article 12 on record-keeping, requires high-risk AI systems to technically allow the automatic recording of events, logs, over the lifetime of the system, and requires those logging capabilities to enable recording of events relevant to identifying situations that may present a risk or a substantial modification, facilitating post-market monitoring, and monitoring the operation of the system. [^6] For remote biometric identification systems it gets even more specific, requiring the usage period of each use, the reference database the system checked, the input data that produced a match, and the identities of the people who verified the results. [^6] That is an obligation aimed at high-risk systems, not at every consumer agent, but it is worth reading carefully because it is the clearest regulatory statement of what defensible agent logging looks like: automatic, continuous across the system's life, and organized around traceability. Whether or not your agent crosses the high-risk line, Article 12 is the reference shape for the record you should already be producing.

The obligation that applies far more broadly is the GDPR's accountability principle. Article 5(2) states that the controller is responsible for, and shall be able to demonstrate compliance with, the processing principles. [^7] The UK data protection authority frames accountability as two halves: be responsible, and be able to demonstrate compliance, which in practice means keeping evidence of what you did and why. [^7] Because most agents process personal data, this applies to almost every deployment, not just regulated ones. The uncomfortable implication is blunt: an organisation that follows every rule but cannot document how it followed them has not finished the job. [^7] The agent trace is that documentation. When a supervisory authority or a data subject asks what the agent did with a person's data, the trace is either the answer, complete and provably unaltered, or there is no answer.

There is a useful connection back to lesson 75. Its incident runbook ran the regulatory clock in parallel, with the EU AI Act's serious-incident reporting duty and the GDPR breach-notification window both ticking from the moment of awareness. Turn the situation around and you see why the audit record is the prerequisite for those clocks to be timeable at all. You cannot report a serious incident within fifteen days, or assess whether a breach crosses a reporting threshold, unless you can reconstruct what happened from a record that already exists. [^6] The audit system is what makes regulatory deadlines achievable instead of aspirational.

## Worked example: the order-support agent, three weeks later

Take the order-support agent from lesson 75 and move forward. It was the system that started promising bereavement-fare customers a retroactive refund that did not exist, and quietly wrote a customer's account number into a shared debug log. The incident was contained, the prompt rolled back, the forty emails un-sent in the only way they could be, with a corrective follow-up. Case closed, except it is not, because three weeks later a customer files a privacy complaint and the data protection office writes to ask for documentation of what the agent did with personal data on the night of the incident, and proof that the record has not been altered.

An operator without the audit system built in this lesson stares at the email. Lesson 75 exported a snapshot in the heat of the moment, but its completeness and integrity were never designed, they were improvisations, and three weeks of subsequent runs have flowed through the same store. Where does one night end and the next begin? What changed in the logs in the interim? How do you prove the investigation did not alter anything, when the investigation itself touched the files?

Now hand the same email to a shop that built the audit record. The response is mechanical. [^9] [^5] Pull the run's trace IDs, filtered by the affected customers, the diagnostic run, and the incident window. Reconstruct the chain from the traces: the original request, the retriever returning the false refund policy, the model call that drafted the promise, the direct-send tool call that produced the email, and the debug write that leaked the account number, every hop attached to the same trace ID. [^9] That is the collection and examination you were trained to do, now routine. Then verify integrity: recompute the message digest of each exported trace and compare it with the hash recorded at write time three weeks ago; they match, which proves the record is unchanged since the night it was made, and the chain-of-custody log shows exactly who exported it and when. [^5] Then replay the flagged run from its recorded events, stubs substituted for the live model and tools, to produce a byte-identical reconstruction without placing a single real call, proving the sequence is real and reproducible. [^4]

What you hand back is a package: the trace tree of what the agent did, the integrity hashes proving it is unaltered, the access log showing who touched it, and a replay that reproduces the run. That package answers the GDPR accountability question, here is what the agent did with this person's data, because the data protection office can satisfy itself the record is intact. [^7] It is also shaped to satisfy the traceability requirement Article 12 names, logs organized around identifying situations that presented a risk. [^6] Lesson 75 froze the evidence fast; this lesson made that freeze usable long after the page was closed.

## Build the audit system before you need it

Everything above is design work best done while things are calm. The build order is small and specific.

1. Instrument at the infrastructure layer, not in agent code. Wrap the LLM client and the tool interfaces with recording proxies so the agent's logic never knows it is being recorded, and there is no risk of an if statement skipping the important branch. [^4] [^10]
2. Give every run one trace ID and attach every model call, tool call, retrieval, and sub-agent hop to it. Without that you cannot reconstruct a chain at all. [^9] [^2]
3. Record the exact request, not a template. The fully rendered prompt, the tool schemas as sent, the model snapshot, and verbatim tool arguments and results, every time. [^10] [^4]
4. Record metadata always, content as a controlled decision. Redact prompt and tool content at the SDK or collector, because an audit log full of unredacted customer data is a second incident. [^2] [^1]
5. Write to an append-only, tamper-evident store outside the agent's control. A compromised agent that can rewrite its own audit trail has none. [^8]
6. Hash at write and store the hashes out of band. Log who accesses the record and run investigations on exported copies, never on the live store. [^5]
7. Version the trace schema so old traces stay replayable as the format evolves. [^4]
8. Set retention to the compliance windows that apply, then prove retention with the store, not a policy document. [^6] [^7]

## The pattern to take away

1. **Auditability is built at write time, not at investigation time.** If you did not record it verbatim, no forensic technique will recover it. [^1] [^4]
2. **One run, one trace ID, and every step under it.** The chain you can reconstruct is bounded by the completeness of that record. [^9] [^2]
3. **The store is append-only and outside the agent's control.** A system that can rewrite its own audit trail cannot be audited. [^8]
4. **The record is evidence only if you preserve it like evidence.** Hash at write, keep hashes out of band, work on copies, log access. [^5]
5. **Compliance is the ability to demonstrate, and the trace is the demonstration.** Article 12 names the record-keeping shape; GDPR Article 5(2) names the obligation to prove what you did. [^6] [^7]

## Try it

Take one agent you have deployed and run the audit test before you change anything else. Ask it five questions a stranger would ask: what was the exact prompt and model version of a run from two weeks ago, what tool calls happened in that run, and with what arguments and results, can you reconstruct the run without calling the model again, is the log append-only and outside the agent's control, and can you prove nothing in it was altered since it was written. Answer honestly. If any of the five is no, you have found the gap, and it is the gap this lesson closes. Then build the smallest replay for that one agent: record a single run's external interactions, replay it with stub responses, and confirm you get the same run without a live call. Finally, test the integrity story: hash one trace, flip a single byte in a copy, and confirm the digest changes. That one pairing, replay works and integrity is provable, is the entire discipline, and it fits in an afternoon.

## Summary

An agent is not a service you can restart and hope, because its failures are semantic, its control flow is chosen at runtime, and its tool calls mutate real systems. [^1] The only way to answer what it did and why is auditing the record: capture, per step, the prompts, tool inputs and outputs, token counts, latency, and the decision trace, linked by one trace ID per run. [^9] [^1] Normalize the shape with the OpenTelemetry GenAI conventions, an `invoke_agent` root span with `chat` and `execute_tool` children that name each call. [^1] [^2] Because a run cannot be reproduced by rerunning it, temperature zero does not help, turn the record into a witness with deterministic replay: record every external interaction, then replay it through stubs that return the recorded responses. [^4] Preserve that record like digital evidence, with the chain of custody and integrity hashes NIST SP 800-86 prescribes, so it survives as proof. [^5] And use it to demonstrate compliance: Article 12 of the EU AI Act names the record-keeping shape for high-risk systems and GDPR Article 5(2) requires you to be able to demonstrate compliance, for which the unaltered trace is the answer. [^6] [^7] Lesson 75 taught you to freeze the evidence fast. This lesson taught you to build the record that makes that freeze worth anything a month later.

## What's next

This lesson showed you how to audit what a single agent did: read its record, replay its run, and prove the evidence intact. Lesson 77 turns to what happens when the thing you need to audit is no longer one agent but several, passing work to each other. An agent that needs something another agent provides has to have a way to call it, a shared understanding of what the call means, and a way to find the right agent in the first place. The next lesson covers agent-to-agent communication: the protocols agents speak to pass work between them, the contracts that define what each side promises and what is delivered, and the discovery mechanisms that let one agent find another capable of a task. The trace ID and the replay discipline you built here become both harder and more important when the run you are reconstructing spans several systems.
