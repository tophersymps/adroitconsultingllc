# Lesson 29: Compliance: Data Residency, Audit Logging, and Retention for AI Systems

Lesson 28 showed you how to gate an agent: prove who is acting and stop it from doing more than it is allowed. Security is the door. Compliance is the logbook that sits beside the door, and it answers a different set of questions. Where did the data the agent touched actually live? What exactly did the agent do, in what order, with which inputs? And once the work is done, how long does any of it stay on disk? Those three questions are the whole of this lesson.

The one idea to carry out of it: **an agent becomes defensible in front of a regulator only when three separate controls are in place. Data residency decides where data is stored and how it may cross borders. Audit logging keeps an unalterable record of every action so the past can be reconstructed. Retention puts a clock on that record, because keeping data forever is itself a compliance failure.** Lesson 20 gave you observability, the ability to see what your agent did for debugging. This lesson is the difference between a record you read to fix a bug and a record you hand to an auditor.

## What compliance means for an agent

Compliance is the discipline of being able to prove, after the fact, that you did what the law requires. For an AI system the law in question is usually one of three things: a data protection regime like the GDPR, an AI-specific regime like the EU AI Act, or an industry code such as a banking or healthcare standard. They overlap, and they all converge on the same three obligations.

Data residency is about geography. An agent touches data in many places: the model provider's inference endpoint, the vector database behind its retrieval, the observability backend that stores its traces, the logs themselves. Every one of those is a location where data is stored or processed, and every one of them has to be legal.

Audit logging is about reconstruction. If an agent made a decision that harmed someone, can anyone show how it got there? The EU AI Act frames this as traceability, and it is the reason regulators care about logs at all. A system that cannot explain its own past is a system whose past cannot be audited.

Retention is about time. Data protection law does not let you keep personal data forever, but audit requirements sometimes need records to survive for years. The design problem is reconciling the two. You will spend most of your compliance energy on that single tension.

## Data residency: where the data actually goes

Data residency is the requirement that certain data be stored and processed in specific geographic locations, decided by the laws of the country where the data subject lives. It is easy to misunderstand, because the two big examples go in opposite directions.

The GDPR does not require data about EU residents to be stored inside the EU. What it requires is that any transfer of personal data out of the EU happens under one of a limited set of legal mechanisms: a destination country that offers an adequate level of protection, or appropriate safeguards such as Standard Contractual Clauses (SCCs) or Binding Corporate Rules (BCRs). [^4] So the rule is not "keep it in Frankfurt." The rule is "if it leaves, make sure the transfer is legal." For an AI system that means the training data, the prompts, and the generated outputs all have to respect those transfer rules, because all of it counts as processed personal data. [^4]

China's PIPL goes the other way. It generally requires personal data gathered from individuals in China to be stored within the country's borders, and it subjects cross-border transfers to strict limitations and security assessments. [^4] Same goal, opposite mechanism. The GDPR allows the data to move if you satisfy the conditions. PIPL keeps it home by default.

Here is what that means for an agent you are deploying. "The cloud lets me pick an EU region" is the start of the answer, not the end. Every system that touches the data is a jurisdiction: the model provider that processes the prompt, the vector database that stores the embeddings, the trace store that keeps the observability records. If any one of those processes or stores data in a country the law does not allow, the choice of region on the front end does not save you. The practical habit is to inventory every data touchpoint in the agent's path and ask, for each one, where the bytes land and under what legal basis. Keeping data inside fewer jurisdictions also reduces exposure to AI-specific regulation, because fewer third parties and fewer cross-border flows touch the system. [^4]

## Audit logging: from observability to accountability

Lesson 20 built observability: traces, logs, and replay so you can debug a live agent. Compliance asks for something stronger. An observability log is a working tool. An audit log is evidence. The same underlying record serves both, but the audit version has requirements the debugging version does not: it must be automatic, it must be complete, and it must survive as written.

The EU AI Act makes this concrete for high-risk AI systems. Article 12 requires that high-risk systems technically allow the automatic recording of events, logs, over the lifetime of the system. [^1] The logging has to be capable of recording what is needed for three things: identifying situations where the system presents a risk or has been substantially modified, facilitating post-market monitoring, and monitoring the operation of the system. [^1] For the high-risk categories listed in Annex III, the logs must capture, at a minimum, the period of each use (start and end date and time), the reference database the input was checked against, the input data that produced a match, and the identities of the natural persons involved in verifying the results. [^1]

Read that list as a design spec for an agent. The agent version of "input data" is the prompt and the context it retrieved. The agent version of "reference database" is the knowledge base or retrieval store it checked. The agent version of "identities involved in verification" is the human-in-the-loop reviewer from lesson 25, and their name needs to be in the record. Article 12 does not say "store the full conversation forever." It says record the events that let you reconstruct what happened, per action, automatically.

The governance side of this lands in the NIST AI Risk Management Framework. The AI RMF is a voluntary framework, released in 2023, built on four functions: Govern, Map, Measure, and Manage, meant to improve an organization's ability to incorporate trustworthiness considerations into the design, development, use, and evaluation of AI systems. [^3] Accountability lives in the Govern function, and it is exactly the traceability thread: roles, responsibilities, documentation, and audit trail. [^3] The framework does not tell you which logger to buy. It tells you that accountability is a design function, not a postscript.

The distinction from lesson 20 is worth making sharp. Observability answers "what happened and why" so you can fix it. Audit logging answers "what happened, permanently and unalterably" so you can be accountable for it. Build the trace for debugging. Keep an append-only, time-ordered copy of the events for the record. The two can be the same data written to two different places with different write policies.

## Retention: the clock on the record

Retention is governed, for personal data, by the GDPR's storage limitation principle. Article 5(1)(e) says personal data must be kept in a form which permits identification of data subjects for no longer than is necessary for the purposes for which it is processed. [^2] The same article pairs it with data minimization, which says data must be adequate, relevant, and limited to what is necessary, and with accountability, which makes the controller responsible for demonstrating compliance. [^2] Three principles, one sentence of intent: keep less, keep it for a reason, and be ready to show why.

This is where the tension lives. The AI Act wants logs kept so the past is reconstructable. The GDPR wants personal data deleted as soon as it is no longer needed. The resolution is not a compromise that keeps everyone slightly unhappy. It is a distinction between the record and the payload. You retain the metadata that proves compliance: who acted, when, which tools, which model version, which database, what decision. You do not retain, or you retain for only a short window, the full prompt, the full retrieved context, and the raw personal data the agent processed. The audit trail stays intact. The personal data inside it gets a short lease.

Set a retention schedule and automate it. Decide the minimum duration your audit obligations require, the maximum the data protection law allows, and build deletion into the pipeline so the data expires without a human remembering to delete it. A retention policy that depends on someone running a script by hand is a policy that will be violated. The same logic applies to training data and vector stores, where stale personal data can linger in model weights or embeddings long after the source record was deleted.

## Worked example: an auditable agent trail

This is not abstract at Adroit. The Fortress runs Hermes agents, and the Hermes event-hook system gives a concrete picture of what an audit log for an agent actually looks like. Gateway hooks fire automatically as an agent works, without blocking the agent's pipeline. The events include `agent:start`, fired when the agent begins processing a message, `agent:step`, fired on each iteration of the tool-calling loop, and `agent:end`, fired when the agent finishes. [^5]

A hook is a small handler that appends one JSON record per event to a log file, with a timestamp and the event's context: which session, which user, which tools ran on which iteration. [^5] That is the audit trail in its most basic and correct form: a per-action, time-ordered, append-only record of what the agent did. Outbound webhooks push signed lifecycle events to an external endpoint, which is how you get the record off the agent's machine and into a store that an investigator cannot reach by talking to the agent. [^5]

Three choices make that working log into a compliance-grade trail. Write the record to an append-only or write-once store so the agent, or an attacker who compromises it, cannot rewrite its own history. Keep the payload lean, timestamps, event type, session id, tool names, model version, decision, and keep personal data out of it, so the record is defensible under data minimization. Attach a TTL or an archive job so the record follows the retention schedule instead of growing forever. The integration point matters too. Hermes can export traces, metrics, and logs to an external backend, which is how the observability stream from lesson 20 and the audit trail here flow into the same place. [^6]

## The pitfalls to avoid

The first is logging the thing you were supposed to protect. An audit log that stores full prompts and raw personal data violates data minimization the moment it is written, and it recreates the residency problem in a second store. Log the metadata that proves compliance, not the payload that exposes people.

The second is treating the region picker as a residency solution. The cloud region is one touchpoint. The model provider, the vector store, the trace backend, and the audit store are all locations too, and each needs its own answer. [^4]

The third is an audit log the agent can edit. If the system that produced the record can also rewrite the record, the record proves nothing. Make the trail append-only and store it where the agent cannot reach it. [^5]

The fourth is the retention pendulum swinging all the way in either direction. Keeping everything forever violates storage limitation. Deleting everything quickly destroys the audit trail the AI Act asks for. [^2] The middle, and the correct, position is keep the metadata for the audit horizon, delete the personal payload on a short automated schedule.

## Try it

1. **Map the data touchpoints.** Take an agent you have deployed and list every system that stores or processes data: model provider, vector database, trace store, log store. For each, write down the country where the bytes land and the legal basis for data from the region you serve. Mark any touchpoint that crosses a border without a mechanism such as SCCs or BCRs. [^4]

2. **Write the per-action log.** Add a hook or middleware that records one event per agent action: timestamp, session id, tool name, model version, and decision. Confirm it is append-only and time-ordered. If you already built the trace in lesson 20, keep this as a separate append-only copy of the event stream. [^5]

3. **Set the retention clock.** For your audit log, write down the minimum retention your obligations require and the maximum the data protection law allows. Then implement an automated deletion that expires the log's payload on that schedule, while keeping the metadata. [^2]
