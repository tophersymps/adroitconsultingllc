# Lesson 8: Designing Tools That Fail Well: Schemas, Error Handling, and Retries

Lesson 7 showed you how the model *proposes* tool calls. This lesson is about the tools themselves: what separates a demo tool from a production tool is not the happy path; it's how the tool behaves when something goes wrong. Enterprise agents are connected to production systems, and a vague schema or a blind retry can cause wrong reports, duplicate orders, or operational disruption. [^1]

The one idea to take from this lesson: **a tool schema is an operational contract between the model, your application layer, and the system being accessed**, and the error path is part of that contract, not an afterthought. [^1]

## The anatomy of a production tool

Most platforms follow the same core pattern: the model receives a list of available tools, each with a machine-readable schema; when it needs external data or an action, it returns a structured tool call instead of text; your application executes the call and sends the result back. [^1]

A high-quality schema has five parts:

1. **Tool name.** Action-based and namespaced. `get_data` is a coin flip for the model; `crm_get_customer_profile` tells it the system (CRM), the action (get), and the target (customer profile) in one string. In enterprise environments one agent may have tools across CRM, ERP, helpdesk, and analytics, so namespacing is a selection strategy, not cosmetics. [^1]
2. **Description.** What the tool does, when to use it, *when not to*, and what it returns. Weak: "Gets customer data." Strong: "Retrieves a customer profile from the CRM using a verified customer ID. Use this tool when the user asks about account details, lifecycle stage, assigned owner, or customer status. This tool does not return billing data or support tickets." That last sentence is what prevents misuse. [^1]
3. **Input schema.** What the model must send. This is where most tool-calling failures happen.
4. **Output schema.** What the tool returns, designed so the model can decide the next step.
5. **Error schema.** How the tool reports failure in a way the model can recover from.

## Designing inputs that remove ambiguity

Vague inputs cause the model to omit required fields, invent unsupported parameters, or pass values in the wrong format. A strong input schema uses specific field names, narrow data types, enums for controlled values, stated units and formats, required/optional markers, and validation constraints. [^1]

```json
{
  "type": "object",
  "properties": {
    "customer_id": {
      "type": "string",
      "description": "The verified CRM customer ID. Do not use customer name, email, or company name here."
    },
    "activity_type": {
      "type": "string",
      "enum": ["all", "sales_call", "email", "meeting", "support_note"],
      "description": "Use 'all' when the user does not specify an activity type."
    },
    "date_from": {
      "type": "string",
      "description": "Optional start date in ISO 8601 format, YYYY-MM-DD."
    },
    "max_records": {
      "type": "integer",
      "description": "Maximum records to return. Defaults to 10. Maximum allowed is 50."
    }
  },
  "required": ["customer_id"],
  "additionalProperties": false
}
```

Two details carry most of the weight. **Enums** constrain the model to values your backend actually understands; "all" beats a free-text string the parser has to guess at. **`additionalProperties: false`** rejects invented fields; combined with validation on your side, it turns a model mistake into a clean, catchable error instead of a silent backend bug. [^1] [^2]

A second, subtler rule from OpenAI's docs: **offload arguments from the model to code when you already know them.** If your application already holds an `order_id` from a prior step, don't make the model fill it in; define `submit_refund()` with no parameters and pass the ID in code. Every argument you remove is a hallucination you prevent. [^2]

## Designing outputs the model can reason about

The output schema is under-designed more often than the input schema, and it directly affects agent reasoning. A poor output dumps raw backend data; a strong output answers four questions: Did the tool succeed? What important data came back? What should the model do next? Does the user need to provide anything else? [^1]

Practical rules: include a `status` field, stable identifiers (IDs, not display names), only the fields needed for the next step, and a summary when result sets are large: a "returned 10 of 24 records" summary plus a one-line synthesis beats 24 raw rows. [^1] This aligns with Anthropic's guidance to return high-signal output with semantic, stable identifiers so the model can reason about the next action. [^3]

## Error schemas: make failure actionable

The cardinal rule: **never return a raw stack trace to the model.** Vague or overly technical error messages are unhelpful; the model needs to know what happened, whether it can recover, and how. A structured error should include an error type, a human-readable message, a recoverability flag, a retry hint, and an optional escalation path. [^4] [^1]

```json
{
  "status": "error",
  "error": {
    "code": "MISSING_REQUIRED_FIELD",
    "message": "customer_id is required.",
    "recoverable": true,
    "retry_hint": "Ask the user for the customer ID or use a customer lookup tool first."
  }
}
```

The `recoverable` flag is the load-bearing piece: **each error should tell the model whether the issue is recoverable; if it is, provide a retry hint; if not, provide a safe user-facing explanation.** [^1]

The common error types you should classify: validation errors (missing/malformed/unsupported fields), permission errors, not-found errors, conflict errors, rate-limit errors, timeouts, and policy errors (business, legal, or security violations). Two more practices from the same playbook: **validate inputs proactively** before any external call so malformed input becomes a clean error instead of an obscure downstream failure, and **translate HTTP codes**: a 401 from an API should surface to the model as "access to [service] was denied; the API key may be invalid or expired," not as a bare status number. [^4] While the model gets friendly structured errors, log the full technical detail (stack traces, timestamps, input context) for developers; the LLM-facing message and the developer log are two different artifacts. [^4]

## Retries: agent retries are not HTTP-client retries

This is where naive engineering gets expensive. The retry patterns that work for an HTTP client (exponential backoff, retry on 5xx, give up after three attempts) **do not translate directly to agent tool calls**, for three reasons. [^5]

1. **Tool calls are often not idempotent.** A `GET /patients/:id` is safe to retry; a `POST /orders` is not. Most network timeouts are on the *response*, not the action; the server processed the request and the reply was lost. Retrying without protection creates two orders for one customer. [^5]
2. **The agent loop adds a higher retry layer.** When a tool fails, the agent can re-plan and choose a different tool. Re-planning on every failure burns tokens; never re-planning gets stuck. The right pattern depends on the tool and the failure mode. [^5]
3. **Retries cost real money.** A turn that retries twelve times on a misconfigured tool can spend $5 on a request that should have cost $0.40. Anthropic's production guidance is blunt: "The autonomous nature of agents means higher costs, and the potential for compounding errors." [^5] [^6]

### Classify: transient vs permanent

Before deciding to retry, classify the failure. The decision should be mechanical, not per-tool guesswork:

| Response | Class | Action |
|---|---|---|
| 2xx | success | record, advance |
| 400, 401, 403, 422 | permanent | escalate or re-plan |
| 404 | usually permanent | re-plan (planner likely chose the wrong ID) |
| 408, 429, 500, 502, 503, 504, connection errors | transient | retry with backoff; honor `Retry-After` on 429 |
| LLM tool-call schema violation / hallucinated tool name | permanent | **re-plan, do not retry verbatim** |

A schema violation is permanent on the literal call but transient at the agent level: retrying the same prompt produces a similar malformed call, so the right move is re-plan with the error appended to context. [^5]

### Backoff with jitter, and a budget

Once you've decided to retry, use **exponential backoff with full jitter**, capped. Exponential growth spreads retries across time so a fleet doesn't synchronize and hammer a recovering service; jitter randomizes the delay; a cap prevents unbounded waits. [^5] The canonical reference for full jitter is AWS's "Exponential Backoff And Jitter" post. [^7]

Then add a **retry budget per turn**: a turn-level counter, decremented on transient failures only, that hard-stops the agent at zero and produces a graceful response instead of a runaway loop. Practical starting points: 6 retries for a typical task agent, 3 for a high-cost agent, 10 for a low-stakes assistant; tune from your own observability. [^5]

### Idempotency keys for write tools

The first pattern to add to any tool that mutates state is an **idempotency key**, the pattern Stripe's API made canonical. The agent derives a stable key (e.g., a hash of turn ID + tool name), passes it on every call, and the server returns the same response for the same key within a window (24 hours is Stripe's default). A retry against the same key returns the first result; the duplicate write never happens. Two rules: derive the key from the turn, not a fresh UUID per call (a fresh UUID defeats the purpose), and apply the same key shape to *every* state-mutating tool; a mixed system is the failure mode hiding in plain sight. If an upstream API has no idempotency support, treat it as a permanent flaw: request the feature or wrap it in your own idempotency proxy. [^5] [^8]

### When writes partially succeed: compensating transactions

The hardest pattern: `CreateOrder` succeeds, `ChargeCard` fails permanently. Retrying the sequence creates a second order; failing the turn leaves an orphan. The answer is the **compensating transaction (Saga) pattern**: each step has a paired undo step (`cancel_order`, `refund_charge`), run in reverse order on failure. Compensations are themselves idempotent so they can be safely retried. If you cannot ship compensations (no cancel endpoint on a third-party API), the agent should not be doing multi-step writes; move the sequence to a server-side workflow and expose it as a single tool. [^5] [^9]

Finally, choose *when* to retry silently vs surface to the user: silent retry is correct for fast read tools on transient errors with budget intact; surface progress for long-running calls; ask the user on ambiguous failures; hard-stop with a graceful message on permanent failures after retries are exhausted, and never silently retry a write without an idempotency key. [^5]

## Worked example: the Fortress publish pipeline

This isn't abstract at Adroit. The Fortress runs Hermes agents whose tools (`web_search`, `write_file`, `patch`, `terminal`) are defined by JSON schemas in a built-in registry, organized into toolsets you enable per platform. [^10] Publishing this very lesson is a real multi-tool sequence: `git pull --rebase origin main`, `git add`, `git commit`, `git push`. The reason this pipeline retries safely is that **git's ref updates are naturally idempotent**: a push that times out and is retried converges to the same commit. That's the property to look for: if a retry can't change the outcome, retrying is free.

Contrast it with the Fortress's kanban gate from Lesson 7, where a local Qwen model began emitting empty `{}` objects for tool-call arguments: a schema violation. Per the classification table, that's a *permanent* failure on the literal call: the right response was not to retry the same request, but to add a validation gate and re-plan, which is exactly the layer that now catches it. [^11] The generalization: **classify before you retry, and make writes idempotent before you allow retries at all.**

## The pitfall to avoid

Treating every failure the same way: "just add retries." Blind retries on non-idempotent writes create duplicate orders; retrying schema violations burns tokens on a call that will fail identically; constant backoff with no jitter synchronizes your whole fleet against a recovering service. [^5] And on the schema side, the mirror-image pitfall is returning raw backend errors to the model; an error the model cannot act on is a failure with no recovery path. [^4]

## Try it

1. **Design one tool end-to-end.** Pick a read operation you already have (e.g., a customer lookup) and write the full five-part schema: namespaced name, 3–4 sentence description with "when not to use", narrow input schema with enums and `additionalProperties: false`, high-signal output with `status`, and a structured error schema with `recoverable` + `retry_hint`. [^1]
2. **Build the classification table into your dispatch layer.** Return structured errors from your tools, then have the dispatcher classify each failure as transient/permanent and route it: backoff+retry (transient), re-plan with error in context (schema violation), or escalate (permanent). Log every classification. [^5]
3. **Add an idempotency key to one write tool** (or wrap a third-party API that lacks one) and verify with a simulated timeout that the second call returns the first call's result instead of executing twice. [^8]

## What's next

You now know how to design a tool that fails well. Lesson 9 is the portability layer: function-calling parity across providers. The same tool schema behaves differently on OpenAI, Azure, Anthropic, Gemini, and local models, and each has quirks in how it names, formats, and invokes functions. You learn to write schemas once and translate them so your agent is not locked to a single vendor.
