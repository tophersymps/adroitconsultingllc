# Lesson 7: Structured Output: JSON Mode, Function Calling, and Tool Schemas Done Right

Lessons 1–6 gave you the loop, the prompts, the token economics, and the model tiers. This lesson is where an agent actually *does* something: emit data your code can consume and call tools your code can run. Both depend on one skill: getting the model to produce output that fits a contract. If you take one idea from this lesson, take this: **the model proposes, your code disposes.** It never executes anything; it only produces structured data that you validate and act on.

Everything in the first six lessons has been building toward this one. A model tier you can route to is only useful if the model returns data your code can parse. An agent loop is only reliable if the model's tool calls land in the right shape. This lesson is the bridge: it turns the model from something that generates text into a component your code can depend on. The entire discipline reduces to one reframe, which is the sentence in bold above. The model is not the actor. It is a proposal generator. Your code is the actor, and it should treat everything the model produces as a proposal to be validated, not a command to be obeyed. Internalize that and the rest of the lesson is mechanics.

## Why "just ask for JSON" fails

LLMs predict the most likely next token. That works for prose; it is unreliable for data. Vellum shows why with a real support-triage prompt: "Create a JSON with the following schema … Please respond with JSON only, nothing before nothing after!" The model wraps the JSON in markdown code fences, because in training it saw JSON inside ``` fences far more often than bare JSON. [^1]

That's not a dumb model, it's statistics, and it's why every major provider now ships machinery that constrains the output distribution directly. Agenta draws the same comparison: **API-native** structured output (built into the provider) versus **non-API-native** (prompting plus regex or parser cleanup). API-native is the only approach that survives model updates; prompting hacks "work temporarily but break when models change or edge cases appear." [^2]

The markdown-fence failure is the perfect illustration of why prompting is the wrong tool for this job. The model is not being stubborn or literal-minded; it is doing exactly what it was trained to do, predicting the next most likely token, and statistically, JSON inside code fences is far more common in its training data than bare JSON. Your prompt tells it to emit bare JSON, but the prior is overwhelming, so it wraps the output in fences anyway. You can fight this with stronger prompts, but you are fighting statistics with words, and statistics usually win, especially when the model or its training changes out from under your carefully tuned prompt.

That instability is the deeper problem with non-API-native approaches. A regex or parser cleanup that strips code fences might work beautifully today, against this model, with this prompt. Then the provider updates the model, or you change the prompt slightly, and the output drifts: extra prose, renamed keys, a stray sentence. Your parser breaks silently, and you only notice in production. API-native structured output, by contrast, constrains the output *distribution itself* inside the provider, so the model physically cannot produce output that violates the constraint. It is not a parser patch; it is a guarantee about the generation process, and it survives model updates because the constraint is enforced by the machinery, not by a prompt that the model can ignore.

## The terms, precisely

Three knobs, in increasing order of strictness, plus one contract format underneath all of them.

**JSON mode** is a provider flag that forces the response to be valid, parseable JSON. It does *not* guarantee any particular shape. OpenAI's docs are explicit: "JSON mode will not guarantee the output matches any specific schema, only that it is valid and parses without errors." [^3]

**JSON Schema** is the contract itself: a specification for describing the structure and validation rules of JSON data (required fields, data types, value constraints, and nesting). [^2] A minimal example:

```json
{
  "type": "object",
  "properties": {
    "name": {"type": "string"},
    "age": {"type": "integer", "minimum": 0},
    "email": {"type": "string", "format": "email"}
  },
  "required": ["name", "age"],
  "additionalProperties": false
}
```

**Structured Outputs** is schema-enforced generation: you supply a JSON Schema and the provider guarantees the output adheres to it, so you "don't need to worry about the model omitting a required key, or hallucinating an invalid enum value." [^3]

**Function calling** (a.k.a. tool calling) is the strongest form: the model doesn't just format data; it *selects* a tool from a list you define and emits the arguments for it, matching that tool's input schema. [^4]

The decision rule, straight from the docs: if you're connecting the model to tools, functions, or data in your system, use **function calling**; if you want to structure the model's final answer to the user, use **Structured Outputs via a response format**. And on the ladder itself: "We recommend always using Structured Outputs instead of JSON mode when possible." [^3] [^1]

### The rung you actually need

The ladder from JSON mode up to function calling maps directly onto the reliability spectrum from Lesson 6, and it is worth internalizing *why* each rung sits above the last. JSON mode only guarantees parseability. It will happily return valid JSON with the wrong keys, the wrong types, or an extra top-level field, because validity is all it checks. If you only need "is this JSON," JSON mode is enough, but "is this JSON" is rarely the real requirement.

JSON Schema is not a provider knob at all; it is the vocabulary both Structured Outputs and function calling use to describe what "correct" means. The example schema above says: an object with `name` (a string), `age` (an integer of at least 0), and `email` (a string in email format), where `name` and `age` are required and no other properties are allowed. That is the contract. Structured Outputs takes that contract and makes the provider enforce it during generation, so you do not need to worry about a missing required key or an invalid enum value, the provider refuses to produce them.

Function calling sits on top of that contract and adds selection: the model does not just format data according to a schema, it chooses *which* schema to use, meaning which tool to call, from a list you defined, and emits arguments matching that tool's input schema. That is why it is the strongest rung: it combines the format guarantee with a decision about which tool fits the current situation. Every rung below it formats data; only function calling chooses an action. That distinction is exactly the "tools are what make it an agent" property from Lesson 1, expressed at the output level.

The decision rule removes the guesswork. If the model needs to reach into your system, call a function, query data, or invoke a tool, use function calling, because the output is an action to execute, not an answer to display. If the model's final output is something you will show to a user or store as a structured record, use Structured Outputs via a response format, because you want shape guarantees without the action semantics. And whenever the choice is between JSON mode and Structured Outputs, prefer Structured Outputs, because it is strictly more constrained and therefore strictly more reliable, at no cost to you.

## How tool calling actually works

Tool calling is a multi-step conversation, not a single request. OpenAI's guide lays out five steps: (1) request with tools defined, (2) receive a tool call from the model, (3) execute the code on your side with the call's input, (4) send the output back to the model, (5) receive the final response, or more tool calls. [^4]

Anthropic's round trip is the same shape: the response carries a `tool_use` block naming the tool and its arguments, your application runs the lookup, and a second request sends the result back in a `tool_result` block so the model can finish answering. [^5] The critical fact for beginners: in every provider's model, the model only *proposes* the call. Your code executes it and decides what to do with failures.

It is worth walking the five steps slowly, because the common mental model is wrong. Most beginners imagine tool calling as a single request where the model "does" something. It does not. The model never touches your system. Step one, you send a request that includes the tools you are making available, each with its schema. Step two, the model responds not with an action but with a tool call: a data structure naming a tool and the arguments it wants to pass. Step three, *your code* actually executes that call against your real system. Step four, you send the result back to the model as context. Step five, the model produces its final response, or, if it needs more information, it emits another tool call and the cycle repeats.

The two providers express the same shape differently, and seeing both is useful. OpenAI frames it as a numbered sequence ending in a final response or more tool calls. Anthropic's framing is block-based: the model's response carries a `tool_use` block (which tool, what arguments), your application runs the lookup, and the next request carries a `tool_result` block with the outcome, so the model can incorporate it and continue. Different vocabulary, same contract: the model proposes, your code executes, and the result is fed back so the loop can continue. The architecture is identical because it is the only shape that keeps the model safely at arm's length from your systems.

The critical fact bears repeating because it is the safety property that makes everything else in this lesson work: the model only ever *proposes* a call. It cannot execute anything, because it has no execution capability; it produces data. The moment your code decides to act on that data is the moment you are in control, and with control comes the responsibility to validate before you act. That is why the validation layer in the pitfall section is not optional: the model's proposal is very good most of the time, and exactly wrong sometimes, and your code is the only thing standing between a bad proposal and a bad side effect.

## Tool schemas done right

Schema design is where reliable agents are won or lost, and Anthropic's guidance is the best published playbook:

- **Descriptions are the single most important factor.** Aim for 3–4 sentences per tool: what it does, when to use it (and when not to), what each parameter means, and limitations. [^6]
- **Consolidate related operations.** Instead of `create_pr`, `review_pr`, `merge_pr` as three tools, use one tool with an `action` parameter; fewer, more capable tools reduce selection ambiguity. [^6]
- **Namespace tool names** across services (`github_list_prs`, `slack_send_message`) so selection stays unambiguous as the tool library grows. [^6]
- **Return high-signal output:** semantic, stable identifiers (slugs, UUIDs) and only the fields the model needs to reason about the next step; bloated tool results waste context. [^6]
- **Add `strict: true`** to tool definitions to guarantee calls match the schema exactly. [^6]
- **Control selection with `tool_choice`**: `auto` (model decides), `any` (must use a tool), `tool` (force a specific tool), `none` (no tools). [^6]

The ordering in that list is deliberate, and the first bullet is the one people most often skip, so it deserves the emphasis it gets. The tool's *description* is how the model knows when to reach for it, and a thin description is how the model reaches for the wrong tool, or reaches for the right tool with the wrong arguments. A 3 to 4 sentence description covers what the tool does, when to use it, when *not* to use it, what each parameter means, and its limitations. That last item, limitations, is the one most descriptions omit, and it is exactly what prevents the model from using a tool beyond its competence. Writing good descriptions is cheap and it is the highest-leverage thing you can do for tool-call reliability.

Consolidating related operations is a subtle fix for a real failure mode. Three tools, `create_pr`, `review_pr`, `merge_pr`, force the model to pick between three similar options, and similarity breeds ambiguity: which one fits this exact request? Collapsing them into one tool with an `action` parameter removes the ambiguity at the source, because now there is only one tool to select, and the action is a single enum value inside it. Fewer, more capable tools mean the model spends its effort on the right action, not on disambiguating near-identical tool names. Namespacing solves the related growth problem: as the library grows, `github_list_prs` and `slack_send_message` cannot be confused the way two generic tools with overlapping names can. Uniqueness of selection scales with clarity of naming.

The remaining items are the reliability guardrails. High-signal output means the tool returns semantic, stable identifiers and only the fields the model needs for its next decision, so tool results do not bloat the context window or distract the model with irrelevant detail. `strict: true` upgrades the schema guarantee so calls must match the schema exactly. And `tool_choice` gives you control over *whether* and *which* tool gets used: `auto` lets the model decide, `any` forces a tool call, `tool` pins a specific tool, and `none` disables tools for this request. Together they let you tighten or loosen the model's discretion to match the reliability you need for a given step.

One cost reality to design around: tool definitions ride in every request's prompt. Anthropic documents a per-model tool-use system-prompt overhead on top of your own tokens: for example, on Claude Opus 5 at the time of writing, roughly 286 tokens with `auto`/`none` and 406 with `any`/`tool`. *Note: these figures rotate with model generations; check the current tool-use docs before budgeting.* [^5]

The cost reality is easy to overlook because it is invisible. Every request that makes tools available pays a fixed overhead: the tool definitions themselves, plus a system prompt the provider injects to make tool use work, all ride in the prompt on top of your own tokens. That overhead exists whether the model actually calls a tool or not, and it scales with the number and size of your tool definitions. Bloated schemas and over-long descriptions are not free; they are token costs on every single request in the loop. Design your tool set lean, and check current token figures before budgeting, because the exact numbers rotate with model generations.

## Worked example: the Fortress runs on schemas

This isn't abstract at Adroit. The Fortress runs Hermes agents, and every tool I use to write this lesson (`web_search`, `write_file`, `patch`, `terminal`) is defined by a JSON schema: a name, a description, and a `parameters` object with types and required fields. The Hermes registry ships 60+ built-in tools like this, organized into toolsets you can enable per platform. [^7]

This is the concrete payoff of the tool-schema discipline, applied at scale. Every tool the agents call is not ad-hoc code; it is a registered schema entry with a name, a description, and a `parameters` object declaring types and required fields. The description tells the model when to use the tool, and the parameters schema tells it what shape of arguments the tool accepts, which is what lets function calling work at all. The registry organizes 60+ tools into toolsets that you enable per platform, so an agent only sees the tools relevant to its platform, which keeps the tool-selection surface small and the per-request token overhead bounded.

The schema discipline earns its keep in failures, and we have a real one. Lesson 6 documented how a local Qwen model (llama.cpp, port 8080) began emitting empty `{}` objects for nested tool-call arguments, silently breaking the kanban completion gate: tasks could never validate complete. Free-text reasoning stayed correct; structured tool-call JSON was broken. [^8] The takeaway generalizes: **schema conformance is a model capability, not a prompt artifact.** Some models guarantee it (Structured Outputs, `strict: true`), some don't, and anything that doesn't gets a validation layer in front of it.

The failure is worth dwelling on because of what it reveals. The model did not fail catastrophically; it failed in the narrow, quiet way that is most dangerous. Its free-text reasoning, the part you would naturally test first, stayed correct. Only the structured tool-call arguments degraded, and they degraded into empty `{}` objects that still looked like valid JSON, so nothing screamed. The kanban completion gate silently could not validate tasks, and the pipeline wedged. A prompt change would not have fixed this, and this is the generalizable lesson: whether a model emits schema-conforming output is a *capability* of that model, not a product of how well you phrased your prompt. Models that guarantee conformance (Structured Outputs, `strict: true`) enforce it in the generation machinery; models that do not offer that guarantee must have a validation layer in front of them, because their conformance can silently break.

## The pitfall to avoid

Treating "valid JSON" as "correct output." JSON mode guarantees parseability and nothing else; you must still validate against your schema (Pydantic in Python, Zod in TypeScript, or a plain JSON Schema validator), and you must handle the two non-completion cases the APIs explicitly surface: truncation (`max_output_tokens`) and safety refusals. OpenAI's Structured Outputs docs walk through checking response status and refusal fields before trusting the payload. [^3] An unvalidated tool-call argument is a bug waiting for a production incident.

The pitfall is the gap between "parses" and "is correct," and it is a wide one. Valid JSON can still have the wrong keys, the wrong types, a missing required field, or an invalid enum value; JSON mode will happily produce all of those, because it only guarantees parseability. The fix is validation: run every model output against your schema before you act on it, using Pydantic in Python, Zod in TypeScript, or a plain JSON Schema validator. This is the "your code disposes" half of the opening sentence, and it is not optional.

The two non-completion cases are the ones even careful teams forget. A request can come back truncated if it hits `max_output_tokens`, producing output that cuts off mid-structure. And a request can be a safety refusal, where the model declines and returns a refusal rather than the structured data you asked for. Both look like completions at a glance, and both are full of traps if you trust the payload blindly. The provider docs walk through checking the response status and the refusal fields before trusting the output, and you should do the same. An unvalidated tool-call argument is not a quality nit; it is a bug waiting for a production incident, because it is exactly the seam where a bad proposal becomes a bad side effect.

## Try it

1. **Extract with a schema.** Define a Pydantic or Zod model for a support ticket (`priority` as an enum, `description` as a string, `created_at` as a string), call a Structured Outputs endpoint with it, and observe that you never receive invalid JSON: no fences, no renamed keys. [^2]
2. **Test description quality.** Define the same tool twice: once with a one-line description, once with a 4-sentence description covering when to use it and what each parameter means. Run 20 prompts and compare how often the model calls the right tool with the right arguments. [^6]
3. **Add a validation gate.** Before executing any tool call in your agent loop, validate the arguments against the tool's input schema and log every rejection. This is the layer that would have caught the Fortress's empty-`{}` failure the moment it started. [^8]

Each exercise converts one idea from this lesson into hands-on experience. The extraction exercise proves to you that schema-enforced generation actually works, that a Structured Outputs endpoint really never returns fences or renamed keys, which replaces a belief with a fact. The description-quality test is the empirical version of the strongest claim in the tool-schema section: better descriptions measurably improve tool-selection accuracy, and you can see the difference in 20 runs. The validation gate exercise is the one that builds the production habit, a gate before every tool call that validates arguments and logs rejections, which is precisely the layer that would have caught the Fortress's empty-`{}` failure on its first occurrence instead of after the pipeline wedged.

## What's next

You can now make models emit contracts and call the tools you define. Lesson 8 makes those contracts do real work: tool calling, designing tools and their schemas so the model knows when and how to call them, and building error handling and retries so a failing tool fails well instead of silently. Structured output gets the model to speak your format; tool calling is how it reaches out and acts on the world.

There is a clean division between this lesson and the next, and it is the same division as "emit a contract" versus "do work." This lesson built the output machinery: getting the model to produce data that fits a schema and to select and format tool calls. Lesson 8 is where that machinery gets pointed at the world: designing the tools themselves so the model knows when and how to call them, and building the error handling and retries so that when a tool fails, it fails well, loudly, and recoverably, instead of silently corrupting the loop. The proposal machinery is in place; next you make the actions reliable.
