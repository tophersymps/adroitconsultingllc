# Lesson 51: Agent Identity: OAuth, Service Accounts, and Scoped Permissions

Lesson 50 protected the people whose data an agent holds. This lesson protects the systems the agent touches, by proving who the agent is. The two are the same discipline from opposite directions. Privacy asks what an agent may know about a person. Identity asks what an agent may do as a machine, and how the systems it calls can trust that it is who it claims to be.

The one idea to carry out of this lesson: **an agent is a machine actor, and a machine actor needs a machine identity, a set of credentials it can present to an API, a way to be scoped to the least it needs to do, and a way to be rotated and revoked when it is no longer trusted.** Every agent you deploy will authenticate to something, a ticketing API, a knowledge base, a database, a model gateway, and the difference between a well-run agent and a leak is almost always in how that identity is issued, scoped, and retired.

## Why an agent cannot just log in

A human logs in with a username and a password, and the password is a secret the person holds in their head. An agent has no head. It runs unattended, often for hours, and it needs to authenticate without a person typing anything. That single constraint reshapes the whole identity design.

The other constraint is that an agent is not a person, and it should not borrow a person's identity to do its work. When an agent acts using a human's credentials, three bad things happen. The human's account becomes the agent's account, so every action the agent takes is attributed to a person who did not take it. The human's permissions become the agent's permissions, so the agent inherits everything that person can do, not just what the task needs. And the human's credentials become a shared secret, which is the one thing credentials are supposed never to be. The fix is to give the agent its own identity, with its own credentials and its own permissions, and to let it act on a person's behalf only through a mechanism that records that delegation explicitly.

That mechanism is OAuth 2.0, the authorization framework that most of the modern API world uses to let one application access resources on behalf of a user, or on its own behalf, without ever sharing the user's password. [^1]

## OAuth 2.0: the four roles and the two flows that matter for agents

OAuth 2.0 defines four roles. The resource owner is the person or system that can grant access to a protected resource. The client is the application, in our case the agent, that wants to access that resource. The authorization server issues tokens after authenticating the client and, when needed, the resource owner. The resource server hosts the protected resource and accepts the access token. [^1]

The framework defines several grant types, the ways a client can obtain an access token. For agents, two of them carry almost all the work, and they answer two different questions.

The authorization code grant answers the question "how does the agent act on behalf of a specific user?" The user is redirected to the authorization server, authenticates there, and approves the access the agent is requesting. The authorization server then issues an authorization code, which the agent exchanges for an access token. The user's password never reaches the agent. [^1] This is the flow behind "connect your account" buttons, and it is how an agent gets permission to read a user's calendar, email, or tickets while the user stays in control of what the agent may do.

The client credentials grant answers the question "how does the agent act on its own behalf, with no user in the loop?" The client authenticates directly to the authorization server using its own credentials, and receives an access token. [^1] This is the machine-to-machine flow, and it is the one you will use most often for a long-running agent that does scheduled work, ingests data, or calls internal services. The RFC is explicit that this grant type must only be used by confidential clients, clients that can keep their credentials secret, which is exactly the profile of a server-side agent. [^1]

![The two OAuth flows for agents: the authorization code grant acts for a user, the client credentials grant acts for the agent itself](</diagrams/agent-identity-oauth-service-accounts-scoped-permissions/1-two-oauth-flows.png>)

The distinction is the whole lesson in miniature. When the agent acts for a user, use the authorization code grant, so the user's consent is recorded and the agent is limited to what that user approved. When the agent acts for itself, use the client credentials grant, so the agent has its own identity and its own permissions, and no user's account is implicated in its actions.

## Service accounts: a durable non-human identity

The client credentials grant needs the agent to have credentials of its own. The clean way to give a long-running agent those credentials is a service account, a special kind of account intended to represent a non-human actor, an application, a workload, a service, rather than an end user. [^2]

A service account is identified by its own unique identity, in Google Cloud, for example, by an email address that belongs to the account, not to a person. [^2] It has its own credentials and its own set of permissions, and it can be granted access to resources independently of any human. Because it is not tied to a person, it does not get locked out when an employee leaves, and it does not carry the permissions of whoever created it. It is a separate principal in its own right.

The same idea appears across clouds under different names. In Microsoft Entra ID, the application registration is the application object, and the service principal is the application's identity in the tenant, the concrete instance that gets assigned roles and permissions. [^3] The service principal is what the agent actually is when it authenticates, and it is what you grant access to. The naming differs, but the shape is the same: a non-human identity with its own credentials and its own permissions, distinct from every person in the organization.

The reason service accounts matter for agents is that an agent is a workload, not a person. It runs on a schedule, it calls APIs, it processes data, and it needs an identity that can be granted exactly the access the workload needs, rotated when the workload's credentials are at risk, and revoked when the workload is retired, all without touching any human account. A service account is that identity.

## Scoped permissions: the least the agent needs

An identity is only as safe as the permissions attached to it. A service account with broad permissions is a standing invitation, because the credentials are machine-held and machine-held secrets get stolen. The control that keeps an identity honest is scope.

In OAuth, the scope parameter is a space-delimited list of strings that the client requests, and the authorization server uses it to decide what the access token may do. [^1] The token the agent receives is limited to the scopes it was granted, and the resource server is supposed to enforce those scopes on every request. Scopes are the mechanism by which you express least privilege in an OAuth world: the agent asks for exactly the permissions the task needs, and the token it gets can do no more than that. [^4]

Least privilege is the principle that every identity, human or machine, should have only the permissions necessary to do its job, and no more. [^4] For an agent this is not a nice-to-have. An agent's credentials are more exposed than a human's, because they sit in configuration, in a vault, in a container, in a pipeline, and they are used by code that may be compromised. The smaller the scope, the smaller the blast radius when those credentials leak. A token that can only read tickets is a much smaller prize than a token that can read and write everything.

The practical pattern is to scope per task, not per agent. If an agent both reads tickets and writes to a knowledge base, give it two identities or two scopes, one that can read tickets and one that can write to the knowledge base, rather than one identity that can do both. Then a compromise of the read path does not automatically become a compromise of the write path.

## Worked example: a support agent with two identities

Put it together on the customer support agent from lessons 49 and 50. That agent does two kinds of work, and it should have two identities to match.

The first kind of work is answering a user's question about their own order. This is delegated work, done on behalf of a specific user, so it uses the authorization code grant. The user clicks "connect your account," authenticates with the authorization server, and approves the agent's request for the scopes it needs, say `tickets:read` and `orders:read`. The agent exchanges the code for an access token scoped to those two permissions, and it can read that user's tickets and orders, and nothing else. The user's password never reaches the agent, and the user can revoke the grant at any time. [^1]

The second kind of work is the nightly job that ingests resolved tickets into the knowledge base. This is the agent acting on its own behalf, with no user in the loop, so it uses the client credentials grant with a service account. The service account is granted exactly two permissions: read resolved tickets and write to the knowledge base. It cannot read open tickets, it cannot delete anything, and it cannot touch user accounts. The agent authenticates with the service account's credentials, gets a token scoped to those two permissions, and runs the job. [^1] [^2]

The two identities are separate on purpose. If the user-delegated token leaks, the attacker can read that one user's tickets, and the user can revoke the grant. If the service account's credentials leak, the attacker can read resolved tickets and write to the knowledge base, but nothing else, and the credentials can be rotated without touching any user. Neither compromise cascades into the other, because neither identity has the other's scope.

![A support agent with two identities: a user-delegated identity for answering order questions and a service account for the nightly knowledge base ingest, each with its own scopes and blast radius](</diagrams/agent-identity-oauth-service-accounts-scoped-permissions/2-support-agent-two-identities.png>)

## The pattern: separate, scope, rotate, revoke

The worked example is one instance of a pattern that generalizes to every agent you deploy.

Separate identities per concern. Give the agent a distinct identity for each distinct kind of access, a user-delegated identity for acting on behalf of users and a service account for acting on its own behalf, and separate service accounts for separate workloads. Do not let one identity accumulate unrelated permissions.

Scope to the least. Request the narrowest scopes the task needs, and enforce them on the resource server, not just in the request. A token that can do more than the task requires is a liability. [^4]

Rotate the credentials. Machine-held secrets should be rotated on a schedule, and rotated immediately when there is any sign of compromise. A service account whose key has been in a repo, a log, or a leaked artifact is a service account that must be re-keyed now, not next quarter.

Revoke when done. When a workload is retired, or a user revokes a grant, the identity must stop working. The user-delegated grant dies when the user revokes it. The service account dies when you delete it or disable its keys. The discipline is the same: an identity that is no longer trusted should stop being able to act.

Store the secrets in a vault, never in code. The credentials the agent uses, the client secret, the service account key, belong in a secret manager, not in the source tree, not in a config file that gets committed, not in an environment variable that shows up in logs. The agent reads them from the vault at runtime, and the vault is where rotation happens. [^5]

![The agent identity pattern: separate identities per concern, scope to the least, rotate the credentials, revoke when done, and store secrets in a vault](</diagrams/agent-identity-oauth-service-accounts-scoped-permissions/3-pattern-separate-scope-rotate-revoke.png>)

## The pitfalls to avoid

The first is sharing one service account across many agents. A single shared identity means you cannot tell which agent did what, you cannot revoke one agent without breaking the others, and you cannot scope one agent without granting the same scope to all of them. The audit trail from lesson 29 becomes useless when every action is attributed to the same principal. Give each workload its own identity.

The second is over-scoping because it is easier. Requesting `read write delete` because the API offers it, or granting a service account broad roles because you did not want to figure out the narrow ones, is how a small leak becomes a large one. The scope you grant is the scope an attacker inherits if the credentials leak. [^4]

The third is treating long-lived static credentials as acceptable. A service account key that never expires is a permanent backdoor. Prefer short-lived tokens and workload identity where the platform offers it, and rotate the static credentials you cannot avoid on a real schedule.

The fourth is storing secrets where they can be read. A client secret in a committed config file, a service account key in a repo, a token in a log line, these are the leaks that turn an identity problem into a breach. The secret belongs in a vault, and the agent should read it from there at runtime. [^5]

## Try it

1. **Map the identities.** List every external system your agent calls. For each, write down whether the agent acts on behalf of a user or on its own behalf, and which OAuth flow that implies, the authorization code grant or the client credentials grant. [^1]

2. **Scope a service account.** Take one workload and write the narrowest set of scopes or permissions it needs to do its job. Then write the broad set you would be tempted to grant instead. Compare the blast radius of a leak under each. [^4]

3. **Audit a secret.** Find where your agent, or a system you use, stores its credentials. Are they in a vault, or in a config file, a repo, or an environment variable? If they are not in a vault, that is the first thing to fix. [^5]

## What's next

This lesson proved who one agent is: it gave the agent a machine identity, scoped it to the least it needs, and showed how to rotate and revoke it. The next lesson, **Multi-tenant agents: isolation, quotas, and abuse prevention**, scales that question up. When many agents, or many customers' workloads, run on the same infrastructure, proving identity is not enough. You have to keep them isolated from each other, cap how much each one can consume, and stop one tenant from abusing the shared platform. You have proven who the agent is. Next you will keep it from harming its neighbors.
