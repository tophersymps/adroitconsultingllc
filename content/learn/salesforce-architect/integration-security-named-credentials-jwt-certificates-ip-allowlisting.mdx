# Lesson 27: Integration Security: Named Credentials, JWT, Certificates, and IP Allowlisting

Lesson 26 taught you how to design the REST integration itself. This lesson is about the layer underneath it: the machinery that decides whether an integration is allowed to talk to your org at all, and what it is allowed to do once it gets there. You have four tools and they do different jobs. Named credentials keep endpoint and secret management out of your code. JWT is the token format that makes server-to-server auth work without a human in the room. Certificates are the cryptographic keys that sign those tokens and, in mutual TLS, let a remote party prove it really is who it says it is. IP allowlisting is the coarsest fence of all: it says calls may only come from certain network ranges. An architect who understands which tool answers which threat is the one who does not leak credentials into source control.

The four fit together. A named credential holds a JWT-based authentication scheme backed by a certificate, and the whole thing sits behind an IP restriction that keeps the token useless off your network. Getting one wrong usually means the integration either leaks secrets or stops working at 2 a.m. when a certificate expires.

## Define the terms

- **Named credential**: a single definition that specifies the URL of a callout endpoint and its required authentication parameters together, so Salesforce handles the authentication for the callout instead of your code. [^1]
- **External credential**: a Salesforce object that stores the authentication protocol and the permission set or profile that authorizes a caller, kept separate from the named credential that points at the endpoint. [^2]
- **JSON Web Token (JWT)**: a compact, URL-safe way to represent claims transferred between two parties, where the claims are encoded as a JSON object inside a signed or encrypted structure. [^6]
- **Certificate**: a signed public key that proves an identity; in Salesforce, certificates are used to sign JWTs and to present a client certificate for two-way SSL. [^4]
- **IP allowlisting (trusted IP ranges)**: restricting which IP addresses are allowed to log in or reach an app, so a call from outside an approved range is refused. [^7]

## Named credentials: the envelope that holds the secret out of code

The starting failure mode in integration security is a hardcoded credential. Someone writes a callout, needs an API key, and pastes the key into the Apex as a string constant. It works. Then the code goes to Git, the repo gets a broader audience, and the secret is now public. Named credentials exist to make that failure hard.

A named credential "specifies the URL of a callout endpoint and its required authentication parameters in one definition. Salesforce manages all authentication for Apex callouts that specify a named credential as the callout endpoint so that your code doesn't have to." [^1] Your Apex never sees the token. It calls a named credential by name, and Salesforce attaches the authorization. The endpoint and the credentials live in Setup, not in code, and an added benefit is that you can skip remote site settings for the site defined in the credential. [^1] When the endpoint URL changes, you update the named credential and every callout that references it keeps working. [^1]

The current model is a two-part structure, and knowing the split helps you reason about who holds what. A **named credential** specifies the callout endpoint and an HTTP transport protocol. An **external credential** holds the authentication protocol and user credentials that authenticate the caller. The same external credential can be reused by several named credentials, and **principals** map the external credential to permission sets or profiles, so at run time Salesforce checks that the user has the permission before the callout is allowed. [^2] Tokens are encrypted and stored on the User External Credential object, and any user making an authenticated callout needs profile- or permission-set access to that object. [^3]

Salesforce introduced an improved, extensible named credential in Winter '23 and strongly recommends it over the legacy version, which is deprecated. [^2] Named credentials serve three kinds of callout: Apex callouts, external data sources, and External Services. [^2] When you reach for one, you are buying three things: no secrets in code, centralized endpoint management, and a place to enforce who is authorized to make the call.

## JWT: the token that needs no human

JSON Web Token is an IETF standard, RFC 7519. The definition is precise: it is "a compact, URL-safe means of representing claims to be transferred between two parties," where the claims are a JSON object used as the payload of a JSON Web Signature or JSON Web Encryption structure. [^6] The word to hold onto is compact. JWTs are small enough to fit in an HTTP Authorization header or a query parameter, which is why they replaced heavier formats for machine-to-machine auth. [^6]

A JWT carries **claims**, pieces of information asserted about a subject. The registered claim names you will meet in every integration are `iss` (issuer), `sub` (subject), `aud` (audience), `exp` (expiration time), and `iat` (issued at). [^6] An architect does not need to build JWTs by hand, but does need to know what each of these fields means, because a JWT with no expiration is a standing credential, and a JWT with the wrong audience is a token that a neighbor system will happily accept.

In Salesforce the JWT bearer flow is how a server authenticates without an interactive login. The client posts a JWT to the Salesforce OAuth token endpoint, Salesforce processes the signed token, and issues an access token based on prior approval of the app. [^5] Three details matter.

First, the JWT must be signed with RSA SHA256, using a certificate uploaded to the connected app as the signing secret. [^5] That is where certificates enter the picture: the signing key is a certificate, not a password.

Second, the claim values are prescriptive. `iss` must contain the client_id of the connected app. `aud` is the authorization server URL, for example `https://login.salesforce.com` or `https://test.salesforce.com`. `sub` is the username the token acts as. `exp` is the expiration time in seconds since the Unix epoch, and Salesforce allows a three minute buffer for clock skew. [^5]

Third, and this surprises people, the JWT bearer flow never issues a refresh token. [^5] The calling system must mint a new JWT and exchange it each time, which means it must hold the private key and keep its clock correct. That is the cost of no-human auth, and it is worth designing for rather than discovering at 3 a.m.

The standard gives you the token vocabulary and the registered claims; Salesforce gives you the flow that turns a signed JWT into an access token. [^6] [^5]

## Certificates: the keys behind the signatures

A certificate is how the parties in an integration prove cryptographic identity. For the JWT bearer flow, Salesforce requires the JWT to be signed using RSA SHA256, and the signing secret is an uploaded certificate. [^5] The connected app registers the certificate, so when a signed JWT arrives, Salesforce can verify the signature against the public key it holds.

Certificates also answer the second, tougher question: what if both sides need to trust each other? That is two-way SSL, and Salesforce supports it for callouts. "To use two-way SSL authentication, send a certificate with your callout that was either generated in Salesforce or signed by a certificate authority (CA)." [^4] The target of the callout receives the certificate and authenticates the request against its keystore, so the remote party knows the call genuinely came from your Salesforce org, not from someone who stole a token. [^4]

Two operational habits keep this from turning into an outage. A certificate has an expiry, and Salesforce will not let the signed JWT or the two-way handshake succeed with a dead one, so certificate rotation belongs in your change calendar, not left to memory. And a certificate is only as protected as the place that holds it. When you use a named credential with a certificate-backed auth scheme, the private material lives in the credential store, not in your Apex, which is exactly where it should be. [^2]

## IP allowlisting: the fence that answers who is allowed to knock

Tokens and certificates answer the question "is this caller who it claims to be?" IP allowlisting answers a cruder, earlier question: "is this caller even coming from a place we recognize?" For a connected app, Salesforce lets you "specify the trusted IP ranges from which a user can log in," and you can apply IP relaxation to all OAuth client apps. [^7] In the connected app's Trusted IP Range section you add a start and end IP address, and you can enter multiple discontinuous ranges to cover, say, one office block and one cloud provider's egress range. [^7]

IP allowlisting is defense in depth, not a replacement for strong auth. A stolen JWT is still a problem if it is used from an IP inside the allowed range, but a token that leaks out to a home network is useless if the allowlist only accepts the office. For server-to-server integrations, restricting the consumer's app to the known egress IPs of the calling system is a cheap, high-value control, because a machine integration has no reason to come from anywhere else. The tradeoff is operational: a cloud provider that rotates its egress IPs will break your allowlist until you update it, so fixed egress IPs or a known range are the precondition for using this control on a machine integration.

One more outbound note on named credentials. Named credentials include an `OutboundNetworkConnection` field you can use to route callouts through a private connection, which is the named-credential equivalent of keeping traffic off the public internet. [^1] That is the symmetric move to IP allowlisting: instead of only letting certain callers in, you also keep your own callouts on a private path.

## Worked example: a payment processor and an inbound ERP sync

A financial services firm connects Salesforce to two external systems. One is a payment processor, a server-to-server integration where Salesforce calls out to submit transactions. The other is a nightly ERP job that pushes invoice status into Salesforce. Here is the security design.

1. **Create an external credential for the payment processor.** Set the authentication protocol to JWT bearer. This is the object that will hold the token scheme and the principal mapping, so it stays reusable and out of the callout code. [^3]
2. **Create a named credential that points at the processor endpoint.** Attach the external credential to it. Your Apex now calls the named credential by name; the endpoint URL and the auth live in Setup. If the processor moves hosts, you change one record, not twenty call sites. [^1]
3. **Register a certificate for signing.** Upload the certificate to the connected app that backs the integration, because the JWT bearer flow requires an RSA SHA256 signature using that certificate. [^5]
4. **Keep the callouts private.** Set the named credential's `OutboundNetworkConnection` so transaction traffic routes over the private connection rather than the public internet. [^1]
5. **Allowlist the inbound ERP.** For the connected app the ERP uses to push invoice status, configure trusted IP ranges that cover the ERP's fixed egress IPs. The ERP is a machine job with a stable network home, so there is no reason to accept token use from anywhere else. [^7]
6. **Rotate, don't assume.** Put both the certificate expiry and the ERP's egress IP changes on the operations calendar, because a dead certificate or a rotated IP produces the same symptom: a working integration that quietly starts failing at the boundary.

## The pitfall to avoid

**Hardcoding a credential, then authenticating forever.** The two failures that undo integration security are a secret copied into Apex (and then into Git) and a token or certificate with no expiration and no rotation. Both look like they are working right up until they are not. The fix is the whole lesson: named credentials to keep secrets out of code, JWT bearer with a real `exp` so nothing authenticates forever, certificates that get rotated before they expire, and an IP allowlist so even a leaked token is only usable from a range you control.

## Try it

1. A developer says they can call the payment API faster if they just paste the API key into the Apex class. Why is that the wrong call, and what is the alternative? *(Answer: the key would land in version control and become a standing credential. Use a named credential backed by an external credential so Salesforce manages the auth and the secret stays in Setup.)* [^1]
2. Your server-to-server integration with a bank needs both sides to prove identity, not just Salesforce proving itself to the bank. Which tool covers the second direction? *(Answer: a client certificate for two-way SSL, presented on the callout so the bank's keystore can verify it.)* [^4]
3. A JWT for a Salesforce JWT bearer flow omits the `exp` claim and uses the wrong `aud`. Which one is the bigger mistake, and why? *(Answer: the wrong `aud` means another system could be a valid audience for the token; a missing `exp` means no expiry. Both are serious, but the flow never issues a refresh token, so `exp` discipline is what keeps a leaked JWT from being a permanent credential.)* [^5] [^6]
4. You add an IP allowlist to a connected app used by a cloud service whose egress IPs change monthly. What do you need to plan for? *(Answer: update the trusted IP ranges when the provider rotates IPs, or the integration will start failing at the boundary; this control assumes stable, known ranges.)* [^7]
