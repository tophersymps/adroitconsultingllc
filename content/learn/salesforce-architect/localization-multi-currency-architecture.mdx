# Lesson 56: Localization and Multi-Currency Architecture: Locale, Language, and Dated Exchange Rates

Lesson 55 gave you the architecture that lets a machine answer in your language. This lesson hands the same instinct to a different problem: one Salesforce org that must feel native to people in many countries, in many languages, with many currencies. The hard part is not that the features exist. It is that each of them solves a specific problem, and if you mix up what each one does, you build an org that formats a German date in Arabic numerals, labels it in French, and prices it in dollars, all for the same record, and calls that localized.

The architect's job is to keep those axes separate in design even though they converge on screen. Three settings, three jobs. **Language** decides what the words say. **Locale** decides how numbers, dates, times, and addresses are shaped. **Currency** decides what unit a money value is expressed in and how it converts to the user's own money. Start by holding those three apart, and everything else in this lesson is details.

## Locale versus language: formatting and meaning are different things

The single most useful distinction in this lesson is also the easiest to blur. People use "language" and "locale" as if they were the same word. On the Salesforce platform they are deliberately separate settings with separate effects. [^1]

**Language** is about meaning. It determines the language of the interface text: the labels on buttons, the names of fields, the on-screen text and help that a user reads. When an org has selected multiple languages, a user picks a personal language, and Salesforce displays all on-screen text, images, buttons, and help in that language. [^1] There is an important nuance buried in that behavior: the data a user enters stays in the language it was entered in. Language translates the chrome of the app, not the records themselves. A user typing a sales note in English gets a Spanish interface and the note stays English, which is the correct outcome. [^1]

**Locale** is about formatting. It determines how the platform writes values on screen: the date and time format, the grouping of numbers, the comma versus the period as the decimal separator, the order of a person's name, even how addresses are laid out and which day the calendar week starts on. [^2] A user in the United States and a user in Germany can both read the interface in the same language, English, yet see completely different date and number patterns. Locale is where "07/04/2026" becomes "04.07.2026", and where "1,234.50" becomes "1.234,50". Same meaning, different shape.

The clean rule to carry into any design conversation: language answers "what word is on the button?" and locale answers "how is the value written on the page?" Salesforce lets a single-language org change its locale even when it cannot change its language, which is a neat demonstration that the two really are independent. [^1] You can format everything for a German reader while every label stays English.

## How language and locale are set: org defaults, then user choice

Neither setting is a single global switch. There is a default layer and a personal layer, and the defaults apply to a user only until that user chooses their own.

The administrator sets three org-wide defaults on the Company Information page: the default language, the default locale, and the default time zone. [^1] These defaults apply to all new users until each user selects a personal language, locale, and time zone in their own settings. [^1] One layer to establish the starting point for a newcomer, one layer to respect that people differ.

A subtle but load-bearing detail hides here. The default language is not only the fallback for a fresh user's display language. It is also the language in which customizations are stored: custom fields, tabs, and user interface labels that you create live with the default language as their master value. [^1] A user's personal language preference does not override that stored master copy. This matters because it is the seam where translation work attaches. A custom field label is authored once in the default language, then separately translated into each of the org's supported languages. [^1] If an architect does not plan for that translation pass, a custom field is simply never translated, and users in another language see the original label no matter what language they selected.

Which is where **local name fields** come in for the data side. Local name fields are additional standard text fields on Account, Contact, and Lead that let you store an original or translated version of a name. [^7] A contact can carry both a name and a local-language name, so the same record reads naturally to a Spanish-speaking and a Japanese-speaking user. The pattern generalizes past names: any value that is both data and presentation, a person's name, an organization's legal name, fits the "store a localized copy alongside the canonical value" shape that local name fields model.

## Worked example: localizing a cross-border sales org

Put the settings layer together against the recurring client from this course, the field-services company that now sells to customers in the United States, Germany, and Japan.

**Decide the language set.** The org enables English, German, and Japanese as supported languages. The default language stays English, because English is where the master copies of custom labels live. Custom fields are authored in English, then translated into German and Japanese through the translation layer, so a German salesperson sees the same field labeled in German while the stored master label remains the English source. [^1]

**Model the locale independently.** No single per-country mapping forces everything together. A French-speaking user based in Montreal and an English-speaking user based in the United Kingdom both use English, but one reads dates as day/month/year and the other reads the same style because both use a European locale, while a U.S. user sees month/day/year. If you pin locale choices to language choice, you get this exactly backwards. Locale is chosen per user, on top of language. [^2]

**Use local name fields for the data.** Each account and contact can hold a local-language name alongside the canonical one, so the CRM that the Tokyo office reads shows company and person names in Japanese script while the same records show their English forms for the U.S. team. [^7]

**Plan the translation pass as first-class work.** The subtle failure in this org would be shipping the three languages without ever translating the custom fields and tabs. The org would claim to be localized while every custom label still read English, because customization storage is tied to the default language. [^1] The translating is not something the platform does for you; it is a deliverable someone owns, and the architect lists it as a release item rather than assuming it happens.

That is the localization half. Now the money.

## Multi-currency fundamentals: corporate, personal, and record currency

Multi-currency is a distinct feature, gated by edition: it is available in Enterprise, Performance, Unlimited, and Developer Editions. [^3] When an architect turns it on, three distinct notions of currency come into play, and confusing them is the root of most multi-currency design errors.

**Corporate currency** is the administrator's anchor. It is meant to reflect the currency of the corporate headquarters, and the administrator maintains both the list of active currencies and each currency's conversion rate relative to that corporate anchor. [^3] Think of it as the base currency every other rate is measured against.

**Active currencies** are the ones the company actually does business in. Only active currencies can be used in currency amount fields. [^3] If the company does not operate in a currency, that currency is not active, and a user cannot put an amount in it. This is a governance control as much as a feature list.

**Personal currency** is the user's default for quotas, opportunities, quotes, and reports. [^3] It is the money framing each individual reads by default, and a user can also enter amounts in other active currencies when they create a record. So the sales director in Germany reads her own pipeline in euros even when a deal is recorded in dollars.

One more notion rounds it out: **record currency**. Every standard and custom object record that has currency fields carries a field that specifies the currency for all the amount fields on that record; you can make it editable or locked by field-level security. [^3] Set an account's currency to US dollars and its annual revenue displays in dollars. If you then change that record's default currency, here is the fact most people misremember: the amounts are not converted. They simply display with the new currency code. [^3] Changing the currency on a record does not revalue the amounts; it changes what unit label they carry. Revaluation is a separate, deliberate operation.

## Conversion mechanics: the shape of the money math

Once multiple currencies exist, conversion is everywhere, and it has rules worth knowing so you can predict the number that shows up.

Conversion happens in two steps. When Salesforce converts a currency amount, it first converts the record's currency to the corporate currency, then converts again from the corporate currency to the user's personal currency. [^5] Because the value travels through the corporate anchor in two hops, an outdated exchange rate on either hop compounds the error across both conversions. [^5] The practical reading for an architect: conversion accuracy degrades as a function of how current your rates are, and it degrades at the seam where the corporate rate is stale, not just at the one rate your user is watching.

Formula fields bend around currency in a specific way. A custom formula field is not tied to any single currency; if its result is a currency amount, it displays in the currency of the associated record. [^3] Workflow rules and approval processes that use filters, as opposed to formulas, convert all currency values to the corporate currency. [^3] These asymmetries are the kind of detail that trips a reviewer, because the "expected" behavior shifts depending on whether a value comes from a formula or a filter.

Reports keep the original currency per amount but let you display totals in any active currency and show a converted column. [^3] The default display is the user's personal currency; the converted column shows amounts in your selected view currency. [^3] The data is not destroyed by conversion, the original currency value persists and the converted view is a projection on top of it. That is a good principle to carry into any custom reporting design: store the native amount, render the conversion.

There is also a locking rule that matters for the lifetime of the org. If Apex code references a record's currency field, which the platform exposes as `CurrencyIsoCode`, then you can never disable multiple currencies for that organization. [^3] Enabling multi-currency is itself a permanent, irreversible-ish organizational change with broad implications, and writing code that touches `CurrencyIsoCode` cements it further. [^3] The decision to go multi-currency is a one-way door, and the code you write can make it more locked than the admin intended.

## Advanced currency management and dated exchange rates

A flat conversion rate is a simplification, and the simplification breaks the moment the truth is historical. Exchange rates do not sit still. So how do you report, this quarter, on a deal that closed last quarter, when the rate has moved since? Salesforce answers with **advanced currency management**, which manages **dated exchange rates**: conversion rates mapped to a specific date range. [^4]

The governing example in Salesforce's own documentation is the cleanest way to hold it. On January 1, 1 USD equals 1.39 AUD; on February 1, 1 USD equals 1.42 AUD. Opportunities that closed between January 1 and February 1 convert using the first rate, 1.39. Opportunities that closed after February 1 use the second rate, 1.42. [^4] The rate a deal is valued at depends on when that deal closed, not on today's spot price. That is the entire point of dated exchange rates: they preserve the economic reality of each deal as of its own time.

Mechanically, a dated exchange rate is defined by a start date and a conversion rate. [^4] Each rate stays in effect until either the end of time or the day before the next start date for that currency. [^4] The window between one start date and the next is called the exchange rate date range, and the ranges can be as short as a single day or as long as all time. [^4] When you first enable advanced currency management, your existing static rates automatically become the first set of dated rates, valid for all time until you define a new range. [^4] And if you disable it, every conversion falls back to the static rate. [^4]

The date that picks the rate is worth stating precisely: with advanced currency management, the opportunity close date determines which conversion rate is used when displaying currency amounts. [^3] The architect does not guess which field drives the conversion; the close date is the selector.

**The object behind the concept is `DatedConversionRate`.** This is the standard object that represents the dated exchange rates used by an org with both multicurrency and the effective dated currency feature enabled. [^6] It carries the `IsoCode` (the three-letter ISO 4217 currency code, unique per org, for example USD, GBP, or JPY), the `ConversionRate` against the corporate currency, a `StartDate`, and a read-only `NextStartDate` that is effectively the day after the current rate's end. [^6] The same object is what you load when you bulk-import dated exchange rates with Data Loader rather than clicking through Setup. [^6] It is only available in multicurrency orgs with advanced currency management enabled; it does not exist in single-currency orgs or in multicurrency orgs that skipped advanced currency management. [^6] Which makes it a clean architectural signal: if your design needs it, your org has made both of those choices.

## Where dated exchange rates apply, and where they do not

The trickiest part of advanced currency management is not what it does. It is where it refuses to operate. Dated exchange rates are used for opportunities, opportunity products, opportunity product schedules, campaign opportunity fields, opportunity splits, and reports related to those objects and fields. [^4] That is the scope, and the scope is narrower than most people assume on day one.

Concretely, dated exchange rates are **not** used in forecasting, in currency fields on other objects, or in currency fields in other types of reports. [^4] They are also not used when calculating formula fields whose return type is Currency. [^4] So the moment a money value flows out of the opportunity family into a forecast, a report on a non-opportunity object, or a currency formula, the dated rate stops applying and the conversion effectively reverts to static behavior. If your design assumes "we turned on dated rates, so all money is historical and correct," that assumption is wrong wherever the value leaves the opportunity scope.

Two more consequences are the kind a reviewer will probe. Roll-up summary fields are supported between two advanced-currency objects, for example from an opportunity line item up to its opportunity, because both sides honor dated rates. [^4] But if you enable advanced currency management, you can no longer create a currency roll-up on the opportunity object that rolls up to the account, and you cannot filter on the opportunity currency field on the account. [^4] Existing currency roll-up summary fields on the opportunity that summarize objects that do not support dated rates get disabled and stop calculating. [^4] And cross-object formulas always use the static conversion rate for currency conversion, never the dated rate. [^4]

There is also a platform constraint worth filing away: with advanced currency management enabled, you cannot bind Visualforce pages that use `apex:inputField` or `apex:outputField` to currency fields that support advanced currency management. [^4] If a legacy page relies on that binding, enabling dated rates breaks it. This is a real migration consideration, not a theoretical one, because it surfaces in a review as a page that stopped working for a reason nobody connected to the currency feature.

## Worked example: dated rates for a quarterly international deal

Put it together against the same cross-border company. It has deals in US dollars and euros and wants its quarterly revenue reporting to reflect the rate that was actually in force when each deal closed, not this morning's rate.

**Enable the right stack.** The org enables multiple currencies, sets USD as the corporate currency, activates USD and EUR as active currencies, then enables advanced currency management so that it can use dated exchange rates. [^3] [^4] Without that last step, it is stuck with a single static rate.

**Load the rate history.** When the org enables advanced currency management, the existing static rates first become the all-time dated set. [^4] The team then imports the historical month-by-month USD-to-EUR rates into the `DatedConversionRate` object with Data Loader, each entry carrying an `IsoCode`, a `StartDate`, and a `ConversionRate` against the corporate currency. [^6] A deal that closed in the month the effective EUR rate was 1.18 converts at 1.18; a deal from a month when the rate was 1.22 converts at 1.22. The close date selects the rate. [^3] [^4]

**Scope the guarantee honestly.** The team wants to shout "all our money is dated." The honest version is narrower: dated rates apply to the opportunity family and its related reports, not to forecasting, not to currency fields on other objects, and not to currency formulas. [^4] The quarterly revenue report built on opportunities gets the guarantee. A forecast roll-up or a currency formula field does not. The architect states this scope in the design so nobody claims historical accuracy for the parts that use static rates.

**Check the roll-up constraint before building.** The old org had a currency roll-up on opportunity summarizing into account to show company-wide revenue. With advanced currency management enabled, that roll-up is no longer creatable and the legacy one stops calculating, because the account object does not honor dated rates. [^4] The design has to surface that migration cost explicitly rather than discover it after the feature is on.

**Guard the two-step conversion.** Every conversion still runs record to corporate, then corporate to personal. [^5] With only two currencies and one corporate anchor this is clean, but as the rate history grows the team must keep the dated rates current, because a stale rate on either hop compounds the variance across both conversions. [^5] Freshness of the rate table is an operational contract, the same discipline lesson 15 and lesson 55 hammered about derived data.

## Pitfalls to design around

**Treating language and locale as one switch.** Pin formatting to language and you force a wrong shape on a Canadian bilingual or a UK-based German speaker. Keep them as separate per-user axes. [^1] [^2]

**Never translating custom labels.** The default language is the master for custom field and tab labels, and users' personal languages do not override it. [^1] A "localized" org that skipped the translation pass is still English on every custom label. Plan the pass as a deliverable.

**Changing record currency expecting revaluation.** Changing an account's currency does not convert its amounts; they just take on the new currency code. [^3] Any expectation that the numbers revalue is wrong, and any downstream logic that assumed revaluation is broken.

**Assuming dated rates cover everything.** Dated exchange rates stop at the edge of the opportunity family. [^4] Forecasting, other objects' currency fields, currency formulas, and cross-object formulas fall back to static behavior. State the scope or your accuracy claims overreach.

**Forgetting `CurrencyIsoCode` locks the org.** Apex that touches the record currency field prevents disabling multiple currencies. [^3] Multi-currency is a durable org decision, and code can make it permanent.

## Try it

1. In one or two sentences each, state what language controls and what locale controls, and give one concrete example of a value that differs by locale but not by language.
2. A German-speaking user in Berlin and an English-speaking user in London both read an English interface. Name one way their on-screen values can still differ, and why.
3. A client enables multi-currency but not advanced currency management. A deal closed in March at a rate that has since moved. Using the lesson, state whether that deal's conversion reflects the March rate or a current static rate, and why.
4. Your org uses Advanced Currency Management and a currency formula field calculates a value that must match opportunity revenue. Based on the lesson, is that formula using the dated rate or the static rate, and what is the risk if you assumed it matched opportunity revenue?
5. A legacy Visualforce page binds `apex:outputField` to an opportunity currency field, and you enable advanced currency management. What does this lesson say happens to that page?

For question 4, the answer is that the formula uses the static conversion rate, because dated exchange rates are not used when calculating formula fields with a return type of Currency, so the formula value will diverge from opportunity revenue that uses the dated rate, and the design should not assume they match.
