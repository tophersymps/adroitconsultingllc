# Lesson 7: Event-Driven Integration: Platform Events + Change Data Capture

Lesson 6 introduced the three outbound archetypes; fire-and-forget was the one where "the remote system acknowledges receipt, processes asynchronously." This lesson opens the hood on that pattern's engine: the **Salesforce event bus**, and its two flagship vehicles: **Platform Events** and **Change Data Capture (CDC)**. Salesforce calls this *process integration*, "event-driven integration through the publication and subscription of platform events to other systems." [^1] It's the architecture that lets you decouple "something happened" from "someone handles it."

## The mental model: producers, consumers, channels

Event-driven architecture rests on three concepts: the **event producer** (publishes), the **event consumer** (subscribes and acts), and the **event channel** (the distribution vehicle between them). [^2] The point is loose coupling: producer and consumer never talk directly, so either side can scale or change independently, and one event fans out to many subscribers. Producers and consumers don't have to live outside the platform; a trigger, a Flow, or a Lightning component can produce or consume an event. [^2] The bus itself is the decoupling mechanism: "The event bus decouples event publishers from event subscribers." [^3]

## Platform Events: you define the message

Platform Events, introduced in 2017, let you define a custom event structure (a message with your fields), publish it, and let subscribers react. They've since evolved into **High Volume Platform Events (HVPEs)**, which "greatly expand the publish/subscribe allocations over the original offering." [^1] New platform events are high-volume by default; the older standard-volume type can no longer be created and is being **retired in Summer '27**, so you should be migrating any legacy standard-volume events. [^4]

You publish from Apex (`EventBus.publish()`), a Flow (a Create Records element on the event object), or REST/SOAP/Bulk APIs; you subscribe with Apex triggers, Flows, the `empApi` Lightning component, or externally via the **Pub/Sub API**, a gRPC/HTTP2 interface delivering binary Avro messages, and the modern way to stream platform events and CDC to your own infrastructure. [^5] [^1]

**What Platform Events are for: business intent.** "Order Shipped," "Payment Failed," "Contract Renewed": you define the payload, you decide when it's published, and it carries meaning beyond a raw record change.

## Change Data Capture: the record-change firehose

CDC is the fastest way to start publishing: select an object in Setup and Salesforce automatically creates a platform event object for it (`AccountChangeEvent` for Account, `Shipment__ChangeEvent` for a custom `Shipment__c`), then publishes **created, updated, deleted, and undeleted** record changes to it. [^1] It's available in Enterprise, Performance, Unlimited, and Developer editions. [^6]

**What CDC is for: record state.** Keep an external data store "updated in real time" instead of periodic exports or repeated API calls. [^6] You don't design a message; you get the record's fields in the event body, noise included: CDC "publishes platform events for every record created, updated, deleted, and undeleted," including non-user changes from batch Apex, ETL jobs, and data loads, which "can potentially overload your allocations and lead to failed event deliveries." [^1]

### Choosing how to publish

Michael Norton's summary chart is the architect's cheat sheet: [^1]

| Option | Category | Benefits | Considerations |
|---|---|---|---|
| **CDC** | No-code | Easy configuration; auto-created `xChangeEvent` structure; low-cost add-on | Publishes *all* record changes, incl. ETL/batch/data-load noise |
| **CDC with filters (custom channels)** | No-code | Reduces delivered messages to subscribers | Still uses resources to publish records never delivered |
| **Record-triggered Flows** | Low-code | Admins/developers know Flow; filter before publishing | Flow mappings need maintenance as the data model changes |
| **Apex triggers** | Pro-code | Most control over filtering, order of execution, single-trigger discipline | Code + unit test updates as the data model changes |

Filtered streams (custom channels with complex filters) went GA in Winter '23 so CometD subscribers can receive only the events they care about. [^1]

## The limits that shape the design

- **Publishing:** 250,000 event messages per hour (Performance/Unlimited and Enterprise/Pro with API add-on; 50,000 in Developer Edition). A platform event add-on raises this to 275,000/hour. [^4]
- **Delivery** (to Pub/Sub API, CometD, `empApi`, and event relays, but *not* to Apex triggers or Flows): 50,000 delivered per rolling 24 hours on Performance/Unlimited, 25,000 on Enterprise, 10,000 on Developer. The add-on moves delivery to a monthly entitlement: e.g., 150,000 per 24 hours plus a 4.5 million monthly entitlement on Performance/Unlimited. [^4]
- **CDC selected entities:** the default allocation caps you at **5 entities** selected for change notifications (AppExchange released package selections don't count; add-ons/custom channels can raise it). [^7]
- **Concurrent CometD subscribers:** 2,000 (Performance/Unlimited), 1,000 (Enterprise), 20 (Developer) across all channels and event types. [^7]
- **Message size:** 1 MB maximum for a change event. Exceed it and the event is replaced by a **gap event** (e.g., `GAP_UPDATE`) that tells subscribers a change happened without the field details. [^7]

## Durability, replay, and the ordering question

**Retention:** high-volume events (platform events *and* CDC) are stored in the event bus for **72 hours**; PushTopic, generic, and legacy standard-volume events for 24 hours. [^3]

**Replay:** every delivered message carries a `ReplayId` that marks its position in the stream. Subscribers persist it and resubscribe with it to catch up on missed events after a connection failure. Two rules matter: replay IDs are **opaque and not contiguous** ("Subscribers must not compute new replay IDs based on a stored replay ID"), and for *identifying* a message, use the `EventUuid` system field; `ReplayId` isn't guaranteed unique across org migrations. [^3]

**Ordering: the part architects get wrong.** The event bus is a distributed system; it does not hand you a strict global order. CDC, however, gives you explicit ordering signals in every event's `ChangeEventHeader`: [^8]

- `transactionKey`: uniquely identifies the Salesforce transaction; group all changes from the same save with it.
- `sequenceNumber`: the change's sequence *within* a transaction, starting at 1 (a lead conversion, for example, emits create-Account, create-Contact, create-Opportunity, update-Lead as a numbered sequence).
- `commitTimestamp` / `commitNumber`: when the change committed and the system change number (SCN), which increases sequentially.

Here's the trap: `commitNumber` is explicitly documented as **"provided for diagnostic purposes,"** not guaranteed unique in Salesforce (only within a single database instance), and it "might not be unique or sequential" after an org migrates databases. So you can *use* these fields to reconstruct order, but treat commitNumber as a hint, not a contract; never build uniqueness logic on it. [^8]

Two more CDC realities: change events for the same operation on multiple records of one object in the same second can be **merged** into a single event whose `recordIds` lists all affected records, and under load or oversize you get **gap/overflow events** instead. [^6] [^7]

**Design rule:** if downstream correctness depends on processing order, don't rely on arrival order; carry an explicit sequence (or use CDC's `sequenceNumber`/`commitTimestamp`) and make consumers idempotent: upsert, don't blind-apply. The `changeOrigin` header field helps you detect and skip events your own API integration initiated, avoiding "a deep cycle of changes" between systems. [^8]

## Worked example: order fulfillment across three systems

An e-commerce company runs Salesforce as the order front office. The warehouse (WMS) and the ERP are external; a notification service sends customer emails. The architect's event design:

1. **CDC for state sync.** Enable CDC on `Order__c` and `Order_Line_Item__c`. A Pub/Sub API client in the WMS subscribes to `/data/Order__ChangeEvent` and `/data/Order_Line_Item__ChangeEvent` and keeps its local copy fresh, no code on the Salesforce side, full record fields included. [^6]
2. **Platform Event for intent.** A record-triggered Flow publishes `Order_Shipped__e` (fields: `Order_Number__c`, `Carrier__c`, `Tracking_Number__c`) when Status changes to Shipped. The ERP and the notification service both subscribe: the ERP creates the invoice, the notification service emails the customer. [^1]
3. **Ordering in the WMS.** The WMS subscriber groups incoming events by `transactionKey` (the Order save and its line-item saves are one transaction), orders within the group by `sequenceNumber`, and orders across transactions by `commitTimestamp`. It treats `commitNumber` as diagnostic only. [^8]
4. **Recovery.** When the WMS disconnects, it stores the last `ReplayId` and resubscribes with it, replaying everything within the 72-hour window. [^3]
5. **Allocation check.** The team estimates ~18,000 change events/day from customer-facing updates but notices the nightly ETL updates every Order record in bulk; that alone would blow past a 25,000/24h Enterprise delivery allocation and risk "failed event deliveries." Fix: move the ETL window's objects to a filtered custom channel, or keep ETL-driven updates off CDC-selected fields. [^1] [^4]

## The pitfall to avoid

**Assuming the bus delivers in order.** Two rapid updates to the same record land at the warehouse in the wrong order; the downstream system shows a stale value until reconciliation. The fix isn't "publish slower"; it's the ordering discipline above: sequence fields in the payload (or CDC's header fields), idempotent consumers, replay-based recovery. The second classic failure is the **CDC flood**: enabling CDC on an object a nightly ETL touches and burning the entire delivery allocation ("overload your allocations and lead to failed event deliveries"). [^1]

## Try it

1. An ERP needs a near-real-time copy of every Account change, including bulk data loads. Platform Event or CDC, and what must you watch? *(Answer: CDC, because you need record state, not a designed message. Watch the delivery allocation: bulk loads publish events too; use a filtered custom channel if the load volume is high.)*
2. A Flow must tell an external system "invoice approved" with an approval number, and a second system must trigger a follow-up task. Platform Event or CDC? *(Answer: Platform Event: that's business intent with a custom payload and two subscribers.)*
3. Your warehouse consumer must never apply changes out of order within one save operation. Which header fields do you sort on? *(Answer: `transactionKey` to group, `sequenceNumber` to order within the group, `commitTimestamp` across transactions; treat `commitNumber` as diagnostic only.)*
4. Your subscriber was down for an hour. How does it catch up without missing or duplicating events? *(Answer: persist the last `ReplayId`, resubscribe with it; events are retained 72 hours for high-volume events. Use `EventUuid` for identity, not `ReplayId`.)*
