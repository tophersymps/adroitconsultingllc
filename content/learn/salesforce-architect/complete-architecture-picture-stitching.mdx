# Lesson 84: The complete architecture picture: stitching integration, security, data, lifecycle

Lesson 83 was about turning a design into something a sponsor will fund. This lesson is about the design holding together when the funding arrives, because the four threads a Salesforce solution always contains are rarely designed by one person at one time. Integration is decided in a workshop with the enterprise team. Security is inherited from the identity program or decided late by a security architect who joins in month four. Data modeling happens when someone finally asks how many records are involved, which is often after the object model is already signed off. Lifecycle and deployment planning gets squeezed into the last three weeks before go-live.

Salesforce's own framework makes the case for treating these as one design rather than four documents. It describes the platform's constraints as genuinely different from generic cloud architecture, naming a multitenant platform with governor limits, decades of business logic in Customer 360, declarative automation, metadata-driven configuration and managed sharing models. [^1] Those are not four topics; they are one set of constraints that appears in a different costume depending on which thread you are discussing.

## Define the terms

- **Trust boundary**: a point where data or control crosses between systems, networks or privilege levels. The security guidance is explicit that multi-org data flows and external integrations each create additional trust boundaries that need authentication and authorization at every crossing. [^2]
- **Defense in depth**: layering controls so that the failure of one control does not compromise the whole system. The framework pairs preventive controls, such as CRUD and field-level security enforcement, with detective controls such as Event Monitoring, and responsive controls such as step-up authentication. [^2]
- **Four-layer access model**: organization, object, field, record. Each layer further restricts the one above it, and the guidance frames it as the structure that least-privilege grants are built on rather than a set of independent switches. [^2]
- **System of record**: the single system whose version of a fact is authoritative. Integration design is mostly an argument about which system owns which fact, settled once and written down.
- **Request and reply versus fire and forget**: the two shapes of a remote process invocation. Request and reply holds the caller until the answer arrives; fire and forget releases the caller immediately and needs a failure path that runs without a user watching. [^3]
- **Batch data synchronization**: moving sets of records on a schedule where near-real-time is not required. The classic failure is choosing this pattern for reference data, then reusing the same middleware for everything else because it is already paid for. [^3]
- **Data virtualization**: reading external data without replicating it. The decision guidance on integration frames replication versus virtualization as an explicit choice to be made per data domain rather than a default, and warns against unnecessary replication. [^4]
- **Large data volume (LDV)**: the guidance declines to fix a single threshold and instead describes the shape: tens of thousands of users, tens of millions of records, or hundreds of gigabytes of total record storage. [^6]
- **Selective query**: a query whose filters return a small enough slice of a large object that the database can use an index. Volume work is mostly query work.
- **Source-driven development**: treating metadata, configuration, code and documentation as versioned artifacts, so that the org state is reproducible rather than remembered. [^5]
- **Sandbox tier**: the sequence of environments a change passes through. The DevOps guidance prices the leanest, the scale-optimized and the governance-optimized versions as trade-offs rather than a maturity ladder. [^5]
- **Observability from version one**: instrumenting the solution as part of designing it, on the argument that the data model, integration patterns and component boundaries are all shaped by what you plan to measure. [^5]

## The four threads and where they touch

Most seam failures are one thread's decision landing as another thread's constraint. This table is the one I keep on a second monitor during design review.

| Thread | Decision | What it forces on the other threads |
| --- | --- | --- |
| Integration | Which system is authoritative for each fact, and which pattern moves it | The object model and its external identifiers, who can call the API, and what the security model must expose |
| Security | Who can reach each record, and through which layer of access | Sharing model and its effect on query performance, the integration's identity, and what data can be logged |
| Data | Volume, retention and where each record lives over time | Whether the integration is a query or a copy, whether the security model can be evaluated, and the archiving job somebody must run |
| Lifecycle | How a change reaches production, and when | Deployment windows against release dates, test data volume, and whether the observability you drew is actually deployed |

Read the table left to right and the pattern is obvious. A decision in any row is a constraint in the other three, so a design review that treats them as agenda items rather than as one system will find the conflict during testing instead of during design.

## Integration: choose the pattern before the tool

Salesforce publishes the classic pattern set for this problem, and it is more useful than a product comparison because it forces the discussion onto behavior first: remote process invocation in request and reply or fire and forget form, batch data synchronization, remote call in, UI update based on data changes, and data virtualization. [^3] The document is written for designers and architects working out how to connect the platform to other applications, and it comes with a selection matrix specifically so that the pattern is chosen before the implementation.

Ask the pattern questions before anyone opens a licensing spreadsheet. Does the business need an answer now, or is eventual consistency acceptable? Is the trigger a user action or a data change? Does the external system have to initiate, or can Salesforce? Is the consumer a UI, a batch job, or another system's queue?

Then price the choice against the decision factors Salesforce's integration decision guidance lists: the existing tools and landscape, the data flow requirements including timing, directionality and expected user experience, implementation complexity, maintainability, data volume, and platform limits. [^4] Two of those are the ones teams skip. Maintainability is where the point-to-point count compounds, because every new pair of systems is a new thing to keep working. Platform limits is where a design that worked in a development org stops working when a bulk load triggers it.

A worked case, kept small. A distributor needs order status visible to dealers within five minutes, and needs pricing refreshed nightly from the ERP.

- Order status is a data change that a UI needs. Platform events published on order update, with the portal subscribing, match the UI update based on data changes pattern and keep the answer inside the platform. [^3]
- Pricing is reference data with no real-time requirement. Batch data synchronization overnight into a read-only staging object matches the shape, and the portal reads the synchronized copy rather than calling the ERP per page view. [^3]
- Dealer-specific pricing history is too large to replicate into the org and is read rarely, so it stays virtualized behind an external object, which the decision guidance explicitly treats as a per-domain choice rather than a fallback. [^4]

Three requirements, three different patterns, no middleware invented for its own sake. What the design still owes the reader is a failure path for each: what the portal shows when an event is delayed, and what happens when the nightly load half completes. Those answers belong in the design, not in the operations handbook someone will write later.

## Security: one identity spine, controls at every layer

The security thread starts with the shared responsibility line. Salesforce secures the infrastructure and the platform, and the architect is responsible for security on the platform, including identity and access management, data governance, and integration security. [^2] When a sponsor asks who owns a control, that sentence is the answer, and it is also the fastest way to end an unproductive argument about whether the platform is "secure".

Three design principles carry most of the weight in the security guidance, and each one has a mechanical consequence in the other threads. [^2]

1. **Apply zero trust across all layers.** Never assume trust from network location, user familiarity or system origin, and verify each request on its own merits. In a multitenant platform the network is not a perimeter you can treat as trusted. The consequence for integration design is that internal callers are not automatically privileged, which changes how you provision the integration's own identity.
2. **Grant least privilege by default.** Start from the most restrictive settings, private organization-wide defaults and minimal permissions, and expand deliberately against documented requirements. The four-layer access model, organization then object then field then record, is how that expansion stays legible. The consequence for data design is performance: sharing rules that spread access widely cost query time, and field-level security is the backstop that protects a field even when a sharing rule is too permissive. [^2]
3. **Implement defense in depth.** Layer preventive, detective and responsive controls so that one failure does not become a compromise. The guidance gives the layers and their controls directly: [^2]

| Layer | Your controls | Platform features you can use |
| --- | --- | --- |
| Data | Field-level security, record sharing, data classification | Organization-wide defaults, sharing rules, Shield Platform Encryption |
| Application | Input validation, output encoding, CRUD and FLS enforcement | Apex security, Lightning Web Security, platform access controls |
| Identity | Session policies, credential management, access recertification | Login flows, session settings, multi-factor authentication |
| Integration | API authentication, IP restrictions, certificate validation | OAuth 2.0 infrastructure, named credentials |

Threat modeling is where the security thread stops being a checklist. The guidance is blunt that threat modeling must be part of designing the solution rather than a step before or after it, and it recommends applying the STRIDE categories (spoofing, tampering, repudiation, information disclosure, denial of service, elevation of privilege) to Salesforce-specific vectors: multi-org data flows, external integrations, custom Apex and Lightning components, Experience Cloud sites that expose unauthenticated users, and third-party and ISV code as a supply chain vector that crosses the trust boundary at install time or at runtime. [^2]

That list is the same list the integration and lifecycle threads are working on. A vendor package installed to save three weeks is a supply chain decision in the security thread, a lifecycle entry because it must be upgraded on the release calendar, and an integration boundary if it calls out.

## Data: volume and retention decide more than the model does

Data design that stops at the entity relationship diagram is missing the half that breaks. The volume guidance defines the shape of the problem: tens of thousands of users, tens of millions of records, or hundreds of gigabytes of record storage counts as a large data volume. [^6] The same guidance names what actually degrades, which is narrower than people expect. It is loading and updating large numbers of records, either directly or through integrations, and extracting data through reports, queries or views. [^6]

Three strategies cover most of that ground. [^6]

1. **Follow standard database practice for schema changes and operations.** Do not treat the platform as exempt from how large relational datasets behave.
2. **Defer or bypass business rule and sharing processing** where the load does not need it, so a bulk update is not also recomputing access for every row.
3. **Choose the most efficient operation for the task**, which is a design statement rather than a tuning tip. A nightly wipe and reload is a different architecture from an incremental upsert, and the choice belongs in the design document.

Retention is the other half, and it is usually a legally named number that nobody has attached to a design. Where did the record live before, where will it live in year three, and which system answers a query about a five-year-old record? For very large histories the platform offers Big Objects, which the guidance describes as storing massive amounts of data with consistent performance from one million records to one billion, populated by Bulk API or Batch Apex, which is also the tool it recommends for archiving. [^6]

Put the data decisions next to the security decisions and a familiar conflict appears. Archiving moves records out of the object the sharing model protects, so the archive needs its own access story. Virtualization keeps records out of the org entirely, so the record-level security you designed does not apply to them and the external system's rules do. Two threads, one decision, and the seam is exactly where a test defect shows up six weeks after go-live.

## Lifecycle: the pipeline is part of the architecture

Deployment is the thread most often described as a project activity rather than an architectural one, and the framework's DevOps guidance treats it as design. Its design principles read like architecture requirements: evolve with observability, standardize operational procedures in source control alongside application code, embrace a DevOps culture, automate repetition, and learn from every operational event. [^5] The observability principle is worth quoting to a sponsor, because it makes instrumentation a design input rather than a later project: observable systems reveal how they actually behave under real conditions, and instrumentation and telemetry decisions shape data models, integration patterns and component boundaries. [^5]

The DevOps guidance then prices three operating models instead of declaring one correct, which is the part candidates and clients find most useful. [^5]

| Model | What it looks like | What it buys, and what it costs |
| --- | --- | --- |
| Lean optimized | Source-controlled metadata deployed manually by CLI or a managed IDE, with manual validation and rollback | Lowest pipeline overhead and the fastest path to production for a small surface. As the team and component count grow, manual deployment becomes the bottleneck and quality rests on individual discipline |
| Scale optimized | Automated continuous integration and deployment, a protected main branch that blocks merges until checks pass, promotion through sandbox tiers | Repeatable, gated change at a safe cadence with regressions caught before merge. You pay for building and operating the pipeline and keeping the test suites and sandbox tiers current |
| Governance optimized | Approval gates and progressive exposure on top of the pipeline, consistent change governance across orgs | Provable, accountable, reversible change at enterprise scale, against approval and audit weight on every change |

Choose one on purpose and write down why. A 900-person company with one administrator buying governance-optimized release management has purchased process it cannot staff. A regulated insurer running lean-optimized manual deployments into three orgs has bought a compliance finding.

Lifecycle also sets the calendar the other threads live on. Release windows in February, June and October, preview instances 4 to 5 weeks earlier, and no rollback for a managed package all belong in the deployment plan, exactly as lesson 83 priced them. [^5]

## Worked example: stitching the threads on one program

A specialty insurer is replacing a claims intake spreadsheet with Service Cloud. Claims arrive by email, by broker upload and by phone. A policy administration system owns policy, premium and payment data. The regulator requires ten years of retention on claim documents with an audit trail. Six hundred adjusters work cases, brokers upload in bursts during renewal season, and the security architect insists on single sign-on from the corporate identity provider.

Here is the same program read as four threads and then as one design.

| Thread | The decision | The constraint it lands on another thread |
| --- | --- | --- |
| Integration | Claim status events inside the platform; nightly policy reference load from the policy system; no virtualized policy read | The claim object needs an external identifier from the policy system before any event can be correlated |
| Security | Single sign-on for adjusters, community identity for brokers, field-level security hiding reserve fields, private organization-wide defaults with sharing sets for broker access | Broker sharing scope has to be expressible as a record filter the sharing engine can evaluate, which rules out the "one community user per broker firm" shortcut |
| Data | Claim attachments to long-term storage with an audit record per document, plus a monthly reconciliation count | The security model no longer protects the archive, so the archive needs its own access control and its own evidence |
| Lifecycle | Scale-optimized pipeline, protected main branch, promotion through a full sandbox, hardening window ahead of each release | Test data must be volume-realistic or the sharing performance regression will not appear until production |

Now read the constraints back into a build order. Identity first, because broker sharing depends on it. Policy external identifier before event correlation, because the integration thread cannot finish without it. Volume-realistic test data before performance sign-off. Archive access control designed with the retention requirement, not after it, because a regulator asking who read a claim document will not accept "the platform".

That is the whole technique. For each thread, name the decision; for each decision, name what it forces elsewhere; then sequence by dependency rather than by whoever is available.

## Exam traps

**Answering in only one thread.** A scenario that mentions an external system of record, a regulator and a mobile workforce is testing whether you link the threads. A response that covers integration patterns and stops is half a design.

**Defaulting to middleware.** Adding an integration platform is a pattern choice with a maintenance cost, and the decision guidance puts existing tools and landscape ahead of new components for exactly that reason. [^4]

**Treating the shared responsibility line as rhetoric.** The split of platform security and solution security is a scored distinction. Say who owns which control.

**Confusing volume with record count.** Tens of millions of records matters less than which operations run over them, because the guidance identifies loading, updating and extraction as the processes that degrade. [^6]

**Choosing a pipeline by aspiration.** Lean, scale-optimized and governance-optimized each carry a real cost. Name the cost you are accepting. [^5]

**Threat modeling after the design.** The guidance is explicit that threat modeling belongs inside design, and that third-party and ISV code crosses your trust boundary at install time or runtime. [^2]

## Try it

Take a live or hypothetical program and do one pass through the table above, in this order.

1. **Write the authority sentence.** One line per domain: which system owns which fact. If two systems can both claim a fact, you have found the integration defect before the build.
2. **Choose three patterns.** For three distinct requirements, name the pattern from the published set and the reason, plus the failure path for each. [^3]
3. **Draw the trust boundaries.** List every crossing, including ISV packages and Experience Cloud surfaces, and name what authenticates at each. [^2]
4. **Write the volume sentence.** Records per object today, expected in three years, the largest operation that runs over each, and where the record lives in year five. [^6]
5. **Pick a DevOps model and price it.** Name it, justify it against team size and regulatory exposure, and write down what it lets you defer. [^5]
6. **Sequence by dependency.** Order the work by what constrains what, not by domain. Then check the order against the release calendar.

Score the result on one thing: for each of the four threads, can you name the decision, the constraint it lands elsewhere, and the evidence you would accept that it works? Seams that cannot answer all three are the ones that will fail in production testing.

## What's next

You now have the method for a complete Salesforce architecture: one identity spine, a pattern chosen per integration requirement, data decisions made against volume and retention rather than the diagram alone, and a deployment model chosen with its cost named. The same four threads show up in systems that are not Salesforce at all, and increasingly that means platforms built around autonomous agents, where integration, trust, data and lifecycle each take on a new failure mode. Lesson 85 walks through general systems architecture end to end, using the architecture of an AI platform as the worked example, so you can see which parts of this method transfer unchanged and which do not.
