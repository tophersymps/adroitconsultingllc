# Lesson 8: Reports and dashboards in production: joined reports, dynamic dashboards, subscriptions, and row-level security

The Monday pipeline call starts badly. The VP opens the dashboard and sees a pipeline number that is forty percent smaller than the one the regional manager sees on her own screen. A monthly KPI email lands in five inboxes with an empty attachment. Someone asks for a single dashboard tile that compares open pipeline against closed won and the report builder simply will not build it. Three complaints, one afternoon, and none of them is a broken formula.

Every one of those failures has a name and a cause, and in production they repeat in the same order. The number differs by viewer because of the running user and the sharing model. The email arrives empty because the schedule runs as a user who cannot see the records. The tile will not build because a joined report cannot be used as a dashboard source. A consultant who can name the failure on demand and reach for the right fix is worth more on a go-live day than one who rebuilds reports from scratch and hopes.

This lesson serves objective sl-4b in the Sales Lifecycle domain, worth 20% of the exam, and asks you to identify ways to transform business outcomes and sales KPIs into reports and dashboards, taken to the production stage where the scenario items live. By the end you will be able to diagnose the standard failures, set the running user to produce the number you intend, and explain the limits that decide what can and cannot be built.

## Deep Dive

### The four failure modes you can name on demand

Production report and dashboard problems fail for predictable reasons, so treat each one as a diagnosis rather than a mystery. The field is missing because the report type does not expose it, and no filter brings it back. The number differs by viewer because the running user renders a different data scope under sharing. The subscription does not arrive, or arrives empty, because of folder access or because the schedule runs as a user who cannot see the records. The component cannot be built because a joined report cannot feed a dashboard component. Learn these four and the scenario items on this objective stop being trick questions and start being pattern matches.

Each failure points at a different fix, which is why naming it correctly matters. A missing field means go back to the report type and choose or build one that exposes the object and relationship you need. A number that changes by viewer means check the running user before you touch the formula. An empty subscription means check who the schedule runs as and whether the folder is shared. A component that will not build means restructure the data into a reportable relationship or split the tile in two, because the joined report is not a valid source. The exam rewards the diagnosis, not a rebuild.

### Row-level security on reports follows the object sharing model

A report returns only the records the running user can see, and that set is decided by the standard sharing model: organization wide defaults, the role hierarchy, sharing rules, and manual shares, plus territory sharing when Enterprise Territory Management is on. A user with View All Data sees everything regardless, which is why an admin testing a report often sees a correct number that a rep will never see. Field level security hides fields even when the object itself is visible, so a column can vanish for one audience while the row count stays the same.

Report folder access is a separate gate again, and this is the one people forget. A user needs the folder shared at View or higher plus the Run Reports permission, or the report simply is not there for them. Put those two mechanisms together and the most common production complaint resolves itself: a report that is empty for one viewer and full for the admin is almost always the viewer's position in the role hierarchy, or their lack of folder access, and it is almost never a filter. Diagnose at the access layer before you suspect the report's logic.

### Scheduled reports and subscriptions have their own access rule

A report can be scheduled to email its results on a recurrence, and the schedule runs as a specified user. That single fact drives most subscription problems. The specified user must be able to see every record the report should include, because the schedule renders in that user's data scope. Recipients do not need record access to receive the email, but they do need the report folder shared to open the live report behind it. So a subscription that arrives empty is a running user problem even when every recipient can see the records themselves.

Dashboard subscriptions behave a little differently. The dashboard is rendered as the dashboard's running user and then sent to subscribers, so subscribers see the running user's data scope rather than their own. A subscription that shows different numbers from the dashboard you open by hand is almost always a running user mismatch between how you opened it and how the schedule runs it. When a KPI email is wrong, check the running user first, the folder share second, and the report logic last.

### Dynamic dashboards and run as another user solve opposite problems

These two features get confused because they both promise to stop you cloning dashboards for every team. They solve the problem from opposite ends. Run as another user renders the dashboard as one specific user and shows that user's data scope to everyone who can view it, which is the standard way to give every viewer the same company wide number. A dynamic dashboard renders as the logged in viewer, so each person sees only their own records without you building a separate dashboard, at the cost of an org entitlement that caps how many dynamic dashboards you may own.[^3]

Choose from the goal. If everyone must see the same pipeline, run as another user. If each rep must see their own pipeline and you do not want to clone dashboards, dynamic dashboards, and accept that you may hit the cap, which for Enterprise Edition is a small number and for Unlimited and Performance Editions is somewhat higher.[^6] Two wrinkles worth memorising: you cannot schedule a refresh or subscribe to a dynamic dashboard, and deleted dynamic dashboards that sit in the recycle bin still count against the limit until they are permanently deleted.

### Joined report limits worth memorising

A joined report combines up to five report blocks into one layout, and each block can carry its own report type and its own filters.[^1] That is what lets you put two different subjects side by side, such as open pipeline in one block and closed won in another, with common columns across the blocks and block specific columns within each. Each block still obeys its own report type's field set, so you cannot show a field in a block whose report type does not expose it.

Two limits carry the exam weight. First, a joined report cannot be used as a dashboard component's source, so any requirement to build a single dashboard tile comparing two objects is impossible as written. You build two components, or you restructure the data into one reportable relationship so a single report type can carry both facts. Second, because each block is bound to a report type, a joined report cannot invent a relationship the data does not have any more than a single report can. Saying "that needs two components or a data restructure" is the correct answer, and it is the answer a lot of candidates miss because they try to build the impossible tile.

### Custom report types, trending, and snapshots for the trend questions

When a requirement needs object combinations no standard type exposes, you build a custom report type. It defines a primary object with up to four related objects, and the with or without setting on each relationship determines inner versus outer join behaviour. With related records means the report returns only primary records that have at least one related record, an inner join. Without means it returns primaries even with no match, an outer join. Those two settings are how the same data answers "accounts that have opportunities" and "accounts including those with none".

For change over time, two mechanisms matter. Historical trend reporting uses a special custom report type that highlights changes between five snapshot dates on a small set of tracked fields and objects, and it refreshes on a schedule rather than on demand.[^5] It is designed for days and weeks, not months, and it retains a rolling window of recent months. A reporting snapshot works differently: it writes the results of a tabular or summary report into a custom object on a schedule you set, so you build your own history you can chart.[^4] When a requirement is to show how pipeline coverage moved month over month, the reporting snapshot is the mechanism that makes it possible, because the live report can only ever show the current values.

### The format limits the exam probes

Know the format ceilings cold, because the exam probes them directly.[^2] A summary report allows up to three row groupings. A matrix report allows up to two row groupings and two column groupings, for a cross tab. A tabular report has no grouping at all and cannot serve as a dashboard source. When a question describes a grouping that exceeds these ceilings, the limit itself is the trap, and the right answer acknowledges that the layout as described cannot be built.

On the component side, a dashboard component points at a source report, and conditional formatting highlights values against thresholds you set, so a metric can turn colour when it crosses a target without any formula. The control set across reports and dashboards is consistent: bucket fields group values without a formula, row level and summary formulas calculate, and cross filters filter by a related object. Keep that mapping in your head and you can answer a format or control question without hesitating, because you will be choosing by mechanism rather than by the sound of the label.

## Exam Traps

Three traps dominate this objective. The first is thinking a joined report can back a dashboard component. Joined reports cannot be used as a dashboard source, so a tile that needs two objects means two components or a data restructure, never a joined report wired into a chart. The second is assuming a scheduled report runs with the recipient's access. The schedule runs as the specified user, so the wrong user changes or empties the numbers regardless of who receives the email. The third is believing dynamic dashboards and run as another user are interchangeable. Dynamic dashboards show each viewer their own scope and consume an org entitlement, while run as another user shows one shared scope to everyone, so the two are opposites and the requirement's goal picks between them.

Two more sit just behind. A dynamic dashboard cannot be scheduled for refresh or subscribed to, so an answer that promises a nightly refresh of a dynamic dashboard is wrong. And custom report type joins are set by the with or without option, not by a filter, so a scenario about including primaries with no related records is answered by the join setting rather than by any control in the builder.

## What a consultant should walk away with

When a report or dashboard gives the wrong number, check three things in order: the report type, which decides whether the field exists, the running user, which decides whose access rendered it, and the folder share, which decides who can open it. When a KPI email is wrong, add one more check first, because a scheduled report runs as the specified user and an empty subscription is nearly always that user's data scope. When a requirement asks for one shared number, run the dashboard as one specific user; when it asks for each viewer's own number, reach for a dynamic dashboard and watch the entitlement. And when a requirement asks for a tile that compares two objects, remember the joined report cannot feed a dashboard and answer with two components or a data restructure.
