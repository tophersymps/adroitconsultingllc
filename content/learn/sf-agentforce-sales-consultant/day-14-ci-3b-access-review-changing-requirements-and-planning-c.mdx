# Lesson 14: Access review, changing requirements, and planning continuous improvement after go-live

A security review flags that a departing sales rep holds Modify All Data. The admin's first move is to assign a more restrictive profile, reasoning that the baseline should override the grant. Nothing changes. The permission still applies, because the user's effective access is the union of the profile and every permission set assigned to them, and shrinking the profile does not subtract a permission a permission set still grants. The admin hardened the wrong layer and reported the finding resolved.

That is the counterintuitive mechanism at the heart of this objective, and it is the reason access review is a skill rather than a checklist. Day 13 covered the diagnosis. This lesson covers the three things the objective asks you to do about it: review user access, absorb changing business requirements, and leave a continuous improvement plan behind. Scenario answers in this half turn on trade-offs rather than definitions, and the defensible answer is usually the one that still works when the enthusiastic consultant is no longer on the engagement.

This lesson serves requirement ci-3b in the Consulting and Implementation Strategies domain, which carries 25 percent of the exam. It teaches the access model that decides a review, the classification that decides how a late requirement is handled, and the plan that decides whether adoption holds after your team leaves. After it, you should be able to run an access review, route a change request, and defend the improvement plan you leave behind.

## Deep Dive

### Access review starts with the mechanism, because the mechanism is counterintuitive

A profile supplies a baseline and permission sets add to it, and the user's effective access is the union of the profile and every assigned permission set. Nothing subtracts, with one exception: a muting permission set inside a permission set group can mute specific permissions granted by that group, and it does not affect what a profile grants or what a permission set assigned outside the group grants.[^1] Important detail: muting only impacts users assigned to the group, and users assigned directly to the included permission sets outside the group remain unaffected.[^2]

The consequence for least privilege is the sentence to remember. A restrictive profile does not reduce access granted by a permission set, so the only way to shrink a user's access is to unassign the permission set that grants it, or to mute it inside the group.[^4] Forget that and you will harden the profile while the user keeps Modify All Data through an assignment nobody reviewed. The exam builds its first question on exactly this: restrictive profile plus a permission set that grants Modify All Data yields the union, so the user keeps the permission until the assignment is removed.

### The mechanics of a review, and the cadence that keeps it alive

The mechanics of a review are a report and a cadence. Pull the permission set assignment data, join it to the user's last login date, and look for three things: assignments held by users who have not logged in, high-privilege permissions such as Modify All Data, View All Data, Manage Users, and Author Apex, and access that was granted by profile where you intended a permission set. Where the org wants this to be repeatable, User Access Policies let you grant and revoke access automatically based on user criteria, which turns the quarterly scramble into a rule that runs on its own.[^3] A user access policy can grant or revoke permission sets, permission set groups, permission set licenses, package licenses, public groups, and queues, and you can set it to run when a matching user is created, updated, or both.[^5]

Two habits make the review defensible. First, deactivate departing users rather than delete them, because ownership of records matters and a deleted user orphans their accounts and opportunities. Second, read the user's login history before you pull the access, because a dormant account with a recent login is a finding rather than a cleanup. The review ends with a documented list of what changed, who approved it, and when, which is why the Setup Audit Trail, with its roughly 180-day window, is part of the same habit rather than a separate task.[^6]

### The agent is a user, and it belongs in the review

An Agentforce agent runs with an identity that carries its own profile and permission sets, so an over-privileged agent user is not a theoretical risk: it is an escalation path, because anyone who can influence the agent's input can influence what it does with that access. Review the agent user the way you review a human employee. Verify that it cannot reach objects it does not need, and include it in the same assignment audit rather than a separate exercise, or it will be the one identity nobody re-reviewed.

There is a communication point inside this too. Tell users plainly that the agent can act on data rather than only read it, because users who assume the agent is read-only will describe the system wrongly to their customers. Pair that message with the Einstein Trust Layer settings, which have to be enabled in the org and which decide what happens to the data a user puts into a conversation. A user who does not know whether the agent can write, or what happens to what they type, will either misuse it or avoid it, and both outcomes are your problem after go-live.

### Changing requirements need a classification and a route

Changing requirements need a classification and a route, and the classification is what the exam rewards. A defect against the agreed requirement goes back to the team at no charge inside the hypercare window. A configuration tweak rides the normal deployment path. A new capability is scope, and scope has a cost, a decision maker, and a date, which usually means the next release rather than next week. A data model change is the expensive class because it touches reports, integrations, and any code that references the field, so it gets a design review even when the field looks trivial.

Two weeks after go-live the business will ask for something new and reasonable. The right answer is not to refuse it and not to build it untested. It is to log it, size it against the success metrics, and schedule it into the release cycle. The exam will hand you a scenario where the business asks for a new object and a new record page three weeks in, and the correct response is that sequence: log, size, schedule. Building it immediately is wrong because the hypercare window covers defects, not new scope. Declining outright is wrong because the requirement is legitimate. Deploying it untested is wrong because direct production edits are how sandbox and production drift apart.

### Continuous improvement is a commitment with four named parts

Continuous improvement is a commitment with four named parts, and the objective says plan for it, so answer with a plan rather than an intention. Name the owner who carries it after the project closes. Name the cadence, which for a launch is a standing 30/60/90 day review. Name the metric, which is the success metric you defined before implementation, so improvement is measured against a baseline and not against memory. Name the intake path, so a user who finds friction has somewhere to send it and a champion who triages it.

Without the owner and the intake path, the plan is a slide, and the friction backlog quietly expires the week the project team leaves. Two supporting moves keep it alive: tie releases to the three-times-a-year upgrade cycle so there is always a nearby window, and keep sandbox preview regression testing on the calendar before each upgrade. The exam frames the failure as an intention that everyone agreed was a good idea and nobody owned, and the correction is the four names.

### The failure modes, and reading the domain as three phases

The failure modes in this half are worth naming because scenario questions are built from them. A big bang go-live with no hypercare owner. Training delivered six weeks before launch, so it is forgotten by the time users start. A single Full sandbox shared by integration, UAT, and training, so it is never refreshed. Access granted by profile instead of permission set, so revoking access means rebuilding a profile. No document saying what was deployed, so a regression cannot be traced. An agent activated in production without testing it in the sandbox preview. Every one of these is cheap to prevent and expensive to discover, and the exam builds its distractors from the version of the answer that skips the step.

Read the whole domain as three phases and place each action correctly, because that placement is what most of these questions test. Pre-implementation is assessment, planning, and metrics. Implementation is sandbox strategy, deployment path, data load, cutover, and verification. Post-implementation is adoption diagnosis, requirement intake, access review, and the improvement plan. A success metric belongs pre. A rollback plan belongs during. A permission set review belongs post. When two answers both sound reasonable, the one that sits in the right phase and leaves a repeatable mechanism behind is the right answer, and the Salesforce Administrator and Advanced Administrator certification tracks, ADX201 and ADX211, are where the underlying access mechanics are taught properly.

### A worked access review, from pull to action

Run a concrete review. You export the permission set assignments, join them to last login dates, and sort the result three ways. First, assignments held by users who have not logged in for ninety days: those are revocation candidates, but you read each user's login history first, because a dormant account with a recent login from an unexpected address is a security finding rather than a cleanup. Second, the specific high-privilege permissions, Modify All Data, View All Data, Manage Users, and Author Apex: you list every holder and confirm each one is justified by the role, because those four permissions are what an auditor looks for and what an over-privileged agent user silently carries. Third, access granted by profile where the design intended a permission set: you move those grants into assignments, so that revoking access later is a single unassign rather than a profile rebuild.

The output is a document, not an impression. It names each user, the change you propose, the reason, and the approver. Where the org wants the review to run itself, you build a user access policy that grants or revokes from user criteria, so the next review starts from an accurate baseline instead of a scramble. You then extend the same document to the agent user, because the agent's profile and permission sets are an identity that can act, not a feature flag, and an agent holding Modify All Data is an escalation path nobody reviewed.

## Exam Traps

Three traps dominate this objective. The first is believing a restrictive profile can remove access granted by a permission set. Effective access is the union of the profile and every assignment, so nothing subtracts except a muting permission set inside a permission set group, and the fix is to unassign the permission set or mute it in the group. The second is believing the agent user is exempt from access review. The agent acts with its own permissions, so an over-privileged agent user turns the agent into a real escalation path rather than a reader of records, and it belongs in the same audit as a human employee. The third is believing continuous improvement runs itself after the project closes. Without a named owner and an intake path, the friction backlog has nowhere to go and adoption decays silently, which is the quiet failure the objective is written to prevent.

## What a consultant should walk away with

Run the access review off the mechanism, not the instinct: effective access is the union, only a muting permission set inside a group subtracts, so shrink access by unassigning permission sets and by muting inside the group, not by hardening profiles. Look for dormant users with recent logins, high-privilege permissions granted by profile, and the agent user alongside your humans. Deactivate departing users rather than delete them, and put User Access Policies behind any review you want to run itself. Classify every late requirement as defect, tweak, new capability, or data model change, and route it through the sandbox pipeline rather than into production. Then leave a plan with an owner, a cadence, a metric, and an intake path, tied to the release calendar, or the improvement you promised will expire the week you leave.
