# Lesson 7: Turning sales KPIs into reports: report types, filters, and the Lightning report builder

A sales leader asks for win rate by quarter. You open the report builder, find the Opportunities report type, and build a report grouped by quarter with a count of closed-won rows. The number looks fine until someone points out that a quarter where the team won two deals out of two shows a hundred percent, and a quarter where they won fifteen out of forty shows thirty seven. The count was never a win rate. It was a tally dressed up with a confident label, and the leader will make a real budget decision on it.

The naive approach is to start from the question and reach for the first field that sounds right. That is how teams end up with a report built on the wrong report type, missing the field they actually need, and trying to patch it with a filter that cannot possibly help. A report cannot show a field its report type does not expose, so no amount of filtering recovers a bad starting choice. The second failure is subtler: building a ratio as a raw count or a grand total, which produces a number that means something different from the KPI on the slide.

This lesson serves objective sl-4a in the Sales Lifecycle domain, worth 20% of the exam, and asks you to identify ways to transform business outcomes and sales KPIs into reports and dashboards. By the end you will be able to choose the report type that exposes both halves of a KPI, pick the format that shows it honestly, build the ratio as a formula, and set the dashboard so every viewer sees the number you intended.

<TLDR>

- Start every KPI with the report type, because it governs which objects and fields exist before any other control does
- Most KPIs are ratios, so build them as a summary formula on a summary report rather than a raw count
- A dashboard filter works only on fields shared across the source reports, and the running user decides whose scope renders

</TLDR>


## Deep Dive

### The report type decides which fields exist at all

Start every KPI with the report type, because the report type governs which objects and fields are available before any other control does.[^1] Standard report types ship with the product, so Opportunities, Accounts with Opportunities, and Campaigns with Contacts are ready on day one and cover most sales questions. When a requirement needs an object combination or a relationship path that none of the standard types exposes, you build a custom report type. The exam keeps landing on the same point: a field appears in the builder only if the report type exposes its object and its relationship, so a missing field is proof of the wrong report type rather than a filter or permission problem.

![The report type is the gate that decides which fields exist: a win rate KPI needs the count of won opportunities and the count of all closed ones, pipeline coverage needs open pipeline value and quota, and the report type chosen must expose both numbers, because a missing field is proof of the wrong report type rather than a filter or permission problem.](</diagrams/day-07-sl-4a-turning-sales-kpis-into-reports-report-types-filte/1-report-type-gate.png>)

Read the KPI and ask which two numbers it needs. A win rate needs the count of won opportunities and the count of all closed ones, which the Opportunities report type provides. Pipeline coverage needs open pipeline value and quota, which may live on different objects and force a custom type. Once you have both halves, choose or build the report type that surfaces both, and only then move on to format and filters. Doing this step last is the single most common cause of a report that cannot be made to work.

### The four formats, and what each one is for

Salesforce gives you four report formats, and the format is really a decision about what the reader sees first.[^2] A tabular report is a flat list of rows with no grouping, closest to a spreadsheet, and it cannot be used as a dashboard source. It is for a mailing list or an activity export, not for a KPI tile. A summary report groups rows with subtotals on one or more groupings and can feed dashboard components, which is why summary is the format behind most dashboards. A matrix report groups on both rows and columns for a cross tab, so you can compare, say, stage by quarter in a grid. The fourth format, joined, combines multiple report blocks into one layout, and because each block can carry its own report type, a joined report is how you place two different subjects side by side, such as open pipeline against closed won.[^3]

![The four report formats side by side: tabular is a flat ungrouped list and cannot be a dashboard source, summary groups rows with subtotals and is the format behind most dashboards, matrix groups on rows and columns for a cross tab, and joined combines up to five blocks, each carrying its own report type, which is how two subjects sit in one layout.](</diagrams/day-07-sl-4a-turning-sales-kpis-into-reports-report-types-filte/2-four-formats.png>)

Choosing the format is choosing emphasis. If the reader needs a number per group, a summary gives it. If they need to compare one dimension against another, a matrix gives the grid. If they need two facts from different objects in one layout, a joined report is the only format that holds both, because a single block is bound to one report type. Note the limits while you are here: a joined report can hold up to five blocks, each block still obeys its own report type's field set, and a grouped format cannot simply invent a relationship the data does not have.

### Filters, cross filters, formulas, and buckets in the Lightning builder

The Lightning report builder is the current interface, and the controls that carry the exam weight are filters, cross filters, formulas, and buckets. A standard filter scopes the rows by a field value, so you might filter to opportunities with a close date in the current quarter. A cross filter filters by a related or parent record, which is how you answer questions about absence: accounts with no activities, or opportunities with no contact roles. That is the tool for "show me the gaps", because a normal filter can only test a value that exists on the row.

Formulas and buckets are the pair people confuse. A row level formula adds a calculated column on each row, such as a days open calculation. A bucket field groups existing values into bands, so you can turn a scatter of annual revenue figures into size tiers without creating a formula or a new field. The habit that matters: when the requirement is to group a whole range of values into a handful of bands, reach for the bucket field, because a formula calculates a value and does not group rows into categories. Buckets are also the usual answer to "how do I band this without building a custom field".

Two builder limits are worth carrying into the exam. A report supports a fixed number of field filters, so a report with a dozen conditions is usually a sign you should have started from a tighter report type or used a cross filter instead of stacking single field filters. And the Rows to Display filter, which caps how many rows a report returns, disappears the moment you switch from tabular to a grouped format, because a grouped report returns subtotals rather than a raw capped list. When a requirement says show the top ten by amount, that is a grouping with a sort and a limit on the group, not a row cap, and the distinction is exactly the kind of thing the scenario items probe.

When the requirement is to find what is missing rather than what is present, a cross filter is the only control that works. A normal filter tests a value on the row itself, so it can confirm that an opportunity has an amount but cannot ask whether that opportunity has a contact role. A cross filter reads the related object and returns the parent records where the related condition is absent, which is how you answer "accounts with no activity in ninety days" or "opportunities with no product line". That pattern shows up constantly in adoption and hygiene scenarios, and reaching for a cross filter rather than a field filter is the mark of someone who has built these reports before.

### A KPI is a ratio, so build it as a summary formula

Most sales KPIs are ratios, not counts. Win rate, average deal size, and pipeline coverage, which is open pipeline divided by quota, are all one number divided by another. A raw count of closed-won opportunities is not a win rate, and the exam offers that count as a distractor precisely because the label sounds right while the math is wrong. To build a ratio you add a summary formula to a summary report, where the formula is evaluated over the grouped rows and can reference other groups.

![A count of fifteen closed-won opportunities is not a win rate, while the ratio of fifteen won out of forty closed reads thirty seven percent, and the ratio is built as a summary formula that divides the group amount by PARENTGROUPVAL of the grand summary on a summary report.](</diagrams/day-07-sl-4a-turning-sales-kpis-into-reports-report-types-filte/3-count-vs-ratio.png>)

Two functions do most of the work. PARENTGROUPVAL returns the value of a parent grouping, so AMOUNT:SUM divided by PARENTGROUPVAL(AMOUNT:SUM, GRAND_SUMMARY) gives each row's share of the grand total, a textbook percentage of total.[^4] PREVGROUPVAL returns a peer grouping, which is how you compare a group against the one before it, such as this month's pipeline against last month's.[^5] Both live only on summary or joined reports, not on tabular, and both need the display setting to match the grouping level you are referencing. When you are asked to turn a count into a rate, this is the tool, and it sits on the summary report rather than in a chart setting.

### Dashboards sit on top of source reports

A dashboard is a set of components, each one a chart, gauge, metric, or table, and each component is bound to a source report or, for filtering, to several reports running as the same user. That binding is where dashboard problems are born. A dashboard filter lets the viewer slice every component that exposes the filter field, but only fields shared across the dashboard's source reports can be used as a filter. If your refreshed pipeline dashboard has three components built from three report types with no field in common, the filter you want does not exist, and the fix is to design the source reports to share a field such as Close Date or Owner whenever the dashboard must be filterable as a whole.

Design the reports for the dashboard, not the other way around. Decide first which slice the viewer will want, say by region or by quarter, then confirm that every source report exposes that field. A dashboard component cannot invent a field its source report lacks, any more than a report can show a field its report type omits. When a requirement asks for one filter to move every tile on the board, the requirement is really a data design requirement about the shared field.

### The running user and folder sharing decide what a viewer sees

The running user is the setting that decides whose data scope a dashboard or scheduled report renders in. Run as logged in user shows only the records the viewer can see under sharing, so two people can legitimately see two different totals on the same dashboard. Run as another user, a specific named user, renders that user's data scope for everyone who can view the dashboard, which is the standard way to give every viewer the same company wide number. A dynamic dashboard instead renders each viewer their own scope, at the cost of an org entitlement that caps how many dynamic dashboards you may own.[^6]

Reports and dashboards also respect the sharing model and field level security. A report returns only records the running user can see, so a total that looks too small often reflects the viewer's position in the role hierarchy hiding records, not a broken formula. Field level security hides fields even when the object is visible, so a column can disappear for one audience and not another. Report folder and dashboard folder sharing is a separate gate again: giving someone a link is not enough if the folder is not shared with them, and a field only appears as a filter option if the report type exposes it. When a KPI tile shows the wrong number, check the report type, the running user, and the folder share, in that order.

### The build sequence in six steps

<Steps>

<Step title="In Setup">

In Setup, open Report Types and either select a standard type such as Opportunities or create a custom report type to expose the objects and relationship path your KPI needs.

</Step>

<Step title="Open the Reports tab">

Open the Reports tab, choose New Report, select that report type, and set the format to Tabular, Summary, Matrix, or Joined as the KPI requires.

</Step>

<Step title="Add fields to the report layout">

Add fields to the report layout, then use Filters for record scope and Cross Filters to filter by a related or parent record.

</Step>

<Step title="Build any ratio KPI with a Summary Formula">

Build any ratio KPI with a Summary Formula, for example a win-rate formula over grouped rows, and use a Bucket Field to group values into bands.

</Step>

<Step title="Save the report into a report folder">

Save the report into a report folder, set folder sharing, then on the Dashboards tab create a dashboard and add a component that points at the report as its source.

</Step>

<Step title="In dashboard settings">

In dashboard settings, set the running user and enable Dynamic Dashboards only if each viewer must see their own scope, then add dashboard filters for fields shared across the source reports.

</Step>

</Steps>


## Exam Traps

<Callout kind="warning">

Three traps dominate this objective. The first is thinking any report type can show any field. A field appears only if the report type exposes its object and relationship, so a missing field means you started from the wrong report type, not that a filter or permission is hiding it. The second is believing a count of closed-won opportunities is a win rate. Win rate is a ratio, and a ratio is built with a summary formula over the grouped rows, so a plain count answer is wrong every time. The third is assuming a dashboard filter can slice on any field. A dashboard filter works only on fields shared across the dashboard's source reports, so a filter request against a field the source reports do not share is impossible as written.

Watch two more. A tabular report cannot serve as a dashboard source, so any answer that points a dashboard component at a tabular report fails. And choosing joined when a single report type would do, or summary when the reader needs a cross tab, is a format mismatch that the label alone will not reveal. Read what the reader must see first, then match the format.

</Callout>


## What a consultant should walk away with

<KeyTakeaways>

- Treat a KPI as a ratio: choose the report type that exposes both numbers, then build the ratio as a summary formula
- Choose the format from what the reader must see first: a list, a grouped set of subtotals, a grid, or two subjects side by side
- Set the running user to match the intent, shared numbers or per viewer scope, and confirm every source report shares the field the filter needs
- Point the dashboard component at the report, and remember a tabular report cannot serve as a dashboard source at all

</KeyTakeaways>
