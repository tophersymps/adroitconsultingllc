# Lesson 37: Generative AI Tools Compared: Prompt Templates, Email Generation, the Trust Layer, and Bring Your Own Model

A sales team asks you to summarize every opportunity into a field the moment a rep requests it. You build an agent, give it a summary topic, and it works. Then the same team asks for an email draft, a field that auto-fills from the record, and a rule that the summary only ever reads the fields legal approved. Suddenly you are maintaining a small agent for what is really one generation with a known input and a known output, and you have made the feature harder to govern than the job required.

The generative surface in Sales Cloud is wider than the agent, and the exam treats it that way. There are prompt templates, email generation and draft replies, the security layer that mediates every call to a model, and the model itself, which can be one Salesforce runs or one the customer connected. The naive approach is to reach for an agent for every request, because an agent looks like the general answer. The problem with that is cost and control: an agent makes decisions you did not need it to make, it consumes model calls per turn, and it hides a single deterministic generation inside a loop that can wander. The better approach is to pick the tool that matches how many decisions the job actually requires.

This lesson serves requirement pg-1b, "Understand what generative AI tools are available in Agentforce Sales," in the Predictive and Generative AI domain, which carries 13 percent of the exam. Lesson 36 covered the agent and its four parts; this lesson covers the rest of the generative stack and how to choose between them. By the end you can create and type a prompt template, explain where a template runs, describe what the Einstein Trust Layer does to a prompt on its way to a model, connect a model of your own in Model Builder, and name the Data Cloud vocabulary that underpins grounding.

## Deep Dive

### A prompt template is one grounded generation, not a conversation

Prompt Builder is where you author a reusable generation, and the certification treats it as a distinct tool from an agent. A prompt template binds a prompt to a data source, so the inputs are typed and grounded rather than free text. You select the object and the fields or related records the template may read, and the template references those values through merge fields. That is what makes a template more reliable than a paragraph pasted into a chat: the values are not retyped by the user, they come from the record.

The practical consequence is that a template is deterministic in shape even though its wording varies. It performs one generation with known inputs and a known output shape. Salesforce's own guidance frames Prompt Builder as the tool for reusable, templated solutions for common workflows, with templates that securely access Salesforce data through merge fields, Flow, Data Cloud and Apex.[^1] When you write the prompt itself, be explicit about tone, length, and what the model must not invent. "Do not state a delivery date unless it appears in the record" belongs in the instruction, because the model will otherwise fill the gap.

### The template types map to the shape of the job

Templates come in types that match the work, and choosing the right type is half the exam's point.[^2] A Sales Email template drafts a personalized outbound message from record data. A Field Generation template returns content into a specific field on a record, and it has a direct relationship to that field, so a button or a Flow can trigger it and write the result back. A Record Summary template produces a narrative summary of a record for a comprehensive view. A Flex template covers anything the other three do not, and its inputs are not predefined: you define up to five resources yourself, choosing objects, files or free text as the inputs the prompt can reference.

![The four prompt template types by output shape: a Sales Email template drafts a personalized outbound message from record data, a Field Generation template writes content into a specific field that a button or a Flow can trigger, a Record Summary template produces a narrative summary of a record, and a Flex template defines up to five resources of its own for anything the other three do not cover.](</diagrams/day-37-pg-1b-generative-ai-tools-compared-prompt-templates-emai/1-template-types-by-output.png>)

Worked example. A rep wants a one-paragraph recap of an Opportunity and its products written into a custom field, with no conversation involved. That is a Field Generation template on the Opportunity, grounded on the Opportunity and its related records, run from a button or a Flow. If the business wanted the recap to appear on the record page as a formatted summary rather than in a single field, it would be a Record Summary template instead. If the recap had to combine the Opportunity, the Account, an asset and a piece of free text, the three-or-more-resource shape pushes you to Flex. Same content, different type, because the type decides what the output is and where it lands. Trailhead's field generation walkthrough shows the pattern: choose the type, name the template and API name, pick the object and the target field, then test against a real record.[^3]

### The lifecycle, versions, and the surfaces a template reaches

A template moves through a lifecycle of draft, in review, active, and inactive. You build it, preview it against a real record, send it through review, and activate it. Saved versions are retained, so you can roll back to an earlier prompt when a change produces worse output, which matters because a prompt edit is a behavior change and you want the previous behavior one click away.

One authored prompt reaches several surfaces without being rewritten. A template can run from Flow, from Apex, from the assistant, or as an agent action. That reuse is the reason to build the template rather than wire the same prompt into three places. It is also the reason to treat prompts as governed artifacts: because one template can power a rep's button and an automated Flow, changing it changes every surface at once. Salesforce's Prompt Builder documentation describes templates that can be batch-processed as well as invoked, so a template can generate at record scale rather than only one record at a time.

Treat generation as an operational feature from the first conversation. Generation costs money per call and takes time, so a template that fires on every record save behaves very differently from one a user triggers on purpose. Ground on the smallest sufficient scope, because a prompt stuffed with an entire account history slows the response and dilutes the signal. Keep a review gate on customer-facing output and remove it only where a wrong sentence is genuinely cheap. Then instrument the feature: track acceptance rate and edit rate on generated emails, because a template reps rewrite every time is a template that is not working, and that number is the only honest measure of whether the prompt is good.

### Email generation and draft replies share one failure mode

Email generation and draft replies are the two generative features a sales team meets first, and they differ in input and in risk. Email generation composes a new outbound message from the record and the template, so its quality depends on the fields and the knowledge you ground it with. Draft replies are generated responses to an inbound message, more common in service, and in a sales context they cover inbound inquiries and follow ups. One produces an open-ended message, the other responds to text the customer already wrote.

Both share a single failure mode: fluent, well-formatted text that states something untrue. A model asked to write a follow up after a call will happily invent a delivery window, a discount, or a commitment that was never made, and it will phrase the invention as confidently as the true parts. The mitigation is not a cleverer prompt on its own. It is grounding the template on the records that carry the facts plus a human review step in front of anything that leaves the org. Add the discipline that the model may only state what the record states, and keep the send button behind a person until the acceptance data proves the output is safe to release.

### When the job needs a template and when it needs an agent

This is the comparison the exam keeps asking for, and the deciding question is simple: how many decisions does the job require? A prompt template performs one generation with known inputs and a known output shape. Use it for a summary, a field fill, or a drafted email where the trigger already knows what it wants. An agent makes a sequence of decisions: it interprets an ambiguous request, selects a topic, selects an action, and may loop through several steps before answering. Use an agent when the request is open ended and the path is not known in advance.

![Tool selection by decision count: a prompt template performs one grounded generation with known inputs and a known output shape, used when the rep asks on demand with no conversation involved, while an agent interprets an ambiguous request, selects a topic and an action, and may loop through several steps before answering. The deciding question is how many decisions the job requires.](</diagrams/day-37-pg-1b-generative-ai-tools-compared-prompt-templates-emai/2-decision-count-chooser.png>)

The trap runs in both directions. A scenario that needs a single deterministic generation will offer an agent option as a distractor, and the right answer is the template. A scenario that describes an open-ended request, one where the user might want a lookup, then a summary, then a draft depending on what the summary says, will offer a prompt template as a distractor, and the right answer is the agent. Read the scenario for the words that give it away. "Whenever the rep asks, with no conversation involved" is a template. "The user can ask anything about the account and the agent decides what to do" is an agent.

### The Einstein Trust Layer, control by control

The Einstein Trust Layer sits between Salesforce and the large language model, and it is the answer to most security questions about generative AI.[^5] It performs dynamic grounding so the prompt carries retrieved record data. It applies data masking so sensitive field values are replaced with masked tokens before the prompt leaves Salesforce and restored, or demasked, in the response. It enforces zero data retention with the model provider, so your prompt and completion are not stored or reused for training. It runs toxicity scoring on the response, defends against prompt injection, and writes an audit trail that records the prompt, the response, and the data accessed.

![The journey a prompt takes through the Einstein Trust Layer: dynamic grounding retrieves record data, data masking replaces sensitive field values with masked tokens before the prompt leaves Salesforce, the model answers, the tokens are restored in the response, toxicity scoring runs before the text is shown, and an audit trail records the prompt, the response and the data accessed. Zero data retention governs what happens after the call rather than whether the prompt was sent, and masking is currently disabled for agents even though it is available for embedded features such as Einstein Service Replies and Work Summaries.](</diagrams/day-37-pg-1b-generative-ai-tools-compared-prompt-templates-emai/3-trust-layer-journey.png>)

Two nuances keep a strong answer from becoming a wrong one. First, zero data retention governs what happens after the call: the prompt is still sent so the model can answer, and what the policy controls is whether the provider stores or reuses it. A question that asks whether the data is sent at all is not answered by zero data retention. Second, masking is not uniformly applied everywhere yet. Trailhead's data masking material notes that for embedded generative AI features such as Einstein Service Replies and Work Summaries, masking is available and configurable in Einstein Trust Layer setup, and that data masking for LLMs is currently disabled for agents.[^4] Say that plainly if a scenario turns on it, because "masking is always on for everything" is a claim the product does not currently support. Salesforce logs masking activity as part of an audit trail so you can show what was masked and when.

When a question asks how Salesforce keeps customer data out of a third-party model, this is the mechanism, and it applies whether the model is Salesforce hosted or one you connected yourself. On the configuration side you confirm masking rules, the audit trail and toxicity scoring for the org, and you can see that the layered controls are what make a customer-facing feature shippable, because grounding decides whether the text is true and the Trust Layer decides whether it is safe to send.

### Model Builder, bring your own model, and the Data Cloud substrate

Model Builder, the surface formerly named Einstein Studio and now also described as AI Models, is how you bring your own model. You register a model from a provider such as Amazon Bedrock, Anthropic, Google, OpenAI, or Azure OpenAI by supplying the connection details and credentials, and Salesforce then exposes that model as a selectable choice for prompt templates and agents.[^7] Adding a foundation model establishes an endpoint connection between the external provider and Salesforce; you then create a model configuration and evaluate responses in a playground before you deploy it.[^6] For anything the named providers do not cover, the LLM Open Connector lets you connect a model you host yourself, provided the endpoint follows the expected path.

Bringing your own model changes which model answers. It does not bypass the Trust Layer, because masking, retention and audit are applied in Salesforce before and after the call. The trade-off is control against oversight. A customer with regional constraints can pin inference to a provider in their region, and in return they own that model's accuracy, latency and cost characteristics, along with the version management that comes with a model that can change under them.

Underneath all of it sits Data Cloud, the grounding substrate, and the exam expects the vocabulary. Data streams bring source data in, whether from Salesforce objects or external systems. The data model objects, the DMOs, are the harmonized schema the streams map into. Identity resolution unifies records into a single profile across sources. A search index, sometimes described as a vector index, chunks unstructured content such as documents and knowledge articles so it can be retrieved by similarity at generation time. Structured grounding sends the field values of a record; unstructured grounding retrieves relevant passages. Getting grounding right is a data management project with an AI delivery attached rather than the other way around.

## Exam Traps

Three traps dominate this objective. The first is believing bring your own model skips the Trust Layer. It does not. Masking, zero data retention and the audit trail all run in Salesforce regardless of which model you connected, because the controls sit around the call rather than inside the model. A scenario that implies an external provider escapes the security layer is testing exactly this.

The second trap is believing a prompt template and an agent are interchangeable. A template performs one grounded generation with known inputs, and an agent chooses topics and actions across multiple steps. When a scenario says the rep wants a summary on demand with no conversation, the agent option is the distractor. When the request is open ended and the path is unknown, the template is.

The third trap is believing generation quality is purely a prompt problem. An ungrounded prompt produces confident text with no relationship to the record, and the fix is the data source, not more adjectives in the instruction. A model that invents a date, a discount or a competitor claim is a model that was never given the fact, and the answer is grounding plus a review gate rather than a longer prompt.

## What a consultant should walk away with

Match the tool to the number of decisions the job requires: a prompt template for one grounded generation with known inputs, an agent for an open-ended request whose path is not known in advance. Choose the template type by the output shape, Sales Email for outreach, Field Generation for a field, Record Summary for a narrative, Flex for anything that needs more or different resources. Treat each template as a governed artifact with a lifecycle and retained versions, because one template can power a button, a Flow and an agent action at once. Assume the Einstein Trust Layer is doing the security work across grounding, masking, zero data retention, toxicity scoring and audit, and be precise that zero data retention governs storage and reuse rather than whether the prompt was sent. Reach for Model Builder when a customer needs a specific model or a specific region, knowing the Trust Layer still applies. Then ground on the smallest sufficient scope, keep a human review gate in front of customer-facing output, and instrument acceptance and edit rates so you know whether the feature is actually working.
