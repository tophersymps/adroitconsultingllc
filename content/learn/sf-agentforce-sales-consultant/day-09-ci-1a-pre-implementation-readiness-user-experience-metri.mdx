# Lesson 9: Pre-implementation readiness: user experience, metrics, and the discovery that prevents rework

A program hits go-live on a Tuesday with a clean deployment and a detailed communication plan. By the second week, adoption has quietly stalled. Nobody complained. Nobody filed a ticket. The reps simply kept the spreadsheet they had always used and opened Salesforce only when a manager asked for a report. The project team calls it a training problem and schedules another session, which changes nothing, because the real problem was decided weeks earlier when nobody watched how the reps actually worked.

The naive approach to readiness is to treat it as paperwork. Write the communication plan, list the training sessions, get the sponsor to sign, then configure. Each of those artifacts can be complete and the project can still fail, because readiness is not a set of documents you produce before go-live, it is a set of risks you either retire or wave through. A readiness assessment that skips the user experience or invents its metrics after launch does not prevent rework. It only delays the discovery.

This lesson serves objective ci-1a in the Consulting and Implementation Strategies domain, worth 25% of the exam, and asks you to assess user experience, communication plan, training, and change management before an implementation, and to establish metrics that measure success. By the end you will be able to run each assessment, set metrics that create an honest baseline, and name the readiness gap behind a scenario where adoption stalls.

## Deep Dive

### The four readiness areas, read as a sequence of risks

The official objective names four areas to assess before you configure anything, user experience, communication plan, training, and change management, plus the metrics that prove success. Read that list as a sequence of risks rather than a checklist of documents, because each item answers a different question. User experience answers whether the thing you are about to build fits the work people actually do. Communication answers whether they will know it changed. Training answers whether they can use it. Change management answers whether they will. Metrics answer whether any of it worked.

Each one, skipped, still lets you go live. That is what makes readiness dangerous. You go live into a project that fails quietly in month two, when the champion stops mentioning it and the old habit quietly returns. The reason to assess all five is not compliance, it is that each one retires a specific way the project can die. When a scenario describes a launch with a sponsor and a plan, and then asks why adoption stalls, the answer is almost always the readiness area nobody assessed.

### User experience assessment means counting the work

Assessing user experience means watching real users in their current tool and counting the work, not surveying them about features. How many records do they touch per day, which fields do they read versus write, what do they do when the system is slow, and do they work on a phone. Those observations tell you what actually has to be on the page, and they are cheap to gather and impossible to guess from an org chart.

Then map each observation to a Salesforce construct. A Lightning app groups the tabs and objects a role needs so they are not hunting through the full navigation. A Lightning record page built in Lightning App Builder controls layout. Dynamic Forms shows only the fields that matter for a given record type, so a renewal record is not buried under every field on the object. A compact layout decides what shows in the highlights panel, and a Path guides the rep through the stages of the sales process. Measure clicks before and after, because clicks are the currency users spend, and a design that adds five clicks to a task done forty times a day will be abandoned no matter how elegant it looks. Know one constraint that trips people up: once you add Dynamic Forms to a record page, that page takes over the fields section and the page layout no longer supplies the fields shown on it, so the layout you thought was driving the page is not.

### Metrics before go-live, with three parts each

Metrics come before go-live, and they come from the business. A metric invented after launch can only describe what already happened, which means the baseline is gone and you can never prove the project improved anything. A success criterion set before implementation, agreed with the business rather than with the build team alone, creates an honest baseline against which every later claim can be tested. Define them prior to implementation, as part of the readiness assessment.

Give every metric three parts: the source, the target, and the measurement date. Adoption rate comes from login history or the Adoption Dashboards app.[^5] Feature usage comes from the Lightning Usage App. Data quality comes from a report that counts records missing a required field. Business outcome comes from a report on the process itself, such as quote turnaround or opportunity close rate. If you cannot name the source, you do not have a metric, you have an opinion, and an opinion will not survive the first steering committee that asks how you know the rollout is working. Putting the metric on a dashboard the sponsor is subscribed to, rather than in a folder nobody opens, is what turns it from a slide into a governance tool.

A worked example shows how the three parts combine. Suppose the stated goal is faster quoting. The source is a report on the Quote object measuring the average days from creation to approval. The target is to cut that average from six days to three inside one quarter of go-live. The measurement date is the first business day of the following quarter, when the sponsor reviews the dashboard. Now the project can be judged. If average days only fell to five, the team has a specific number to investigate and a specific date to answer to. Contrast that with the vanity alternative, a target of "more users active in Salesforce", which no amount of good engineering can fail and no stakeholder can question, because it measures the tool rather than the business.

### A communication plan needs a way back

The communication plan needs an audience, a channel, a cadence, and a way back. For every role, state what changes, what they must do differently on the Monday after go-live, and who to contact when it breaks. That last part is the one teams forget. A plan that tells people a change is coming but gives them no route to raise a problem produces complaints in the hallway and nothing in the backlog.

A cadence that works looks like this: an announcement four weeks out, a role specific how to the week before, a reminder the day before, a hotline on go-live day, and a wins and friction note a week after. The trap is a communication plan that only announces the date. That produces a notification, not readiness, and notifications do not change behaviour, because knowing a system changed does not tell a rep what to do differently on Monday morning. The way back is what converts a passive announcement into a feedback loop you can act on.

### Training follows role, and the last mile is in the app

Training design follows role, not feature. A sales rep needs the four things they do daily, not a tour of every object in the org. Instructor led sessions catch role confusion early because you hear the questions, and they scale badly because they consume calendars and cannot be repeated for free. Self paced modules scale to hundreds of users and go stale the moment the configuration changes. The best last mile is an in-app guidance prompt on the record page, because it appears where the user is already looking, on the page where the work happens.[^1]

Pair a short formal session for the mental model with embedded guidance for the last mile. Time it close to go-live, because skills delivered six weeks early have decayed by the time the user ever needs them, and plan a refresher roughly thirty days out, once the questions have become specific.[^2] Pick the training environment deliberately. A Developer sandbox copies metadata only with a small data allowance, so users train on near empty records and never meet the volume that breaks them.[^3] When training has to feel real, choose a sandbox type that carries realistic data rather than the fastest one to refresh.[^4]

### Change management is the discipline that makes the rest land

Change management is what makes the other three areas land, and it is where projects actually fail. Build a business sponsor who communicates rather than just approves, and build user champions from the most affected group and involve them in design. The people who feel the change most are the ones who either sink it or sell it, and a champion who helped shape the design will defend it long after the project team has moved on. Treat resistance as data. When a group pushes back, find out which step costs them time and fix that step rather than arguing about attitude.

Two failure modes repeat. The first is a project with an executive sponsor and no champions, which stalls the moment the sponsor stops talking about it, because the message had no local voice to carry it. The second is a silent majority that never says anything is wrong and quietly keeps using the old spreadsheet, so the usage numbers look acceptable while the business value never appears. Both are readiness failures that a proper assessment catches before go-live, when a fix is a conversation rather than a rescue.

### Readiness also means assessing the data plan

Before implementation also means before you commit a data plan. Assess data quality and volume early, because they set the loading approach, the cutover window, and whether you migrate history at all. A readiness assessment that ignores data will promise a go-live date the data load cannot meet, and the slip lands at the worst possible moment. The mechanics you lean on here, the permission model, page layouts, and reporting, are the same ones an administrator relies on day to day, and the access controls that make an access review possible are the ones you configure now. Readiness is where the consulting half of this domain stops being theory and starts being a plan you can defend.

## Exam Traps

Three traps dominate this objective. The first is believing success metrics should be defined after go-live so they reflect real usage. A metric defined after go-live can only describe what happened, so the baseline is gone and you can never prove improvement, which is why metrics are set prior to implementation and agreed with the business. The second is thinking a Developer sandbox is fine for end user training. Developer and Developer Pro sandboxes copy metadata only, with tight data allowances, so users practise on nearly empty records and never encounter the volume the real org carries. The third is treating Dynamic Forms as additive to a page layout. When you add Dynamic Forms to a record page you take over the fields section, so the page layout stops supplying the fields on that page.

Watch two more. A communication plan that only announces a date is a notification, not readiness, so a scenario that describes a plan with no role specific guidance and no way back is describing the gap, not the fix. And a project with an executive sponsor but no user champions behaves exactly like the stalling program in the quiz scenarios, so the missing element is the champions, not more training or a bigger sandbox.

## What a consultant should walk away with

Run the readiness sequence in order and name each risk out loud: does it fit the work, will they know, can they do it, will they, and how will we prove it worked. Watch users count the work before you design the page, and remember that adding Dynamic Forms takes over the fields section. Set three part metrics, source, target, and measurement date, before go-live and with the business, then put them on a dashboard the sponsor actually reads. Write a communication cadence that includes a route back, train by role with in-app guidance carrying the last mile, and build champions from the most affected group. Do those and the quiet month two failure stops being a surprise.
