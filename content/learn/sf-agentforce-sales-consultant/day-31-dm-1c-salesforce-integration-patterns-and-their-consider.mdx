# Lesson 31: Salesforce Integration Patterns and Their Considerations

A client calls you in because orders are showing up in Salesforce twice, and nobody can tell which copy finance will invoice. The build works in the sandbox. In production, the ERP pushes an order, the request times out after the gateway's thirty second limit, the middleware retries, and both attempts eventually land. There is no external ID on the order object, so the second attempt has no way to recognize the first. That scene is not a code defect. It is a pattern choice and a design gap, and it is exactly what this objective tests.

The naive approach is to treat every integration as the same job: call the API, get the data in, move on. That works while there are two systems and a hundred records a night, and it breaks the moment the volume grows or the count of systems grows. Adding a second caller to a direct connection is easy. Adding a sixth is not, because every new participant multiplies the connections you have to build, secure, and monitor, and none of the systems involved agreed on what a customer record is. Timing adds a second failure: a design that holds a user waiting for a slow remote system passes its tests and then times out in front of a customer.

This lesson serves the exam guide's requirement dm-1c, in the Data Management domain, which carries 18 percent of the exam. The objective asks you to explain the use cases and considerations for data migrations and integrations. By the end of this lesson you will be able to look at a scenario, name the pattern that fits, choose between a synchronous and an asynchronous shape, pick the right API, and list the production considerations that decide whether the integration survives contact with real data.

<TLDR>

- The five integration patterns, and the sync or async shape that decides who waits
- Picking the API: REST, SOAP, Bulk API 2.0, Streaming, and Pub/Sub
- The limits, idempotency, and monitoring that separate a demo from production

</TLDR>


## Deep Dive

### The five patterns, and what each one costs you

Integrations come in a small number of recognizable patterns, and the exam almost always hands you a scenario and asks which one fits. Point to point is a direct call between two systems. It is the fastest to build and the hardest to maintain, because every new system adds another set of connections and every connection carries its own mapping, credentials, and error handling. Four systems talking directly to each other is six connections; ten systems is forty five. The count grows faster than the participant list, which is why point to point is fine at two and painful at six.

Middleware, or an integration platform as a service such as MuleSoft, sits in the middle: every system talks to the hub instead of to each other, and the hub handles mapping, transformation, retry, and monitoring in one place. This is the pattern you choose when many systems must share the same data, when the remote system does not speak the Salesforce API natively and needs a translator, or when one business process has to orchestrate steps across several systems. Event driven uses Platform Events, Change Data Capture, or the Pub/Sub API to broadcast a change and let interested systems react on their own. Batch moves large volumes on a schedule through Bulk API 2.0 or an extract, transform, and load tool. File based hands a flat file over on a schedule, and it survives in the field because some systems, particularly older finance and logistics packages, still only speak files.

Two of the patterns are easy to underrate because they feel old. Batch is not outdated; it is the right answer for a nightly finance sync of closed deals, where nobody needs the data at 9am and the volume would make a synchronous call impossible. Bulk API 2.0 is REST based and asynchronous, which means you submit a job, poll its status, and retrieve the results once Salesforce has finished processing server side.[^1] File based integration is the pattern of last resort, and it survives for a reason: a legacy warehouse system that can only drop a CSV on an SFTP server at 3am still has to be fed. The cost is that files are late and fragile. There is no schema contract on a CSV, a truncated export fails quietly, and the receiving system is always a day behind. Choose file based because the other side cannot do anything better, not because it is simple to build.

Name the pattern out loud before you name a tool. The exam rewards the consultant who says "that is event driven, so three downstream systems do not each poll Salesforce," not the one who reaches for the first API that comes to mind.

### Synchronous versus asynchronous: the choice that decides who waits

The synchronous versus asynchronous decision matters more than any other, because it decides who waits. A synchronous call holds the user or the process until the remote system answers. It gives an immediate result and a fast experience when the remote system is fast, and it also means a slow or down remote system breaks your transaction. If the ERP takes forty seconds to price a quote, the rep sits on a spinner and then gets an error, and that error can roll back the save they were trying to make.

Asynchronous work hands off the message and continues. It is the right shape for anything slow, anything large, and anything that does not need an immediate answer, such as a nightly volume sync or a downstream update that can land seconds later. The everyday rule the exam expects is blunt: if the scenario says the user must see the result immediately, the shape is synchronous. If it says large volume, scheduled, or fire and forget, the shape is asynchronous. Do not read a scenario that mentions millions of records and then answer with a synchronous call; that combination is the single most common wrong answer on this objective.

One more consequence is worth stating. Asynchronous work does not guarantee order, and it does not tell the caller what happened later unless you build that in. A subscriber can receive change events out of order or more than once, so the consumer has to be written to tolerate both. If your design assumes exactly once and in order, it will produce duplicates under load.

### Picking the API: REST, SOAP, Bulk API 2.0, Streaming, and Pub/Sub

Know the API types and why you would pick each. REST is the default for lightweight, standard, synchronous work, and it is simple to call. SOAP is heavier and is chosen when the integration needs a formal contract, transaction support, or access to the full metadata shape, and many enterprise middleware adapters still expect it. Bulk API 2.0 is the asynchronous path for large volumes, designed so a very large job processes server side without holding a synchronous request open. Salesforce's own guidance is a useful threshold: any data operation over 2,000 records is a good candidate for Bulk API 2.0, and jobs under that size should use synchronous REST, for example Composite, or SOAP.[^1]

Streaming API delivers near real time events to subscribers, and the Pub/Sub API is the gRPC based event interface that supports subscribing to and publishing platform events and change events at scale.[^2] The selection rule the exam rewards is short. Small and synchronous, REST. Large and asynchronous, Bulk API 2.0. Event driven and near real time, the streaming or Pub/Sub path. Composite and batch REST endpoints exist for bundling a handful of synchronous operations, but they do not change the shape: they still hold the request open, so they are not the answer for a million rows.

Every synchronous call also consumes a concurrent request slot. Salesforce caps concurrent inbound requests that run 20 seconds or longer at 25 for a production org and 5 for a Developer or trial org, and a call that exceeds it gets a REQUEST_LIMIT_EXCEEDED error until the long running count drops.[^5] That limit is another reason the synchronous answer is wrong for big jobs.

### Event driven integration in practice

Event driven integration is where modern designs land, and the pieces are specific. Platform Events are custom messages you define and publish, so you control the shape of the payload and can model a business event like Order Shipped with exactly the fields subscribers need.[^4] Change Data Capture publishes standard change events automatically when records on monitored objects are created, updated, deleted, or undeleted, so downstream systems react to Salesforce changes without polling for them.[^3] Both are consumed through subscriptions, either with Streaming API, a CometD client, an Apex trigger, or the Pub/Sub API.

The advantage is decoupling. The publisher does not know or care who listens, so you can add a warehouse, a partner portal, and a logistics system without touching the Opportunity trigger that publishes the event. Compare that with a poll: the same three systems each asking Salesforce every minute for "what changed since last time" spend API requests continuously and still find out late. Change Data Capture is the push replacement for that poll, and it is the answer the exam wants whenever a scenario mentions several systems reacting to the same change.[^6]

The consideration is that an event is a delivery mechanism, not a database. Events are not retained forever, subscribers can miss them during downtime, and a redelivered event can arrive twice. A publisher does not require a subscriber to be present to publish successfully, so a subscriber that was down simply never sees what happened. Handle the gap by reading the current state on reconnect rather than trusting the stream alone, and by carrying a unique key so a duplicate event does not create a duplicate record.

### When middleware earns its place

Middleware earns its place when direct connections stop being manageable, and the exam rewards naming the trigger. Reach for a middleware layer when several systems must share the same data and you want one place for mapping, transformation, retry, and monitoring, rather than the same logic reimplemented in every point to point connection. Reach for it when the remote system does not speak the Salesforce API natively and needs a translator. Reach for it when you need orchestration across multiple systems for one business process, or when you need enterprise grade error handling, queuing, and replay that you would otherwise have to build and operate yourself. Do not reach for it on a single simple call, where the overhead is pure cost and a direct integration or a Flow callout is enough.

The trade is real, and a good answer names both sides. Middleware adds a component to operate and monitor, it adds licensing and skills the customer may not have, and it adds a place for integration failures to hide if nobody watches it. A hub that quietly drops messages is worse than a point to point call that returns an error, because the error at least tells someone. When you recommend middleware, recommend the monitoring with it.

### The considerations that turn a demo into production

The considerations that separate a working demo from a production system are the ones the exam keeps pointing at, and they are limits and design rather than features.

Every call consumes API requests against the org's daily and concurrent limits, and the daily allocation is enforced across all calls in a 24 hour period.[^5] A chatty integration that polls every minute can exhaust an allowance that a bulk design or an event subscription would use a fraction of, and the users who lose access when the allowance runs out are the customer's own reps.

Every integration should be idempotent: a retried message must not create a second record. The usual implementation is to match on an external ID and use upsert, so the second attempt updates the record the first attempt created instead of inserting a twin. This is why an external ID on the integration key matters, and why it is also an indexed field that makes lookups fast.

Retry strategy is where idempotency and limits meet. When a batch of a thousand records fails, do not resend the whole batch blindly. Resend the failed records only, keyed by external ID, and log anything that fails twice so a human sees it. A blind whole batch retry is how one bad record becomes a duplicate of the nine hundred ninety nine good ones.

Errors must be surfaced to someone who acts on them, with the failed payload retained so it can be replayed. A job that fails silently at 2am is a data quality incident discovered days later, and the customer will blame the system, not the exception nobody read. Credentials belong in a connected app with OAuth and, ideally, a named credential so the endpoint and the secret live outside the code and Apex or Flow references them by name. Finally, the integration needs monitoring: throughput, error rate, and a threshold that pages a human.

### Putting the patterns against a sales scenario

Put the patterns against a sales scenario and the choices sharpen. Syncing closed opportunities to a finance system nightly is a batch integration on Bulk API 2.0, because it is large, scheduled, and asynchronous. Showing a sales rep the current order status from the ERP while they are on the phone is a synchronous REST call, because the rep needs the answer now. Notifying a warehouse, a data warehouse, and a partner portal every time an opportunity stage changes is event driven with Change Data Capture or Platform Events, because three downstream systems should not each poll Salesforce. A one off load of a purchased contact list is a migration, not an integration, and it belongs to the migration tooling and ordering you learned earlier. When you can name the pattern, the API, and the sync or async shape for the scenario, you have answered the objective the way the exam wants.

## Exam Traps

<Callout kind="warning">

Three traps dominate this objective. The first is answering with a synchronous call when the scenario describes large volume or a nightly schedule. Synchronous requests time out on big jobs and occupy a 20 second plus concurrent slot that is capped at 25 in production, so a scenario about millions of records or a nightly sync is asking for Bulk API 2.0 or another asynchronous pattern, never a synchronous per record call.

The second trap is thinking Change Data Capture reverses direction. Change Data Capture publishes Salesforce changes outward to subscribers, and it does not by itself write changes into Salesforce. An answer that has Change Data Capture loading an ERP's records into Salesforce has the arrow pointing the wrong way. Change Data Capture exports your changes; something else has to import theirs.

The third trap is ignoring API limits and idempotency. A polling integration can exhaust the daily request allowance that the business depends on for its own users, and a retry that is not idempotent creates duplicates. An answer that skips external ID matching or request budgeting is incomplete even when the pattern it names is right, because the exam is testing whether you think about the second and third day of running, not just the first.

</Callout>


## What a consultant should walk away with

<KeyTakeaways>

- Choose the shape first: synchronous REST when the user needs the answer now, and Bulk API 2.0 when the work is large or scheduled
- When several systems must react to the same change, publish an event with Platform Events or Change Data Capture instead of letting each poll
- Reach for middleware when connections or transformations outgrow point to point, and say out loud what it adds to operate and monitor
- Design the details: an external ID so retries upsert instead of duplicating, credentials in a connected app and named credential, retained payloads, and monitoring

</KeyTakeaways>
