# Lesson 13: Post-implementation adoption diagnostics: finding why users stopped

Six weeks after go-live the sponsor tells you nobody is using the new Agentforce app. The project manager's instinct is to schedule more training. You open one user's record, check the permission set assignment, and find it was created but never assigned, so the app was never visible in the App Launcher for half the sales team. The tool was not rejected. It was hidden. Training would have taught forty people to use something they could not open.

That is the pattern to internalize before anything else on this objective. Low adoption is a symptom, and the job is diagnosis, not remedy. The naive response is to treat every drop-off as an attitude problem and reach for training or a survey. The correct response is to find the stage of the funnel where users fell out, because the cause at each stage is different and the fix at each stage is different too.

This lesson serves requirement ci-3a in the Consulting and Implementation Strategies domain, which carries 25 percent of the exam. It covers the four-stage adoption funnel, the access diagnostics that must run before any other diagnosis, the tools that measure usage and agent behavior, and the sequence for responding to low adoption. After it, you should be able to name the stage a user is stuck at and propose the fix that actually addresses it.

<TLDR>

- Low adoption is a symptom: name the funnel stage where users fell out before you propose a fix
- Run access diagnostics first, because a missing permission assignment looks identical to a user rejecting the tool
- Read Login History for presence only, the Lightning Usage App for usage, and Agent Analytics for escalations

</TLDR>


## Deep Dive

### Adoption is a funnel with four stages, and each stage has its own cause

Treat adoption as a funnel with four stages, and treat the fall-off between them as diagnostic. Provisioned means access exists. Activated means the user logged in at least once. Engaged means they used the feature in the last 7 or 30 days. Proficient means they use it the intended way without help. Falling between provisioned and activated points at an access, licensing, or communication problem. Falling between activated and engaged points at a friction or value problem. Falling between engaged and proficient points at a training or design problem.

![Diagram of the four-stage adoption funnel: provisioned, activated, engaged, and proficient, with the cause each fall-off points at. A drop between provisioned and activated points at access, licensing, or communication, between activated and engaged points at friction or value, and between engaged and proficient points at training or design.](</diagrams/day-13-ci-3a-post-implementation-adoption-diagnostics-finding-w/1-adoption-funnel.png>)

The discipline is to name the stage before you propose the fix. Retraining a user who cannot see the app in the App Launcher wastes a month. Sending a satisfaction survey to a user whose permission set was never assigned tells you nothing you can act on. The exam rewards the person who places the user at the right stage first, because almost every distractor is a fix aimed at the wrong stage.

### Run the access diagnostics first, always

In practice most findings of "the app is not being used" reduce to a missing permission. Check that the permission set is assigned and not just created, that the profile can see the app in the App Launcher, that the record type is available to that profile, and that the user holds a license type that can reach the app at all. Use Login As to see the org the way the user sees it, because that is the only way to confirm what actually appears on their screen rather than what the admin's override shows.

Remember that every Login As is written to the Setup Audit Trail.[^2] That is useful for forensics and it is also a limit: the Setup Audit Trail retains roughly the last 180 days of setup changes, after which setup entity records are deleted. The 180-day window is a real boundary on your post-launch forensics, so if the review will span longer than that, export the audit trail before the window rolls. The exam tests this window directly, and the wrong answers describe the audit trail as a live click stream or as agent transcripts, which it is not.

Login History on a user record shows whether the user authenticated and with what status, and it holds up to 20,000 records for the past 6 months.[^1] Read it for what it is. A login is presence, not usage, so a daily login proves nothing about whether the user opened the app or created a record. This is one of the exam traps on this objective, and the correction is to pair login data with an actual usage source rather than treating authentication as adoption.

The other supporting fact is that Login History includes logins through the API and shows the how and the from-where: HTTP login method, SAML SSO history, IP tracking, and connected-app login subtypes. When you are diagnosing a subset of users who never activated at all, Login History is where you separate "could not get in" from "never tried to get in", and those two answer different questions about your launch.

### Quantitative usage: the Lightning Usage App, dashboards, and Event Monitoring

Then go quantitative. The Lightning Usage App breaks usage down by app, time range, browser, device, and page performance, which tells you whether people are in the right app and whether slowness is pushing them out.[^4] It shows the most used pages in the org and their page load time, and it measures performance in Experienced Page Time, the time it takes a page to reach a state a user can meaningfully act on. When the same people log in every day and create nothing, page performance is a plausible culprit and the Lightning Usage App is where you confirm or rule it out.

The Adoption Dashboards app, installed from AppExchange, reports active users and adoption trends by user group, which is the view you put in front of a sponsor who wants trends rather than a page-level table. Event Monitoring is a separate add-on license that exposes event-level data through event log files and, with Real-Time Event Monitoring, as a stream.[^5] It is the answer when a scenario needs per-user, per-event granularity that Login History and usage reporting cannot give. If the question says "every user click" or "per-event telemetry without an add-on", the answer is not Event Monitoring, because Event Monitoring is the add-on.

### Agentforce adoption needs its own instrument

A conversation is not a page view, so Agentforce needs a different measure. Agent Analytics reports sessions, how many resolved without a person, and the share of sessions that escalated to a human.[^3] That escalation share is the single most useful number for improving an agent, because each escalation names a topic the agent could not close, which becomes a prompt change, a new action, or a data-quality fix. The metric families are explicit: deflection rate is the share of sessions that ended without escalation, escalation rate is the share that went to a human or another agent, and abandonment rate captures sessions that timed out or dropped off.

Two supporting facts matter after launch. The agent user's access has to be correct, or every session fails in a way users read as "the AI is broken". The Einstein Trust Layer settings have to be enabled in the org, because users who are not told what happens to their data with the agent will stop using it.[^7] Agentforce Testing Center is how you catch a regression after a change rather than after a complaint, and it belongs in your improvement loop, not only in your release checklist.[^6]

### Responding to low adoption is a sequence, not a brainstorm

Responding to low adoption is a sequence: verify access, then verify value, then reduce friction, then retrain, then escalate to the sponsor with the data. Value verification means asking the blunt question: does the new process actually take less time or produce a better result for the user, measured rather than asserted. If it does not, no amount of training fixes it, and the honest recommendation is a design change.

Friction reduction is the cheapest lever and the most underused: fewer required fields, a better default, a Stage or Path that shows the next step, and an in-app guidance prompt on the screen where people stall. Retraining comes after you have confirmed the user can reach the feature and that the feature earns its place. Escalation comes last and it comes with numbers, because a sponsor can act on a dashboard and cannot act on an impression. When you walk into the steering meeting, you bring the funnel stage, the cause, the metric, and the proposed fix, in that order.

### Continuous improvement is a plan with four named parts

Continuous improvement is what the objective asks you to plan, and a plan needs four named things: an owner, a cadence, a metric, and a decision rule. The owner is a person after the project team leaves, because a friction backlog with no owner simply expires. The cadence is a standing 30/60/90 day review, which matches how training decays and how release cycles arrive. The metric is the success metric you defined before implementation, so improvement is measurable against a baseline rather than against memory. The decision rule is what happens when the metric misses, so the meeting ends with a decision instead of a discussion.

Tie the plan to the release calendar, because Salesforce upgrades production three times a year in Spring, Summer, and Winter, and each upgrade is a natural shipping window plus a mandatory regression test in the sandbox preview period. That tie is what keeps a small improvement from waiting for a big project. It also answers the exam's scenario question about changing business requirements, which arrive after go-live on a schedule you can predict: classify each one rather than negotiate it, route it through the same sandbox pipeline you used during the implementation, and avoid editing production directly, because direct production edits are how sandbox and production drift apart and drift is what makes the next deployment unpredictable.

### Worked example: a launch that stalled at activated

Suppose the data says forty percent of licensed users logged in once and never returned. That places them between activated and engaged, which is a friction or value problem rather than an access problem, and the fix is not training. You open the Lightning Usage App and find the app they need is the fourth item in the App Launcher, behind three apps they never touch, and that the record page they land on loads slowly enough to push people to a bookmark instead. You confirm the pattern in the usage dashboards, and the fix is a reordered navigation menu and a page weighed down with components nobody reads. Neither fix is training. Both are friction reductions, and both are cheaper than a retraining program that would have changed nothing.

Now suppose the data says one team never logged in at all. That places them between provisioned and activated, which is an access or licensing problem, and the first check is the permission set assignment, then the profile's app visibility, then the license type. Users who were never provisioned point at a communication problem, and the fix is the message that never reached them. The two scenarios look identical on a dashboard and demand opposite responses, which is the whole reason the funnel stage comes first.

## Exam Traps

<Callout kind="warning">

Three traps dominate this objective. The first is concluding the org is not adopted when the permission set was never assigned. A missing assignment looks identical to a user rejecting the tool, so verify access before you diagnose attitude, and use Login As to confirm what the user actually sees. The second is treating a login as usage. Login History records authentication, so a daily login proves nothing about whether the user opened the app or created a record, and the fix is to pair it with the Lightning Usage App rather than stop there. The third is believing agent behavior cannot be measured per agent. Agent Analytics reports sessions, resolutions, and human escalations, and the escalation topics are exactly the improvement backlog for the agent.

</Callout>


## What a consultant should walk away with

<KeyTakeaways>

- Treat adoption as a four-stage funnel, provisioned, activated, engaged, proficient, and name the stage before proposing a fix
- Run access diagnostics first, using Login As to confirm what the user sees, because a missing assignment looks like rejection
- Read Login History for presence only, the Lightning Usage App for usage and page performance, and Event Monitoring only with the add-on
- For Agentforce watch the escalation share and its topics, keep the agent user's access and the Trust Layer correct, and test after changes

</KeyTakeaways>


Diagnose the funnel stage before you propose the fix, because the wrong stage turns a two-day fix into a two-month program. Run access diagnostics first, every time, using Login As to confirm what the user sees. Read Login History for presence only and reach for the Lightning Usage App for usage and page performance; reach for Event Monitoring only when the scenario needs per-event granularity and the org has the add-on. For Agentforce, watch the escalation share and the topics behind it, keep the agent user's access and the Einstein Trust Layer correct, and run Testing Center after changes. Then leave behind an owner, a cadence, a metric, and a decision rule, so the improvement plan survives the week your team leaves.
