# Lesson 9: Quality at Scale: Golden Sets, Eval Gates, and Regression Discipline

Lesson 3 gave you the first eval suite: a small collection of known-good cases, a scheduled run, a pass bar you could defend. That suite is the right start, and it is a start, not a destination. It was built in a week, for one system, when you could still look at most of the output. This lesson is about what happens when that system keeps running and growing, and when the output stops being something you can eyeball.

Scale changes the nature of the quality problem, not just its size. The lesson you can trust now is that volume defeats review. When a delivery produces a handful of outputs a week, a consultant reads every one and catches the drift by eye. When it produces dozens or hundreds a week, and when it has been running long enough that the rules, the data sources, and the models underneath it have all changed more than once, nobody is reading everything anymore. The question stops being "is this one output right?" and becomes "how do I know the whole stream is still right, and how do I catch the moment it stops?" Answering that question at depth is the difference between a delivery that quietly decays and one that holds its quality bar for a year.

Three things carry that answer: a golden set treated as living reference data, eval gates placed where they actually stop the wrong change, and the regression discipline that turns a failing gate into a diagnosed event instead of a buried one. Each looks administrative. Each is load-bearing, and all three fail in predictable ways when you run them for real.

## Volume defeats review, so you gate and sample instead

Start from the mechanism that drives everything else. A human can verify an agent's output only up to a certain volume, and past that volume the verification has to change shape. There is no way to hire enough reviewers to read a hundred outputs a day at the same scrutiny you gave five. So the practitioner stops trying to scale the review and instead changes what is reviewed.

The shift has two moves. The first is to move verification forward, into a gate that runs before output ships, rather than after it ships. You stop asking a human to read each document and start asking a fixed reference set whether the production change that just happened broke anything. The gate does not review the individual output. It checks the system that produces the output, against a set of cases that encode what good looks like, and it runs every time the system changes. This is the regression suite, and it is how an agent estate gets a test suite at all, because there is no code to unit test in the usual sense.

The second move is to sample the live stream instead of reading all of it. The gate protects you from regressions caused by changes. Sampling protects you from degradation that happens without any single change, the slow rot that comes from data drifting or a model getting updated upstream or a source quietly changing format. You pull a fixed share of the real output, every period, and you review that sample to a standard. The sample is your window into the stream the gate cannot see, because the gate only sees its own cases and the stream includes everything the cases never covered. Between the gate and the sample you have both sides: you catch the change that breaks a known case, and you catch the drift that shows up only in the un-gated majority.

The trap is believing one of these is enough. A gate alone misses the case that was never added to the set. A sample alone misses the regression that happens on the night after a deploy, across every output at once. The two are not alternatives. The gate is fast and automatic and narrow. The sample is slow and human and broad. A quality system at scale runs both and knows which one caught what.

## The golden set is living reference data, not a frozen artifact

The most common mistake in evals is treating the golden set like a document you wrote once and lock. It is not. It is reference data with a lifecycle, and if you do not manage that lifecycle it quietly stops meaning anything. Three disciplines keep it honest.

The first is provenance. Every case in the set should trace to something real: a requirement from the original capture, an incident a client actually hit, an edge case that surfaced in production. A case with provenance can be defended when someone asks why it is there. A case without provenance is a guess that will eventually be removed or, worse, trusted when it should not be. When you add a case, you write down what it came from. When you look at the set in six months, you can still tell what each case is protecting.

The second is growth with restraint. The set should grow as real use surfaces new edge cases, because an agent that is harder to silently break this month than last is the whole trajectory you want. But every addition is also a cost and a risk. Each case must be maintained, must keep matching reality as the world changes, and can become a source of drift if it encodes behavior that stopped being correct. The restraint is that you add a case because reality demanded it, not because you want a bigger number. A thousand cases nobody can maintain is worse than fifty cases you can defend.

The third is the refusal to encode today's bug. This is the subtle one. When a case fails and the fix is hard, there is a strong temptation to rewrite the expected output to match what the system currently does, because that makes the gate green and the delivery looks healthy. That is how a golden set rots from the inside. The set exists to hold the bar, and the moment you move the bar to fit the output, you have deleted the only record you had of what correct used to be. When a case fails, the question is whether the system regressed or whether the world changed and the bar itself is now wrong. You answer that question honestly before you touch the case, and you never move the expected output just to make the gate pass. A gate that passes because you lowered it is not quality assurance. It is bookkeeping.

The deeper point is that the golden set is the institutional memory of what good looks like, and like any memory it needs versioning. When you change a case, you record why. When the bar changes because a client changed a rule, you can look back and see that it changed on purpose, not because someone was tired of a red X. The set is an asset the engagement owns, and assets get changelogs.

## Eval gates stop the wrong change, not all change

An eval gate is only worth its place if it is placed where it can actually stop something. That means deciding, for each kind of change, whether it passes through a gate at all, and making the gate's verdict binding rather than advisory. A gate that reports and is ignored is decoration.

There is a natural hierarchy of what needs a gate. A change to the system's rules or instructions needs one, because that is the most common cause of a silent behavior shift. A change to a data source or its format needs one, because the agent reads the world through that source. A change to the model underneath needs one, because the model is where the most unpredictable behavior lives. What does not need a full gate on every run is the routine, unchanged production pass, because nothing changed for it to regress against. The gate is for change, and the discipline is to name which changes trigger it.

In Hermes terms the gate is a scheduled eval job, and it has a shape worth copying. The job loads the golden set, runs each case through the current system, and reports pass or fail per case to wherever the team watches. [^1] A change is deployable only if the gate is green, and a red case blocks the change regardless of how good it looked in isolation. The gate does not need to catch everything, and this is where consultants over-engineer. Its job is precision, not recall. It should catch the regressions that matter and rarely fire on things that do not, because a gate with a high false-alarm rate gets ignored, and an ignored gate is worse than no gate because it creates the illusion of protection.

The objective scoring where you can get it makes the gate cheaper and sharper. When a case has an output you can check mechanically, a script does the checking and no model is needed. Hermes supports this directly: a no-agent job runs a script on a schedule and returns its output verbatim, with no inference call at all. [^1] Where the check is a script, the gate costs nothing per run and never drifts in its own judgment. You save the model judgment for the cases that genuinely need it, and you keep the mechanical cases cheap and deterministic. The rule of thumb is that the more objectively a case can be checked, the more it should be, because a deterministic check is the one part of the whole system that cannot quietly change its own mind.

## A failing gate is an event with an owner, not a red X

Here is where most eval setups fall apart in practice. The gate fails, and nothing happens. The consultant is busy, the failure looks like noise, the deploy ships anyway because the deadline is real, and after the second or third time everyone stops even looking at the gate. The regression discipline is the practice that prevents this, and it has three parts.

The first is that a failing gate is triaged like an incident, with an owner and a deadline. When the gate goes red, someone decides which of three things it is. It is a real regression, meaning the system's behavior actually got worse and must be fixed before the change ships. It is stale reference, meaning the case or its expected output no longer reflects reality and the bar itself needs to move, deliberately and with a recorded reason. Or it is a flaky gate, meaning the test itself is unreliable and must be stabilized before it can be trusted again. Naming which of the three it is is the whole skill, because the fix is different for each: fix the system, update the case, or repair the test. Misdiagnosing a stale reference as a regression leads you to fight the wrong battle. Misdiagnosing a real regression as a stale reference is how you lower the bar to hide a defect.

The second part is that real regressions get root-caused, not reverted and forgotten. The value of a regression is not that it blocks a bad change. It is that it points at the specific requirement or behavior that broke, and that pointer is the cheapest diagnostic you will ever get. When the gate tells you the boundary case failed, you already know which rule to inspect. You find the change that caused it, you understand why that change broke the case, and you fix the cause, not the symptom. A regression you reverted without understanding is a regression you will meet again on the next change.

The third part is that you track the rate and the pattern over time. A regression discipline is not a single gate run. It is a record: which changes caused failures, which cases are the fragile ones, which parts of the system break most often. Over weeks that record tells you where the real risk lives, and it lets you add cases and change guardrails where the data says the system actually fails, rather than where you guessed it might. The pattern is the strategic output of the whole discipline. The individual gate runs are just its raw material.

## Keep the gate trustworthy, or it stops being a gate

A gate is only as good as the trust the team places in it, and trust is earned by precision and destroyed by noise. This deserves its own discipline, because the failure mode is quiet and compounding. Every time the gate fires on something that turns out to be fine, it costs a little credibility. Every time a false alarm is ignored and nothing bad happens, it costs more. Eventually the gate is firing and nobody looks, and the one time it fires on a real regression it is missed. This is the boy who cried wolf, and it is the most common reason eval suites get abandoned.

Two practices keep a gate precise. The first is that you review and sharpen the false alarms. When the gate fires and the triage says it was stale reference or flaky test, you do not just move on. You fix the case or the test so it does not fire that way again. A gate that fires on the same stale case every week is not doing its job, and the fix is not to ignore it. It is to correct the case so the gate goes quiet for the right reason. Precision is a maintenance activity, not a one-time setting.

The second practice is calibration, and this is where human review comes back in at a strategic level. The gate runs the golden set through the system, but if nothing ever checks whether the golden set itself is still right, the whole edifice rests on a foundation nobody audits. Periodically, a human reviews the golden set as a set, not the system's output against it but the set's own cases and expected outputs against current reality. This is different from reviewing output. It is reviewing the standard. A consultant who never audits the golden set is trusting that the cases they wrote last quarter still define what good means this quarter, and in a client environment where rules and sources change, that assumption decays. The calibration review is how the reference data stays a live asset instead of a fossil.

## Measure quality over time, not just at the gate

The gate and the sample tell you whether today's output is acceptable. Neither tells you whether quality is trending up, holding, or decaying, and trend is what you owe the client who is paying for a system that stays good. So the last piece of the discipline is measurement that accumulates.

You need a small set of numbers you actually track every period. The sample gives you the real one: the error rate on live output, computed by a human reviewer on a fixed share, period over period. The gate gives you another: how often changes pass cleanly and how many regressions they cause. Both belong on a simple ledger you update each period, because a single number is noise and a series is a signal. The error rate that held for four weeks and crept up in week five is a warning you can act on. The same number read once tells you nothing.

The trap in measurement is measuring what is easy instead of what matters. A pass rate on the golden set is easy and it is not the same as real-world quality, because the golden set is by definition the cases you already know about. The sample error rate on the live stream is harder and it is the truth, because it includes everything the set never covered. A consultant who reports only the gate pass rate is reporting on the part of the system they curated. The part that matters, the uncurated live output, is measured by the sample, and it is the number a client should care about. When you present quality to a client, present both, and be honest that the sample is the one that would tell you if you were wrong.

## Worked example: the runbook and release-note engine

Take a concrete delivery and run the whole discipline through it. A software vendor engaged you to build an agent that drafts release notes and operational runbooks from code changes and support tickets, every week, across a product suite. The engagement delivered, and now the system runs at volume: dozens of documents a week, too many for any reviewer to read, and the client cares because these documents go to their customers and their own operations team. This is where the quality discipline earns its keep.

Start with the golden set. At delivery you wrote twenty cases from the requirements and the incidents the client had already lived: the release note that must state a breaking change, the runbook step that must not contradict the known config, the ticket whose fix must be attributed to the right version. Each case has provenance, written down when you added it. Over the next two quarters the set grows to sixty, not because you wanted a bigger number but because real use surfaced real edge cases, each added with its source. One case in particular, the one encoding a newly discovered config interaction, came from a support ticket that burned the client for a week, and it is the case you are most proud of and most careful never to relax.

The gate sits between change and ship. The client's team updates the runbook rules, a source system changes its export format, a model gets swapped upstream, and every one of those changes triggers the eval before the new output is trusted. Where a case can be checked by script, a no-agent job does the checking for free and deterministically. [^1] Where the case needs judgment, the scheduled eval handles it. A change that passes is deployable. A change that reds one case is not, no matter how good it looked.

Then the regression the discipline was built for. The client swaps the model provider to cut cost. The gate goes red on the breaking-change case, the one that must state clearly when a behavior change will break a customer. The team does not ship and does not bury it. They triage it as an incident with an owner and a deadline. The triage says it is a real regression: the new model, on the same instructions, softens the breaking-change language until it no longer meets the bar. Root cause is the model's instruction-following on that specific phrasing, not the case and not the test. The team rewrites the instruction, re-runs the gate, the case goes green, and the change ships knowing the bar held. Without the gate and the triage, the softer language would have reached customers, and the client would have found out from an angry one.

The sample runs alongside. Every week a human reviewer pulls a fixed share of the shipped documents, checks them against the standard, and records the error rate on the live ledger. For a month it holds at zero. In week five it ticks up, and the ledger catches it before any single document is egregious enough to notice by itself. The pattern points back at the model swap, and the consultant adds a case to the golden set for the exact phrasing that drifted, so the gate now covers what the sample caught. The gate got stricter because the stream taught it something, and that is the whole trajectory: the system is harder to silently break this month than it was last month.

The client sees the honest picture, because the consultant reports both numbers. The gate pass rate is high, and it is high partly because the set was curated to catch the real failures. The sample error rate is the number that would tell them if the whole thing were lying to them, and it is low and trending. The client trusts the report because it does not hide the sample behind the gate, and because they have watched the gate catch a real regression before it reached them.

## The pitfalls that rot a quality system

**A golden set nobody maintains.** Cases without provenance, never grown, never audited, slowly encoding behavior that stopped being correct. Treat the set as living reference data with a changelog, and audit it as a set on a schedule.

**Moving the bar to make the gate green.** The strongest corruption in evals. When a case fails and the fix is hard, rewriting the expected output to match the system hides the regression and deletes the record of what correct used to be. Never move the bar to fit the output.

**A gate that is decorative.** Placed where it cannot stop a change, or run and then ignored when it goes red. A gate is only a gate if its verdict is binding, and a change that ships over a red gate is not protected by anything.

**High false alarms.** A gate that fires on stale cases or flaky tests loses credibility until nobody looks, and the one real regression gets missed. Fix false alarms by correcting the case or test, and keep the gate precise by maintenance, not by ignoring it.

**A failing gate with no owner.** A red X that nobody triages is a regression that ships. Treat a failure as an event: is it a real regression, stale reference, or flaky gate, and who fixes it by when?

**Reporting only the curated number.** The gate pass rate measures the cases you already know about. The sample error rate on live output measures everything else, and it is the number that would tell you if you were wrong. Report both.

## Try it

Take the delivery you hardened in Lesson 3 and run it at scale in your head, or take a live delivery you actually maintain.

1. Audit your golden set. Write down, for each case, what real requirement or incident it traces to. Remove or fix any case you cannot defend, and note which cases encode behavior that may have stopped being correct.
2. Decide which changes trigger your gate. List the change types: rules, data sources, model, config. Write which ones run the full set before they ship, and make the verdict binding in writing.
3. Identify which cases can be scored by script instead of by model judgment. Move the mechanical ones to a deterministic check, and keep model judgment for the cases that genuinely need it.
4. Write your triage protocol. For a red gate, state the three diagnoses (real regression, stale reference, flaky gate), who owns the triage, and the deadline. State explicitly that you never move the expected output to make the gate pass.
5. Design your calibration review. Write how often a human audits the golden set as a set, against current reality, and who does it. This is distinct from reviewing output.
6. Start a quality ledger. Pick the two numbers you will track every period: the sample error rate on live output and the gate pass rate. Define the sample size and the reviewer, and commit to reporting both, not just the curated one.

If you can hold all six, your delivery does not just work. It stays working, and you can prove it is still working in a month and in a quarter, which is the promise a client actually paid for.
