# Lesson 4: Building a Reusable Delivery Toolkit: Skill Packaging Done Right

Lesson 3 taught you to harden a single agent for production: route its work by tier, prove its output against a gold set, and hold its boundaries by construction. You now have one system that runs without you in the room. This lesson is about the harder move, the one that separates a practitioner who delivers engagements from one who builds a practice. It asks what happens after the engagement, when you want to take what worked and run the next project faster instead of starting over.

The answer is packaging. You take the working patterns from this engagement, the capture discipline, the eval suite, the guardrail set, and you turn them into a reusable delivery toolkit that another consultant can load on the next project without relearning them. In Hermes Agent, the concrete mechanism for that is the skill, and the discipline of packaging is skill authoring done right. Most people do this badly. They write a wall of prose, dump it in a folder, and call it a toolkit, and the next person never reads it. This lesson teaches you to package a delivery toolkit that actually gets used.

## Why the second engagement must not look like the first

Here is the core economic claim of this lesson, and it is worth sitting with because it changes how you work. A one-off engagement pays for its own delivery, once. A reusable toolkit pays every time it shortens the next delivery, which is every engagement after the first. The consultant who rebuilds the same capture template, the same eval suite, and the same guardrail checklist from scratch on project after project is not working harder. They are redoing work they already did, and they are billing the client for their own lack of memory.

The insight transfers to any delivery craft, not just agents. A lawyer who rewrites the same contract from a blank page each time, an architect who re-derives the same review checklist, a doctor who re-learns the same diagnostic path: each is leaking their own prior work. The professionals who scale are the ones who extract the repeatable part of what they do and package it so it is cheap to bring to bear next time. That is the entire craft this lesson teaches, and Hermes Agent is the concrete vehicle because its skills are the cleanest expression of the pattern: a repeatable procedure, saved once, loaded on demand.

The failure mode to avoid is on the other side of the same coin. Packaging done wrong is worse than no packaging, because it creates the illusion of reuse. A skill nobody loads, a checklist nobody reads, a template too generic to apply: these cost you the trust of the team that tried them once, failed, and concluded the toolkit is worthless. So this lesson is not about writing skills. It is about writing skills that earn their place, which is a much narrower and more demanding standard.

## What a skill is, and why it is the right unit of reuse

Define the thing precisely. A skill in Hermes Agent is an on-demand knowledge document the agent can load when it needs it, stored in `~/.hermes/skills/` under a category directory, with a `SKILL.md` at its root and optional supporting files. [^1] It is loaded through a progressive disclosure pattern: the agent first sees only a list of skill names and one-line descriptions, then loads the full content of a skill when the task actually calls for it, and only then opens a specific reference file if it needs one. [^2] That design is not incidental. It is what makes skills reusable at scale, because the agent does not carry every skill's full text in its context all the time. It carries the index, and it pulls the depth only when relevant.

That loading model is exactly the structure a delivery toolkit needs. The toolkit is not one giant document. It is an index of small, well-scoped procedures, each loadable on its own, each describing one thing the next consultant might need to do. The skill is the right unit of reuse because it matches the unit of work: one deliverable, one checklist, one decision procedure.

The anatomy of a good skill file is short and fixed. It opens with frontmatter: a name, a description that tells the agent when to load it, a version, and optional platform and metadata fields. [^1] Then the body follows a standard order: when to use it, the numbered procedure, the pitfalls, and how to verify it worked. [^1] The description is the most load-bearing field in the whole file, because it is what the agent sees when deciding whether to load the skill at all. A skill whose description does not make its trigger condition obvious is a skill that never gets loaded, no matter how good the body is.

## Packaging as consulting, not as documentation

Here is the distinction that separates a practitioner from a hobbyist. Documentation records what happened. Packaging encodes how to do it again, and it is written for the person who has never seen the original engagement. The audience shift is the whole game. When you wrote the as-built register in Lesson 2, you wrote for the team that maintains this system. When you package a skill, you write for a stranger who will run the next engagement and has never met you or this client. Every assumption you make about what they already know is a risk you are shipping to them.

So the first discipline of packaging is ruthless extraction. You do not package the whole engagement. You package the load-bearing procedure that made it work, and you strip everything that is specific to this client. The reconciliation process that came from the warehouse system's export format is not reusable. The discipline of reconciling two sources and refusing a mismatch, and the rule that you write the expected output before you trust the answer, is reusable. Your job is to find the transferable core inside each client-specific practice and lift it out.

The second discipline is writing for the trigger, not for the archive. A skill lives or dies on whether the agent knows to load it. That means the description must name the situation, not the content. A description that reads "Contains my notes on reconciliation" is useless, because nothing tells the agent this is the skill to load when a client asks to match two data sources. A description that reads "Use when reconciling two data sources and refusing mismatches" is a trigger. The difference is one sentence, and it decides whether the skill is part of the toolkit or part of a drawer.

The third discipline is keeping the skill honest about scope. A skill that tries to cover everything covers nothing well, and worse, it bloats the index until the agent cannot tell which skill applies. One deliverable, one decision procedure, one checklist per skill. When you find a skill doing two unrelated jobs, split it. The packaging craft is mostly subtraction: taking what worked, removing what did not transfer, and keeping each package small enough that it loads and applies cleanly.

## The worked example: packaging the delivery toolkit

Carry the logistics engagement from Lessons 1 through 3 to its end, and watch what the consultant extracts. This is the moment the engagement stops being a job and starts being an asset.

The consultant looks back at what actually carried the delivery. Not the mood, not the effort, but the repeatable procedures. Three stand out, and they map exactly onto the three prior lessons.

**The capture skill.** Lesson 2's as-built discipline, the habit of writing down the enacted rule, the exception, and the boundary as you find them, is a procedure that transfers to every engagement. The consultant packages it as a skill with a trigger for the situation: a discovery or requirement-capture phase, when a rule, an exception, or a boundary needs recording. The body walks the next consultant through the method, the rule, the exception, the boundary, each written down the moment it surfaces, never left in someone's head. The pitfalls section names the ones the consultant actually hit: capturing the aspirational process instead of the as-built one, and trusting memory over the written record. [^3] This is the capture discipline, extracted from one client's warehouse problem and made loadable on the next.

**The eval skill.** Lesson 3's gold set, the practice of turning the validation record into known-good cases with exact expected output and running them on a schedule, transfers whole. The consultant packages it with a trigger for the situation: when a change to a rule, a source, or a model needs to be trusted, or when an agent's output must be proven correct on a recurring basis. The body teaches building the gold set from the as-built register, writing the expected output for each case, making the pass bar specific enough that nobody judges it by eye, and running it on a schedule. [^4] The pitfalls name the failures the consultant watched happen: trusting an eval you never built, and treating a failing case as a problem to hide instead of the earliest warning that a requirement broke. [^4]

**The guardrail skill.** The discipline of converting a documented boundary into an enforced one, the floor that never comes down, the operator's deny list, the headless policy, transfers. The consultant packages it with a trigger for the situation: when a boundary needs to be enforced rather than just written down, or when an unattended agent needs a safe fail-closed posture. The body walks through building the floor, the deny list, and the headless policy, and the pitfalls name the ones that cost real trust: a guardrail that lives only in a document, and an unattended job silently inheriting cost or capability. [^5]

Each of these is a small, scoped, trigger-first skill. None of them mentions the logistics client by name, because none of them needs to. The next consultant loads the capture skill at discovery, the eval skill at the first change, the guardrail skill at the boundary conversation, and the delivery starts weeks ahead of where this one did.

## The tooling that makes the toolkit portable

Packaging a skill in Hermes Agent is a concrete act with concrete tooling, and a practitioner knows the options and when each applies. There are three ways a skill gets into the toolkit, and they serve different needs.

**Authoring by hand.** The cleanest way to package a well-understood procedure is to write the `SKILL.md` directly, with the standard frontmatter and section order. [^1] This is the right tool when you know exactly what you are encoding and you want full control over the trigger, the scope, and the pitfalls. It is also the tool the agent itself uses to save its own procedures.

**The agent's own learning loop.** Hermes does not just store skills you write. The agent saves its own non-trivial workflows through the `skill_manage` tool, recording a procedure when it works one out, when it hits errors and finds the working path, or when a correction teaches it something. [^6] This is the background self-improvement loop: memory stores small durable facts that belong in context, while skills store longer procedures that should load only when relevant. [^6] For a consultant, this is the mechanism that quietly captures the hard-won procedure during delivery, so the toolkit grows from the work instead of from a separate documentation project. You can gate these writes if you want eyes on them before they land. [^6]

**The `/learn` path.** For the fastest route from material to skill, Hermes offers a `/learn` command that gathers the source, reads it with its own tools, and authors a skill following the house standards, with the ≤60-character description and the standard section order. [^7] Point it at a docs folder, an online page, a described procedure, or pasted notes, and it turns the material into a loadable skill. [^7] Large sources become knowledge-base skills: a lean `SKILL.md` carrying the core mental models plus an index, with one distilled file per topic under `references/`, loaded on demand so query cost stays proportional to the answer, not the source. [^7] This is the tool for packaging a body of material fast, and it is the reason the toolkit can grow even when you do not have time to hand-author everything.

Beyond the individual skill, two portability mechanisms make the toolkit shareable across a team. **Skill bundles** group several skills under one slash command, so a recurring task like a release prep or an incident response pulls in the whole set it needs with one invocation, and a bundle is just a YAML file that lists skills plus an optional shared instruction. [^8] This is how you ship a team-wide task profile: check the bundle YAML into a shared dotfiles repo and symlink it into the bundles directory, and every consultant on the team gets the same toolkit. [^8] And the **Skills Hub** lets you publish and fetch skills from online registries, including a custom tap for your own org's repository, so the toolkit is not locked to one laptop. [^9]

## The pitfalls that kill a toolkit

**Packaging the client instead of the procedure.** The most common failure. A skill that embeds the warehouse system's export format, the client's team names, the specific Monday report is not reusable, it is a museum piece. Extract the transferable core and strip the client-specific detail. The toolkit travels only if it is client-agnostic.

**A description that describes content instead of a trigger.** A skill nobody knows when to load is a skill nobody loads. Name the situation in the description: "Use when reconciling two data sources and refusing mismatches," not "Contains my reconciliation notes." The trigger is the whole game.

**One giant skill trying to cover everything.** A skill that does discovery, evals, guardrails, and reporting is a skill that does none of them well, and it bloats the index until the agent cannot pick. One deliverable, one decision procedure, one checklist per skill. Split when it grows past one job.

**Packaging a procedure you never actually ran.** There is a seductive trap in writing a skill for something you have not done, because the skill reads fine and has never been tested. A toolkit skill must come from a procedure that worked, with the pitfalls you actually hit written in. A skill authored from theory is documentation, and documentation does not earn reuse.

**Letting the toolkit rot.** The engagement changes, the tools change, and a skill that is not revisited drifts out of date. The packaging craft is not finished when the skill is written. It is maintained when the next use reveals a missing step or a changed pitfall, and the update is applied the way the agent itself prefers: targeted patches, not full rewrites. [^6]

## Try it

Turn the engagement you have been building through these lessons into a packaged toolkit.

1. Look back at the work you did in Lessons 1 through 3 and name the three procedures that actually carried the delivery. Not the effort, the repeatable steps.
2. For each one, write the extraction: what is the transferable core, and what is client-specific detail to strip? State the core in one sentence.
3. Write the trigger-first description for each skill. Make it name the situation, not the content, and keep it under 60 characters.
4. Draft the `SKILL.md` for one of the three, following the standard order: frontmatter, when to use, the numbered procedure, the pitfalls, verification. Include at least two pitfalls you actually hit, not ones you guess.
5. Decide how each skill should be packaged: hand-authored, through the agent's learning loop, or via `/learn` from material you already have. Justify the choice.
6. Define the team portability: would these ship as a bundle, a shared repo, or a hub tap, and what would you include in the shared instruction that the team always follows?

If you can defend all six, you have moved from delivering an engagement to building the toolkit that makes the next one faster, and that is the whole shift from practitioner to professional.
