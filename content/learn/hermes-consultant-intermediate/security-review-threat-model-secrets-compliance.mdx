# Lesson 16: Security Review for a Client Engagement: Threat Model, Secrets, and Compliance

Somewhere in every client engagement there is a moment when the agent you built has to justify its existence to people who do not trust it. A security architect asks how the agent accesses the database. A compliance officer asks where the client's data travels. An IT director asks what the agent can do on its own. You have a choice about when you meet that moment. You can run a real security review during delivery, when the answers are still cheap to change, or you can discover the questions at the go-live review, when the answers are expensive and your credibility is on the line. This lesson is about doing the first.

The failure mode this lesson exists to kill is the treat security as a final gate. You scope the work, you build the agent, you test it, and then on the last day you run a security scan and hope it passes. That order is backwards, and it is how engagements stall at the worst possible time. Security is not a downstream gate to clear; it is a constraint you design against from the first estimation call, the same way you design against scope creep and environment constraints. The working practitioner treats threat modeling, secrets hygiene, and compliance evidence as part of the delivery, not as a phase appended to it. That mindset is the transferable skill, and it applies to any agent platform, not just Hermes.

## The threat model is the client's, not yours

Start with a threat model, and mean the term precisely. A threat model is a structured account of three things: the assets you are protecting, the actors who threaten them, and the trust boundaries the actors would have to cross to reach the assets. You write it down, you get the client's security team to correct it, and everything you do afterward is tested against it. Without one, every security decision you make is a guess about what matters, and you are guessing on the client's behalf about what matters to them. That is exactly the kind of assumption the intermediate consultant has learned not to make.[^1]

The assets in an agent engagement are not just the obvious ones. The client's data is an asset, certainly, and so is the agent's access to that data, which is the thing an attacker actually wants. The credentials that grant that access are an asset. The model and its provider connections are an asset, because a compromised agent outbound is a path out of the client's network. The environment the agent runs in is an asset. List them all before you start protecting anything.

The actors are the uncomfortable part, because the worst of them usually has a corporate badge. Yes, there is the external attacker probing your exposed surfaces. But there is also the disgruntled employee whose account the agent uses, the contractor who overreaches, the prompt injection that turns the agent itself into a tool for exfiltration, and the well-meaning operator who pastes a secret into a chat. A threat model that only names the hacker in the parking lot is a threat model the client's security team will correct within a minute. Name the insiders, name the prompt injection, name the accidental leak. They are the threats that actually break agent deployments.

The trust boundaries are where your agent skills do the real work. A trust boundary is the line an actor must cross to reach an asset: the boundary between the human and the agent, between the agent and its filesystem, between the agent and the network, between the agent and the client's data stores. Your job is to enumerate every boundary and then, for each one, ask what stands at it. What stops an untrusted actor from crossing? What stops a compromised agent from crossing it further than the task requires? If the answer is nothing, that is a finding, and you have found it in scoping instead of at go-live.

## Map the trust boundaries around an agent that acts

The reason agent security stumps traditional security teams is that an agent is not a passive application. It reads files, runs commands, calls APIs, and takes actions without a human approving each one. That autonomy is the entire value of the engagement and the entire surface of the risk. The professional frames the conversation around that tension: how much autonomy does the agent need, and what is in place to keep that autonomy from exceeding the task.

Hermes Agent runs on an explicit defense-in-depth model, and walking its layers is a useful way to think about your own design because each layer corresponds to a trust boundary you will also meet in the client's environment. The first layer is user authorization: who is allowed to talk to the agent at all, enforced by allowlists and pairing on messaging gateways. The second is dangerous-command approval, which puts a human in the loop for destructive operations. Then come file write safety, which denylists and sandboxes writes, and container isolation, which runs the agent inside a hardened Docker, container, or remote filesystem boundary. The model continues with MCP credential filtering to keep subprocess credentials isolated, context-file scanning to catch prompt injection in the files the agent reads, cross-session isolation so one session cannot reach another's data, and input sanitization against shell injection.[^2]

Here is the lesson an intermediate consultant carries away from that architecture: security is layered, and no single layer is sufficient. Each layer covers a different boundary, so a weakness in one is caught by another. When you review a client setup, you check that the layers exist, not that one magic control is turned on. You ask who can reach the agent, what it can write, where it runs, whether its credentials leak to subprocesses, whether the files it reads are scanned, and whether sessions are isolated. A setup that answers all six has a defense-in-depth posture. A setup with one strong control and five gaps is not secure; it is a gate with an open field around it.

The same principle transfers to the delivery environment. Hermes runs as a multi-agent system through profiles, and the critical boundary there is that a profile is its own directory of config, credentials, memory, sessions, and jobs, not a sandbox. Profiles separate one agent's state from another's, but they do not by themselves stop an agent from reading the wider filesystem if the terminal backend allows it.[^3] If you are handing a client a deployment that runs several agents, you review where each one can reach, and you use a terminal backend that actually contains the agent rather than assuming a profile is a security boundary.

## Secrets are the first thing the client's security team looks at

Run this thought experiment. The engagement is almost done, and you are walking the client's security lead through the deployment. The first thing they reach for is not the model config or the orchestration logic. It is the credentials: where are the API keys, where are the database tokens, where are the service accounts, and who can read them. That instinct is correct, because a leaking secret is the highest-severity, lowest-effort failure in any agent system. If your secrets are not right, nothing else about your security matters. You have already lost.

The discipline starts with knowing where secrets live and refusing to let them live in visible places. In Hermes terms the correct home for a credential is an environment variable or a credential file loaded from configuration, not a value embedded in a prompt, a script, or a committed file. The security model reflects this: environment variables are passed through to agent terminal calls, and credential files for OAuth tokens and the like are passed through separately, so the agent gets what it needs without the secret entering the conversation or the transcript. MCP subprocesses get their credential-bearing environment variables isolated and redacted, so a Web Search or other integration does not expose the parent's keys.[^2]

Then there is the question of whether a secret should be there at all. Least privilege is the rule that keeps reviews short: give each agent, each job, each profile the narrowest set of credentials the task actually requires, and nothing wider. A data-reading cron job does not need production write access. A reporting agent does not need the admin service account. When the security reviewer asks why an agent holds a credential, the answer should be specific: this job reads this table, and this token is scoped to that read. If you cannot give that answer, the credential should not exist.

Rotation and leakage are the two secrets you will actually be tested on. Rotation means every credential has a lifetime and a documented way to be replaced, so a leaked key is a bounded incident and not a permanent backdoor. Leakage means you know exactly where a secret could have been written and you check there: chat transcripts, commit history, log files, and session records. Hermes applies secret-redaction rules to its process result logs even when live-output redaction is disabled, which is a good model for the client's own logging.[^4] The review you run on your own deployment should mirror that: prove that no credential appears in the places a credential should not appear.

## Least privilege and approval are containment, not weakness

An autonomous agent makes the client nervous precisely because it acts without asking. The professional reframes autonomy as a dial, not a binary. You decide how much approval the agent needs, and you set the dial according to the risk of the action and the trust in the environment, then you document why the dial is where it is.

Hermes exposes this as a configurable approval model with distinct modes, and the mode you choose is itself a security decision you should be able to justify. In smart mode a risk assessment auto-approves safe commands and escalates genuinely dangerous ones. In manual mode every dangerous command prompts a human. In off mode, which maps to the yolo flag, all guards are disabled, and the documentation is blunt that this is for trusted disposable environments only. The sharper control for headless work is the per-context mode: cron jobs default to deny, so a scheduled run that hits a dangerous command fails closed instead of silently executing or waiting forever on an approval nobody can give.[^2]

Two details here are the difference between a professional review and a superficial one. First, containment via approval still trusts the model to classify commands correctly, so approval is a boundary, not a substitute for a constrained environment. Second, the hardline blocklist exists below everything: catastrophic commands are refused regardless of approval mode or yolo, because some actions are unrecoverable once executed. When you review a deployment you check that containment has both halves: the approval dial set appropriately for the context, and an irreducible floor that no mode can lower.

The containment story is also where the client's risk appetite gets a concrete shape. A client that wants the agent near production data gets a deployment where the agent runs in a restricted terminal backend, where file writes are sandboxed, where sessions are isolated, and where approvals fail closed in unattended contexts. A client that is still uneasy gets a demonstration of the dial at its most restrictive, then a walk up to precisely the autonomy the work requires. You are not selling the client a trust-me; you are selling the client a dial they can turn and see what changes.

## Compliance is evidence, not assurances

When the client's compliance officer enters the review, the register of the conversation changes. They are not asking whether the system is safe in the abstract. They are asking whether it can be shown to satisfy a standard, a data-residency rule, a retention policy, or an audit requirement. Compliance is the practice of producing evidence for those questions, and the intermediate consultant answers with evidence, not with claims.

The first compliance question is about data flow. Where does the client's data go when the agent uses a model? Does any of it leave the client's environment, and if so, with which provider, in which region, under what retention? This is not a question you should be surprised by in the review, because you should have asked it during scoping when you chose the model provider and the deployment shape. If the answer involves transmission, the client needs to know and to have signed off on it. The consultant who can produce the model's data-handling documentation and explain exactly what the agent sends is the consultant who passes the review.

The second question is about the audit trail. When a compliance requirement says the client must be able to show what happened in a system, the agent's sessions, logs, and delivery records are the exhibit. In Hermes terms that means the session records, the cron run status, and the process logs are not incidental; they are the compliance artifact the client's auditors will read. You design the deployment so this trail is intact: timestamps, who or what initiated an action, what the outcome was. A deployment whose history is legible is a deployment you can defend in front of an auditor. A deployment whose history lives only in one person's memory is not.[^5]

The third question is the one that governs everything else: what is the client's regulatory context, and what does it actually require? The honest professional answer, which the intermediate consultant learns to give, is that this is the client's call, informed by their counsel, and not yours to improvise. What you bring is the technical evidence that lets their call be an informed one: what the agent can access, where data travels, what gets logged, how credentials are scoped, and what the approval posture is. You do not decide their compliance posture for them. You give them enough truthful, specific information to decide it themselves, and you flag precisely where their determination changes what you would build.

## Worked example: the engagement that had to survive a security review

Walk through one engagement end to end. You are delivering an agent that summarizes and triages support tickets for a financial-services client, and the client's security team has scheduled a review before production access is granted. This is not a hostile moment; it is a routine gate, and how well you prepped determines whether it is a 30-minute confirmation or a two-week rework.

You began the engagement by writing the threat model. The assets are the ticket data, which includes customer PII, the agent's access credentials, the model endpoints, and the support system. The actors include an external attacker, a rogue insider, prompt injection aimed at tricking the agent into extracting or forwarding data, and accidental exposure. The trust boundaries are the chat surface, the agent's filesystem, its network access, and the support API it reaches. You wrote all of this in a one-page document and handed it to the client's security team in week one, and they corrected two points: they added a stricter data-retention requirement and they named a specific internal system the agent must not touch. That page is now the contract for every decision that follows.

The secrets lived in a credentials file and environment variables, scoped to a read-only service account for the support API, with a rotation policy and a documented replacement path. Nothing was embedded in a prompt, a script, or a transcript. When the reviewer asked where the keys were and who could read them, you answered with the file path, the scope, and the rotation cadence.

The approval dial was set to smart mode for interactive sessions and deny for the nightly cron job, because a scheduled run that needed human approval should fail closed and report, not hang silently. The agent ran on a terminal backend that could not reach beyond its working directory, file writes were constrained, and sessions were isolated. You demonstrated each control rather than asserting it.

At the review the security lead asked the three questions the model prepared you for. Where does the data go? You named the provider, the region, and what the agent actually sends, from the model's data-handling documentation. What would happen in a compromise? You walked the trust boundaries, the credential scope, and the no-touch list the client had added in week one. What can the agent do on its own? You showed the approval dial, the fail-closed cron mode, and the irreducible blocklist floor. The review closed with a list of three tightening requests, none of which re-opened your architecture, because the threat model had already pinned the decisions to their requirements. The gate passed because you designed against it from the first week instead of discovering it on the last.

## The discipline that transfers

Strip away Hermes and the same moves apply to every agent engagement you will ever run.

**Write the threat model in week one.** Assets, actors, trust boundaries, written down and corrected by the client's security team. It is the contract every later decision is tested against.

**Map every trust boundary and name what stands at it.** Authorization, approval, file-write safety, containment, credential isolation, session isolation. Check that the layers exist, not that one magic control is on.

**Treat secrets as the first thing a reviewer checks.** Know where every credential lives, scope each one to the narrowest task, rotate them on a schedule, and prove none appears where it should not.

**Set the approval dial precisely and document it.** Autonomy is a dial, not a binary. Choose the mode for the context's risk, and confirm unattended work fails closed.

**Produce compliance evidence, not assurances.** Answer data-flow, audit-trail, and regulatory questions with documentation and legible records, and let the client's counsel set the regulatory bar.

## The pitfalls that turn a review into a rework

**Writing the threat model at the end.** Discovering the boundaries during the go-live review, when the answers are expensive and your credibility is on the line. Write it in week one and get it corrected.

**Naming only the external hacker.** Ignoring the insider, the contractor, the prompt injection, and the accidental leak. The threats that break agent deployments are usually not the ones in the parking lot.

**Leaving secrets visible.** Embedding a key in a prompt, a script, or a committed file. Secrets belong in environment variables or credential files, scoped, rotated, and never in a transcript.

**Believing a profile or a strong control is a security boundary.** Separation of state is not containment of access. Check the whole layer stack, not the one impressive control.

**Setting one approval mode as a blanket.** Running interactive and unattended work through the same dial. Headless jobs must fail closed on a dangerous command, not hang or proceed.

**Answering compliance with assurances.** Telling the reviewer it is fine instead of showing them where data goes, what is logged, and how credentials are scoped. Evidence passes reviews; claims get re-opened.

## Try it

A client is asking you to deploy an agent that reads a shared customer database and drafts follow-up emails. They have not asked you to do a security review; they have asked you to estimate the work. Your estimate needs a security line in it.

1. Write the one-page threat model you would hand the client in week one: the assets, the actors including the insider and the accidental leak, and the trust boundaries the agent must cross.
2. For each trust boundary, name the control you would put at it, and say which Hermes defense-in-depth layer it maps to.
3. List every credential the deployment will need, how you will scope each one, and where each will live so it cannot leak into a transcript or commit.
4. State the approval posture you would set for the interactive agent versus the nightly batch job, and justify why the two differ.
5. Draft the three data-flow, audit-trail, and credential-scope answers you will give the client's compliance lead when they ask.

If you can do all five, you have a security review skill: you threat-model first, you contain by layer, you treat secrets as the first thing a reviewer checks, and you answer compliance with evidence. That is what turns a delivery that passes a gate into one that never needed to fear it.

## What's next

You can now run a security review of your own delivery: you threat-model first, you map trust boundaries to real controls, you keep secrets scoped and invisible, and you produce compliance evidence instead of assurances. But a review is not the last stop. The client's security, IT, and legal teams are not just adversaries to satisfy; they are stakeholders you must work with for the life of the rollout. The next lesson teaches exactly that: working with IT, compliance, and legal on agent rollouts. It covers how you get those teams triaged in early, translate technical decisions into the language each one speaks, and carry the rollout through procurement, sign-off, and ongoing governance without stalling on the seams between the technical and the administrative.
