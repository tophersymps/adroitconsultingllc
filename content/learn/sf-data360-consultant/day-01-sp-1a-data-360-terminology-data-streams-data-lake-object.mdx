# Lesson 1: Data 360 Terminology: Data Streams, Data Lake Objects, Data Model Objects, and the Three Stages

A consultant walks into a Data 360 design review with a diagram that looks fine. Data flows from four systems into one box labeled customer, then out to marketing. The architect asks one question about that box: is it the data lake object or the data model object? The consultant cannot answer, because the diagram used the two words as if they meant the same thing. The review stalls, the team redraws the diagram, and a week disappears over four letters of vocabulary.

That week is avoidable. Every question in this domain, and every argument on a real project, rests on a small set of words that Data 360 uses with precision. Each word names a stage, a container, or a boundary, and moving data across those boundaries has consequences. Learn the words loosely and you will map fields that should have stayed raw, unify records that were never the same person, or promise a real time answer from a pipeline that only refreshes once a night.

This lesson covers requirement sp-1a, part of the Solution Positioning domain worth 14% of the Salesforce Certified Data 360 Consultant exam. The requirement asks you to describe Data 360's key terminology and business value, covering the core constructs (data streams, data lake objects, data model objects, data spaces, data graphs, unified profiles) and the three processing stages they live in. The exam tests this vocabulary directly, so treat each term here as a working tool rather than a glossary entry.

## Deep Dive

### The three stages are Connect Data, Harmonize and Unify, then Analyze and Act

Data 360 moves data through three stages, and an exam question will ask you to name them in order: Connect Data, Harmonize and Unify, Analyze and Act. If a question asks for the correct sequence, it always starts at Connect Data, never at Analyze and Act. The order is the point, because you cannot harmonize data you have not connected, and you cannot activate a segment built from data you never unified.

Connect Data brings your enterprise data in, structured and unstructured, regardless of where it lives. That includes Salesforce CRM data across clouds, external applications, and data in lakes or warehouses, which Data 360 can reach through Zero Copy Data Federation without physically copying it. Harmonize and Unify does the governance, transformation, and identity work. This is where you tag and classify data, run transforms to clean and shape it, map it to the standard model, and collapse many source records into one unified profile per person. Analyze and Act turns the unified data into outcomes: calculated insights and segments, predictive models, and activation that pushes the result into Salesforce apps, agents, and third party destinations.

The exam tip that pays off is simple. Before you answer any terminology question, place the term in a stage. A stream is Connect Data. A data lake object is the landing copy from Connect Data. A data model object is Harmonize and Unify. A data graph, a calculated insight, and an activation are Analyze and Act. Once you can sort the words into those three buckets, the wrong answers usually announce themselves.

### A data stream is the source connection, and a data lake object is where its rows land

A data stream is a configured connection that brings a specific data source into Data 360. It comes in two shapes. A batch stream runs on a schedule or as a one time load, and a streaming stream carries continuous events as they happen. The choice is a design decision with cost and latency consequences, because a streaming pipeline is metered differently and is meant for data that must be acted on in motion, while a nightly batch is fine for data that only needs to be current by morning.

When a stream runs, its rows land in a data lake object, or DLO. The DLO is the persistent storage container for the ingested copy, and it lives inside a data space.[^1] A DLO is created automatically when you bring data in, though you can also create one manually, and it can be an external data lake object that holds only metadata for data federated from an external source.[^2] Think of the DLO layer as storage and landing, not as the customer model. It is the raw material: the ingested rows, still shaped like the source system, waiting to be harmonized.

This distinction is where exams and projects both go wrong. A data lake object is the landed, persisted copy of ingested data. A data model object is the harmonized mapping to the Customer 360 Data Model. If an answer calls the ingested, landed table a DMO, it is wrong, and if a design document maps fields before the data has landed, it has the stages out of order. Keep the two roles separate in your head and the rest of the pipeline reads cleanly.

### A data model object maps DLO fields to the Customer 360 Data Model

A data model object, or DMO, is a harmonized grouping of data, made of attributes, that you create by mapping DLO fields to the standard Customer 360 Data Model.[^2] The Customer 360 Data Model is the standard model that makes data interoperable: it organizes the types of data and the relationships between them, so that two systems that both describe a customer produce records that can be understood together. An attribute is a standardized piece of information about a DMO, typically held in a field.

Common standard DMOs include Individual, Account, Sales Order, and Email Engagement. Locating your data in one of these standard objects is what makes the downstream steps possible, because identity resolution, segmentation, insights, and activation can only use mapped fields and objects with relationships. DMOs can be standard or custom, and a DMO provides a physical or a virtual view of the underlying data. A virtual DMO is a view over a DLO rather than a fully persisted object, which matters when you want to expose shaped data without materializing another copy.[^7]

Mapping is the step that makes a DMO real. Data mapping connects the fields in your DLOs to the standardized fields in the Customer 360 Data Model DMOs, and while some starter data bundles arrive with fields already mapped, custom fields and unmapped standard fields usually need manual work.[^4] The fields that carry the most weight are the ones identity resolution depends on later: names, identifiers, email addresses, and phone numbers, because those are what let Data 360 link one person's records across sources. Map carelessly here and unification has nothing reliable to match on.

Once identity resolution runs, the reconciled attributes live in a unified DMO, which is a DMO that contains unified data after you unify disparate data with identity resolution rulesets.[^3] The unified DMO is the single source of truth for segmentation and activation, and this is the layer, not the DLO layer, that downstream features should read from. When a colleague asks where the trustworthy customer record lives, the answer is the unified DMO, not the raw landing table.

### A data space partitions data, metadata, and processes, and doubles as a governance boundary

A data space is a logical partition that organizes your data, metadata, and processes for profile unification, insights, and marketing, and it doubles as a governance boundary.[^5] Enterprises split data spaces by brand, region, business unit, or regulatory zone, and a user sees and works only inside the space they are assigned to. This lets one company run several brands on a single Data 360 instance instead of standing up several instances, which is exactly the problem data spaces were built to solve.

The mechanics matter for exams. Data is ingested first and then segregated into the relevant spaces by mapping data lake objects into the space, with or without filters, and a single DLO can be added to more than one data space. You create the space's data models, calculated insights, identity resolution, segments, and activations inside it. Access is controlled through permission sets, and by default users with standard permission sets get the default data space. A Data 360 license includes one default data space, and additional spaces are add on licenses; you cannot delete the default space, but you can create more.[^5]

The reason data spaces sit in the same lesson as DLOs and DMOs is that they are the container those objects live inside. A DLO is mapped into a data space, and a DMO and its mapping live within a space as well. When a question mentions brand separation, regional data residency, or a team that must not see another team's data, the answer is usually a data space, and the follow up detail is that DLOs are the objects you assign into it.

### A unified profile links matching records, and it is not a golden record

A unified profile is a single, comprehensive view of a customer, created by linking data from multiple sources based on the identity resolution rules you configure.[^4] It consolidates everything Data 360 knows about a customer or account into one profile, and it is mutable, meaning it improves as source data changes, as new sources are processed, or as you adjust the rules. The ruleset that builds it contains two kinds of rules. Match rules decide which source profiles are the same person, using methods such as exact, fuzzy, and normalized matching. Reconciliation rules decide which single value to display when matched sources disagree, using options such as last updated, most frequent, or source sequence.

Here is the sentence the exam wants from you. A unified profile is not a golden record, and identity resolution does not overwrite your source data; it is a set of keys that links matching records without changing source data. Contact points such as email and phone all stay on the profile, and each linked identifier stays unique, but the profile gives you access to the context behind all of them. Reconciliation only decides what displays in the unified view; it never changes the underlying source objects. Even a value that is not selected for the unified profile is still stored, so nothing is lost when two sources disagree.[^4]

This is why the trap answer, that a unified profile overwrites the source records with the winning values, is wrong. Data 360 is deliberately non destructive at this layer because source systems usually remain the systems of record for their own data. If a design promises that unifying records will clean up the CRM, it will not, and the consultant who lets that expectation stand is setting up a disappointed client when the source still shows two spellings of the same name.

### Data graphs, insights, and activations are the Analyze and Act layer

A data graph is a grouping of data built by joining and transforming normalized DMO table data into new, materialized views. Because the data is precalculated, a query can return a complete profile in near real time with fewer calls, and real time data graphs are what make real time identity resolution, real time calculated insights, and real time segmentation possible.[^6] A data graph is not an ingestion channel and it is not a report. It is a precomputed, denormalized view that serves fast reads.

Calculated insights are metrics and aggregates, such as customer lifetime value or an engagement score, computed by combining data from several sources and refreshed automatically. They can be defined at the profile, segment, or population level, and once processed they materialize into a calculated insight object that you can query, report on, and feed into segments. Activation publishes a segment to a destination such as Marketing Cloud, an advertising platform, or an agent. Data graphs, calculated insights, and activations all sit in the Analyze and Act stage, and every one of them consumes credits as it runs, which is why the design choices in this lesson are also cost choices.

### Walking the whole pipeline in the org

You can trace all of this in a trial org in a few minutes, and doing it once makes the vocabulary stick.

1. In the Data 360 app, open Data Streams and note whether the connected source is a batch stream or a streaming stream, then open the resulting data lake object to see the landed rows.
2. Go to Data Model and inspect a standard DMO such as Individual, then confirm which DLO fields map to which DMO attributes.
3. Open Data Spaces and identify the default space, then check which DLOs and DMOs are mapped into each space.
4. Under Identity Resolutions, open the ruleset and read the match rules and reconciliation rules, then view a unified profile to see the reconciled attributes and the preserved contact points.
5. In Data Graphs, open the Profile data graph and confirm the included objects, then list the materialized views it exposes.
6. Trace one metric end to end: pick a calculated insight, note its source DMOs, then find the segment and the activation that consume it.

Step one alone separates the students who pass from the ones who guess, because seeing the landed rows in a DLO next to the mapped attributes in a DMO removes any doubt about which is which.

## Exam Traps

Three traps dominate this objective, and each one is a vocabulary slip rather than a knowledge gap.

First, swapping DLO and DMO. A DLO is the landed, persisted data in a data space, while a DMO is the harmonized mapping to the Customer 360 Data Model. Any answer that calls the ingested landed table a DMO is wrong, and the correct order to remember is a data lake object, then a data model object after mapping harmonizes it.

Second, believing a unified profile is a golden record that replaces source values. It is not. Identity resolution links records and reconciliation decides what displays, and neither step overwrites the underlying source objects. If a question offers you a choice where the source data is changed, that choice is the trap.

Third, treating a data graph as another word for a data stream or a report. A data graph is a precomputed, denormalized materialized view that serves real time queries. It is not an ingestion channel and it is not a reporting surface, so an answer that puts a data graph in the Connect stage has misread the term.

## What a consultant should walk away with

The decision rules are short. Place every term in a stage before you reason about it: Connect Data, Harmonize and Unify, Analyze and Act, in that order, always starting at Connect. Remember that a stream lands rows in a data lake object, and mapping turns a DLO into a data model object. Keep the raw DLO layer and the harmonized unified DMO layer distinct in every diagram, because the unified DMO, not the DLO, is the source of truth for segmentation and activation. Treat a data space as the container and the governance boundary that holds the objects. And describe a unified profile as a set of keys that links matching records without changing source data, never as a golden record that overwrites them.
