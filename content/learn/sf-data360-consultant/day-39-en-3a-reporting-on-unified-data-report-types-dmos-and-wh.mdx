# Lesson 39: Reporting on Unified Data: Report Types, DMOs, and What to Configure First

A marketing lead asks for "a report of our customers." A consultant builds a standard report on the Unified Individual data model object, runs it, and returns a clean count. The lead looks at it and asks why the number is half what the source system reports. The answer is that the unified object counts people, and the source system counted rows. The report was correct for the grain the consultant chose and wrong for the question the lead asked. Reporting on unified data is mostly a discipline of choosing the right grain before choosing the right chart.

This lesson covers requirement en-3a, "View and build reports and dashboards using Data 360," inside the Data Enhancements, Sharing, and Analysis domain, worth 18% of the Salesforce Certified Data 360 Consultant exam. The requirement focuses on where Data 360 data appears in reports, the report types exposed, and what a consultant must configure first. It is the reporting counterpart to the reference paths in Lessons 37 and 38: those taught how data leaves Data 360 and reaches a record page; this lesson teaches how the same data becomes an analysis a business will act on.

## Deep Dive

### Reporting on Data 360 data uses the standard report builder with data model object sources

Reporting on Data 360 data uses the same Reports tab and report builder that CRM reporting uses, but the source records come from data model objects rather than from CRM tables. From the Reports tab you choose New Report, pick the Data 360 report category, and select the object to report on. The muscle memory of Lightning reporting still applies, and that is deliberate. Grouping, filtering, summarizing, and charting all work the way they do for any other report; only the source of the rows changes.

A consultant has to configure the data path first, because none of the clever report building matters if the data was never there. The org has to be connected to Data 360, the reporting user needs the Data 360 permission set and the appropriate license, and the data model objects used in the report must already be populated by streams, transforms, or identity resolution. A report cannot surface data that never landed. When a report comes back empty in a stable org, the first place to look is upstream, at the stream or the transform that should have filled the object, not at the report definition.[^1]

### Standard reports read one object, including calculated insights

A standard Data 360 report is built on a single object: a data model object, a semantic model, or a calculated insight object. That single-object scope is the defining feature. When the source is a calculated insight, the builder treats the insight measures as columns and its dimensions as groups, so you can group, filter, and chart precalculated metrics without rebuilding the logic that produced them. If a calculated insight already ranks web traffic sources by product category, the report can break that ranking out into columns the moment you point the builder at the insight.[^3]

Standard reports are the fastest path for a single subject area, and they run against near real time data, so the figures move as streams and transforms refresh. Choose this surface when the question concerns one object and one grain of analysis. The trap is stretching a standard report to answer a question that spans objects, which it cannot do, because it reads exactly one object and then stops.

### Choose the object before the chart: data model object, semantic model, or calculated insight

A standard report can be built on a data model object, a semantic model, or a calculated insight, and the three answer different questions. A data model object is the grouped entity itself, such as Individual or a custom DMO you created for a use case. A semantic model sits above the DMOs and presents a modeled subject area with its own fields and relationships, which suits reporting when the business wants a curated vocabulary rather than the underlying object names. A calculated insight is a precomputed metric object, and it is the right surface when the number has already been computed and you only need to slice it.

The order of preference is simple. If the metric exists as a calculated insight, report the insight, because rebuilding the same logic in a report wastes effort and risks a second definition of the metric. If the need is a curated subject area, report the semantic model. If the need is a plain list of records from one entity, report the data model object. The mistake is reporting a DMO when a calculated insight already holds the answer, which produces a report that recomputes what Data 360 already knows and can disagree with the insight by a rounding rule or a filter difference.

### Custom report types join up to four related DMOs

When the question spans related objects, you use a custom report type on Data 360 objects. A report type defines the set of records and fields available to a report based on the relationships between a primary object and its related objects, and a custom report type extends that to objects and fields the standard types do not cover.[^2] For Data 360, a custom report type joins multiple related data model objects, up to four, and lets you lay out fields from each related object through the lookup relationships. The truthful contrast is that a custom report type can join up to four related data model objects, while a standard report reads a single object. That single sentence separates the two surfaces on the exam.

You create a custom report type from Setup under Report Types, then New Custom Report Type, choosing the primary object and a store-in category. Data 360 supports unified objects and the unified link objects that identity resolution produces, which is what makes cross-source analysis possible. The unified link object is the joining point between the source data and the unified individual; it lets you traverse from the unified profile back up to the individual source records, which is why it is the bridge a report needs to show a customer next to the records that unified into them.[^5]

This is the surface for the requirement that trips people up: a report on a customer together with the source records that unified into that customer. To build it, create a custom report type using the unified object as the primary object and relating the source object and the unified link object. A standard report on the Unified Individual alone cannot show the contributing source rows, because it reads a single object. The link object is what turns "here is the customer" into "here is the customer and every source record behind them."

Put the pieces together with an example. A retailer wants a report that lists each unified customer next to every loyalty transaction that fed that customer's profile. The consultant starts a custom report type on the Unified Individual as the primary object, relates it to the Unified Link Individual object, and brings in the transaction DMO through the link, all within the four-object ceiling. The report then shows one unified row per customer with the contributing transactions beneath it, which is exactly the shape the retailer asked for. Building the same thing as a standard report on Unified Individual would show the unified customers with none of the source transactions, because a standard report reads a single object and stops.

### You can start a report from the object itself

You can start a report from the object rather than from the Reports tab, which is a small convenience with a real consequence for unified data. Open a data model object record page and choose Create Report, or use the Create Report action from the object list view, and the builder opens preloaded with that object. The consultant lands on the right report type without hunting for it.

This matters for unified data because a unified profile and its unified link are ordinary data model objects to reporting. To analyze one customer with its source records, begin from the unified object and add the link object through a custom report type, so the related source rows appear as related records rather than as separate, unrelated counts. Starting from the object nudges you toward the correct primary object before you have built anything you have to undo.

### Report features that carry over

Several report features carry over from Lightning reporting and are worth naming in a solution. Matrix reports group records in rows and columns so you can compare subtotals across sections of the data. Bucket columns group and compare records without a formula or custom field, defining ranges or categories over numeric, picklist, or text values, for example bucketing an engagement score into low, medium, and high. Standard fiscal calendar options let you trend over time, and you can group, sort, and filter Data 360 reports by fiscal week, month, year, or quarter when the org uses a standard fiscal year.[^3]

These features operate on the report, not the data model, so they change presentation and grouping only and never write back to the underlying objects. That single fact resolves several exam questions at once. A report reads data and presents it; it does not create a field, does not update a record, and does not modify a DMO. If an answer choice claims a report writes its output back to the objects, the choice is wrong no matter how useful that behavior would be.

### What to configure first, and how visibility follows the object

Reporting on Data 360 data is governed, so ground the prerequisites before promising a report. The org must be connected to Data 360, the user needs the connector permission set and the appropriate license, and the objects must exist. Object access is itself governed by data space access, so a user who cannot reach the data space that holds an object cannot query or report on that object.[^6]

Report visibility then follows the sharing model of the object: a user who cannot see the underlying data model object cannot report on it. If a user holds the correct license and the connector permission set but cannot find a Data 360 object in the report builder, the most likely cause is that the user lacks access to the underlying data model object, so it is not available to report on. Page layouts, unified object support, and bucket columns are unrelated to whether the object appears; object access is the whole story.[^4]

The last prerequisite is a decision, not a setting: for unified data, decide deliberately whether a report should read the source object or the unified object. One counts source profiles and the other counts unified profiles, and the difference is exactly the duplication that unification removed. Both numbers can be correct, and only one of them answers the question that was asked. When a stakeholder wants to reconcile to a source system, report the source object; when they want a deduplicated view of people, report the unified object.

Object availability inside the builder is the most common surprise for a capable admin. A user can hold every Data 360 permission and still open a report builder that shows no Data 360 objects, because the object list is filtered by what the user can actually access. That filter is not a bug and no setting removes it. Confirm the object is populated, confirm the user can reach its data space, and confirm the sharing model lets the record be read, in that order. If those three hold and the object still does not appear, the problem is upstream in the data pipeline, not in reporting.

### Reports become dashboards

A saved report is an input to a dashboard, and the same governance that governs the report governs its dashboard. Lightning dashboards run on the reports beneath them, so a user who cannot open a Data 360 report cannot see the dashboard component built from it either. Plan the folder structure and the dashboard sharing together with the report, because a dashboard inherits the access of its running user and its source reports. When a stakeholder asks for a Data 360 dashboard, the first answer names the reports it needs and the access those reports require, not the widget count.

### A six-step walkthrough

1. Confirm the org is connected to Data 360 and that the reporting user holds the Data 360 connector permission set and license, then verify the data model objects are populated.

2. From the Reports tab, click New Report, and in the Data 360 report category select the object to report on, then click Start Report.

3. To span related objects, go to Setup, use Quick Find to open Report Types, click New Custom Report Type, and choose a unified object or data model object as the primary object and set the store-in category.

4. In the custom report type, relate the primary object to the source object and the unified link object, place the fields you need, and save.

5. Alternatively, open a data model object record page or its list view and choose Create Report to start from that object.

6. Add columns, summarize measures, group or bucket values, refresh the preview, and save the report to a folder.

## Exam Traps

The first trap is confusing a standard Data 360 report with a custom report. A standard report on a calculated insight is not the same as a custom report: the standard report reads one object, and only a custom report type joins related data model objects, up to four. When a scenario needs data from more than one object, the standard report is off the table.

The second trap is believing a report can create the unified data it shows. Reporting cannot create unified data. If the unified object is empty, the fix is upstream in streams, harmonization, or identity resolution, not in the report builder. No amount of grouping will conjure rows that never survived unification.

The third trap is not noticing that the grain changes the count. Reporting a source object and reporting the unified object give different counts on purpose. Choosing the source object reintroduces the duplicate rows that unification consolidated, so pick the grain the question actually needs. If a scenario asks for a deduplicated customer count, the source object is the wrong answer for the stated goal.

## The decision rules to carry out of this lesson

Before designing a Data 360 report, confirm three things in order: the org is connected, the objects are populated, and you have chosen the unified grain rather than the source grain. Use a standard report for a single object, including a calculated insight, whose measures become columns and dimensions become groups. Use a custom report type when the question spans related objects, and remember that a custom report type can join up to four related data model objects, while a standard report reads a single object. To show a customer with the records that unified into them, create a custom report type using the unified object as the primary object and relating the source object and the unified link object. When a permitted user still cannot find an object in the builder, the cause is almost always that the user lacks access to the underlying data model object, so it is not available to report on.
