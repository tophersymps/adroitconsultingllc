# Lesson 40: Dashboards Versus Tableau Next Analytics: Choosing and Sharing the Right Surface

A stakeholder opens the dashboard you built and sees blank tiles. She is the same audience you tested with, the report is the same one that filled correctly when you ran it an hour ago, and nobody changed the data. What changed is who is looking. A dashboard renders through the viewer's access to the object and fields behind each report, and a viewer who cannot see the underlying Data 360 object sees an empty tile. That blank tile is the failure this lesson exists to prevent.

There is a second failure nearby, and it is quieter. A team answers the question of which surface to use with a preference rather than a decision. One consultant reaches for a Lightning dashboard because that is what the org already runs, another reaches for Tableau Next because it is newer, and neither can say why the surface fits the stakeholder in front of them. Requirement en-3b, in the Data Enhancements, Sharing, and Analysis domain worth 18% of the Salesforce Data 360 Consultant exam, asks you to view and build reports and dashboards using Data 360, covering dashboards, the analytics surfaces available, and how to share the right one with a given stakeholder.

This lesson covers the three surfaces a Data 360 consultant chooses between: the Data 360 report, the Lightning dashboard, and the Tableau Next stack with its semantic layer. It works through when each one fits, how they stack rather than compete, and why sharing is a separate decision from building. By the end you should be able to name the surface for a stakeholder, say why it fits, and confirm that the recipient can actually see the result.

## Deep Dive

### A Lightning dashboard is a collection of components, each driven by its own report

A Lightning dashboard is not one query. It is a collection of components, and each component can be driven by a different report. That is the key Data 360 behavior, and it is what makes the dashboard the right surface for a mixed audience. You can build one dashboard whose widgets use several Data 360 reports, or mix a Data 360 report with a CRM report in the same dashboard so a stakeholder sees unified metrics and CRM pipeline side by side.

The mechanics are worth stating plainly. Each component points at a source report, and the report is what reads the data. The dashboard does not query the object directly, it reads report output.[^1] Because the dashboard reads report output, a change to the underlying report or the underlying data flows through the dashboard on refresh. Add a column to the report and the component picks it up. Fix the report's filter and every dashboard that uses it reflects the fix. This is why you always build the report before the dashboard: the dashboard is a presentation layer over reports, not a data layer of its own.

The quiz tests the mixed-source case directly. A stakeholder needs one view that shows a Data 360 unified customer metric next to CRM pipeline, and the question asks which surface fits best without extra architecture. The answer is a Lightning dashboard with one component on the Data 360 report and another component on the CRM report. The dashboard combines components driven by different reports, so a Data 360 report and a CRM report can sit in one view. A standard report reads one object. A custom report type joins Data 360 objects, not CRM data with Data 360 data. A calculated insight computes metrics inside Data 360 rather than blending in CRM data. None of those give you the mixed view without extra architecture; the dashboard does.

Use a dashboard when the audience needs several related insights in one view. The signal is plural insight and a single audience. If the stakeholder wants to see unified engagement next to open pipeline next to last quarter's trend, that is three components and one dashboard. If the stakeholder wants to explore and re-slice the data themselves, that is a different requirement and a different surface.

### Tableau Next is the analytics platform built on the same data layer

Tableau Next is the analytics platform built on the same data layer as Data 360, and its assets run from data to semantics to consumption.[^3] Data is a Data 360 object: a data model object, a data lake object, or a calculated insight object. Semantic models add business meaning on top of that data. Metrics and visualizations follow. Dashboards present them. That sequence is not a marketing diagram, it is the order you build in, and skipping a step shows up later as a metric that means something different in two places.

For most business users, prefer a dashboard over a bare visualization. A single chart is a unit of analysis, and a dashboard carries formatting, context, filters, and actions that a single chart does not. The dashboard is where a business user lives; the visualization is a building block an analyst assembles. When the requirement is governed self-serve exploration, Tableau Next is the surface. Governed means the person exploring is working from approved definitions rather than rebuilding a metric from raw fields, and self-serve means they are not waiting on an analyst for every question.

Tableau Next organizes this work in workspaces, which are the units that hold a discrete project's assets. A workspace is not a folder of loose files. It is the place an analyst creates and reuses the data connections, semantic model, metrics, and visualizations that answer a set of related questions. Assets live in a single workspace and can be referenced from others, so the same governed metric can serve several projects without being copied and redefined. When the analysis question is genuinely different, a new workspace is the cleaner answer even if some assets are shared by reference.

### Underneath Tableau Next is the semantic layer, Tableau Semantics

Underneath Tableau Next is the semantic layer, Tableau Semantics. A semantic model records which data model objects to use, how they relate, and the business definitions layered on top: field names, aggregations, and calculations. The raw data is numbers and strings; the semantic model is what makes an amount mean revenue and a count mean active customers. Semantic models are built with the Semantic Model Builder, which is available in Data 360 on the Semantic Layer tab and in Tableau Next. You open Data 360, go to the Semantic Layer tab, and click New Model to start.[^5]

Two behaviors matter for the exam. First, relationships mapped between data model objects in Data 360 are carried into the model. When you build a semantic model, the relationships you already defined between DMOs come with it, so you are not re-declaring joins, and circular relationships are removed to keep the model queryable. Second, semantic models are first-class Salesforce metadata and a single source of truth. Because they are metadata and not a copy of the data, reports, Tableau Next, intelligent apps, and AI all consume the same definitions. A metric defined once reads the same in a report and in a conversational answer.[^4]

The quiz tests this point directly, and the trap it sets is the word copy. The statement that is TRUE is that Semantic models define business meaning, relationships, and metrics over Data 360 objects and are reused across Salesforce. A semantic model is first-class Salesforce metadata that records which data model objects to use, how they relate, and the business definitions on top, and it is consumed by reports, Tableau Next, and AI. It does not copy Data 360 data into a separate store, it is not limited to Tableau Desktop, and it does not replace the data model objects it describes.

### Choosing an analytics surface is a consulting decision, not a preference

Choosing an analytics surface is a consulting decision, not a preference. The surface follows the question and the audience, and a consultant states the reason out loud. Use a Data 360 report when the question is one object and a defined grain. One object, one grain, one answer: that is a report. Use a Lightning dashboard when the audience needs several reports in one view or a blend of Data 360 and CRM data, and when the audience works inside Lightning. Choose Tableau Next when the requirement is governed metrics shared across Salesforce, richer visualization, workspaces for analysts, or conversational analysis where natural language prompts are translated into semantic queries.

The decision is not which surface is better. It is which surface matches the stakeholder and the governance requirement. A sales manager who lives in Lightning and wants unified engagement next to pipeline needs a dashboard. A data analyst who needs to explore governed metrics across a hundred field combinations needs Tableau Next. A single team that wants one number on a page needs a report. State the match and the reason: audience, governance, and grain. A consultant who cannot say why a surface fits is guessing, and the exam is built to catch guessing.

Conversational analysis is worth naming because it is the newest reason to choose Tableau Next. Natural language prompts are translated into semantic queries, so the answer comes from governed metrics rather than from whatever a language model happens to recall. The user asks a question in plain language, the platform resolves it against the semantic model, and the answer stays inside the definitions the org approved. That is the governance payoff of building the semantic layer before you build the conversational surface.

### Sharing is a data access decision layered on top of the surface

Sharing is a data access decision layered on top of the surface, and it is where most analytics rollouts break. Reports and dashboards are shared through folders and with users, groups, or roles. You share the folder, not the report or dashboard itself, and the recipient needs access to the folder, the right user permission, and access to the underlying object. That last requirement is the one teams forget.[^2]

The sharing still inherits the recipient's access to the underlying object, so a dashboard built on a Data 360 object only shows a viewer the rows and fields they are permitted to see. This is a feature, not a bug. It means you cannot leak data by sharing a dashboard, and it also means you cannot promise a dashboard of unified data before viewer access is confirmed. The same dashboard can look full to one user and empty to another, correctly, because the two users have different access.

The quiz builds a scenario on exactly this. A Data 360 report is shared as a dashboard but renders empty for the recipient, and the question asks for the most likely cause. The answer is The recipient lacks access to the underlying data model object, so the component shows nothing. A dashboard inherits the viewer's access to the object and fields behind each report, so a recipient without access to the data model object sees an empty component. Dashboards do display Data 360 reports, so that is not the cause, and report kind or bucket columns do not cause an empty render.

Analytics also reaches beyond its own tab. Insights can be brought into the flow of work, so the audience question is not only which dashboard but where the insight should appear. A metric can surface in the tool a team already uses, and Tableau Next assets can be shared and embedded in the flow of work rather than only opened in the analytics tab. Confirm the recipient's access before sharing, then decide where the insight lands.

### Treat the surfaces as a stack rather than competitors

Treat the surfaces as a stack rather than competitors. Raw insight lives in a Data 360 report. Several reports combine in a Lightning dashboard for CRM users. The semantic model makes those metrics consistent wherever they are consumed. Tableau Next turns them into governed visualizations and dashboards for analysts and business users. Each layer has a job, and the same numbers travel up the stack.

The decision a consultant states has three parts: which layer the stakeholder needs, what grain the data model objects must have first, and who is allowed to see the result. Grain comes first because no surface fixes a wrong grain. Access comes second because a perfect dashboard that renders empty for its audience is not done. Layer comes last because it falls out of the first two. When you can answer all three, the surface choice stops being a debate.

Do not promise a dashboard of unified data before the object is populated and viewer access is confirmed. The two prerequisites are boring and they are the whole game. A populated object gives the report something to read. Confirmed access gives the viewer something to see. Skip either one and the dashboard is a demo, not a deliverable.

## Config Walkthrough

Build the surface in six steps.

1. Build the underlying Data 360 report or reports first, confirming each is based on the correct object and grain. A report reads one object or a related set, so if the grain is wrong here it is wrong everywhere above it.

2. In Lightning, open Dashboards and click New Dashboard, then drag components and assign each one a source report, mixing Data 360 and CRM reports as the audience needs. Each component points at a report, and the dashboard reads report output.

3. Save the dashboard to a folder and share it with the users, groups, or roles who should see it, confirming they can access the underlying object. Sharing a dashboard does not grant access to the data behind it.

4. For governed analytics, open the Semantic Layer tab in Data 360 or a Tableau Next workspace and create a semantic model with the Semantic Model Builder. Select the data model objects, keep the fields that carry business meaning, and let the relationships mapped in Data 360 come across.

5. In Tableau Next, build visualizations from the semantic model, then assemble them into a dashboard with the Dashboard Builder. The visualization reads governed definitions, and the dashboard adds the formatting, filters, and actions a business user needs.

6. Verify access by viewing the dashboard as a representative user and checking that no widget renders empty because of object or field permissions. This is the step that catches the blank-tile failure before the stakeholder does.

## Exam Traps

Three traps dominate this objective.

The first trap is assuming a shared dashboard grants access. A dashboard inherits the viewer's access to the underlying object and fields, so it can render empty for a user who cannot see the data. Sharing a folder does not open the data behind it. When a stakeholder reports a blank dashboard, check the viewer's access to the underlying data model object before you touch the report.

The second trap is treating Tableau Next and a Lightning dashboard as interchangeable. A Lightning dashboard blends existing reports quickly, which is exactly what a mixed Data 360 and CRM view needs. Tableau Next adds a governed semantic layer, richer visualizations, and natural language analysis, which is what a self-serve analytics program needs. Each is right for its requirement and wrong for the other's.

The third trap is believing a semantic model copies data. It defines meaning, relationships, and metrics over Data 360 objects, which is why the same definitions are reused across reports, dashboards, and AI. Because the semantic model is metadata and not a copy, there is no second store to refresh and no drift between two copies. If you catch yourself describing the semantic layer as a copy, rewrite the sentence.

## The decision rules to walk away with

Use a Data 360 report for one object and a defined grain. Use a Lightning dashboard to combine several reports or blend Data 360 and CRM data for an audience that works inside Lightning. Choose Tableau Next when the requirement is governed metrics shared across Salesforce, richer visualization, or conversational analysis. Build the report first, build the semantic model before the governed visualization, and always name the reason for the surface you pick.

Before you call a dashboard done, confirm two things: the underlying object is populated, and every recipient can see it. Sharing a dashboard does not grant access, a semantic model is metadata and not a copy, and the same numbers should travel from the report to the semantic layer to the Tableau Next dashboard without being redefined along the way. Get those right and the blank tile never reaches the stakeholder.
