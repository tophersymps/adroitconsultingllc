# Lesson 6: Choosing a First Use Case: Sales, Service, Analytics, and Advertising Patterns

A steering committee loves the boldest idea on the whiteboard: unify every source across the enterprise, then build a personalization engine. Six months later, not one thing has shipped. The integration work is real, the credit spend is real, and there is no number to show the executive who signed the check, so sponsorship quietly evaporates. The program did not fail because the technology was wrong. It failed because the first use case was chosen for ambition instead of for provable value on data that was already reachable.

The requirement behind this lesson is sp-3b: "Identify initial use cases for Data 360, covering how to choose a first use case across sales, service, analytics, and advertising and how to sequence a low-risk start." It sits in the Solution Positioning domain, which is 14% of the Salesforce Certified Data 360 Consultant exam. Where sp-3a named the starting patterns, sp-3b tests judgment: given several candidates, which one should go first, and why.

This lesson gives you the four use case families across the business, the scoring test that picks between them, the sequencing rule that keeps a program alive, and the cost and governance realities that shape what is actually feasible. Choosing a first use case is a consulting decision, and the exam is checking whether you can make it the way a real consultant does.

## Deep Dive

### Choosing a first use case is a consulting judgment, not a technical one

The best first use case has three properties: clear business value, data that is already connected or easily connected, and a measurable KPI so success is provable. Read that list as a filter. Value without data cannot ship, data without value does not get funded, and value without a KPI cannot be proven, which means it cannot unlock the next phase. The combination that indicates the most sensible starting point is a use case with clear business value, data already connected, and a measurable KPI. When those three line up, the first deliverable is reachable and its success is legible to the people who fund the program.

The failure mode is starting with the hardest ideation before any data is in place. That choice usually stalls, because nothing ships and the program loses sponsorship before it has produced a single result. The discipline is to start where the data exists and the outcome is quantifiable, produce a quick win that funds the next phase, and let the demonstrated result, not the roadmap slide, carry the argument for expansion. This is judgment, and it is the judgment the exam rewards.

The strongest distractor is always the "high value but no data connected yet" option, because it sounds strategic. It is not. It cannot ship, so it delays proof of value and puts sponsorship at risk. The most technically complex use case is wrong for the same reason dressed differently: complexity adds time before the first result, and a first use case exists to produce a first result. A use case that requires every source to be unified first is the version of "boil the ocean" that the next section rejects directly.

### Sales use cases center on revenue

Sales use cases put a score or an insight in front of a rep. Reps can see propensity to convert, predicted deal value, account health, and next best deal, and Data 360 can enrich records and related lists so the insight appears where the rep already works. A propensity score is only useful if it shows up next to the opportunity the rep is working, so the design decision is as much about placement as about modeling. Enrich the record, and the score becomes part of the daily workflow instead of a separate report nobody opens.

The KPI is what wins the funding. A sales leader cares about pipeline and win rate, so a sales use case should name the metric it moves, not the feature it uses. When several use cases compete for the same budget, the one tied to a number the executive already reports on is the one that gets funded, because it plugs into a conversation that is already happening. "We will lift win rate on renewal opportunities by surfacing a propensity score and a next best deal on the account" beats "we will deploy predictive AI" every time.

A sales-focused first use case is usually strong on value and, if the CRM data is already connected, strong on readiness. That combination makes sales patterns a frequent starting point. The risk to watch is scope: a "single view of the rep's world" can quietly expand into every object in the org. Keep the first slice narrow, tied to one metric, and proven before widening it.

### Service use cases center on retention and effort

Service use cases aim at the cost of support and the risk of churn. Unified case history across channels, churn or dissatisfaction risk scores, and proactive outreach before a customer complains all reduce contacts and improve satisfaction. The shift the platform enables is from reactive ticket handling to proactive enablement, and it shows up in the numbers service leaders already track.

A clean example is a calculated insight that combines contractual entitlement with product usage to flag an adoption gap. The customer is paying for a capability they are not using, which is a churn signal well before the customer says anything. That insight can trigger a proactive outreach or a coaching task for the account team, and it turns a static account record into a retention action. The point is that the signal comes from combining data no single system holds alone.

The service KPI is usually cost per contact, first contact resolution, or retention. All three are measured in money or in churn, so a service use case lands in the funding conversation easily. The one caution is channel sprawl: a service use case that tries to unify every channel history at once can balloon the scope. Start with the channel that carries the most contacts and the clearest churn signal, prove the reduction, then bring in the rest.

### Analytics use cases make unified data visible to analysts

Analytics use cases expose the unified data to the people who model and report on it. Data 360 data can be connected to business intelligence tools such as Tableau so analysts explore unified profiles and build dashboards on trustworthy data. Tableau reaches Data 360 through connectors that use the Hyper query engine for fast processing, so analysts can explore the data in near real time, and the standard Data 360 objects and relationships are viewable in Tableau directly.[^1] This is why an analytics use case is served by connecting Data 360 data to a business intelligence tool such as Tableau.

Analytics is often the least disruptive first use case because it does not change any user's workflow. It just gives analysts a better source. No rep has to learn a new screen, no journey has to be rewired, and the risk of breaking a customer-facing process is near zero. That low blast radius is exactly what makes it a safe start when an organization wants to see value before it commits to a personalization or activation build.

There is a second benefit that consultants should not undersell. An analyst who trusts the numbers becomes an advocate for the platform. When the analyst who once distrusted the CRM's data quality starts reporting from unified Data 360 profiles, the platform earns credibility with the most skeptical audience in the building. Validating the unified profile through analytics is therefore both a use case and an adoption strategy.

### Advertising use cases exploit cleaner audiences

Advertising use cases take the unified profile to paid media. A segment built on a unified profile can be activated to ad platforms to reach the right people, scale a lookalike audience, or suppress customers who already converted or opted out. The pattern is well documented: a marketing team builds a segment of its best customers, activates it to a platform such as Meta or Google Ads, and uses lookalike modeling to find new audiences similar to the seed.[^2] Because the audience is built from reconciled identity rather than a single system's view, overlap waste drops and frequency is controlled more tightly.

Suppression is the half of advertising that candidates forget. An advertiser can exclude customers from seeing an ad, which saves money and avoids unwanted messages, and a common example is suppressing customers with open service cases so an irritated customer is not shown more advertising while a problem is unresolved.[^2] That suppression logic only works if the open-case signal and the advertising audience sit on the same unified profile, which is the whole point of the platform. The cleaner the identity, the sharper both the targeting and the exclusion.

The advertising KPI is usually return on ad spend or cost per acquisition, and the value story is sharper targeting at lower spend. One realistic caution: advertising runs on a consent boundary. An advertising use case has to honor consent flags, and it depends on identity resolution just like every audience pattern. Get the governance right and advertising is a powerful first use case; skip it and the cleanest audience in the world is unusable.

### The sequencing principle: prove one journey, then scale

All four families obey one sequencing rule. Prove one journey, then scale. Pick a single use case that crosses the connect, harmonize, and activate stages, deliver it, measure it, and then reuse the same unified data for the next use case. The unified data is the compounding asset: the second use case should be cheaper and faster than the first because the profiles already exist.

The mistake the exam warns about is trying to unify every enterprise source before delivering the first use case. That approach delays time to value and consumes credits without a proven outcome, and it is a mistake for a practical reason, not a technical one. Unification scales, and multi-brand unification is possible through data spaces, so the objection that some sources "cannot" be unified is the wrong reason. The right reason to avoid boiling the ocean is that one well-chosen journey would have proven the platform sooner and for less.

Governance and cost are part of the plan from day one, because they shape what is feasible. Consent, masking, and credit consumption are not afterthoughts; they determine whether a use case can run and what it costs to run. Data 360 consumption is metered, with usage types such as unification, segmentation, activation, inferences, and queries each decrementing credits, monitored in the org's Digital Wallet, and some usage, such as the internal pipeline for structured Salesforce data, is included rather than metered.[^3][^4] A consultant who can name a first use case, its KPI, its data readiness, and its rough cost is answering the real question the business is asking. That combination of a provable outcome on data the company already has is what turns a platform purchase into a funded program that keeps earning budget for the next phase.

## Config Walkthrough

Pick and deliver a first use case in five steps.

1. Run a short workshop to list candidate use cases across sales, service, marketing, analytics, and advertising, and capture the KPI each would move. Force every candidate to state a number; a candidate that cannot name a metric is not ready to be first.

2. Score each candidate on business value, data readiness, and time to deliver, then pick the one that wins on value with the lowest data risk. This is the scoring test that keeps the program on the rails, because it makes the trade-off explicit instead of political.

3. Confirm the unified entity and source streams are in place, and identify any governance steps such as consent or masking the use case requires. If the unifying entity is not unified, nothing downstream can run, so this step gates the whole plan.

4. Estimate credit consumption for the dominant usage types so the value case includes cost, not just benefit. A use case whose credits dwarf its benefit is not a first use case, no matter how appealing it looks.

5. Deliver the single use case, measure the KPI, and reuse the same unified data to plan the next use case on the roadmap. The measured result is what funds phase two, so instrument the KPI before you ship, not after.

## Exam Traps

Three traps dominate this objective.

First, choosing a use case with high value but no data connected yet. Without the data in place it cannot ship, so it delays proof of value and puts sponsorship at risk. The trap is tempting because the value story is compelling, but a first use case that cannot ship is not a first use case at all.

Second, trying to unify every enterprise source before delivering the first use case. Beyond being slow and politically exhausting, it delays time to value and consumes credits without a proven outcome, when a single well-chosen journey would have proven the platform. Unification does scale and multi-brand unification is possible through data spaces, so the "we must do it all at once" instinct is not a technical necessity; it is a scope error.

Third, framing value in features instead of business outcomes. Naming capabilities rather than the KPI they move is what loses the funding conversation. "We will use calculated insights and activations" is a feature list. "We will cut cost per contact by surfacing an adoption-gap insight before the customer calls" is a business outcome, and it is the one that gets approved.

## Decision rules to carry into the exam

When several use cases compete, rank them on value, data readiness, and time to deliver, and start with the one that wins on value while carrying the least data risk. Map the business situation to the family: revenue and rep decisions are sales, cost per contact and retention are service, analyst exploration and dashboards on trusted data are analytics, and cleaner, suppressed audiences for paid media are advertising. Then apply the sequencing rule, prove one journey and scale, and keep governance and cost in the plan from the start. Hold those rules and this objective is a matter of matching the scenario to the pattern and naming the KPI it moves.
