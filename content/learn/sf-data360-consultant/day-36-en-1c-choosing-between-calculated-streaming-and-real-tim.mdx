# Lesson 36: Choosing Between Calculated, Streaming, and Real-Time Insights, Data Actions, and Enrichments

A consultant reads four requirements on one call and reaches for one feature to solve all of them. The team wants a nightly lifetime value score, an alert to a webhook when a customer abandons a cart, a lifetime value number on the service rep's contact page, and a personalized offer the moment a shopper looks at a product. The consultant builds four calculated insights, because that is the calculator they know best. Three of the four fail. The nightly score works. The webhook never fires, the record page shows nothing, and the offer arrives too late to matter.

The problem was never the math. The consultant reached for a compute feature to satisfy an act requirement and a show requirement, and used a batch calculator where the scenario demanded per event timing. Requirement en-1c, in the Data Enhancements, Sharing, and Analysis domain worth 18% of the Salesforce Data 360 Consultant exam, asks you to demonstrate how to enhance data and build insights on unified data, focused on selecting the right insight type for a requirement and distinguishing that compute step from data actions, which act on data, and enrichments, which display it in other systems. This lesson gives you the sorting rule and the mechanics behind each choice.

## Deep Dive

### Start with the data available and the freshness required

The decision starts with the data available and the freshness required, not with the feature you happen to like. Each insight type assumes a different source and a different latency, and matching the requirement to that profile is most of the answer.

Calculated insights need large historical stored data and run in batches, so they suit complex math over a body of records. Streaming insights need engagement events arriving on a stream over a rolling window, so they suit near real time reactions to recent activity. Real-time insights need a real-time data graph and answer in milliseconds per event, so they suit live personalization where the current action drives the response.[^6]

The tell is in the scenario language. If it says stored records and complex historical math, it is calculated. If it says near real time, Web or Mobile SDK events, and a time window, it is streaming. If it says milliseconds, a real-time data graph, and website personalization, it is real-time. Read the scenario for the data shape and the freshness, and the choice follows.

Run the four requirements from the opening through the test. The nightly lifetime value score wants stored history and complex math, so it is calculated. Cart abandonment alerting wants an engagement event acted on within minutes, so the trigger is a streaming insight feeding a data action. The number on the contact page is a value this person owns, so it is a copy field enrichment, and it is a show requirement, not a compute one. The live offer depends on the current page event and has to land in milliseconds, so it is a real-time insight inside a real-time data graph. Four requirements, three feature families, and one of them is not a calculator at all.

The freshness tiers also mix legitimately. A calculated insight can produce a durable score that a real-time insight reads as context, and a streaming insight can watch for the moment while a data action responds. Freshness is not a single setting you choose once for a solution. It is a property of each requirement, and a well built design matches each feature to the tier its own requirement demands.

### A Data Action is how Data 360 acts on a signal

A Data Action is how Data 360 acts on a signal rather than only displaying it. You define a data action in Data 360 and send its payload to a data action target. A data action sends a payload to a target such as a Marketing Cloud Engagement data extension, the core platform, or a webhook, and the supported targets also include Salesforce Platform Events and Amazon Kinesis.[^1]

A data action can be enriched with a related object, either a DMO or a data graph mapped to an external DLO, and that related object must have a many-to-one or one-to-one relationship with the primary object. When you use a DMO as the related object you can add up to ten related attributes. When you use a data graph, the entire payload goes to the target rather than individually selected attributes.[^2]

The targets are worth memorizing because the exam names them directly. A data action can send its payload to a Marketing Cloud Engagement data extension, to the core platform as a platform event, to a webhook, or to Amazon Kinesis. A webhook target needs a Salesforce generated secret key, because without a key the target receives no payload and the call is marked with a signing key failure. Knowing which target a scenario names is often the difference between two plausible answers.

The rules are the other half of the mechanics. You select an event rule to react to record changes, and an action rule to evaluate when the action should fire, and the action rule can combine conditions with AND and OR. An insight that identifies the moment is the trigger; the data action is the response. That is the division of labor: the insight computes, and the action reacts. A data action never edits the unified profile in place, and it does not replace identity resolution.

### Enrichments are how Data 360 data appears in Salesforce components

Enrichments are how Data 360 data appears in Salesforce components, and there are three types. They differ by the relationship between the data and the Salesforce record, so the relationship is what you match, not the look you want.

A related list enrichment shows DMO objects with a one-to-many relationship to an Individual or a Unified Individual. A contact can have many email engagements, and the related list shows them all across the enterprise. A direct-DMO related list uses a direct relationship between a DMO and a Salesforce object, and it does not require identity resolution for that DMO, so it fits a system to system link that never went through unification.[^4] A copy field enrichment copies field data from an object with a one-to-one relationship to a Data 360 Individual, Unified Individual, Data 360 Account, or Unified Account DMO.[^3]

The three types are not interchangeable, and each carries a relationship precondition. A related list needs a one-to-many link to a unified individual or individual, which is why an engagement history fits. A direct-DMO related list skips identity resolution entirely, which is why it suits an object that was never unified, such as a telematics event tied to a vehicle. A copy field needs a one-to-one link to a unified individual or account, which is why a single lifetime value fits but a list of orders does not.

Enrichments are configured in Setup and added to page layouts. You open the object management settings for the target object and select the Data 360 related lists or copy fields option to create the enrichment, then place it on the page. The relationship requirement is hard: a copy field needs the one-to-one unified link, and a related list needs the one-to-many relationship to the unified individual.

### Choosing among them follows the relationship and the readiness of unification

Choosing among the three follows the relationship and the readiness of unification, and the wording of the scenario points to the answer. For broad context on a record page, a related list enrichment shows the many engagements. For a direct system to system link that never went through unification, a direct-DMO related list fits. For surfacing a single computed value on the record, the right answer is a copy field enrichment, because it copies a one-to-one value into a field.

The cardinality test settles most questions. If the requirement is a list of many related things, it is a related list. If the requirement is one number that belongs to one person, it is a copy field. The unification test settles the rest. A copy field needs a one-to-one relationship to a unified Individual or Account DMO, while a related list needs the one-to-many relationship to the unified individual. If identity resolution has not run for a DMO, the direct-DMO related list is the one that does not require it.

### A common design chains the three

A common design chains the three features in one flow. A streaming insight aggregates recent engagement into a window, then a data action fires to a webhook or a data extension when a threshold is met. Separately, a copy field enrichment places a calculated insight value on the Contact page for a rep. The insight computes, the action reacts, and the enrichment displays.

Think of the chain as a pipeline with three verbs. The insight computes a fact, the action reacts to that fact, and the enrichment shows the fact to a human. A well designed solution can use all three at once without confusing them, because each answers a different question. A solution that tries to make one feature do all three jobs is the one that fails in production, exactly as it did in the opening scenario.

The reason this is worth naming is that the three sound similar and sit at different points. Compute selects the insight type. Act selects a data action. Show selects the enrichment type. Confusing the three is a frequent exam trap, so name the verb the scenario asks for before you name the feature. A scenario that says show a rep a number is a show requirement, not a compute one, and no insight type can satisfy it.

### Enrichments, actions, and insights consume credits and need permissions

Enrichments, the queries behind them, and the insights all consume Data 360 credits, so the number of related lists and copy fields and the frequency of action triggers are design decisions rather than free add-ons. Adding a related list to every record page and firing an action on every change is a design choice with a bill attached, and the exam expects you to treat it as one.

Access is the other half. A related list enrichment is visible only to users whose permission set grants access to the data space it reads, so the permission set is part of the design. An enrichment grants no access by itself. Always pair a recommendation with the access requirement, because an answer that ignores who can see the enrichment, or what it costs, is incomplete.

Access and cost are the two things consultants forget under time pressure. The enrichment reads a data space, and only users whose permission set maps that space can see the enriched data, so shipping the enrichment without the permission set produces a locked door. The cost is the other half: every related list and copy field queries Data 360, and every action trigger publishes a payload, so a design that adds enrichments and triggers without a cost check is an incomplete design no matter how clean the data model is.

## Config Walkthrough

Choosing and wiring the right feature is a short sequence once the verbs are sorted.

1. Decide the insight type by freshness. Calculated Insight for batch on stored data, Streaming Insight for a near real time engagement window, Real-Time Insight for per event answers inside a real-time data graph.
2. To act on a signal, create a Data Action in Data 360, choose the primary object, optionally add a related object, a DMO or a data graph mapped to an external DLO with a many-to-one or one-to-one relationship, and set the data action target.
3. To display Data 360 data on a record page, choose the enrichment type. A related list for one-to-many DMO data, a direct-DMO related list for a direct relationship that needs no identity resolution, or a copy field for a one-to-one unified value.
4. In Setup, open the object management settings for the target object, for example Contact, Lead, or Account, and select Data 360 Related Lists or Data 360 Copy Fields to create the enrichment.
5. Confirm the acting user has a permission set that grants access to the data space, then add the enrichment to the page layout and verify it renders on the record. For a data action, verify the target receives events and that a webhook target has a secret key generated, because a webhook target without a key receives no payload.[^5]

## Try it

Take a requirement verb and test it against the three feature families. If the requirement says calculate, decide the insight type by freshness and stop there. If it says alert, notify, or trigger, design a data action with a primary object, a target, and a rule. If it says display, show, or surface, pick the enrichment by relationship: one-to-many for a related list, a direct relationship for a direct-DMO related list, and one-to-one for a copy field. Write the verb beside each requirement before you pick anything, and the feature choice almost chooses itself.

## Exam Traps

Three traps dominate this objective.

First, choosing calculated insights for a real time need. Calculated insights run in batches and can lag, so they cannot answer a millisecond personalization scenario, which requires a Real-Time Insight inside a real-time data graph. When the scenario says milliseconds and a data graph, a batch calculator is the wrong tool.

Second, treating a copy field enrichment as usable for any relationship. Copy fields need a one-to-one relationship to a unified Individual or Account DMO, while a one-to-many relationship is served by a related list enrichment. If the requirement is a list of many rows, a copy field cannot produce it, and if the requirement is a single value, a related list is not the fit.

Third, forgetting that an enrichment grants no access by itself. Its data is visible only to users whose permission set maps the data space, so the permission set is part of the design, not an afterthought. An answer that stops at creating the enrichment and ignores who can see it is incomplete.

## Decision rules to carry forward

Sort every choice by verb. Compute selects the insight type, act selects a data action, and show selects the enrichment type, then match the freshness tier the scenario demands. For the insight type, read the data and the latency: batch on stored records is calculated, a rolling engagement window is streaming, and per event answers in a data graph are real-time. For actions, remember the payload goes to a target such as a data extension, the core platform, or a webhook, with a many-to-one or one-to-one related object. For enrichments, match the cardinality and the unification state, and always name the permission set and the credit impact alongside the recommendation.

Distractors in this domain usually swap the verb, not the noun. A copy field enrichment appears as an answer for a compute requirement, or a calculated insight appears as an answer for a millisecond requirement. Reading the verb first neutralizes both, because a show answer cannot satisfy a compute requirement no matter how well it displays, and a batch answer cannot satisfy a real-time requirement no matter how good the math is.
