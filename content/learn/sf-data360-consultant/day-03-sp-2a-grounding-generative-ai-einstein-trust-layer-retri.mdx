# Lesson 3: Grounding Generative AI: Einstein Trust Layer, Retrieval Augmented Generation, and Unstructured Data

A team ships an AI assistant that confidently invents a refund policy that does not exist. The model is not broken. It simply had no idea what the company's policy was, because nobody gave it the company's documents, and a large language model will fill a gap with something that sounds plausible. The fix is not a smarter model. The fix is grounding: putting the right, current, trustworthy data in front of the model at the moment it answers.

Grounding is where Data 360 earns its place in an AI conversation, and it is the subject of requirement sp-2a, part of the Solution Positioning domain worth 14% of the Salesforce Certified Data 360 Consultant exam. The requirement asks you to articulate Data 360's foundational role in generative and predictive AI, covering how Data 360 grounds generative AI through the Einstein Trust Layer and retrieval augmented generation over structured and unstructured data. This lesson covers the trust architecture, the retrieval mechanism, and the unstructured data pipeline that feeds both.

## Deep Dive

### Generative AI depends on trusted, current data, and Data 360 supplies it

A large language model only knows the general knowledge it was trained on. To answer a question about a specific customer, account, or policy, it must be grounded in the organization's own data, because without that context it can only guess from statistical patterns. Data 360 consolidates disparate sources into unified profiles and insights, and that consolidated data becomes the grounding context, so answers reflect what is actually true in the business rather than what is merely common on the internet.

That is why accurate answers on the first try depend on the data layer. A model trained a year ago does not know that a customer upgraded their plan last week. A unified profile does. When you map a question to its answer, you are really mapping it to the data that holds the answer, and the quality of the grounding data sets the ceiling on the quality of the response. The practical consequence for a consultant is that an AI project that skips the data work will ship a confident guesser, and the failure will look like a model problem when it is a data problem.

### The Einstein Trust Layer governs how the data is used

The Einstein Trust Layer is the secure AI architecture built into the Salesforce platform, a set of agreements, security technology, and data and privacy controls.[^1] It is what lets an organization use generative AI without surrendering control of its data. Two of its guarantees matter most for the exam.

The first is the zero data retention policy. Under it, your data is not retained by third party large language models, and no data is used for model training or product improvements by those third party LLMs.[^1] The answer to any question about whether a third party model learns from your prompts is the phrase the exam is fishing for: zero data retention. Prompt defense, which limits harmful or injected outputs, is a different guarantee, and it does not govern retention, which is exactly why it is the strongest wrong answer on a retention question.

The second is dynamic grounding with secure data retrieval. Relevant information from a Salesforce record is merged with the prompt to provide context, and that retrieval is based on the permissions of the user executing the prompt. The precise sentence to remember is that secure data retrieval merges grounding data while preserving the running user's permissions and field-level security, and it does so for data from your CRM instance or Data 360.[^1] Grounding is dynamic because it happens at run time and depends on who is asking, which is what keeps a generative feature from becoming a permissions bypass.

The Trust Layer rounds out with data masking, which detects and masks sensitive information such as personally identifiable information before a prompt reaches an external model, prompt defense, which uses system policies to limit hallucinations and reduce the likelihood of unintended or harmful outputs, and toxicity scoring.[^1] All of these signals land in an audit trail: prompts, responses, and trust signals are logged and stored in Data 360, which is what makes the platform part of the trust story rather than just the data story.[^1]

![Einstein Trust Layer controls mapped to the boundary where each one acts: data masking and prompt defense before the prompt reaches an external model, dynamic grounding with secure data retrieval that preserves the running user's permissions and field-level security, zero data retention at the third party model, and an audit trail stored in Data 360](</diagrams/day-03-sp-2a-grounding-generative-ai-einstein-trust-layer-retri/1-trust-layer-controls.png>)

The trust guarantees are not automatic just because the platform offers them. A consultant configuring a generative feature has to set up the Trust Layer to match the organization's privacy and security policies, and the audit trail has to be turned on so that prompts, responses, and trust signals are actually captured. Once the audit data is flowing, the Einstein Generative AI audit and feedback data supports pre built reports and dashboards, which turns a security requirement into something an admin can monitor rather than assume. If a client asks how they would know whether an agent is grounding on the right data or drifting toward toxic output, the answer is the audit trail and the toxicity scoring that feeds it.

### Retrieval augmented generation makes unstructured knowledge usable

Retrieval augmented generation, or RAG, is the mechanism that turns a pile of documents into something a model can answer from. In Data 360, RAG is a framework for grounding LLM prompts, and it works in a fixed sequence: it retrieves relevant information from structured and unstructured data indexed in the vector database, augments the prompt by combining that information with the original prompt, and generates a response.[^2] The order matters, because the retrieval happens before generation, not after.

The pipeline that makes RAG possible runs in two parts. Offline preparation connects the unstructured data, creates a search index configuration that chunks and vectorizes the content, and stores and manages the search index in Data 360. Chunking breaks the text into smaller, semantically meaningful units, and vectorization converts those chunks into numeric representations that capture semantic similarity. Retrievers then act as the bridge between search indexes and prompt templates, refining the search criteria and pulling the most relevant information to augment a prompt. Online usage is the reverse path: the retriever is invoked with a dynamic query, the query is vectorized, the relevant context is retrieved from the vector database, the prompt is populated with that context, and the LLM generates the response.[^2]

![Retrieval augmented generation in two phases: offline preparation connects the unstructured data and chunks and vectorizes it into a search index stored in Data 360, a retriever bridges that index to prompt templates, and online usage vectorizes a dynamic query, retrieves the relevant context from the vector database, populates the prompt and generates the response](</diagrams/day-03-sp-2a-grounding-generative-ai-einstein-trust-layer-retri/2-rag-two-phases.png>)

One more reason retrieval augmented generation fits enterprise knowledge is that it avoids retraining. Many large language models were trained generally across the internet on older content, and fine tuning a model on proprietary data is slow, costly, and hard to keep current. With RAG, a prompt template can hand the model the most accurate, up to date information at query time and bring proprietary data to the LLM without retraining or fine tuning the model. That is why a team can ship a grounded assistant in weeks rather than months, and why the answer improves the moment the underlying documents are updated rather than when someone retrains a model.

The exam phrase to keep ready is retrieval augmented generation over a vector database, because that is how unstructured files are made retrievable at prompt time. A team that wants an AI agent to answer questions from internal PDFs and support transcripts feeds those files through chunking and vectorization into the vector database, and the retriever grounds the agent's prompts from there. Calculated insights compute metrics from structured data and do not index documents, and segment activation moves records to a destination, so neither one makes a PDF retrievable.

### Unstructured data follows the same arc as structured data, with different steps

Unstructured data such as PDFs, audio, chat transcripts, and text runs through the same five step arc as structured data, but the middle steps do different work. The arc is Connect, Process, Store, Index, and Activate.[^3]

Connect ingests the unstructured data using prebuilt connectors, including Amazon S3, Azure, and Google Cloud Storage. Process unpacks the data with chunking and transcribing strategies, extracts metadata such as entities, keywords, summaries, questions, and topics, and categorizes the content. Store vectorizes the processed data, converting it into a numerical representation, and stores it in a vector database. Index creates keyword and knowledge graph indexes for retrieval that goes beyond simple text matching. Activate makes the data available for Agentforce, analytics, Apex code, automations, Customer 360, and search through no code retrievers, hybrid search, and retrieval augmented generation, so that AI answers are grounded in the business's own trusted information.[^3]

![The unstructured data arc in five steps: Connect ingests files with prebuilt connectors such as Amazon S3, Azure and Google Cloud Storage and brings knowledge articles through the CRM connector, Process chunks and transcribes and extracts metadata, Store vectorizes into a vector database, Index builds keyword and knowledge graph indexes where hybrid search merges semantic and lexical matches, and Activate delivers the data to Agentforce, analytics, Apex code, automations, Customer 360 and search](</diagrams/day-03-sp-2a-grounding-generative-ai-einstein-trust-layer-retri/3-unstructured-data-arc.png>)

Data 360 ships connectors built for ingesting unstructured data from third party applications and sources such as Amazon S3, Azure, Google Drive, and Microsoft SharePoint, and it can ingest knowledge article data from Salesforce records through the CRM connector.[^5] Indexing deserves a closer look because it is where retrieval quality is won or lost. Data 360 supports a vector search index and a hybrid search index. Vector search understands semantic similarity, but it can miss specific domain vocabulary and exact tokens such as a product number, while keyword search excels at lexical similarity but not at meaning. Hybrid search combines both, querying the vector index for semantic matches and the keyword index for lexical matches, then merging and ranking the results.[^4] For a customer facing assistant that must find a specific order number and understand a paraphrased question, hybrid search is usually the right index, and the retrieved chunks are what ground the response.

### Data 360 is what makes Agentforce and other AI experiences reliable

Agents need real time, all source context to be useful, and grounding and governance have to travel together. Agents use retrieval augmented generation and hybrid search over Data 360 data to answer questions, resolve issues, and automate tasks. Unified profiles give an agent the full view of who it is talking to, and secure retrieval keeps role based and field level controls intact, so an agent never sees more than the person it acts for.[^3] This is the point that separates a working agent from a liability, because an agent that ignores field level security is a data leak with a friendly voice.

Grounding structured data matters too. A prompt template can merge fields from CRM records, flows, Apex, Data 360 DMOs, and related lists, so an agent can speak to a specific case, order, or profile rather than to customers in general. The same secure retrieval rules apply to that merge: it is based on the running user's access, so an agent acting for a service rep sees exactly what that rep is allowed to see. Combine a unified profile with secure retrieval and the agent gets both breadth and a permissions boundary, which is precisely the combination the requirement is describing.

The walkthrough for a grounded assistant, whether you are configuring a trial or reviewing a client build, follows the unstructured path end to end.

1. Confirm the unstructured data ingestion path: identify the source connector, such as an object store, and connect it to the intended data space.
2. In the unstructured data setup, choose chunking and transcription strategies, and configure metadata extraction for entities, keywords, summaries, and topics.
3. Verify that the processed content is vectorized into a vector database and that keyword and knowledge graph indexes are built.
4. Review the Einstein Trust Layer settings and the audit configuration in Setup, and confirm that prompts, responses, and trust signals are logged in Data 360.
5. Test a grounded prompt through an agent or prompt template, then open the audit trail to see the grounding, toxicity, and trust signals recorded for that interaction.

Step five is the one consultants skip and regret. If the audit trail does not show the grounding and trust signals for a test interaction, the feature is not actually running through the Trust Layer, and that gap will surface in a security review rather than in testing.

### Not every AI feature requires Data 360, but the demanding ones do

An honest positioning answer does not claim that Data 360 is required for every generative AI feature on the platform. Plenty of smaller features run without it. The capabilities that need fast, trusted answers grounded across all sources do require it, and those are the ones clients care about. Data 360 brings in all types of data, structured and unstructured; it processes and reacts to data in seconds for real time experiences; Zero Copy expands reach to data outside Salesforce without duplicating it; the Trust Layer keeps the whole thing trusted; and multi model support lets a team choose a model, build one, or bring its own. Taken together, that combination is the case for Data 360 as the AI data foundation.

That framing is also the bridge to the next lesson. Grounding generative AI is one half of Data 360's AI story, and predictive AI is the other. The same unified profiles and calculated insights that ground a generative prompt are the training ground for models that anticipate what a customer will do next, and the exam treats both as part of the same foundational role.

## Exam Traps

Three traps dominate this objective, and each one is a wrong belief about how trust and data meet.

First, assuming a third party large language model trains on or retains your data. The Trust Layer enforces zero data retention, so any answer that says the model learns from your prompts is wrong. Prompt defense and toxicity detection are real, but neither is about retention.

Second, assuming grounding ignores security. Dynamic grounding uses secure data retrieval that preserves the running user's permissions and field-level security, so grounding never widens access. The classic wrong belief is that the model runs outside Salesforce and therefore cannot respect permissions, and the Trust Layer exists specifically to make that belief false.

Third, treating retrieval augmented generation as a separate product, or assuming Data 360 only handles structured data. RAG is a Data 360 capability, and the platform ingests unstructured data too. If an option tells you RAG is external to Data 360 or that only structured data can ground a prompt, it has misread the platform.

## What a consultant should walk away with

Lead with the data layer when you talk about AI, because accuracy on the first try depends on trusted, current data. When a client asks whether a third party model can see or keep their data, answer with zero data retention. When they ask whether grounding respects their security model, answer with secure data retrieval that merges grounding data while preserving the running user's permissions and field-level security. For unstructured knowledge bases, describe retrieval augmented generation over a vector database, and reach for hybrid search when the queries mix meaning with exact terms. And keep grounding and governance together: an agent grounded on unified profiles but blind to field level security is not a solution, it is a risk.
