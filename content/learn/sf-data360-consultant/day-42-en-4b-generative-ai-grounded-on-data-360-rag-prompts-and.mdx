# Lesson 42: Generative AI Grounded on Data 360: RAG, Prompts, and the Trust Layer

An agent answers a customer question with confident, fluent, and completely generic prose. It reads like a policy document, because it is: the language model is improvising from its general training, not from this company's warranty terms. The customer asked about this order and got an answer about orders in general. The fix is not a better model. It is grounding, which is the practice of putting the right context into the prompt so the answer is tied to your data rather than to the model's memory.

The requirement behind the lesson is en-4b, in the Data Enhancements, Sharing, and Analysis domain worth 18% of the Salesforce Data 360 Consultant exam. It asks you to apply the predictive and generative AI tooling capabilities of Data 360 to customer scenarios, focusing on retrieval and grounding, prompt and agent use cases, the trust layer, and the governance a customer expects before AI touches unified customer data. The exam wants the mechanics of grounding and the four answers a customer needs before customer data reaches a model.

This lesson covers what grounding is, how retrieval augmented generation works end to end, how a search index prepares content for retrieval, how Prompt Builder authors a reusable template with merge fields and retrievers, and how the Einstein Trust Layer governs the whole journey. The thread through it is the same one from the predictive lesson: nothing AI does is useful until it is wired into a process the customer actually runs.

## Deep Dive

### Grounding keeps the answer tied to the customer

Grounding is the practice of adding contextual, specific information to a prompt so the language model's output is more relevant and accurate. Generative AI in Data 360 grounds prompts on your own data, which is what keeps answers tied to the customer rather than to the model's general training. The pattern is retrieval augmented generation: retrieve relevant information, augment the prompt by combining that information with the original ask, then generate the response.

A consultant explains grounding as the reason the answer is about this customer, and secure data retrieval as the reason a user only ever grounds on data they are allowed to see. Those are two different sentences, and the exam keeps them apart. Grounding is a quality argument: without it, the model improvises. Secure data retrieval is a governance argument: with it, the model never sees data the executing user could not open themselves. Both are true at the same time, and a good design states both.

The mechanical definition of RAG is worth committing to memory because the quiz can test any step of it. RAG in Data 360 pulls relevant information from structured and unstructured data indexed in a vector database, augments the prompt by combining that information with the original prompt, and generates a response. It is helpful to think of it in two parts: offline preparation, where you index the content, and online usage, where a prompt retrieves from that index at run time.[^1]

### Retrieval runs against a search index

Retrieval runs against a search index. In Data 360 you connect the unstructured and structured content you want searchable, then create a search index configuration that chunks the data into semantically meaningful units and vectorizes those chunks into numeric embeddings. Chunks are held in chunk data model objects and the embeddings in index data model objects, and the search index is stored and managed in Data 360.[^6] Content can be ingested from a variety of sources and file types, including service replies, cases, RFP responses, knowledge articles, emails, and meeting notes.[^1]

The offline preparation is three steps. Connect your unstructured data. Create a search index configuration to chunk and vectorize the content, where chunking breaks text into smaller, semantically meaningful units and vectorization converts chunks into numeric representations that capture semantic similarity. Store and manage the search index in Data 360. Search indexes are defined in a data space and associated with a data model object, and Data 360 uses a vector data store for unstructured data such as documents and conversation histories.[^1][^2]

At run time the retriever does the work. The retriever is invoked with a dynamic query initiated from the prompt template. The query is vectorized, so search can find semantic matches rather than exact keyword matches. The query retrieves the relevant context from the vector database, the original prompt is populated with the information, and the prompt is submitted to the language model, which generates and returns the response.[^1] Retrievers serve as the bridge between search indexes and prompt templates, and you build them in AI Models (formerly Einstein Studio) and activate them so Prompt Builder users can use them.[^2]

The quiz tests the setup step directly, and the trap is the belief that the model already knows your documents. A team wants an agent to answer questions from internal documents and from customer data in Data 360, and the question asks what must be configured for the documents to be retrieved. The answer is Connect the content and create a search index that chunks and vectorizes it. Retrieval augmented generation pulls context from a search index, so the content must be connected and indexed into chunked, vectorized data before an agent can retrieve it. The model does not already know your documents, record fields alone do not index them, and the trust layer is not disabled for retrieval.

### Prompt Builder is where you author a reusable prompt template

Prompt Builder is where a consultant authors a reusable prompt template. You create a new prompt template, choose a prompt template type that matches the use case, and lay out the instructions and the grounding in the template workspace. Grounding uses merge fields, and those merge fields can source CRM record fields, values produced by a flow or Apex, Data 360 data model objects, and related lists. Because the template is reusable and can be invoked from a flow or from Apex, a generative step becomes part of an automated process rather than a one off prompt a user types.[^3]

The quiz tests the field-sourcing question, and its answer is the whole point of Prompt Builder. A prompt must include a value computed by an Apex process and an attribute from a Data 360 data model object, and the question asks which approach fits. The answer is Grounding with merge fields, which can source record fields, flow or Apex values, and Data 360 data model objects. When you write the template in the Prompt Template Workspace, you use the Insert Resource button to add merge fields that reference record fields, flows, Apex, Data 360 DMOs, and related lists. Hard coding the values is not grounding, Data 360 objects are supported, and vectorizing is part of building the search index, not something you do before every prompt run.[^3]

The three grounding sources each have a job. Record merge fields connect the template to standard or custom object fields, and at run time real values populate the field based on the records the user selects. Flow merge fields add complex logic and can reach unified Data 360 objects through a Get Records element, so a flow can branch on a decision and return different instructions. Apex merge fields return data from a SOQL query or an external API, which is how you generate well formatted JSON or do programmatic filtering. A template can mix all three, which is why it works for both a quick field generation prompt and a multi step agent action.

Retrievers are the other half of grounding. In the Prompt Template Workspace you add a retriever through the same resource picker, and the retriever pulls indexed knowledge into the prompt at run time. An individual retriever targets one search index and can apply filters to narrow the search, and you can also use an ensemble retriever, which runs several retrievers, combines and reranks their results, and returns the most relevant information. The design question for a consultant is which data answers the question, whether it is retrieved through a retriever or reached through a merge field, and which user's permissions govern the retrieval.

### The Einstein Trust Layer is the sequence of safeguards

The Einstein Trust Layer is the sequence of safeguards a prompt passes through. The first step is secure data retrieval: the prompt is grounded only with data the executing user has access to, and standard role based controls and field level security are preserved when grounding from CRM or Data 360, so grounding is dynamic and depends on the user's access at run time. Retrieval is based on the permissions of the user executing the prompt, and it preserves in place all standard Salesforce role based controls for user permissions and field level security when grounding data from your CRM instance.[^4]

The layer also applies toxicity scoring and logs prompts, responses, and trust signals as an audit trail stored in Data 360, with prebuilt reports and dashboards available to analyze them. The audit trail includes data about the Einstein Trust Layer features such as data masking and toxicity scores, and it is stored in Data 360. You use Data 360 reports to see how the trust layer protects sensitive data from exposure to an external model, and you can see both the masked prompt that was sent out and the full response that was served to the user. To access the data you turn on the Einstein generative AI data collection and storage and install the report package.[^5]

Customer data is not used to train the language model. Salesforce enforces a zero data retention policy with external model providers, so data sent to the model is not retained and is deleted after a response is sent back, and no data is used for model training or product improvements by third party models.[^4] That is the sentence a customer wants to hear, and it is grounded in a platform policy rather than a promise.

The quiz tests the trust layer directly, and its true statement is that Prompts are grounded only with data the executing user can access, and prompts, responses, and trust signals are logged as an audit trail in Data 360. Secure data retrieval grounds the prompt only with data the executing user can access, preserving role based controls and field level security, and the layer logs prompts, responses, and trust signals as an audit trail stored in Data 360. The wrong options invert the facts: customer data is not used to train the model, grounding is not permission-blind, and toxicity scoring does not replace access controls.

### The same grounding powers agents and conversational analytics

The same grounding powers agents and conversational analytics. Vector search on the search index is available to Prompt Builder, to AI agents, and to analytics surfaces, so an agent can answer a question with context pulled from Data 360 and the semantic layer rather than from the model's memory. In Tableau Next, natural language prompts are translated into semantic queries so the answer comes from governed metrics. The retrieval index and the semantic model are two different grounding sources, and a mature design uses each where it fits.

For a consultant the design question is consistent across both. Which data answers the question, whether it is indexed or reached through a merge field, and which user's permissions govern the retrieval. Answer those three and the generative feature is grounded and governed at the same time. Skip them and you get the fluent, generic answer from the opening.

### Governance: the four answers a customer expects

Before AI touches unified customer data, a customer expects named answers on four points. Where the data goes: grounding data is retrieved under the executing user's permissions, and customer data stays in Salesforce and is not used to train the model. What is logged: prompts, responses, and trust signals are recorded as an audit trail stored in Data 360. How bad output is caught: toxicity scoring runs as part of the trust layer. Who can see what: retrieval respects roles and field level security, so a user cannot ground on data they cannot access.

Deliver those four answers and the governance conversation is grounded, not reassuring. Grounded means each answer names a mechanism the customer can verify: permissions on retrieval, an audit trail in Data 360, toxicity scoring, and a zero data retention policy. Reassuring means nothing verifiable, and a customer who has been burned once will hear the difference.

The exam tip that falls out of this is simple. Answer any generative AI governance question with the trust layer's four points: permissions bound retrieval, no training on customer data, toxicity scoring, and an audit trail stored in Data 360. If a multiple choice option contradicts any of the four, it is wrong.

## Config Walkthrough

Ground a generative feature in six steps.

1. Confirm Einstein is enabled in Setup and that the org is connected to Data 360 before building any generative feature. The trust layer and the retrieval index both depend on Data 360 being provisioned.

2. In Data 360, connect the unstructured and structured content you want retrievable, then create a search index configuration that chunks and vectorizes the data. This is the offline preparation that makes content findable at run time.

3. In Setup, open Prompt Builder, click New Prompt Template, and choose a prompt template type for the use case. The type determines which merge fields and objects are available.

4. In the prompt template workspace, write the instructions and add grounding with merge fields, choosing CRM record fields, flow or Apex values, Data 360 data model objects, or related lists as appropriate. Add a retriever through the resource picker when the answer needs indexed knowledge.

5. Save the template and invoke it where the use case runs, from a flow or from Apex, so the generative step is part of the process. A template that only runs when a user types is not yet an automated feature.

6. Review the trust layer audit trail, which stores prompts, responses, and trust signals in Data 360, to confirm grounding, toxicity scoring, and access behavior. Turn on the generative AI data collection and storage and install the report package to read it.

## Exam Traps

Three traps dominate this objective.

The first trap is assuming the language model is trained on your data. Grounding supplies context at run time and customer data is not used to train the model, so answers are tied to retrieved data rather than learned from it. If a design relies on the model having memorized your content, it will fail the moment the content changes.

The second trap is believing grounding ignores permissions. Secure data retrieval grounds the prompt only with data the executing user can access, and it preserves role controls and field level security, so grounding depends on who runs the prompt. The same template can produce different answers for two users because the two users can see different data, and that is correct behavior.

The third trap is expecting raw content to be answerable without preparation. Retrieval uses a search index that chunks and vectorizes content, so unstructured data must be connected and indexed before an agent can retrieve it. Dropping a document somewhere in the org does not make it retrievable; the search index does.

## The decision rules to walk away with

Ground every generative feature on your own data, and remember that grounding is a run time operation: retrieve, augment, generate. Connect and index unstructured content into a search index before expecting an agent to retrieve it, and author reusable templates in Prompt Builder with merge fields that source record fields, flow or Apex values, Data 360 data model objects, and related lists. Invoke the template from a flow or Apex so the generative step lives inside a process.

Before AI touches unified customer data, deliver the trust layer's four points: permissions bound retrieval, no training on customer data, toxicity scoring, and an audit trail stored in Data 360. Grounding is why the answer is about this customer, secure data retrieval is why a user only grounds on data they can see, and the two together are what make a generative feature safe to ship.
