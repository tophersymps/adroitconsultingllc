# Lesson 9: Data 360 Standard Permission Sets and Permission Set Licenses

A newly onboarded analyst opens Salesforce on their first morning and cannot find Data 360 anywhere. Their manager swears the access was granted, and the admin confirms the permission set is assigned to the user record. The analyst can log in, can see their CRM objects, and can do their job in every other respect. Data 360 is simply missing from the menu. Nothing is broken. The org never had the entitlement that makes those features appear, and the permission set on the user record was granting access the org could not actually provide.

This is an administration problem, and it is where the certification expects precision. Requirement sa-1a sits in the Data 360 Setup and Administration domain, worth 13% of the Salesforce Certified Data 360 Consultant exam, and it asks you to configure Data 360 permissions, permission sets, and organization-wide settings, focused on assigning the standard Data 360 permission sets, understanding permission set licenses, and choosing between standard and cloned custom sets. Three moving parts, and the exam tests them together because in practice they fail together.

The rule that unlocks most of this domain is one sentence long. Access to Data 360 is granted through permission sets, not profiles, and the permission sets you can assign depend on the licenses your org holds. Hold those two halves apart and the rest is mechanical. Mix them up and you will chase a profile change that was never the answer.

## Deep Dive

### Access is granted through permission sets, not profiles

Access to Data 360 is granted through permission sets, not profiles. Every Salesforce user has one profile, and the profile controls tab visibility, page layouts, record types, and IP ranges, but a profile does not open Data 360.[^1] The lever is a Data 360 permission set combined with the matching license. The platform is explicit that emailing the profile approach is a dead end: unless a user holds the System Administrator profile, the profile alone will not open Data 360.[^1]

An org ships with a set of standard Data 360 permission sets, and the exact names depend on the license your org was contracted under. A Data Cloud license provides Data Cloud Architect, formerly known as Data Cloud Admin, Data Cloud Activation Manager, formerly known as Data Cloud Marketing Manager, Data Cloud Activation Specialist, formerly known as Data Cloud Marketing Specialist, and Data Cloud User.[^1] Notice the naming: the platform renamed the older marketing-flavored sets to activation-flavored ones, and the exam may use either the current name or the former name, so recognize both.

A Customer Data Platform licensed org instead sees a different family: Data Cloud Admin, Data Cloud Data Aware Specialist, Data Cloud Marketing Manager, and Data Cloud Marketing Specialist.[^2] Four sets, no Data Cloud User, no Data Cloud Architect. This difference matters because the license in the org determines which sets even exist to assign. If you are looking for Data Cloud Architect in an org that was provisioned under a Customer Data Platform license, it is not hiding in a filter. It is not there, because it ships with the other license.

A Customer Data Platform license provides Data Cloud Admin, Data Cloud Data Aware Specialist, Data Cloud Marketing Manager, and Data Cloud Marketing Specialist, with no Data Cloud User and no Data Cloud Architect.](</diagrams/day-09-sa-1a-data-360-standard-permission-sets-and-permission-s/1-license-families.png>)

You can combine a Data 360 permission set with other Salesforce permission sets for a user who needs additional access, and there is no conflict in doing so, because permission sets are additive.[^1] What the platform does not recommend is building a Data 360 permission set from scratch. Some Data 360 features cannot be accessed with permission sets created from a blank slate, because the feature metadata that a standard set exposes is not something you can reliably reassemble by hand. The supported pattern is to start from a standard set, and the next sections cover the two reasons why.

### Opening Data Cloud Setup requires the admin profile or the Architect set

To open Data Cloud Setup, a user needs the System Administrator profile or the Data Cloud Architect permission set.[^3] That single sentence answers a whole family of exam questions about who can reach the admin console, and it is why the analyst in the opening scenario, holding only Data Cloud User, sees no setup access at all.

Data Cloud Architect grants full access to every Data 360 feature, including Data Cloud Setup, mapping data to the data model, creating data streams, identity resolution rulesets, and insights.[^1] Its full-access list spans the entire platform surface: data spaces, data governance, data shares, data streams, data lake objects, data model objects, data transforms, data graphs, the query editor, identity resolution, insights, data actions and their targets, communication capping, segments, activations and their targets, AI models, the unstructured data hub, the search index, and the semantic layer. It is the set for the person who builds.

Data Cloud Architect also bundles the Customize Application system permission.[^1] That is the detail the exam loves, because Customize Application is a broad Salesforce Setup permission that lets a user customize the org's setup in ways far beyond Data 360. Handing an architect Data Cloud Architect as shipped is therefore handing them broad Setup reach as a side effect. Because of that, architects who should not touch general Setup usually clone the permission set and remove Customize Application before assigning it.[^1] The capability survives, the Setup reach does not.

The exam phrases this as a scenario about giving a developer every Data 360 capability while keeping them out of broad Setup changes, and the supported answer is to Clone Data Cloud Architect and remove the Customize Application permission before assigning. The tempting distractor is to assign Data Cloud Architect exactly as shipped, which delivers the capability and the broad Setup reach together. Assigning Data Cloud User instead grants no build capability at all, and creating a brand new permission set from scratch runs into the missing-feature problem described earlier. Cloning and trimming is the only option that keeps the power and drops the side effect.

### Data Cloud User is read-only

Data Cloud User is read-only, and understanding exactly how limited it is prevents a lot of misconfiguration. It grants full access to none of the Data 360 features and view-only access to nearly all of them: data spaces, data governance, data shares, data streams, DLOs, DMOs, data transforms, data graphs, the query editor, identity resolution, profile explorer, insights, data actions and their targets, communication capping, segments, activations and their targets, AI models, the unstructured data hub, the search index, and the semantic layer. And it grants no access to Data Cloud Setup.[^1]

That last line is the crux, and it is exactly what the exam tests. An admin assigns Data Cloud User to a business analyst, and the analyst reports they cannot open Data Cloud Setup. The reason is that Data Cloud User grants view-only access and no Data Cloud Setup access. The distractor that the analyst also needs the System Administrator profile is wrong, because the analyst was never meant to administrate, and the correct set for build work is Data Cloud Architect. The distractor that the permission set license expired overnight invents a mechanism that does not exist, and the claim that Data Cloud User requires Modify All Data is unrelated to how the set works.

Grant Data Cloud User when a person only needs to inspect data and profiles, and reserve the architect or activation sets for the people who actually build, map, and publish. The activation sets sit between the two extremes: Data Cloud Activation Manager can manage an overall segmentation strategy including activation targets and activations, and Data Cloud Activation Specialist can create segments, while neither grants Data Cloud Setup access.[^1] Match the set to the job rather than defaulting everyone to Architect, which both over-grants and hands out Customize Application by accident.

### Permission set licenses govern how many users can hold access

Permission set licenses govern how many users can hold Data 360 access and which entitlements are available. A Data Cloud permission set license is a separate allocation from the Salesforce user license, and the two are not the same thing.[^4] A user can hold a Salesforce user license and still lack the Data Cloud permission set license that makes Data 360 features available, which is precisely the situation in the opening scenario: the permission set was assigned, but the entitlement underneath it was never in place.

The practical mechanics are straightforward once you know where to look. A permission set carries a License field, and you check that field against the licenses the org actually holds. To assign a permission set license directly, you go to Setup, open Users, select the user, and edit the Permission Set License Assignments related list, or you open Company Information, scroll to the Permission Set Licenses section, and assign the license to multiple users at once.[^4] There is a documented cap on the number of Data Cloud permission set licenses an org can hold, so the assignment is a metered resource, not an infinite grant.

This is why the exam tip holds. If a permission set fails to assign, or features disappear for a user, check the license field on the permission set and the user's assigned licenses before changing anything else. Admins who treat a failed assignment as a broken permission set go spelunking through object permissions when the real problem is that the org has run out of permission set licenses or the set points at a license the user does not hold. Check the license first.

The confusion the exam targets is between a permission set license and a user license. They are different objects with different jobs. The user license determines the kind of access a user can have at all; the permission set license entitles users to access additional features not included in their assigned user license.[^4] When a question offers "nothing, access carries over with the license" as an answer to a lost-access scenario, it is betting on that confusion, and the bet is wrong.

### Clone standard sets rather than building from scratch

Salesforce does not recommend building a Data 360 permission set from scratch, because some features will not appear or work in a blank set.[^1] The supported pattern is to clone an existing standard Data 360 permission set and then add or trim object, field, and feature permissions. Cloning carries over the feature metadata that makes Data 360 features appear in the interface, which is the part a blank set cannot reproduce.

Weighing the clone against the standard set is a genuine design decision, not a formality, and the trade-off runs in both directions. Standard permission sets are refreshed with each release as new features become available, so a user on a standard set gets new capabilities automatically.[^1] A custom clone does not, because it is a frozen copy, so custom clones can quietly fall behind and leave users without access to newly shipped features. The platform is blunt about the consequence: using a custom permission set could result in users not having access to new features or functionality.[^1]

So the rule for a consultant is to prefer the standard set and clone only when you have a specific reason, such as the Customize Application trim from earlier. When you do clone, plan to review the clone against each release, because a clone that never gets maintained is a slow-motion access outage. The exam frames the "build from scratch" option as the wrong answer whenever it appears, because a blank custom set can be missing feature access that only cloned standard sets expose.

### Migrating between licenses is a permission set change, not an inheritance

When an org migrates from a Customer Data Platform license to a Data Cloud license, the permission sets tied to the old license stop granting Data 360 access. Access is not inherited automatically, so users who were fine on Friday can be locked out after the cutover, and the fix is to Assign the permission sets associated with the new Data Cloud license.[^5] The old sets are not corrupt and the users are not misconfigured. The license that made the old sets meaningful is simply gone.

The migration has a defined shape. Identify which Data Cloud permission sets are associated with the new license, optionally customize the standard sets or create custom sets from them, assign the new sets to users, and remove the sets granted by the old Customer Data Platform license.[^5] Doing that user by user is slow and error-prone, which is why the platform recommends User Access Policies for the population move.

User Access Policies let you grant the new sets and revoke the old ones for whole groups of users based on criteria you set. You enable User Access Policies and the Enhanced Interface for User Access Policies in User Management Settings, create a new policy, configure the criteria so the resource is Permission Set with an Equals operator on the current set's API name, and define the action as Grant with the new set's API name as the target. Then you apply the policy, optionally to a subset, and review the affected users under Recent User Access Changes.[^6] Repeat with a revoke action to remove the old sets. It is far safer and faster than editing each user record during a license cutover.

## Config Walkthrough

Five steps cover the common administration tasks for this objective.

1. In Data 360, open the Setup gear and select Data Cloud Setup. Under User Management, click Users. This is the entry point for both user access and permission set assignment.[^3]

2. Select a user or create one, open Permission Set Assignments, click Edit Assignments, select the standard Data 360 permission set, and click Add, then Save. Repeat for every user who needs Data 360 features.[^3]

3. To build a custom set, open Setup, search Permission Sets, clone an existing standard Data 360 permission set, and adjust feature, object, and field permissions rather than creating a blank set. This is the pattern that preserves feature access while letting you trim, for example, Customize Application.[^1]

4. To check entitlements, open the permission set and review its License field, then open the user record and confirm the assigned permission set licenses match the Data Cloud license in the org. When access is missing, this is the first place to look.[^4]

5. To migrate a population, enable User Access Policies in User Management Settings, create a policy that grants the new Data Cloud permission set and revokes the old one, then apply it and review the affected users under Recent User Access Changes.[^6]

## Exam Traps

Three traps dominate this objective.

First, assuming a profile grants Data 360 access. Profiles alone do not open Data 360 unless the user holds the System Administrator profile, so the real lever is a Data 360 permission set plus the matching permission set license. When a scenario describes a user who cannot see Data 360, the answer is almost never a profile change. It is a permission set or a permission set license.

Second, confusing a permission set license with a user license. A user can hold a Salesforce user license and still lack the Data Cloud permission set license that makes Data 360 features available, which is exactly why a set can appear assigned while the features stay invisible. When a set will not assign or a user loses features, check the License field on the set and the user's assigned licenses before touching anything else.

Third, building a Data 360 permission set from scratch. Blank custom sets can be missing feature access that only cloned standard sets expose, so creating a brand new set is usually the wrong answer. The supported pattern is to clone a standard set and adjust it, and when a scenario needs a capability boundary, the answer is to Clone Data Cloud Architect and remove the Customize Application permission before assigning rather than to invent a fresh set or to hand over the standard set unmodified.

## The decision rules to carry out

Walk away with four rules. Data 360 access comes from a permission set plus the matching license, never from a profile change. Match the standard set to the job: Data Cloud Architect for builders, the activation sets for marketers and segment creators, and Data Cloud User for read-only inspectors who do not need setup. Clone rather than build from scratch, and trim Customize Application when the role should not touch broad Setup. And when an org changes licenses, Assign the permission sets associated with the new Data Cloud license and use User Access Policies to make the move in bulk, because access is never inherited across a license cutover.
