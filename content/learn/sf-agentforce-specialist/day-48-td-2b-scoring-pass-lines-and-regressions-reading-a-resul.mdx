# Lesson 48: Scoring, Pass Lines, and Regressions: Reading a Result That Looks Ambiguous

A tester watched a case that had passed for six weeks turn red the morning of a release, panicked, rewrote the subagent instructions, and shipped a change that broke two cases which had been green. The original red was noise from a non-deterministic agent, and the rewrite was a real regression. The tester had read one cell, acted on it, and moved a working agent backward, all because a single failing square looked like a verdict.

A lone cell is a weak signal. A result becomes readable only when you hold the set still, read a column at a time, and compare a run against a baseline you recorded before you changed anything. A regression is not a case that failed; it is a case that moved from pass to fail between two runs of the same suite, and the difference between those two definitions is the whole skill this lesson teaches.

This lesson serves requirement td-2b, the same objective as day forty seven, "Explain how Testing Center evaluations work.", taken now from the side of reading results. It sits in the Testing, Deployment, and Maintenance domain at ten percent of the exam. By the end you can read the scale behind each scorer, work an ambiguous grid to a diagnosis, and turn a suite into a release gate that catches a regression instead of inventing one.

## Deep Dive

### Scoring depends on which scorer you read

Scoring depends on which scorer you are reading. The default agent evaluations are pass or fail: the subagent assertion scores 1 for the expected subagent and 0 for an unexpected one, and the action assertion scores 1 when all the expected actions occurred.[^1] Response quality is scored by the judge on a zero to five scale, and Testing Center treats 3 or higher as a pass.[^1] That pass line is set at 3 by default, and Salesforce's guidance is to add a custom scorer with your own prompt when the default bar does not match what you need.[^2] Read the scale rather than the tick: a 3 means the agent met the goal, a 5 means the reply was precise, complete, and aligned to the brand, and a 0 means it never addressed the intent.[^1]

The lesson in that scale is that passing and being good are different claims. A 3 clears the bar, and the band from 3 to 4 still covers partial clarity and completeness, so a green cell can hold a reply a reviewer would call thin. The default bar is a floor, not a target, and if your team wants a higher one you raise it with a custom scorer rather than by wishing the default meant more than it does.

The scales are worth keeping separate in your head because they fail differently. An assertion is a fact and cannot be half-right: the subagent matched or it did not. A judged score is a gradient and can sit anywhere, so it invites the question of how far above the line a reply sat and whether the line was set where your business needs it. Reading an assertion and a response score with the same eye is the first habit to break.

### One case can pass one column and fail another

Because a run applies several scorers to the same case, one case can pass one column and fail another in the same row. Routing correct and response poor. Response excellent and routed to the wrong subagent. That combination is the useful signal, not a row total, because each column answers a different question and a row that is half green is telling you exactly which half of the contract held. When you read the grid, read a column across the cases to find a pattern, then read a single row to understand one failure. Recurring failures in a column usually point at configuration, whether that is unclear subagent instructions, a knowledge gap, or a missing action, rather than one unlucky reply. A lone failure in an otherwise green column is a different kind of problem and deserves a retest before a rewrite.

A worked row shows the value of the split. Suppose a case shows a green subagent assertion, a green action assertion, a response score of 2, and a coherence of 2. The agent routed and acted exactly as written and handed the customer a raw JSON block instead of a sentence, which is a phrasing failure the coherence scorer named for you, not a routing failure. Read the row as a diagnosis and the four numbers collapse to one sentence: routing fine, words wrong.

### Ambiguous results are read in the detail panel

Ambiguous results are read in the detail panel. Select the cell and you get the full JSON output and the judge's reasoning behind the score, which is usually enough to see which half of the contract failed. Two patterns cover most of it. If the assertions pass and the quality scores are low, the agent routed and acted correctly and phrased the answer badly, so the fix belongs in the subagent instructions or the prompt. If the assertions fail and the response still reads well, the agent answered the wrong question confidently, which is a classification or action-selection problem rather than a wording problem. And when instruction adherence returns UNCERTAIN, the judge is saying it could not decide, which is an invitation to reread the instructions and tighten them rather than to record a pass.[^1]

The two patterns are the reason the panel is the first stop and not the last. Assertions green with quality low sends you to the prompt and the instructions. Assertions red with a clean reply sends you to classification and action selection. Acting on the second pattern as though it were the first is how a tester rewrites a good prompt to chase a routing problem the prompt never caused, and the result is two failures where there had been one.

### A regression is a case that moved, not a case that failed

A regression is a case that passed on the previous version of the agent and fails on the new one, and catching one depends on holding something still. Pick a suite, keep it, and treat it as your release gate. Run it against the agent as it stands and record the per-scorer result as a baseline before you change anything. Then make one change at a time, whether that is a subagent instruction, an action binding, a subagent boundary, the model, or the knowledge sources, and run the same suite again. Compare the two runs column by column. A case that moved from pass to fail names the behavior you broke, and the difference between the two runs is the evidence you hand to whoever owns the change.

The phrase that carries the concept is held suite. An unchanged set run against two versions of the agent is a controlled comparison, and a set you edit between runs is not, because you can no longer tell whether the difference came from the agent or from the cases. Hold the suite, and the suite becomes a measuring instrument instead of a moving target.

The baseline is the artifact that makes this possible, and it is cheap to produce. Before you touch the agent, run the suite and save the per-scorer result. The saved run is your reference point, and every later run is read against it rather than against your memory of how the agent used to behave. A team that skips the baseline is not running a regression test; it is running a fresh test and calling the surprises regressions.

### Three rules keep the comparison honest

Three rules keep that comparison honest. Do not change the test set and the agent in the same step, or you cannot attribute the difference to either. Agree the floor before the run, not after you have seen the scores: assertions are pass or fail, so a primary scenario should have no failures, and each quality scorer carries whatever bar your team accepted in advance. And remember that the agent is non-deterministic, so a single newly failing case can be noise. Salesforce's own remedy is to retest the failed utterance manually in Agentforce Builder and read the reasoning, which separates a real break from a run-to-run wobble.[^1]

The floor deserves one more thought, because it is a decision you make once and then live with. A primary scenario with an assertion failure is an unambiguous problem, and the floor for it is zero failures. A quality scorer is a range, so the floor is whatever number your team agreed as the release bar, and agreeing it in advance is what stops the bar from sliding to meet whatever the run happened to produce. Set the floor before the run, and the run becomes a pass or a fail rather than a negotiation.

### The action that follows a red cell, by scorer

The actions that follow a red cell are specific, and the scorer tells you which one applies. For a failed subagent assertion or action assertion, retest the utterance manually in Builder, read the plan and the reasoning, and then refine the instructions for the expected subagent and action while restricting the incorrect one.[^1] For a low completeness or coherence score, look first at the expected response you wrote and at the knowledge the agent retrieved, because the target and the grounding are the usual causes of a reply that reads thin or raw. For latency, look at what the agent called, because the millisecond figure measures the actions and services behind the reply rather than the wording. For an unexplained flop in a single case, rerun before you rewrite, since changing instructions to fix noise makes the next run worse.

Notice the ordering the remedies share: read before you rewrite. Every fix in the list begins with reading something, the reasoning, the expected response, the retrieved knowledge, or what the agent called, and only then changes the agent. The temptation after a red cell is to edit immediately, and it is the wrong move twice over: it makes the next run harder to interpret, and if the red was noise it leaves the agent worse than it started.

### After deployment the loop continues with different instruments

After deployment the same loop continues with different instruments. Testing Center is the pre-deployment half: the baseline you set in a suite is the number production gets compared against, and custom criteria can carry forward as session scorers so the same measurement keeps running on real conversations in Agent Analytics.[^3] Two cautions apply when you read the post-launch side. Live scoring runs on a sample of sessions, so the rate reflects that sample rather than every conversation that happened. And the metrics a test suite cannot produce, deflection, abandonment, escalation, and error rate, come from Analytics on real traffic rather than from any suite. Read the suite for routing, actions, and response quality. Read Analytics for what happened to the customer.

The bridge between the two instruments is the scorer. A custom scorer you defined for the suite can carry forward as a session scorer, so the exact criterion you gated the release on keeps being measured on live traffic. That continuity is what makes the pre-deployment baseline more than a one-time gate: it becomes the reference a production trend is compared against, and the same question, is the agent still meeting this bar, is asked both before and after launch, with the same yardstick.

## Exam Traps

Three misconceptions dominate this objective. The first is believing a quality score of 3 means a good response. The pass line is set at 3, and the band from 3 to 4 still covers partial clarity and completeness, so a 3 clears the bar and says nothing about how far above it the reply sat, which is why the bar your team sets is a separate decision from the default. The second is believing a single newly failing case is a regression. The agent is non-deterministic, so retest the utterance manually in Builder before rewriting anything, because a rewrite aimed at noise produces a real regression in its place. The third is believing a run is good because every assertion passed. Assertions confirm only the expected subagent and actions, so a case can pass both and still score low on response quality, which means a grid with no assertion failures can still be a grid with a phrasing problem running the length of it.

## What a consultant should walk away with

Read each column with its own scale in mind: assertions return pass or fail, the judge scores zero to five and passes at 3 by default, and latency returns milliseconds, so never read the grid as though one bar fit every column. Read a column for a pattern and a row for a single failure, and open the detail panel on anything ambiguous, because the two common patterns, assertions green with quality low, and assertions red with a clean-sounding reply, point at completely different fixes. Turn the suite into a release gate by holding it still: record a baseline, change one thing, rerun, and compare the two runs column by column. Treat a regression as a case that moved, not a case that failed, agree the floor before you see the scores, and retest a lone red cell before you rewrite anything. Then keep the loop running after launch, reading the suite for routing, actions, and response quality while Analytics tells you what happened to the customer.
