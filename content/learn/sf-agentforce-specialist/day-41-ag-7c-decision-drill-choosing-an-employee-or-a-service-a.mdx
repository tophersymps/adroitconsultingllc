# Lesson 41: Decision Drill: Choosing an Employee or a Service Agent From the Scenario

A consultant finishes an Employee agent for a client's internal service desk, demonstrates it on the intranet, and then field marketing asks to put the same agent on the public website so shoppers can ask about returns. Someone points the web widget at the agent, and within a day the security team is asking how an anonymous visitor got a greeting that referenced internal case queues. Nothing was hacked and no data was leaked in that first build, but the audience had changed and nobody had renamed the agent to match.

Agent type is not a skin you can move between surfaces. It is a decision about who the conversation serves and which identity the agent runs as, and the platform encodes that decision in the agent record itself. An Employee agent is built for authenticated people inside the company and runs as the logged-in user, inheriting that person's access. A Service agent is built for external customers and runs as the agent user, a dedicated identity with its own permission set. The moment the audience moves from staff to the public, the correct identity moves with it, and a build that ignores that carries the wrong access onto the wrong surface.

This lesson is a decision drill, written the way the exam writes its scenarios: a short situation, then one distinguishing fact that resolves it. It serves requirement ag-7c, "Given a scenario, identify when to use an Employee or Service agent," in the AI Agents domain, which is the heaviest on the exam at 35 percent. By the end you can translate any scenario into the audience and the identity before you name a type, and you can spot the two near misses, a login that is external and a channel that is internal, that the exam uses to pull candidates off the answer.

## Deep Dive

### Lock the audience and the identity before you name a type

Every scenario in this drill has the same two-part solution path. First find the audience: is the conversation for people inside the company, or for people outside it? Second find the identity: does the agent run as the person in the conversation, or as a dedicated agent user? Lock the audience first, because the audience fixes the running identity, and the running identity fixes the agent type. An internal audience means a logged-in user, which points at an Employee agent. An external audience means no internal identity to inherit, which points at a Service agent running as the agent user.

The reason to rehearse the method rather than memorise a list of cases is that the exam rarely states the audience plainly. It hides the audience behind a channel name or a login. Slack reads as a chat surface but is internal. A portal sign-in reads as authentication but the user is still external. When you meet either one, translate it back to audience and identity before you let the surface name the type for you. Salesforce's own documentation makes the split explicit in the execution model: an Employee agent runs as the logged-in user and inherits that user's permissions, while an external Service agent runs as a system or agent user and needs explicit grants to its own permission set.[^2]

This is why the drill exists. The exam is testing whether you can hold audience and identity separate from channel and activity, because those last two are the distractors. An agent's channel is where it appears, and its actions are what it does. Neither one sets the type.[^4] Keep the two questions in front of you and every scenario below resolves in a single line.

### An internal help desk sits inside Salesforce, so it is an Employee agent

Scenario one. An internal help desk wants an agent that answers policy and benefits questions for employees inside the Salesforce app and can raise a ticket through a workflow the employee already has access to. This is an Employee agent. The distinguishing fact is that the users are authenticated employees working inside Salesforce, so the agent runs as each logged-in user and inherits that person's access. The ticket workflow is a component the agent calls, not a reason to change its type.

The near miss is the workflow action, which tempts a candidate toward a build or an integration answer. Agent type is not set by what the agent does; it is set by who it serves and as whom it runs. A help desk agent that raises tickets is still an Employee agent if its users are internal, just as it would still be an Employee agent if it raised nothing at all. The action is orthogonal to the type, and the exam will offer an action-flavoured distractor precisely because it looks relevant.

On the exam, this is the clean case that the others are variations on. When you see internal staff, an internal app, and a logged-in user, you can answer before you finish reading the options. The rest of the drill is about the disguises that cover that same clean case.

### Anonymous shoppers break the Employee test, so it is a Service agent

Scenario two. A retailer wants anonymous shoppers on its public marketing site to ask about return policy and shipping, with no login at all. This is a Service agent on an enhanced messaging channel. The distinguishing fact is that the users are unauthenticated external visitors, so the agent runs as the agent user. There is no logged-in user for an Employee agent to inherit, which rules the Employee agent out on the identity, not on politeness or on the size of the topic.[^3]

The near miss is the simple knowledge-only conversation, which tempts a prompt template answer because a policy question feels like a single generated response. But a conversational surface with an unknown user is a Service agent, not one generated response. The distinguishing line is that the shopper is holding a conversation with state across turns, not asking for one document to be produced. The unauthenticated audience makes it external, and the conversational surface makes it an agent rather than a template.

Note what does not matter here. The retailer's site is custom, the widget is embeddable, and the knowledge behind it is small. None of that changes the type. What matters is that the person is outside the company and is not signed in, and a Service agent with those facts is the answer even when the knowledge base is tiny.

### Outbound prospect email is neither, it is a Lead Nurturing agent

Scenario three. A sales team wants the agent to send outbound email to cold prospects and nurture them toward a meeting. This is a Lead Nurturing agent, not an Employee or a Service agent. The distinguishing fact is that the audience is external prospects reached over outbound email on an automated cadence, which is the Lead Nurturing template's job.[^1]

The near miss is that the recipients are external and unauthenticated, which looks exactly like a Service agent. The difference is the direction and the modality. A Service agent answers inbound customer conversations on a messaging channel, while a Lead Nurturing agent runs outbound email on a schedule. When the exam offers both, the outbound email cadence decides it, because none of the other types reach out on their own initiative.

This scenario exists to show that the Employee-versus-Service drill is not the whole map. The full question is which type, and sometimes the right type is a third one. The method still holds: find the audience, find the identity or the modality, and the type follows. A prospect reached by automated email is not a customer holding a conversation, and it is not an employee asking a question.

### A portal login is not an internal user, so it stays a Service agent

Scenario four. A bank wants customers to sign in on its portal and then ask the agent about their own accounts and balances. This is a Service agent with credential-based user verification. The distinguishing fact is that the user must see only their own records, which only the verified site user identity provides.

The near miss is the login, which tempts a candidate to call it an Employee agent because the user is authenticated. The correction is that authenticating to the portal is not the same as being an internal Salesforce user. The customer is external, so it stays a Service agent, and verification, not the audience, is what narrows the data. The agent still runs as the agent user; verification supplies the specific customer's identity to constrain what the agent may return to that person.

This is the single most common trap in the drill, and it is worth stating twice. Authentication is not the test; the audience is. A logged-in customer is external. A logged-in employee is internal. If your answer changes based on the phrase signed in, you are reading the login and not the audience. The verified site user is how a Service agent shows a customer their own data without switching to an Employee agent, and it is the reason the login and the identity are two different facts.

### A Slack surface for staff is still an Employee agent

Scenario five. A sales operations team wants an agent in Slack that answers questions about pipeline and drafts account summaries for reps. This is an Employee agent. The distinguishing fact is that Slack here is an internal channel for authenticated staff, so the agent runs as the logged-in rep.

The near miss is the channel itself, because a candidate who treats any chat surface as customer-facing will reach for a Service agent. The correction is that the audience, internal staff, sets the type, and the channel only has to be one an Employee agent supports, which Slack is. An Employee agent in Slack is not a different animal from an Employee agent in the app panel; it is the same type placed on a channel built for employees.[^1]

Pair this with scenario two and the lesson of the drill falls out. A widget on the public web and a channel in Slack are both conversational surfaces, but one is external and one is internal, so one is a Service agent and one is an Employee agent. The surfaces are identical in feel and opposite in type, which is exactly why the exam reaches for them.

### The method that decides the remaining cases, and the retired default

Scenario six. A company has a retired Agentforce (Default) agent in its org and asks what to do with it. The distinguishing fact is that the Agentforce (Default) template is retired, with no new features and no availability in new environments, so the answer is to migrate it to an Employee agent rather than extend it.[^1] The near miss is treating the default as a neutral general agent, which leads a candidate to keep building on it instead of moving off it.

The default was employee-facing, which is why the migration target is the Employee agent rather than a Service agent. The retirement is a fact about product state, not about type, so the method still decides the destination: internal audience, logged-in identity, Employee agent. Migrating is the answer because extending a retired template strands the client on a surface Salesforce will not improve, and the exam uses this scenario to test that you separate a product-state fact from a type decision.

Across all six scenarios the same two questions hold. Is the audience internal or external, and does the agent run as a logged-in user or as the agent user? The internal-audience, logged-in-identity pair gives an Employee agent. The external-audience, agent-user pair gives a Service agent. The two extra scenarios, outbound email and the retired default, show the method reaching past the two-way drill when the modality or the product state decides the case. The exam rarely hides the audience in a plain sentence; it hides it behind a channel or a login, so translate those two things back into audience and identity before you answer.

## Exam Traps

Three traps dominate this objective, and they are all versions of the same mistake. The first is believing an authenticated user is always an internal user: a customer who logs into a portal is still external, so the agent stays a Service agent with credential-based verification, and the login is a red herring rather than a signal. The second is believing outbound prospect email is a Service agent job: automated outbound email to prospects is the Lead Nurturing agent, while a Service agent answers inbound customer conversations, so the direction of the conversation decides it. The third is believing a chat surface implies a Service agent: Slack and the in-app panel are internal channels, so an agent there for staff is an Employee agent no matter how closely it resembles a customer widget. In every case the correction is the same, trade the surface and the login for the audience and the identity, and let the type follow from those two facts.

## What a consultant should walk away with

Read every scenario for two facts before you look at the options. Find the audience, internal or external, and find the running identity, the logged-in user or the agent user. Internal staff with a logged-in identity is an Employee agent, whether it lives in the app, on the intranet, or in Slack. External customers with the agent user is a Service agent, whether the visitor is anonymous or signed into a portal, and a signed-in customer gets credential-based verification rather than a new type. When the modality is outbound email, the type is Lead Nurturing, and when the template is the retired Agentforce (Default), the destination is the Employee agent. Treat the channel and the login as disguises, translate them back into audience and identity, and answer from the two facts rather than the surface.
