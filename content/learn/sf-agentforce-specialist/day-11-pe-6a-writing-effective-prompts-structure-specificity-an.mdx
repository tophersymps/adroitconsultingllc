# Lesson 11: Writing Effective Prompts: Structure, Specificity, and Output Shape

A support manager ships a prompt that reads write a good response to this case, and the first replies come back wordy, generic, and about a paragraph too long for the channel. The team's answer is to add more words to the prompt, and the replies get no better. The prompt was never too short. It was never specific about the job, the data the answer had to rest on, or the shape the reply should take.

The cause is that a model does not infer what you hoped it would. It responds to what you state, and a prompt that gestures at a task rather than describing it produces exactly that: a gesture back. Good prompt writing is a set of named practices, not a talent, and each one closes a gap where the model would otherwise guess.

This lesson covers those practices for requirement pe-6a in the Prompt Engineering domain: being specific, supplying context, keeping a consistent structure, naming the output shape, adding constraints and examples, and iterating against real data. The exam tests them as a set of concrete techniques, so learn what each one fixes rather than memorizing a list. The lesson shows two prompts side by side where it helps, so you can see the improvement rather than read a claim that it exists.

## Deep Dive

### Be specific: name the task, not the hope

Best practices for prompt writing start with being specific. Name the task, the audience, the tone, and the length in plain language, because the model does not infer what you hoped it would [^2]. A prompt that says write a good email fails, while a prompt that says write a professional email apologizing for a delayed refund, naming the refund process, and asking the customer for no further action succeeds, because it states the job instead of gesturing at it.

The reference example from Salesforce's own guidance is the same shape: replace a vague ask with a described outcome, and the response stops being generic [^2]. Specificity is the first lever because every later practice, context, structure, and output shape, only matters once the task itself is unambiguous. An ambiguous task with perfect grounding still produces the wrong thing, written well.

The mechanism is simple to state. A prompt is a specification, and a specification that leaves a requirement implicit leaves the model to choose, and the model will choose the most general reading available. Writing the requirement down removes that choice. If you cannot say in one sentence what the output must accomplish, the model cannot either.

### Before and after: what one specific sentence buys you

Put the same requirement through two prompts and the difference is visible. The before is a single line: Draft a response to the customer about their refund. The after names the job, the audience, the tone, and the outcome: Draft a two-sentence reply to the customer that apologizes for the delayed refund, confirms the refund is processing under our standard timeline, and closes without asking the customer to take further action.

The before leaves four things open: the length, the tone, whether to promise a date, and whether to ask for anything else. The model fills each gap with a default, so the reply arrives longer and more generic than the channel wants, and often asks the customer to check back, which is the opposite of the outcome the team needed. The after closes all four gaps in one sentence, so the reply arrives at the right length, in the right tone, and ends the way the business intended.

Nothing about the after takes more platform skill; it takes a minute longer at authoring time. That is the trade specificity makes: a little more writing now in exchange for output you do not have to fix later. On the exam, an option that describes the outcome in specific terms beats an option that adds adjectives or extra instructions without naming the job.

**Four gaps a vague prompt leaves open**

| Left open by the vague prompt | Closed by the specific prompt |
| --- | --- |
| Length | States a two-sentence reply |
| Tone | Sets an apologetic tone |
| Whether to promise a date | Confirms the standard refund timeline |
| Whether to ask for anything else | Closes without asking for more |

### Context is grounding seen from the writer's side

The second practice is to provide context, which is to ground the prompt in the data the model needs so it does not guess. Context is the customer name, the purchase history, the open cases, or the product names that the answer depends on. In Prompt Builder, context is inserted as resources, so a merge field, a Flow, an Apex class, or a Data 360 data model object supplies the real value at run time [^3], which Prompt Builder resolves into the prompt before it reaches the model [^4].

A prompt with no context produces filler, and a prompt with context produces something specific, which is why context and grounding are the same move seen from two angles. Day seven and day eight cover choosing the resource; here the point is that leaving context out is a prompt-writing defect, not a platform one. The writer who omits the customer's name and order history has asked the model to write to a stranger.

Ground the data the answer actually needs and reference it once. Salesforce's own guidance on the ingredients of a prompt template lists participants, setting, goal, relationships, and data as the pieces a strong template supplies, and each of those is context the model would otherwise invent [^5]. Supplying them is what turns a template that could describe any customer into one that describes this one.

### A consistent structure is the reusable skeleton

The third practice is to use a consistent structure. A reliable prompt has a role, a task, a set of instructions, and a format block, and the worked examples in Salesforce's own prompt training write them as labeled sections: a task line, then instruction points, then a format block that lists the expected output shape [^2].

Salesforce's guidance on a template's ingredients makes the same point from the other side: keep the instructions together in one labeled section, separated from context, so the model can tell the two apart, and surround the instructions with triple quote boundaries to mark where they begin and end [^5]. Keeping the same structure every time makes a prompt easier to reuse and easier to update later, because you always know where each requirement lives.

Consistent formatting is one of the named best practices, not a cosmetic preference. When the structure never changes, a revision is a one-line edit rather than a rewrite, and a teammate can read your prompt and find the output rule without hunting. Structure is what makes the other practices maintainable over the life of a template.

### Name the output shape or reformat it by hand

The fourth practice is to make the output shape explicit. If you want a numbered list, a JSON object, a subject line plus a body, or a fixed set of bullet points, you say so in the prompt, and if the goal is a summary you say how long it should be. Explicit output formatting is one of the core elements of an effective prompt, alongside a clear task and relevant context, and leaving the shape implicit invites a response you then have to reformat by hand [^1].

When a downstream system consumes the output, the shape is a contract, and the prompt is where the contract is written. A prompt that leaves it implicit produces a response the parser rejects, which then reads as a model failure when it is really a prompt failure. The same is true for a human consumer: a reply that must be two sentences for the channel, or that must open with a subject line, is a shape you state rather than hope for.

State the shape as a short block at the end of the instructions, and let that request for structure guide the model's last pass. Naming the shape up front also makes two prompts comparable, because when the format is fixed the only variable left is the content.

### Before and after: the output shape is a contract you write

Take a prompt that has to feed a field a team reads, and compare two versions. The before ends the instructions with: Summarize the case. The after ends them with: Return a subject line of no more than eight words, then a body of exactly three sentences that states the issue, the current status, and the next step.

The before produces a paragraph of unpredictable length, sometimes with a heading the reader did not ask for, and every record gets a differently shaped summary. The after produces the same three-part shape on every run, so a rep can skim any case note in seconds and a Flow that consumes the output gets a consistent pattern. The content was never the problem; the shape was.

This is where output formatting stops looking cosmetic. A fixed shape is what makes generated text usable downstream, and the prompt is the only place that shape can be specified. On the exam, an option that names the format and the length is almost always the stronger answer than one that repeats the content request more forcefully.

### Constraints and worked examples pin down tone and format

The fifth practice is to set constraints and give examples. State what the response must avoid, such as speculation or advice outside approved data, and state the length you want. When consistency matters, provide a few worked examples of input and output, which is few-shot prompting, so the model learns the format and tone from the pattern rather than from a description [^7].

For a multi-step reasoning task, instruct the model to work through the intermediate steps before the final answer, which is chain-of-thought prompting and improves the quality of the reasoning it shows [^7]. Both techniques are levers on the same dial: they reduce the space of acceptable outputs so the response you get is the one you actually wanted.

Salesforce's guidance adds two practical versions of the same idea. Asking the model to role-play a character, such as a support representative, and then defining that character's goal gives the model a perspective to write from, and starting from an example template in the library and customizing it gives you a working structure to imitate rather than a blank page [^1][^6]. Both are ways of showing the model the shape you want instead of describing it.

### Reference each fact once, then test and iterate

The last two practices tie it together: reference data once, and test and iterate. Repeating the same facts in one prompt can produce inconsistent output, so the reference-once principle says to name each fact a single time and rely on grounding rather than restatement [^2].

Then test the prompt against real data and refine based on what comes back. If information is missing, add explicit instructions for the required elements. If the tone is wrong, add specific tone guidance. If the length is wrong, add an explicit length constraint. Optimizing a prompt is an iterative cycle of write, test, and refine, not a one-shot, and treating it as a cycle is the practice that separates a good prompt from a lucky one.

The loop is worth stating as a routine because the exam rewards it as a practice in its own right. Change one thing, run it against a real record, and read which part of the output moved. That is how you learn which instruction caused which behavior, and it is why the iterate step is named alongside the writing practices rather than left as an afterthought.

### Worked scenario: the reply that would not fit the channel

A support manager ships a prompt that reads write a good response to this case, and the first replies come back wordy and generic, about a paragraph too long for the messaging channel. The team's fix is to add more words to the prompt, and the replies get no better. What is actually wrong, and what is the correct fix?

Diagnose against the practices. The prompt is specific about nothing: it does not name the task, it does not supply the case context as a resource, and it does not state the output shape or the length. Adding more words without naming those three things changes the volume of instruction, not the specification, so the model still chooses its own length and tone. The defect is a missing specification, not a missing paragraph.

The wrong answer is to keep lengthening the prompt, or to blame the model and reach for a different one. The right fix names the job, grounds the prompt in the case fields the reply depends on, and states the shape and length, for example a two-sentence reply that acknowledges the issue and states the next step. That is the same requirement as before, written as a specification rather than a wish.

### The build sequence in six steps

<Steps>

<Step title="Open Prompt Builder">

In Setup, open Einstein and then Prompt Builder and create a new prompt template for the task you want to improve.

</Step>

<Step title="Write the prompt">

Write the prompt in labeled sections: a role line, a task line, instruction points, and a format block for the output shape.

</Step>

<Step title="Use Insert Resource">

Use Insert Resource to add the context the answer needs as merge fields, related lists, flows, Apex, or Data 360 data model objects.

</Step>

<Step title="State the output format explicitly">

State the output format explicitly, such as a subject line plus a plain-text body or a numbered list, and name any length limit.

</Step>

<Step title="Add constraints and examples">

Add constraints and, where consistency matters, a few worked input and output examples to set the tone and format.

</Step>

<Step title="Click Save and Preview">

Click Save and Preview, run the prompt against a real sample record, and refine the instructions based on how the response reads.

</Step>

</Steps>

## Exam Traps

<Callout kind="warning">

Three traps dominate this objective. The first is believing a longer prompt is a better prompt. Length is not quality. Specifying the task, the context, and the output shape is what improves the answer, and padding the prompt with repeated data can make the response worse. The second is believing the model will infer the format you want. The output shape is a constraint you state, so a request for JSON, a subject plus body, or a fixed set of bullets belongs in the prompt rather than in the reader's head. The third is believing examples are optional when consistency matters. A few worked input and output examples teach the model the format and tone to mimic, so a prompt that must match a house style benefits from few-shot examples directly. Each trap is a version of the same error: assuming the model will fill a gap you never declared.

</Callout>

## What a consultant should walk away with

<KeyTakeaways>

- Specificity beats length: describe the outcome instead of gesturing at it, because a longer prompt is not a better prompt
- Insert the data the answer depends on as grounded resources, because the model will not infer context you leave out
- Keep one structure, a role, a task, instructions, and a format block, so the prompt stays reusable and easy to edit
- Reference each fact once and treat the prompt as something tested against real records, not written once and trusted

</KeyTakeaways>
