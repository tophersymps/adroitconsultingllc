# Lesson 11: Writing Effective Prompts: Structure, Specificity, and Output Shape

A support manager ships a prompt that reads write a good response to this case, and the first replies come back wordy, generic, and about a paragraph too long for the channel. The team's answer is to add more words to the prompt, and the replies get no better. The prompt was never too short. It was never specific about the job, the data the answer had to rest on, or the shape the reply should take.

The cause is that a model does not infer what you hoped it would. It responds to what you state, and a prompt that gestures at a task rather than describing it produces exactly that: a gesture back. Good prompt writing is a set of named practices, not a talent, and each one closes a gap where the model would otherwise guess.

This lesson covers those practices for requirement pe-6a in the Prompt Engineering domain: being specific, supplying context, keeping a consistent structure, naming the output shape, adding constraints and examples, and iterating against real data. The exam tests them as a set of concrete techniques, so learn what each one fixes rather than memorizing a list.

## Deep Dive

### Be specific: name the task, not the hope

Best practices for prompt writing start with being specific. Name the task, the audience, the tone, and the length in plain language, because the model does not infer what you hoped it would [^1]. A prompt that says write a good email fails, while a prompt that says write a professional email apologizing for a delayed refund, naming the refund process, and asking the customer for no further action succeeds, because it states the job instead of gesturing at it.

The reference example from Salesforce's own guidance is the same shape: replace a vague ask with a described outcome, and the response stops being generic [^2]. Specificity is the first lever because every later practice, context, structure, and output shape, only matters once the task itself is unambiguous.

### Context is grounding seen from the writer's side

The second practice is to provide context, which is to ground the prompt in the data the model needs so it does not guess. Context is the customer name, the purchase history, the open cases, or the product names that the answer depends on. In Prompt Builder, context is inserted as resources, so a merge field, a Flow, an Apex class, or a Data 360 data model object supplies the real value at run time [^3].

A prompt with no context produces filler, and a prompt with context produces something specific, which is why context and grounding are the same move seen from two angles. Day seven and day eight cover choosing the resource; here the point is that leaving context out is a prompt-writing defect, not a platform one.

### A consistent structure is the reusable skeleton

The third practice is to use a consistent structure. A reliable prompt has a role, a task, a set of instructions, and a format block, and the worked examples in Salesforce's own prompt training write them as labeled sections: a task line, then instruction points, then a format block that lists the expected output shape [^2].

Keeping the same structure every time makes a prompt easier to reuse and easier to update later, because you always know where each requirement lives. Consistent formatting is one of the named best practices, not a cosmetic preference. When the structure never changes, a revision is a one-line edit rather than a rewrite.

### Name the output shape or reformat it by hand

The fourth practice is to make the output shape explicit. If you want a numbered list, a JSON object, a subject line plus a body, or a fixed set of bullet points, you say so in the prompt, and if the goal is a summary you say how long it should be. Explicit output formatting is one of the core elements of an effective prompt, alongside a clear task and relevant context, and leaving the shape implicit invites a response you then have to reformat by hand [^1].

When a downstream system consumes the output, the shape is a contract, and the prompt is where the contract is written. A prompt that leaves it implicit produces a response the parser rejects, which then reads as a model failure when it is really a prompt failure.

### Constraints and worked examples pin down tone and format

The fifth practice is to set constraints and give examples. State what the response must avoid, such as speculation or advice outside approved data, and state the length you want. When consistency matters, provide a few worked examples of input and output, which is few-shot prompting, so the model learns the format and tone from the pattern rather than from a description.

For a multi-step reasoning task, instruct the model to work through the intermediate steps before the final answer, which is chain-of-thought prompting and improves the quality of the reasoning it shows. Both techniques are levers on the same dial: they reduce the space of acceptable outputs so the response you get is the one you actually wanted.

### Reference each fact once, then test and iterate

The last two practices tie it together: reference data once, and test and iterate. Repeating the same facts in one prompt can produce inconsistent output, so the reference-once principle says to name each fact a single time and rely on grounding rather than restatement [^2].

Then test the prompt against real data and refine based on what comes back. If information is missing, add explicit instructions for the required elements. If the tone is wrong, add specific tone guidance. If the length is wrong, add an explicit length constraint. Optimizing a prompt is an iterative cycle of write, test, and refine, not a one-shot, and treating it as a cycle is the practice that separates a good prompt from a lucky one.

## Exam Traps

Three traps dominate this objective. The first is believing a longer prompt is a better prompt. Length is not quality. Specifying the task, the context, and the output shape is what improves the answer, and padding the prompt with repeated data can make the response worse. The second is believing the model will infer the format you want. The output shape is a constraint you state, so a request for JSON, a subject plus body, or a fixed set of bullets belongs in the prompt rather than in the reader's head. The third is believing examples are optional when consistency matters. A few worked input and output examples teach the model the format and tone to mimic, so a prompt that must match a house style benefits from few-shot examples directly. Each trap is a version of the same error: assuming the model will fill a gap you never declared.

## What a consultant should walk away with

Say the task, supply the context, and name the output shape. Specificity beats length every time, so describe the outcome instead of gesturing at it, and insert the data the answer depends on as grounded resources rather than leaving the model to guess. Keep one structure, a role, a task, instructions, and a format block, so the prompt stays reusable and easy to edit. State the format and the length, add paired constraints and worked examples where tone must hold, reference each fact once, and treat the prompt as something you test against real records and refine, not something you write once and trust.
