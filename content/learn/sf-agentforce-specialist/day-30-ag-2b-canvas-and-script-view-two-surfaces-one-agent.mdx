# Lesson 30: Canvas and Script View: Two Surfaces, One Agent

A delivery lead had two people working the same agent. An admin configured the return flow in one editor. A developer refined the same flow in a different editor and told the lead the two were out of sync. When they finally looked together, both editors were showing the same agent, and the only real problem was that they had been editing it at the same time without saving. The confusion was not the product; it was a mental model in which two editors must mean two agents.

That mental model is the thing this lesson removes. Agentforce Builder gives you two views over one artifact: a document-style Canvas that summarizes Agent Script into blocks with shortcuts, and a Script view that exposes the same text with the tools a developer expects. There is exactly one Agent Script definition per agent. Switching views does not convert one agent into another and does not create a second definition, because both surface the same source and both write back to it.

This lesson serves requirement ag-2b, the same requirement as day twenty nine, taken now from the side of the author: how Agent Script functions in Canvas and Script View. It sits in the AI Agents domain, which carries 35 percent of the exam. By the end you can say which view produces which artifact, describe what each surface does well and where it stops, and name the two rules that keep a team out of trouble: one artifact, and one editor at a time.

## Deep Dive

### One artifact, two editors: the sentence to remember

There is exactly one Agent Script definition per agent. Canvas renders that script as blocks with typeahead and inline tools; Script view shows the same text with syntax highlighting, autocompletion, and validation. Whichever surface you use, what is stored is Agent Script, and what ships to the runtime is the Agent Graph compiled from it.[^2] If you remember one sentence for the exam, it is that the two views are skins over the same file, and neither is a different kind of agent.[^5]

The platform is explicit that configuration and edits are consistent across both views.[^1] When you open or create an agent, it opens in Canvas view by default, and if you edit in Canvas using natural language, the builder writes Agent Script in the background so the two stay in sync. A switch between the views never reconciles two documents; it re-renders one.

The practical test for whether you have the model right is to ask what changes when you switch views. Nothing about the agent changes; what changes is how the same source is presented. Canvas shows the agent summary, its details, its router, and its subagents as view-only blocks, and you go into a block to edit it or switch to Script view. That is a rendering of the file, not a different file, and a team that treats the switch as a migration will waste time reconciling two views of one artifact.

A useful way to say it for the exam is that the surface is a preference and the artifact is a fact. Two authors can prefer different surfaces, and both are correct, because neither surface changes what the agent is. What changes is the ergonomics of editing and the ceiling on complexity. The moment someone says the Canvas agent and the Script agent, the model is already wrong.

### Canvas is the low-code surface, and the shortcuts are the point

Canvas behaves like a document editor. You move blocks, add an action filter, and describe intent in natural language, and you can format text with Markdown. The shortcuts are what make it fast: type a forward slash to insert a common pattern such as an if/else conditional, and type an at sign to insert a resource, meaning a subagent, an action, or a variable.[^1]

Because the shortcuts emit valid Agent Script, Canvas is hard to get syntactically wrong, and it suits an admin or a consultant who understands the process but does not want to maintain a code file. It is the right default when the process is well understood and mostly standard. Canvas is also where quick if-then transitions between subagents and conditional action availability get configured without touching syntax, and the platform underlines errors in Canvas while telling you to switch to Script view for the detail.[^1]

The two shortcuts cover the two things a block author does most. The forward slash inserts a common pattern such as an if/else conditional, and the at sign inserts a resource, which is an explicit reference to a subagent, an action, or a variable. Resources resolve like merge fields in reasoning instructions, and the platform guidance is to use them rather than free text whenever you reference a subagent, an action, or a variable, because an explicit reference guides the agent more reliably than prose.

Canvas also carries an inline action shortcut, a way to add deterministic logic that runs before any reasoning takes place, so the block author can place a conditional that fires ahead of the model without writing the arrow syntax by hand. The pattern to notice is that Canvas is not just a presentation of the script; it is a set of authoring gestures, each of which emits a specific Agent Script construct.

### Script view is the pro-code surface, and validation is its spine

Script view exposes the raw Agent Script with the tools a developer expects: syntax highlighting, autocompletion, and validation that flags critical issues such as syntax errors, undefined references, and missing variables, plus warnings such as unused variables and unreachable logic. Complex business rules written as expressions, action chaining where a sequence of actions must run in a guaranteed order, and fine-grained conditional branching all belong here.[^5][^3]

You can type an at sign and pick a resource from autocomplete, and the same source can be retrieved into a Salesforce DX project and edited in an IDE with the Agentforce DX extension, so the file travels between Builder and the developer's toolchain. The trade is that you must understand the language and you own its correctness, and it is possible to make changes in Script view that make Canvas unavailable until the errors are fixed.[^1]

The validation layer is the reason Script view is safe for a developer. It separates critical issues, such as syntax errors, undefined references, and missing variables, from warnings, such as unused variables, data type mismatches, and unreachable logic. A critical issue blocks a commit; a warning does not. That split tells you when a red line is a genuine defect and when it is a note you can carry forward knowingly, and it is why the error console is part of the surface rather than an afterthought.

The autocompletion entry point is the same at sign you use in Canvas, so the syntax you type is the syntax the shortcut would have written. Type the at sign, pick the resource, and the reference is inserted with the right form, whether it is a variable, an action, or a subagent. The Agentforce DX extension carries the language into an IDE with the same editing features, so a developer who prefers a full IDE is not forced into the browser, and the artifact stays one file either way.

### Neither view produces a Flow: the artifact is Agent Script, compiled to the Agent Graph

It is worth being precise about artifacts, because the exam likes the distinction. Canvas does not produce a Flow and does not produce a document; it produces Agent Script, the same source Script view edits. The compiler turns Agent Script into the Agent Graph, a serialized execution plan, and the Atlas Reasoning Engine executes that graph.[^4]

So the answer to which view produces which artifact is that both views produce one Agent Script source, that source compiles to one Agent Graph, and the graph is what runs. A conversational mode, sometimes described as the Agent Optimizer, is a third on-ramp: you describe the behavior and the builder scaffolding writes subagents, actions, and expressions, again as Agent Script, so all three paths converge on the same file.[^1]

This is why an exam option that says Canvas generates a Flow, or that Script view deploys an Apex class, is testing the artifact model. The only artifact the two views share is Agent Script; the only compiled artifact is the Agent Graph; the only executor is the Atlas Reasoning Engine. Hold those three and the which-artifact questions answer themselves.

### The trade-off is reach against risk

The trade-off of Canvas is reach against risk. It is faster to start, forgiving for a non-developer, and hard to get syntactically wrong because the shortcuts emit valid script. Its cost is a ceiling: the most complex conditional logic, precise sequencing, and exact control over how instructions are phrased are hard to achieve through blocks and typeahead, and work a developer would do once in Script view can turn into a lot of block editing.

Script view trades convenience for precision. Everything is expressible and validation catches mistakes as you type, but you must understand the language and you own its correctness. Choose the surface for the job and for the author's skill, not out of loyalty to one view. Both are legitimate, both edit the same artifact, and neither is more correct than the other.

A worked split makes the trade concrete. Suppose a process needs a simple yes or no branch and a set of action filters: that is Canvas work, and the block author can finish it without help. Suppose the same process later needs an expression that compares several variables and a chain of actions that must run in a guaranteed order: that is Script view work, and the block author will either hand it to a developer or spend a long time approximating it through blocks. The surface follows the complexity, not the other way around.

### Two authors, one agent: the conflict you should avoid

The rule that catches teams is that changes are not visible to another editor until they are saved, so two people editing the same agent at once can conflict. Check the Modified By column to see recent work before you start, and serialize edits rather than assuming the other person saw your change.[^5]

This is the operational face of the one artifact rule. Because both views are skins over the same source, a conflict is not a merge between two documents; it is one person's unsaved work colliding with another's saved change. The disciplined pattern is one editor of the agent at a time, with the others reading rather than writing.

It helps to separate the conflict risk from the consistency guarantee. Consistency is automatic: because both views write the same source, the stored configuration is never two documents to merge. Conflict is about timing: two unsaved edits from two people can collide because neither sees the other's change until it is saved. So the mitigation is a workflow habit, one writer at a time and a glance at the Modified By column, not a technical reconciliation.

There is a second timing trap beyond concurrent writes. An edit made in Script view that breaks parsing can leave Canvas view unable to render until the error is fixed, so a developer who leaves the file mid-edit can block a block author who only wanted to read it. Saving a valid intermediate state before switching authors avoids that, and it is a small habit that keeps the low-code surface available to the people who rely on it.

### Drafts, Simulate, and Live Test: what each surface actually does

Two cautions apply to both surfaces. First, both views are drafts until saved, and when you save, Agentforce Builder runs validation checks in both views; you can commit an agent that has warnings but not one with errors.[^1] Second, Simulate uses mock data during development while Live Test changes real records, so the testing surface you choose decides whether you are touching live data.

Keep the testing order straight and it will serve you on the exam and in delivery. Draft in the surface that matches the author, save to run validation, Simulate against mock data to exercise the path, and reserve Live Test, which writes to real records, for the point where you need production-shaped data. The compiled Agent Graph is the thing that actually runs, so what you verify is the behavior of the graph your script produced, not the appearance of the editor.

The commit rule is the part people misremember. An agent with warnings can be committed, but an agent with errors cannot, and the same validation runs when you save. That means the error console is not advisory: a critical issue stops the save, and a warning is a note you can carry forward knowingly. Read the console before you save, because fixing an error after a failed save attempt is slower than fixing it before.

Keep the two testing surfaces distinct in your head. Simulate is the development surface: it uses mock data, so you can exercise a path without touching real records, which is what you want while the agent is still changing. Live Test is the production-shaped surface: it changes real records, so you reach it only when you need data that mock values cannot represent. Choosing the wrong one is not a correctness bug, but it is a data-safety one.

## Exam Traps

Three misconceptions carry the marks. The first is believing Canvas builds a different agent from Script view, when both edit the same single Agent Script file and there is never a separate Canvas agent. The second is believing Canvas produces the running artifact, when it produces Agent Script and the compiler produces the Agent Graph that the Atlas Reasoning Engine executes. The third is believing two authors can safely edit an agent at once, when changes are not visible until saved, so simultaneous edits risk conflict and you should check the Modified By column before you write.

## What a consultant should walk away with

Hold one sentence: two views, one file, one graph. Canvas is the low-code surface where the shortcuts, the slash for a pattern and the at sign for a resource, keep the script valid and suit the author who knows the process but not the syntax; Script view is the pro-code surface with highlighting, autocompletion, and validation, where complex expressions and guaranteed action sequences belong. Neither view produces a Flow, and neither produces a second agent: both produce one Agent Script source that compiles to one Agent Graph. Pick the surface for the author's skill, keep both editors pointed at the same file, never let two people write at once, and treat the compiled graph as the thing that actually runs. Remember that a draft is not saved until you save it, that Simulate uses mock data while Live Test writes real records, and that you can commit warnings but not errors.
