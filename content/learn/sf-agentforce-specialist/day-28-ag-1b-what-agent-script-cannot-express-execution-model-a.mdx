# Lesson 28: What Agent Script Cannot Express: Execution Model and Failure Modes

A team ships an agent that must always validate an order before it offers a replacement. They write the rule the way it reads most naturally, as a line of instruction telling the model to run the validation action first and never to skip it. For weeks it holds. Then a customer phrases the request in a way the team did not test, and the agent offers a replacement without running the check. The instruction was still there, in the same place, in the same words. The model simply did not follow it, because a natural-language line is a suggestion and never a guarantee.

What the team needed was code, not emphasis. The fix is to move the validation into a block that executes unconditionally on every pass, or to gate the replacement action so the model cannot reach it until the check has passed. Both moves depend on understanding something the script does not show you on its surface: the script you write is not the thing that runs. It is compiled into an execution plan that a reasoning engine traverses, and where you place a step in that plan decides whether it is enforced or merely suggested.

This lesson serves requirement ag-1b, in the AI Agents domain, which carries 35 percent of the exam. It is the second lesson of the domain and it names the ceiling of the first: having learned the building blocks, you now learn what they cannot do, because a candidate who knows only what Agent Script can express will over-promise. By the end you will be able to describe the three stages from script to execution, explain the parse as the real unit of execution, state what hybrid reasoning resolves first, name what Agent Script cannot express, and recognize the drift, gate, and loop failure modes by their signatures.

<TLDR>

- Understand that the authored Agent Script is compiled into an Agent Graph the Atlas Reasoning Engine executes
- Treat the parse, not the user turn, as the unit of execution, so before_reasoning runs on every pass
- Learn what Agent Script cannot express and the drift, gate, and loop failure modes that follow

</TLDR>

## Deep Dive

### The agent you author is not the artifact that runs

The pipeline moves through three stages, and only the first is yours to touch.[^1] Authoring is where you work, writing Agent Script in Agentforce Builder. Compilation is where the Salesforce compiler transforms your Agent Script into an Agent Graph, a serialized execution plan optimized for machine execution rather than human reading.[^4] Runtime execution is where the Atlas Reasoning Engine takes over, reading the Agent Graph, traversing it based on current session state, and deciding at each node whether to execute deterministically or invoke the model.

The Agent Graph is the intermediate representation between your readable script and the running agent, and its structure is optimized for the state machine that consumes it rather than for the person who authored the script. You debug at the authoring layer and you read the trace at run time, and you never hand-edit the graph. That separation is deliberate: it lets the platform enforce deterministic behavior independently of how the script was written, which is the reason a rule you place correctly is honored even though you cannot see the machinery that honors it.

![The three stages from script to running agent: you author Agent Script in Agentforce Builder, the compiler builds the Agent Graph, and the Atlas Reasoning Engine executes it.](</diagrams/day-28-ag-1b-what-agent-script-cannot-express-execution-model-a/1-three-stages.png>)

Hold this as the frame for the rest of the lesson. Every failure mode that follows is a mismatch between what you intended in the script and what the compiled plan actually enforced. When you debug an agent, you are not reading a prompt that ran; you are reading evidence about which nodes the engine traversed, which is why the trace and the variables view matter more than re-reading the instructions.

### The unit of execution is the parse, not the user turn

The real unit of execution is not the user turn, it is the parse: one complete pass through a subagent's three lifecycle zones. This is the fact that most changes how people reason about an agent, because a turn and a parse are not the same thing and the difference explains most surprises. The three zones are before_reasoning, which runs at the start of every parse before the model sees anything, with no model involvement. The reasoning zone mixes deterministic resolution with any prompt calls. And after_reasoning runs after the model has responded, again with no model involvement unless a displayable action exits the loop early.[^1]

A parse begins on first entry into the subagent, again after every tool call returns, and again on every new user turn inside that subagent. That means one user turn can trigger several parses: once on entry, then once after each action completes. The consequence is concrete. Work placed in before_reasoning runs more than once per turn in a multi-action flow, so a counter incremented there reflects parse count rather than turn count, and an action with side effects, such as a record write or an external call, repeats unless re-execution is genuinely acceptable.

![A parse is one pass through before_reasoning, the reasoning zone, and after_reasoning, and one user turn triggers several parses, once on entry and again after every tool call returns.](</diagrams/day-28-ag-1b-what-agent-script-cannot-express-execution-model-a/2-parse-lifecycle.png>)

Practical consequences follow from the parse count, and they are the ones a consultant feels. A counter incremented in before_reasoning tracks how many times the subagent parsed, not how many messages the user sent, so a budget or an audit tally built on it will overcount in any flow that calls actions. An idempotency check placed there fires again after every tool call, which is fine only if re-running it is harmless. Read before_reasoning as a block that runs often, and reserve it for work that is safe to repeat.

The second consequence is that work you need only once per session cannot simply live in before_reasoning, because before_reasoning is not a constructor. It is a pre-flight check that runs with every parse. The standard guard is a boolean: run the initialization action only while a sessionInitialized flag is false, then set the flag true, so the heavy work happens on the first parse and the rest of the parses skip it. Naming the parse as the unit is what makes that guard necessary rather than mysterious.

### Hybrid reasoning resolves logic first and prompt second

Hybrid reasoning in practice is the same instruction block carrying both kinds of line, resolved in order. The engine resolves the logic instructions top to bottom first, running actions and setting variables in a fixed sequence. Only then does it assemble the prompt from the surviving prompt lines, with their merge fields resolved, and send that to the model. Logic first, prompt second, and the model receives a prompt whose facts are already correct before it is asked to phrase anything.[^1][^3]

A refund subagent shows how the two halves cooperate. It can run its validate-order action and its get-loyalty-tier action deterministically before the model ever sees a prompt, capturing each result into a variable, and then let the model phrase a reply using variables that are already correct. The model never decides whether the validation happened, because the validation already happened as code before the prompt was built. The variable carries the truth; the prompt carries the wording.

This is why the placement of a step is a design decision and not a style choice. A step written as a logic line is guaranteed to run in the resolution phase, in the order you wrote it. The same step written as a prompt line is a request to the model that it may or may not honor. The exam tests the difference directly: given a behavior that must always happen, the credited placement is the logic line or a deterministic block, not a firm sentence in a prompt.

The cost and latency story follows from the same boundary. Every node the engine can resolve as code costs no model call, and every node carrying a prompt instruction triggers one, so pushing a decision into logic removes a model call rather than merely tidying the script. A node with no prompt instruction executes without an LLM call at all, while reasoning and response generation always go through the model. That is why the boundary is a budget decision as much as a reliability one: where you place a step decides both whether it is guaranteed and what it costs.

### What Agent Script cannot express

Knowing what Agent Script cannot express is as examinable as knowing what it can, because the boundary is where design errors live. It is an orchestration language, not a computation engine, so heavy math and record logic belong behind an action in a Flow or an Apex class, and the script's job is to call that action and store the result. It also cannot configure or fine-tune the model itself, and it cannot change how the model was trained, so any expectation that the script improves the model's raw capability is misplaced.[^1]

The harder boundary is behavioral. Agent Script cannot guarantee that a prompt instruction is obeyed, because a natural-language line is a suggestion and only a logic line executes unconditionally. It also cannot step outside the reasoning engine's runtime, so there is no escape hatch for a step that the engine does not traverse. The practical rule that falls out of both is short: anything you truly need enforced has to be written as logic, a guard, or a gate rather than as forceful wording in a prompt.[^2]

Read requirement scenarios with this boundary in hand. When a scenario asks how to make an agent reliably refuse an action before a precondition is met, the answer is a deterministic check or a gate, never a strong sentence. When a scenario asks how to make the agent do complex arithmetic, the answer is an action that computes it, not a prompt that asks the model to try. The ceiling is the point of the objective, so treat each "cannot" as a design instruction rather than as a limitation to complain about.

### Drift, and the gate that removes an action entirely

The central failure mode is drift between what the model decides and what the script intended. A prompt line that tells the model to always run an action first is not a guarantee; the model may skip it depending on context, which is exactly the variability hybrid reasoning exists to remove. The fix is to move the must-run step into before_reasoning, where a run directive executes unconditionally on every parse, or to gate the action so the model cannot reach it at all.

Conditional availability is written as an available when clause, and it is the strongest form of the fix because it is a platform-level gate rather than a hint. When the condition evaluates to false, the action is removed from the tool list presented to the model entirely, so the model cannot call an action it cannot see. Any false value suppresses it, including None, False, a zero, or an empty string, which means the gate closes on more inputs than people expect.[^1]

The design rule that makes the gate trustworthy is that the variable in an available when clause must have a deterministic set path. If the gate variable is set by code in before_reasoning or in a deterministic run and set block, its state is known before the action is evaluated. If it is left to the model to set, the gate opens as randomly as the model, which reintroduces the exact variability the gate was built to prevent. Never let the model set a gate variable.

### The action loop and the displayable exit

Two more concrete failures close the objective, and both come from the platform not doing something people assume it does. The first is the action loop. The platform does not automatically suppress an action after it runs, so if the gate stays open and the reasoning text never tells the model to stop, the model calls the same action on every parse indefinitely. The loop is the natural result of two conditions holding at once: the available when condition is still satisfied after the action ran, and nothing in the reasoning instructions tells the model to stop.[^1]

There are two reliable ways to break the loop, and both give the gate a deterministic closed state. You can set the gate variable to a closed value as part of the action's post-execution logic, so the condition evaluates false on the next parse. Or you can add a separate has_run boolean that closes the gate after first execution. Either way, the fix is to give the platform the closed state it needs, rather than to add a prompt line asking the model to stop, which shares the unreliability of every other prompt line.

The second failure concerns the displayable exit. When an action is marked displayable, the engine exits the reasoning loop the moment the model surfaces that output, so after_reasoning never runs and any logic placed there is skipped. The fix is the same principle applied one step forward: put logic that must execute into the before_reasoning block of the next subagent rather than the after_reasoning block of the current one. The reasoning loop is not a place to park a guaranteed step, because a displayable action can end it early.

**Failure modes with trigger and fix**

| Failure mode | Trigger | Fix |
| --- | --- | --- |
| Drift | A prompt line tells the model to always run it | Move it to before_reasoning or gate the action |
| Model-set gate | The available when variable is set by the model | Give the gate variable a deterministic set path |
| Action loop | Gate stays open with no instruction to stop | Close the gate or add a has_run flag |
| Displayable exit | A displayable action surfaces and ends the loop | Move the logic to the next subagent's before_reasoning |

### The build sequence in six steps

<Steps>

<Step title="Open Agentforce and then Agentforce Studio">

In Setup, open Agentforce and then Agentforce Studio, and open the agent in Agentforce Builder.

</Step>

<Step title="Add a before_reasoning block">

In Script view, add a before_reasoning block and place there the run directives that must execute on every parse, such as validation and context hydration.

</Step>

<Step title="Gate once-per-session work">

Guard once-per-session work with a flag: run the initialization action only when the flag is false, then set the flag true.

</Step>

<Step title="Add an available when clause">

Add an available when clause to each gated action and give the controlling variable a deterministic set path in the logic instructions.

</Step>

<Step title="Break any possible action loop">

Break any possible action loop by closing the gate variable or adding a has_run flag after the action executes.

</Step>

<Step title="Run Simulate first">

Run Simulate first, then Live Test, and open Interaction Details, Trace, and the Variables tab to confirm which path the engine actually took.

</Step>

</Steps>

## Exam Traps

<Callout kind="warning">

Three traps dominate this objective. The first is believing a prompt instruction is a guarantee. It is not: a natural-language line is a suggestion the model may skip, while a run directive in before_reasoning is code that executes unconditionally, so a behavior that must always happen belongs in logic or a gate rather than in forceful wording. The second trap is believing before_reasoning runs once per session. It runs at the start of every parse, including after each tool call and each new user turn, so unguarded side effects repeat, counters reflect parse count, and once-per-session work needs an explicit flag. The third trap is believing after_reasoning always runs. It does not: when an action is marked displayable, the engine exits the reasoning loop as soon as the model surfaces that output, so after_reasoning is skipped and any logic there is lost.

</Callout>

## What a consultant should walk away with

<KeyTakeaways>

- A prompt instruction is a suggestion the model may skip; anything you must enforce belongs in logic, a guard, or a gate
- The parse, not the user turn, is the unit of execution, so before_reasoning runs every pass and once-per-session work needs a guard flag
- Never let the model set an available when gate variable; it needs a deterministic set path in the logic instructions
- An action marked displayable exits the reasoning loop early, so after_reasoning is skipped; put guaranteed logic in the next subagent's before_reasoning

</KeyTakeaways>
