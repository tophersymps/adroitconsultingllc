# Lesson 35: Connecting an Agent to Channels: Lightning, Messaging, Email, Voice, and Slack

A delivery lead demos a service agent in the Agentforce panel and it looks excellent: it reads the open case, finds the order, and drafts a reply the whole room approves. Energised, the stakeholder asks for the same thing in Slack for the internal support team and on the company website for customers, and the lead promises all three by Friday. On Friday the panel still works, the website mostly works, and Slack is a blank where the agent should be, because the agent was built as a service agent and the Slack connection only attaches to an employee agent. Nobody wrote anything wrong. The channel was never a checkbox on the agent; it was a decision about the agent's type made weeks earlier.

The cause is that a channel is not a skin you pull over a finished agent. Each channel is reached through a connection, every connection declares which agent types it supports, and the connection also tells the agent what the surface can carry. So the same request for Slack and for a website resolves to two different agent types with two different connection sets, and assuming one agent can go anywhere is the assumption that breaks at demo-plus-two days. This is why the exam treats channel connection as a deliberate choice and not a deployment afterthought.

This lesson serves requirement ag-5a in the AI Agents domain, which carries 35 percent of the exam. You will learn how connections reuse one agent across surfaces, which channels the service agent and the employee agent each own, and how email and voice differ from live chat in ways that change the agent you should build. Slack here is one channel among several; the focus is how an agent connects to it, not how to administer it.

## Deep Dive

### A connection is how one agent reaches several surfaces

A channel is the surface where a user meets the agent, and connections are how you get one agent onto several surfaces without rebuilding it. In Agentforce Builder you build the agent once and then add connections, each connection pointing at a channel [^1]. The point of connections is exactly that reuse: an agent that handles a job in the Agentforce panel can be added to Slack, messaging, email, or voice by attaching the matching connection rather than authoring a second agent. Salesforce frames connections as the mechanism that scales agent development, letting you build once and add the agent to multiple channels [^1].

Not every connection is available to every agent, because channel support varies by agent type. The Agentforce Service agent and the Agentforce Employee agent are the two broad types, and a connection that a service agent supports may not exist for an employee agent and the reverse [^1]. This single constraint quietly governs the whole design. Before you promise a channel, you confirm that the agent's type supports a connection to that channel, because a correct agent of the wrong type still cannot reach the surface you named.

Each connection also carries behind-the-scenes instructions that help the agent reason and respond for its channel, and it bundles the adaptive response formats the channel can render [^1]. So a connection is doing two jobs at once: it is the plumbing that carries the conversation to a surface, and it is the context that tells the agent what that surface can do. Keeping both jobs in mind is what turns channel selection from a deployment chore into a design decision.

### Channel support varies by agent type, so the agent type gates the channel

The cleanest way to hold this objective is to start from the agent type and read outward, because the type gates the channel. The Agentforce Service agent connects to the customer-facing surfaces: messaging, service email, telephony, and web chat. The Agentforce Employee agent connects to the surfaces where employees already work: the Agentforce panel in Lightning Experience, the Salesforce mobile app, Slack, and Enhanced Web Chat for employees [^2]. Pick the wrong type and the connection you want simply is not in the list, which is a harder failure than a misconfiguration because it is a rebuild.

The messaging connection is the broadest service surface, and it carries Enhanced Chat along with the other enhanced messaging channels, including Enhanced Web Chat, Enhanced In-App Chat, WhatsApp, Facebook Messenger, Apple Messages for Business, LINE, and a bring-your-own-channel path [^2]. A single messaging connection therefore covers many places a customer meets the brand, which is the reuse advantage in concrete form. The channel's own setup, not the connection alone, is what publishes the agent to a specific surface, so the connection and the channel deployment are two halves of one job.

The employee surfaces are reached differently because the audience is different. The Agentforce panel in Lightning Experience and the Salesforce mobile app are employee surfaces, and deploying an employee agent there is largely a matter of activating the agent [^1]. Slack is the collaboration surface for an employee agent, and Enhanced Web Chat can also carry an employee agent [^2]. Read every connection's supported agent types before you promise a channel, and the channel-to-type mapping becomes the first line of your design.

### The service agent owns the customer-facing channels

The service agent connects to the customer-facing channels, and the exam expects you to know each connection's shape. The messaging connection carries Enhanced Chat and the other enhanced messaging channels, so it is the connection behind nearly every text surface a customer uses. The service email connection routes to Email-to-Case, so an Agentforce Service agent can respond autonomously to customer email inquiries [^2]. The telephony connection routes voice conversations to a voice-enabled agent through Agentforce Voice, and marketing email runs over unified messaging [^1].

Salesforce recommends a specific design discipline here: for the best customer experience, build a separate service agent for the telephony and service email connections rather than folding them into one agent, because those channels behave differently enough that a shared agent is harder to tune [^1]. That recommendation is the seed of the next lesson. Email and voice do not carry the same session, the same identity, or the same context as a live chat, so an agent tuned for one will be off-balance on the others unless you build for the difference.

Read a service-agent scenario for the channel behind the requirement. Autonomous answers to customer email points at the service email connection through Email-to-Case. A voice call points at telephony and Agentforce Voice. A chat window on a website points at Enhanced Web Chat under the messaging connection. Naming the connection is the concrete answer, and naming the agent type it requires is the reasoning that earns the point.

### The employee agent owns the places employees already work

The employee agent connects to the places employees already work, and the split from the service agent is what most scenario questions probe. The Slack connection lets an Agentforce Employee agent collaborate with the team inside Slack, so the agent meets employees in their collaboration tool rather than in a customer window [^2]. The Agentforce panel in Lightning Experience and the Salesforce mobile app are employee surfaces, and Enhanced Web Chat can also carry an employee agent [^2]. When a requirement says the agent should help employees inside their collaboration tool, that is the Slack connection on an employee agent.

The reason this matters for selection is that choosing a channel also constrains the agent type you are deploying. Slack carries employee agents, and the messaging and email connections carry service agents, so the two worlds do not share one agent by default. A requirement that asks for the agent to appear both in Slack for staff and on the website for customers is a requirement for, at minimum, an employee agent and a service agent, each with its own connection set, because no single connection spans both audiences.

Slack is taught here strictly as a channel, as one of the surfaces an employee agent can be attached to. The connection is added to the agent in Agentforce Builder, and the Slack-side setup finishes the job so the agent appears where the team collaborates [^3]. What the exam cares about is that Slack lives on the employee side and that attaching it requires the right agent type, not the administrative detail of the collaboration tool itself.

### Email is turn-based, not a live chat in a new skin

The email channel changes the shape of the conversation, and the exam tests that you know it. A service email connection routes through Email-to-Case, so an inbound customer email becomes a case and the agent responds to it [^2]. Email is turn-based rather than a live back and forth, which means the agent is not holding an open session the way a chat does. A message arrives, the agent answers it, and the interaction is closed until the next message brings a fresh one.

The channel's adaptive response formats reflect that cadence. The service email connection includes a Rich Service Email Response format, while the marketing email connection carries Marketing Email Text with inputs such as the email signature and disclosure [^2]. These formats are how the connection tells the agent what an email can carry, which is different from what a chat window can render. Getting the format right is part of connecting the channel, not an optional polish.

When you connect the email channel, expect the agent to answer a message rather than to run a live conversation, and design its instructions for that cadence. An agent whose instructions assume it can ask a clarifying question and wait for the reply in the same open session will under-perform on email, because the wait is a real elapsed gap and the next message starts fresh. Email is a channel where the agent must be complete in one turn, and that expectation belongs in the design before the connection is added.

### Voice changes the medium, not just the surface

Voice is the channel that changes the medium, not just the surface. A telephony connection routes calls to a voice-enabled service agent using Agentforce Voice, and before it works you choose a telephony provider, because voice-enabled agents sit on top of a contact-center telephony layer rather than a text surface [^4]. The connection optimizes the agent for handling voice calls, and you confirm the agent's language settings and voice settings as part of adding it [^5].

The agent still reasons the same way, but the interaction is audio and real time, so responses that assume a screen, rich cards, or typed input do not translate. There is no place to click a button on a phone call, and a response designed around a link or a picker has nowhere to live. Salesforce positions Agentforce Voice as replacing static IVR hierarchies with dynamic, intent-driven conversations, which is a strong signal that the agent is expected to converse and decide, not to read a menu of options [^4].

Connecting a channel therefore sets both where the agent runs and what kinds of responses it can render there. For voice that means real time, audio, and no rich surface, so the agent's instructions and actions have to be re-read for a medium without a screen. An action that returns a structured record page, useful in the panel, is meaningless on a call, and the format declarations on the connection are how the platform keeps that mismatch from reaching a caller.

### Adaptive response formats are what a channel can render

Each connection declares which adaptive response formats it supports, and this is the mechanism behind the phrase that a channel tells the agent what it can carry. The messaging connection carries Rich Choice Response, Rich Link Response, and a Time Picker, with the Time Picker tied to Apple Messages for Business [^2]. The service email connection carries a Rich Service Email Response format, and the marketing email connection carries Marketing Email Text with inputs such as the email signature and disclosure [^2]. Telephony has no rich card surface at all.

These declarations exist because rich responses are not universal. A choice button, a link card, or a time picker renders on a messaging surface and does not render on a phone call or in a plain email body. When an action returns a rich choice the channel cannot render, the customer sees a degraded or empty result, and that is a real failure mode, not a theoretical one. The connection's format list is your map of what is safe to return on that surface.

So connecting a channel is a two-part promise: the agent type must support the connection, and the actions must fit the formats the connection declares. Read a scenario that describes an agent returning a rich card on a voice call as a channel-fit failure, and the fix is either a different response shape for that channel or a different channel. The connection is where that fit is declared, which is why the exam ties channel selection to the response formats rather than to the agent's text alone.

## Exam Traps

Three traps dominate this objective. The first is believing any agent can connect to any channel: channel support varies by agent type, so a connection that a service agent supports may not be available to an employee agent, and the supported types have to be checked before a channel is promised [^2]. The second is believing Slack carries a service agent: Slack is an employee surface connected to an Agentforce Employee agent, while the messaging and email connections carry service agents, so asking for Slack changes the agent type you deploy [^3]. The third is believing email behaves like live chat: the service email connection routes through Email-to-Case and is turn-based, so the agent answers messages rather than holding an open live session, and instructions written for a live chat will under-perform there [^2].

## What a consultant should walk away with

Start from the agent type, because it gates the channel. Build the agent once, then add connections, each pointing at a channel, and confirm the connection supports the agent type before you promise a surface. The service agent owns the customer-facing channels: messaging and the enhanced channels under it, service email through Email-to-Case, telephony for voice, and marketing email over unified messaging. The employee agent owns the places employees work: the Agentforce panel and mobile app, Slack, and Enhanced Web Chat. Reach for a separate service agent for email and voice, as Salesforce recommends, because those channels behave differently from chat. Treat email as turn-based and voice as audio with no screen, and read each connection's adaptive response formats as the list of responses that channel can safely render, because a rich card on a phone call or in a plain email body is a fit failure waiting to happen.
