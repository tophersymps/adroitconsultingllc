# Lesson 7: Grounding Techniques: What Grounds a Prompt and Where It Lives

A service team ships an agent that is supposed to answer policy questions from their knowledge base, and the first week of answers is confident, fluent, and wrong. The agent quotes a refund window the company retired two years ago and invents a phone number that never existed. Nothing in the prompt template was broken. The template had no grounding at all, so the model answered from its training data, and training data does not know your refund policy. The team's instinct was to rewrite the instructions, but wording was never the problem. Missing data was.

The cause is a distinction the exam builds half this domain around: what a prompt says versus what a prompt is given. Grounding is the act of connecting a prompt to the data relevant to the request, so the model answers from your facts instead of only from what it learned during training[^2]. Without grounding, a model's response drifts toward generic phrasing and plausible but wrong specifics. The prompt template is the vehicle, and the grounding resources you insert into it are what make the answer true.

This lesson maps the grounding techniques and, more importantly, the job each one is built for: a merge field for a known value on the associated record, a Flow or Apex resource for a value that must be computed or fetched, a Data 360 retriever for meaning-based search over a large corpus, and the Agentforce Data Library for a quick single-source library. For each technique you will look at four things: what it retrieves, where that data actually lives, how fresh it can be, and what choosing it wrongly costs. The exam cares because grounding questions are scenario questions, they name a job and expect you to name the technique, and the wrong options are almost always the other techniques wearing the same label.

<TLDR>

- Name the job first, then the technique: merge field, Flow or Apex, retriever, or data library
- Grounding is a governed substitution in which Prompt Builder replaces placeholder resources with real org data
- Check four beats per technique: what it retrieves, where data lives, when it goes stale, what it costs

</TLDR>

## Deep Dive

### Grounding is a substitution, and the resolved prompt is what reaches the model

In Prompt Builder, grounding happens through resources you insert into the template: merge fields that reference record fields and related lists, and also flows, Apex actions, Data 360 data model objects, and uploaded files[^1]. An inserted resource acts as a placeholder, and at run time Prompt Builder replaces it with the org's real data.

That replacement step is called prompt resolution, and the resolved prompt, not the template text, is what reaches the LLM[^2]. The template is a set of instructions with holes in it; resolution fills the holes; the model only ever sees the filled result. This is why a template that previews wrongly will also run wrongly, and why reviewing the resolved prompt against a sample record is the only honest test before activation.

One property of this pipeline is worth holding onto for governance. The data that grounds the template stays in Salesforce, and the Einstein Trust Layer masks sensitive values such as personally identifiable information before anything leaves, under a zero-retention agreement so the prompt is not stored or used for training[^1]. Grounding is therefore not the same as exporting your data to a model vendor. It is a governed substitution in which the model receives the specific context the template declares and nothing more, which is why the resources you choose decide both the answer quality and the security posture of the template.

### The merge field: a known value read straight off the associated record

Start with the cheapest technique, because most scenarios need nothing heavier. You associate the template with an object such as Account, Contact, or Case, then insert merge fields from that record, and you can also pull related list data from child records[^1]. A merge field retrieves a named field value, such as the account status or the contact title, and drops it into the prompt.

Follow the four beats. What it retrieves: a specific field you name, deterministically, plus child records through related lists. Where the data lives: on the record itself, inside your org, under the platform's sharing rules and field-level security. When it goes stale: never, by design, because the merge field is resolved at run time against the current field value, so it always reflects the record as it stands at the moment of the run. What the wrong choice costs: a merge field cannot search, and it only reaches fields on the associated record, so asking it for a value that lives on another object or inside a document is a requirement it cannot carry.

That last limit is the whole reason the other techniques exist. If the value you need already exists on the associated record and changes slowly, a merge field is correct and anything heavier is wasted effort and added failure surface. A merge field is also the most auditable technique, because a reviewer can point at the exact field it reads, which matters when the generated output feeds a compliance-sensitive workflow and someone later has to explain where a claim came from.

### The Flow or Apex resource: the value that must be computed or fetched

When the value must be produced rather than read, you reach for a Flow or an Apex resource, and the setup rules decide whether a template will even accept the resource. A prompt template works with Apex or flows whose required inputs are a subset of the template's inputs. For flows, all inputs are considered required and must be present in the template, while for Apex, inputs are optional unless annotated as required, and Apex and flows with no parameters work with all prompt templates[^1]. So a Flow resource binds tightly to the template's inputs, and an Apex action is the more forgiving of the two.

Again, the four beats. What it retrieves: a value assembled by logic, such as a loyalty tier computed from spend, a price fetched from a different object, or a formatted string the model should describe rather than derive. Where the data lives: whatever the Flow or Apex can reach under its own run context, which can be wider than the associated record, and that reach is exactly the security consideration a reviewer must check. When it goes stale: it does not, because the logic runs at run time and returns a current value. What the wrong choice costs: a run-time processing step on every execution and a piece of logic you own and maintain, so using it for a value that already sits on the record is needless complexity.

The reason the technique earns its keep is cross-object reach and computation. A discount computed from purchase history on a different object is a Flow or Apex job, because a merge field cannot reach across objects and cannot compute. The reason to prefer a merge field whenever it will do is that every Flow or Apex resource is another moving part that can fail, and a template with fewer moving parts is easier to trust in production and easier to hand to the next consultant who inherits it.

### The Data 360 retriever: meaning-based search over an index

The third technique is a Data 360 retriever, the mechanism behind retrieval augmented generation[^7]. When content is large or unstructured, such as Knowledge articles, documents, or call transcripts, you index it. Data preparation for retrieval involves loading, chunking, vectorizing, and storing the content in a search-optimized way: Data 360 uses a vector data store for unstructured data, and a search index holds the chunked and vectorized data that a retriever can search[^3]. A retriever queries that index at run time and returns the most relevant passages to the LLM.

The four beats are more involved here than for a merge field. What it retrieves: passages or chunks matched by meaning, not one named field, so it can return content you never explicitly pointed at. Where the data lives: in a search index defined in a data space and associated with a data model object, inside Data 360 rather than on the record[^3]. When it goes stale: the index is refreshed on an indexing schedule, so the retriever serves whatever the last indexing run captured, and a fact that changed since then is served as if it were current. What the wrong choice costs: slower and costlier setup than the other techniques, plus a real freshness risk that no amount of prompt rewording fixes.

Two operational details make the retriever safe to use. First, retrievers adhere to the data governance policies set up for your data, with row-level access checks to make sure users have access to the data and knowledge the retriever returns[^3], so access is enforced in the retrieval step rather than left to the model. Second, retrievers are versioned and only one version can be active at a time[^3], which mirrors the activation discipline you apply to the template itself. Retrievers can also cite their sources, so a citation links the generated answer to the content it drew from, which is how you let a reader verify a claim rather than trust it[^3].

### Retriever types map to the shape of the question

Retriever types map to the shape of the question, and the exam expects you to match them. An individual retriever searches one search index, and to build one you select its search index, define filters, and specify what information it returns[^3]. Across matches you choose the retriever type that fits the question, and in Prompt Builder the ones you can insert are the individual retriever and the ensemble retriever built in AI Models, plus the web retriever created by an Agentforce Data Library[^4]. An ensemble retriever is a collection of individual retrievers. When it runs, it executes them, combines their results into a single list, reranks that list by relevance, and returns only the most relevant information, which fits a question whose answer is blended across systems[^3].

Two further flavors round out the set. A custom SQL retriever is defined with SQL queries directly in the retriever interface, without switching between tools, which suits a builder who wants to query model objects, data lake objects, and calculated insights explicitly[^3]. A dynamic retriever uses placeholders that accept values at run time from the prompt template, so the same retriever can answer a question scoped to a particular id or region[^3]. The reading rule that falls out is direct: one focused index points at an individual retriever, a question whose answer is blended across several at an ensemble retriever, an explicit structured query at a custom SQL retriever, and a run-time-scoped question at a dynamic retriever[^3].

### The Agentforce Data Library and the full Data 360 setup are not the same job

Two ways to stand up retrieval look similar and differ in cost, so keep them apart[^5]. The Agentforce Data Library is the fast path: it uses grounding to index your knowledge articles and fields, your file uploads, or your web sources, so an agent knows which information to base responses on[^6]. It requires Data 360 to be set up, and data libraries consume Data 360 credits[^6]. The fuller Data 360 setup takes longer, because it involves ingestion, modeling, and identity resolution, but it supports multiple sources through ensemble retrievers and data graphs, harmonizes the data into unified profiles, and can ground the agent in real-time and zero-copy data[^5].

The trade-off is a scope decision, and the four beats make it concrete. What each retrieves: the Data Library returns from the single source you assigned it, while the full setup can return from many sources at once. Where the data lives: the Data Library indexes knowledge, files, or web content, while the full setup indexes harmonized profiles and real-time sources. When it goes stale: both depend on an indexing schedule for the indexed sources, and only the full setup reaches real-time data. What the wrong choice costs: choosing the Data Library for a multi-source, harmonized requirement under-builds and forces a later migration, while choosing the full Data 360 setup for a single Knowledge library over-builds and burns setup time and credits the requirement never needed.

### Worked scenario: the policy bot that needed two techniques

Return to the opening scene with a clear requirement. A service agent must answer policy questions from a knowledge base, and separately must always state the customer's current account status, which is a field on the Contact. Two jobs, so two techniques, and the failure comes from treating them as one.

The policy answers live in unstructured articles and must be matched by meaning, because the customer's wording will not match the article title, so the technique is a Data 360 retriever over the indexed articles, with the index built first and the retriever configured to the right data space and returned fields[^3]. The account status is a known field on the associated Contact, so the technique is a merge field, which reads it deterministically at run time[^1]. The wrong answer is to fetch the account status with the same retriever, because a retriever matches by meaning and returns passages, while the status is a single exact value that a merge field returns exactly and cheaply. Using a retriever for a known field is both slower and less reliable, and using a merge field for the policy answers is impossible, because a single field cannot search a corpus.

### Name the job first, and the technique follows

Read the scenario, name the requirement, then name the technique. A field value already on the associated record is a merge field. A value computed or fetched across objects is a Flow or Apex resource. A meaning-based search over a large or unstructured corpus is a Data 360 retriever, with retriever type following the shape of the question. A quick single-source Knowledge or file library is the Agentforce Data Library[^2].

A retriever dressed up as a field lookup, or a Flow offered for a value that already exists, sounds reasonable until you ask what the requirement actually needs. Naming the job first is what separates a correct answer from a plausible one, and running the four questions on each candidate, what it retrieves, where the data lives, when it goes stale, and what the wrong choice costs, is what makes the job name reliable rather than a hunch.

### The build sequence in six steps

<Steps>

<Step title="Open Einstein and then Prompt Builder">

In Setup, open Einstein and then Prompt Builder, or open Prompt Builder from the app launcher, and create a new prompt template.

</Step>

<Step title="Choose the template type">

Choose the template type and associate it with an object such as Account or Case; for a field generation template, also select the field to complete.

</Step>

<Step title="Use the Insert Resource button">

In the Prompt Template Workspace, use the Insert Resource button to add merge fields, related lists, flows, Apex, Data 360 data model objects, or files as grounding.

</Step>

<Step title="Open Data 360">

For retrieval grounding, open Data 360 and go to Agentforce Studio, then Data, then Retrievers, and create a retriever over a search index you have built.

</Step>

<Step title="Select the data space">

On that retriever, select the data space, the source object, the search index, the fields to return, and enable citation settings so the agent can show sources.

</Step>

<Step title="Click Save and Preview">

Back in the template, click Save and Preview, pick a sample record, and review the resolved prompt to confirm every placeholder was replaced with real data.

</Step>

</Steps>

## Exam Traps

<Callout kind="warning">

Three misconceptions recur. The first is believing grounding means feeding the model all your data. Grounding means pulling the specific, relevant data into the resolved prompt, so dumping the whole record or the whole library is a different failure, not grounding. The second is believing a retriever stores a live copy of the data. The search index holds chunked, vectorized content that refreshes on an indexing schedule, so retrieval freshness depends on that schedule and not on the moment of the question. The third is believing merge fields and retrievers are interchangeable. A merge field pulls a known field value deterministically, while a retriever performs semantic search over an index and can return passages you did not name, so a scenario needing a specific known field is a merge field, not a retriever.

</Callout>

## What a consultant should walk away with

<KeyTakeaways>

- A known value on the associated record is a merge field: it resolves at run time and is read exactly.
- A value computed or fetched across objects is a Flow or Apex resource, current but with a run-time step you maintain.
- A Data 360 retriever matches by meaning over an index, so its freshness follows the indexing schedule.
- A quick single-source Knowledge or file library is the Agentforce Data Library; a multi-source, harmonized, real-time need is the fuller Data 360 setup.

</KeyTakeaways>
