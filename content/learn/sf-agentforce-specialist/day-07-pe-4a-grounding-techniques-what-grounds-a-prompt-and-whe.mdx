# Lesson 7: Grounding Techniques: What Grounds a Prompt and Where It Lives

A service team ships an agent that is supposed to answer policy questions from their knowledge base, and the first week of answers is confident, fluent, and wrong. The agent quotes a refund window the company retired two years ago and invents a phone number that never existed. Nothing in the prompt template was broken. The template had no grounding at all, so the model answered from its training data, and training data does not know your refund policy. The team's instinct was to rewrite the instructions, but wording was never the problem. Missing data was.

The cause is a distinction the exam builds half this domain around: what a prompt says versus what a prompt is given. Grounding is the act of connecting a prompt to the data relevant to the request, so the model answers from your facts instead of only from what it learned during training[^3]. Without grounding, a model's response drifts toward generic phrasing and plausible but wrong specifics. The prompt template is the vehicle, and the grounding resources you insert into it are what make the answer true.

This lesson maps the grounding techniques and, more importantly, the job each one is built for. A merge field for a known value on the associated record, a Flow or Apex resource for a value that must be computed or fetched, a Data 360 retriever for meaning-based search over a large corpus, and the Agentforce Data Library for a quick single-source library. The exam cares because grounding questions are scenario questions: they name a job and expect you to name the technique, and the wrong options are almost always the other techniques wearing the same label.

## Deep Dive

### Grounding is a substitution, and the resolved prompt is what reaches the model

In Prompt Builder, grounding happens through resources you insert into the template: merge fields that reference record fields and related lists, and also flows, Apex, Data 360 data model objects, and uploaded files[^2]. An inserted resource acts as a placeholder, and at run time Prompt Builder replaces it with the org's real data.

That replacement step is called prompt resolution, and the resolved prompt, not the template text, is what reaches the LLM[^3]. The template is a set of instructions with holes in it; resolution fills the holes; the model only ever sees the filled result. Preview shows you that result, which is the only honest test of your grounding.

### The merge field is the cheap, deterministic default

The simplest technique is the merge field. You associate the template with an object such as Account, Contact, or Case, then insert fields from that record. A merge field is deterministic and cheap: it pulls a known value, such as the account status or the contact title, and drops it into the prompt. It can also pull related list data from child records[^2].

Its ceiling is reach, because a merge field only sees fields on the associated record. If the value already exists there and changes slowly, a merge field is right and anything heavier is wasted effort.

### A Flow or Apex resource is for values that must be computed or fetched

The next technique is a Flow or Apex resource, used when the value must be computed or fetched rather than read off the record. A template-triggered prompt flow runs and returns data or instructions the template then grounds with, and Apex does the same when the logic is beyond Flow[^2]. Use it to compute a loyalty tier from spend, fetch a different object, or assemble a value the model should describe.

The trade-off is real: a Flow or Apex adds a run-time step and is something you own and maintain, so reserve it for values that need logic or a cross-object lookup. A discount computed from purchase history on another object is a Flow or Apex job, because a merge field cannot reach across objects and a retriever is the wrong shape for an exact computed number.

### A Data 360 retriever matches by meaning over an index

The third technique is a Data 360 retriever, the mechanism behind retrieval augmented generation. When content is large or unstructured, such as Knowledge articles, documents, or transcripts, you index it: Data 360 splits it into chunks, converts the chunks into vector embeddings, and stores them in a search index. A retriever queries that index at run time and returns the most relevant passages[^5].

This is the technique for matching on meaning rather than exact keywords. An agent that must answer policy questions from Knowledge articles, where the customer's wording never matches the article title, needs a retriever, not a merge field, because the retriever finds passages by semantic similarity and a field lookup cannot.

### Retriever types map to the shape of the question

Retriever types map to the question. A structured retriever runs over records, a vector retriever over unstructured text, and a hybrid retriever combines semantic and keyword matching. An ensemble retriever searches several sources in parallel, which fits a question whose answer is blended across systems[^5].

Read the scenario and ask what content holds the answer. Records point at a structured retriever, free text at a vector retriever, mixed wording at a hybrid, and a question spanning several systems at an ensemble, which combines the individual results into one ranked list.

### The Agentforce Data Library and the full Data 360 setup are not the same job

Two ways to stand up retrieval look similar and differ in cost. The Agentforce Data Library is the fast path: it can hold Knowledge articles, uploaded files, open web search, or a custom retriever, but a single library holds one data source, and it has no real-time or zero-copy capability[^6]. The fuller Data 360 setup takes longer, because it involves ingestion, modeling, and identity resolution, but it supports multiple sources through ensemble retrievers and data graphs, and harmonizes the data into unified profiles.

So the split is a scope decision. A quick, single-source Knowledge or file grounding is a Data Library job, right when speed to value beats breadth. A multi-source, harmonized, real-time grounding is a Data 360 job, worth the longer setup only when the requirement needs that reach.

### Name the job first, and the technique follows

Read the scenario, name the requirement, then name the technique. A field value already on the associated record is a merge field. A value computed or fetched across objects is a Flow or Apex resource. A meaning-based search over a large or unstructured corpus is a Data 360 retriever. A quick single-source Knowledge or file library is the Agentforce Data Library[^3].

Naming the job first is what separates a correct answer from a plausible one, because the wrong options are almost always the other techniques wearing the same label. A retriever dressed up as a field lookup, or a Flow offered for a value that already exists, sounds reasonable until you ask what the requirement actually needs.

## Exam Traps

Three misconceptions recur. The first is believing grounding means feeding the model all your data. Grounding means pulling the specific, relevant data into the resolved prompt, so dumping the whole record or the whole library is a different failure, not grounding. The second is believing a retriever stores a live copy of the data. The search index holds chunked, vectorized content that refreshes on an indexing schedule, so retrieval freshness depends on that schedule and not on the moment of the question. The third is believing merge fields and retrievers are interchangeable. A merge field pulls a known field value deterministically, while a retriever performs semantic search over an index and can return passages you did not name, so a scenario needing a specific known field is a merge field, not a retriever.

## What a consultant should walk away with

Name the job before you name the tool. A known value on the associated record is a merge field. A value that must be computed or fetched across objects is a Flow or Apex resource. A meaning-based search over a large or unstructured corpus is a Data 360 retriever, and a retriever type follows from the shape of the question. A quick, single-source Knowledge or file library is the Agentforce Data Library, and a multi-source, harmonized, real-time need is the fuller Data 360 setup. Ground the specific data the answer needs, and remember that the resolved prompt, not the template, is what the model reads.
