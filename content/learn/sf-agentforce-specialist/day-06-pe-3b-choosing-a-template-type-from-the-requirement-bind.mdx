# Lesson 6: Choosing a Template Type from the Requirement: Bindings and Wrong-Type Traps

A sales-ops analyst must draft a personalized outreach email for each of her company's partners. She opens Prompt Builder, sees the output is an email, chooses Sales Email, and then discovers the type will not accept her custom Partner object at all, because Sales Email binds to a Contact or a Lead[^1]. Her instinct, that the destination names the type, was half right. The other half is the binding, and the binding can override the destination. She rebuilds the whole template in Flex, the type built for her requirement, because nothing on the screen told her to check the input side before she committed.

The cause is that a requirement carries two facts, not one, and the second is easy to skip when the first is loud. Where the output goes narrows the type. How many and which objects the prompt must read settles it, and when the two disagree the binding wins. A requirement that must combine objects the destination type cannot join has already ruled that type out, no matter how well the output description fits.

This lesson takes the types you learned and turns them into a decision procedure you can run on any scenario in the exam. Read the destination, then read the inputs, then check the entry point the requirement implies, and the type falls out. The exam cares because the wrong options are almost always a correct-sounding type paired with a binding it does not have, and the only way to see the mismatch is to check the binding deliberately.

## Deep Dive

### Two questions, asked in this order, resolve almost every scenario

Two questions in this order resolve almost every type question. First, where does the generated output go: into a field on a record, into an email, into a summary view, or somewhere custom. Second, how many objects must the prompt read to produce it. The first question is a filter that removes most candidates. The second is the tie-breaker, and it is also a veto, because a requirement that must join objects a type cannot bind has already eliminated that type.

Ask them in that order and you will not reach for a type whose binding cannot carry the requirement[^1]. Skip the first question and you compare bindings that do not matter yet, because you have not settled what the output is. Skip the second and you land on a type that reads well on the output side and then runs wrong on the input side, because the type is fixed at creation and carries its binding with it[^3]. The order is the discipline, and the exam is built to reward it.

### Start with where the output lands, because the requirement says it plainly

Work the destination first, because the requirement usually states it in plain words. Text that lands in a field on a specific record is Field Generation, bound to that record's object and run from a record page[^5]. A customer email anchored on a Contact or a Lead is Sales Email. An overview of one record meant for a human to read is Record Summary. Anything else, meaning open text used anywhere, is Flex.

The destination is often answerable from one sentence, which is why it comes first and why it feels decisive. It narrows the field to one or two candidates, but it rarely gives the final answer alone, because two different types can share a destination while binding different inputs. That gap is exactly what the second question closes, and closing it is where the exam separates a careful reader from a fast one.

### Then check how many objects feed it, because that vetoes types

Now work the input breadth, where the traps hide. Field Generation binds one object. Record Summary binds one object. Sales Email binds a Contact or a Lead, optionally one more object. Flex is the only classic type that defines its own resources and grounds with several objects, so it answers any prompt that must read across objects the others cannot join[^2].

The second question is both a tie-breaker and a veto. A requirement to combine several objects rules out every single-object type regardless of where the output goes. The binding is a hard limit set at creation, and the exam writes its wrong answers around a type that sounds right on the output and fails on the input. When two candidates survive the destination question, the one whose binding fits the objects is the one that ships.

### The classic traps the exam reuses

Four traps recur. Field Generation is wrong when the prompt must read several objects, since it binds one, so the type is Flex. Sales Email is wrong on an object that is not a Contact or a Lead, because the binding is fixed there. Record Summary is wrong when the requirement is to write into a field, because a summary is an overview, not a field value. And Flex is wrong when a standard type already fits, because it is more setup than the job needs, and the correct answer is the type built for the requirement[^1].

The fourth trap comes from under-reading the requirement and reaching for the general tool when a specific one was sitting right there. The other three come from reading only the output side and never checking the binding. Learn them as pairs: each trap names a type, the condition that makes it wrong, and the type that is right instead, so you recognize the shape rather than memorizing four separate sentences.

### Read the anchor object, not the noun, to split the two email types

One comparison decides more scenarios than any other, so make it explicit. Two types both produce a customer email, and the word email cannot choose between them. Sales Email anchors on a Contact or a Lead, optionally with one more object. Case Email Draft anchors on a Case. So an email requirement is settled only once you read the record the email is about, and the noun in the requirement is the wrong signal.

This is the trap in its most distilled form. A scenario asks for a personalized email, and the natural reach is Sales Email, but the scenario's anchor record might be a Case or a custom object. If the anchor is a Case, the type is Case Email Draft; if the anchor is anything the two email types cannot bind, then neither email type fits the requirement as stated, and a genuinely grounded email either resolves through Flex with the email composed from the output or tells you the requirement needs a different anchor. Read the anchor every time, because the noun misleads and the anchor is decisive.

### Entry points are set by the type, so the surface names the type

The type also gates the entry points. Field Generation surfaces on a record page, so a requirement that a user clicks a button and the field fills points there[^5]. Sales Email surfaces in the email composer. Record Summary is invoked by the Summarize Record action, which an agent or a Flow can call. Flex is invoked from a Flow, Apex, or a prompt action[^2].

So a requirement that names its invocation point has already told you something. A record-page button leans to Field Generation, the composer to Sales Email, and a Flow element or an Apex call to Flex. A type that cannot be reached from the named surface is the wrong answer, because a template you cannot call from the required place cannot ship. When the destination and the objects leave a tie, the entry point usually breaks it, which is why it is the last of the three questions rather than an afterthought.

### Flex grounds up to five objects, and a bigger requirement is a design signal

One ceiling is worth stating precisely, because the exam uses it as a distractor. Flex is the multi-object type and it grounds with up to five resources, so a requirement that names several objects fits Flex as long as it stays within that set[^2]. A requirement that genuinely must read more objects than Flex carries is not a cue to find a different classic type with a wider binding, because none exists among the four. It is a signal that the prompt, or the architecture around it, needs rethinking.

Within the classic four, the meaningful limits are the single-object binding of Field Generation and Record Summary, and the Contact-or-Lead binding of Sales Email. State those bindings precisely on the exam, because the wrong options are usually a correct-sounding type paired with a binding it does not have. The exact number for Flex matters less than the fact that it is finite, and that exceeding it is a design problem rather than a type-selection problem.

### Worked scenario: the requirement with three plausible answers

Read this requirement slowly. An account team wants a grounded summary of an Account that a service rep can read before a call, combining the Account's open cases and its recent activity. Three answers look plausible: Record Summary, because the word summary is present; Field Generation, because someone might want the text saved on the record; and Flex, because two objects are involved.

Resolve it in order. The destination is a readable overview for a human, which points at Record Summary and away from a record field, so Field Generation is out on the destination question. Then the inputs: the requirement combines the Account with its open cases and recent activity, so it reads more than one object, and Record Summary binds a single object. The object count vetoes Record Summary. That leaves Flex, the type that defines its own resources and can ground with several objects.

The wrong answer is Record Summary, chosen because the word summary appears in the requirement and matched the destination exactly. It is wrong for a precise reason: Record Summary binds one object, and the requirement is explicitly cross-object. A reader who stops at the destination picks it and never sees the veto. The lesson is that the loudest word in a requirement is often the destination, and the destination is only half of the decision.

### A second pass: when the loudest word is the wrong type

Take a shorter requirement. A team wants a summary of each Case written onto the Case record and refreshed when an agent clicks a button. The loud words are summary and click a button. The word summary pulls a reader toward Record Summary, and the button pulls toward Field Generation. Resolve it with the two questions. The destination is a field on the Case record, because the text is written onto the record rather than read as a standalone overview, and a destination of a field points at Field Generation[^5]. The inputs are a single object, the Case, which Field Generation binds. Both questions agree, so the type is Field Generation, and Record Summary is the wrong answer despite the word summary.

The general habit is to distrust the nouns and trust the mechanics. A requirement uses the word summary for a field value, the word email for a Case, and the word report for a generated explanation. None of those nouns decide the type. The destination and the object count decide it, and the nouns only tell you what the business calls the thing. Translate the business noun into one of the four destinations before you let it influence the choice, and the misleading word loses its pull.

### The drill: destination, inputs, entry point

Here is the drill. Name the destination, then the inputs, then the entry point the requirement implies, and the type falls out. A field on one record is Field Generation. An email to a contact or lead is Sales Email. An overview of one record is Record Summary. Open text from several objects, called from a Flow or Apex, is Flex.

And if the requirement names a standard business surface, such as a knowledge answer or a call wrap-up, check whether a standard type already exists before you build a Flex template to imitate it[^4]. Run the drill on every scenario, in the same order, and the choice stops being a guess and becomes a procedure you can defend in a design review as well as on the exam. The order matters as much as the questions, because the destination saves you work and the inputs keep you honest.

## Exam Traps

Three misconceptions carry the trap questions. The first is believing Flex is always the safe choice. It is the general type, but choosing it when a standard type already fits means more setup than the job needs, so the type built for the requirement is the correct answer. The second is believing Sales Email works on any object. Its binding is a Contact or a Lead, optionally with one more object, so a requirement anchored on another object needs Flex instead. The third is believing a single-object type can join records. Field Generation and Record Summary bind one object, so a requirement that must combine several objects rules them out no matter where the output goes. The common thread is that each trap catches the reader who stops at the loud word and never checks the binding, so checking the binding is the single habit that defuses all three.

## What a consultant should walk away with

Destination first, inputs second, entry point last. The output tells you a short list and the binding vetoes the wrong members of it, so read the requirement in that order before you choose. Keep the four bindings at your fingertips: Field Generation and Record Summary on one object, Sales Email on a Contact or a Lead, and Flex on the several objects you define yourself. Read the anchor object rather than the noun to split the two email types, and when a standard business type already covers the surface, use it rather than building a Flex template to do the same work.
