# Lesson 6: Choosing a Template Type from the Requirement: Bindings and Wrong-Type Traps

A sales-ops analyst must draft a personalized outreach email for each of her company's partners. She opens Prompt Builder, sees the output is an email, chooses Sales Email, and then discovers the type will not accept her custom Partner object at all, because Sales Email binds to a Contact or a Lead[^1]. Her instinct, that the destination names the type, was half right. The other half is the binding, and the binding can override the destination. She rebuilds the whole template in Flex, the type built for her requirement, because nothing on the screen told her to check the input side before she committed.

The cause is that a requirement carries two facts, not one, and the second is easy to skip when the first is loud. Where the output goes narrows the type. How many and which objects the prompt must read settles it, and when the two disagree the binding wins. A requirement that must combine objects the destination type cannot join has already ruled that type out, no matter how well the output description fits.

This lesson takes the types you learned and turns them into a decision procedure you can run on any scenario in the exam. Read the destination, then read the inputs, then check the entry point the requirement implies, and the type falls out. The exam cares because the wrong options are almost always a correct-sounding type paired with a binding it does not have, and the only way to see the mismatch is to check the binding deliberately.

## Deep Dive

### Two questions, asked in this order, resolve almost every scenario

Two questions in this order resolve almost every type question. First, where does the generated output go: into a field on a record, into an email, into a summary view, or somewhere custom. Second, how many objects must the prompt read to produce it. The first narrows the type. The second settles a tie and also acts as a veto, because a requirement that must join objects a type cannot bind has already eliminated that type.

Ask them in that order and you will not reach for a type whose binding cannot carry the requirement[^1]. Skip the first and you compare bindings that do not matter yet. Skip the second and you land on a type that reads well and runs wrong.

### Start with where the output lands

Work the destination first, because the requirement usually states it plainly. Text that lands in a field on a specific record is Field Generation, bound to that record's object and run from a record page. A customer email anchored on a Contact or a Lead is Sales Email. An overview of one record meant for a human is Record Summary. Anything else, meaning open text used anywhere, is Flex.

The destination is often answerable from one sentence, which is why it comes first. It gives a short list. It rarely gives the final answer alone, because two types can produce text and the difference between them is what they read, not what they write.

### Then check how many objects feed it, because that vetoes types

Now work the input breadth, where the traps hide. Field Generation binds one object. Record Summary binds one object. Sales Email binds a Contact or a Lead, optionally one more object. Flex is the only classic type that defines its own resources and grounds with several objects, so it answers any prompt that must read across objects the others cannot join[^3].

The second question is both a tie-breaker and a veto. A requirement to combine several objects rules out every single-object type regardless of where the output goes. The binding is a hard limit, and the exam writes its wrong answers around a type that sounds right on the output and fails on the input.

### The classic traps the exam reuses

Four traps recur. Field Generation is wrong when the prompt must read several objects, since it binds one, so the type is Flex. Sales Email is wrong on an object that is not a Contact or a Lead, because the binding is fixed. Record Summary is wrong when the requirement is to write into a field, because a summary is an overview, not a field value. And Flex is wrong when a standard type already fits, because it is more setup than the job needs, and the correct answer is the type built for the requirement[^1].

The first three come from over-reading the output and ignoring the binding. The fourth comes from under-reading the requirement and reaching for the general tool when a specific one was sitting there.

### Entry points are set by the type, so the surface names the type

The type also gates the entry points. Field Generation surfaces on a record page, so a requirement that a user clicks a button and the field fills points there. Sales Email surfaces in the email composer. Record Summary is invoked by the Summarize Record action, which an agent or a Flow can call. Flex is invoked from a Flow, Apex, or a prompt action[^2].

So a requirement that names its invocation point has already told you something. A record-page button leans to Field Generation, the composer to Sales Email, and a Flow element or Apex call to Flex. A type that cannot be reached from the named surface is the wrong answer, because a template you cannot call from the required place is not one you can ship.

### Flex grounds up to five objects, and a bigger requirement is a design signal

One ceiling is worth stating precisely, because the exam uses it as a distractor. Flex is the multi-object type and it grounds with up to five objects, so a requirement that names several fits Flex as long as it stays within that set[^2]. A requirement that genuinely must read more objects than Flex carries is not a cue to find a different classic type with a wider binding, because none exists among the four. It is a signal that the prompt, or the architecture around it, needs rethinking.

Within the classic four, the meaningful limits are the single-object binding of Field Generation and Record Summary, and the Contact-or-Lead binding of Sales Email. State those bindings precisely on the exam, because the wrong options are usually a correct-sounding type paired with a binding it does not have.

### The drill: destination, inputs, entry point

Here is the drill. Name the destination, then the inputs, then the entry point the requirement implies, and the type falls out. A field on one record is Field Generation. An email to a contact or lead is Sales Email. An overview of one record is Record Summary. Open text from several objects, called from a Flow or Apex, is Flex.

If two types seem to fit, the single-object binding vetoes one of them. And if the requirement names a standard business surface, such as a knowledge answer or a call wrap-up, check whether a standard type already exists before you build a Flex template to imitate it[^1].

## Exam Traps

Three misconceptions carry the trap questions. The first is believing Flex is always the safe choice. It is the general type, but choosing it when a standard type already fits means more setup than the job needs, so the type built for the requirement is the correct answer. The second is believing Sales Email works on any object. Its binding is a Contact or a Lead, optionally with one more object, so a requirement anchored on another object needs Flex instead. The third is believing a single-object type can join records. Field Generation and Record Summary bind one object, so a requirement that must combine several objects rules them out no matter where the output goes.

## What a consultant should walk away with

Destination first, inputs second, entry point last. The output tells you a short list and the binding vetoes the wrong members of it, so read the requirement in that order before you choose. Keep the four bindings at your fingertips: Field Generation and Record Summary on one object, Sales Email on a Contact or a Lead, and Flex on the several objects you define yourself. When a standard business type already covers the surface, use it rather than building a Flex template to do the same work.
