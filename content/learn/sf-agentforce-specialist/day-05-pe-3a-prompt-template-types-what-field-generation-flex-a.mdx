# Lesson 5: Prompt Template Types: What Field Generation, Flex, and the Standard Types Bind

A consultant is asked to add a generated next-step suggestion to an Opportunity record page. She opens Prompt Builder, picks Field Generation because the word field is in the requirement, writes a clean prompt, activates it, and drops it onto the page. It works, until the same stakeholder asks for a recommendation that reads the Opportunity, its Products, and the Account at once. She opens the template and finds she cannot add the other two objects at all, because Field Generation binds to a single object[^1]. The fix is not a setting. It is a new template of a different type, a rebuilt prompt, and a fresh activation.

The cause is that the template type is not a preference you set later. It is the first decision in Prompt Builder, and it fixes three things at once: which objects the prompt can ground with, what inputs it accepts, and where it can be invoked[^3]. You choose it when you create the template, and you cannot change it afterward. Every later choice is downstream of that one click.

This lesson teaches the four classic types by what they bind and where they run, then widens the view to the standard, business-specific types Prompt Builder also ships. Read every requirement as two facts, where the output goes and how many objects feed it, and the type follows. The exam cares because Prompt Engineering is twenty percent of the blueprint, and the fit of a type to a requirement is one of its most repeated question shapes.

## Deep Dive

### The type is a contract you sign before you write a word

When you click New Prompt Template, the type dropdown is the first control you meet, and the most committing. The type decides which objects you can associate with the template, which grounding resources it accepts, what inputs it takes, and where in Salesforce it can be invoked[^3]. None of those are editable later. You cannot open a finished Field Generation template and reclassify it as Flex.

The type is therefore a fit question, not a feature tour. The exam hands you a requirement and expects two facts off it. Where does the generated output land: in a field on a record, in an email, in a summary view, or somewhere custom. And how many objects must the prompt read to produce it. Answer those two and the type falls out.

### Field Generation writes text into one record's field

Field Generation is the type for putting generated text into a field. It binds to a single object, and it is built to run from a record page, where a user clicks a button and the output fills a field on that record[^1]. The output is text that lands on the record, not an email and not a standalone summary. It fits completing a specific field on a specific record, such as a generated case description, an account tier note, or a next-step suggestion on an opportunity.

The single-object binding is the whole constraint. Because it reads one object, Field Generation cannot reach across several unrelated objects, and it is not designed to stand alone outside a record context. A requirement that names more than one source object is one Field Generation cannot carry, no matter where the output goes.

### Flex is the catch-all that defines its own resources

Flex is the type you reach for when the others do not fit, and it earns that role by being the most open of the four. It does not inherit a fixed object association. Instead you define the resources yourself, and it can ground with more than one object, which is what makes it the type for a prompt that reads from several places at once[^2]. A recommendation drawing on an account, its open opportunities, and a product catalog is the classic case.

Its outputs serve purposes the other types do not cover, and it is invoked from a Flow, Apex, or a prompt action rather than a record page button. When a requirement must combine several objects and the output goes somewhere custom, Flex is the answer.

### Sales Email is bound to a Contact or a Lead

Sales Email covers one use case: a personalized customer email grounded in record data. Its binding is narrow. It associates with a Contact or a Lead, optionally with one more object, and it surfaces through the email composer, though a Flow or Apex can also invoke it[^1]. If the output is an email to a customer and the anchor is a Contact or a Lead, Sales Email is the type.

If the requirement needs a different anchor object or a broader set of records, the binding is the wrong shape and Flex is the fallback. This is a favorite wrong answer on the exam, because Sales Email sounds general but is bound tighter than its name suggests.

### Record Summary explains one record, and the catalog runs wider than four

Record Summary is the type for summarizing a record. It binds to a single object and produces a rich-text overview of that record from its own data, and it is the type behind the Summarize Record action an agent or a Flow can call[^1]. A meeting-prep summary for an opportunity, or a quick case overview for a rep, is Record Summary work. It gives a reader an overview, which is not the same as filling a field.

The four classic types are not the whole catalog. Prompt Builder also ships standard, business-specific types such as Knowledge Answers for how an agent answers questions, Work Summary for the call or messaging wrap-up, and Case Summary for a case overview[^1]. These are customized rather than built from scratch. Recognize one when a scenario names its exact surface, and place everything else into the classic four first.

### Read the destination and the breadth, and the type falls out

Pull the considerations together, because the objective is about considerations, not just names. The type picks your binding, one object or several. It picks your entry points, a record page button, the email composer, a Flow, Apex, an agent action, or a prompt action. It picks your output shape, a field value, an email, a summary, or open text. And it is fixed for the life of the template.

So read a scenario by asking where the output goes and how many objects feed it. A field on one record points at Field Generation. An email to a contact or lead points at Sales Email. An overview of one record points at Record Summary. Open text from several objects, called from a Flow or Apex, points at Flex. Those two questions land you on the right type almost every time.

## Exam Traps

Three misconceptions recur. The first is believing the type can be changed after creation. It cannot: the type fixes the binding and the entry points, so a wrong type means rebuilding the template rather than adjusting a setting. The second is believing Field Generation can read several objects. It binds to a single object, so a requirement that must combine multiple objects belongs to Flex, not Field Generation. The third is believing Record Summary and Field Generation are interchangeable. Field Generation writes text into a record field from a record page, while Record Summary produces an overview of a record, so the destination decides between them.

## What a consultant should walk away with

Read the destination first and the object count second, and let those two facts choose the type before you write a line of the prompt. Field Generation for a field on one record, Sales Email for a customer email anchored on a Contact or a Lead, Record Summary for an overview of one record, and Flex for open text that reads several objects and runs from a Flow, Apex, or a prompt action. Treat the type as a contract signed at creation[^4], and check whether a standard business type already covers the surface before you build one by hand.
