# Lesson 5: Prompt Template Types: What Field Generation, Flex, and the Standard Types Bind

A consultant is asked to add a generated next-step suggestion to an Opportunity record page. She opens Prompt Builder, picks Field Generation because the word field is in the requirement, writes a clean prompt, activates it, and drops it onto the page. It works, until the same stakeholder asks for a recommendation that reads the Opportunity, its Products, and the Account at once. She opens the template and finds she cannot add the other two objects at all, because Field Generation binds to a single object[^2]. The fix is not a setting. It is a new template of a different type, a rebuilt prompt, and a fresh activation.

The cause is that the template type is not a preference you set later. It is the first choice in Prompt Builder, made when you create the template, and it sets three things at once: which objects the prompt can ground with, what inputs it accepts, and where it can be invoked[^3]. Every later choice, from which merge fields the resource picker offers to which surface can call the template, hangs from that one click. In practice, a template built with the wrong type gets rebuilt rather than re-configured, because the binding, the entry points and the resource picker were all set around the type you chose.

This lesson teaches the four classic types by what they bind and where they run, then widens the view to the standard, business-specific types Prompt Builder also ships. Read every requirement as two facts, where the output goes and how many objects feed it, and the type follows. The exam cares because Prompt Engineering is twenty percent of the blueprint, and the fit of a type to a requirement is one of its most repeated question shapes.

<TLDR>

- The template type is a contract signed at creation that fixes the binding, the inputs, and the entry points
- Read where the output goes and how many objects feed it; when the two conflict, the binding wins
- A wrong type is a rebuild, so check the standard business types before building a Flex template by hand

</TLDR>

## Deep Dive

### The type is a contract you sign before you write a word

When you click New Prompt Template, the type dropdown is the first control you meet and the most committing. The type decides which objects you can associate with the template, which grounding resources it accepts, what inputs it takes, and where in Salesforce it can be invoked[^3]. Those are set by the type you pick at creation, so a finished Field Generation template carries the binding, the entry points and the resource picker its type established. In practice, a template built on the wrong type gets rebuilt rather than re-configured, because the type is the key those three hang from.

That single choice also fixes the interaction shape a user will get. A Field Generation template is built to run from a record page against the record in front of the user, so its whole design assumes a record context. A Flex template is built to be called by another system, a Flow, Apex, or a prompt action, and its design assumes the caller supplies the inputs. Get the type wrong and you have not made a small error in a dropdown; you have designed the wrong interaction, and you will not discover the mismatch until the template refuses the objects, the surfaces, or the inputs that the requirement needs.

The exam hands you a requirement and expects two facts off it. Where does the generated output land: in a field on a record, in an email, in a summary view, or somewhere custom. And how many objects must the prompt read to produce it. Answer those two and the type falls out. That is the whole method this lesson teaches, and the next lesson drills it against a stack of scenarios.

### Field Generation writes text into one record's field

Field Generation is the type for putting generated text into a field. It binds to a single object[^2], and it is built to run from a record page, where a user clicks a button and the output populates a field on that record[^1]. The output is text that lands on the record, not an email and not a standalone summary. It fits completing a specific field on a specific record, such as a generated case description, an account tier note, or a next-step suggestion on an opportunity[^5].

Field Generation is stricter than the other types about what it needs before you can write the prompt. When you create one you first select the object that contains the field, and then you select the object field you want Einstein to populate[^2]. That second selection is the type's distinctive setup cost. It is also why the target field sits in the template's definition rather than arriving as a runtime argument the caller passes in, so a different destination field means a new template rather than a changed setting.

The single-object binding is the whole constraint, and it is where the extra objects in a requirement become a hard stop. Because it reads one object, Field Generation cannot reach across several unrelated objects, and it is not designed to stand alone outside a record context. A requirement that names more than one source object is one Field Generation cannot carry, no matter where the output goes, which is exactly the wall the consultant hit in the opening scene.

### Flex is the catch-all that defines its own resources

Flex is the type you reach for when the others do not fit, and it earns that role by being the most open of the four. It does not inherit a fixed object association. Instead you define the resources yourself, and it can ground with more than one object, which is what makes it the type for a prompt that reads from several places at once[^4]. A recommendation drawing on an account, its open opportunities, and a product catalog is the classic case.

Defining a resource is a small ceremony, and knowing it helps you plan the template's inputs. For each object you add as a resource you give it a unique name and API name, and you mark it required or optional with a checkbox, so the template declares the inputs it needs rather than inheriting them from a fixed association[^4]. Its outputs serve purposes the other types do not cover, and it is invoked from a Flow, Apex, or a prompt action rather than from a record page button. That invocation difference matters as much as the binding: Flex is the type you integrate, not the type you drop onto a page and forget.

Flex does have a ceiling, and it is worth stating because the exam uses it as a distractor. Flex grounds with up to five resources, so a requirement that names several objects fits Flex as long as it stays inside that set[^4]. A requirement that genuinely must read more objects than Flex carries is not a cue to find a wider classic type, because none of the four is wider. It is a signal that the prompt, or the architecture around it, needs rethinking rather than a different value in the dropdown.

### Sales Email is bound to a Contact or a Lead

Sales Email covers one use case: a personalized customer email grounded in record data. Its binding is narrow. You select a recipient object, which is how the type lands on a Contact or a Lead, you can optionally pull in data from one related object such as an Account, and the template surfaces in the email composer on contacts and leads[^8]. If the output is an email to a customer and the anchor is a Contact or a Lead, Sales Email is the type.

If the requirement needs a different anchor object or a broader set of records, the binding is the wrong shape and Flex is the fallback. This is a favorite wrong answer on the exam, because Sales Email sounds general but is bound tighter than its name suggests. A scenario that says draft an email about this custom Partner record reads like Sales Email until you remember the binding is fixed at Contact or Lead, and the requirement's anchor object has already excluded the type.

There is a sibling worth naming for completeness. Case Email Draft is the email type anchored on a Case rather than on a Contact or a Lead, so the two email types together show the pattern: the anchor object, not the word email, decides which email type can carry the requirement. Read the anchor before you read the noun.

### Record Summary explains one record, and the catalog runs wider than four

Record Summary is the type for summarizing a record. It binds to a single object and produces a rich-text overview of that record from its own data, and it is the type behind the Summarize Record action an agent or a Flow can call[^1]. A meeting-prep summary for an opportunity, or a quick case overview for a rep, is Record Summary work. It gives a reader an overview, which is not the same as filling a field, and that destination difference is what separates it from Field Generation.

The four classic types are not the whole catalog. Prompt Builder also ships standard, business-specific types, and the list is long: Knowledge Answers for how an agent answers questions, Work Summary for the call or messaging wrap-up, Case Summary for a case overview, Campaign Brief for marketing content, and Record Research for research results, among many others[^1]. These are customized rather than built from scratch, and each carries its own binding and its own entry points[^6]. Recognize one when a scenario names its exact surface, and place everything else into the classic four first.

![The four classic prompt template types compared by what each one binds, where each one runs and what each one produces: Field Generation writes into a field on one record, Flex declares its own resources and runs from a Flow, Apex or a prompt action, Sales Email anchors on a Contact or a Lead, and Record Summary produces an overview of one record.](</diagrams/day-05-pe-3a-prompt-template-types-what-field-generation-flex-a/2-four-classic-types.png>)

The reading rule that falls out is a search order. Before you build a Flex template by hand, check whether a standard type already covers the surface the requirement names, because imitating a Work Summary or a Knowledge Answers template with a generic Flex build is more work and less on-target. The exam states the same preference from the other side: Flex is the general type, so choosing it when a standard type already fits is the wrong answer even though it would technically run.

### Field Generation needs the object and the field, and the page needs Dynamic Forms

Two setup consequences of the Field Generation binding deserve their own beat, because they are where a build most often stalls. The first is the field selection you already met: the template is created against an object and a target field together[^2], so if the stakeholder later decides the generated text should land somewhere else, or in two fields, you are back at New Prompt Template. Plan the target field with the business before you write a sentence, confirm its API name, and confirm its type can hold generated prose.

The second consequence is on the page rather than in the template. To add a Field Generation template to a Lightning record page, Dynamic Forms must be enabled[^2], and Dynamic Forms is supported for most but not all standard LWC-enabled objects[^7]. So a record page that still uses the legacy page layout, or an object that Dynamic Forms does not support, will not host the button the requirement assumes. A consultant checks that page readiness before promising the feature, because the template can be perfect and still have no surface to run on. This is the kind of detail the exam leaves implicit and a delivery lead cannot, because the template is only half of a field generation rollout.

### The wrong type is a rebuild, and the exam prices it that way

Here is the worked scenario. A requirement reads: fill a Next Step text field on the Opportunity record page with a generated suggestion when a user clicks a button, drawing on the Opportunity and its Open Activities. The output destination points at a field on a record, so Field Generation is the first candidate. But the requirement also names two objects, the Opportunity and its related Open Activities, and Field Generation binds a single object. The correct reasoning is that the destination narrows the answer and the object count vetoes it, so the type is Flex, wired to run on demand rather than called from a Flow.

The wrong answer is the obvious one: pick Field Generation because the word field is in the requirement, and hope the related activities come along as a related list. Related lists are selectable grounding resources inside a template, but a related list still belongs to the associated record's object, and Field Generation's association is a single object. The wrong answer fails for the same reason the opening scene failed: the binding, not the wording, is the limit, and the exam builds its distractor around the reader who stops at the destination and never checks the inputs.

### Read the destination and the breadth, and the type falls out

Pull the considerations together, because the objective is about considerations, not just names. The type picks your binding, one object or several. It picks your entry points, a record page button, the email composer, a Flow, Apex, an agent action, or a prompt action. It picks your output shape, a field value, an email, a summary, or open text. And every one of those is set by the type you choose at creation.

So read a scenario by asking where the output goes and how many objects feed it. A field on one record points at Field Generation. An email to a contact or lead points at Sales Email. An overview of one record points at Record Summary. Open text from several objects, called from a Flow or Apex, points at Flex. Those two questions land you on the right type almost every time, and when the two seem to conflict, the binding wins.

### The build sequence in six steps

<Steps>

<Step title="Open Prompt Builder">

In Setup, open Prompt Builder and click New Prompt Template.

</Step>

<Step title="Choose the template type first">

Choose the template type first, matching Field Generation to a record field, Sales Email to an email, Record Summary to a summary, and Flex to everything else.

</Step>

<Step title="Confirm the type's binding">

Confirm the type's binding: Field Generation and Record Summary bind one object, Sales Email binds a Contact or a Lead, and Flex lets you define multiple objects as resources.

</Step>

<Step title="Write the prompt">

Write the prompt and insert the grounding resources the type permits: merge fields, related lists, a Flow, an Apex action, or a Data 360 retriever.

</Step>

<Step title="Note the type's entry points">

Note the type's entry points, for example a record page button for Field Generation or a Flow and Apex invocation for Flex, and plan where the template will surface.

</Step>

<Step title="Preview against representative records">

Preview against representative records and activate a version, then wire the template into its entry point.

</Step>

</Steps>

## Exam Traps

<Callout kind="warning">

Three misconceptions recur. The first is treating the type as a setting you can adjust after creation. It is a type chosen at creation, and it sets the binding and the entry points, so in practice a template built on the wrong type gets rebuilt rather than re-configured. The second is believing Field Generation can read several objects. It binds to a single object, so a requirement that must combine multiple objects belongs to Flex, not Field Generation. The third is believing Record Summary and Field Generation are interchangeable. Field Generation writes text into a record field from a record page, while Record Summary produces an overview of a record, so the destination decides between them.

</Callout>

## What a consultant should walk away with

<KeyTakeaways>

- Read the destination first and the object count second: Field Generation for a field on one record, Flex for open text that reads several objects
- The type is fixed at creation and cannot be changed later, so a wrong type means rebuilding the template rather than adjusting a setting
- Field Generation binds to a single object, so a requirement that must combine several objects belongs to Flex, not Field Generation
- Sales Email anchors on a Contact or a Lead and Record Summary produces an overview of one record, so the destination decides the type

</KeyTakeaways>
