# Lesson 2: The Decision Boundary in Practice: When a Prompt Template Is the Wrong Tool

A sales operations manager asks for a field on every opportunity that shows a go or no-go call. A consultant builds a prompt template, grounds it in the opportunity, and lets a model decide. The field now says something different on Tuesday than it said on Monday, the reps cannot explain it, and the audit team cannot reconcile it against the deal review standard. The business asked for a decision, and the build returned an opinion.

The requirement had one exact right answer, and that is the tell that a model is the wrong tool. A prompt template earns its place when the output cannot be known in advance, when the words themselves are the deliverable, and when a model reading grounded data produces something a rule could not. It is the wrong tool the moment the requirement has a single correct value that a formula, a Flow, or a report can produce.

This lesson works the boundary in both directions: the requirement shapes that belong to Flow, to a formula, and to a report, then the shapes that genuinely point at Prompt Builder, and finally the middle ground where the honest answer is to compute first and phrase second. Requirement pe-1b sits in the Prompt Engineering domain at 20 percent of the exam, and it is the objective the scenario questions keep returning to.

## Deep Dive

### Ask what the output has to be, not what the tool is

The real question behind when to use Prompt Builder is a boundary: generated text on one side, computed or retrieved truth on the other. Start every requirement by asking what the output has to be. If the answer is words, and those words have to be shaped by the record in front of the reader, you are on the generation side. If the answer is a value, a sequence of record changes, or an aggregate, you are on the deterministic side.

This framing keeps you out of the trap of reasoning from familiarity. Consultants reach for the tool they know, and scenario writers know that. The exam questions in this objective almost always hinge on a single phrase that names the output type, so train yourself to find that phrase before you look at the answer options.

### Deterministic Flow owns record changes and sequences

Take deterministic Flow first. When the requirement is to update records, run a sequence of steps, request an approval, or enforce a validation, the tool is Flow, not a prompt template [^1]. Flow acts on your data: it changes fields, creates records, and fires other automation, all in a defined order with an auditable run.

A prompt template produces text and stops; it does not update the record it was grounded in unless something else takes its output and writes it. So a requirement phrased as whenever a case closes, set the status and notify the owner is Flow work, and an answer that reaches for a generative prompt has confused the producer of language with the actor on records. The exam likes this stem because both options sound plausible until you check which one touches the data.

### A formula computes the defined value exactly

Next, the formula field. When the output is a value derived by a fixed rule, a discount percentage off a price, a rating from a score, a combined label from two fields, a formula computes it every time, on every record, with no model call, no token cost, and no variation [^2]. A generated field looks tempting because it reads cleverly, but if a formula can produce the exact value the business defined, the prompt is the wrong answer and an expensive one.

Generation is for text where the value is not defined by a formula: a rationale, a next step, a plain-language summary. If you can write the rule as a formula, write the formula. The reason is not cost alone. A formula is reproducible, testable, and explainable to a business reviewer, and a model that decides a discount has quietly moved a business rule into something nobody can audit.

### A report answers the aggregate question

Then the report and the dashboard. When the requirement is to see aggregated or filtered record data, totals, counts, trends, a list of deals by stage, the answer is a report, because a report is a query over your data and returns exact numbers every time. A prompt that summarizes the pipeline is not the same thing and should not be sold as one.

The disciplines differ too: a report is reproducible and drillable, while a generated summary varies run to run. The exam likes the pair of requirements show me the total and explain the account, and the correct tools are a report for the first and a prompt template for the second [^3].

### The shapes that genuinely point at Prompt Builder

Now the shapes that do point at Prompt Builder. The output is free text, not a number. The wording matters and should adapt to the record: tone, personalization, a summary written for a human to read. The source is unstructured or semi-structured content such as case notes, email threads, or transcripts.

The task is drafting or explaining: draft a follow-up email, summarize this call, explain the renewal risk in plain language. And the same prompt must run again and again over many records, which is why you want it saved, typed, and versioned rather than retyped. If the requirement has several of those traits, a prompt template is the tool. Notice that none of them mention the platform surface, because the requirement is about the output, and the surface follows.

### Compute first, phrase second

Most real requirements sit in the middle, and the honest pattern is compute first, phrase second, not choose one or the other. A Flow or an Apex action computes the exact facts: the loyalty tier, the days to renewal, the open case count. The prompt template is grounded with those computed values and its job is only to write the sentence [^4].

That split keeps determinism where determinism matters and puts the model where it adds value, which is language. When a scenario needs both an exact figure and a human-readable explanation of it, the best answer is rarely prompt yes or flow no, it is the two composed so each does its own job. A build that asks a model to invent the number and the explanation together is the one that drifts and cannot be defended.

### What getting the choice wrong costs

Getting the choice wrong costs in two directions. Use a prompt template for a rule that a formula could compute, and you have made a deterministic value non-deterministic: it costs a model call per run, it can drift across runs, and it is hard to audit against a business definition. Use Flow or a formula for work that genuinely needs generation, and you force brittle string logic that breaks on the first edge case a human would have understood.

Every template run also passes through the Einstein Trust Layer, which is a safeguard you want, not overhead to avoid [^5]. Match the mechanism to the requirement, and the exam questions and your production builds both get simpler.

## Exam Traps

Three traps dominate this objective. The first is believing a generated field replaces a formula, when a formula computes the defined value exactly on every record and a prompt generates text where no exact value exists, so reaching for generation to fill a computable field is the wrong tool. The second is believing a prompt template can update records on its own, when a template returns text and stops, so a Flow or an action must write that output, and treating generation as automation is wrong. The third is believing summarize the pipeline and show the pipeline total are the same task, when the total is a report and the summary is a prompt, so answering the numeric request with generation gives a number that varies run to run.

## What a consultant should walk away with

Name the output before you name the tool. A record change or a sequence is Flow. A value from a fixed rule is a formula. An aggregate is a report. Free text that adapts to the record, drawn from notes or threads, is a prompt template. When a requirement needs both an exact figure and an explanation, compute the figure with a Flow or a formula and let the prompt phrase it. Match the mechanism to the requirement and both the exam and the production build get simpler.
