# Lesson 33: Standard and Custom Topics and Actions: The Agentforce Building Blocks

A service operations manager sits beside you to watch a pilot agent answer a refund request. The customer asked to return an order and get the money back. The agent greets warmly, looks up the order, confirms the shipping address, and then quotes a return window the company retired two seasons ago. The pilot scored well on tone and lost the room on truth, and the manager asks the question every stakeholder asks first: why did it say that.

The cause is neither the model nor the wording. A support lead had pasted the old return policy into the topic instructions as plain text, because that was the quickest place to put it, and instructions are guidance the agent follows loosely rather than a rule it always obeys. The refund window was a deterministic fact, and it belonged inside the Flow behind an action, where it would run the same way on every request. When you let the guidance layer carry logic that should live in the tool layer, the same question can produce a different answer on a different day, and no amount of prompt polishing repairs it.

This lesson serves requirement ag-4a in the AI Agents domain, which carries 35 percent of the exam, the heaviest of the six domains. You will learn to name the job an agent is doing, list the tools that job requires, and decide whether to reuse a standard asset that Salesforce ships or build a custom one. The exam treats this as a scenario skill, so the target is a build you can defend: the right topic, the right actions grouped under it, and natural language written so the agent classifies and routes correctly.

<TLDR>

- Name the job, list the tools it needs, then decide whether a standard asset fits
- A topic is a job and an action is a tool; the deterministic logic belongs inside the action
- Reuse the standard asset when its job is yours, and carve a narrow custom topic otherwise

</TLDR>

## Deep Dive

### A topic is a job, an action is a tool, and the gap between them is the whole design

An Agentforce agent is assembled from a few constructs you have to tell apart on sight. A topic is a job the agent can do, such as managing an order or handling a return. An action is a tool the agent uses to do a piece of that job, such as a Flow that updates a record or a prompt template that drafts a customer reply. Instructions are natural language that tells the agent how to decide and how to behave. The classification description is the text the reasoning engine reads to route a request into a topic, and it is the single most important sentence you will write on a topic [^1].

When a scenario asks you to select and configure topics and actions, the first move is always the same. Name the job the agent is being asked to do, then name the tools that job needs, and only then decide whether each piece already exists as a standard asset. This order matters because it stops you from starting with a feature you like and inventing a job to justify it. Salesforce describes the agent as a library of topics and actions, with the reasoning engine interpreting the request, classifying it into a topic, and then finding and launching the right actions to reach the goal [^2].

Hold the layers apart as you read every later section of this course. The topic decides whether the agent can help at all, because an action that is not attached to the topic the request lands in is unreachable. The action decides whether the help is correct, because the tool holds the actual logic. And the instructions sit between them as guidance, useful for tone and sequencing and unreliable for anything that must be exact. Most production failures you will debug trace back to a layer that was asked to do another layer's job.

### Start from the standard library, then narrow it on purpose

Salesforce ships a library of standard topics and standard actions, and the recommended starting point is to add the standard asset that matches the job and edit it rather than build from a blank page [^2]. Standard topics cover common jobs such as order management, case handling, and general FAQ work, and the library also carries managed topics and actions contributed by the wider partner ecosystem. Reuse is the fast path, and on a first build it is also the safer path, because the shipped asset already carries a classification description and an action set that were written by people who test agents for a living.

The counterintuitive part, and one Salesforce states directly, is that for the best performance you often finish by replacing a broad standard topic with purpose-built custom topics. This is not a contradiction of the reuse rule; it is the second half of it. A narrow, clearly described topic classifies more reliably than a catch-all, because the classifier has less to guess about. A standard topic called something like General Service that has grown to cover billing, returns, and warranty at once will blur its boundaries, and the request that sits between those jobs will land somewhere arbitrary [^1].

So the selection rule has two halves. Select the standard asset when its defined job is genuinely the job in front of you, which is common for well-scoped jobs the platform anticipated. Create a custom topic when your job is specific enough that a standard topic would describe it poorly, which is common once the agent matures and you can see where the broad topic is guessing. The exam rewards the candidate who names that trade-off rather than reaching for standard or custom as a reflex.

![Reuse the shipped standard asset and edit it, then carve narrow custom topics when a broad standard topic starts blurring jobs.](</diagrams/day-33-ag-4a-standard-and-custom-topics-and-actions-the-agentfo/2-standard-or-custom.png>)

**Choosing standard or custom**

| Aspect | Standard asset | Custom asset |
| --- | --- | --- |
| When it fits | The shipped job is genuinely yours | Your job is specific enough a standard one describes poorly |
| Starting point | Add the shipped asset and edit it | Build from a Flow, Apex, prompt template, or integration builder |
| Access | Available to users who can reach the default agent | Inherits the permissions of the Flow or Apex it references |

### Custom actions are assembled from a small, fixed set of builders

Standard actions are the pre-built tools that come with Agentforce, and custom actions are the ones you build to reach your own org. A custom action is assembled from a short list of builders: a Flow, an Apex class, a prompt template, and, on current releases, an Apex REST class, an External Service, or a MuleSoft API [^3]. The builder you pick is decided by where the logic already lives. A Flow is the default for declarative work on your objects, Apex is for logic that exceeds Flow, a prompt template is for generated text, and the integration builders are for a system of record the platform does not natively speak to.

Every action, standard or custom, carries four things you configure: a name, a description, a set of inputs, and a set of outputs. The name should be unique and verb-led, because the agent distinguishes actions largely by name and description, and near-duplicate names blur that choice [^3]. The description should say in a sentence or two what the action does and what goal it serves, including what happens when the record is not found. You are not writing logic when you configure an action. You are describing it precisely enough that the model chooses it correctly and wires its parameters correctly, and the logic lives in the Flow, Apex, or prompt behind it.

This division is what makes an action testable. Because the logic sits in the referenced asset, you can test the Flow or the Apex on its own, run its own tests, and know that it behaves. The action is a thin declarative wrapper that tells the agent when and how to call that tested logic. When you build a custom action correctly, you are not adding code to the agent; you are pointing the agent at code you already own and can already trust.

### Group the right actions under the right topic, and keep the group tight

Assigning actions to topics is the step that makes the design coherent. Inside a topic in Agentforce Builder, the This Topic's Actions tab is where you list the actions that this job may use, and grouping the right actions under the right topic is what keeps the agent from firing a tool in the wrong context [^3]. A common and sound build pattern puts a topic around a business process and the supporting actions together, so the classification description, the scope, and the action list all point at the same job.

You can reuse an action across more than one topic when the same tool genuinely serves two jobs, but do that deliberately. An action exposed in a topic where it does not belong gives the model a way to take an unhelpful path, because the agent now has a tool in hand that the situation never called for. The tighter the action list, the smaller the space the model has to choose wrongly. If two topics both need to update the same record, that is often a sign the two topics overlap and should be merged or redrawn, not a sign the action should be duplicated everywhere.

Read a topic's action list as a claim about scope. If someone asks what this topic can actually do, the honest answer is the union of its actions, not its description. A topic whose description promises warranty handling but whose action list has no action that reads or writes a warranty claim cannot deliver the promise, and the gap will surface the first time a customer asks. Keep the description, the scope, and the action list saying the same thing.

### Write the classification, the scope, and the instructions as three different jobs

The reliability of the whole build comes down to the quality of the natural language, and the exam expects you to keep three pieces of it distinct. The classification description is short and specific, written so it clearly distinguishes this job from adjacent jobs; it should describe what kinds of user messages should trigger the topic [^1]. The scope states what the topic does and, just as importantly, what it does not do, so the borderline request routes to the topic that owns it. Instructions guide behavior and tone inside the topic once the request has landed.

The division that candidates miss is the one between guidance and logic. Salesforce is explicit that topic and action instructions are non-deterministic, so any sensitive or deterministic business rule does not belong in them; it belongs inside the action's own logic, in the Flow or the Apex, where it always runs the same way [^3]. Validation is the clearest example: input format should be enforced in the action, not requested politely in the instructions, because a rule that depends on the model's cooperation is not a rule. Write the classification, the scope, and the instructions knowing which of the three is allowed to be approximate.

A practical test is to read each sentence and ask whether it must be true every time. If it must, it is logic and it moves into the tool. If it is about how the agent should sound, what it should ask first, or how it should phrase a result, it can stay in the instructions. Keeping that line clean is what separates an agent that works in a demo, where the happy path is all anyone tries, from an agent that works in production, where the edge cases arrive unprompted.

### Choosing the standard or custom action is also a security decision

Access to what an agent can do is governed at the asset level, not only at the agent level, and this is the part of topic and action design that reaches into security. Standard topics and standard actions are generally available to users who can access the default agent, but a custom action inherits the access of the thing it references [^3]. A custom action backed by a Flow follows that Flow's permissions and run context, and a custom action backed by an Apex class follows the class it calls. The wrapper does not add privilege; it inherits whatever the underlying asset carries.

That inheritance is why two people can open the same agent and find that one can run a custom action and the other cannot, with no difference in their agent access at all. The difference lies in their access to the Flow or the class behind the action. When you select assets for a scenario, remember that choosing a standard action versus a custom one also changes who ends up able to invoke it, because the standard action's access and the custom action's inherited access are not the same grant.

Treat the choice as a security decision and not only a build decision, and it will shape how you answer scenario questions about agents that behave differently for different users. The fix for a user who cannot run a custom action is usually a grant on the underlying Flow or class, or a redesign that moves the work behind a different asset, not a change to the agent itself. The agent is doing exactly what its design allows; the access is what differs.

### Verify the design with the Plan Tracer and the Testing Center

Verify the design before you trust it, because agent behavior is not obvious from reading the configuration. Agentforce gives you the Plan Tracer inside Agentforce Builder to see how the agent reasoned through a request, including which topic it entered and which actions it considered and chose [^2]. Alongside it, the Testing Center lets you run defined scenarios against the agent at scale and check that it picks the right topic and the right actions across many inputs rather than one lucky conversation [^4].

The distinction that the exam rewards is between testing an action and testing the agent. Testing an action checks that the Flow or the Apex does what it was coded to do, which is deterministic and can be automated. Testing agent reasoning checks that the model interprets the instructions and chooses correctly, which is non-deterministic and has to be sampled across scenarios. The two fail for different reasons, and a passing action test tells you nothing about whether the agent will ever call that action.

Treat topic selection and action firing as a separate discipline from tool logic for exactly that reason. If the tool logic is right but the agent never reaches it, the problem is in the topic or the description, and the Plan Tracer will show you where the reasoning went. If the agent reaches the tool and the result is still wrong, the problem is in the Flow or the Apex. Naming which of those two layers you are testing, before you test, is how you fix the right thing instead of guessing.

### The build sequence in six steps

<Steps>

<Step title="Open Agentforce Studio">

In Setup, open Agentforce Studio, then Agentforce Agents, and open the agent you are building or create a new one in Agentforce Builder.

</Step>

<Step title="Open the Topics panel">

In Agentforce Builder, open the Topics panel and add the standard topic that matches the job, or click to create a custom topic and give it a clear name.

</Step>

<Step title="Write the Classification Description">

In the topic, write the Classification Description so the job is distinct from neighboring jobs, write the Scope so it states what the topic does and does not handle, and add Instructions for behavior.

</Step>

<Step title="Open This Topic's Actions">

Open the topic's This Topic's Actions tab and add the standard actions the job needs, or create a custom action from a Flow, Apex class, Prompt Template, External Service, or MuleSoft API.

</Step>

<Step title="Set a unique verb-led name">

For each custom action, set a unique verb-led name, write a one-to-three sentence description of what it does, and define each input and output with its data type and meaning.

</Step>

<Step title="Open the Plan Tracer">

In Agentforce Builder, open the Plan Tracer to inspect how a sample request is routed, then use Testing Center to run defined scenarios and confirm the agent selects the correct topic and actions.

</Step>

</Steps>

## Exam Traps

<Callout kind="warning">

Three traps dominate this objective. The first is believing that deterministic business rules belong in topic instructions: they do not, because topic and action instructions are non-deterministic, so anything that must always behave the same way belongs inside the action's Flow or Apex logic where it runs identically every time [^3]. The second is believing that a broad standard topic is always the safest choice: Salesforce recommends narrow, clearly described topics for reliability, so a catch-all standard topic that blurs several jobs classifies worse than a set of specific custom topics carved out of it [^1]. The third is believing that selecting a custom action does not change access: a custom action inherits the permissions of the Flow, Apex class, or prompt template it references, so who can run it depends on that underlying asset and not on the agent alone, and the same agent can behave differently for two users for access reasons [^3].

</Callout>

## What a consultant should walk away with

<KeyTakeaways>

- Deterministic business rules belong inside the action's Flow or Apex logic, because topic and action instructions are non-deterministic and cannot enforce them
- A narrow, clearly described topic classifies more reliably than a catch-all standard topic, so carve specific custom topics as the agent matures
- A custom action inherits the permissions of the Flow, Apex class, or prompt template it references, so access depends on that asset
- Give each action a unique verb-led name and a short description, and define every input and output with its type and meaning

</KeyTakeaways>
