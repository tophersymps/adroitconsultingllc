# Lesson 13: The Einstein Trust Layer: The Security and Privacy Features Around Every Prompt

A delivery team had a working service agent and a security review booked for the same week. The reviewer asked one question that stopped the room: when an end user sends a message, name everything that leaves the org and name what guards it on the way out. The builder could demo the agent and walk the topics. Nobody could list the controls between the record and the external language model, so the review stalled on a gap that had nothing to do with the build.

The cause is that the Trust Layer is deliberately invisible. It wraps every prompt an agent or a prompt template sends and every response that returns, yet it never asks a builder to configure it and never appears as a surface to point at during a demo. Because it works quietly, teams describe it as a vague safety promise instead of a defined set of features they can name and defend.

This lesson names those features one at a time, then traces a single request through them. The objective asks you to identify the security and privacy features of the Trust Layer, a recall question with precise answers, so the goal is six names, what each one does to a request, and the order in which a request meets them.

## Deep Dive

### The Trust Layer is an architecture, not a product you license

The Einstein Trust Layer is a secure AI architecture built into the Salesforce platform [^1]. It is a set of agreements, security technology, and data and privacy controls that sit between your org and the external language model. Every prompt an Agentforce agent or a prompt template sends leaves your org through this layer, and every response comes back through it, so the layer sits on the path of every request whether or not anyone thought to configure it.

That framing rules out a family of wrong answers that treat the layer as something you buy, install, or subscribe to. It ships with the platform, so the work is to turn its features on, configure the ones that need configuration, and confirm the settings hold. The objective is a recall question, so start with the six names: zero data retention, dynamic grounding with secure data retrieval, data masking, prompt defense, toxicity scoring, and the audit trail.

Because the layer is invisible by design, it never asks a builder to configure it and never appears as a surface in a demo, which is why teams default to describing it as a vague safety promise. The exam wants the defined set instead. Learn the six by name, then learn the stage of the request each one operates on, because a scenario will hand you a value and ask which feature protects it.

### Zero data retention binds the provider, not your own org

Zero data retention is the agreement that governs what the external provider keeps [^2]. Salesforce partners with all of its external model providers, such as OpenAI or Azure OpenAI, so that prompts and responses are not retained by the third party and are not used to train the model or improve the provider's product [^1].

The promise has three parts, and naming all three is what wins the recall question. No data is used for model training or for product improvement by a third-party model. No data is retained by the third-party model. And no human being at the third-party provider looks at data sent to their model unless Salesforce grants view access in response to documented suspicion of illegal activity or a significant violation of applicable usage policies. The data is deleted once the response returns to Salesforce [^1].

Read that precisely, because it is the most misread clause here. Zero data retention constrains the external provider. It says nothing about what Salesforce stores for you, and the audit feature keeps prompts, responses, and trust signals inside your org's data platform. An answer that says zero data retention means the org stores nothing has confused the provider's obligation with the platform's record keeping.

### Secure data retrieval grounds under the running user's permissions

Dynamic grounding with secure data retrieval is the data-in side of the layer [^1]. When an agent needs a record's contents to answer, the platform merges the relevant information from the record into the prompt as context.

The retrieval does not run above the user's own access. It runs with the permissions of the user executing the prompt, so standard role-based access controls, sharing rules, and field-level security all stay in force as the grounding data is assembled. That protection holds whether the grounding data comes from your CRM records or from Data 360, because secure data retrieval preserves the controls you already set rather than replacing them [^2].

This is what stops an agent from reading a record the running user could not open themselves. The trap is to believe the layer widens access, when in fact it prevents the model from being grounded on anything the running user cannot already see. When a scenario shows an agent surfacing data a user should not have, the defect is upstream in access, not a property of the layer.

### Data masking swaps values before the prompt crosses, and is off for agents

Data masking detects sensitive data and replaces it with a placeholder before the prompt is sent to the model [^3]. The layer identifies sensitive data two ways. Pattern-based detection uses regular expressions and surrounding context words, backed by machine learning models trained to catch values that have no fixed pattern, such as names of people or companies. Field-based detection uses the metadata on fields you classified with Shield Platform Encryption or Data Classification, so the classification you already applied to your data extends to what the model sees [^3]. Masking supports multiple regions and languages, and you can select what must and must not be masked. The placeholder, not the real value, crosses to the model, and the platform restores the value in the response afterward.

One fact settles a whole family of questions: data masking for large language models is disabled for agents [^4]. It remains available and configurable for embedded features such as Einstein Service Replies and Einstein Work Summaries, but with an agent you cannot rely on it, so the discipline is to keep raw sensitive values out of the prompt in the first place. The settings you configure for an embedded feature do not protect an agent conversation, and that asymmetry is a favorite exam distractor.

### Prompt defense and toxicity scoring put a name and a number on safety

Prompt defense is a set of system policies that limit hallucinations and reduce the likelihood of unintended or harmful output from the model [^1]. System policies are instructions to the model about how to behave, for example not to answer from information it does not have, and they are one way the platform defends against jailbreaking and against prompt injection, where instructions are hidden in the input to try to make the model disregard its own instructions. The policies can differ across features and use cases.

Toxicity scoring is the measurable half. The layer scores prompts and responses across five categories, which are violence, sexual, profanity, hate, and physical [^5]. The individual results combine into an overall score from 0 to 1, where 1 is the most toxic, and the score travels back with the response.

Naming the categories and the scale matters because the exam treats toxicity scoring as a concrete feature with a numeric output. A toxicity score is not a sentiment label and not a confidence value. It is a safety signal that runs on the prompt going out and on the response coming back, and it is one of the trust signals the audit trail stores.

### The audit trail is what makes the other five provable

Prompts, responses, and trust signals are logged and stored in Data 360, and the platform ships pre-built reports and dashboards so you can see how the layer protected sensitive data and whether responses were safe [^6]. Data in transit between the Salesforce gateway and the model providers is protected with TLS encryption [^2], so the audit trail is what proves the chain worked after the fact.

The trail is not on until an admin turns it on. To read the stored generative AI data, turn on Einstein generative AI data collection and storage in Einstein Audit, Analytics, and Monitoring Setup and install the report package; without that step there is no evidence, and any later question about what a past request carried has no answer to point at. Enable it before your first go live, not after a reviewer asks [^6].

### Trace one request through the layer, feature by feature

Take one end user turn and walk it. The user types a message inside your org. The agent or the prompt template assembles the prompt, grounding merges the relevant record data under the running user's permissions, and masking runs on the prompt text, unless the surface is an agent, where masking is disabled. The assembled prompt then crosses one seam: the point where it leaves the Salesforce gateway and reaches the external model. Everything on the org side of that seam is under Salesforce controls, and everything across it is governed by the zero data retention agreement and by TLS encryption in transit.

On the way back, the order reverses. The model returns a response across the same seam. The layer scores the response for toxicity, demasks any placeholder it substituted, and writes the prompt, the response, and the trust signals to the audit trail before the user sees the result. Prompt defense is active the whole time the model is generating, shaping what it will and will not produce.

Hold that order and the six features stop being a flat list and become a path. Retention governs what the provider keeps, grounding and masking govern what data goes out, prompt defense and toxicity govern behavior and safety on both sides, and the audit trail records the whole crossing. When a scenario asks which feature protects a specific value, place the value on this path first, then name the feature that operates at that point.

### The audit trail records more fields than most teams expect

The stored audit record is richer than a log line, and knowing its fields is how you answer the questions about what is retained. A generative AI audit record carries the prompt template ID and details, request metadata and a request ID, the org ID, the region and language, the hydrated prompt text before masking, the final masked prompt text that actually went to the model, the retrieved grounding data, the model response text, the final unmasked response text, a response safety score, the response toxicity scores, and the model details and parameters such as the vendor model and the temperature [^7].

Both the masked and the unmasked prompt text are kept, and that is exactly why zero data retention and org storage are two different promises. The provider saw only the masked text and kept nothing, while your org keeps both versions so the audit can show what was protected and what was returned. Feedback is stored separately: a thumbs up or a thumbs down with reason text, and actions such as accept, regenerate, modify, or decline, and those feedback records do not include the user data that the audit records do [^7].

The data lands in the default data space of your Data 360 instance. Turning collection on requires Data 360 to be provisioned and Einstein to be on, and the system provisions the data model in a few minutes before it starts collecting; collected data appears in Data Cloud within 24 hours and refreshes hourly thereafter [^8]. Plan for that lag, because a request is not queryable in the audit reports the instant it runs. A team that promises a live audit view and gets a one-day delay has misread the retention model, not found a bug.

### A worked scenario: proving masking to a security reviewer

The requirement arrives as a question. A security reviewer at a financial services org says: prove that a customer's account number never reaches the external model. The builder's first instinct is to answer with masking, because masking is the feature named for exactly that problem. That instinct is half right and, for an agent, wholly wrong.

Reason through it in order. First, name the surface: is this an agent conversation, or an embedded feature such as Service Replies? If it is an embedded feature, masking is available and configurable, so you can point at the masking rule that catches the pattern and show the masked prompt text in the audit record. If it is an agent, data masking for the large language model is disabled, so no rule protects the prompt at the boundary. The control that remains is grounding, because the number can be grounded only if the running user is entitled to see it, plus the design rule that you do not place a raw sensitive value in the prompt at all.

The wrong answer is to promise that masking protects every prompt, the agent included, because the agent is the one case where it does not. The right answer names the surface first, then names the control that actually operates there: masking for the embedded feature, grounding permissions plus prompt design for the agent, and the audit trail as the evidence either way. The reviewer wanted the mechanism, not the marketing line, and the mechanism turns on which side of that one fact the surface falls on.

## Exam Traps

Three misconceptions recur. The first is believing the Trust Layer is a separate product you license or install, when it is built into the platform, so an answer that says you buy or subscribe to it describes the wrong object. The second is believing zero data retention means Salesforce stores nothing, when the agreement covers only the external provider while prompts, responses, and trust signals are logged and stored in Data 360 for the audit trail, including both the masked and the unmasked prompt text. The third is believing secure data retrieval ignores sharing rules, when grounding runs as the user executing the prompt, so role-based access and field-level security still decide what can be grounded.

## What a consultant should walk away with

Name the six features by heart, because the objective is recall before reasoning: zero data retention, secure data retrieval, data masking, prompt defense, toxicity scoring, and the audit trail. Then attach each to its part of the request. Zero data retention covers the provider, grounding and masking cover the data, prompt defense and toxicity cover behavior and safety, and the audit trail covers proof. Design prompts as though masking will not run, because it is disabled for agents.
