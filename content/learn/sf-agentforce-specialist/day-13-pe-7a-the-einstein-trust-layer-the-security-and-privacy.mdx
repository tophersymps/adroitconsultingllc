# Lesson 13: The Einstein Trust Layer: The Security and Privacy Features Around Every Prompt

A delivery team had a working service agent and a security review booked for the same week. The reviewer asked one question that stopped the room: when an end user sends a message, name everything that leaves the org and name what guards it on the way out. The builder could demo the agent and walk the topics. Nobody could list the controls between the record and the external language model, so the review stalled on a gap that had nothing to do with the build.

The cause is that the Trust Layer is deliberately invisible. It wraps every prompt an agent or a prompt template sends and every response that returns, yet it never asks a builder to configure it and never appears as a surface to point at during a demo. Because it works quietly, teams describe it as a vague safety promise instead of a defined set of features they can name and defend.

This lesson names those features one at a time. The objective asks you to identify the security and privacy features of the Trust Layer, a recall question with precise answers, so the goal is six names and what each one does to a single request.

## Deep Dive

### The Trust Layer is an architecture, not a product you license

The Einstein Trust Layer is a secure AI architecture built into the Salesforce platform [^1]. It is a set of agreements, security technology, and data and privacy controls that sit between your org and the external language model. Every prompt an Agentforce agent or a prompt template sends leaves your org through this layer, and every response comes back through it.

That framing rules out a family of wrong answers that treat the layer as something you buy, install, or subscribe to. It ships with the platform, so the work is to turn its features on, configure the ones that need it, and confirm the settings hold. The six features are zero data retention, dynamic grounding with secure data retrieval, data masking, prompt defense, toxicity scoring, and the audit trail, and knowing the six plus what each one does is the whole of this lesson.

### Zero data retention binds the provider, not your own org

Zero data retention is the agreement that governs what the external provider keeps [^2]. Salesforce partners with all of its external model providers, such as OpenAI or Azure OpenAI, so that prompts and responses are not retained by the third party and are not used to train the model or improve the provider's product. No person at the provider reads the data unless Salesforce grants view access in response to documented suspicion of illegal activity or a significant violation of applicable usage policies, and the data is deleted once the response returns to Salesforce.

Read that precisely, because it is the most misread clause here. Zero data retention constrains the external provider. It says nothing about what Salesforce stores for you, and the audit feature keeps prompts, responses, and trust signals inside your org's data platform. An answer that says zero data retention means the org stores nothing has confused the provider's obligation with the platform's record keeping.

### Secure data retrieval grounds under the running user's permissions

Dynamic grounding with secure data retrieval is the data-in side of the layer [^1]. When an agent needs a record's contents to answer, the platform merges the relevant information from the record into the prompt as context. The retrieval does not run above the user's own access. It runs with the permissions of the user executing the prompt, so role-based access controls, sharing rules, and field-level security all stay in force as the grounding data is assembled.

This is what stops an agent from reading a record the running user could not open themselves. The trap is to believe the layer widens access, when it prevents the model from being grounded on anything the running user cannot already see. When a scenario shows an agent surfacing data a user should not have, the defect is upstream in access, not a property of the layer.

### Data masking swaps values before the prompt crosses, and is off for agents

Data masking detects sensitive data and replaces it with a placeholder before the prompt is sent to the model [^3]. Pattern-based detection uses regular expressions and surrounding context words, backed by machine learning models trained to catch values with no fixed pattern, such as names of people or companies. Field-based detection uses the metadata on fields you classified with Shield Platform Encryption or Data Classification [^4]. The placeholder, not the real value, crosses to the model, and the platform restores the value in the response afterward.

One fact settles a whole family of questions: data masking for large language models is disabled for agents [^3]. It remains available and configurable for embedded features such as Einstein Service Replies and Einstein Work Summaries, but with an agent you cannot rely on it, so the discipline is to keep raw sensitive values out of the prompt in the first place.

### Prompt defense and toxicity scoring put a name and a number on safety

Prompt defense is a set of system policies that limit hallucinations and reduce the likelihood of unintended or harmful output from the model [^1]. It includes defenses against prompt injection, where instructions are hidden in the input to make the model disregard its own instructions, and the policies can differ across features and use cases.

Toxicity scoring is the measurable half. The layer scores prompts and responses across five categories, which are violence, sexual, profanity, hate, and physical [^5]. The individual results combine into an overall score from 0 to 1, where 1 is the most toxic, and the score travels back with the response. Naming the categories and the scale matters because the exam treats toxicity scoring as a concrete feature with a numeric output.

### The audit trail is what makes the other five provable

Prompts, responses, and trust signals are logged and stored in Data 360, and the platform ships pre-built reports and dashboards so you can see how the layer protected sensitive data and whether responses were safe [^6]. To read the stored generative AI data, an admin turns on Einstein generative AI data collection and storage and installs the report package. Data in transit between the Salesforce gateway and the model providers is protected with TLS encryption [^2], so the audit trail is what proves the chain worked after the fact.

## Exam Traps

Three misconceptions recur. The first is believing the Trust Layer is a separate product you license or install, when it is built into the platform, so an answer that says you buy or subscribe to it describes the wrong object. The second is believing zero data retention means Salesforce stores nothing, when the agreement covers only the external provider while prompts, responses, and trust signals are logged and stored in Data 360 for the audit trail. The third is believing secure data retrieval ignores sharing rules, when grounding runs as the user executing the prompt, so role-based access and field-level security still decide what can be grounded.

## What a consultant should walk away with

Name the six features by heart, because the objective is recall before reasoning: zero data retention, secure data retrieval, data masking, prompt defense, toxicity scoring, and the audit trail. Then attach each to its part of the request. Zero data retention covers the provider, grounding and masking cover the data, prompt defense and toxicity cover behavior and safety, and the audit trail covers proof. Design prompts as though masking will not run, because it is disabled for agents.
