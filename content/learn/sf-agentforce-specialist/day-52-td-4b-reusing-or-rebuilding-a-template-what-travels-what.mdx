# Lesson 52: Reusing or Rebuilding a Template: What Travels, What Does Not, and How to Decide

A consultant is asked whether to reuse the template the client already has or to build a new one. The instinct is to reuse, because a template exists and rebuilding sounds like waste. But the target org runs a different agent type, the template's actions point at flows that do not exist there, and its grounding model is a data domain the template was never built for. Reusing it would ship a blueprint the org cannot support. Rebuilding, in that case, is the cheaper and more honest path.

The exam asks exactly this kind of choice, and it is not decided by habit. Reuse is not automatically the efficient answer, and rebuild is not automatically the safe one. The right call depends on three things: what the template carries, what the target org already has, and how much of the agent is org-specific. Get those straight and the answer usually falls out of the scenario before you reach the options.

This lesson serves requirement td-4b, the considerations for deploying a template from sandbox to production, in the Testing, Deployment, and Maintenance domain, at ten percent of the exam. It separates the portable core of a template from the org-scoped pieces around it, gives a concrete fit test for reuse and a concrete divergence test for rebuild, and ends with the habit that keeps a shared template from becoming a store of stale assets.

<TLDR>

- The decision turns on three facts: what the template carries, what the target org has, and how much is org-specific
- What travels is the portable core; the agent user, name, channels, connections, and grounding data must be rebuilt
- Reuse only when the agent type, referenced actions, and grounding model fit; otherwise rebuild instead of carrying stale assets

</TLDR>

## Deep Dive

### The choice turns on three facts, not on habit

The exam asks you to choose between reusing an existing template and rebuilding one, and the deciding facts are three: what the template carries, what the target org already has, and how much of the agent is org-specific.[^1] Get those straight and the choice usually falls out. Reuse is not automatically the efficient answer, and rebuild is not automatically the safe one, because the right call depends on whether the blueprint fits the target use case and whether the target org can support the dependencies the template brings.[^1]

Read a scenario for those three facts before you read it for a recommended action. A question that describes a template and a target org is really asking you to compare the blueprint's structure against the target's type and dependencies and then decide. Habit, such as always reusing because a template exists or always rebuilding because imports feel risky, is exactly the reasoning the wrong answers are built on.

The three facts are worth holding apart because the exam probes them one at a time. A question can give you a template that fits the use case but a target org missing the agent type, which kills reuse on the type alone. Another can give you a target org with every dependency in place but a use case that needs different subagents, which kills reuse on fit alone. Reading the scenario for whichever fact is the binding constraint is the whole skill, and it is faster than weighing the three against each other.

### What travels cleanly is the portable core

What travels cleanly is the portable core: the subagents and their instructions, the action set, the filters, the variables, and the default system messages.[^1] These describe the agent's logic rather than the org's data, so they move intact, and the template is designed to be copied from, which is why creating an agent from a template lets you select which of those assets to bring across.[^1]

It helps to think of the portable core as the agent's reasoning rather than its reach. The subagents and their instructions describe how the agent decides, and the actions describe what it may call, but neither names an org's records or its user. That is why the core moves without translation, and why the parts that do not move are exactly the parts that name something org-specific.

When the target org already has the flows, Apex, prompt templates, and objects those actions reference, the template drops in and needs little more than a name, an API name, and an agent user.[^4] This is the case where reuse wins, because the hard part, which is the design of how the agent reasons and acts, is already done and the environment is easy to satisfy. The work of reuse is small precisely when the environment is already prepared for it, and the work of rebuilding is large precisely when that design would have to be re-authored anyway.

### What does not travel is the real work of the promotion

What does not travel forces work in the target org and is the reason a template promotion is never a one-step go-live. The agent user and its permission assignments, the agent's unique name and API name, the channel connections and their deployment plumbing, the external service authentication, and the records and grounding data all live outside the template.[^2][^3] Every one of those has to be created or reconnected in the target org, and any that is skipped produces a production-only failure: an agent that exists and cannot complete the task the scenario expects.[^2]

A short worked list makes the size of the real work visible. One agent user and its permission assignments. One agent name and API name. One set of channel connections and their deployment plumbing. One set of external service authentications. One body of grounding data, or a data library. None of those are in the template, and all of them are required before the agent can do its job, so they are the promotion.

Count those items before you promise a go-live date, because they are the real work of a template promotion. The template is the part that is already finished, and the org-scoped pieces are the part that is not. A consultant who sizes the job by the template alone will underestimate it every time, and a consultant who sizes the job by the org-scoped list, the user, the permissions, the connections, the channels, and the data, will estimate it correctly.

### Reuse a template when the structure fits

Reuse a template when the structure fits, and the fit test is concrete: the target use case shares the subagent layout and action set, the target org has the same agent type and the referenced dependencies, and the org-specific pieces are few and quick to set up.[^1][^4] Under those conditions reuse is right, because you are carrying a proven blueprint into an environment that can already run it. The dependency check is the part teams skip: if the referenced flows, Apex, and prompt templates exist in the target, reuse lands cleanly, and if they do not, you are really deciding whether to build them or to build the agent fresh.[^4]

The mirror of that dependency check is the cost of building the dependencies. If the target org lacks the referenced flows, Apex, and prompt templates, the decision becomes whether creating them is cheaper than authoring the agent fresh, and often it is not, because the template's actions were built against another org's data model and its objects may not map cleanly to the target's.

Reuse is also right when you must stand up the same agent across many orgs that mirror each other, such as a set of similarly configured production orgs that share the agent type.[^6] The package route exists for exactly this shape: you create the template, include it in the package, and create a new agent from it in each target org, so one governed blueprint produces many agents.[^6] When the many orgs are genuinely alike, the reuse path is the one that keeps them alike, and it is the whole reason the template exists as a separate, shippable asset rather than a private build inside one org.

### Rebuild when the structure diverges

Rebuild when the structure diverges, and the divergences are specific. Rebuild when the target org's agent type differs from the template's, because a template is bound to one type and cannot attach elsewhere.[^1] Rebuild when the referenced actions do not exist and recreating them is more work than authoring new ones, when the use case needs different subagents, different routing, or a different grounding model, or when the data model is different enough that a template built for one industry's data model no longer fits another's.[^1]

A useful way to decide is to ask whether the template would need edits that amount to a rewrite. Trimming one subagent is selection, and selection happens at instantiation on the reuse path. Replacing the routing, the grounding model, or most of the action set is not selection; it is authoring, and doing that work inside an imported template costs more than starting clean in the target org, where you would build only the parts you need.

Agentforce Prospecting is the case where the platform itself pushes toward rebuilding. The Prospecting agent does not support deployment through change sets or metadata across environments, and the guidance is to configure the agent in production to mirror the sandbox rather than to ship it.[^5] When the supported path is configuration in the target org, rebuilding is not a reluctant fallback. It is the documented method, and a scenario that names a Prospecting agent is pointing you at exactly that answer.

**Reuse versus rebuild signals**

| Decision signal | Reuse or rebuild |
| --- | --- |
| Same agent type and referenced dependencies exist | Reuse |
| Referenced actions absent and costly to recreate | Rebuild |
| Same subagent layout and action set fit the use case | Reuse |
| Grounding model or data model does not carry | Rebuild |
| Must mirror one agent across many similar orgs | Reuse |

### Treat the template as a maintenance contract, not a shipping crate

Finally, treat a template as a maintenance contract, not just a shipping crate. Whatever the template contains is what every org that builds from it inherits, so a template you keep current is a governance asset, and a template you forget becomes a source of stale assets that every new agent copies.[^1] Because an agent created from a template is built from the blueprint rather than wired to it, the discipline is to keep the template's structure deliberate and current, since the template is a source you draw from rather than a live configuration you edit in place.

![Two-band diagram: at instantiation one template produces three agents that each carry their own org-scoped setup, and after the template is edited only future agents receive the change while agents already built keep their old structure](</diagrams/day-52-td-4b-reusing-or-rebuilding-a-template-what-travels-what/3-template-is-a-source.png>)

The maintenance view changes how you review a template before you decide to reuse it. Instead of asking only whether it fits this one use case, ask whether it is current enough to be the source for the next ten agents built from it, because a template that is several releases stale seeds every new agent with an old design and quietly spreads the staleness across the estate.

That asymmetry is why some teams govern a shared template and drive all new agents from it, while others keep a live agent and push changes through metadata deployment instead. The first approach values consistency across many orgs and accepts that the template is a thing to maintain. The second values a single source of truth for one production agent and accepts that there is no shared blueprint to reuse. Neither is wrong, but the exam expects you to know which pattern a scenario is describing and why the two are governed differently.

### A decision rule you can defend

Pull the lesson into one habit you can say out loud. Name the structure the template contains, name the type and dependencies the target org has, and name the org-scoped pieces you would still have to build. If the structure matches, the type matches, the dependencies exist, and the org-specific work is short, reuse the template and instantiate an agent from it. If the type differs, the referenced actions would cost more to recreate than to author, or the grounding model does not carry, rebuild in the target org and keep only the design you actually want. Either way, the pieces that never travel, the agent user, the name, the channels, the connections, and the data, are your checklist on the far side.[^1][^2][^4]

### The build sequence in six steps

<Steps>

<Step title="List what the template actually contains">

In the source org, list what the template actually contains: subagents, actions, filters, variables, and system messages, and separate those from the agent-specific pieces such as its name and agent user.

</Step>

<Step title="Check the agent type">

In the target org, check the agent type and the referenced flows, Apex, prompt templates, and objects the actions need, and note which already exist and which you would have to build.

</Step>

<Step title="Decide reuse or rebuild">

Decide reuse or rebuild: reuse when the blueprint matches and the dependencies exist, and rebuild when the agent type, the referenced actions, or the grounding model differ.

</Step>

<Step title="Reuse the template and its dependencies">

For reuse, deploy the template with its dependencies, then create the agent from the template, name it, set its API name, and select or create its agent user.

</Step>

<Step title="For rebuild, author the agent or template">

For rebuild, author the agent or template directly in the target org rather than importing assets you would strip later, keeping the subagent and action design you actually want.

</Step>

<Step title="Either way, recreate the org-specific pieces">

Either way, recreate the org-specific pieces in the target org: the agent user and its permissions, external service connections, channel deployments, and the grounding data or data library.

</Step>

</Steps>

## Exam Traps

<Callout kind="warning">

Three traps dominate this objective. The first is believing a template promotion is a one-step go-live, when the template carries the blueprint while the agent user, the agent name, the channels, the external connections, and the grounding data are all created in the target org.[^3] The second is believing you should reuse a template whenever one exists, when reuse is right only if the agent type, the referenced actions, and the grounding model fit, and when rebuilding avoids carrying assets you would only remove.[^1] The third is believing template edits reach agents already built from it: an agent is built from the template as a starting set, so the thing you maintain is the template for future agents, and a team that expects a template change to propagate to running agents is relying on something that will not happen.[^1] Each trap is a boundary error, mistaking the reusable blueprint for the deployed instance.

</Callout>

## What a consultant should walk away with

<KeyTakeaways>

- Reuse when the target shares the subagent layout and action set, the org has the same agent type and dependencies, and setup is short
- Rebuild when the agent type differs, referenced actions cost more to recreate than to author, or the grounding or data model does not carry
- Plan for the org-scoped work that never travels: the agent user and its permissions, the name, the channels, the connections, and the data
- Template edits reach only agents newly created from the template, so keep the template current; agents already running stay unaffected until rebuilt

</KeyTakeaways>
