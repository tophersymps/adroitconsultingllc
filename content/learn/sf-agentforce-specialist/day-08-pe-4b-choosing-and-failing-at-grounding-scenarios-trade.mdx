# Lesson 8: Choosing and Failing at Grounding: Scenarios, Trade-offs, and Failure Modes

A retailer's agent is told to quote the current returns policy, and for three weeks it is flawless. Then the policy changes. The agent keeps quoting the old one, in the same confident tone, because its grounding runs against a search index that refreshes on a schedule and nobody changed the retriever. The team spends a day rewriting the prompt instructions to say use the most recent policy, which does nothing, because the wording was never the problem. The index was serving content from before the change, and the model presented it as current.

The cause is a mismatch between how fresh the requirement is and how fresh the technique can be. Every grounding technique has a trade-off, and the failures all come from ignoring one. A retriever reads an index that updates on a schedule, so a fact that changes often can be served stale. A prompt with no grounding falls back on training data and invents specifics. A retriever tuned too loose pulls in noise that pulls the answer off course. None of these are prompt-writing problems, and none are fixed by rewording.

This lesson is the scenario half of the grounding objective, so it drills the choice and then the failures. Name the requirement, weigh the trade-off that matters most in the case, and match the technique to it. The exam cares because these are the questions where four options all sound plausible and only one matches the constraint the scenario actually names, whether that constraint is freshness, reach, cost, or access.

## Deep Dive

### Scenario skill: name the requirement, then name the technique

This objective is a scenario skill, so read the case, name the requirement, then name the technique. A field value already on the associated record is a merge field. A value computed or fetched across objects is a Flow or Apex resource. A meaning-based search over a large or unstructured corpus is a Data 360 retriever. A quick single-source Knowledge or file library is the Agentforce Data Library[^1].

The wrong options are almost always one of the other techniques, so naming the requirement first is what makes the choice clean. The scenario rarely says to use a retriever. It describes a job, such as always quote the current policy or never repeat a retired refund window, and the job is the key. Translate the described job into one of the four technique shapes before you look at the options, and the distractor techniques lose their grip.

### The trade-offs decide the close calls

When two techniques could work, the trade-offs decide. Merge fields are the cheapest and most deterministic, but they only reach fields on the associated record and cannot search. A Flow or Apex resource is the most flexible, because it can compute and fetch anything, but it adds a run-time step and logic you maintain. A Data 360 retriever reaches large and unstructured content and matches on meaning, but it depends on an indexing schedule for freshness and on Data Cloud permission sets and data spaces for access. The Agentforce Data Library is the fastest setup, but one library holds one data source and offers no real-time or zero-copy capability[^5].

Match the technique to the constraint that matters most. If the scenario stresses freshness, the index-based techniques are suspect. If it stresses reach across many sources, the single-source library is out. If it stresses deterministic exactness, the search-based techniques are out. If it stresses low setup cost, the full Data 360 build is out. The constraint in the scenario is effectively the answer key, and the exam usually names exactly one constraint and leaves the rest as neutral detail, so find the named constraint before you weigh anything else.

### Freshness and reach are the two constraints that decide most scenarios

Most grounding scenarios reduce to two constraints, and naming which one the requirement stresses resolves the choice before you compare features. Freshness asks how current the fact must be. Reach asks how many and which sources the answer must span. When freshness dominates, an index is a liability and a run-time read is the answer. When reach dominates, a single-source library is a liability and a multi-source retriever or a computed resource is the answer.

Walk a scenario both ways to see the difference. A customer asks about their own order status, which is a field that changes by the minute on a record, so freshness dominates and the technique is a field read at run time rather than any index. The same agent must also summarize the product's return policy, which changes once a quarter and lives in a document, so freshness is loose and reach is narrow, and a single-source Data Library over the policy file is enough. Two questions in one conversation, two techniques, and the deciding factor was freshness in the first and a loose single source in the second.

Read every grounding scenario for which of the two it stresses, and state it in one word before you reach for an option. Freshness or reach is usually the whole difference between two answers that both sound correct, and the exam writes its distractors by swapping one for the other.

### Worked scenario: the daily price that kept being wrong

Take a requirement with a freshness trap built in. An agent must always state the current promotional price for a product, and the promotion changes daily. The natural reach is a retriever over the pricing documents, because the price lives in content and the team already indexed the catalog. That choice fails, and it fails silently.

Resolve it with the constraint. The requirement stresses freshness, and a retriever reads an index refreshed on a schedule, so between indexing runs the agent will quote yesterday's price with full confidence[^2]. The correct technique is an action that reads the current price record at run time, so the value is fetched live rather than recalled from an index. The wrong answer is the retriever over the pricing docs, chosen because the data is textual and the retriever was already built. It is wrong because freshness, not content shape, is the deciding constraint, and an index always lags its source.

### Failure one: stale grounding, because the index refreshes on a schedule

The first failure mode is stale grounding, and the daily price is its clearest case. A search index is refreshed on an indexing schedule, so a retriever returns whatever the last indexing run captured[^2]. A price, a policy, or a status that changed after that run is served as if current, and the model presents it with confidence. The fix is to set a freshness expectation that fits the use case, and for any fact that must be live, ground the prompt with an action that reads the record at run time instead of a retriever that reads the index.

Do not try to solve staleness by rewording the prompt, because the wording is not the problem. A prompt that says always use the latest policy will still receive the stale passage the retriever hands it, and the model has no way to know the passage is old. The fix lives in the technique and the indexing schedule, not in the instructions, which is why the opening scene's day of prompt rewriting changed nothing.

### Failure two: no grounding, and its mirror image of the wrong data

The second failure mode is no grounding at all. With nothing pulled into the resolved prompt, the model falls back on its training data: it produces generic phrasing and plausible but wrong specifics such as a hallucinated policy or an invented detail. The fix is to ground the prompt in the data the answer needs, through a merge field, a Flow or Apex resource, or a retriever.

The mirror-image mistake is grounding with the wrong data, such as a field loosely related to the question, which is just as damaging because the model now writes confidently from an irrelevant fact. Presence is not the goal. Relevance is, and the technique must match the question rather than merely exist. A template that grounds with the account's billing city when the question is about renewal risk has technically satisfied the grounding step and produced a worse answer than one that asked for nothing, because the model will weave the wrong fact into a confident sentence.

### Failure three: over-broad retrieval is a configuration problem

The third failure mode is over-broad retrieval. When a retriever returns too much or matches too loosely, the prompt fills with noisy, off-topic chunks that dilute the signal, and the model can be pulled toward an answer from the noise rather than from the relevant passage. Fix it at configuration time, not in the prompt: narrow the retriever to the right data space and source object, filter by metadata such as an id, chunk unstructured content by semantic boundary such as an article section or a call segment rather than a fixed token count, and return only the fields the answer needs.

The specific levers are worth naming because the exam rewards them. Filters narrow the search to more relevant data, an individual retriever can carry up to ten filter conditions, and you configure which fields of data the retriever returns along with the number of results[^3][^6]. You can test these settings before deployment in the retriever playground, where you configure pre-filters, select test data, and tune result parameters against a domain-specific case such as retrieving compliance documents or knowledge articles[^3]. The instinct to move to a larger model, or to tell the prompt to ignore irrelevant parts, is the trap: retrieval quality is a configuration decision, and a tighter retriever usually beats a larger model.

### Access to retrieved content is scoped by data space and permission sets

Access to retrieved content is governed by Data Cloud permission sets and scoped by data space and data category, so scope each library by audience and never rely on the model to redact what a user should not see[^4]. Retrievers also enforce row-level access checks, so a run returns only the data the user is entitled to see rather than everything in the index[^3]. A library that mixes content for different audiences will eventually surface the wrong content to the wrong person, and no prompt instruction will prevent it. Where citations are enabled, the generated answer also links back to the source content so a reader can verify the claim instead of trusting it[^7].

Enforce access at retrieval time, not after. Grounding and access are the same design decision, and a retriever does not know who should read what unless you scope it. This is the same principle that governs merge data elsewhere in Prompt Builder, where access travels with the running user, and it is why a grounding review is also a security review rather than a separate step.

### Retrievers do not travel with the template, so promotion is a trap

Two operational facts close the scenario set. Access scoping is a build step, not a default, and retrievers and search indexes do not travel as prompt-template metadata, so plan to create them in each org before the template that uses them is deployed[^4]. A promotion that copies the template without the retriever lands a template whose grounding does not exist yet, and the failure appears only when a user runs it, well after the deployment looks green.

Grounding that works in a sandbox is not automatically grounding that works in production. Test the deployment path, not just the template, and sequence the org setup so the index and retriever exist before the template references them. In a real build this is the difference between a launch that works and one that fails on day one, and it is why the grounding of a template belongs on the cutover checklist rather than only on the build checklist.

### The failure modes in one decision order

Put the checks in the order a reviewer would run them. First, is the requirement fresh or historical, and does the technique match that freshness. Second, is the prompt grounded at all, and grounded with relevant data rather than merely some data. Third, is the retrieval narrow enough to be signal rather than noise, and if not, which filter or returned field fixes it. Fourth, is access scoped so the run cannot surface content the user should not see. Fifth, will the grounding resources exist in the target org when the template is deployed.

Run those five in order on any deployment and the failure modes stop being surprises. Each one is a question about the requirement and the technique together, not about the prompt wording, which is the theme of this whole lesson and the reason a grounding bug is almost never fixed in the prompt.

## Exam Traps

Three misconceptions recur. The first is believing a retriever returns live data. The index refreshes on a schedule, so a retriever can serve content older than the last change, and a fact that changes often belongs behind an action that reads it live. The second is believing more retrieved context always helps. Over-broad retrieval returns noisy chunks that dilute the prompt, so narrowing the source, the filters, and the returned fields usually improves the answer. The third is believing the model will filter out content the user should not see. Access is governed by Data Cloud permission sets and data spaces, so it must be enforced at retrieval time rather than left to the model.

## What a consultant should walk away with

Name the requirement before you name the technique, then let the constraint in the scenario pick between close options. For a field that already exists, a merge field. For a computed or cross-object value, a Flow or Apex resource. For meaning-based search over a corpus, a Data 360 retriever, with its type following the shape of the question. For a quick single-source library, the Agentforce Data Library. When the requirement is freshness, ground with a run-time action rather than an index. When retrieval returns noise, tighten the configuration rather than the prompt. When access is the concern, scope the data space rather than trusting the model, and when you deploy, sequence the grounding resources ahead of the template.
