# Lesson 17: The Agentforce Data Library: A Retrieval Layer, Not a Knowledge Base

A service operations lead asks for an agent that answers billing questions straight from the help center. The admin opens Agent Builder, points the agent at Knowledge, and considers the job done. In testing, the agent handles the easy questions in general terms, misses a policy that was written only as a PDF the month before, and never cites a source a customer could check. The lead reads the generic answers as a weak model and asks whether a better one can be bought.

The model is not the problem. The Agentforce Data Library is not a Knowledge base wearing a new name. It is the retrieval layer that wires your content to a retriever an agent can call, and it only sees what you point at and what that content is allowed to expose. The two PDFs were never added as a source, several articles were still in draft, and nothing had been surfaced as publicly available, so the library had nothing to retrieve even though the help center looked complete to a human reading it in the browser.

This lesson serves requirement df-1a in the Data 360 Fundamentals domain, which carries 20 percent of the exam. You will learn what a Data Library actually is, the sources it wraps, the objects it provisions, and the four concepts the objective names: grounding, chunking, indexing and retrievers [^1]. The exam tests the concept definitions and the boundary between a library and a Knowledge base, so the goal is precision about what the feature is, not a tour of every button on its setup page.

## Deep Dive

### A Data Library is wiring, not a second knowledge base

The Agentforce Data Library is the configuration surface that connects an agent to your trusted, mostly unstructured content so it grounds answers in your data instead of the model's training set [^2]. Salesforce calls that act grounding: you add domain-specific knowledge or customer information to the prompt so the LLM has context for the request in front of it. A library is not a second knowledge base you populate by hand. It is the wiring.

That distinction decides how you read the whole feature. When you save a library, Salesforce provisions the underlying Data 360 objects for you, so the library is a managed path from your content to a retriever an agent can call [^2]. You never fill a separate store with documents; you point the library at content that already exists somewhere and let it assemble the machinery that makes that content retrievable. The library is the instruction set, and Data 360 is where the instruction set becomes real objects.

On the exam, this is the sentence to hold: a Data Library is the friendly front end, and Data 360 is the engine. The thing you configure in Setup is a set of instructions that materializes as Data 360 objects you can later inspect and edit. If you can describe the library as a managed path rather than a place you store documents, the concept questions resolve cleanly and the distractor that calls it a Knowledge clone reads as obviously wrong.

That lack of grounding is what makes the feature worth configuring. An ungrounded model answers from its training data: it produces fluent, confident and often wrong specifics such as an invented return window or a policy that never existed. Grounding replaces that guess with content the library retrieved, so the model phrases facts instead of manufacturing them. The whole point of wiring a source to a retriever is to move the answer's source of truth out of the model and into your data, and every other concept in this lesson exists to serve that one purpose.

### It indexes content a Knowledge base never held

Compare the two shapes directly. A plain Salesforce Knowledge base stores articles that an author writes and a customer reads; the article is the unit, and the base is the place it lives. A Data Library wraps a source and turns it into searchable, retrievable chunks, and that source can be Knowledge articles and fields, uploaded files such as PDF, HTML and text, web search, or a custom retriever [^3]. The library is a layer over sources, not a container for one kind of content.

The consequence is that a library indexes content that never lived as a Knowledge article. A PDF that a product team wrote and dropped into the org becomes retrievable once you add uploaded files as the source, and a large text field can be chunked and indexed the same way [^3]. None of that content was ever an article, so a mental model that equates the library with Knowledge will miss the cases where the library is doing more than the article base ever could.

The exam leans on exactly this boundary. A data library can point at Knowledge, but it is a broader retrieval layer, not a synonym for Knowledge. When a stem says the agent must answer from uploaded PDFs, or from a blend of articles and a live web source, the library is still the answer, and an option that restricts the library to Knowledge articles is the trap set for candidates who stopped at the name.

### The stack runs Data 360, then Prompt Builder, then the agent

See the library as one link in a three-part chain. Data 360 ingests and indexes the content. Prompt Builder holds the prompt template that references the retriever. The agent invokes the standard action Answer Questions with Knowledge, which uses that template to return sourced, formatted answers [^5]. Each part has one job, and the library automates the first.

![Three linked stages: Data 360 ingests and indexes, building data streams, mapped data objects, a search index and a retriever; Prompt Builder holds the template that references the retriever; the agent invokes the Answer Questions with Knowledge action to return sourced, formatted answers.](</diagrams/day-17-df-1a-the-agentforce-data-library-a-retrieval-layer-not/2-chain-data360-prompt-builder-agent.png>)


What automates means here is concrete. Creating a library pushes data streams to Data 360, maps data objects, and creates a search index and a retriever [^2]. You get the same objects you would build by hand, assembled for you. That is why the library saves days of setup without changing the underlying architecture: it is performing the Data 360 work on your behalf, and the objects it makes are ordinary Data 360 objects you can open and edit.

Read a scenario against the chain and the failure localizes instead of blurring. If the agent answers in generalities, ask which link is weak: was the source added (Data 360), does the template reference the retriever (Prompt Builder), and is the Answer Questions with Knowledge action attached (the agent)? Naming the link is what separates a diagnosis from a guess, and it is the habit that turns a vague "the agent is bad" complaint into a fixable defect.

A worked example makes the chain tangible. Suppose a library is created over a set of help articles, and an agent answers questions about those articles but never about a launch guide that lives as a PDF. Walk the chain: the library pushed a stream against Knowledge, so the PDF was never in its source, and no answer can retrieve content that was never wired. Adding uploaded files as a second source, or building a second library over the files, is the fix, and neither involves touching the model. The chain told you where the content was missing before you changed anything.

### Without Data 360 there is no library at all

There is a hard prerequisite that small orgs discover the expensive way. To use Data Libraries you must have Data 360 set up and activated in the org, and data libraries consume Data 360 credits [^3] [^4]. Without Data 360 there is no vector store, no search index and no retriever, so the library cannot be created at all. The feature is not a standalone add-on you can switch on in isolation.

That is not a licensing formality; it is an architectural fact. The whole value of the library is the objects it builds inside Data 360, and those objects need the platform to exist before they can be assembled. A team that wants a Data Library without enabling Data 360 is asking for a retriever with no index behind it, which is not something the platform offers, however the request is phrased.

Treat the prerequisite as the first line of any plan. Confirm Data 360 is set up and activated, and confirm the credit budget, before you promise a grounding feature to a stakeholder. When a scenario describes a library that stubbornly refuses to be created, the missing or inactive Data 360 platform is usually the cause the question is probing, and the answer is to enable the platform rather than to rework the source.

Credit consumption is part of the same planning conversation, and it is easy to overlook until a billing question arrives. Because libraries draw on Data 360 credits, a grounding feature has a running cost that scales with content and usage rather than a one-time setup fee. The practical takeaway is to treat Data 360 activation and the credit budget as a gating decision made with the business, not an implementation detail discovered after the first library is built.

### Four concepts the exam expects you to define exactly

Salesforce names four concepts you must be able to define [^2]. Grounding is adding the source context to the prompt. Chunking splits a document into smaller pieces. Indexing organizes those chunks so search is fast. A retriever is the pointer that pulls relevant chunks from Data 360 for a feature. Four words, four jobs, and the objective asks for all four.

Knowing where each one lives matters as much as knowing what it does. Grounding happens at the prompt, when the resolved prompt carries your content into the model call. Chunking and indexing happen inside Data 360, when the source is processed into a search index. Retrieval happens at run time, when the retriever queries that index for the agent's request. A candidate who can place each concept at its stage will not be fooled by an option that swaps chunking and indexing or calls the index a retriever.

The later part of this course, days 22 to 26, goes deep on chunking, indexing and retriever mechanics. For this objective you need the shape of each concept and its place in the pipeline, not the tuning detail. If you can say which stage does which job, and hand the fine tuning to the deeper lessons, you have what this objective asks for.

A small image locks the four apart. Picture a single article: chunking cuts it into sections, indexing arranges those sections so a search can reach them quickly, and a retriever selects the two sections that match a question at run time, while grounding is the act of placing those two sections into the prompt. Chunking and indexing happen once, when the content is prepared; retrieval and grounding happen on every request. Holding the one-time steps apart from the per-request steps is the cleanest way to keep the four concepts from running together.

### The packaged action or your own retriever: convenience against control

Two ways to put a library to work answer to different needs, and the exam expects you to tell them apart. The default path is the Answer Questions with Knowledge action plus the retriever Salesforce builds for you, which returns well-formatted, cited answers with little setup [^5]. You attach the action, point it at the library, and the packaged template handles the retrieval and the phrasing.

The other path is to wire a custom retriever into your own prompt template. That is the choice when you need control over the formatting of the answer or over which datasets the agent reaches [^2]. It costs more setup and more to maintain, and in exchange you decide exactly how the retrieved content is shaped into the prompt. A team with a strict house style for answers, or a need to reach one particular dataset among several, is buying that control deliberately.

The exam separates the two cleanly. The packaged action gives you cited answers quickly; a custom retriever gives you flexibility for cases the automatic pipeline does not fit. Neither is wrong, and the deciding question is how much control the use case genuinely needs. When a stem stresses formatting control or dataset selection, it is pointing at the custom path, and when it stresses speed of setup with citations, it is pointing at the action.

### Two sources that behave like exceptions

Two source types break the assumption that every library ingests and indexes content the same way, and they are worth naming before the exam. A Knowledge-based library still requires the source articles to be public and published before they become retrievable [^6]. An author can open a draft that a customer and an agent never can, so a library over Knowledge is only as complete as the published, public set, no matter how many articles the help center appears to hold.

A web search library goes the other way entirely. It is read-only and builds no search index at all, only a retriever [^3]. Because its content is fetched live rather than chunked and stored, there is no index to build, which is why a scenario describing a library that never created a search index is describing web search rather than a Knowledge library that failed halfway through its build.

Keep both exceptions in mind when you evaluate a scenario. The default rule is that most libraries move structured or uploaded content through streams and an index, while these two bend the pattern: Knowledge demands published, public articles, and web search skips indexing outright. Spotting which of the two the stem describes is often the whole question, and the fix in each case is different from the fix for a broken build.

## Exam Traps

Three misconceptions carry the marks. The first is believing an Agentforce Data Library is just another name for a Knowledge base; it wraps Knowledge, uploaded files, web sources, or a custom retriever, so an answer that says it only indexes Knowledge articles is wrong. The second is believing you can create a Data Library without Data 360; every library builds a data stream, a search index and a retriever inside Data 360, so if the platform is not activated the library cannot be created at all. The third is believing a web search data library is built like the others; web search libraries are read-only and create no search index, only a retriever, so a stem that shows a library with no index is describing web search rather than a defective build.

## What a consultant should walk away with

Read a Data Library as wiring, not storage: it points at a source and provisions the Data 360 objects that make that source retrievable. Name the four concepts by their stage, grounding at the prompt, chunking and indexing inside Data 360, retrieval at run time. Confirm Data 360 is set up and activated before you promise the feature, because there is no library without it. Choose the packaged Answer Questions with Knowledge action for cited answers with little setup, and a custom retriever when the use case needs control over formatting or which datasets the agent reaches. And remember the two exceptions: Knowledge-based libraries need public, published articles, while web search libraries build a retriever and no index.
