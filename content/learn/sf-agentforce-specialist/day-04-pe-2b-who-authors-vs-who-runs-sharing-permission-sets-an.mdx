# Lesson 4: Who Authors vs Who Runs: Sharing, Permission Sets, and Record Access

A manager authors and activates a case summary template, runs the preview, and it looks perfect: a clean paragraph naming the account, the history, and the internal assessment. They ship it to the service team. Within an hour a rep reports that the summary comes back missing the whole section the team cared about, and a second rep says theirs threw an error. The template never changed between those runs. What changed was who was running it.

The seam between the authoring role and the run role is where this objective lives. A user with Manage Prompt Templates can edit what a template says but has no automatic audience; a user with Execute Prompt Templates can run what is published but cannot change it. On a small team the same person does both and the seam never shows. On a governed org the two roles separate, and the data each runner can reach decides what their run actually produces. Requirement pe-2b sits in the Prompt Engineering domain at 20 percent of the exam, and it tests the combinations, not the vocabulary.

This lesson drills that seam: the independence of the two rights, why record and field access travel with the runner, the risk surface when grounding runs through a Flow or an Apex action, the preview-passes-production-fails failure, and how to read the scenario questions by naming which role is in play.

## Deep Dive

### The authoring right and the run right are independent

Day three named the controls; now the seam between them. The authoring right and the run right are independent, and every failure mode in this objective comes from assuming one implies the other. A user with Manage Prompt Templates can edit what a template says but has no automatic audience; a user with Execute Prompt Templates can run what is published but cannot change it.

Read every scenario by asking who authors, who runs, and whether the two see the same data [^1]. Those three questions resolve almost every stem in this objective, because the scenario is almost always a mismatch on one of them. The roles can be held by the same person, and often are on a small team, but the platform treats them as separate capabilities.

### Record and field access travel with the runner

The first divergence is data access. A prompt template grounds merge data under the executing user's security: the org-wide defaults, the sharing rules, the role hierarchy, and field-level security all decide what that user's run can read [^2]. So the same activated template can produce a full summary for a manager and a thinner one for a rep with less record access, and neither is a bug.

Record access and field access travel with the runner, not with the template. If a requirement says every rep must see the same grounding regardless of their record access, that requirement asks you to change the runner's access or to filter the data before it is grounded, not to change the template. The template is fixed metadata, and it is the same object for everyone who runs it, which is exactly why two runs can differ without the template differing.

### The Flow and Apex risk surface

That last point is the real risk surface, so make it precise. Merge fields and related data that the template names are filtered by the executing user's access, which is the safe default. But when a template is grounded through a Flow or an Apex action, that action runs under its own context, and it can surface data the runner could not otherwise open [^3].

The documented fix runs the other way too: if a template returns data a user should not see, or omits data they should, add a Flow or an Apex action that filters records before the data is grounded. In other words, granular enforcement is your job at the resource, and the platform gives you the tool to do it. The Trust Layer preserves the standard role-based controls when it merges grounding data, but a resource you write runs with the context you gave it, so review those resources deliberately [^4].

### Preview passes and production fails

The failure mode that the exam loves is preview passing and production failing. A manager authors and activates a template, and Preview runs with the manager's own access, so it looks complete. An end user then runs the same activated template and gets a summary missing the exact field the prompt centers on, or an error, because that user cannot read the record or the field.

The template was never wrong; the access was. The lesson is to test a template as a representative runner, not as the author, and to confirm that every grounding resource resolves for the lowest-access user expected to run it [^2]. A preview that only ever runs as the author tests the author's access, not the feature.

### Over-privileging never fixes a functional gap

A second failure is over-privileging to make a problem disappear. When a rep cannot run a template, the tempting shortcut is to grant Customize Application, which carries prompt permissions but also opens a broad slice of Setup. The correct grant is the narrow one: Prompt Template User for run access, Prompt Template Manager for the people who author.

This is the same principle the whole platform teaches, that a permission set should grant the smallest set of permissions the job needs, and an answer that widens access to fix a functional gap is wrong on the exam and in an org. If a rep cannot run a template, diagnose the actual cause, whether a missing permission or an inactive version, rather than handing out a wide administrative permission.

### Keep the mechanism straight

Keep the mechanism straight while you are at it. Permission sets are additive: they grant capabilities on top of a user's profile without changing it, and you assign them from Setup, which is why they are the delivery vehicle for the two prompt permissions. The org-wide defaults and sharing rules decide record visibility for the runner, and field-level security decides which fields that runner's run can read [^2].

Activation is org-wide in effect: because only one version is active at a time, deactivating the active version withdraws it for every runner at once, which is a blunt lever you should use deliberately rather than per user [^5]. Keep the layers separate and you will not confuse a record access problem with a permission problem or a version problem, which is the most common way a scenario answer goes wrong.

### How to read the scenario questions

Here is how to read the scenario questions. If a user runs a template but sees less than expected, the problem is the runner's record or field access, not the template. If a user cannot run at all, check Execute Prompt Templates and whether a version is active. If a user can run but not edit, that is correct and intended.

If an author's preview looks complete but users get less, you tested as the wrong user. If grounding through a Flow or Apex exposes data the runner should not see, your resource needs a filter. Name which of the two roles the scenario is about and the answer falls out.

## Exam Traps

Three traps dominate this objective. The first is believing the template decides what data a run sees, when the executing user's sharing and field-level security decide it, so identical runs can differ per user even though the template is the same for everyone. The second is believing Preview is a valid user test, when Preview runs with the author's access, so a template that looks complete there can return less for a lower-access runner. The third is believing Customize Application is a safe way to grant prompt access, when it grants the permissions but opens broad Setup access, so the narrow Prompt Template User or Prompt Template Manager set is the correct grant.

## What a consultant should walk away with

Name the role before you answer. If the scenario is about authoring, the permission is Manage Prompt Templates; if it is about running, it is Execute Prompt Templates; if it is about output that differs per user, it is the runner's record and field access, not the template. Test as a representative runner rather than as the author, review any Flow or Apex grounding resource for what it can surface, and fix functional gaps with the narrow grant rather than a wide permission. The template is the same for everyone; the runner's access is what makes two runs differ.
