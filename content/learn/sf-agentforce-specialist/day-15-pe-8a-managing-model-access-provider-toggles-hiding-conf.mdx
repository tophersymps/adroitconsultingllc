# Lesson 15: Managing Model Access: Provider Toggles, Hiding Configurations, and the Agentforce Model Option

An admin was asked to stop a newly connected model from being used before it had been cleared by legal. She found the model in the library, clicked the first control that looked like an off switch, and told the business it was blocked. Two days later a prompt template that no one had touched failed a test run, because the control she had used blocked a whole vendor rather than the one model she meant to pause. The audit that followed cost a week.

The cause is that model access in Salesforce is not one control but several, each with a different scope, and they look interchangeable until one of them takes production down. A provider toggle blocks a vendor org wide. Hiding a configuration removes one model from an author's pick list. The Agentforce model option selects the default the reasoning engine runs on. Reach for the wrong lever and the blast radius is larger than the request.

This lesson separates the levers by scope so you can pick the one that matches the requirement and say exactly what it affects. The objective asks you to explain how to manage and prevent specific models from being accessed, which the exam frames as a scenario about choosing the right control and knowing its reach.

## Deep Dive

### Three levers with three different scopes

Managing model access gets clear once you separate three levers, because most wrong answers confuse them. The first is provider access: which model vendors are allowed to operate in your org at all, controlled by a toggle in Einstein Setup. The second is configuration visibility: which configured models an author can select in Prompt Builder, controlled by hiding or showing a configuration in AI Models [^1]. The third is the org level model option that the Agentforce reasoning engine uses, set in Setup [^4].

Keep the scopes straight and the scenario answers fall out. Provider access is a hard, org wide block. Hiding is a soft block that only removes a model from the author's list. The model option is not a block at all, it chooses the default the reasoning engine runs on. When a question asks how to stop a specific model, the verb tells you which lever is in play: to block, to hide, or to switch.

### The provider toggle is a hard, org-wide block

Provider access is managed in Einstein Setup. From Setup, search for Einstein Setup, turn Einstein on if it is not already on, then scroll to Configure Model Providers and selectively turn providers on or off [^2]. Providers are usually enabled by default, so an admin is normally switching some off rather than on.

When you turn a provider off, its models stop working across agents, prompt templates, APIs, and other generative AI features that reference them, and the platform warns you before the change that affected components will stop running. For Amazon Bedrock specifically, only the Anthropic and Amazon model families are affected by that toggle. The change is not instant: it can take up to ten minutes for model provider disablement to take effect, so re-check rather than assume.

### Hiding a configuration is the narrow, soft block

Hiding a configuration is the narrow control. In AI Models, formerly Einstein Studio, the Model Library lists every large language model configuration, and each row carries a Model Visibility value. To hide one, open the configuration, go to the Configured Models tab, and choose Hide Model from the dropdown. The Model Visibility column then reads Hidden and the configuration name is prefixed with a Not Available marker [^1].

Hiding does not disable the provider and does not stop a template that already uses the model. It removes the model from being newly selected. The classic use is suspending a new or newly connected model until your team finishes testing it, then showing it again when you are ready. To show it, you choose the same Hide Model action to toggle the visibility back. This is the lever to reach for when the requirement is author choice rather than a hard block.

### The Agentforce model option sets the reasoning engine default

The Agentforce model option is the org default for the reasoning engine, and it lives in a different place again. From Setup, in Quick Find enter Audit, Analytics, and Monitoring, open Einstein Audit, Analytics, and Monitoring Setup, and choose an option in the section that selects the model for Agentforce. The setting applies to all Agentforce agents in the org [^4].

The recommended choice is the Salesforce Default option, a managed mix of trusted models optimized for accuracy, trust, and performance. Other options exist, including an AWS hosted option and a Google Gemini option, and if you pick one you update custom agent actions to the matching model for consistency. Because this setting governs the reasoning engine for every agent rather than one pick list, changing it is an org wide decision, not a per author convenience.

### Beta models, in-region routing, and bring your own model extend the set

Two more surfaces extend what you can manage. Beta generative models are not on by default. An admin turns them on in Einstein Setup, after which they appear in AI Models like any managed model. Einstein Setup also offers a setting to enable in-region model requests only, which restricts routing to in-region endpoints for teams with data residency requirements.

Beyond the managed catalog, a bring your own model path lets an admin connect an external OpenAI, Azure, Vertex, or Bedrock model using their own credentials, and an open connector lets you connect a custom built model [^3]. That means the set of models in an org is not a fixed list, which is exactly why governance is about controls rather than about memorizing vendor names. Know the levers, not the catalog.

### Stopping a model means choosing the lever and verifying it took

The prevention question has a short answer once the levers are clear. To stop a specific model from being reachable at all, turn off its provider, which blocks that vendor's models org wide across every surface that references them. To stop authors from choosing it while it stays available to the org, hide its configuration so Prompt Builder cannot present it. To move the reasoning engine off a model, change the model option in Einstein Audit, Analytics, and Monitoring Setup.

Whichever you pick, verify the result rather than trusting the toggle. Confirm the author no longer sees the model, and give a provider change its ten minutes before you call it done. The exam rewards the answer that names the right lever and confirms the outcome, not the answer that flips a switch and moves on.

## Exam Traps

Three misconceptions recur. The first is believing hiding a configuration and disabling a provider are the same control, when hiding removes a model from Prompt Builder selection while the provider toggle blocks the vendor's models org wide across agents, templates, and APIs. The second is believing turning off a provider takes effect immediately, when it can take up to ten minutes for model provider disablement to take effect, so a re-check right after the toggle can mislead you. The third is believing the Agentforce model option is set per agent, when the option in Einstein Audit, Analytics, and Monitoring Setup applies to all agents in the org while per agent and per subagent overrides live in Agent Script.

## What a consultant should walk away with

Three levers, three scopes: the provider toggle blocks a vendor org wide, hiding a configuration removes a model from the author's list, and the model option sets the reasoning engine default. Match the lever to the requirement before you touch anything, so a request to pause one model does not become an org wide outage. Then verify the change took, because a provider change can lag by up to ten minutes.
