# Lesson 18: Getting Data In: Streams, DMO Mapping and File Eligibility

A support team builds a data library over its help center and a folder of troubleshooting PDFs, then waits for the agent to answer. The article answers come back fine. Every question whose answer lives only in a PDF returns a confident but empty paraphrase, and one whole product line is missing. The admin checks the library twice, sees the source selected, and concludes the indexing is broken.

Nothing is broken. The content took two different routes into the library, and only one of them was set up. The helper articles rode a data stream into a data lake object that was mapped to a data model object, while the PDFs needed an unstructured path that references the files where they already live. The product line was missing because a set of articles sat unpublished, and an unpublished article is not eligible to be retrieved no matter how well the library is configured.

This lesson serves requirement df-1b in the Data 360 Fundamentals domain, which carries 20 percent of the exam. You will learn the two doors data enters through, what a data stream is and what it connects to, how mapping turns raw shapes into a common model, and the eligibility rules that decide whether a source is retrievable at all. The exam treats ingestion as an ordering problem, so the goal is to be precise about which object comes before which.

<TLDR>

- Structured rows ride a stream into a DLO and a DMO; unstructured files ride a UDLO into a UDMO
- Mapping is automatic but still mandatory, and the strict build order gates each stage on the one before it
- Eligibility decides retrieval: articles must be public and published, files must be supported types, or content drops out silently

</TLDR>

## Deep Dive

### Data enters through two doors: streams for structure, references for files

Data enters a library through two doors, and keeping them apart answers most of the questions in this objective. Structured data arrives on a data stream and lands in data lake objects, or DLOs, which are then mapped to data model objects, or DMOs, that follow the C360 Data Model [^1]. That is the route for rows and fields: the stream carries them, the DLO holds them in their original schema, and the DMO gives them a standard shape.

Unstructured data is different. It is referenced directly by an unstructured data lake object, or UDLO, which holds metadata for a collection of files rather than the files themselves [^1]. A UDLO does not copy your files into Salesforce; it points at an external blob store and extracts the metadata needed to make the contents searchable. That reference-not-copy behavior is the single most tested fact about unstructured ingestion, because the instinct to assume the platform duplicates your files is wrong.

Keep DLO and DMO for structured content separate from UDLO and UDMO for unstructured content, because the exam swaps the letters to see whether you noticed. A UDLO is created manually and mapped to a UDMO; a DLO is created from the data brought in and mapped to a DMO [^1]. If a scenario describes files being referenced where they live, you are in the unstructured pair, and if it describes rows arriving continuously, you are in the structured pair.

Unstructured files are referenced by a UDLO that holds metadata only and does not copy the files, then modeled as a UDMO. Both routes feed the same search index and retriever.](</diagrams/day-18-df-1b-getting-data-in-streams-dmo-mapping-and-file-eligi/1-two-doors.png>)

**The two routes and their objects**

| Object | Role |
| --- | --- |
| Data stream | Continuously ingests data from enterprise sources |
| DLO | Holds ingested data in its original schema |
| DMO | Standard shape following the C360 Data Model |
| UDLO | Holds metadata for a collection of files, not the files |
| UDMO | Unstructured object the UDLO maps to |

### A stream is a decision about which connector you trust

Data streams are connections that continuously ingest data from enterprise sources, and Data 360 offers over 270 connectors, APIs, SDKs and MuleSoft integration, plus zero-copy connectors that federate read-only access to data already sitting in a partner platform [^3]. A stream is therefore not one thing; it is whichever connection you chose, and choosing it is the first real decision in the build.

For a Knowledge-based library the choice is already made for you in a sense. The stream is created against the Salesforce CRM data source on the Knowledge object, and standard object fields auto-map to the relevant Data 360 data model objects, which saves you the mapping work [^1]. That is why a Knowledge library feels lighter than a custom one: the connector and much of the mapping come preconfigured, and you are mainly choosing which fields and categories to include.

Read the source you pick in a library as a decision about which stream gets created. If you select Knowledge, a stream against Knowledge is provisioned. If you select uploaded files, the unstructured path is provisioned instead. The library hides the connector choice behind a friendly picker, but the connector is still the thing doing the ingesting, and the exam expects you to know that the picker is a proxy for a stream.

Two words worth fixing about streams are continuous and source. A stream is not a one-time export; it keeps the data current as the source changes, which is why the same connector that seeds a library also keeps it fresh. And the source is whichever system you connected, so a question that names an ERP, a data warehouse or a marketing platform is asking you to reason about a stream from that system. When the exam shows a library that is missing recent changes, the stream and its refresh are the place to look, not the retriever.

### Mapping is what gives raw data a common shape

Ingested data is stored in DLOs in its original schema, then mapped to DMOs, which follow the C360 Data Model and ship preloaded with over 300 industry-agnostic objects [^3] [^4]. Unstructured data lake objects are mapped to unstructured data model objects, the UDMO side of the same idea. Mapping is the step that takes varied raw data and gives it the common shape a search index can actually consume.

Why mapping matters is easy to miss. A search index does not query your arbitrary source columns; it works against the harmonized model. Mapping is what makes the fields recognizable and consistent enough to be indexed, segmented or activated. For a data library the mapping largely happens automatically once you pick your sources, but automatic does not mean optional: the mapping still has to complete and be active.

The most common silent failure in a library build is a mapping that is incomplete or inactive, because that is the most common reason a later step in the chain never runs [^2]. The stream succeeds, the objects exist, and then nothing downstream appears. When you diagnose a stalled library, check the mapping before you touch the source, because a half-finished mapping blocks everything after it and leaves no obvious error at the agent.

It helps to think of mapping as translation between two dialects. The source speaks its own field names and types; the DMO speaks the standard Customer 360 language. Mapping is the dictionary between them, and a mapping that is only half written leaves part of the source unable to be understood downstream. That is why the failure is silent rather than loud: the parts that mapped cleanly keep working, and only the unmapped parts vanish, so the library looks mostly healthy while quietly missing a slice of its content.

### Chunking time is the honest cost of a large corpus

Once a search index is created on the UDMO or the DMO, chunking begins. Chunking time depends on the number, size and complexity of the knowledge articles or uploaded files, and on how many knowledge fields you selected for chunking, so a library over a large corpus with many fields builds slowly [^5]. A small library with three fields finishes in minutes; a sprawling one with every field selected can take far longer.

This is not a bug to route around. It is the honest cost of turning documents into retrievable pieces, and the delay is the platform doing real work on real content. The practical consequence is that you size the field selection before you build rather than after, choosing the fields that carry meaning for the questions and leaving the rest out, because every extra field you index adds to both build time and noise.

Treat build time as a design input, not an annoyance. If a stakeholder wants the library live by a certain hour, the number of fields you chunk and the size of the corpus are the levers you have. Naming that tradeoff early, rather than apologizing for it later, is what a consultant does when the corpus is large, and it is the habit the objective rewards.

There is a second reason to care about field count, and it is about answer quality rather than build time. Every field you chunk contributes passages to the index, and passages that carry little meaning dilute the ones that matter. A focused field set makes the search index sharper, so the chunks that surface for a question are more likely to be the sections that answer it. Sizing the fields before the build is therefore both a speed decision and an accuracy decision, and it is the kind of choice a consultant makes deliberately with the business.

### Eligibility is a permissions question as much as a content question

What makes a document eligible for retrieval is a permissions question as much as a content question, and the two are easy to conflate. For a Knowledge-based library the source article must be public and published, surfaced as IsVisibleInPkb being true, and its data categories must be visible [^5]. The running user must also be able to read the Knowledge object and the fields used in the search index [^5]. One missing permission and the content quietly drops out.

Uploaded files carry their own eligibility rule: they must be supported types such as text, HTML and PDF [^2]. A file in a format the platform does not index will not become retrievable just because it sits in the library's source. This is a plain content constraint rather than a permission one, but it produces the same symptom, an agent that ignores a file the team is certain it added.

The word that ties both rules together is silently. A source that fails any of these conditions simply will not be retrievable, which is why an agent can look healthy and still miss content [^5]. There is no dramatic error, only a gap. The discipline is to check eligibility deliberately, article by article and file by file, rather than trusting that a selected source means a retrievable one.

![Eligibility for retrieval. A Knowledge article must be public and published with IsVisibleInPkb true, its data categories visible, and the running user able to read the Knowledge object and the fields in the search index. An uploaded file must be a supported type such as text, HTML or PDF. Failing any check means the source is not retrievable, and the agent silently misses the content.](</diagrams/day-18-df-1b-getting-data-in-streams-dmo-mapping-and-file-eligi/3-eligibility.png>)

A short diagnostic keeps eligibility from being a mystery. Pick one article you expect the agent to use, confirm it is published and public, confirm its data category is visible, and confirm the running user can read the object and every indexed field. If the agent still ignores it, the fault is upstream in the pipeline rather than in eligibility, and you have narrowed the search to the index and the retriever. Running the check on a single article is faster than auditing the whole base, and it usually reveals the pattern behind the missing content.

### The build order is strict, and the status card shows every link

The build order is strict, and the exam rewards knowing it cold. A data stream is created first, then the data lake and data model objects, then the mapping, then the search index, then chunking, then the retriever [^2]. The search index can be created only after the previous steps are successful and active, so if the mapping half-fails, nothing downstream builds at all.

![The strict build order, six steps each gated on the last: data stream, then data lake and data model objects, then mapping, then search index, then chunking, then retriever. A missing retriever means the index was never ready, a missing index means the mapping did not finish, and missing objects mean the stream did not land. Web search is read-only, creates no search index, and gives you a retriever alone.](</diagrams/day-18-df-1b-getting-data-in-streams-dmo-mapping-and-file-eligi/4-build-order.png>)

That ordering is why you cannot debug the pipeline from the top down. If the retriever is missing, the index was never ready; if the index is missing, the mapping did not finish; if the objects are missing, the stream did not land. Each symptom points one step earlier, so the fastest diagnosis is to walk backward from the missing object to the first step that did not reach an active state.

The status card in the library setup page walks you through each stage and links to the underlying Data 360 objects, so you inspect the pipeline rather than guess at it [^6]. That visibility is the feature you lean on in delivery: instead of asserting that the build is finished, you open each stage, confirm it is active, and can point the stakeholder to the exact link that is still pending.

### Web search skips the ingest and index chain entirely

One source skips the ingest and index chain entirely, and it is worth naming because it breaks the order you just memorized. A web search data library is read-only and creates no search index, just a retriever, because its content is fetched live rather than chunked and stored [^7]. There is no stream to land, no DLO or DMO to map, and no index to build, because nothing is being stored in the first place.

That single fact is the whole answer to a certain kind of question. When a scenario describes a library that never created a search index, the expected response is not to hunt for a stuck mapping; it is to recognize web search, where the absence of an index is correct rather than broken. The chain you learned for structured and unstructured content simply does not apply to a live fetch.

Hold the contrast in one picture. Structured content flows stream to DLO to DMO, unstructured content is referenced by a UDLO and modeled as a UDMO, and both then feed an index and a retriever. Web search short-circuits all of that and hands you a retriever alone. Get that map right and the ingest questions answer themselves, because most of them are asking which route the content in the stem is taking.

A quick way to test yourself is to run each source through the routes. Knowledge articles and uploaded files both move through the full chain toward an index and a retriever, though one is structured and the other is referenced. A custom retriever is a route you have already built by hand, so the library adopts it rather than making a new one. And web search skips straight to a retriever with nothing stored. Naming the route out loud turns a confusing scenario into a single choice between four well-defined paths, which is exactly the reasoning the exam is measuring.

### The build sequence in six steps

<Steps>

<Step title="Enter Data Streams">

In Setup, enter Data Streams in the Quick Find box, or open the Data 360 app, and create a data stream from the Salesforce CRM data source, selecting the Knowledge object for a Knowledge based library.

</Step>

<Step title="Review the fields carried">

Review the fields carried by the stream; standard object fields auto-map to the relevant Data 360 data model objects.

</Step>

<Step title="Connect the external blob store">

For unstructured content, connect the external blob store and create an Unstructured Data Lake Object (UDLO) that references the files.

</Step>

<Step title="Map the UDLO">

Map the UDLO to an Unstructured Data Model Object (UDMO) so the content takes the C360 Data Model shape.

</Step>

<Step title="Create a library">

In Agentforce Data Library, create a library and pick the source; Salesforce creates the stream, objects and mapping for you.

</Step>

<Step title="Confirm the objects are active">

Confirm the objects are active in Data 360 before relying on the search index, because indexing fails if any prior step is not active.

</Step>

</Steps>

## Exam Traps

<Callout kind="warning">

Three misconceptions carry the marks. The first is believing a UDLO copies your files into Salesforce; a UDLO references the unstructured data where it already lives and extracts metadata, so it does not duplicate the underlying files. The second is believing any Knowledge article is retrievable once you point a library at Knowledge; the article must be public and published, its data categories visible, and the running user must have read access to the object and the indexed fields. The third is believing the search index builds in any order; the data stream, the objects and the mapping must all be successful and active before the search index can be created, because a half-finished mapping blocks every step after it.

</Callout>

## What a consultant should walk away with

<KeyTakeaways>

- Name the route before the object: structured content rides a stream to a DLO then a DMO, while files are referenced by a UDLO to a UDMO
- A UDLO references unstructured data where it already lives and extracts metadata, so it does not copy or duplicate the underlying files
- A Knowledge article is retrievable only when it is public and published, its categories are visible, and the running user can read the object and indexed fields
- The search index builds only after the stream, the objects and the mapping are all successful and active, so a half-finished mapping blocks every later step

</KeyTakeaways>
