# Lesson 39: Employee Agents and Service Agents: The Two Audience Types and What Separates Them

A services firm decided it wanted one smart assistant. It would answer HR policy questions for staff in Slack and, on the marketing site, deflect customer support questions, all from a single agent built once. The build looked tidy in the demo. In production it broke in two directions at once: the Slack version could not read the internal knowledge articles it needed, and the public version, running as the same agent user, could reach customer records an anonymous visitor should never see. The team had optimized for one build surface and ignored the fact that the two audiences require two different identities.

That is the trap this objective sets. Agentforce ships agent templates, and the certification asks you to choose between the two the exam cares about: the Agentforce Employee agent and the Agentforce Service agent. The employee agent is built to help people inside your company with company knowledge, task execution, and workflow steps across departments. The service agent is built to serve external customers and partners, answer their inquiries, and escalate the issues it cannot resolve. Both are authored in Agentforce Builder with subagents, the current name for topics, plus actions and instructions, so the build surface looks similar. What differs is who they serve, which channel carries them, and which security identity they run under at run time.

This lesson serves requirement ag-7a, "Given a scenario, identify when to use an Employee or Service agent," in the AI Agents domain at 35 percent. The scenario is always a question of audience, and the audience always implies an identity. By the end you can name the running user for each type, read a scenario for the channel that goes with it, handle the credential-based-verification case where a service agent changes identity, and reject the neighbouring templates the exam offers as distractors. Lesson 40 turns the same requirement into the design decision, including what each type can actually reach.

## Deep Dive

### Two templates, one build surface, two audiences

The employee agent and the service agent are separate agent types with separate default templates, and the type is what fixes the audience. An employee agent template is built for internal users and is designed to run in the logged-in user context, and you can assign each employee agent to specific profiles or users so that only the right staff see it.[^5] A service agent template is built to support external customers, connect to messaging channels, and escalate to a human when needed.[^2]

Because both are built in the same builder with the same kinds of subagents, actions, and instructions, the difference is easy to miss if you read a scenario for the build. Read it instead for the audience. A scenario phrased around enabling staff is an employee agent. A scenario phrased around serving, deflecting, or escalating customer cases is a service agent. The build surface is identical enough that the exam will describe a plausible agent and expect you to decide by who is on the other side of the conversation.

This is the first and most important habit for the objective: decide the audience before you evaluate any other detail. Channel, verification, escalation, and permissions all follow from the audience, so choosing the audience first keeps the rest of the scenario consistent.

The labels themselves are worth reading literally. The word employee names the audience, not the channel or the license, and the word service names the relationship, a customer being served, not the department that built the agent. When a scenario uses neither word, the giveaway is who the conversation is for, and the exam expects you to supply the missing label from the audience rather than from the build details.

### The running user is the fact that separates the two types

The running user is the fact that separates the two types, and it is the fact most scenario questions turn on. An employee agent runs as the logged-in end user, so every action and every record read happens under that person's profile, permission sets, field-level security, and sharing rules. A service agent runs as a dedicated agent user, a service identity the org provisions, because an external visitor on a web widget has no Salesforce login.[^1]

The agent user carries its own profile, permissions, field-level security, and sharing, so you grant it exactly the access the customer conversation needs and no more. Its name and profile are fixed by the platform, and it is created with minimal access so that the agent is secure by default.[^2] When the exam asks who the agent acts as, the answer follows the audience: the logged-in internal user for an employee agent, the agent user for a service agent.

Make the identity concrete with an example. A sales operations lead builds an employee agent that looks up her team's pipeline, and she can see every opportunity in her division. A rep on her team asks the same agent for the same pipeline and sees only the rep's own deals, because the agent runs as the rep, and the rep sees fewer opportunities. The agent was not misconfigured; it faithfully reflected two different users. Hold that example, because a scenario that says one agent gives two people different answers is describing the running user at work.

Hold this as a rule rather than a fact to recall. The audience determines the identity, and the identity determines everything the agent can reach. If you can name the running user for a scenario, you already know which of the two agent types it describes.

### Channels are the visible clue in the scenario

Channels differ too, and the channel is often the visible clue in a scenario. An employee agent reaches Lightning Experience, the Salesforce mobile app, Slack, and Enhanced Web Chat placed on Experience Cloud sites. A service agent reaches the enhanced messaging channels, including Enhanced Chat v1 and Enhanced Chat v2, which are the surfaces that support authenticated and unauthenticated external users.[^1]

Read the scenario for where the conversation happens. An agent on a public marketing site talking to anonymous visitors is a service agent, and an agent answering questions inside the Salesforce app for your own reps is an employee agent. An agent deployed in Slack for internal staff is an employee agent, because Slack is an internal channel in this sense. The channel does not decide the type on its own, but it usually confirms the audience you already inferred.

There is a second reason the channel matters beyond confirming the audience: the channel is often what your integration and rollout plan depends on. An employee agent on Slack needs the Slack surface enabled and the staff assigned to the agent, while a service agent on Enhanced Chat needs the messaging deployment and the Omni-Channel routing in place. The channel therefore predicts the setup work as well as the identity, which is why a scenario that names a channel is usually testing whether you drew the right two conclusions from it.

One caution: do not split by channel alone. The split follows the audience and the identity, and the channel is a symptom of the audience rather than its cause. A scenario that says the conversation is internal but names a messaging channel is testing whether you trust the audience over the surface.

### Credential-based verification is where a service agent changes identity

Credential-based user verification is the one case where a service agent stops running as the agent user and starts running as a logged-in site user. When the flow verifies the customer against a site login, the agent runs under that verified user's profile, permissions, field-level security, and sharing for the rest of the session, which is how a customer sees only their own orders.[^1]

Without that verification, the agent user's grants govern, and the conversation must be scoped so an anonymous visitor cannot reach another customer's data. A scenario that says the customer must see only their own account is pointing at credential-based verification on a service agent, not at an employee agent. The two are different mechanisms answering different questions about identity: one borrows the customer's own access, and the other uses a shared service identity with tight grants.

This nuance is worth stating precisely on the exam, because it is the exception that makes the rule testable. The default answer for a service agent is the agent user; the qualified answer, when identity is verified, is the logged-in site user. Name both and say which applies.

### Read the scenario in one order: audience, identity, channel

Run every scenario through the same three questions in the same order. Who is the conversation for: staff inside the company, or customers and partners outside it. Given that audience, which identity does the agent run under: the logged-in user for staff, the agent user for customers, or the verified site user when credential-based verification is in play. Given that identity, which channel carries the conversation: an internal surface such as Lightning, mobile, or Slack, or an enhanced messaging channel for external users.

The order matters because each answer constrains the next. Deciding the channel first is the mistake the opening scene made, because a channel can be made to host more than one audience if you force it to. The audience does not flex, and it settles everything downstream. When two agent types seem to fit, the audience question breaks the tie, and the identity confirms it.

Practice the order on a one-line brief. A scenario that says customers on the company website need help with billing is a service agent, running as the agent user, on an enhanced messaging channel, unless the customer is asked to sign in, in which case credential-based verification moves the identity onto the customer's own access. Four clauses, four answers, and the type is settled before any action is named.

### Reject the neighbouring templates before you answer

Not every agent is one of these two types, and the exam offers neighbouring templates you must reject. The Lead Nurturing agent, historically the SDR agent, runs outbound email to prospects on its own agent user and is a different template with a different job.[^3] The Agentforce (Default) agent is retired: it takes no new features and the guidance is to migrate those agents to the employee agent.[^4] Setup with Agentforce is an internal assistant context rather than a customer-facing agent.

Read the distractor for its channel and its running user as well as its job. The lead nurturing agent runs outbound email, which is a channel the two primary types do not use for outreach, and it runs as its own agent user with a different name. A scenario that describes proactive email to people who have not asked to be served is not a service agent, because a service agent responds to inquiries rather than initiating campaigns.

When a scenario describes outreach to cold prospects over email, the Lead Nurturing agent is the fit, not a service agent. When it describes a general internal helper that used to be built on the default agent, the employee agent is the successor and the answer should name the migration path rather than the retired template. Recognizing these distractors is as important as knowing the two primary types, because a wrong answer often names a template that exists but serves a different audience.

So the full choice is a small set: employee agent for internal staff, service agent for external customers and partners, lead nurturing for outbound email to prospects, and the retired default rejected in favor of the employee agent. Everything else is a narrower skill or assistant template, not the audience decision this objective tests.

### Two housekeeping facts ride along with the choice

Two housekeeping facts ride along with the choice. Managing and building agents depends on the Manage AI Agents permission, which grants org-wide control of every agent, so it is assigned sparingly rather than to every admin. Consumption is metered in Flex Credits, and each standard or custom action the agent runs in a text conversation counts as an action for billing, so an agent that chains many actions costs more to run than one that answers from knowledge alone.[^2]

Flex Credits are worth a second look because they turn an architecture choice into a cost choice. A customer-facing service agent that answers from the Agentforce Data Library with no action chaining spends far less than one that calls three actions per turn to look up an order, apply a credit, and send a confirmation. When a scenario asks which of two service agents is cheaper to run, the answer is the one that resolves more from knowledge and calls fewer actions.

Neither detail decides the agent type, but both appear in implementation questions, so keep them attached to the choice rather than treating them as separate trivia. The Manage AI Agents permission is the one to watch, because it is easy to grant casually and hard to justify, since it reaches every agent in the org rather than the one being built.

Keep the whole objective in one sentence: read the scenario for who the conversation serves, let the audience pick the template, and let the template pick the running user. The audience is the question, and the identity is the answer.

## Exam Traps

Three misconceptions carry the marks. The first is believing an employee agent can serve anonymous website visitors, when it runs as the logged-in user and therefore needs an authenticated internal user, so an unauthenticated external audience belongs to a service agent. The second is believing a service agent always runs as a guest or agent user, when credential-based user verification makes it run as the verified site user and inherit that user's access for the session. The third is believing Agentforce (Default) is still the general template to build on, when it is retired with no new features and the migration path is to the employee agent.

## What a consultant should walk away with

Read every scenario for the audience before you read it for anything else: staff means an employee agent, and customers or partners means a service agent. Let the audience pick the template and the template pick the running user, the logged-in person for an employee agent and the agent user for a service agent, and let the channel confirm what the audience already told you. Remember the one exception, that credential-based verification on a service agent switches it to the signed-in site user so a customer sees only their own records. Reject the distractors: lead nurturing for outbound prospect email, and the retired default agent replaced by the employee agent. Keep Manage AI Agents assigned sparingly because it reaches every agent, and remember that consumption is metered in Flex Credits per action. Name the audience, the identity, and the channel, and the scenario answer is complete.
