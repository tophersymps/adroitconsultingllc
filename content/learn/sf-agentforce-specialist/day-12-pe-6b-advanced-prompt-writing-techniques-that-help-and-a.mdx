# Lesson 12: Advanced Prompt Writing: Techniques That Help and Anti-Patterns That Fail

A team ships a prompt that packs an entire case, its full history, and three unrelated instructions into one block, and the replies come back missing a requirement here and inventing a policy detail there. The prompt looks thorough. It is long, it is detailed, and it fails for two reasons anyone can name once they see the levers. The requirements had no structure, and the context drowned the signal.

The cause is that prompt quality comes from a small set of specific techniques, not from effort. When a prompt underperforms, the fix is almost always one identifiable lever, and the anti-patterns that look careful each fail for a reason you can point at. This is the advanced half of prompt writing: naming the technique that maps to the defect.

This lesson covers requirement pe-6b in the Prompt Engineering domain: structured instructions, an explicit output shape, paired constraints, injected context, worked examples, and the anti-patterns that quietly fail. The exam tests the technique, not the platitude, so learn to diagnose before you rewrite. Where it helps, the lesson shows a before and after of the same prompt so the effect of a lever is visible rather than asserted.

## Deep Dive

### Five levers move output quality

This lesson takes the advanced half of the objective, so it drops the general advice and names the specific techniques that actually change output quality. There are five levers: structured instructions, an explicit output shape, constraints, injecting the right context, and worked examples [^1]. Structured instructions split the prompt into a role, a task, and a format block, so the model can follow several requirements at once without dropping one. The output shape names what the answer should look like. The constraints name what it must avoid. The injected context grounds the answer in real data. The examples set tone and format by pattern.

Almost every lever that moves quality is one of those five. Read a weak prompt and you can almost always name the missing lever, which is the skill this objective rewards. A prompt that feels detailed but still underperforms is missing one of the five, not more words.

The exam's phrasing points the same way. Its scenarios describe a symptom, such as a dropped requirement or a rejected parser output, and ask which technique fixes it. The answer is never more effort; it is the one lever whose absence matches the symptom. So learn each lever by the failure it prevents, and diagnosis becomes mechanical.

### Structured instructions give the model a checklist

Structured instructions are worth seeing concretely. Write a role line that sets the model's perspective, a task line that states the single job, instruction lines that list the requirements, and a format block that lists the exact output sections. Keep the order stable so the same prompt is reusable and easy to update [^1].

The reason structure helps is that a flat paragraph of requirements invites the model to satisfy the ones it notices and drop the rest, whereas a labeled block makes each requirement visible and gives the model a checklist to work through. A prompt with several requirements and no structure is where output quietly goes wrong, because the failure is a dropped instruction rather than a wrong answer.

Salesforce's guidance on a template's ingredients backs the same design from the other direction: keep the instructions in their own labeled section, apart from context, and surround them with triple quote boundaries so the model can tell instructions from data [^5]. The boundary is the trick that keeps instructions and grounding from bleeding together when both appear in the same prompt.

### Before and after: restructuring a prompt that dropped requirements

Compare two versions of the same request. The before is a single run-on line: Write a follow-up email to this customer and mention the open case and be friendly and keep it short and do not promise a delivery date. The after is the same requirements in labeled sections: Role, a customer success representative; Task, draft a follow-up email about the open case; Instructions, acknowledge the open case, use a friendly tone, and do not promise a delivery date; Format, a subject line and a body of no more than 120 words.

The before reads as one errand, so the model tends to satisfy the opening verbs and quietly drop the trailing constraint, which is exactly how the delivery-date promise slips through. The after gives each requirement its own line, so the model works the list and the constraint survives alongside the task. Same content, same author, different structure, and the difference in compliance is the whole point.

The lesson is that a dropped requirement is usually a structure defect, not a model defect. When output omits something you asked for, the first fix to try is not a stronger restatement; it is breaking the request into labeled sections so nothing hides in the middle of a sentence.

![The same request written two ways: one run-on line that quietly drops its trailing constraint, and four labeled sections for role, task, instructions and format that keep the constraint in view](</diagrams/day-12-pe-6b-advanced-prompt-writing-techniques-that-help-and-a/2-before-after-structure.png>)

### An explicit output shape is a contract

An explicit output shape is the technique most writers skip and then regret. Name the shape, not just the content: a numbered list of five items, a two-sentence summary, a subject line plus a plain-text body, or a JSON object with named keys. If a downstream system parses the output, the shape is a contract, and a prompt that leaves it implicit produces a response the parser rejects, which then reads as a model failure when it is a prompt failure.

Naming the shape up front also lets you compare two prompts on equal footing, because the only thing that changes is the content, not the format. That is how you isolate which edit actually improved the answer.

A JSON request is the sharpest example, because it fails loudly. A downstream system that expects named keys will throw on a sentence, so the prompt must state the object and its keys, and the response preview becomes your test. Loud failure is easier to fix than quiet failure, which is why an explicit shape belongs in every prompt whose output something else consumes.

### Constraints work as a pair, positive and negative

Constraints narrow the space the model explores, and the useful ones are positive and negative together. State what the response must include and what it must avoid: no speculation, no promises the business cannot keep, no content outside approved data, no technical jargon [^2]. A constraint paired with its positive counterpart steers the response, while a negative instruction on its own leaves the space open, and the model fills it, often with exactly the thing you asked it to avoid.

Length is a constraint too, and giving a length target is more reliable than asking for a summary and hoping it comes back short. When you say keep it to two sentences, you have removed the ambiguity that made the output unpredictable.

The pairing rule is the part people resist, so state it plainly. Do not mention competitors forbids one thing and guides nothing; say instead, describe only our published plans and do not mention competitors by name. The positive half tells the model where to go, and the negative half tells it where not to. A constraint with only the negative half is an instruction to avoid a void.

### Before and after: pairing a negative instruction with a positive one

Watch the pairing fix a real defect. The before is a lone prohibition: Do not give legal advice in the reply. What comes back often hedges around the question without answering it, or substitutes a different overreach, because the model avoided legal advice and had nothing positive to write instead. The after pairs the halves: Answer only from the approved help-article content, and if the question needs legal advice, tell the customer a specialist will follow up. Do not state or imply specific legal outcomes.

The before narrows the forbidden space and leaves the required space untouched, so the model improvises a filler reply. The after defines what to do, what to do when the boundary is reached, and what to avoid, so the reply stays useful inside the boundary. The negative half is the guardrail; the positive half is the road.

This is the anti-pattern behind the trap the exam keeps setting. An option that only forbids is weaker than an option that forbids and directs, and the difference shows up in the output, not just in principle.

### Injecting the right context is the strongest lever

Injecting the right context is the most powerful technique of the five, because grounding is what makes an answer specific and true. Pull the facts the answer needs, such as the record fields or the retrieved passages, and reference each one a single time [^3]. Too little context produces generic answers, and the wrong context, such as an unrelated field or an over-broad retrieval block, actively misleads the model into writing confidently from the wrong fact.

The move is to match the grounding to the question, exactly as a merge field, a Flow resource, or a retriever is chosen on day seven, and then to trust that context rather than restating it in the prose. Context and grounding are the same decision seen from two sides, and injecting the specific fact beats stuffing the prompt with the whole record. The workspace resolves those resources into the prompt before the model sees it, so what you inject is literally what the model reads [^4].

The reason this lever is the strongest is that it changes the facts the answer is built on, not just its shape. A structure fix improves how requirements are followed. A context fix changes whether the answer is true. When a response is confidently wrong rather than sloppily right, the lever to reach for is grounding.

### The anti-patterns each fail for a nameable reason

The anti-patterns look reasonable and fail in predictable ways. Vague instructions such as help with this customer issue leave the task undefined. Bundling several unrelated tasks into one prompt splits the model's attention. Conflicting instructions, such as asking for brevity and a full explanation in the same prompt, cancel each other out. Negative-only instructions forbid without guiding. Stuffing the prompt with the whole record and the full case history dilutes the signal until the relevant fact is buried. Repeating the same data invites inconsistency. And asking the model for a fact that should have been grounded with, such as an account status it cannot know, produces a confident guess [^2].

Each of these feels careful, and each fails for a reason you can name. That is the exam's real test here: not whether you can recite a best practice, but whether you can point at a defect and name the lever that fixes it.

Two more anti-patterns round out the set. Reusing one prompt for tasks that need different shapes forces a single format onto work that wants several, and copying an example template without trimming it leaves instructions that no longer apply to your use case. Starting from an example is a good move [^6], but the customization is where the prompt becomes yours, and an untrimmed example carries requirements you never intended.

### Worked scenario: the parser that kept rejecting the output

A downstream system parses an agent's output as JSON, and the parser keeps failing in test. The team assumes the model is unreliable and raises temperature experiments, then adds a longer role description, and the failures continue. What is the actual defect, and what is the correct fix?

Diagnose against the levers. The parser fails on shape, and nothing the team has changed touches shape. Temperature and a longer role description address tone and perspective, not format, so the output keeps arriving in a shape the parser cannot read. The missing lever is the explicit output shape: the prompt never states that the response must be a JSON object with named keys.

The wrong answers are the ones that reach for model changes. A larger model or a raised temperature does not fix a prompt that never declared the contract, and removing constraints makes the output less predictable, not more. The right fix states the object and its keys in the prompt, then uses the response preview to confirm the shape before wiring the parser. Structure fixes compliance, and shape fixes parseability; keep the two levers distinct.

## Exam Traps

Three traps dominate this objective. The first is believing be clear and specific is enough. The levers that change quality are concrete: structured sections, an explicit output shape, paired constraints, worked examples, and the right grounding, so a prompt with none of those underperforms a well-structured one even if it reads clearly. The second is believing a negative instruction alone steers the model. Do not mention competitors leaves the space open, so it must be paired with a positive instruction about what the response should say instead. The third is believing more context is always safer. Over-broad or repeated context dilutes the prompt and can mislead the model, so inject the specific facts the answer needs and reference each one once. The three share a shape: a prompt that feels careful but omits the lever that would have fixed it.

## What a consultant should walk away with

Name the lever that maps to the defect you see. If the model drops a requirement, add structure. If the output cannot be parsed, name the shape. If the response ignores the boundary you set, pair the negative constraint with a positive one. If the answer is generic or wrong, fix the grounding rather than the wording. If the tone drifts, add worked examples. Structure, output shape, paired constraints, the right context, and worked examples are the five levers, and every anti-pattern on this objective fails because one of them is missing. When a prompt underperforms, diagnose before you rewrite, because the fix is almost always a specific lever rather than more words.
