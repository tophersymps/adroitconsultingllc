# Lesson 9: Creating, Activating, and Executing Prompt Templates

A sales operations lead builds a case summary prompt, clicks Save, and tells the service team it is ready. Two days later a rep opens a case record and finds nothing. The template exists, it previewed perfectly in the author's browser, and it is still invisible to the floor. Nothing was broken. One step was simply never taken.

The cause is that a prompt template is not usable the moment you save it. Saving creates a draft version, and a draft is not published. A template becomes a feature only after you activate a specific version and then invoke it from a surface that consumes it, and those are three separate moments in one lifecycle: create, activate, execute.

This lesson walks that lifecycle end to end in Prompt Builder, from choosing a type to reading the resolved prompt to wiring the activated asset into a Flow or an agent. It serves requirement pe-5a in the Prompt Engineering domain, and the exam tests the sequence: which association a field generation template needs, what the resolved prompt contains, and how an activated template is invoked.

## Deep Dive

### A prompt template is a named asset, not a chat message

A prompt template is a reusable, named prompt that you build and manage in Prompt Builder, with placeholders for the details that change, such as a customer name or a product price [^1]. It is not a message you type into a chat window. It is metadata that lives in the org with a name, a type, a version history, and an activation state, which is what lets you test it, version it, govern it, and reference it by name from automation.

The lifecycle runs in four moves: create, test, activate, execute. You choose a type and create the template, test it against sample data, activate a version to make it available, and invoke it from a consuming surface. The first time you save a new prompt it becomes Version 1, and its status sits at Inactive in Prompt Builder until you activate it, at which point it reads Active. Inactive and Active in the workspace map to Draft and Published in metadata terms, the vocabulary the exam uses for deployment.

### The type and the object decide what you can bind

Creating starts with two choices that constrain everything after: a template type and an associated object. The classic types are Field Generation, which helps a user complete a specific field, Record Summary, which summarizes a record, Sales Email and Case Email Draft, which produce email, and Flex, the freeform type that runs on an object or from a flow. A Field Generation template requires both an object and the field to complete, while the other types need only the associated object [^2].

The object you associate decides which merge fields are available, so pick it before you write the prompt. Attach a template to Case and the Contact fields you wanted are simply not on the resource list. The type is chosen at creation and it fixes the binding and the entry points for the life of the template, so the decision is hard to undo. For the exam, hold one detail tight: the two associations a Field Generation template needs are the object and the field to complete, and a question that offers a flow and an Apex class is testing exactly that.

### Author in the workspace and preview the resolved prompt

Authoring happens in the Prompt Template Workspace, where you write instruction text and insert resources for grounding: merge fields, related lists, flows, Apex, Data 360 data model objects, and files [^3]. Merge fields use the braces and leading exclamation syntax, so a reference to a company name or an input field resolves at run time.

Then you test with sample data. Choose a sample record, click Save and Preview, and read the resolved prompt. The resolved prompt is the template with its merge fields replaced by that record's real data, and it is what actually gets sent to the LLM, so it is the only honest preview of what a user will receive [^1].

### Activation is the switch that makes the template real

Activation is the step that makes the template usable, because a template is not available to users by default. When you activate, you make one specific version available to the surfaces that consume it. Only one version of a template can be active at a time, and if no version is active the template becomes unavailable [^4].

Activating also makes that version immutable. You cannot edit an active version in place, no matter how small the change; to change an active template you save a new version and activate that. Day ten takes the version operations apart in detail, but the rule you need here is simpler: getting activation right is the difference between a finished template and a draft that nothing can call.

### Execution turns the template into a feature

Every saved and activated prompt template is exposed as an invocable action, which is how it becomes part of an app [^5]. From Flow, you use the regular Actions element and filter the list by the Prompt Template category, passing the associated record as a related entity. From an agent, you add a Prompt Template reference action, bind the inputs and outputs, and mark at least one output to show in conversation [^6].

From Agent Script, the action target is generatePromptResponse:// followed by the template developer name, inputs are referenced as Input: followed by the api name, and the standard output is promptResponse [^7]. Apex and the REST API can also invoke a template. Because each of these points at the template by name, the version that runs is always the active version, which makes activation the real control surface and execution just the wiring.

### Under the hood, the template is versioned metadata

A prompt template is stored as the GenAiPromptTemplate metadata type, which carries one or more versions, an active version, a type, and the associated entity, with a separate related field for field generation [^5]. Because the template is a named, versioned asset, changing the prompt is a version operation rather than a code change, and invoking it from a flow or an agent is a reference to that asset.

The line to remember is that the template text itself never reaches the model. The resolved prompt does, and the active version is the one that resolves. That single fact explains why an unactivated template does nothing and why activating a different version changes every consumer at once.

## Exam Traps

Three traps dominate this objective. The first is believing a saved template is immediately usable. A template stays inactive until you activate a version, and a template with no active version is unavailable to every consuming surface. The second is believing you can activate more than one version at a time. Only one version is active at a time, so activating a different version replaces the one before it. The third is believing the template text is what the LLM receives. The resolved prompt, with the merge fields replaced by real org data, is what is sent to the model, so a template that previews wrongly will also run wrongly.

## What a consultant should walk away with

Treat a prompt template as an asset with a lifecycle, not a prompt you type once. Choose the type and object first, because they fix what you can bind. Ground the prompt with the resources it needs, preview the resolved prompt against a real record so you see what the model sees, then activate exactly one version. When the output is right, invoke the template by name from a Flow Action under the Prompt Template category, an agent reference action, Agent Script, Apex, or the REST API, and let the active version drive every consumer.
