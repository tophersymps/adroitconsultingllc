# Lesson 9: Creating, Activating, and Executing Prompt Templates

A sales operations lead builds a case summary prompt, clicks Save, and tells the service team it is ready. Two days later a rep opens a case record and finds nothing. The template exists, it previewed perfectly in the author's browser, and it is still invisible to the floor. Nothing was broken. One step was simply never taken.

The cause is that a prompt template is not usable the moment you save it. Saving creates a draft version, and a draft is not published. A template becomes a feature only after you activate a specific version and then invoke it from a surface that consumes it, and those are three separate moments in one lifecycle: create, activate, execute.

This lesson walks that lifecycle end to end in Prompt Builder, from choosing a type to reading the resolved prompt to wiring the activated asset into a Flow or an agent. It serves requirement pe-5a in the Prompt Engineering domain. The exam tests the sequence rather than any single screen: which two associations a field generation template needs, what the resolved prompt actually contains, which version a consumer runs, and how an activated template is invoked from a Flow, an agent, or Agent Script. Read the four moves as gates, because a template cannot skip one, and most wrong answers on this objective are a correct step placed after the gate it belongs to.

<TLDR>

- A prompt template is a named, versioned asset, not a chat message sent once
- The lifecycle runs in four moves: create, test, activate, execute, each gated by the next
- Activation publishes exactly one version; saving only writes a draft no consumer can call

</TLDR>

## Deep Dive

### A prompt template is a named asset, not a chat message

A prompt template is a reusable, named prompt that you build and manage in Prompt Builder, with placeholders for the details that change, such as a customer name or a product price [^1]. It is not a message you type into a chat window. It is metadata that lives in the org with a name, a type, a version history, and an activation state, which is what lets you test it, version it, govern it, and reference it by name from automation.

Hold the asset framing, because every later fact follows from it. Because a template is named metadata, a Flow or an agent can point at it by name instead of embedding prompt text in code. Because it is typed, the type fixes which objects it can bind and where it can run. Because it is versioned, changing the wording is a version operation rather than a code change. And because it carries an activation state, publishing it is a separate decision from rewriting it.

The lifecycle runs in four moves: create, test, activate, execute. You choose a type and create the template, test it against sample data, activate a version to make it available, and invoke it from a consuming surface. The first time you save a new prompt it becomes Version 1, and its status sits at Inactive in Prompt Builder until you activate it, at which point it reads Active. Inactive and Active in the workspace map to Draft and Published in metadata terms, the vocabulary the exam uses for deployment.

This is the distinction the objective turns on. A chat prompt is consumed once and forgotten, so nothing about it is versioned, typed, or published. A template is a shared asset, so each of those properties becomes a step someone has to take. The exam keeps testing the steps.

### The type and the object decide what you can bind

Creating starts with two choices that constrain everything after: a template type and an associated object. The classic types are Field Generation, which helps a user complete a specific field, Record Summary, which summarizes a record, Sales Email and Case Email Draft, which produce email, and Flex, the freeform type that runs on an object or from a flow. A Field Generation template requires both an object and the field to complete [^9], while the other types need only the associated object [^2].

The object you associate decides which merge fields are available, so pick it before you write the prompt. Attach a template to Case and the Account fields you wanted are simply not on the resource list, and no amount of prompt wording brings them back. The type is chosen at creation and it fixes the binding and the entry points for the life of the template, so the decision is hard to undo: changing it means building the template again.

For the exam, hold one detail tight. The two associations a Field Generation template needs are the object and the field to complete. A question that offers a Flow and an Apex class, or a data space and a search index, is testing exactly that pairing. The other types need the object alone, because their output is not written into a single named field.

Think of the pairing as the template's address. The object says which records the template can read, and for field generation the field says which slot the output fills. Get the address wrong and every later step, grounding, preview, activation, still works while producing the wrong thing, which is the most expensive kind of mistake because nothing errors.

![The type and the object fix what a template can do: Field Generation needs an object plus the field to complete, while the other classic types need the associated object alone](</diagrams/day-09-pe-5a-creating-activating-and-executing-prompt-templates/1-type-and-associations.png>)


### Author in the workspace and preview the resolved prompt

Authoring happens in the Prompt Template Workspace, where you write instruction text and insert resources for grounding: merge fields, related lists, flows, Apex, Data 360 data model objects, and files [^3]. Merge fields use the braces and leading exclamation syntax, so a reference to a company name or an input field resolves at run time against the associated record or its related lists [^1].

Then you test with sample data. Choose a sample record, click Save and Preview, and read the resolved prompt. The resolved prompt is the template with its merge fields replaced by that record's real data, and it is what actually gets sent to the LLM, so it is the only honest preview of what a user will receive [^1]. The response preview beside it shows the generated text a user would see.

Do not read only the output and skip the resolved prompt. The resolved prompt is where grounding problems announce themselves: a placeholder that resolved empty, a related list that came back blank, or a field the sample record does not populate all show up there, and each explains an output that otherwise looks merely poor. A template that previews wrongly will run wrongly, because the resolved prompt is what the model receives.

There is a second reason to preview honestly. The placeholders you wrote are instructions to the platform about what data to fetch, and the resolved prompt is the platform's answer. Reading it confirms that the object you associated actually carries the fields the prompt depends on, which is the first thing to check when a preview reads as confident but empty of specifics.

### The lifecycle is four moves across three gates

Read the four moves as gates, because that is how the platform enforces them and how the exam frames the questions. The first gate is creation: you pick a type and an object, and that pairing fixes the bindings for good. The second is the draft: saving a new prompt writes Version 1 with a status of Inactive in the workspace and Draft in metadata, and a draft is callable by no one. The third is activation: activating a version flips its status to Active in the workspace and Published in metadata, and only an active version is available to the surfaces that consume the template [^4].

The transitions between those gates are exact. Create produces Version 1 as a draft. Save rewrites the current draft in place. Activate publishes the chosen version and makes it immutable. Save As for a new version drafts a second version beside the live one. Deactivate withdraws the active version, but only when another version is already active, so no consumer is ever left with nothing to call.

The exam works the gap between the second gate and the third, because a saved draft looks finished and is not. Authoring permission and run permission publish nothing on their own; only an activated version does. So if a question asks what must be true before a user can run a template, there are two halves to the answer: the user needs the run permission, and some version of the template must be active.

![The prompt template lifecycle: create, test, activate, execute, with the status of each stage and the three gates that separate them](</diagrams/day-09-pe-5a-creating-activating-and-executing-prompt-templates/2-lifecycle-four-moves.png>)

**Lifecycle moves and what each decides**

| Move | Resulting state | What it decides |
| --- | --- | --- |
| Create | A typed, object-bound template | Which objects it can read |
| Save | Version 1 as an Inactive draft | Nothing a user can call |
| Activate | One version shown as Active | What every consumer runs |
| Execute | An invocable action | Where the template is called from |

### Activation is the switch that makes the template real

Activation is the step that makes the template usable, because a template is not available to users by default. When you activate, you make one specific version available to the surfaces that consume it. Only one version of a template can be active at a time, and if no version is active the template becomes unavailable [^4].

Activating also makes that version immutable. You cannot edit an active version in place, no matter how small the change; to change an active template you save a new version and activate that [^4]. Day ten takes the version operations apart in detail, but the rule you need here is simpler: getting activation right is the difference between a finished template and a draft that nothing can call.

The uniqueness of the active version is the design point. Because exactly one version is published at a time, an activated template is a single agreed-upon answer to the question of what it says right now, and that is what makes it safe to build a Flow or an agent action on top of it. Activation does not change the template's content; it decides which version every consumer receives.

### What an edit to a live template actually changes

What happens when someone edits the prompt behind a running template is a scenario the exam returns to, and the answer is entirely about versions. The running surfaces resolve against the active version. A new version you draft is invisible to them until you activate it, so editing a draft changes nothing a user sees. If you want to change what users see, you save a new version and activate it, and the switch happens in that one deliberate step [^8].

The version you cannot touch is the old active one, because activation froze it. Even if you later deactivate it, any version that was ever active stays immutable, so there is no path back to editing the wording that is currently live [^8]. That is why the disciplined workflow drafts a new version beside the active one, tests it against real records, and activates it only when it is ready, rather than trying to patch the version already in service.

The consequence for a delivery lead is that a prompt change is a release, not a text edit. You can prepare the new wording, preview it, and stage the version without disturbing anyone, then publish it when the change is agreed. The active version never changes under a user mid-conversation; it changes only at the moment you activate a different one.

![Editing a live template: version 1 stays active and frozen while a new version 2 sits in draft, invisible to consumers until it is activated](</diagrams/day-09-pe-5a-creating-activating-and-executing-prompt-templates/3-version-state-machine.png>)

### Execution turns the template into a feature

Every saved and activated prompt template is exposed as an invocable action, which is how it becomes part of an app [^5]. From Flow, you use the regular Actions element and filter the list by the Prompt Template category, passing the associated record as a related entity; for a field generation template, that record is the one whose field is being completed [^5]. From an agent, you add a Prompt Template reference action, bind the inputs and outputs, and mark at least one output to show in conversation [^6].

From Agent Script, the action target is generatePromptResponse:// followed by the template developer name, inputs are referenced as Input: followed by the api name, and the standard output is promptResponse [^7]. Apex and the REST API can also invoke a template [^5]. Because each of these points at the template by name, the version that runs is always the active version, which makes activation the real control surface and execution just the wiring.

Notice what the invocation surfaces do not do. None of them names a version, and none of them carries prompt text. The Flow Action, the agent action, and the Agent Script target all reference the asset, and the platform resolves the active version at run time. That is why a single activation can change the behavior of every consumer at once, and why keeping the version history clean is an operational concern rather than housekeeping.

### Worked scenario: preview passed and the floor saw nothing

Here is the shape the exam uses most. A consultant builds a Case Summary template, previews it against a well-populated case, sees a clean summary, saves, and hands it to the service team. A rep runs it from the record and gets an error, or gets nothing at all. What is the most likely cause?

Reason from the gates. The preview ran in the author's workspace against a sample record, so it proves the prompt and the grounding, not the publish state and not the runner's access. Two gates could be shut. If the template was saved but never activated, then no version is active and the template is unavailable to every consumer, which fits a rep who sees nothing. If a version is active but the rep lacks the run permission, then the asset is published and the rep still cannot invoke it.

Work the symptom against the wrong answers. The tempting answer is that the template needs more grounding, so the reply asks you to add resources. But the preview already resolved the grounding, and an unactivated template never reaches the model at all, so more grounding fixes nothing. The other tempting answer is to grant a broad permission such as Customize Application, which over-reaches and still does not publish the template. The right reading names the gate: activation first, then the run permission, and the grounding last.

![Diagnosing a template that previews fine but runs empty: check whether a version is active, then the run permission, then the grounding, in that order](</diagrams/day-09-pe-5a-creating-activating-and-executing-prompt-templates/4-diagnose-silent-template.png>)

### Under the hood, the template is versioned metadata

A prompt template is stored as the GenAiPromptTemplate metadata type, which carries one or more versions, an active version, a type, and the associated entity, with a separate related field for field generation [^5]. Because the template is a named, versioned asset, changing the prompt is a version operation rather than a code change, and invoking it from a flow or an agent is a reference to that asset.

The line to remember is that the template text itself never reaches the model. The resolved prompt does, and the active version is the one that resolves. That single fact explains why an unactivated template does nothing, why activating a different version changes every consumer at once, and why two users can get different output from the same template when their record access differs. The asset is shared; the resolved prompt is personal to the run.

### The build sequence in six steps

<Steps>

<Step title="Open Einstein and then Prompt Builder">

In Setup, open Einstein and then Prompt Builder, or open Prompt Builder from the app launcher, and click New Prompt.

</Step>

<Step title="Choose the template type">

Choose the template type, such as Field Generation, Record Summary, Sales Email, or Flex, and associate it with an object and, for field generation, the field to complete.

</Step>

<Step title="Write the instructions">

In the Prompt Template Workspace, write the instructions, then click Insert Resource to add merge fields, related lists, flows, Apex, or Data 360 data model objects.

</Step>

<Step title="Click Save and Preview">

Click Save and Preview, choose a sample record, and review the resolved prompt and the generated response before you commit.

</Step>

<Step title="Click Save to keep the version">

When the output is right, click Save to keep the version, then click Activate to make that version available to users.

</Step>

<Step title="Wire the template into a Flow">

To use it, add it to a Flow as an Action under the Prompt Template category, or to an agent as a Prompt Template action, binding inputs and outputs.

</Step>

</Steps>

## Exam Traps

<Callout kind="warning">

Three traps dominate this objective. The first is believing a saved template is immediately usable. A template stays inactive until you activate a version, and a template with no active version is unavailable to every consuming surface, so saving is not publishing. The second is believing you can activate more than one version at a time. Only one version is active at a time, so activating a different version replaces the one before it and switches what every consumer receives. The third is believing the template text is what the LLM receives. The resolved prompt, with the merge fields replaced by real org data, is what is sent to the model, so a template that previews wrongly will also run wrongly. Each trap is the same category of error: treating one step in the lifecycle as if it were the whole lifecycle.

</Callout>

## What a consultant should walk away with

<KeyTakeaways>

- Saving is not publishing: a template with no active version is unavailable to every consuming surface.
- Only one version is active at a time, and activating a different version replaces the one that ran before.
- The resolved prompt, with merge fields replaced by real org data, is what reaches the model, not the template text.
- Before a user can run a template, two things must hold: a version is active and the user holds the run permission.

</KeyTakeaways>
