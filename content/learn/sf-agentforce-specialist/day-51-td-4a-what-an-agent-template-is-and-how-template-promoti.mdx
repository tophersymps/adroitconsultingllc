# Lesson 51: What an Agent Template Is, and How Template Promotion Differs from Agent Promotion

A team is asked to stand up the same service agent in a second production org. One consultant exports the running agent and tries to import it as it stands; the attempt fails, or it lands an agent that cannot attach to anything, because the agent does not move that way. The team that succeeds does something different. It turns the working agent into a template, ships the template, and then builds a fresh agent from it on the other side, naming it and giving it its own user. The two moves look similar from a distance and are not the same move at all.

That difference is the subject of this lesson. An agent template is the reusable blueprint for one agent built for a use case, and understanding what it contains, what it is a child of, and how promoting it differs from promoting a named agent is what separates a clean multi-org rollout from a month of manual repair. The blueprint is the part the platform lets you ship; the agent is the part each org still has to build.

This lesson serves requirement td-4a, the considerations for deploying a template from sandbox to production, in the Testing, Deployment, and Maintenance domain, at ten percent of the exam. It defines the template, explains the agent type it is a child of, shows why the template is the deployable unit when the agent itself cannot be packaged, and draws the boundary between the blueprint that travels and the org-specific pieces that do not.

## Deep Dive

### An agent template is the reusable blueprint for one use case

An agent template is the reusable blueprint for one agent built for a particular use case.[^1] It contains the subagents, actions, filters, variables, and system messages that describe how an agent reasons and what it can do, which is to say it holds the design of the agent rather than a single instantiation of it.[^1] A subagent groups the actions and instructions for a job, a filter limits when a subagent or action is available, a variable stores context about a conversation, and the system messages set the agent's tone and its default replies.[^1] Read the list once and the concept settles: a template is everything about the agent that is not specific to the org it runs in.

The contrast worth fixing early is between a template and a named agent. A named agent is one instantiation: it has a name, an API name, and a user record, and it is the thing a customer or an employee actually talks to. A template is the design those instantiation steps draw from. You can have one template and many agents built from it, or one agent and no template at all, but the moment you want the design to travel to another org, the template is the artifact that carries it. Keeping that pair distinct is what makes the words promotion and instantiation mean different things later in the lesson.

That distinction is also why a new org ships with default templates, such as a default service agent template and employee agent templates, so a team starts from a working blueprint rather than a blank canvas.[^1] The template is the platform's own answer to the question of how you avoid rebuilding the same reasoning from scratch, and it is the unit the platform expects you to reuse, copy, and adapt rather than author again. When you build a new agent from scratch, you are authoring a template and an instantiation at the same time; when you build one from a template, the first of those jobs is already done.

### A template is a child of exactly one agent type

A template is a child of an agent type, and the relationship is strict in one direction: a type can be associated with many templates, but a template is associated with exactly one type.[^1] When you create an agent from a template, you first select an agent type and then choose a template of that type, which is the sequence the interface walks you through.[^2] A customer-channel service type can own many templates, each suited to a different use case, but any given template belongs to one type and no other.

The exam turns on the strictness. A template cannot attach to a different type, so if the target org does not have the type the template belongs to, the template has nothing to build on.[^1] That is a deployment consideration before it is a design one: verifying the type exists and is licensed in the target is part of moving a template, not an afterthought once the package installs. A template without its type is a package that lands and cannot be used, which is the quietest kind of failed promotion because the install itself reports success.

Creating an agent from a template also requires the permissions tied to that type, along with any additional permissions the template itself needs, so the gate is both the type's existence in the org and the operator's access to it.[^2] Because the binding is one-to-one on the template side, the type check is the first thing to verify on the far side of any promotion. If the target org lacks the type, no amount of correctness in the template's contents will let it build an agent, and the fix is to provision the type before the deploy rather than after.

### The template is the deployable unit when the agent cannot be packaged

The packaging distinction is what makes the template the deployable unit. The agent itself cannot be packaged directly, so to move an agent as a package you create an agent template, include the template in the package, and create a new agent from that template in the target org.[^3] The development guide for agent templates says the same thing in build terms: you retrieve the agent, generate an agent template from it, and package the template together with all of its dependencies, which can include actions, Apex classes, flows, and prompt templates.[^4]

The reason the agent resists packaging is worth stating, because it explains the whole design. A package is a set of metadata components with a version and an install path, and a running agent is not only metadata. Its name, its user, and its channel ties are instance state, so the platform gives you a shippable unit that holds only the reusable parts, which is the template, and asks the target org to build the instance itself. The template is the platform's way of separating what can travel from what must be built in place.

For an internal sandbox-to-production move, an admin can take a different and often simpler route: promote the agent as metadata using AiAgentDefinition and AiAgentDefinitionVersion with Salesforce CLI or a change set, which is the path covered on day 49.[^5] The template matters most when the deliverable is a package or a reusable starting point for many orgs rather than a single migration of one agent into one production org. One caveat sharpens the point: managed packaging is not supported for the newer agent metadata types, which is another reason the template, not the raw definition, is what carries an agent into a managed package.[^7]

### Template promotion ends with instantiation, not activation

Template promotion and agent promotion are different shapes of move, and the difference is the step at the end. Promoting an agent moves a specific, already-named agent together with its identity and its agent user, so after the deploy you mostly check that it is active and reachable.[^5] Promoting a template moves a blueprint and then requires you to instantiate a new agent in the target org: you create the agent, choose the template, name it, set its API name, and select or create the agent's user record.[^5]

The template supplies what the agent is made of, and the target org supplies the agent itself. That extra instantiation step is the single biggest difference between the two promotions, and it is the step a scenario question is usually probing. If a question asks what is different about deploying a template versus deploying an agent, the answer is that the template delivers a blueprint that the target org must still turn into a named, permissioned agent rather than a finished, running one.

The two promotions also differ in what a rollback means, which is a useful way to hold the distinction. Rolling back an agent takes you to a prior version of one agent. Rolling back a template means removing or replacing a blueprint, and any agent already built from it stays where it is, because the template and its instantiations are separate objects. A template that is replaced does not reach back and change the agents that were built from it.

### What a template carries is the structure, and you choose how much of it

A template carries the agent's structure: the subagent definitions and their instructions, the set of actions, the filters that gate which subagents and actions may be used, the variables, and the default system messages.[^1] That is the portable core, and it moves intact because it describes the agent's logic rather than the org's data.

When you create an agent from a template, you can choose which of those assets to include, so a template is a starting set rather than a locked bundle, and it is normal to trim subagents that do not apply to the target use case.[^1] That selection step is also a risk control: it lets you leave out assets the target org is not licensed or configured for, which keeps the new agent inside what the environment can actually support. Treating the template as a menu rather than a monolith is part of using it well, and it is a reason one template can serve several related use cases without being rebuilt for each.

A worked slice of that selection makes it concrete. If a template carries a billing subagent, a returns subagent, and an escalation subagent, and the target org has no returns process, you include the first and third and leave the second out at instantiation. The template stays complete for the org that needs all three, and the new agent stays inside the target's real scope.

### What a template does not carry is everything scoped to an org

What a template does not carry is everything scoped to an org. It does not carry the agent's unique name and API name, the agent user record and its permission assignments, the channel connections such as Embedded Service Deployments, Enhanced Chat, or Omni-Channel flows, the external service authentication, or the org's records and grounding data.[^5][^6] Those are per org whether you promote an agent or a template, and they are the reason a template promotion is never a one-step go-live.[^6]

A useful phrasing for the exam is that the template carries the agent's design while the target org contributes the agent's identity and its environment. When a scenario asks which item must be recreated rather than deployed, the answer is always one of the identity or environment pieces, never a subagent or an action. Read the objective with that boundary held tight: the considerations for deploying a template are the template's type and permissions, its dependency actions, and every org-specific piece you must recreate on the other side. The blueprint travels; the home you build it in does not.

### Walk the promotion once, end to end

Take a concrete case and watch the whole shape. A team has a working employee service agent in a sandbox and wants the same agent in a second production org. They open the sandbox agent in Agentforce Studio, confirm the subagents, actions, filters, variables, and default system messages are the set worth reusing, and generate a template from it.[^4] They package the template with the flows, Apex, and prompt templates those actions call, because the agent itself cannot be packaged directly.[^3] In the target org they confirm the agent type is available and licensed, deploy the package, and then create a new agent from the template, naming it, setting its API name, and giving it its own agent user.[^5] Finally they recreate what the template never carried, which is the channel deployment and the grounding data.[^6]

Read the steps as two jobs rather than one. Every step before the instantiation is moving a blueprint; every step after it is building a home. The first job is the part the package does for you, and the second job is the part it cannot. That is why a template promotion is best described as a deployment, then an instantiation, then an environment build, in that order, and why estimating the work from the package alone leaves most of it uncounted.

## Exam Traps

Three traps dominate this objective. The first is believing you can package and deploy the agent directly: the agent itself cannot be packaged directly, so you create an agent template, include the template in the package, and create a new agent from that template in the target org.[^3] The second is believing a template carries the agent user or its channels, when the template carries subagents, actions, filters, variables, and system messages while the agent user, its permissions, and the channel connections are recreated per org.[^6] The third is believing any template can attach to any agent type: a template is a child of exactly one agent type, and creating an agent from it requires that type's permissions, so the type must exist in the target org.[^1] All three are the same error, treating the blueprint as the building.

## What a consultant should walk away with

Know which unit you are moving. If the deliverable is one named agent into one production org, promote the agent as metadata with its definition and version, the path from day 49. If the deliverable is a package or a reusable starting point, build an agent template, pack the template with its dependency actions, and plan the instantiation step in the target org, where you create the agent, name it, and give it its own user record. Before you deploy, verify the agent type is available and licensed in the target and confirm the permissions needed to create an agent from that type. Carry the template's structure, choose which assets to include, and then recreate everything the template does not carry, which is the agent name, the agent user and its permissions, the channels, the external connections, and the grounding data. A template is the blueprint you can ship; the target org still builds the agent from it.
