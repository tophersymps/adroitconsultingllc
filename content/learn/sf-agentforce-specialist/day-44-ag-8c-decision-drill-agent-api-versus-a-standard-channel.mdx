# Lesson 44: Decision Drill: Agent API Versus a Standard Channel or a Flow Callout

An integration team spends three weeks building an Agent API client, a middleware wrapper, and a token exchange flow so a rep can summarize a case from a button on a Lightning record page. An admin watches the demo and asks why a Flow with an AI Agent action on the same button was not enough. The agent is identical, the button is identical, and the seam was overbuilt. The team reached for the API before asking where the caller sat.

The cause is that Agent API is a strong answer to a narrow question, and the exam is really testing whether you can tell when the question is narrower than the tool. A caller inside Salesforce already has a running user with a security context, so it needs no token, no base URL, and no session object. A human on a native channel already has authentication, rate limiting, and abuse protection handled by the channel. Agent API earns its place only when the caller is a system outside Salesforce that must reach the agent programmatically.

This drill serves requirement ag-8c, "Given a scenario, identify when it's appropriate to use Agent API," in the AI Agents domain, which carries 35 percent of the exam. It trains one judgment: given a scenario, is Agent API the right seam, or is a native channel, a Flow callout, or an embedded feature the better answer. By the end you can read any scenario for two facts, where the caller sits and who owns the protections, and name the seam before you name the tool.

<TLDR>

- Ask two questions of every scenario: is the caller outside Salesforce, and is it human or system
- A caller already inside Salesforce is a Flow callout or a shipped feature, never Agent API
- A human on a web or messaging surface belongs on the native channel that owns the protections

</TLDR>

## Deep Dive

### Two questions decide every scenario: where the caller sits and who owns the protections

Every scenario in this drill resolves to two questions. First, is the caller outside Salesforce or already inside it? Second, is the surface a human conversation or a system? A system outside Salesforce points at Agent API. A human on a native channel points at the channel, because the channel owns authentication, identity propagation, rate limiting, and abuse protection.[^1] A caller already inside Salesforce points at a Flow callout, where an AI Agent action runs under the running user with no external token to obtain.

The reason to rehearse the method is that the exam hides the caller behind words like integration, app, and service. Integration can mean an external ERP or a Flow on a record. App can mean a customer's mobile app or an internal Lightning app. The word tells you nothing until you ask where the caller sits and whether it is a human or a system. Name those two facts and the seam follows, which is why the drill is built from short scenarios rather than from a catalogue of tools.

The protections question is the second half of the judgment, and it is the part candidates miss. A native channel gives you authentication, rate limiting, and abuse protection without your building them. Agent API does not; it leaves those duties to your host application. So when a scenario describes a human on a web or messaging surface, choosing Agent API means volunteering to rebuild what the channel already provides, which is work the exam expects you to decline.

Hold four seams in mind, not two. The drill contrasts Agent API with a native channel, with a Flow callout, and with an embedded feature on a shipped surface. An embedded feature is an in platform interface the platform already renders, so it needs no external token and no base URL, which puts it on the same side of the line as a Flow callout. When you can place a scenario on the right side of that line, naming the exact seam is a short step further.

### An external ERP that needs a structured decision is Agent API

Scenario one. An external ERP needs to invoke the agent, receive a structured decision, and act on it, with no human in the loop. This is Agent API, using the synchronous pattern and reading the structured output. The distinguishing fact is that a system outside Salesforce needs the agent programmatically and consumes the result as data, which is exactly what the API's structured response exists to provide.[^2]

The near miss is the word integration, which can tempt a middleware answer. Middleware is only required for the asynchronous pattern where reasoning is too slow to hold the connection; here a single request response call is the seam, and a wrapper would be extra moving parts guarding against a timeout that is not coming. The distinguishing fact is that the caller is a system outside Salesforce that wants a value, not a conversation and not an in platform action.

Note what the ERP scenario is not. It is not a case where a human reviews the decision before it is used. The absence of a human is what keeps it a pure system integration, and a scenario that adds a reviewer on a Salesforce page would move the answer toward a Flow callout instead. The human or system question is doing as much work here as the inside or outside question.

### A Flow on a case record is a Flow callout, not Agent API

Scenario two. A Salesforce Flow on a case record needs the agent to summarize the case and write a field, triggered when a rep clicks a button. This is a Flow callout with the AI Agent action, not Agent API. The distinguishing fact is that the caller is already inside Salesforce, so the agent runs under the running user's security with no external token to obtain, no base URL to set, and no session to manage.

The near miss is that the agent is still doing generative work, which tempts the Agent API answer because the word AI pulls toward the API. But Agent API earns its place only when the caller is a system outside the platform, and a Flow on a record is inside the platform. The button, the record, and the running user are all in Salesforce, so the in platform action is the seam, and the security context is the running user's rather than a bearer token's.[^6]

This is the most common Agent API over-answer on the exam. When the caller is a record, a button, or a scheduled job inside Salesforce, the answer is the Flow callout, and the consultant gains nothing from an external token, a base URL, or a session object. The running user already carries the access the agent needs, so an external identity would only add a token to rotate and a seam to maintain.

### A public website chat widget is a native channel, not Agent API

Scenario three. A public website wants a chat widget where anonymous shoppers ask questions and the site handles no authentication. This is a native enhanced messaging channel, not Agent API. The distinguishing fact is that the surface is a human conversation, and the native channel already handles authentication, identity propagation, rate limiting, and abuse protection.

The near miss is that the widget is a custom front end, which tempts a build it yourself answer through Agent API. The correction is that rebuilding those protections on Agent API is exactly the work the channel exists to save you, so you use the channel and let it own the conversation. A human on a web surface is the channel's job, and the anonymous visitor is served by a Service agent behind that channel rather than by an API integration.[^5]

![Comparison of who owns the protections. A native channel for a human on a web or messaging surface owns authentication, identity propagation, rate limiting and abuse protection. Agent API for a system outside Salesforce leaves those same four duties to your host application.](</diagrams/day-44-ag-8c-decision-drill-agent-api-versus-a-standard-channel/2-protection-ownership.png>)

Contrast this with scenario four later in the drill. Both are customer built external surfaces, but this one is anonymous and human, so the channel owns it, while scenario four carries a specific identity and so moves to Agent API. The presence or absence of an identity to propagate is the fact that separates the two, not the fact that both are custom front ends.

### An external app that must carry a user's identity is Agent API with an identity flow

Scenario four. A customer's own mobile app must embed the agent and pass its signed-in user's identity through so that person's access governs. This is Agent API with an identity carrying OAuth flow such as token exchange, or the customer applies the Agentforce mobile SDK over the same seam. The distinguishing fact is that an external, customer built surface must invoke the agent and propagate a specific user's identity.

The near miss is treating it as a plain chat channel, but the requirement that the user's own identity cross the boundary is what points at Agent API and at the flow that carries identity rather than a shared service account. A shared integration user would collapse every customer into one identity, which is the exact failure that makes customers see each other's data. The identity requirement, not the surface, decides the seam here, and it is the fact that separates this scenario from the anonymous widget.

### A headless back office service is Agent API with client credentials

Scenario five. A back office service with no user interface must call the agent on a schedule to triage overnight cases. This is Agent API using the client credentials flow, running as a dedicated integration user. The distinguishing fact is that there is no human and the caller is a service, so the integration authenticates as itself and lets the running identity field govern the session.

The near miss is the lack of a conversational surface, which can tempt a non agent answer such as a plain scheduled batch that never touches the agent. The correction is that a headless system invocation is precisely Agent API's native use. With client credentials there is no interactive user, so the running identity is set to the agent user, and the service calls the agent the same way it would call any other API.[^2]

The scheduled nature of the job does not change the seam. A service that runs at two in the morning and a service that calls on demand both authenticate the same way, with client credentials, because neither has a user behind the request. The cadence is an operational detail, and the identity is the decision.

### An MCP client uses the MCP path, and an embedded panel is a shipped feature

Scenario six. A caller wants to invoke the agent from an MCP compatible client as one step in a wider agentic workflow. This is the Agentforce via MCP path rather than a hand built Agent API integration. The distinguishing fact is that the caller is an MCP client delegating a step, so the out of the box MCP server manages the session lifecycle and the caller just makes a tool call.

The near miss is defaulting to Agent API for any AI to AI call, but when the caller is MCP compliant you use the MCP path and let it manage sessions. Salesforce exposes Agentforce agents and Prompt Builder templates as MCP tools so an external assistant can invoke them through the protocol, and the MCP server handles the plumbing rather than your code.[^3][^4]

Scenario seven. A service console wants an embedded agent panel on the case record so reps get step by step resolution guidance in the flow of work. This is an embedded feature on a shipped surface, not Agent API. The distinguishing fact is that a rep is working inside Salesforce on a surface the platform already renders, so authentication, identity, and the interface are all handled by the platform, and there is nothing for an external integration to build. The near miss is that the user is a person, which tempts a channel answer, but this is an internal in platform surface rather than an external messaging channel, and the shipped capability is what the rep uses.[^5]

Scenarios six and seven show the same shape from opposite sides, and together they close the drill. One caller is outside Salesforce but speaks a standard protocol, so a ready made server manages the session. The other caller is inside Salesforce on a shipped surface, so the platform manages everything. Agent API is the answer only for the case in between, a system outside Salesforce that is not speaking the MCP protocol and needs the raw seam. The whole drill reduces to two questions: is the caller outside Salesforce, and is it a human surface or a system.

### The build sequence in six steps

<Steps>

<Step title="Map each invocation to a caller">

In Setup, map each agent invocation you are planning and label the caller: a human in a native channel, a system outside Salesforce, or automation inside Salesforce.

</Step>

<Step title="Plan an AI Agent action invoked">

For callers already inside Salesforce, plan an AI Agent action invoked from Flow and confirm the running user has access to the records the agent will touch.

</Step>

<Step title="Choose the enhanced messaging channel">

For human conversations on a web or messaging surface, plan the native enhanced messaging channel and confirm the channel handles authentication, rate limiting, and abuse protection.

</Step>

<Step title="Plan Agent API">

For external systems, plan Agent API and choose the session pattern: single turn for a request-response, multi turn for a conversation, and a wrapper when reasoning may exceed the caller's timeout.

</Step>

<Step title="Choose an OAuth identity flow">

For external systems that must carry a user's identity, choose an identity carrying OAuth flow such as token exchange rather than a shared integration user.

</Step>

<Step title="Plan the Agentforce via MCP path">

For MCP compatible callers, plan the Agentforce via MCP path so the MCP server manages sessions, and reserve hand built Agent API integrations for callers that are not MCP clients.

</Step>

</Steps>

## Exam Traps

<Callout kind="warning">

Three traps dominate this objective. The first is believing Agent API is the answer whenever an integration touches an agent: a Flow callout keeps an in platform caller under the running user with no external token, so Agent API is not needed there. The second is believing you must build a custom channel for a human web surface: the native enhanced messaging channel already handles authentication, identity propagation, rate limiting, and abuse protection, so building on Agent API volunteers for work the channel does for you. The third is believing any AI to AI call defaults to Agent API: when the caller is an MCP compatible client, the MCP path manages the session lifecycle and the Agent API integration is unnecessary. The corrections all point the same way, which is to ask where the caller sits and who owns the protections before you name a tool.

</Callout>

## What a consultant should walk away with

<KeyTakeaways>

- Agent API answers a system outside Salesforce; a caller inside the platform is a Flow callout under the running user.
- A human on a web or messaging surface uses the native channel, which owns authentication, identity propagation, rate limiting, and abuse protection.
- An external app carrying a specific person's identity uses Agent API with an identity carrying OAuth flow such as token exchange.
- An MCP compatible client uses the MCP path, which manages the session lifecycle, so a hand built Agent API integration is unnecessary.

</KeyTakeaways>
