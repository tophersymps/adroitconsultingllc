# Lesson 46: Building a Test Set from Real Conversations: What a Passing Result Proves

A team celebrated a fully green suite the week before go-live, and by the end of the first live week the agent had failed on the one utterance every customer actually typed. The suite held forty tidy cases written straight from the subagent list, each one phrased the way the builder phrased it, and none of them was the messy half-sentence the contact center heard a thousand times a day. The suite was green because it tested the agent the team designed, which was not the agent customers met.

Cases generated from the configuration inherit the configuration's assumptions about phrasing and routing, because they are written from the same metadata that built the agent. Real conversations carry the opposite: typos, missing words, a request that changes topic mid-sentence, a customer who answers a question with another question. The best source of test cases is therefore not the agent configuration at all, it is the conversations the agent already had, and a suite built from those conversations fails in the ways a customer would notice.

This lesson serves requirement td-1b, the same objective as day forty five, "Given a scenario, test an agent using Testing Center.", taken now from the side of what a suite proves. It sits in the Testing, Deployment, and Maintenance domain at ten percent of the exam. By the end you can build a set from real transcripts, write expectations that produce an honest score, and state precisely where a passing result stops being evidence.

## Deep Dive

### The best test cases come from production, not the configuration

Agent Analytics and Session Trace show what customers actually typed, which utterances recur, and where the agent misrouted, escalated, or handed off.[^1] Pull those transcripts, group the utterances by the subagent that should have handled them, and keep the ones with real phrasing: typos, half-sentences, a request that changes topic halfway through, a customer who answers a question with another question. Generated cases from your subagent metadata are tidy, and production utterances are not. A suite built only from your own imagination tests the agent you designed, which is not the agent your customers meet.

The grouping is the analytical step that turns a transcript pile into a suite. Raw utterances are not cases until they are bucketed by the subagent that should have caught them, because that bucketing supplies the expected subagent the case needs. The utterances that broke before are the highest-value cases of all, because you already hold evidence that the agent mishandles them, and a case built from a known failure is a case you can watch turn green.

A worked pull makes the step concrete. Open Session Trace for a busy subagent and look for two things at once: volume and failure. The utterances that recur most are the ones a miss costs the most to repeat, and the utterances that ended in an escalation or a handoff are the ones that already cost you a customer once. Copy both into the same suite, tag them so you can tell a high-volume case from a known-failure case, and you have a set whose every row earns its place. The tidy cases you would have written from the subagent metadata are the rows you no longer need, because the production pull has already covered the ground they would have covered, with real phrasing instead of designed phrasing.

### Two rules keep the set honest

Two rules keep the set honest. First, write the expected subagent, the expected actions, and the expected response as statements of fact, not as advice about behavior. Salesforce's own guidance is that an expected response field should hold the reply you expect, because a field that says the agent should mention the order number and be polite describes behavior instead of stating a reply, and it produces an inaccurate score.[^2] The judge that grades the response reads your text as the target, so a behavioral instruction makes the target fuzzy and the score meaningless even though it still looks precise and authoritative.

Second, size the set so a run finishes and you actually read it. You can generate up to 200 cases at a time, but a set you never read is worth nothing, so trim to the subagents that carry risk and the utterances that broke before. A thousand cases nobody reviews is not rigor. It is a green number that hides its own contents, and the first time a stakeholder asks which failure you accepted, the size becomes an embarrassment rather than a strength. The honest size is the largest set whose every failing row you would actually open.

The two rules fail in a predictable pair. A tester who writes behavioral expectations gets precise-looking scores that do not track quality, and a tester who writes a set too large to reread gets a green total nobody can defend. Both mistakes share a cause: treating the suite as a deliverable to be finished rather than an instrument to be maintained. A suite is a living set you reread and prune, not a document you file after the release.

### What a pass actually asserts

A pass is not one claim, it is a bundle of specific claims about the cases you wrote. The subagent assertion passing means the agent routed that utterance to the subagent you specified. The action assertion passing means it selected the actions you expected. The response evaluation passing means a judge model read the reply against your expected response and scored it at or above the pass line.[^3] Put together, they say that for these inputs the configuration routes, acts, and answers as designed.

That is a genuine result, and it is the result you want before a release, because it is repeatable, it is written down, and it can be compared against the next version of the agent. A suite run twice with the same cases is a measurement. A demo run once is an impression. The value of Testing Center is that it converts an impression into a number you can hold next to another number and compare without arguing about memory.

Read a green row slowly and the bundle becomes concrete. The case says: for this utterance, I expected the Billing subagent, I expected it to call the lookup and the update actions, and I expected a reply that names the new address. The row is green, so the agent chose Billing, called both actions, and the judge scored the reply at or above the pass line. Three separate claims, each one a fact about the run, and each one a thing a later run can contradict. That is what makes the suite a fence you can compare against, rather than a feeling that the agent is fine.

### The longer list of what a pass does not prove

The list of what a pass does not prove is longer than the list of what it does. It says nothing about utterances that never entered the set, which is how a suite goes green while the agent still fails on a Tuesday afternoon. The conversation-level action assertion passes when every expected action occurred even if the agent also performed actions you never listed, so a pass is not evidence that the agent restrained itself.[^4] And no test case changes the security context: actions run under the running user, so a missing permission or a sharing rule fails in production no matter what the suite said. Testing Center proves routing, action selection, and response quality on the cases you wrote. It does not prove the business outcome.

Read that list as the coverage boundary of a fence. Everything inside the cases is measured, and everything outside is assumed. A consultant who can state where the fence ends is more useful to a release than one who reports a green total, because the fence is the exact part a stakeholder will mistake for the whole field.

A concrete non-proof makes the boundary real. Picture a suite that is green on a refund subagent, every case routing and acting as written, while a sharing rule hides the field the refund action reads from the running user. The suite never touches the running user's access, so it never sees the field vanish, and the first live refund fails on a configuration the test could not observe. Nothing about that is a fault in Testing Center; it is the boundary of what a conversation can prove, and it is the reason security review stays a separate gate.

### Two properties that make one green cell a weak signal

Two properties make a single green cell a weak signal. First, the agent is non-deterministic, so the same utterance can pass one run and fail the next, which is why the pass rate across the set matters more than any one result. Second, the response evaluation is a judge model comparing the reply to your expected response, so the score is a judgment against your text rather than ground truth. If your expected response is vague or wrong, the score is wrong in a way that still looks precise. Write expected responses you would defend in a review, and treat a sudden score swing as a reason to open the detail panel, not as a result to celebrate.

The two properties compound. Non-determinism means any single case carries noise, and a judged score means even a stable result is only as good as the target it was measured against. Together they say the unit you trust is a pattern across cases and runs, never a lone cell that happened to land green.

The operational consequence is that you read runs, not cells, and you read repeats, not singles. Before you act on a red cell, ask whether the same case is red across the last several runs or red once. A case red once is a candidate for noise. A case that went red and stayed red is a candidate for a real break. And when you improve the agent, expect the pass rate to move in small amounts, because a single case flipping sits inside the normal wobble of a stochastic system.

### When Testing Center is the wrong tool

Testing Center is the wrong tool for several jobs, and naming them is examinable. Use Builder preview or Live Test when you are debugging one conversation in a working session, because a batch run is slow feedback for that loop. Use Live Test when the question is whether an action updates a real record end to end. Use Agent Analytics and session scorers when the question is what happens in production, since a suite only contains cases somebody wrote. And use none of these as a substitute for load, security, or architecture review: throughput ceilings, sharing rules, and the running user's permissions are not things a scored conversation can settle, however many cases the suite holds.

The tell for the wrong tool is usually in the question, not the feature. If the question is why did this one exchange go wrong, the answer lives in Builder and its trace, not in a batch grid. If the question is does this action actually write the record, the answer is a Live Test against real data. If the question is what are customers hitting that we never wrote a case for, the answer is Agent Analytics. Only when the question is does the agent still pass the scenarios we care about does Testing Center become the right instrument.

### The judgment call the exam rewards

Reach for Testing Center when you need repeatable breadth over a written set of scenarios before a change ships, when you need a baseline a later run can be compared against, or when a stakeholder wants evidence that the agent routes and answers as specified. Do not reach for it when you need to watch the agent think through one exchange, when the failure only appears against real records or real services, or when the thing that is broken is not the conversation at all. A suite is a regression fence with a coverage boundary, and knowing where that boundary sits is the skill the objective is really testing.

The decision rule compresses to one line: use Testing Center when you want a comparable number, and use something else when you want to understand a single behavior. A comparable number is what buys a release its confidence, because it is the artifact you can put beside last month's artifact and see movement. Understanding a single behavior is what buys a fix, and it happens one conversation at a time.

## Exam Traps

Three misconceptions dominate this objective. The first is believing a green suite means the agent is production ready. A pass covers the cases you wrote, on the routing, actions, and responses you specified, and it says nothing about permissions, real records, or business outcomes, so a green total is a statement about the set and not about the business. The second is believing a passing action assertion proves the agent took only the expected actions. The test passes when every expected action occurred, even if extra actions also ran, so a pass bounds the actions the agent missed and not the actions it added. The third is writing instructions into the expected response field. That field should hold the reply you expect, because a field describing how the agent should behave produces an inaccurate score that still looks authoritative, and it quietly poisons every comparison you build on top of it.

## What a consultant should walk away with

Build the set from the conversations the agent already had, not from the configuration: pull the real utterances from Agent Analytics and Session Trace, group them by the subagent that should have caught them, and keep the messy ones and the ones that broke. Write the expected side as fact, because the judge scores against your text and a behavioral instruction makes the target fuzzy. Keep the set small enough that you read every failing row, since a suite you never read proves nothing. Read a pass as three specific claims about routing, action selection, and response quality on your cases, and read the boundary around it just as carefully: the utterances you never wrote, the extra actions a pass allows, the permissions a test cannot check, and the business outcome a conversation cannot settle. Then choose the tool by the question: Builder to watch one conversation, Live Test to prove an action writes, Analytics to see production, and Testing Center to fence a release with a set you can rerun next month.
