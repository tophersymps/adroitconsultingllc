# Lesson 3: Access Controls for Prompt Templates: Permission Sets and Activation

An admin finishes a case summary template, previews it, and tells the service team it is ready. The next morning the reps open the record page, click the button, and get nothing. The admin insists the template is fine because it looked perfect on their screen, and they are right about the template and wrong about everything else. The version was still a draft, and the surface the reps use only ever sees an active version.

This is the failure the access control objective is built to catch, and it has two halves. One half is permissions: who is allowed to author a template and who is allowed to run one, which are separate rights the platform ships as two permission sets. The other half is activation: a template is unavailable until a version is published, and permissions do not publish anything. Requirement pe-2a lives in the Prompt Engineering domain at 20 percent of the exam, and it asks you to identify the access controls governing prompt templates, so the exam tests both halves at once and often in the same stem.

This lesson names the two permissions, the two permission sets that deliver them, the separate activation gate, the split between the author and the runner, and the security fact that a run reads only what the executing user may see. Hold the four controls separate in your head, because the scenario questions are built to make you merge them, and a stem that sounds like a permissions problem is often an activation problem in disguise.

## Deep Dive

### Two permissions govern every prompt template

Two user permissions govern prompt templates, and the exam expects you to keep them apart. Manage Prompt Templates lets a user create and edit templates in Prompt Builder. Execute Prompt Templates lets a user run them [^1]. Everything else in this lesson is a delivery mechanism for those two permissions plus one separate gate, activation.

A user who can author but not execute, or execute but not author, is a normal and intended state, which is why the platform ships two permission sets instead of one. That design is the answer to most of this objective's stems. When a scenario describes someone who should build templates but not have them run, or someone who should run a template without touching how it is written, the platform already has a shape for that, and you should reach for the narrow grant rather than one wide permission that happens to include both.

### The two permission sets deliver the rights

Salesforce delivers the permissions through permission sets [^1]. The Prompt Template Manager permission set grants both Manage Prompt Templates and Execute Prompt Templates, so a manager can build, edit, and run. The Prompt Template User permission set grants only Execute Prompt Templates, so an end user can run an activated template without any authoring reach.

The broad Customize Application permission also carries both, but it is a wide permission that opens much of Setup, so treat it as the wrong way to grant prompt access [^1]. The exam's clean answer is the narrow permission set, not the wide system permission. When two options both technically work, the scenario is testing least privilege, and least privilege always points at the permission set built for the job. Note the asymmetry of the two sets as well: the Manager set is a superset of the User set, which is why a manager can test a template the way a runner will, and a runner can never author by accident.

### Activation is the gate permissions do not open

Activation is the second control, and it is independent of permissions. Prompt templates are not available to your users by default, because Prompt Builder is an iterative drafting space; you must activate a version to publish it [^2]. Only one version of a template can be active at a time, and if no version is active the template is unavailable to users [^6].

So a user with Execute Prompt Templates still cannot run a template that was never activated, and that is the point: authoring permission and run permission do not publish anything on their own. Deactivating the active version withdraws it for everyone at once. The single-active-version rule is also why editing a live template is a version switch rather than an in-place edit, a detail the lifecycle lessons return to, and it is why an org review for this objective always asks which version of each template is currently active.

![The activation gate: a draft version is unseen by users, activating it publishes the version, and deactivating withdraws it for everyone at once.](</diagrams/day-03-pe-2a-access-controls-for-prompt-templates-permission-se/2-activation-gate.png>)

### The author and the runner are separate roles

Put the pieces together and you have the author and the runner. The author holds Manage Prompt Templates, works in Prompt Builder, drafts, previews, and activates a version. The runner holds Execute Prompt Templates and consumes an activated version from wherever the template type allows it to surface, such as a record page button, an agent action, or a Flow [^7].

The two roles can be the same person, but they need not be, and on a governed org they should not be: the person who decides what a template says is usually not the whole population that runs it. Access control that reflects that split is the goal. A scenario that describes one small group curating the prompts and a large group consuming them is describing the intended design, not a problem to solve.

### A run reads only what the running user may see

One more control sits behind the run itself. When a template executes, the values for its merge fields are added to the prompt, and access to that merge data is governed by the permissions of the executing user [^4]. That means record sharing, the org-wide defaults, and field-level security still bound what the template can read, so a run is not a back door around your model.

Dynamic grounding from Data 360 works the same way: the retriever returns data the running user is entitled to see, and the Trust Layer preserves those role-based controls when grounding data from your CRM or Data 360 [^5]. The exam tests this as a security fact. A template that shows a user data they could not otherwise open is a defect, not a feature, and the answer to fix it is to change the runner's access or filter the data, never to widen the template blindly.

### Where the controls live

Knowing where these controls live is part of the objective. Permissions are assigned in Setup through Permission Sets and their Manage Assignments page; to add a user to the Prompt Template Manager set, the user must be able to reach Setup [^1]. Templates themselves live in Prompt Builder, where you can see versions and the active state, and where activation happens [^3].

The broad alternative, Customize Application, lives on profiles and permission sets in Setup too. An org review for this objective comes down to two questions: who holds each permission, and which version of each template is active. Answer those two and you have covered the entire objective, and a scenario that seems to ask about a third thing is usually one of those two in disguise.

### The four controls compose

So the access controls governing prompt templates are four and they compose. Who can author, through Manage Prompt Templates. Who can run, through Execute Prompt Templates. Whether a version is published, through activation. And what data a run can see, through the executing user's sharing and field access.

Day four drills the combinations, including the failure modes when who-authors and who-runs drift apart, because the exam asks about the seam between the two roles, not just the names of the two permission sets. Hold the four in order and any scenario question in this objective becomes a matter of naming which one it is describing.

### Why the platform ships two permission sets instead of one

The two-permission design is not decoration; it is a statement about how prompt work divides. Authoring a template is a curation job: it decides what the instructions say, which fields the template merges, and when a version goes live. Running a template is a consumption job: a rep clicks a button, an agent calls an action, a Flow invokes the template, and the output appears. Those two jobs carry different risk, different audiences, and different review needs, so the platform gives them different rights [^1].

If a single permission controlled both, every person who needed to run a template would also be able to rewrite it, and every rewrite would be a governance event nobody planned. Two permission sets let an org put the pen in a few hands and the button in many. That is why the Manager set grants both rights and the User set grants only the run right, and why the exam keeps returning to the pair. When you can name which job a person is doing, the permission follows, and least privilege is the default answer.

### What a run can read is a sharing decision, not a prompt decision

The fourth control sits behind the run, and it is the one people forget because it lives in a different part of Setup. When a template executes, its merge fields are filled from org data, and access to that data follows the permissions of the executing user, so the org-wide defaults, the sharing rules, the role hierarchy, and field-level security still decide what the prompt can read [^4]. The Trust Layer preserves those standard role-based controls when it merges grounding data, so the prompt is not a route around your model [^5].

The practical reading is that a run is only as broad as the person who triggers it. Two users can run the same activated template and get different grounding, and the difference is not a defect in the template; it is the security model working. A template that surfaces a record or a field a user could not otherwise open is the defect, because the platform means for the run to inherit the runner's access. On the exam, treat this as a security fact rather than a feature: sharing and field-level security bound the run, always.

### Customize Application is the widest answer and never the right one

The broad Customize Application permission also carries both prompt rights, which makes it a tempting grant when someone is blocked [^1]. It is also the wrong answer on almost every stem, because it opens a wide slice of Setup and hands a user far more reach than running or even authoring a template requires. The exam uses it as the noisy distractor, and the correct choice is the permission set built for the job.

There is a delivery reason too. Permission sets are additive: they grant capabilities on top of a user's profile without changing it, and they are assigned from Setup, which is why they are the right vehicle for the two prompt permissions. Granting Customize Application to solve a prompt problem changes the user's overall administrative surface, which is a much larger change than the requirement asked for. When a stem offers the broad permission and the narrow one together, the narrow one is the answer, and the reason is least privilege.

### A worked scenario: who runs, who authors, and who must not touch it

A service organization wants a small enablement team to own and update a set of case templates, wants the whole service floor to run them, and wants nobody to be able to edit a template by accident. Design the access.

Name the jobs. The enablement team authors and activates, so they hold the Prompt Template Manager permission set, which grants both authoring and running. The service floor only runs, so they hold the Prompt Template User permission set, which grants only the run right [^1]. Nothing else is needed, and no wide permission belongs in the design. With those two groups assigned, a rep can run an activated template but cannot change what it says, which is exactly the requirement.

Now the wrong answer. Granting the whole floor the Prompt Template Manager set, or worse, Customize Application, would let anyone on the floor edit a live template, which is the accident the requirement asked you to prevent. A second wrong answer is to stop at permissions and skip the gate: even a perfectly assigned floor sees nothing until a version is active, so the design has to include the activation step [^6]. Read the requirement for the two roles and the gate, and the answer is a pair of permission sets plus a published version.

## Exam Traps

Three traps dominate this objective. The first is believing Execute Prompt Templates is enough to author a template, when Execute only allows running an activated template and creating or editing needs Manage Prompt Templates, which the Manager permission set adds. The second is believing a permitted user can run any template, when a template is unavailable until a version is active, so Execute plus an activated version are both required. The third is believing a prompt runs in system context and sees all records, when access to merge data is governed by the permissions of the executing user, so sharing and field-level security still bound what the prompt can read.

## What a consultant should walk away with

Two permissions and one gate: Manage to author, Execute to run, and activation to publish. Use the Prompt Template Manager set for the people who build templates and the Prompt Template User set for everyone who only runs them, and avoid Customize Application for prompt access. Keep the author and the runner roles deliberate rather than accidental. Then remember that the runner's own record and field access decides which data a run can read, so a template never becomes a route around sharing or field-level security. Name the control a scenario is testing, authoring, running, publishing, or data reach, and the answer falls out.
