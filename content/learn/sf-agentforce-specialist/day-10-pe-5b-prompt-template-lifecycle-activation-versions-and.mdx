# Lesson 10: Prompt Template Lifecycle: Activation, Versions, and Invocation

A contractor standardizes a support org on one prompt template, then improves it: the wording is tighter, the tone is warmer, and a colleague test-runs it happily. They click Save and tell the team the rollout is done. Nothing changes for anyone. The fix they shipped is sitting in a version that no one is running, because the version in the field is still the previous one.

The cause is that activation, not saving, is what publishes a template. The surfaces that consume a template resolve against its active version, so a version you are drafting is invisible until you activate it. Saving changes your workspace. Activating changes what your users get.

This lesson takes the lifecycle half of requirement pe-5b in the Prompt Engineering domain: how a template moves between versions, why an active version is immutable, what happens to a running template when you edit it, how versions deploy, and how each consuming surface points at the active version.

## Deep Dive

### Activation decides availability, not content

Activation is the first thing to get straight. It does not change the template's content, it decides which version is available to the surfaces that consume the template. Only one version of a template can be active at a time, and if no version is active the template is unavailable [^1]. When a template is in use, you cannot deactivate the active version unless another version is already active, so the system never leaves a consumer with nothing to call.

That is a deliberate design choice, not a quirk. The active version is a single, agreed-upon answer to the question of what this template says right now, and giving it that uniqueness is what makes an activated template safe to build automation against.

### Version movement is a small set of exact operations

The version operations are few and you should be able to name them exactly. The first time you save, the template becomes Version 1. Clicking Save edits the current version in place, as long as that version is still a draft. Clicking Save As offers two choices: Save as a New Version keeps the same template name and adds an incremental version, while Save as a New Template creates a separate template with its own name and API name [^2].

The version number is part of the workspace URL, so any version is addressable. When more than one version exists, the version control at the top of the workspace becomes a dropdown that lists each version, when it was created, and which one is active, and you can select any version to work from. That dropdown is your map of the template's history.

### Activation freezes a version, so you never edit the live one in place

The immutability rule is the detail most people miss. Activating a version makes it immutable, and even if you later deactivate it, any version that was ever active stays immutable [^2]. That means you cannot edit an activated version in place, no matter how small the change. To edit such a template you save it as a new version.

This is why the disciplined workflow is to draft a new version beside the active one, test the new version against real data, and activate it only when it is ready, instead of trying to patch the version that is already running. The rule is a safety feature. An immutable active version is a version that cannot drift under the automation built on it, and any change to what users see is a deliberate activation you chose to make.

### What a running template does when you edit it

The immutability rule answers the question of what happens to a running template that is edited. The running surfaces resolve against the active version, so a new version you are drafting is invisible to them until you activate it. If you edit a draft version, nothing the users see changes. If you want to change what users see, you save a new version and activate it, which flips the available version in one deliberate step.

The active version never changes under a user mid-conversation. It changes only at the moment you activate a different version. Editing the live template is therefore a version switch, never an in-place edit. This is the mental model that resolves the exam's scenario questions, because the answer is always about which version is active, not about how the prompt was worded.

### Deployment follows from the same rules

In metadata terms a template version has a status of Published, which shows as Active in Prompt Builder, or Draft, which shows as Inactive. A setting controls whether only the active version is deployed. When that setting is on, inactive versions are skipped and a template with no active version fails the deployment [^3].

Because published versions are immutable, a redeploy that targets a version already present updates the content only if that version is still a draft, and otherwise changes only the activation status. With the setting off, templates deploy but arrive inactive and must be activated in the target org, unless the deploy-activate setting is enabled to carry activation across [^3]. The practical takeaway for a promotion is blunt: know whether activation travels with the deploy, or plan a post-deploy activation step, because a template that lands inactive is a template nothing can call.

### Invocation closes the loop, and the active version always wins

The invocation mechanics are worth naming for each surface. From Flow you add an Actions element, filter by the Prompt Template category, and pass the associated record as a related entity. From an agent you add a Prompt Template reference action, bind the inputs and outputs, and mark at least one output to show in conversation [^4]. From Agent Script the target is generatePromptResponse:// followed by the developer name, inputs are referenced as Input: plus the api name, and the output is promptResponse [^5].

Because every one of these points at the template by name, the version that runs is always the active version, which is why activation is the real control surface. You can build the automation, bind every input and output, and still control what it produces entirely through which version you have activated.

## Exam Traps

Three traps dominate this objective. The first is believing you can edit the active version in place. Activating a version makes it immutable, so after activation you must save as a new version to change the prompt, and an attempt to edit the live version in place is the wrong answer. The second is believing deactivating a version removes it. Deactivation only changes which version is available; the version still exists in the history, and any version that was ever active stays immutable. The third is believing a template deploys with all its versions. Only the active version is deployed when the deploy-only-active setting is on, inactive versions are skipped, and a template with no active version can fail the deployment outright. Each of the three is a version-control fact dressed as a deployment or editing question.

## What a consultant should walk away with

Learn to think in active versions, not saved drafts. Saving edits your workspace; activating changes what every consumer gets, and only one version can be active at a time. Once a version has been active it is immutable forever, so the way to change a live template is to draft and test a new version and then activate it in one deliberate switch. Keep the version dropdown as your map, and when you promote a template between orgs, decide up front whether activation travels with the deployment or needs a post-deploy step. Every invocation surface points at the template by name, so which version runs is never a question of wiring. It is always the active version.
