# Lesson 60: Open Standards for Multi-Agent: The Purpose of MCP and A2A

A discovery call turns on one question. The customer's integration team asks whether the agent will use MCP or A2A to reach a third-party logistics platform. Half the room says MCP, half says A2A, and the meeting stalls, because both answers sound reasonable and nobody in the room can state the test that separates them. The vendor who can name the test wins the room. The vendor who guesses loses the technical decision to whichever integrator says the words back with more confidence.

That gap is worth closing here because for many learners this lesson is the only place the material will appear before the exam. MCP and A2A are not in the module lists of the official Agentforce prep trails, so a consultant who does not learn them deliberately meets them first in a customer conversation or in a scenario question that assumes them. The two protocols are also easy to mix up, because both connect an agent to something outside its own org, and only one thing distinguishes them: whether the remote side is a capability you call or a peer that reasons.

This lesson serves requirement ma-2a, "Explain the purpose of existing open standard multi-agent protocols such as MCP and A2A," in the Multi-Agent Orchestration domain, which carries 5 percent of the exam. It is deliberately self-contained. By the end you can explain why an open standard exists at all, describe what MCP is for and the roles it defines, describe what A2A is for and the effort Salesforce co-founded, apply the rule of thumb that separates a remote tool from a remote agent, and place both protocols on the edges of an Agentforce architecture in both directions.

## Deep Dive

### An open standard replaces bespoke glue with a shared language

The purpose of an open standard in multi-agent design is to replace bespoke point-to-point integration with a shared language. When every system you connect requires its own custom glue, each integration is built, maintained, and secured separately, and the cost compounds with each new tool or agent. Open, vendor-neutral protocols give agents a common way to reach tools and to reach each other, so the same client can talk to many systems and the same server can serve many clients. Salesforce positions MCP and A2A as the protocols that make this interoperability possible across orgs, systems, and vendors.[^3]

An open protocol also draws the boundary cleanly. In-org orchestration cannot cross an org or a vendor line, so a requirement that needs a capability living elsewhere has nowhere to go inside the single-org design. The protocols exist precisely to make that crossing deliberate and governed rather than improvised. That is the architectural reason they appear at all, and it is the reason a consultant has to be able to say which protocol applies to a given outside system.

### MCP is capability exposure: it gives an agent reach

The Model Context Protocol, MCP, is an open and vendor-neutral standard, originally created by Anthropic, that defines how AI agents connect to external tools, data sources, and APIs.[^1] Its purpose is capability exposure: it lets an external system describe what it can do as callable tools that an agent can discover and invoke without knowing that system's native API or schema. Salesforce describes MCP as acting like a translator between systems, so the manual work of API connectivity, authentication, and data access is handled by the standard instead of being rebuilt for every pair of systems.[^1]

An MCP deployment has three roles, and the exam expects you to keep them straight. Servers expose the assets that an external system makes available. Clients connect to one or more servers to access those tools and data. A host is the application that coordinates the process and manages the client.[^1] The assets a server exposes come in three kinds: tools, which are executable functions an LLM can call to act in external systems; prompts, which are natural-language instructions from the server to the model; and resources, which are data the server can reach, such as files or feeds.[^1] In an Agentforce architecture Salesforce has built the MCP client into Agentforce, so registering a server and its tools turns those tools into agent actions rather than into a bespoke integration per system.[^1]

![MCP's three roles in sequence: the host coordinates the process, the client holds the connection, and the server exposes tools, prompts, and resources](</diagrams/day-60-ma-2a-open-standards-for-multi-agent-the-purpose-of-mcp/1-mcp-roles.png>)

Walk the canonical example, because the exam and the customer both use it. A service agent needs a loan risk score for a contact before it decides the next step in a conversation. Without MCP, the team would hand-build the connection to the third-party banking service, handling authentication, data access, and code. With MCP, the banking service exposes that lookup as a tool on its server, the Agentforce MCP client registers the server, and the tool appears as a callable action the agent can select. The agent searches Salesforce for the contact's details, calls the tool, receives the risk score, and uses it in the reply, all without a bespoke integration written for that one system.[^1] That is the difference MCP is bought for: one standard replaces the custom glue you would otherwise write, secure, and maintain for every pair of systems.

### A2A is delegation among peers: it gives an agent a colleague

The Agent-to-Agent Protocol, A2A, is an open protocol for agent-to-agent communication that enables agents from different vendors or platforms to discover, invoke, and collaborate with each other.[^4] Salesforce was a founding member of the effort alongside Google, Microsoft, SAP, and AWS, which is the strongest signal that this is a cross-vendor standard rather than a Salesforce-only construct.[^4] Its purpose is delegation among peers: agents publish an Agent Card, a machine-readable description of their capabilities, other agents discover those cards, and the agents then communicate to hand work back and forth.

Salesforce describes that communication as LLM-native, unstructured dialogue over OAuth 2.0 and HTTP/JSON, which is a conversation between agents rather than a rigid function signature.[^4] Where MCP connects an agent to a tool, A2A connects an agent to another agent that reasons and plans on its own. Trailhead frames the same idea in plainer words: A2A is one agent handing work directly to another agent, automatically and without a human intermediary, so several agents complete a task as a single workflow.[^5] The phrase to keep is that the peer owns part of the thinking. That is what makes it an agent and not a tool.

Think about what has to be true for two agents to work together without a shared codebase. They may be written in different frameworks, by different vendors, and to different internal designs, and neither can see inside the other. A2A handles that by making the boundary explicit: each agent publishes what it can do, authenticates the caller, and exchanges messages about a shared task while keeping its own reasoning, memory, and tools private. The point of the standard is that the two agents never need to share internals, only a declared contract. That is why A2A is described as working between opaque agents, and it is why the protocol fits cross-vendor collaboration rather than two agents inside one org, which SOMA already connects through descriptions. The card is the published half; everything behind it stays the peer's own business.

### The rule of thumb: a tool means MCP, an agent means A2A

The rule of thumb that resolves most exam items is simple to state and worth memorising: if the remote thing is modelled as a capability or a tool, use MCP, and if it is modelled as a collaborating agent, use A2A.[^3] A system that simply does something on request, such as retrieve a document or run a workflow, is a tool and MCP is the fit. A system that owns part of the reasoning or the planning, and that you want to delegate a sub-task to as a peer, is an agent and A2A is the fit.

Salesforce states the same distinction in its interoperability guidance, recommending MCP when the remote thing is a capability or a tool and A2A when the remote thing is truly an agent partner.[^3] The distinction is about what sits on the other side, not about which product you happen to use, and the exam uses that framing repeatedly. So before you answer a scenario, ask what the remote system is expected to do: if it returns a result you requested, it is a tool; if it decides how to do the work, it is a peer.

![MCP compared with A2A across purpose, remote side, discovery, roles, wire protocol, and origin: a tool means MCP, a peer means A2A](</diagrams/day-60-ma-2a-open-standards-for-multi-agent-the-purpose-of-mcp/2-mcp-vs-a2a.png>)

Apply the test to the systems a real engagement always contains. A search index, a document store, a payments API, and a workflow engine are tools, because each performs a function you ask for and returns a result, so they belong on MCP. A vendor's customer-support agent, a partner's scheduling assistant, or a platform's research agent are peers, because each reasons about how to fulfil the request and returns a judgement, so they belong on A2A. The failure mode, both in a scenario and in a build, is picking the protocol by which company owns the remote system rather than by what that system does, and that is precisely the error the exam is written to catch.

### The protocols show up in both directions

The protocols appear in an Agentforce architecture on two edges and in both directions.[^3] For MCP, the Agentforce MCP Client lets the org consume external tools as agent actions, and a hosted or custom MCP server lets external hosts such as another copilot or an LLM platform call Agentforce capabilities through the same standard, so Agentforce can be a tool to someone else.[^2] For A2A, outbound A2A lets an Agentforce agent delegate to an external agent, and inbound A2A lets an external agent or orchestrator call an Agentforce agent as an expert.

![Agentforce in the center with four edges: MCP client outbound to external tools, hosted MCP server inbound, outbound A2A delegation, and inbound A2A calls](</diagrams/day-60-ma-2a-open-standards-for-multi-agent-the-purpose-of-mcp/3-both-directions.png>)

Salesforce's interoperability guidance works through each of these as a named pattern: the MCP client for using external capabilities, outbound A2A for collaborating with an external agent, inbound A2A for letting an external agent call an Agentforce agent, and Agentforce as an MCP server for letting external hosts consume the org in a standardised way.[^3] Read that as one idea in two directions: the same standards that extend what Agentforce can reach also extend who can reach Agentforce. A design that only ever uses one direction is using half of what the protocols offer.

The two-directional view also explains why a single integration can pay off twice. Once an external capability is exposed as a tool, any MCP-compatible client can reach it, and once an Agentforce capability is exposed as a tool through a hosted server, any compliant host can call the org. The same logic holds for peers: an external agent registered for outbound delegation can also be the caller for inbound work when the arrangement is reciprocal. Designing for both directions up front is cheaper than adding the second direction after the first has shipped, because the registration and authentication choices are made once and reused.

### Open standards keep Salesforce the central brain while extending it

Why open standards matter to the business is the same reason they matter to the architecture. An open protocol keeps Salesforce as a central brain while extending its capability, instead of forcing you to rebuild Salesforce logic inside every external system.[^3] It reduces lock-in, because a standard endpoint is reachable by any compliant client rather than by one vendor. It also gives the architecture a governance story: when the remote thing is a tool you register it as a tool, and when it is an agent you register it as a partner with declared skills and transport protocols, so the crossing is configured and reviewed rather than improvised.[^3]

That is the answer to a purpose question, and it is also the reason the protocols are tested at all, even though the official prep trail does not otherwise cover them. A consultant who can explain that open standards protect the org's position while extending its reach is answering the business question, not just the technical one.

### Hold each purpose as a single sentence

Hold the purpose of each protocol as a single sentence, because the exam often asks for exactly that. MCP exists so that an agent can use the capabilities of any system that can describe them as tools, without a custom integration for each one. A2A exists so that an agent can collaborate with a peer agent on another platform or from another vendor, discovering its capabilities and delegating work to it under a governed handshake. Salesforce, as a founding member of the A2A effort, treats both as the interoperability layer that sits above single-org orchestration.[^4] When a scenario asks about purpose, name the direction of the connection: capability into the agent is MCP, and collaboration with a peer is A2A.

## Exam Traps

Three traps dominate this objective. The first is believing MCP and A2A are Salesforce proprietary. Both are open standards, with MCP originally created by Anthropic and Salesforce a founding member of the A2A effort alongside Google, Microsoft, SAP, and AWS, so an answer that calls either one Salesforce-only is wrong. The second trap is believing MCP is how agents talk to each other. MCP connects an agent to tools, data, and APIs, while it is A2A that connects agents to peer agents, so an answer that uses MCP for agent delegation has the two swapped. The third trap is believing the choice between the protocols depends on the vendor. The rule is whether the remote thing is a tool or an agent, so a scenario that picks a protocol by vendor rather than by what sits on the other side is wrong.

## What a consultant should walk away with

Carry two sentences and one test. MCP is the open standard, originally created by Anthropic, that lets an agent use any system that can describe its capabilities as tools, with servers exposing tools, prompts, and resources. A2A is the open protocol, co-founded by Salesforce alongside Google, Microsoft, SAP, and AWS, that lets an agent discover a peer through its Agent Card and delegate work to it as a colleague. The test is what sits on the other side: a tool that does what you ask is MCP, and a peer that owns part of the reasoning is A2A. Then remember that both protocols cut both ways in an Agentforce architecture, so the org can consume external capabilities and be consumed as one, and keep the business reason handy: an open standard extends Salesforce's reach without rebuilding its logic elsewhere or locking the org to a single vendor.
